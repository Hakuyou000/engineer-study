# CCNA テキスト 1.0 ネットワークインフラストラクチャと接続(25%)

対象: 200-301 CCNA v2.0

ケーブルとインターフェース、仮想化、IPv4 と IPv6 のアドレス、無線 LAN、クライアントの接続の問題、DHCP を学びます。すべての分野の土台になる部分です。

## 1.1 インターフェースとケーブルの障害診断

出題範囲: コリジョン、エラー、デュプレックスの不一致、速度、距離、インターフェース、信号のレベル、ピンの配列、ケーブルの種類(銅線・光ファイバー)。

### 1. イーサネットの規格

| 規格 | IEEE | 速度 | 媒体 | 最大の距離 |
|---|---|---|---|---|
| 10BASE-T | 802.3 | 10 Mbps | UTP Cat3 以上 | 100 m |
| 100BASE-TX | 802.3u | 100 Mbps | UTP Cat5 以上 | 100 m |
| 1000BASE-T | 802.3ab | 1 Gbps | UTP Cat5e 以上 | 100 m |
| 1000BASE-SX | 802.3z | 1 Gbps | マルチモードファイバー(MMF) | 220〜550 m |
| 1000BASE-LX | 802.3z | 1 Gbps | シングルモードファイバー(SMF。MMF も可) | SMF で 5 km |
| 10GBASE-T | 802.3an | 10 Gbps | UTP Cat6a(Cat6 は 55 m まで) | 100 m |
| 10GBASE-SR | 802.3ae | 10 Gbps | MMF | OM3 で 300 m / OM4 で 400 m |
| 10GBASE-LR | 802.3ae | 10 Gbps | SMF | 10 km |
| 10GBASE-ER | 802.3ae | 10 Gbps | SMF | 40 km |

Cisco の機器のインターフェースの名前は、速度によって `FastEthernet`(100 Mbps)、`GigabitEthernet`(1 Gbps)、`TenGigabitEthernet`(10 Gbps)となります。

### 2. 銅線(UTP)

| カテゴリ | 対応する速度 | 備考 |
|---|---|---|
| Cat5 | 100 Mbps | |
| Cat5e | 1 Gbps | |
| Cat6 | 1 Gbps(10 Gbps は 55 m まで) | |
| Cat6a | 10 Gbps | 100 m |

- コネクタは RJ-45 で、8 本の線(4 対)があります。
- 10BASE-T と 100BASE-TX は2対(ピン1,2 と 3,6)を使います。1000BASE-T は4対をすべて使い、両方向に同時に送受信します。
- ケーブルの長さは最大 100 m です。超えると信号が弱まり(減衰)、CRC エラーや切断が起きます。
- 電気のノイズ(EMI)が強い場所では、シールド付きの STP か、光ファイバーを使います。

**ピンの配列とケーブルの種類**

| 種類 | 両端の配列 | 用途 |
|---|---|---|
| ストレート | 同じ(T568B と T568B など) | 種類の違う機器の間。PC とスイッチ、ルーターとスイッチ |
| クロス | T568A と T568B(1↔3、2↔6 を入れ替える) | 同じ種類の機器の間。スイッチ同士、PC 同士、ルーター同士、PC とルーター |
| ロールオーバー | 1↔8、2↔7 … と完全に逆 | コンソールへの接続(RJ-45 とシリアル / USB) |

| 送信に使うピン | 機器 |
|---|---|
| 1,2 で送信(MDI) | PC、ルーター、サーバー、アクセスポイント |
| 3,6 で送信(MDI-X) | スイッチ、ハブ |

送信に使うピンが同じ機器同士はクロス、違う機器同士はストレートでつなぎます。**Auto-MDIX** が有効なら、どちらのケーブルでも機器が自動で合わせます。Auto-MDIX は、speed と duplex が auto のときに確実に動きます。

> **【ひっかけ】** PC とルーターは、どちらも MDI です。直接つなぐときはクロスケーブルを使います。「ルーターはネットワーク機器だからスイッチと同じ種類」ではありません。

### 3. 光ファイバー

| | マルチモード(MMF) | シングルモード(SMF) |
|---|---|---|
| コア(光が通る部分)の太さ | 50 / 62.5 µm | 9 µm |
| 光源 | LED、VCSEL | レーザー |
| 距離 | 短い(〜550 m 程度) | 長い(10 km 以上) |
| 費用 | 安い | 高い |
| 規格の例 | SX、SR | LX、LR、ER |

- MMF は光が何通りもの経路で進む(モード分散)ため、長い距離には向きません。
- コネクタは LC(小型で、SFP でよく使われる)や SC です。送信(TX)と受信(RX)で2本のファイバーを使います。
- トランシーバー(光と電気を変換する部品): SFP(1G)、SFP+(10G)、SFP28(25G)、QSFP+(40G)、QSFP28(100G)。
- 電気のノイズの影響を受けず、盗聴されにくい特徴があります。

**光ファイバーの障害**

| 原因 | 症状 |
|---|---|
| 送信(TX)と受信(RX)のファイバーが逆 | リンクが上がらない |
| MMF 用と SMF 用のトランシーバーやケーブルが合っていない | リンクが上がらない、エラーが多い |
| 両端のトランシーバーの規格や波長が違う(SR と LR など) | リンクが上がらない |
| 距離の超過、ファイバーの曲げすぎ、端面の汚れ | 受信する光が弱くなる、CRC エラー |
| 短い距離で長距離用(ER など)を使う | 受信する光が強すぎる。アッテネーター(減衰器)が必要 |

光の強さ(信号のレベル)は dBm で表します。`show interfaces transceiver` で、送信の強さ(Tx Power)と受信の強さ(Rx Power)、警告のしきい値(high/low alarm、warning)を確認できます(DOM に対応したトランシーバーの場合)。

```
Switch# show interfaces te1/0/1 transceiver
                 Optical   Optical
       Temp      Tx Power  Rx Power
Port   (Celsius) (dBm)     (dBm)
Te1/0/1  31.2     -2.3     -18.9
```

Rx Power が low alarm のしきい値を下回っていたら、ケーブル、コネクタ、距離を疑います。

### 4. 速度とデュプレックス

| | 半二重(half) | 全二重(full) |
|---|---|---|
| 送信と受信 | 同時にできない | 同時にできる |
| CSMA/CD(衝突を検出する仕組み) | 使う | 使わない |
| コリジョン(衝突) | 起きる | 起きない |
| 相手 | ハブ | スイッチ、ルーター、PC |

**オートネゴシエーション**(IEEE 802.3u): 両端が対応している中で、最も速い速度とデュプレックスを自動で選びます。

片方だけオートネゴシエーションを無効にした(固定で設定した)場合:

- 速度: auto の側は、電気信号から検出できます。
- デュプレックス: 検出できません。auto の側は、10/100 Mbps なら **half**、1000 Mbps なら full を選びます。

その結果、片方が full の固定、反対側が auto(half になる)という **デュプレックスの不一致** が起きます。リンクは up のままですが、通信が極端に遅くなります。

| 側 | 増えるカウンタ |
|---|---|
| half の側 | collisions、**late collisions** |
| full の側 | **CRC**、runts、input errors(FCS のエラー) |

```
interface GigabitEthernet0/1
 speed 100
 duplex full
```

> **【原則】** 両端とも auto にするか、両端とも同じ値に固定します。片方だけを固定してはいけません。

速度が一致しない場合は、リンクが上がりません(down/down)。

```
  Hardware is Gigabit Ethernet, address is 0c1a.2b3c.4d01
  MTU 1500 bytes, BW 1000000 Kbit/sec, DLY 10 usec,
     reliability 255/255, txload 1/255, rxload 1/255
  Full-duplex, 1000Mb/s, media type is 10/100/1000BaseTX
  5 minute input rate 1000 bits/sec, 2 packets/sec
     1200 packets input, 98000 bytes, 0 no buffer
     0 runts, 0 giants, 0 throttles
     0 input errors, 0 CRC, 0 frame, 0 overrun, 0 ignored
     2400 packets output, 180000 bytes, 0 underruns
     0 output errors, 0 collisions, 1 interface resets
     0 late collision, 0 deferred
```

**1 行目(物理層 / データリンク層の状態)**

| 表示 | show interfaces status での表示 | 意味・原因 |
|---|---|---|
| up / up | connected | 正常 |
| administratively down / down | disabled | `shutdown` されている |
| down / down | notconnect | ケーブルがつながっていない、断線、相手が shutdown、速度の不一致 |
| down / down (err-disabled) | err-disabled | ポートセキュリティの違反、BPDU ガードなどで自動で止められた |
| up / down | — | L2 の問題。カプセル化の不一致、キープアライブが届かない(主にシリアル) |

**カウンタ**

| カウンタ | 意味 | 主な原因 |
|---|---|---|
| runts | 64 バイト未満の短すぎるフレーム | コリジョン、デュプレックスの不一致、NIC の故障 |
| giants | 最大の長さ(1518 バイト。VLAN タグ付きは 1522)を超えたフレーム | MTU の不一致、NIC の故障 |
| CRC | FCS(誤り検出の値)が合わない | ケーブルの不良、ノイズ、距離の超過、デュプレックスの不一致 |
| input errors | runts、giants、CRC、frame、overrun、ignored などの合計 | |
| frame | バイトの区切りが合わない不正なフレーム | コリジョン、物理層の不良 |
| collisions | コリジョンの回数 | 半二重では、ある程度は正常に起きる |
| late collisions | 最初の 64 バイト(512 ビット)を送った後のコリジョン | **デュプレックスの不一致**、ケーブルの長さの超過 |
| output errors | 送信の失敗の合計 | コリジョンが多すぎる |
| input queue drops / output drops | 待ち行列(キュー)があふれた | 混雑、処理能力の超過 |
| interface resets | インターフェースがリセットされた回数 | |

関連するコマンド:

```
show interfaces status              ! ポートの一覧。状態、VLAN、デュプレックス、速度
show ip interface brief             ! IP アドレスと状態の一覧
show interfaces g0/1 counters errors
show controllers ethernet-controller g0/1
clear counters g0/1                 ! カウンタを消して、増え方を見る
```

`show interfaces status` の Duplex 列と Speed 列にある `a-full`、`a-1000` の `a-` は、オートネゴシエーションで決まった値であることを表します。

> **【1.1 まとめ】**
>
> - 同じ種類(送信のピンが同じ)の機器はクロス、違う種類はストレート。PC とルーターはクロス
> - MMF は短い距離で安い。SMF は長い距離でレーザーを使う
> - 片方を固定し、片方を auto にすると、auto の側は half になり(10/100 Mbps)、デュプレックスの不一致が起きる
> - late collisions は half の側、CRC と runts は full の側に出る
> - administratively down は shutdown、err-disabled は保護機能による停止
> - 光の信号のレベルは `show interfaces transceiver` の Rx Power で確認する

## 1.2 ハイパーバイザー、仮想マシン、コンテナ

### 1. サーバーの仮想化

1台の物理サーバー(ホスト)の上で、複数の仮想マシン(VM)を動かす技術です。CPU、メモリ、ストレージ、NIC を **ハイパーバイザー** が仮想的に分けて、それぞれの VM に割り当てます。

| 種類 | 動く場所 | 例 | 用途 |
|---|---|---|---|
| Type 1(ベアメタル、ネイティブ) | ハードウェアの上で直接動く | VMware ESXi、Microsoft Hyper-V、KVM、Xen | データセンター、本番の環境 |
| Type 2(ホスト型) | ホスト OS の上で動く | VirtualBox、VMware Workstation / Fusion | 検証、個人での利用 |

ハイパーバイザーの 2 つの種類を、重ね方の違いで比べます。

```text
Type 1                     Type 2
[VM] [VM]                  [VM] [VM]
[Hypervisor]               [Hypervisor]
[Hardware]                 [Host OS]
                           [Hardware]
```

Type 1 は、ハードウェアの上でハイパーバイザーが直接動きます。Type 2 は、ホスト OS の上でハイパーバイザーが動きます。

Type 1 はホスト OS を通さないので、処理の無駄(オーバーヘッド)が小さくなります。

### 2. 仮想マシン(VM)

- VM ごとに、**ゲスト OS**(カーネルを含む)を持ちます。
- 仮想の NIC(vNIC)を持ち、ハイパーバイザーの中の **仮想スイッチ(vSwitch)** につながります。
- 仮想スイッチは、物理 NIC(アップリンク)を通して物理スイッチにつながります。複数の VLAN を通すので、物理スイッチ側は普通トランクにします(→ 2.2)。
- 利点: サーバーの集約、互いの分離、スナップショット、動かしたままの移動(ライブマイグレーション)、すばやい展開。

```text
[VM1]  [VM2]  [VM3]     それぞれにゲスト OS と vNIC がある
  |      |      |
[      vSwitch      ]   ハイパーバイザーの中の仮想スイッチ
          |
[       NIC         ]   物理 NIC(アップリンク)
          |
          |             トランク(複数の VLAN を通す)
          |
[      switch       ]   物理スイッチ
```

### 3. コンテナ

- ホスト OS の **カーネルを共有** し、アプリケーションと、それが必要とするもの(ライブラリなど)だけをまとめて分離します。
- ゲスト OS を持たないので軽く、数秒で起動します。
- コンテナエンジン(Docker、containerd、Podman)がコンテナを動かします。たくさんのコンテナの管理には、Kubernetes などのオーケストレーターを使います。
- Linux の namespace(分離)と cgroups(資源の制限)という機能で実現しています。
- イメージという形で配布するので、環境による違いが出にくくなります。

| | 仮想マシン | コンテナ |
|---|---|---|
| 分離の単位 | ハードウェアを仮想化する | OS を仮想化する(プロセスを分離する) |
| OS | VM ごとにゲスト OS を持つ | ホストのカーネルを共有する |
| 大きさ | GB 単位 | MB 単位 |
| 起動 | 分単位 | 秒単位 |
| 分離の強さ | 強い | VM より弱い |
| 異なる OS | 動かせる(Linux の上で Windows など) | ホストと同じ系統のカーネルだけ |
| 集約できる数 | 少ない | 多い |

仮想マシンとコンテナを、重ね方の違いで比べます。

```text
VM                                  Container
[App A]      [App B]                [App A]      [App B]
[Guest OS A] [Guest OS B]           [Container engine]
[Hypervisor]                        [Host OS (kernel)]
[Hardware]                          [Hardware]
```

仮想マシンは、それぞれがゲスト OS を持ちます。コンテナは、ホスト OS のカーネルを共有します。

> **【ひっかけ】** コンテナは、ハイパーバイザーがなくても動きます。必要なのはコンテナエンジンです。「コンテナごとにゲスト OS を持つ」は誤りです。

### 4. ネットワーク機能の仮想化

- ルーター、ファイアウォール、WLC などを、VM やコンテナとして動かせます(仮想アプライアンス、NFV)。例: Catalyst 8000V。
- **VRF**: 1台のルーターの中で、ルーティングテーブルを論理的に分ける技術です。サーバーの仮想化とは別の「ネットワークの仮想化」です。

> **【1.2 まとめ】**
>
> - Type 1 はハードウェアの上で直接、Type 2 はホスト OS の上で動く
> - VM はゲスト OS を持つ。コンテナはホストのカーネルを共有する
> - VM は vNIC → vSwitch → 物理 NIC の順に外部とつながる
> - コンテナは軽くて起動が速い。VM は分離が強い

## 1.3 IPv4 アドレスの設定・割り当て・サブネット化のトラブルシュート

### 1. 基礎

- IPv4 アドレスは 32 ビットで、ネットワーク部とホスト部をサブネットマスク(プレフィックス長)で分けます。
- ホスト部がすべて 0 のものはネットワークアドレス、すべて 1 のものはブロードキャストアドレスです。どちらもホストには割り当てません。

| クラス | 先頭のオクテット | 既定のマスク | 用途 |
|---|---|---|---|
| A | 1〜126 | /8 | |
| B | 128〜191 | /16 | |
| C | 192〜223 | /24 | |
| D | 224〜239 | — | マルチキャスト |
| E | 240〜255 | — | 実験用 |

0.0.0.0/8 と 127.0.0.0/8 は特別な用途に使われます。

**プライベートアドレス(RFC 1918)**

| 範囲 | CIDR |
|---|---|
| 10.0.0.0 〜 10.255.255.255 | 10.0.0.0/8 |
| 172.16.0.0 〜 172.31.255.255 | 172.16.0.0/12 |
| 192.168.0.0 〜 192.168.255.255 | 192.168.0.0/16 |

プライベートアドレスは、インターネットではルーティングされません。外に出るには、NAT でパブリック(グローバル)アドレスに変換します。

| 特別なアドレス | 意味 |
|---|---|
| 127.0.0.0/8 | ループバック(自分自身) |
| 169.254.0.0/16 | リンクローカル(APIPA)。DHCP でアドレスを取得できなかったときに自動で付く |
| 0.0.0.0 | 未指定。デフォルトルートのあて先 |
| 255.255.255.255 | リミテッドブロードキャスト(自分のネットワークの全員あて) |
| 100.64.0.0/10 | キャリアグレード NAT 用の共有アドレス |
| 192.0.2.0/24、198.51.100.0/24、203.0.113.0/24 | 文書や例で使うためのアドレス |

### 2. サブネットの計算

| プレフィックス | マスク | ブロックの大きさ | ホストの数 |
|---|---|---|---|
| /24 | 255.255.255.0 | 256 | 254 |
| /25 | 255.255.255.128 | 128 | 126 |
| /26 | 255.255.255.192 | 64 | 62 |
| /27 | 255.255.255.224 | 32 | 30 |
| /28 | 255.255.255.240 | 16 | 14 |
| /29 | 255.255.255.248 | 8 | 6 |
| /30 | 255.255.255.252 | 4 | 2 |
| /31 | 255.255.255.254 | 2 | 2(ポイントツーポイント専用。RFC 3021) |
| /32 | 255.255.255.255 | 1 | 1(ホストルート、ループバック) |

第3オクテットで区切る場合も、考え方は同じです。

| プレフィックス | マスク | 第3オクテットのブロック | ホストの数 |
|---|---|---|---|
| /16 | 255.255.0.0 | 256 | 65,534 |
| /17 | 255.255.128.0 | 128 | 32,766 |
| /18 | 255.255.192.0 | 64 | 16,382 |
| /19 | 255.255.224.0 | 32 | 8,190 |
| /20 | 255.255.240.0 | 16 | 4,094 |
| /21 | 255.255.248.0 | 8 | 2,046 |
| /22 | 255.255.252.0 | 4 | 1,022 |
| /23 | 255.255.254.0 | 2 | 510 |

> **【手順】** 例: 172.16.45.200/20
> ① /20 は第3オクテットで区切ります。ブロックの大きさは 256 − 240 = 16 です。
> ② 16 の倍数は 0、16、32、48 … で、45 は 32〜47 の範囲に入ります。
> ③ ネットワークアドレスは 172.16.32.0、ブロードキャストアドレスは 172.16.47.255 です。
> ④ ホストの範囲は 172.16.32.1 〜 172.16.47.254 で、ホストの数は 2 の 12 乗 − 2 = 4,094 です。

例の 172.16.45.200/20 を、ビットで見ます。マスクの 1 の部分がネットワーク部、0 の部分がホスト部です。

```text
address    10101100.00010000.00101101.11001000
mask /20   11111111.11111111.11110000.00000000
           |<- network 20 bits ->|< host 12 ->
network    10101100.00010000.00100000.00000000   = 172.16.32.0
broadcast  10101100.00010000.00101111.11111111   = 172.16.47.255
```

ネットワーク部は変えず、ホスト部をすべて 0 にするとネットワークアドレス、すべて 1 にするとブロードキャストアドレスになります。

- ホストの数: 2 の(ホスト部のビット数)乗 − 2
- サブネットの数: 2 の(借りたビット数)乗
- 必要なホストの数からプレフィックスを決める: 50 台なら 2 の 6 乗 − 2 = 62 ≥ 50 なので、ホスト部は 6 ビットで /26 になります。

### 3. VLSM

VLSM は、サブネットごとに違う長さのマスクを使い、アドレスを無駄なく割り当てる方法です。**大きいサブネットから順に** 割り当てます。

例: 192.168.10.0/24 を、100 台、50 台、20 台の LAN と、ルーター同士をつなぐ2本のリンクに分けます。

| 用途 | 必要な数 | 割り当て | 範囲 |
|---|---|---|---|
| LAN A | 100 | 192.168.10.0/25 | .0 〜 .127 |
| LAN B | 50 | 192.168.10.128/26 | .128 〜 .191 |
| LAN C | 20 | 192.168.10.192/27 | .192 〜 .223 |
| リンク1 | 2 | 192.168.10.224/30 | .224 〜 .227 |
| リンク2 | 2 | 192.168.10.228/30 | .228 〜 .231 |

```
!
```

### 5. よくある障害

| 症状 | 原因 |
|---|---|
| 同じ LAN の一部のホストとだけ通信できない | サブネットマスクの誤り。相手を別のネットワークだと判断している |
| 同じ LAN は通るが、外に出られない | デフォルトゲートウェイの誤り、または未設定。ゲートウェイが別のサブネットのアドレスになっている |
| ときどき切れる。`%IP-4-DUPADDR` のログ | IP アドレスの重複 |
| `% 192.168.1.0 overlaps with GigabitEthernet0/0` | 同じルーターの別のインターフェースとサブネットが重なっている |
| `Bad mask /24 for address 192.168.1.0` | ネットワークアドレスやブロードキャストアドレスを、ホストに設定しようとした |
| ホストのアドレスが 169.254.x.x | DHCP サーバーに届いていない |
| インターフェースが administratively down | `no shutdown` のし忘れ(ルーターの物理ポートは、最初は shutdown になっている) |
| 外部と通信できない(内部は通る) | プライベートアドレスのまま。NAT が設定されていないか、誤っている |

> **【ひっかけ】** ホストとゲートウェイのマスクが違うと、片方向だけ通ることがあります。10.1.1.200/24 のホストと 10.1.1.1/25 のルーターでは、ルーターは 10.1.1.200 を自分のサブネットの外だと判断し、直接返信できません。

> **【1.3 まとめ】**
>
> - ブロックの大きさ = 256 − マスクの値。その倍数がネットワークアドレスになる
> - ホストの数は 2 の n 乗 − 2。/30 は 2 台、/31 はポイントツーポイント専用で 2 台
> - VLSM は大きいサブネットから割り当てる
> - プライベートアドレス: 10/8、172.16/12、192.168/16
> - 169.254.x.x は DHCP の失敗
> - マスクの誤り、ゲートウェイの誤り、重複、overlaps がよくある原因

## 1.4 IPv6 アドレスの設定・割り当て・プレフィックスサイズのトラブルシュート

### 1. 書き方

IPv6 アドレスは 128 ビットで、16 ビットずつ8つのブロックを 16 進数で書き、`:` で区切ります。

- 各ブロックの先頭の 0 は省略できます。
- 0 だけのブロックが続く部分は、`::` に置き換えられます。使えるのは **1か所だけ** です。
- `::` を使える場所が複数あるときは、最も長い 0 の連続に使います。同じ長さなら左側に使います(RFC 5952)。

```
2001:0db8:0000:0000:00a0:0000:0000:0001
→ 2001:db8::a0:0:0:1
```

### 2. アドレスの種類

| 種類 | プレフィックス | 説明 |
|---|---|---|
| グローバルユニキャスト(GUA) | 2000::/3 | インターネットで一意のアドレス。IPv4 のパブリックアドレスにあたる |
| ユニークローカル(ULA) | fc00::/7(実際に使うのは fd00::/8) | 組織の中で使うアドレス。IPv4 のプライベートアドレスにあたる |
| リンクローカル(LLA) | fe80::/10 | 同じリンクの中だけで使える。ルーターは転送しない。IPv6 が有効なインターフェースには必ず付く |
| マルチキャスト | ff00::/8 | グループあて |
| エニーキャスト | (ユニキャストと同じ範囲) | 複数の機器に同じアドレスを付け、最も近い1台に届ける |
| ループバック | ::1/128 | 自分自身 |
| 未指定 | ::/128 | アドレスを取得する前の送信元 |
| デフォルトルート | ::/0 | |
| 文書用 | 2001:db8::/32 | 例で使うためのアドレス |

IPv6 には **ブロードキャストがありません**。

**主なマルチキャストアドレス**

| アドレス | あて先 |
|---|---|
| ff02::1 | リンク上のすべてのノード |
| ff02::2 | リンク上のすべてのルーター |
| ff02::5 / ff02::6 | OSPFv3 のすべてのルーター / DR と BDR |
| ff02::1:2 | DHCPv6 のサーバーとリレー |
| ff02::1:ffXX:XXXX | 要請ノードマルチキャスト。ユニキャストアドレスの下位 24 ビットから作る。NS のあて先 |

### 3. プレフィックスの大きさ

| プレフィックス | 用途 |
|---|---|
| /32 | ISP への割り当て(一般的) |
| /48 | 1つの拠点(組織)への割り当て。/64 を 65,536 個作れる |
| /56 | 小さな拠点。/64 を 256 個作れる |
| **/64** | 1つの LAN(サブネット)。SLAAC と EUI-64 は /64 が前提 |
| /127 | ルーター同士をつなぐポイントツーポイントのリンク(RFC 6164) |
| /128 | ホストルート、ループバック |

GUA の構造(/48 が割り当てられた場合): グローバルルーティングプレフィックス 48 ビット + サブネット ID 16 ビット + インターフェース ID 64 ビット。

例のアドレスで、3 つの部分の位置を示します。

```text
2001:0db8:acad:0001:0e1a:2bff:fe3c:4d5e
^^^^^^^^^^^^^^ ^^^^ ^^^^^^^^^^^^^^^^^^^
|              |    |
|              |    +-- インターフェース ID(64 ビット)
|              +------- サブネット ID(16 ビット)
+---------------------- グローバルルーティングプレフィックス(48 ビット)
```

LAN ごとにサブネット ID を変えて、/64 のサブネットを作ります。

サブネットは 4 ビット(16 進数の1桁。ニブル)単位で分けると読みやすくなります。

```
2001:db8:acad::/48 から /64 を切り出す
2001:db8:acad:0000::/64
2001:db8:acad:0001::/64
 …
2001:db8:acad:ffff::/64
```

> **【ひっかけ】** /64 以外のプレフィックスでは、SLAAC が動きません。「LAN に /65 より長いプレフィックスを設定したら、ホストが自動でアドレスを作れない」という問題に注意します。

### 4. Modified EUI-64

48 ビットの MAC アドレスから、64 ビットのインターフェース ID を作る方法です。

1. MAC アドレスを、前半 24 ビットと後半 24 ビットに分けます。
2. 真ん中に `fffe` を入れます。
3. 先頭から7番目のビット(U/L ビット)を反転します。

```
MAC:      0c1a.2b3c.4d5e
① fffe を入れる: 0c1a:2bff:fe3c:4d5e
② 7 ビット目を反転: 0c = 0000 1100 → 0000 1110 = 0e
IF ID:    0e1a:2bff:fe3c:4d5e
アドレス: 2001:db8:1:1:e1a:2bff:fe3c:4d5e
```

> **【計算のコツ】** 先頭のバイトの2桁目(16 進数)に注目します。7 番目のビットは「2 の位」です。2 桁目が 0,1,4,5,8,9,c,d なら 2 を足し、2,3,6,7,a,b,e,f なら 2 を引きます。
> 例: `00` → `02`、`0c` → `0e`、`a6` → `a4`、`52` → `50`

真ん中に `ff:fe` があれば、EUI-64 で作られたアドレスだと分かります。

### 5. IOS での設定

```
ipv6 unicast-routing                          ! IPv6 のルーティングを有効にする(RA の送信も始まる)
!
interface GigabitEthernet0/0
 ipv6 address 2001:db8:1:1::1/64              ! 手動で設定する
 ipv6 address 2001:db8:1:1::/64 eui-64        ! プレフィックスは手動、インターフェース ID は EUI-64
 ipv6 address fe80::1 link-local              ! リンクローカルアドレスを手動で決める
 ipv6 address autoconfig                      ! SLAAC で取得する
 ipv6 address dhcp                            ! DHCPv6 で取得する
 ipv6 enable                                  ! リンクローカルアドレスだけを作る
 no shutdown
```

- グローバルアドレスを設定すると、リンクローカルアドレスは自動で作られます(既定は EUI-64)。
- 1つのインターフェースに、複数の IPv6 アドレスを持てます。`ipv6 address` を追加しても上書きされません(IPv4 では `secondary` が必要です)。
- `ipv6 unicast-routing` がないと、ルーターは IPv6 のパケットを転送せず、RA も送りません。自分あての通信はできます。

```
Router# show ipv6 interface brief
GigabitEthernet0/0     [up/up]
    FE80::E1A:2BFF:FE3C:4D5E
    2001:DB8:1:1::1
```

```
show ipv6 interface g0/0      ! 参加しているマルチキャストグループや、ND の設定も表示する
show ipv6 route
show ipv6 neighbors           ! IPv4 の ARP テーブルにあたる
ping 2001:db8:1:1::2
ping fe80::2                  ! リンクローカルあては、出力インターフェースの指定を求められる
```

### 6. 近隣探索(NDP)とアドレスの自動設定

NDP は ICMPv6 を使います。IPv4 の ARP の役割も、NDP が担います。

| メッセージ | ICMPv6 のタイプ | 役割 |
|---|---|---|
| RS(Router Solicitation) | 133 | ホストがルーターに RA を求める。あて先は ff02::2 |
| RA(Router Advertisement) | 134 | ルーターがプレフィックスとデフォルトゲートウェイを知らせる。あて先は ff02::1。既定では 200 秒ごと |
| NS(Neighbor Solicitation) | 135 | MAC アドレスの問い合わせ(ARP 要求にあたる)、DAD |
| NA(Neighbor Advertisement) | 136 | NS への応答(ARP 応答にあたる) |

**DAD(重複アドレス検出)**: アドレスを使う前に、そのアドレスあてに NS を送ります。NA が返ってきたら、すでに誰かが使っています。

| 方式 | RA のフラグ | アドレス | DNS などの情報 |
|---|---|---|---|
| SLAAC | M=0、O=0 | RA のプレフィックス + 自分で作るインターフェース ID | RA(RDNSS)または手動 |
| ステートレス DHCPv6 | M=0、**O=1** | SLAAC | DHCPv6 |
| ステートフル DHCPv6 | **M=1** | DHCPv6 | DHCPv6 |

**デフォルトゲートウェイは、いつも RA から得ます**(ルーターのリンクローカルアドレス)。DHCPv6 はゲートウェイを配りません。

### 7. よくある障害

| 症状 | 原因 |
|---|---|
| ホストが SLAAC でアドレスを得られない | ルーターで `ipv6 unicast-routing` が設定されていない。プレフィックスが /64 ではない |
| リンクローカルアドレスしか持っていない | RA が届いていない。`ipv6 enable` だけを設定している |
| 同じリンクの中は通るが、他のセグメントに届かない | `ipv6 unicast-routing` が設定されていない。経路がない |
| アドレスに `[DUP]` と表示される | DAD で重複が見つかった。`show ipv6 interface` で確認する |
| アドレスが `[TEN]`(tentative、仮の状態)のまま | インターフェースが down、または DAD が終わっていない |
| 手動で設定したプレフィックスが隣の機器と違う | 入力の誤り。`::` の位置や桁の間違い |
| EUI-64 の結果が予想と違う | 7 番目のビットの反転を忘れている |

> **【1.4 まとめ】**
>
> - GUA は 2000::/3、ULA は fc00::/7、リンクローカルは fe80::/10、マルチキャストは ff00::/8
> - LAN は /64。SLAAC と EUI-64 は /64 が前提。ポイントツーポイントは /127
> - EUI-64: 真ん中に fffe を入れ、7 番目のビットを反転する
> - `ipv6 unicast-routing` がないと、転送も RA の送信もしない
> - RS は 133、RA は 134、NS は 135、NA は 136。ARP の代わりは NS と NA
> - ゲートウェイは RA から得る。M フラグはステートフル、O フラグはステートレス DHCPv6

## 1.5 無線の原理

### 1.5.a 周波数帯とチャネルの選び方

| 周波数帯 | 特徴 |
|---|---|
| 2.4 GHz | 遠くまで届き、障害物に強い。チャネルが少なく混みやすい。電子レンジや Bluetooth と干渉する |
| 5 GHz | チャネルが多く、速い。届く距離は短く、障害物に弱い。一部のチャネルは DFS(レーダーを避ける仕組み)の対象 |
| 6 GHz | Wi-Fi 6E 以降。使える幅が広く、干渉が少ない。WPA3 が必須 |

**2.4 GHz のチャネル**: チャネルの間隔は 5 MHz で、1つのチャネルの幅は 20 MHz(802.11b は 22 MHz)です。そのため、隣り合うチャネルは重なります。互いに重ならない組み合わせは **1、6、11** です。

**5 GHz のチャネル**: 20 MHz の幅で重ならないチャネルが多数あります(36、40、44、48 …)。チャネルボンディング(チャネルをまとめること)で 40 / 80 / 160 MHz の幅にすると速くなりますが、使えるチャネルの数が減り、干渉しやすくなります。

**チャネルの設計の原則**

- 隣り合うアクセスポイント(AP)は、重ならないチャネルにします。
- 電波の届く範囲(セル)は 10〜20% 重ね、移動したときの切り替え(ローミング)を滑らかにします。
- 2.4 GHz では 20 MHz の幅を使い、ボンディングはしません。
- 利用者が多い場所では送信の出力を下げ、セルを小さくします。

| 規格 | 世代の名前 | 周波数帯 | 最大の速度(理論値) | 主な技術 |
|---|---|---|---|---|
| 802.11b | — | 2.4 GHz | 11 Mbps | DSSS |
| 802.11a | — | 5 GHz | 54 Mbps | OFDM |
| 802.11g | — | 2.4 GHz | 54 Mbps | OFDM |
| 802.11n | Wi-Fi 4 | 2.4 / 5 GHz | 600 Mbps | MIMO、40 MHz |
| 802.11ac | Wi-Fi 5 | 5 GHz | 6.9 Gbps | MU-MIMO(下り)、160 MHz |
| 802.11ax | Wi-Fi 6 / 6E | 2.4 / 5 / 6 GHz | 9.6 Gbps | OFDMA、MU-MIMO(上りと下り) |
| 802.11be | Wi-Fi 7 | 2.4 / 5 / 6 GHz | 46 Gbps | MLO、320 MHz |

### 1.5.b 電波(RF)の性質

| 用語 | 意味 |
|---|---|
| 周波数 | 1 秒間の波の数(Hz)。高いほど波長が短く、弱まりやすい |
| 振幅 | 波の強さ |
| 吸収 | 壁、水、人の体などが電波のエネルギーを吸い取って弱める |
| 反射 | 金属やガラスで跳ね返る。マルチパスの原因になる |
| 屈折 | 密度の違うものを通るときに曲がる |
| 回折 | 障害物の端を回り込む |
| 散乱 | でこぼこの面で、ばらばらの方向に広がる |
| 減衰 | 距離や障害物で信号が弱まること |
| 自由空間伝搬損失 | 障害物がなくても、距離と周波数に応じて弱まること |

| 指標 | 意味 |
|---|---|
| dBm | 1 mW を基準にした電力の値。0 dBm = 1 mW |
| dB | 比べるための値。+3 dB で約 2 倍、+10 dB で 10 倍、−3 dB で約半分 |
| RSSI | 受信した信号の強さ。−50 dBm は強く、−80 dBm は弱い |
| ノイズフロア | 背景の雑音の強さ |
| SNR | 信号とノイズの差(dB)。大きいほど良い。25 dB 以上が目安 |
| EIRP | 送信の出力 + アンテナの利得 − ケーブルの損失 |

SNR = RSSI − ノイズフロア です。例えば RSSI が −65 dBm、ノイズが −90 dBm なら、SNR は 25 dB です。

**サービスセット(無線 LAN のまとまり)**

| 用語 | 意味 |
|---|---|
| SSID | 無線 LAN の名前 |
| BSS | 1台の AP と、それにつながるクライアントの集まり |
| BSSID | BSS を見分ける ID。AP の無線の MAC アドレス |
| ESS | 同じ SSID を持つ複数の BSS を、有線(DS)でつないだもの。ローミングできる |
| IBSS | AP を使わない端末同士のつながり(アドホック) |
| DS | AP 同士をつなぐ有線のネットワーク(ディストリビューションシステム) |

無線は半二重で、CSMA/CA(衝突を避ける仕組み)を使います。同じチャネルの端末は、帯域を分け合います。

### 1.5.c セキュリティのプロトコル

| 規格 | 暗号化 | 改ざんの検知 | 認証 | 評価 |
|---|---|---|---|---|
| WEP | RC4 | CRC | 共有鍵 | 破られている。使ってはいけない |
| WPA | TKIP(RC4) | MIC | PSK / 802.1X | 推奨されない |
| WPA2 | **AES-CCMP** | CBC-MAC | PSK / 802.1X | 今の最低限のライン |
| WPA3 | AES-GCMP / CCMP | GMAC | **SAE** / 802.1X | 推奨 |

| モード | 認証 | 用途 |
|---|---|---|
| パーソナル | WPA2 は PSK(4ウェイハンドシェイク)。WPA3 は SAE | 家庭、小規模の環境 |
| エンタープライズ | 802.1X / EAP。RADIUS サーバーでユーザーごとに認証する | 企業 |

**WPA3 の要点**

- SAE(Simultaneous Authentication of Equals): PSK に対する、パスワードの総当たりの推測(オフライン辞書攻撃)に強くなっています。
- 前方秘匿性(forward secrecy): 後でパスワードが漏れても、過去の通信は復号できません。
- PMF(管理フレームの保護。802.11w)が必須です。
- エンタープライズでは、192 ビットのモードを選べます。
- OWE(Enhanced Open): パスワードのないオープンな SSID でも、通信を暗号化します。
- WPA2/WPA3 の移行(混在)モード: どちらの端末もつなげられます。

**802.1X の3つの要素**: サプリカント(端末)、オーセンティケーター(AP や WLC)、認証サーバー(RADIUS)。EAP の種類には、PEAP、EAP-TLS(証明書を使う)、EAP-FAST などがあります。

### 1.5.d 干渉の原因

| 種類 | 内容 | 対策 |
|---|---|---|
| 同一チャネル干渉(CCI) | 近くの AP が同じチャネルを使う。互いに送信を待ち合うので遅くなる | チャネルを設計し直す、送信の出力を下げる |
| 隣接チャネル干渉(ACI) | 重なるチャネル(1 と 3 など)を使う。ノイズとして働くので、CCI より悪い | 1、6、11 だけを使う |
| Wi-Fi 以外の機器 | 電子レンジ、Bluetooth、コードレス電話、無線カメラ、ベビーモニター(主に 2.4 GHz) | 5 GHz / 6 GHz に移す、機器を離す |
| レーダー | 5 GHz の DFS チャネルで、気象や航空のレーダーを検出すると、AP はチャネルを変える | DFS ではないチャネルを使う |
| 物理的な障害物 | コンクリート、金属、水(水槽や人の体)、鏡 | AP の位置や台数を見直す |
| マルチパス | 反射した電波が時間差で届く | MIMO はこれを利用する。アンテナの配置を見直す |

> **【1.5 まとめ】**
>
> - 2.4 GHz の重ならないチャネルは 1、6、11。遠くまで届くが混みやすい
> - 5 GHz はチャネルが多く速いが、届きにくい。DFS がある
> - 周波数が高いほど弱まりやすい。+3 dB で 2 倍、+10 dB で 10 倍
> - SNR = RSSI − ノイズ。大きいほど良い
> - WEP(RC4)→ WPA(TKIP)→ WPA2(AES-CCMP)→ WPA3(SAE、GCMP、PMF が必須)
> - パーソナルは PSK / SAE、エンタープライズは 802.1X + RADIUS

## 1.6 有線・無線のクライアントの接続のトラブルシュート

出題範囲: Windows、macOS、Linux での IP の設定、到達性、無線のセキュリティの設定。

### 1. 確認のコマンド

| 目的 | Windows | macOS | Linux |
|---|---|---|---|
| IP の設定の表示 | `ipconfig`、`ipconfig /all` | `ifconfig`、`ipconfig getifaddr en0`、`networksetup -getinfo Wi-Fi` | `ip addr`、`ip -br addr` |
| DHCP のアドレスの返却と取り直し | `ipconfig /release`、`ipconfig /renew` | `sudo ipconfig set en0 DHCP` | `sudo dhclient -r` → `sudo dhclient`、`nmcli con up <名前>` |
| ルーティングテーブル | `route print`、`netstat -r` | `netstat -rn` | `ip route` |
| ARP テーブル | `arp -a` | `arp -a` | `ip neigh` |
| 到達の確認 | `ping`(4 回で止まる) | `ping`(止めるまで続く) | `ping`(止めるまで続く) |
| 経路 | `tracert`(ICMP) | `traceroute`(UDP) | `traceroute`(UDP)、`tracepath` |
| DNS の問い合わせ | `nslookup` | `nslookup`、`dig` | `dig`、`host`、`nslookup` |
| DNS の設定の表示 | `ipconfig /all` | `scutil --dns` | `resolvectl status`、`cat /etc/resolv.conf` |
| DNS のキャッシュの消去 | `ipconfig /flushdns` | `sudo dscacheutil -flushcache` | `resolvectl flush-caches` |
| 無線の状態 | `netsh wlan show interfaces` | Option キーを押しながら Wi-Fi のアイコンをクリック | `iw dev wlan0 link`、`nmcli dev wifi` |
| ポートと接続 | `netstat -an` | `netstat -an` | `ss -tln` |
| IPv6 の到達の確認 | `ping -6` | `ping6` | `ping -6` |

`ipconfig /all` で分かること: IPv4 アドレス、サブネットマスク、デフォルトゲートウェイ、DHCP が有効か、DHCP サーバー、リースの取得日時と期限、DNS サーバー、物理(MAC)アドレス。

`netsh wlan show interfaces` で分かること: SSID、BSSID、無線の規格(802.11ax など)、認証(WPA2-Personal など)、暗号、チャネル、電波の強さ(%)、受信・送信の速度。

### 2. 原因を絞り込む順番

| 段階 | 確認すること | 失敗したときに疑うもの |
|---|---|---|
| 1 | 物理・無線の接続(リンクのランプ、SSID への接続) | ケーブル、ポートの shutdown、VLAN、SSID と認証 |
| 2 | IP の設定(アドレス、マスク、ゲートウェイ、DNS) | DHCP、手動の設定の誤り |
| 3 | `ping 127.0.0.1` | TCP/IP の仕組み(スタック)そのもの |
| 4 | 自分の IP アドレスに ping | NIC |
| 5 | デフォルトゲートウェイに ping | LAN の中、VLAN、マスク |
| 6 | 外部の IP アドレスに ping(例: 8.8.8.8) | ルーティング、NAT、ACL |
| 7 | 名前で ping、または nslookup | DNS |
| 8 | アプリケーションのポート | ファイアウォール、サービスの停止 |

### 3. 症状と原因

| 症状 | 原因 |
|---|---|
| アドレスが 169.254.x.x | DHCP サーバーに届いていない。VLAN の誤り、リレーの設定がない、プールの枯渇、サーバーの停止 |
| アドレスは正しいが、ゲートウェイに ping が通らない | ポートの VLAN の誤り、マスクの誤り、ゲートウェイのアドレスの誤り |
| ゲートウェイには通るが、外に出られない | ルーター側の経路、NAT、ACL |
| IP アドレスでは通るが、名前では通らない | DNS サーバーの設定の誤り、DNS サーバーに届かない、レコードがない |
| ping の結果が「宛先ホストに到達できません」 | 経路がない、または同じサブネットの中で ARP の解決ができない |
| ping の結果が「要求がタイムアウトしました」 | 返信が戻ってこない。相手の停止、戻りの経路がない、ファイアウォール |
| 予想外のサブネットのアドレスを取得した | 不正な DHCP サーバー、ポートの VLAN の誤り |
| IPv6 がリンクローカル(fe80::)だけ | RA が届いていない |

### 4. 無線のクライアント特有の障害

| 症状 | 原因 |
|---|---|
| SSID が見えない | 周波数帯に対応していない(5 GHz 専用の SSID に 2.4 GHz だけの端末)、SSID のブロードキャストが無効、電波が届かない、WLAN が無効 |
| 認証に失敗する | PSK(パスフレーズ)の誤り。大文字と小文字も区別される |
| つながらない(古い端末) | セキュリティの方式が合っていない。WPA3 専用の SSID に WPA2 までの端末。PMF が必須の設定に対応していない |
| エンタープライズの認証に失敗する | ユーザー名やパスワードの誤り、EAP の方式の不一致、サーバーの証明書を信頼していない、端末の時刻のずれ、RADIUS サーバーに届かない |
| 接続済みだが「インターネットなし」と表示される | 認証には成功したが、DHCP に失敗している(169.254.x.x)。WLAN に対応する VLAN と DHCP を確認する |
| 遅い、切れる | RSSI や SNR が低い、同一チャネル干渉、Wi-Fi 以外の干渉、遅い速度で通信する端末がいる |
| 移動すると切れる | セルの重なりが足りない、ローミングの失敗 |

> **【1.6 まとめ】**
>
> - Windows は `ipconfig /all`、`tracert`、`netsh wlan show interfaces`
> - Linux は `ip addr`、`ip route`、`resolvectl`、`iw`
> - 近くから遠くへ: ループバック → 自分 → ゲートウェイ → 外部の IP → 名前
> - 169.254.x.x は DHCP の失敗
> - IP で通り、名前で通らない → DNS
> - 無線につながらないときは、PSK の誤り、方式の不一致(WPA2 と WPA3)、周波数帯の非対応を疑う

## 1.7 IOS 機器での DHCPv4 クライアント、サーバー、リレーのトラブルシュート

### 1. DHCP の動き(DORA)

DHCP は、IP アドレスなどの設定を自動でクライアントに配る仕組みです。

| 順番 | メッセージ | 方向 | あて先 |
|---|---|---|---|
| 1 | **D**iscover(サーバーを探す) | クライアント → サーバー | ブロードキャスト(255.255.255.255) |
| 2 | **O**ffer(アドレスを提案する) | サーバー → クライアント | ユニキャスト(またはブロードキャスト) |
| 3 | **R**equest(申し込む) | クライアント → サーバー | ブロードキャスト |
| 4 | **A**ck(承認する) | サーバー → クライアント | ユニキャスト(またはブロードキャスト) |

DORA のやり取りを、順に描きます。

```text
 Client                          Server
    |                               |
    |- Discover ------------------->|   サーバーを探す(ブロードキャスト)
    |<- Offer ----------------------|   アドレスを提案する
    |- Request -------------------->|   申し込む(ブロードキャスト)
    |<- Ack ------------------------|   承認する
```

- UDP を使います。サーバーは **67** 番、クライアントは **68** 番です。
- Discover の送信元の IP アドレスは 0.0.0.0 です(まだアドレスを持っていないため)。
- リースの更新: 期間の 50%(T1)でユニキャストの Request を、87.5%(T2)でブロードキャストの Request を送ります。
- その他のメッセージ: Nak(拒否)、Release(返却)、Decline(重複を見つけて辞退)、Inform。

配る情報: IP アドレス、サブネットマスク、デフォルトゲートウェイ、DNS サーバー、ドメイン名、リース期間、その他のオプション(150: TFTP サーバー / 43: WLC のアドレス など)。

### 2. サーバーの設定

```
ip dhcp excluded-address 192.168.10.1 192.168.10.10   ! 配らない範囲。グローバルコンフィグで書く
!
ip dhcp pool VLAN10
 network 192.168.10.0 255.255.255.0                   ! /24 と書いてもよい
 default-router 192.168.10.1
 dns-server 8.8.8.8 8.8.4.4
 domain-name example.com
 lease 7                                              ! 日 [時 分]。既定は 1 日
```

- `ip dhcp excluded-address` は、プールの中ではなく、グローバルコンフィグで設定します。
- サーバーは、要求を受けたインターフェース(またはリレーの giaddr)と同じサブネットのプールを選びます。
- アドレスを配る前に ping で使われていないかを確かめ、応答があれば conflict(重複)として記録します。

### 3. クライアントの設定

```
interface GigabitEthernet0/1
 ip address dhcp
 no shutdown
```

DHCP でデフォルトゲートウェイを受け取ると、ルーターは AD 254 のデフォルトルートを自動で登録します。

```
show dhcp lease
show ip interface brief      ! Method の列が DHCP になる
```

### 4. リレーエージェント

Discover はブロードキャストなので、ルーターを越えられません。サーバーが別のサブネットにあるときは、クライアント側のインターフェースにリレーを設定します。

```
interface GigabitEthernet0/0          ! クライアントがいる側(L3 スイッチなら SVI)
 ip address 192.168.10.1 255.255.255.0
 ip helper-address 10.1.1.5           ! DHCP サーバーのアドレス
```

- リレーは Discover を **ユニキャスト** に変えて、サーバーへ転送します。
- そのとき **giaddr**(ゲートウェイの IP アドレス)という欄に、受信したインターフェースのアドレスを入れます。サーバーは giaddr からプールを選び、giaddr あてに返信します。

リレーエージェントがあるときの流れです。数字は例です。

```text
 Client           Router(relay)            DHCP server
    |                   |                       |
    |- Discover ------->|                       |   ブロードキャスト
    |                   |- Discover ----------->|   ユニキャスト。giaddr = 192.168.10.1
    |                   |<- Offer --------------|   giaddr あてに返す
    |<- Offer ----------|                       |   クライアントに渡す
```

Request と Ack も、同じようにリレーを通ります。
- `ip helper-address` は DHCP 以外も転送します。既定では UDP の 37(Time)、49(TACACS)、53(DNS)、67 / 68(DHCP)、69(TFTP)、137 / 138(NetBIOS)です。

> **【ひっかけ】** `ip helper-address` を設定するのは **クライアント側** のインターフェースです。サーバー側ではありません。指定するのはサーバーのアドレスです。

### 5. 確認のコマンド

```
show ip dhcp binding               ! 貸し出し中のアドレスと MAC(クライアント ID)
show ip dhcp pool                  ! プールの範囲、貸し出し数、残り
show ip dhcp conflict              ! 重複が見つかったアドレス
show ip dhcp server statistics     ! メッセージの種類ごとの送受信の数
show running-config | section dhcp
show ip interface g0/0             ! "Helper address is 10.1.1.5"
debug ip dhcp server events
debug ip dhcp server packet
clear ip dhcp binding *
clear ip dhcp conflict *
```

### 6. トラブルシュート

| 症状・出力 | 原因 | 対処 |
|---|---|---|
| クライアントのアドレスが 169.254.x.x | サーバーに届いていない | 下の各項目を確認する |
| 別のサブネットのクライアントだけ取得できない | リレーが設定されていない。`ip helper-address` を設定したインターフェースや、アドレスの誤り | クライアント側に正しく設定する |
| リレーは正しいが取得できない | サーバーから giaddr のサブネットへの **戻りの経路** がない | サーバーや経路の途中に経路を追加する |
| 同上 | giaddr のサブネットに対応するプールがない。`network` の誤り | プールを直す |
| 一部のクライアントだけ取得できない | プールの枯渇。`show ip dhcp pool` で残りを確認する | リース期間を短くする、範囲を広げる、不要なバインディングを消す |
| 同上 | `show ip dhcp conflict` に多くの登録がある。conflict のアドレスは配られない | 原因の機器を見つけ、`clear ip dhcp conflict *` |
| アドレスは取れるが外に出られない | `default-router` の誤り、または未設定 | プールを直す |
| 名前解決できない | `dns-server` の誤り、または未設定 | プールを直す |
| ルーターや固定の機器とアドレスが重なる | `ip dhcp excluded-address` の漏れ | 除外する範囲を設定する |
| 誰も取得できない | `no service dhcp` で機能が止まっている。ACL が UDP 67/68 を遮断している。クライアント側のポートの VLAN の誤り | 機能を有効にする、ACL を直す |
| 予想外のアドレスを取得した | 不正な DHCP サーバー | DHCP スヌーピング(→ 4.7) |
| スイッチを通すと取得に時間がかかる | STP の状態の遷移待ち(約 30 秒) | PortFast(→ 2.5) |

> **【1.7 まとめ】**
>
> - DORA。サーバーは UDP 67、クライアントは UDP 68。Discover はブロードキャスト
> - `ip dhcp excluded-address` はグローバルコンフィグで設定する
> - プールの中に `network`、`default-router`、`dns-server`、`lease` を書く
> - クライアントは `ip address dhcp`
> - リレーは **クライアント側** のインターフェースに `ip helper-address <サーバー>`
> - リレーを通すときは giaddr でプールが選ばれる。サーバーから giaddr への経路が必要
> - `show ip dhcp binding` / `pool` / `conflict` で確認する
