# LinuC 102 テキスト 1.10 セキュリティ

## 1.10.1 セキュリティ管理業務の実施 （重要度3）

### 1. SUID / SGID ファイルの監査

| ビット             | 数値 | 効果                                                       |
|--------------------|------|------------------------------------------------------------|
| SUID               | 4000 | 実行したユーザーではなく、ファイルの**所有者**の権限で動く |
| SGID               | 2000 | ファイルの**所有グループ**の権限で動く                     |
| スティッキービット | 1000 | ディレクトリ内のファイルを、所有者以外が削除できない       |

rootが所有するSUIDプログラムに欠陥があると、一般ユーザーがroot権限を得る足がかりになる。不要なものがないか、定期的に探す。

``` bash
# SUIDが付いたファイル
find / -perm -4000 -type f
# SGIDが付いたファイル
find / -perm -2000 -type f
# どちらかが付いたファイル
find / -perm /6000 -type f
# エラー表示を捨てる
find / -perm -4000 2>/dev/null
```

| 書き方        | 条件                                   |
|---------------|----------------------------------------|
| `-perm 4755`  | パーミッションが**完全に一致**         |
| `-perm -4000` | 指定したビットが**すべて**立っている   |
| `-perm /6000` | 指定したビットの**どれか**が立っている |

`-perm -u+s`（SUID）、`-perm -g+s`（SGID）とも書ける。

### 2. パスワードの有効期限（エージング）

**［図1　パスワードの有効期限］**

| 段階     | chage | 意味                                               |
|----------|-------|----------------------------------------------------|
| 最短日数 | `-m`  | 変更後、この日数が過ぎるまで再変更できない         |
| 有効期限 | `-M`  | 変更後、この日数を過ぎると変更を求められる         |
| 警告     | `-W`  | 期限の何日前から警告するか                         |
| 無効化   | `-I`  | 期限切れ後、この日数を過ぎるとログインできなくなる |

`chage` でパスワードの有効期限を管理する。

``` bash
chage -l kuro
chage -M 90 -W 7 kuro
chage -E 2026-12-31 kuro
chage -d 0 kuro
```

| chage     | 意味                                              | passwd | usermod |
|-----------|---------------------------------------------------|--------|---------|
| `-l`      | 設定を表示                                        | `-S`   |         |
| `-m 日数` | 変更できるまでの最短日数                          | `-n`   |         |
| `-M 日数` | 有効期限の最長日数                                | `-x`   |         |
| `-W 日数` | 期限前の警告日数                                  | `-w`   |         |
| `-I 日数` | 期限切れ後、無効になるまでの日数                  | `-i`   | `-f`    |
| `-E 日付` | **アカウント**の失効日                            |        | `-e`    |
| `-d 日付` | 最終変更日（`-d 0` で次回ログイン時に変更を強制） |        |         |

- 設定は `/etc/shadow` に記録される。
- `chage -l` は一般ユーザーも自分の分を見られる。変更はrootのみ。
- 新規ユーザーの既定値は `/etc/login.defs`（`PASS_MAX_DAYS` など）。

> **【ひっかけ】**
>
> `-M` はパスワードの期限、`-E` はアカウントそのものの失効日。`-E` を過ぎると、パスワードが有効でもログインできない。

### 3. 開いているポートの確認

| コマンド        | 調べる対象       | 調べ方                                         |
|-----------------|------------------|------------------------------------------------|
| `ss`、`netstat` | 自分のホスト     | 待ち受け状態を内側から見る                     |
| `nmap`          | 自分や他のホスト | 外からポートスキャンする                       |
| `lsof`          | 自分のホスト     | 開いているファイルとポートを、プロセスから見る |
| `fuser`         | 自分のホスト     | ファイルやポートを使っているプロセスを特定する |

``` bash
ss -tuln
netstat -tuln
```

**nmap**

``` bash
nmap localhost
nmap 192.168.1.10
nmap -p 22,80 192.168.1.10
nmap -p 1-1024 192.168.1.10
nmap -sU 192.168.1.10
```

| オプション | 意味                         |
|------------|------------------------------|
| `-p`       | ポートを指定                 |
| `-sT`      | TCPコネクトスキャン          |
| `-sS`      | SYNスキャン（rootが必要）    |
| `-sU`      | UDPスキャン                  |
| `-O`       | OSを推定                     |
| `-sV`      | サービスのバージョンを調べる |

管理下にないホストへのポートスキャンは、攻撃とみなされる。許可なく行わない。

**lsof**

``` bash
lsof -i        # ネットワーク接続
lsof -i :22    # 22番ポート
lsof -i TCP    # TCPのみ
lsof -u kuro   # ユーザー別
lsof -p 1234   # プロセス別
lsof /var/log/messages
```

**fuser**

``` bash
fuser 22/tcp   # 22番を使うPID
fuser -v /mnt  # 使用中のプロセス
fuser -k /mnt  # それらを終了
```

`umount` が「device is busy」で失敗するとき、`fuser -vm /mnt` で使用中のプロセスを探せる。

### 4. ログイン状況と履歴

| コマンド  | 表示                                           | 参照するファイル   |
|-----------|------------------------------------------------|--------------------|
| `who`     | 現在ログイン中のユーザー                       | `/var/run/utmp`    |
| `w`       | ログイン中のユーザーと、実行中のコマンド、負荷 | `/var/run/utmp`    |
| `last`    | ログインの履歴                                 | `/var/log/wtmp`    |
| `lastb`   | ログイン**失敗**の履歴                         | `/var/log/btmp`    |
| `lastlog` | 各ユーザーの最終ログイン                       | `/var/log/lastlog` |

`last reboot` で再起動の履歴、`last kuro` で特定ユーザーの履歴を表示する。

### 5. ulimit

シェルと、そこから起動するプロセスが使える資源を制限する。bash の組み込みコマンド。

``` bash
ulimit -a          # すべて表示
ulimit -n 4096     # 開けるファイル数
ulimit -u 100      # プロセス数
```

| オプション  | 制限する対象                    |
|-------------|---------------------------------|
| `-a`        | すべての制限値を表示            |
| `-n`        | 同時に開けるファイル数          |
| `-u`        | ユーザーが起動できるプロセス数  |
| `-f`        | 作成できるファイルのサイズ      |
| `-v`        | 仮想メモリのサイズ              |
| `-c`        | コアファイルのサイズ            |
| `-t`        | CPU時間（秒）                   |
| `-S` / `-H` | ソフトリミット / ハードリミット |

| 種類           | 意味                                                       |
|----------------|------------------------------------------------------------|
| ソフトリミット | 実際に適用される値。ユーザーがハードリミットまで上げられる |
| ハードリミット | 上限。一般ユーザーは下げられるが、上げられない             |

- ulimit の設定は、そのシェルの中だけ有効。
- 恒久的に設定するには `/etc/security/limits.conf` に書く。

``` bash
# /etc/security/limits.conf
kuro  hard  nproc   100
@dev  soft  nofile  4096
```

### 6. su と sudo

**su**：別のユーザーに切り替える。切り替え先のパスワードが必要。

``` bash
su          # rootになる
su -        # rootのログインシェル
su - kuro   # kuroのログインシェル
su -c "id"  # 1コマンドだけ実行
```

ハイフンなしの `su` は、元のユーザーの環境変数やカレントディレクトリを引き継ぐ。`su -` は切り替え先のユーザーでログインし直した状態になる。

**sudo**：許可されたコマンドを、別のユーザー（通常root）の権限で実行する。入力するのは**自分の**パスワード。

``` bash
sudo systemctl restart sshd
sudo -l          # 許可内容を表示
sudo -u kuro id  # kuroとして実行
sudo -i          # rootのシェル
sudo -k          # 認証の記憶を破棄
```

|                      | su                 | sudo                   |
|----------------------|--------------------|------------------------|
| 入力するパスワード   | 切り替え先（root） | 自分                   |
| 権限の範囲           | すべて             | 許可されたコマンドだけ |
| rootパスワードの共有 | 必要               | 不要                   |
| 実行の記録           | 切り替えのみ       | コマンドごとに残る     |

**/etc/sudoers**：sudo の設定ファイル。必ず `visudo` で編集する。

``` bash
# 誰 ホスト=(実行ユーザー) コマンド
kuro    ALL=(ALL)  ALL
%wheel  ALL=(ALL)  ALL
shiro   ALL=(root) /usr/bin/systemctl
ops     ALL=(ALL)  NOPASSWD: ALL
```

| 記述                        | 意味                                                       |
|-----------------------------|------------------------------------------------------------|
| `%wheel`                    | `%` はグループ                                             |
| `ALL=(ALL) ALL`             | すべてのホストで、すべてのユーザーとして、すべてのコマンド |
| `(root) /usr/bin/systemctl` | rootとして、このコマンドだけ                               |
| `NOPASSWD:`                 | パスワード入力なし                                         |

- `visudo` は文法を確認してから保存し、同時編集も防ぐ。直接エディタで開くと、書き間違えたときに sudo が使えなくなる。
- 個別の設定は `/etc/sudoers.d/` にファイルを置いてもよい。

### 7. TMOUT

bash の変数。入力がないまま指定した秒数が過ぎると、自動的にログアウトする。

``` bash
# /etc/profile に書く（全員に適用）
TMOUT=600
readonly TMOUT
export TMOUT
```

`readonly` にしておくと、ユーザーが解除できない。離席中の端末を悪用されるのを防ぐ。

> **【1.10.1 まとめ】**
>
> - SUIDの検索は `find / -perm -4000`、SGIDは `-perm -2000`
> - `chage -M` 期限、`-m` 最短、`-W` 警告、`-I` 無効化、`-E` アカウント失効、`-l` 表示
> - 自ホストのポートは `ss -tuln`、外からは `nmap`
> - `lsof -i` で開いているポート、`fuser` で使用中のプロセス
> - `who` と `w` は現在、`last` は履歴、`lastb` は失敗
> - `ulimit -n` ファイル数、`-u` プロセス数。恒久設定は limits.conf
> - sudo は自分のパスワード。設定は /etc/sudoers を `visudo` で編集
> - `TMOUT` で自動ログアウト

## 1.10.2 ホストのセキュリティ設定 （重要度3）

### 1. シャドウパスワード

`/etc/passwd` は、UIDとユーザー名の対応を調べるために全ユーザーが読める必要がある。ここに暗号化パスワードを置くと、誰でも持ち出して解読を試せる。そこでパスワードだけを、rootしか読めない `/etc/shadow` に分けた。これがシャドウパスワード。

| ファイル      | パーミッション             | パスワード欄           |
|---------------|----------------------------|------------------------|
| `/etc/passwd` | 644（全員が読める）        | `x`                    |
| `/etc/shadow` | 000 または 640（rootのみ） | 暗号化されたパスワード |

- `/etc/shadow` には、有効期限の情報も入る（1.10.1）。
- 補足：`pwconv` でシャドウ化、`pwunconv` で元に戻す。

### 2. /etc/nologin

このファイルが**存在する**と、root以外のユーザーはログインできない。ファイルの中身は、ログインを試みたユーザーに表示される。メンテナンス時に使う。

``` bash
echo "メンテナンス中" > /etc/nologin
# 作業後に削除
rm /etc/nologin
```

> **【ひっかけ】**
>
> `/etc/nologin`（ファイル。全一般ユーザーを一時的に締め出す）と `/sbin/nologin`（シェル。特定のアカウントを恒久的にログイン不可にする）は別物。

### 3. 不要なサービスを止める

動いているサービスは、すべて攻撃の入口になりうる。使わないものは止め、自動起動も無効にする。

**systemd（systemctl）**

``` bash
systemctl status telnet.socket
systemctl stop telnet.socket
systemctl disable telnet.socket
systemctl list-unit-files \
  --type=service
```

| コマンド             | 動作                                   |
|----------------------|----------------------------------------|
| `start` / `stop`     | 今すぐ起動 / 停止                      |
| `enable` / `disable` | 自動起動を有効 / 無効                  |
| `disable --now`      | 無効化と停止を同時に行う               |
| `mask`               | 起動できないようにする（手動でも不可） |
| `is-enabled`         | 自動起動の設定を確認                   |
| `is-active`          | 動作中か確認                           |

> **【ひっかけ】**
>
> `stop` だけでは、再起動後にまた起動する。`disable` だけでは、今動いているものは止まらない。両方必要。

**SysVinit（/etc/init.d、service、chkconfig）**

``` bash
/etc/init.d/httpd stop
service httpd stop
chkconfig --list
chkconfig httpd off
chkconfig --level 35 httpd on
```

| 操作           | SysVinit              | systemd                     |
|----------------|-----------------------|-----------------------------|
| 停止           | `service httpd stop`  | `systemctl stop httpd`      |
| 自動起動を無効 | `chkconfig httpd off` | `systemctl disable httpd`   |
| 一覧           | `chkconfig --list`    | `systemctl list-unit-files` |

`/etc/init.d/` には、サービスごとの起動スクリプトが置かれている。

### 4. スーパーサーバー（inetd / xinetd）

複数のサービスのポートを代表して待ち受け、接続が来たときだけ該当するサーバープログラムを起動する仕組み。利用頻度の低いサービスの常駐を減らせる。

| 実装   | 種類               | パス               |
|--------|--------------------|--------------------|
| inetd  | 設定ファイル       | `/etc/inetd.conf`  |
| inetd  | 個別設定の置き場所 | `/etc/inetd.d/`    |
| xinetd | 設定ファイル       | `/etc/xinetd.conf` |
| xinetd | 個別設定の置き場所 | `/etc/xinetd.d/`   |

inetd は古くからある実装。xinetd は、アクセス制御などを強化した後継。

**inetd**：`/etc/inetd.conf` に1サービス1行で書く。行頭に `#` を付けると無効になる。

``` bash
#ftp stream tcp nowait root /usr/sbin/ftpd
```

左から、サービス名、ソケットの種類、プロトコル、待ち方、実行ユーザー、プログラム。

**xinetd**：全体の設定は `/etc/xinetd.conf`。サービスごとの設定は `/etc/xinetd.d/` にファイルで置く。

``` bash
# /etc/xinetd.d/telnet
service telnet
{
  disable     = yes
  socket_type = stream
  wait        = no
  user        = root
  server      = /usr/sbin/in.telnetd
  only_from   = 192.168.1.0/24
}
```

| 項目            | 意味                         |
|-----------------|------------------------------|
| `disable = yes` | このサービスを**無効**にする |
| `server`        | 起動するプログラム           |
| `user`          | 実行ユーザー                 |
| `only_from`     | 接続を許可する接続元         |
| `no_access`     | 接続を拒否する接続元         |
| `access_times`  | 利用できる時間帯             |

設定を変えたら、xinetd を再起動する。

> **【ひっかけ】**
>
> 無効にするのは `disable = yes`。`disable = no` が有効。二重否定に注意。

補足：TCP Wrapper（`/etc/hosts.allow`、`/etc/hosts.deny`）も、接続元によるアクセス制御に使われてきた。

### 5. ファイアウォールの概要

通過するパケットを、IPアドレス・ポート番号・プロトコルなどの条件で許可または拒否する（パケットフィルタリング）。Linuxではカーネルの netfilter が処理し、それを操作するのが iptables や firewalld。

**［図2　iptables のチェイン］**

| チェイン | 対象                                                         |
|----------|--------------------------------------------------------------|
| INPUT    | 自ホストあてに入ってくるパケット                             |
| OUTPUT   | 自ホストから出ていくパケット                                 |
| FORWARD  | 自ホストを経由して転送されるパケット（ルータとして動く場合） |

**iptables**

``` bash
# ルールを表示
iptables -L
# 22番への接続を許可
iptables -A INPUT -p tcp --dport 22 \
  -j ACCEPT
# 既定の動作を破棄にする
iptables -P INPUT DROP
```

| 項目        | 内容                                                           |
|-------------|----------------------------------------------------------------|
| テーブル    | `filter`（フィルタリング。既定）、`nat`（アドレス変換）        |
| チェイン    | `INPUT`、`OUTPUT`、`FORWARD`                                   |
| ターゲット  | `ACCEPT`（許可）、`DROP`（黙って破棄）、`REJECT`（拒否を通知） |
| `-A` / `-D` | ルールを追加 / 削除                                            |
| `-L` / `-F` | ルールを表示 / すべて消去                                      |
| `-P`        | チェインの既定の動作（ポリシー）                               |

iptables のルールは再起動で消える。`iptables-save` で保存する。

**firewalld**

iptables より上位の管理ツール。ゾーン（信頼度の区分）ごとに、許可するサービスやポートを決める。

``` bash
firewall-cmd --list-all
firewall-cmd --add-service=http
firewall-cmd --add-port=8080/tcp
firewall-cmd --permanent \
  --add-service=http
firewall-cmd --reload
```

| 項目          | 内容                                         |
|---------------|----------------------------------------------|
| ゾーン        | `public`（既定）、`trusted`、`drop` など     |
| `--permanent` | 恒久的な設定に書く。付けないと再起動で消える |
| `--reload`    | 恒久的な設定を読み直して反映する             |

|            | iptables        | firewalld                        |
|------------|-----------------|----------------------------------|
| 設定の単位 | ルールを1つずつ | ゾーンとサービス                 |
| 変更の反映 | 即時            | 即時（通信を切らずに変更できる） |
| コマンド   | `iptables`      | `firewall-cmd`                   |

> **【1.10.2 まとめ】**
>
> - パスワードは /etc/shadow に分離。/etc/passwd のパスワード欄は `x`
> - /etc/nologin があると、root以外はログインできない
> - サービスの停止は `systemctl stop`、自動起動の無効は `systemctl disable`
> - SysVinit では `service` と `chkconfig`、スクリプトは /etc/init.d/
> - xinetd は /etc/xinetd.d/ のファイルで `disable = yes`
> - inetd は /etc/inetd.conf の行をコメントアウト
> - iptables は INPUT / OUTPUT / FORWARD と ACCEPT / DROP / REJECT
> - firewalld は `firewall-cmd`。恒久設定は `--permanent`

## 1.10.3 暗号化によるデータの保護 （重要度3）

### 1. 共通鍵暗号と公開鍵暗号

|      | 共通鍵暗号               | 公開鍵暗号                   |
|------|--------------------------|------------------------------|
| 鍵   | 暗号化と復号に**同じ鍵** | **公開鍵**と**秘密鍵**のペア |
| 速度 | 速い                     | 遅い                         |
| 課題 | 鍵を安全に渡す必要がある | 公開鍵が本物かの確認が必要   |
| 例   | AES                      | RSA、ECDSA、Ed25519          |

公開鍵暗号の2つの使い方：

| 用途   | 使う鍵                                            | 目的                                     |
|--------|---------------------------------------------------|------------------------------------------|
| 暗号化 | 相手の**公開鍵**で暗号化 → 相手の**秘密鍵**で復号 | 相手だけが読める                         |
| 署名   | 自分の**秘密鍵**で署名 → 自分の**公開鍵**で検証   | 本人が作ったこと、改ざんがないことを示す |

秘密鍵は絶対に他人に渡さない。公開鍵は配ってよい。

### 2. SSH の公開鍵認証

**［図3　SSHの公開鍵認証］**

| 場所         | ファイル                  | 内容                                                     |
|--------------|---------------------------|----------------------------------------------------------|
| クライアント | `~/.ssh/id_ed25519` など  | ユーザーの秘密鍵。外に出さない                           |
| サーバー     | `~/.ssh/authorized_keys`  | ログインを許可するユーザーの公開鍵を登録する             |
| クライアント | `~/.ssh/known_hosts`      | 接続したことのあるサーバーの公開鍵（ホスト鍵）を記録する |
| サーバー     | `/etc/ssh/ssh_host_*_key` | サーバー自身の鍵（ホスト鍵）                             |

SSHの認証は2段階ある。

| 認証         | 確認すること             | 使うファイル                                   |
|--------------|--------------------------|------------------------------------------------|
| ホスト認証   | 接続先が本物のサーバーか | クライアントの `known_hosts`                   |
| ユーザー認証 | 接続してきたのが本人か   | サーバーの `authorized_keys`、またはパスワード |

初回接続時に表示されるフィンガープリントの確認が、ホスト認証。`yes` と答えると `known_hosts` に記録される。サーバーの鍵が変わると、次回の接続で警告が出る。

### 3. ssh-keygen

鍵ペアを作る。

``` bash
ssh-keygen -t ed25519
ssh-keygen -t rsa -b 4096
ssh-keygen -t ecdsa -b 521
```

| オプション  | 意味                               |
|-------------|------------------------------------|
| `-t`        | 鍵の種類（rsa、ecdsa、ed25519）    |
| `-b`        | 鍵の長さ（ビット）                 |
| `-f`        | 保存するファイル名                 |
| `-C`        | コメント                           |
| `-p`        | パスフレーズを変更                 |
| `-l`        | フィンガープリントを表示           |
| `-R ホスト` | `known_hosts` からホストの鍵を削除 |

| ファイル                    | 内容                   | パーミッション |
|-----------------------------|------------------------|----------------|
| `~/.ssh/`                   | ディレクトリ           | 700            |
| `~/.ssh/id_rsa`             | RSAの秘密鍵            | 600            |
| `~/.ssh/id_rsa.pub`         | RSAの公開鍵            | 644            |
| `~/.ssh/id_ecdsa`、`.pub`   | ECDSAの鍵ペア          |                |
| `~/.ssh/id_ed25519`、`.pub` | Ed25519の鍵ペア        |                |
| `~/.ssh/authorized_keys`    | 許可する公開鍵の一覧   | 600            |
| `~/.ssh/config`             | クライアントの個人設定 | 600            |

- 作成時にパスフレーズを設定すると、秘密鍵が暗号化される。鍵ファイルが盗まれても、すぐには使われない。
- 公開鍵の登録は、サーバーの `authorized_keys` に `.pub` の中身を1行追記する。`ssh-copy-id user@host` で自動化できる。

> **【ひっかけ】**
>
> `.pub` が付くのが公開鍵。サーバーに登録するのは**公開鍵**。秘密鍵は手元から動かさない。パーミッションが緩いと、SSHは鍵の使用を拒否する。

### 4. 鍵のアルゴリズム

| 種類      | 特徴                                                                                               |
|-----------|----------------------------------------------------------------------------------------------------|
| `rsa`     | 古くから使われ、対応する環境が最も多い。安全性は鍵の長さに依存（2048ビット以上、推奨は3072や4096） |
| `dsa`     | 古い方式。現在は非推奨で、新しいOpenSSHでは無効                                                    |
| `ecdsa`   | 楕円曲線暗号。短い鍵でRSAと同等の強度。鍵長は256、384、521ビット                                   |
| `ed25519` | エドワーズ曲線を使う新しい方式。高速で安全。鍵長は固定（256ビット）。現在の推奨                    |

### 5. ssh-agent と ssh-add

パスフレーズ付きの秘密鍵は、使うたびにパスフレーズの入力が必要になる。`ssh-agent` は、復号した秘密鍵をメモリに保持し、入力を1回で済ませる。

``` bash
# エージェントを起動
eval $(ssh-agent)
# 鍵を登録（パスフレーズを入力）
ssh-add
ssh-add ~/.ssh/id_ed25519
# 登録済みの鍵を表示
ssh-add -l
# 削除
ssh-add -d ~/.ssh/id_ed25519
ssh-add -D
```

| コマンド            | 意味                                       |
|---------------------|--------------------------------------------|
| `ssh-agent bash`    | エージェントの下で新しいシェルを起動       |
| `eval $(ssh-agent)` | 今のシェルでエージェントを使えるようにする |
| `ssh-add`           | 既定の鍵を登録                             |
| `ssh-add -l`        | 登録済みの鍵の一覧                         |
| `ssh-add -d` / `-D` | 指定した鍵を削除 / すべて削除              |

`ssh -A` でエージェント転送を使うと、踏み台サーバーの先でも手元の鍵で認証できる。

### 6. OpenSSH クライアントの設定と利用

``` bash
ssh kuro@server
ssh -p 2222 kuro@server
ssh -i ~/.ssh/id_work kuro@server
ssh kuro@server "uptime"
scp file.txt kuro@server:/tmp/
sftp kuro@server
```

| 設定ファイル           | 対象                         |
|------------------------|------------------------------|
| `~/.ssh/config`        | クライアント（ユーザーごと） |
| `/etc/ssh/ssh_config`  | クライアント（システム全体） |
| `/etc/ssh/sshd_config` | **サーバー**                 |

``` bash
# ~/.ssh/config
Host web
    HostName 192.168.1.20
    User kuro
    Port 2222
    IdentityFile ~/.ssh/id_work
```

上の設定があれば、`ssh web` だけで接続できる。

> **【ひっかけ】**
>
> `ssh_config` はクライアント、`sshd_config` はサーバー。d は daemon。

サーバー側（`sshd_config`）の代表的な項目：

| 項目                        | 意味                                 |
|-----------------------------|--------------------------------------|
| `Port`                      | 待ち受けるポート                     |
| `PermitRootLogin no`        | rootの直接ログインを禁止             |
| `PasswordAuthentication no` | パスワード認証を禁止（鍵だけにする） |
| `PubkeyAuthentication yes`  | 公開鍵認証を許可                     |

### 7. SSH ポート転送

SSHの暗号化された経路（トンネル）を通して、別の通信を運ぶ仕組み。

**［図4　ローカルポート転送（-L）］**

`ssh -L 8080:192.168.1.20:80 kuro@gateway` を実行すると、クライアントの `localhost:8080` への接続が、SSHで暗号化されて gateway（SSHサーバー）に届き、そこから `192.168.1.20:80` へ転送される。クライアントから直接届かない接続先に、SSHサーバーを経由して到達できる。

| 種類             | 書式                                    | 動作                                                      |
|------------------|-----------------------------------------|-----------------------------------------------------------|
| ローカル転送     | `-L 手元ポート:接続先:接続先ポート`     | **手元**のポートへの接続を、SSHサーバー経由で接続先へ送る |
| リモート転送     | `-R サーバーポート:接続先:接続先ポート` | **SSHサーバー**のポートへの接続を、手元経由で接続先へ送る |
| ダイナミック転送 | `-D 手元ポート`                         | 手元にSOCKSプロキシを作る                                 |

| オプション | 意味                                       |
|------------|--------------------------------------------|
| `-N`       | リモートでコマンドを実行しない（転送だけ） |
| `-f`       | バックグラウンドで実行                     |
| `-X`       | X11転送（リモートのGUIを手元に表示）       |

接続先は「SSHサーバーから見た」ホスト名。`-L 8080:localhost:80` の localhost は、SSHサーバー自身を指す。

### 8. GnuPG（gpg）

ファイルの暗号化と電子署名を行うツール。OpenPGP の実装。

``` bash
# 鍵ペアを作る
gpg --gen-key
# 鍵の一覧
gpg --list-keys
gpg --list-secret-keys
# 公開鍵を書き出す・取り込む
gpg --export -a kuro > kuro.asc
gpg --import shiro.asc
```

``` bash
# 相手の公開鍵で暗号化
gpg -e -r shiro file.txt
# 自分の秘密鍵で復号
gpg -d file.txt.gpg > file.txt
# パスフレーズだけで暗号化（共通鍵）
gpg -c file.txt
```

``` bash
# 署名する
gpg --sign file.txt
gpg --clearsign file.txt
gpg --detach-sign file.txt
# 署名を検証する
gpg --verify file.txt.sig file.txt
```

| オプション                   | 意味                               |
|------------------------------|------------------------------------|
| `--gen-key`                  | 鍵ペアを作成                       |
| `--list-keys`（`-k`）        | 公開鍵の一覧                       |
| `--list-secret-keys`（`-K`） | 秘密鍵の一覧                       |
| `--export` / `--import`      | 公開鍵の書き出し / 取り込み        |
| `-a`（`--armor`）            | ASCII形式で出力                    |
| `-e`（`--encrypt`）          | 暗号化                             |
| `-r`（`--recipient`）        | 受取人を指定                       |
| `-d`（`--decrypt`）          | 復号                               |
| `-c`（`--symmetric`）        | 共通鍵で暗号化                     |
| `-s`（`--sign`）             | 署名                               |
| `--clearsign`                | 本文を読める形のまま署名を付ける   |
| `-b`（`--detach-sign`）      | 署名だけを別ファイル（.sig）に出す |
| `--verify`                   | 署名を検証                         |
| `--gen-revoke`               | 失効証明書を作成                   |

| 名前                   | 内容                                                                                       |
|------------------------|--------------------------------------------------------------------------------------------|
| `~/.gnupg/`            | 鍵と設定を保存するディレクトリ。パーミッションは700                                        |
| `~/.gnupg/pubring.kbx` | 公開鍵の鍵束（古い版は `pubring.gpg`）                                                     |
| `~/.gnupg/trustdb.gpg` | 信頼度のデータベース                                                                       |
| `~/.gnupg/gpg.conf`    | 設定ファイル                                                                               |
| `gpg-agent`            | 秘密鍵とパスフレーズを管理するデーモン。gpg が自動で起動する。ssh-agent の役割も兼ねられる |

> **【ひっかけ】**
>
> 暗号化は**相手の公開鍵**、署名は**自分の秘密鍵**。逆にしない。

> **【1.10.3 まとめ】**
>
> - 暗号化は相手の公開鍵で、復号は相手の秘密鍵で
> - 署名は自分の秘密鍵で、検証は自分の公開鍵で
> - `ssh-keygen -t ed25519`。公開鍵（.pub）をサーバーの authorized_keys に登録
> - known_hosts はサーバーのホスト鍵の記録
> - rsa は互換性、ecdsa は楕円曲線、ed25519 は現在の推奨
> - `ssh-agent` が鍵を保持し、`ssh-add` で登録する
> - `-L` はローカル転送、`-R` はリモート転送
> - gpg は `-e -r` で暗号化、`-d` で復号、`--sign` と `--verify`
> - 鍵は ~/.gnupg/ に保存。gpg-agent が秘密鍵を管理

## 1.10.4 クラウドセキュリティの基礎 （重要度3）

### 1. オンプレミスとパブリッククラウド

|                      | オンプレミス                     | パブリッククラウド                         |
|----------------------|----------------------------------|--------------------------------------------|
| 機器の所有・設置     | 自社                             | クラウド事業者                             |
| 物理的な保護         | 自社で行う                       | 事業者が行う                               |
| 管理の経路           | 社内ネットワーク、現地作業       | **インターネット経由の管理コンソール**     |
| サーバーの作成・削除 | 機器の調達が必要                 | 画面やAPIの操作ですぐできる                |
| 外部への公開         | 自社で経路を作らない限り届かない | 設定次第で、すぐインターネットに公開される |

クラウドでは、設定の誤り1つでサーバーやデータが外部に公開される。物理的に守られていても、設定の責任は利用者にある。

### 2. 責任の分担

**［図5　責任の分担（仮想サーバーの場合）］**

| 層                                       | 責任を負う側   |
|------------------------------------------|----------------|
| データ、アカウント、アクセス権           | 利用者         |
| アプリケーション、ミドルウェア           | 利用者         |
| OS（更新、設定、OS上のファイアウォール） | 利用者         |
| 仮想化基盤                               | クラウド事業者 |
| 物理サーバー、ネットワーク、施設         | クラウド事業者 |

仮想サーバーを借りる形（IaaS）では、OSから上はすべて利用者の責任。OSの更新を怠って侵入されても、事業者の責任にはならない。

### 3. クラウドの管理機能と Linux サーバーの機能分担

同じ働きをする機能が、クラウド側とサーバー側の両方にある。

| 機能               | クラウドの管理機能                                       | Linux サーバーの機能                        |
|--------------------|----------------------------------------------------------|---------------------------------------------|
| ファイアウォール   | セキュリティグループなど。サーバーの**外側**で通信を制限 | firewalld、iptables。サーバーの**中**で制限 |
| ルーティング       | 仮想ネットワークのルートテーブル、ゲートウェイ           | `ip route` で見えるサーバー内の経路         |
| 起動・停止・再起動 | 管理コンソールから操作                                   | `systemctl reboot` など                     |
| コンソール         | 管理コンソール経由のシリアルコンソール                   | 通常のログイン                              |
| バックアップ       | スナップショット                                         | tar、rsync など                             |

- ファイアウォールは二重。通信は、クラウド側と**サーバー側の両方**で許可されて初めて通る。つながらないときは両方を確認する。
- クラウド側のファイアウォールは、サーバーに侵入されても書き換えられない。サーバー側だけに頼らない。
- 経路の設定はクラウド側で行う。サーバー内の経路は、通常DHCPで自動設定される。

### 4. リージョン

データセンターが置かれている**地理的な地域**。利用者が選ぶ。

| 観点       | 内容                                                                                                                                       |
|------------|--------------------------------------------------------------------------------------------------------------------------------------------|
| 法令       | データは、置かれた国の法律の適用を受ける。海外リージョンでは、現地当局による開示請求などがありうる。個人情報を国外に置くことへの制約もある |
| 遅延       | 利用者に近いリージョンほど応答が速い                                                                                                       |
| 災害対策   | 複数のリージョンに分散すれば、広域災害に耐えられる                                                                                         |
| 料金・機能 | リージョンによって価格や使えるサービスが異なる                                                                                             |

リージョンの選択は性能だけの問題ではない。国内外の法的な制約を含めて決める。

### 5. 揮発性ストレージ

仮想サーバーに付属する一時的なディスク。サーバーを**停止・削除すると中身が消える**。ホストの障害でも失われる。

| 種類             | サーバー停止後 | 用途                                   |
|------------------|----------------|----------------------------------------|
| 揮発性ストレージ | 消える         | 一時ファイル、キャッシュ、スワップ     |
| 永続ストレージ   | 残る           | OS、データベース、ログなど残すべきもの |

- 高速なことが多く、一時的な作業領域には向いている。
- 消えて困るデータは置かない。必要なら、永続ストレージや別の保存先へ定期的に退避する。
- OSの再起動（reboot）では消えないことが多いが、停止（stop）では消える。事業者ごとの仕様を確認する。

### 6. クラウド事業者の制約

事業者の都合で、利用者のサーバーに影響が出ることがある。

| 制約         | 内容                                                                 |
|--------------|----------------------------------------------------------------------|
| メンテナンス | 基盤の保守作業が、事業者の予定で行われる。事前に通知される           |
| 再起動       | 保守や障害により、サーバーが再起動・別のホストへ移動されることがある |
| 利用上の制限 | 送信メール（25番ポート）の制限、侵入テストの事前申請など             |

対応：

- 再起動されても自動で復旧するようにする。必要なサービスは `systemctl enable` で自動起動を有効にしておく。
- 複数のサーバーや区画（ゾーン）に分散し、1台が止まってもサービスが続くようにする。
- 事業者からの通知を確認する。

### 7. 管理コンソールへのアクセスと認証

管理コンソール（Webの管理画面）は、**インターネット経由で、どこからでも**アクセスできる。ここを乗っ取られると、全サーバーの削除、データの持ち出し、高額な不正利用まで可能になる。サーバーのrootより強い権限であり、認証が最後の防壁になる。

| 項目         | 内容                                                                                       |
|--------------|--------------------------------------------------------------------------------------------|
| アクセス経路 | インターネット（HTTPS）。接続元IPアドレスの制限ができる場合もある                          |
| 認証方式     | クラウド事業者が提供する。IDとパスワードに、多要素認証を加える                             |
| 権限の分離   | 管理者アカウントを日常的に使わない。作業者ごとにアカウントを作り、必要最小限の権限を与える |
| APIキー      | プログラム用の認証情報。ソースコードに書かない。漏れると管理コンソールと同じ被害が出る     |

**認証の3要素**

| 要素                   | 例                                             |
|------------------------|------------------------------------------------|
| 知識（知っていること） | パスワード、暗証番号                           |
| 所持（持っているもの） | スマートフォン、ハードウェアトークン、ICカード |
| 生体（本人の特徴）     | 指紋、顔                                       |

| 用語                        | 意味                                                                                                         |
|-----------------------------|--------------------------------------------------------------------------------------------------------------|
| 多要素認証（MFA）           | **異なる要素**を2つ以上組み合わせる。パスワード＋スマートフォンのコードなど                                  |
| 多段階認証                  | 認証を複数回行う。要素が同じ場合も含む。パスワード＋秘密の質問は、どちらも知識なので多段階だが多要素ではない |
| ワンタイムパスワード（OTP） | **1回だけ**、または短時間だけ有効なパスワード                                                                |

OTPの方式：

| 方式        | 仕組み                                                         |
|-------------|----------------------------------------------------------------|
| TOTP        | 現在時刻から計算する。認証アプリが30秒ごとに新しい値を表示する |
| HOTP        | カウンタ（使用回数）から計算する                               |
| SMS・メール | サーバーが生成した値を送る                                     |

パスワードが漏れても、OTPを生成する端末がなければログインできない。

**サーバー自体へのアクセス**

- SSHは公開鍵認証にする。クラウドの仮想サーバーは、初期状態でパスワード認証が無効なことが多い。
- SSHの接続元IPアドレスを、クラウド側のファイアウォールで限定する。
- SSHでつながらなくなったときは、管理コンソールのシリアルコンソールから操作する。

> **【1.10.4 まとめ】**
>
> - OSから上は利用者の責任。基盤と施設は事業者の責任
> - ファイアウォールはクラウド側とサーバー側の二重。両方で許可が必要
> - リージョンは地理的な地域。国内外の法令の制約も考えて選ぶ
> - 揮発性ストレージは、サーバーを停止すると消える
> - 事業者のメンテナンスで再起動されることがある。自動起動と冗長化で備える
> - 管理コンソールはインターネットからアクセスできる。多要素認証で守る
> - 多要素は異なる要素の組み合わせ。OTPは1回だけ有効
