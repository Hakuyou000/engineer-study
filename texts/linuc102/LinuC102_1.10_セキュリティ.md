# LinuC 102 テキスト 1.10 セキュリティ

サーバーを安全に保つための、日々の管理作業、ホストの設定、暗号化、クラウドを使うときの注意点を学びます。

## 1.10.1 セキュリティ管理業務の実施 (重要度3)

### 1. SUID / SGID の付いたファイルの監査

| ビット | 数値 | 効果 |
|---|---|---|
| SUID | 4000 | 実行したユーザーではなく、ファイルの **所有者** の権限で動く |
| SGID | 2000 | ファイルの **所有グループ** の権限で動く |
| スティッキービット | 1000 | ディレクトリの中のファイルを、所有者以外が削除できなくなる |

root が所有する SUID のプログラムに欠陥があると、一般ユーザーが root の権限を手に入れるきっかけになります。不要なものがないかを定期的に探します。

``` bash
# SUID が付いたファイル
find / -perm -4000 -type f
# SGID が付いたファイル
find / -perm -2000 -type f
# どちらかが付いたファイル
find / -perm /6000 -type f
# エラーの表示を捨てる
find / -perm -4000 2>/dev/null
```

| 書き方 | 条件 |
|---|---|
| `-perm 4755` | パーミッションが **完全に一致** する |
| `-perm -4000` | 指定したビットが **すべて** 立っている |
| `-perm /6000` | 指定したビットの **どれか** が立っている |

`-perm -u+s`(SUID)、`-perm -g+s`(SGID)とも書けます。

### 2. パスワードの有効期限(エージング)

**［図1　パスワードの有効期限］**

| 段階 | chage | 意味 |
|---|---|---|
| 最短の日数 | `-m` | 変更してから、この日数が過ぎるまで再び変更できない |
| 有効期限 | `-M` | 変更してから、この日数を過ぎると変更を求められる |
| 警告 | `-W` | 期限の何日前から警告するか |
| 無効化 | `-I` | 期限が切れてから、この日数を過ぎるとログインできなくなる |

日数のたつ順に並べて図にします。

```text
[変更した日]
  |
  |  -m 日がたつまでは、再び変更できない
  |  期限の -W 日前から、警告が出る
  v
[変更した日 + M 日] 有効期限。変更を求められる
  |
  |  期限から -I 日がたつ
  v
[期限 + I 日] アカウントが無効になる(passwd -l のロックとは別)
```

`chage` で、パスワードの有効期限を管理します。

``` bash
chage -l sato
chage -M 90 -W 7 sato
chage -E 2026-12-31 sato
chage -d 0 sato
```

| chage | 意味 | passwd では | usermod では |
|---|---|---|---|
| `-l` | 設定を表示する | `-S` | |
| `-m 日数` | 次に変更できるまでの最短の日数 | `-n` | |
| `-M 日数` | 有効期限の最長の日数 | `-x` | |
| `-W 日数` | 期限の前に警告する日数 | `-w` | |
| `-I 日数` | 期限が切れてから無効になるまでの日数 | `-i` | `-f` |
| `-E 日付` | **アカウント** の失効日 | | `-e` |
| `-d 日付` | 最後に変更した日(`-d 0` で次のログインで変更を強制) | | |

- 設定は `/etc/shadow` に記録されます。
- `chage -l` は、一般ユーザーも自分の分を見られます。変更は root だけができます。
- 新しいユーザーの既定値は `/etc/login.defs`(`PASS_MAX_DAYS` など)にあります。

> **【ひっかけ】**
>
> `-M` はパスワードの期限、`-E` はアカウントそのものの失効日です。`-E` の日を過ぎると、パスワードが有効でもログインできません。

### 3. 開いているポートの確認

| コマンド | 調べる対象 | 調べ方 |
|---|---|---|
| `ss`、`netstat` | 自分のホスト | 待ち受けの状態を内側から見る |
| `nmap` | 自分や他のホスト | 外からポートを順に調べる(ポートスキャン) |
| `lsof` | 自分のホスト | 開いているファイルとポートを、プロセスの側から見る |
| `fuser` | 自分のホスト | ファイルやポートを使っているプロセスを特定する |

``` bash
ss -tuln
netstat -tuln
```

**nmap**

``` bash
nmap localhost
nmap 192.168.1.10
nmap -p 22,80 192.168.1.10
nmap -p 1-1024 192.168.1.10
nmap -sU 192.168.1.10
```

| オプション | 意味 |
|---|---|
| `-p` | ポートを指定する |
| `-sT` | TCP の接続を試すスキャン |
| `-sS` | SYN スキャン(root が必要) |
| `-sU` | UDP のスキャン |
| `-O` | OS を推定する |
| `-sV` | サービスのバージョンを調べる |

自分が管理していないホストへのポートスキャンは、攻撃とみなされます。許可なく行ってはいけません。

**lsof**

``` bash
lsof -i        # ネットワークの接続
lsof -i :22    # 22 番ポート
lsof -i TCP    # TCP だけ
lsof -u sato   # ユーザーごと
lsof -p 1234   # プロセスごと
lsof /var/log/messages
```

**fuser**

``` bash
fuser 22/tcp   # 22 番を使っているプロセスの ID
fuser -v /mnt  # 使っているプロセスを詳しく表示
fuser -k /mnt  # それらのプロセスを終了させる
```

`umount` が「device is busy」で失敗するときは、`fuser -vm /mnt` で使っているプロセスを探せます。

### 4. ログインの状況と履歴

| コマンド | 表示されるもの | 読むファイル |
|---|---|---|
| `who` | 今ログインしているユーザー | `/var/run/utmp` |
| `w` | ログインしているユーザーと、実行中のコマンド、システムの負荷 | `/var/run/utmp` |
| `last` | ログインの履歴 | `/var/log/wtmp` |
| `lastb` | ログインに **失敗** した履歴 | `/var/log/btmp` |
| `lastlog` | 各ユーザーが最後にログインした日時 | `/var/log/lastlog` |

`last reboot` で再起動の履歴を、`last sato` で特定のユーザーの履歴を表示します。

### 5. ulimit

シェルと、そこから起動するプロセスが使える資源を制限します。bash に組み込まれたコマンドです。

``` bash
ulimit -a          # すべて表示する
ulimit -n 4096     # 同時に開けるファイルの数
ulimit -u 100      # プロセスの数
```

| オプション | 制限する対象 |
|---|---|
| `-a` | すべての制限の値を表示する |
| `-n` | 同時に開けるファイルの数 |
| `-u` | ユーザーが起動できるプロセスの数 |
| `-f` | 作れるファイルの大きさ |
| `-v` | 仮想メモリの大きさ |
| `-c` | コアファイル(異常終了したときのメモリの記録)の大きさ |
| `-t` | CPU を使える時間(秒) |
| `-S` / `-H` | ソフトリミット / ハードリミット |

| 種類 | 意味 |
|---|---|
| ソフトリミット | 実際に適用される値。ユーザーがハードリミットまで上げられる |
| ハードリミット | 上限の値。一般ユーザーは下げられるが、上げられない |

- ulimit の設定は、そのシェルの中だけで有効です。
- ずっと有効にするには `/etc/security/limits.conf` に書きます。

``` bash
# /etc/security/limits.conf
sato  hard  nproc   100
@dev  soft  nofile  4096
```

### 6. su と sudo

**su**: 別のユーザーに切り替えます。切り替え先のユーザーのパスワードが必要です。

``` bash
su          # root になる
su -        # root のログインシェルになる
su - sato   # sato のログインシェルになる
su -c "id"  # 1つのコマンドだけ実行する
```

ハイフンなしの `su` は、元のユーザーの環境変数やカレントディレクトリを引き継ぎます。`su -` は、切り替え先のユーザーでログインし直したのと同じ状態になります。

**sudo**: 許可されたコマンドを、別のユーザー(普通は root)の権限で実行します。入力するのは **自分の** パスワードです。

``` bash
sudo systemctl restart sshd
sudo -l          # 自分に許可されている内容を表示する
sudo -u sato id  # sato として実行する
sudo -i          # root のシェルを起動する
sudo -k          # 認証の記憶を消す
```

| | su | sudo |
|---|---|---|
| 入力するパスワード | 切り替え先(root)のもの | 自分のもの |
| 権限の範囲 | すべて | 許可されたコマンドだけ |
| root のパスワードの共有 | 必要 | 不要 |
| 実行の記録 | 切り替えたことだけ | コマンドごとに残る |

**/etc/sudoers**: sudo の設定ファイルです。必ず `visudo` で編集します。

``` bash
# 誰が  どのホストで=(誰として)  どのコマンドを
sato    ALL=(ALL)  ALL
%wheel  ALL=(ALL)  ALL
suzuki  ALL=(root) /usr/bin/systemctl
ops     ALL=(ALL)  NOPASSWD: ALL
```

| 書き方 | 意味 |
|---|---|
| `%wheel` | `%` はグループを表す |
| `ALL=(ALL) ALL` | すべてのホストで、すべてのユーザーとして、すべてのコマンドを実行できる |
| `(root) /usr/bin/systemctl` | root として、このコマンドだけを実行できる |
| `NOPASSWD:` | パスワードの入力なしで実行できる |

- `visudo` は、保存する前に文法を確認し、複数の人が同時に編集するのも防ぎます。エディタで直接開いて書き間違えると、sudo が使えなくなります。
- 個別の設定は、`/etc/sudoers.d/` にファイルを置いてもかまいません。

### 7. TMOUT

bash の変数で、入力がないまま指定した秒数が過ぎると、自動でログアウトします。

``` bash
# /etc/profile に書く(全員に適用される)
TMOUT=600
readonly TMOUT
export TMOUT
```

`readonly` にしておくと、ユーザーが解除できません。席を離れている間に端末を悪用されるのを防げます。

> **【1.10.1 まとめ】**
>
> - SUID の検索は `find / -perm -4000`、SGID は `-perm -2000`
> - `chage -M` は期限、`-m` は最短、`-W` は警告、`-I` は無効化、`-E` はアカウントの失効、`-l` は表示
> - 自分のホストのポートは `ss -tuln`、外からは `nmap`
> - `lsof -i` で開いているポート、`fuser` で使っているプロセス
> - `who` と `w` は今の状況、`last` は履歴、`lastb` は失敗の記録
> - `ulimit -n` はファイルの数、`-u` はプロセスの数。ずっと有効にするには limits.conf
> - sudo では自分のパスワードを使う。設定は /etc/sudoers を `visudo` で編集する
> - `TMOUT` で自動ログアウト

## 1.10.2 ホストのセキュリティ設定 (重要度3)

### 1. シャドウパスワード

`/etc/passwd` は、UID とユーザー名の対応を調べるために、全ユーザーが読める必要があります。ここに暗号化したパスワードを置くと、誰でもそれを持ち出して解読を試せてしまいます。そこで、パスワードだけを root しか読めない `/etc/shadow` に分けました。これがシャドウパスワードです。

| ファイル | パーミッション | パスワードの欄 |
|---|---|---|
| `/etc/passwd` | 644(全員が読める) | `x` |
| `/etc/shadow` | 000 または 640(root だけ) | 暗号化されたパスワード |

- `/etc/shadow` には、有効期限の情報も入ります(1.10.1)。
- 補足: `pwconv` でシャドウパスワードにし、`pwunconv` で元に戻します。

### 2. /etc/nologin

このファイルが **存在する** と、root 以外のユーザーはログインできません。ファイルの中身は、ログインしようとしたユーザーに表示されます。メンテナンスのときに使います。

``` bash
echo "メンテナンス中です" > /etc/nologin
# 作業が終わったら削除する
rm /etc/nologin
```

> **【ひっかけ】**
>
> `/etc/nologin`(ファイル。すべての一般ユーザーを一時的に締め出す)と、`/sbin/nologin`(シェル。特定のアカウントをずっとログインできなくする)は別のものです。

### 3. 不要なサービスを止める

動いているサービスは、どれも攻撃の入口になる可能性があります。使わないサービスは止め、自動起動も無効にします。

**systemd(systemctl)**

``` bash
systemctl status telnet.socket
systemctl stop telnet.socket
systemctl disable telnet.socket
systemctl list-unit-files \
  --type=service
```

| コマンド | 動作 |
|---|---|
| `start` / `stop` | 今すぐ起動 / 停止する |
| `enable` / `disable` | 自動起動を有効 / 無効にする |
| `disable --now` | 自動起動の無効化と停止を同時に行う |
| `mask` | 起動できないようにする(手動でも起動できない) |
| `is-enabled` | 自動起動の設定を確認する |
| `is-active` | 動いているかを確認する |

> **【ひっかけ】**
>
> `stop` だけでは、再起動するとまた起動します。`disable` だけでは、今動いているサービスは止まりません。両方が必要です。

**SysVinit(/etc/init.d、service、chkconfig)**

古い仕組みの SysVinit を使うシステムでは、次のコマンドを使います。

``` bash
/etc/init.d/httpd stop
service httpd stop
chkconfig --list
chkconfig httpd off
chkconfig --level 35 httpd on
```

| 操作 | SysVinit | systemd |
|---|---|---|
| 停止 | `service httpd stop` | `systemctl stop httpd` |
| 自動起動を無効にする | `chkconfig httpd off` | `systemctl disable httpd` |
| 一覧 | `chkconfig --list` | `systemctl list-unit-files` |

`/etc/init.d/` には、サービスごとの起動スクリプトが置かれています。

### 4. スーパーサーバー(inetd / xinetd)

複数のサービスのポートをまとめて待ち受け、接続が来たときだけ、そのサービスのプログラムを起動する仕組みです。あまり使われないサービスを、ずっと動かしておかずに済みます。

| 実装 | 種類 | パス |
|---|---|---|
| inetd | 設定ファイル | `/etc/inetd.conf` |
| inetd | 個別の設定の置き場所 | `/etc/inetd.d/` |
| xinetd | 設定ファイル | `/etc/xinetd.conf` |
| xinetd | 個別の設定の置き場所 | `/etc/xinetd.d/` |

inetd は古くからある実装で、xinetd はアクセス制御などを強化した後継です。

**inetd**: `/etc/inetd.conf` に、1つのサービスを1行で書きます。行の先頭に `#` を付けると無効になります。

``` bash
#ftp stream tcp nowait root /usr/sbin/ftpd
```

左から、サービス名、ソケットの種類、プロトコル、待ち方、実行するユーザー、プログラムです。

**xinetd**: 全体の設定は `/etc/xinetd.conf` で、サービスごとの設定は `/etc/xinetd.d/` にファイルで置きます。

``` bash
# /etc/xinetd.d/telnet
service telnet
{
  disable     = yes
  socket_type = stream
  wait        = no
  user        = root
  server      = /usr/sbin/in.telnetd
  only_from   = 192.168.1.0/24
}
```

| 項目 | 意味 |
|---|---|
| `disable = yes` | このサービスを **無効** にする |
| `server` | 起動するプログラム |
| `user` | 実行するユーザー |
| `only_from` | 接続を許可する送信元 |
| `no_access` | 接続を拒否する送信元 |
| `access_times` | 使える時間帯 |

設定を変えたら、xinetd を再起動します。

> **【ひっかけ】**
>
> 無効にするのは `disable = yes` です。`disable = no` で有効になります。「無効にする = いいえ」という二重の否定に注意します。

補足: TCP Wrapper(`/etc/hosts.allow`、`/etc/hosts.deny`)も、送信元によるアクセス制御に使われてきました。

### 5. ファイアウォールの概要

ファイアウォールは、通過するパケットを、IP アドレス、ポート番号、プロトコルなどの条件で許可したり拒否したりします(パケットフィルタリング)。Linux ではカーネルの netfilter という機能が処理し、それを操作するのが iptables や firewalld です。

**［図2　iptables のチェイン］**

| チェイン | 対象 |
|---|---|
| INPUT | 自分のホストあてに入ってくるパケット |
| OUTPUT | 自分のホストから出ていくパケット |
| FORWARD | 自分のホストを経由して転送されるパケット(ルーターとして動く場合) |

パケットがどのチェインを通るかを図にします。

```text
[外から]
|
v
[ルーティングの判断]
|
+--> INPUT --> [自分のプロセス] 自分のホストあてのパケット
|
+--> FORWARD --> [外へ] 自分のホストを経由して転送されるパケット

[自分のプロセス] --> OUTPUT --> [外へ] 自分のホストから出ていくパケット
```

**iptables**

``` bash
# ルールを表示する
iptables -L
# 22 番への接続を許可する
iptables -A INPUT -p tcp --dport 22 \
  -j ACCEPT
# 既定の動作を「破棄」にする
iptables -P INPUT DROP
```

| 項目 | 内容 |
|---|---|
| テーブル | `filter`(フィルタリング。既定)、`nat`(アドレスの変換) |
| チェイン | `INPUT`、`OUTPUT`、`FORWARD` |
| ターゲット | `ACCEPT`(許可)、`DROP`(知らせずに破棄)、`REJECT`(拒否したことを知らせる) |
| `-A` / `-D` | ルールを追加 / 削除する |
| `-L` / `-F` | ルールを表示 / すべて消去する |
| `-P` | チェインの既定の動作(ポリシー)を決める |

iptables のルールは、再起動すると消えます。`iptables-save` で保存します。

**firewalld**

iptables より上の層で使う管理ツールです。ゾーン(信頼の度合いの区分)ごとに、許可するサービスやポートを決めます。

``` bash
firewall-cmd --list-all
firewall-cmd --add-service=http
firewall-cmd --add-port=8080/tcp
firewall-cmd --permanent \
  --add-service=http
firewall-cmd --reload
```

| 項目 | 内容 |
|---|---|
| ゾーン | `public`(既定)、`trusted`、`drop` など |
| `--permanent` | 恒久的な設定に書く。付けないと再起動で消える |
| `--reload` | 恒久的な設定を読み直して反映する |

| | iptables | firewalld |
|---|---|---|
| 設定の単位 | ルールを1つずつ | ゾーンとサービス |
| 変更の反映 | すぐ | すぐ(通信を切らずに変更できる) |
| コマンド | `iptables` | `firewall-cmd` |

> **【1.10.2 まとめ】**
>
> - パスワードは /etc/shadow に分けられ、/etc/passwd のパスワードの欄は `x` になる
> - /etc/nologin があると、root 以外はログインできない
> - サービスの停止は `systemctl stop`、自動起動の無効化は `systemctl disable`
> - SysVinit では `service` と `chkconfig` を使い、スクリプトは /etc/init.d/ にある
> - xinetd は /etc/xinetd.d/ のファイルで `disable = yes`
> - inetd は /etc/inetd.conf の行をコメントにする
> - iptables は INPUT / OUTPUT / FORWARD と ACCEPT / DROP / REJECT
> - firewalld は `firewall-cmd`。恒久的な設定は `--permanent`

## 1.10.3 暗号化によるデータの保護 (重要度3)

### 1. 共通鍵暗号と公開鍵暗号

| | 共通鍵暗号 | 公開鍵暗号 |
|---|---|---|
| 鍵 | 暗号化と復号に **同じ鍵** を使う | **公開鍵** と **秘密鍵** のペアを使う |
| 速さ | 速い | 遅い |
| 課題 | 鍵を安全に相手に渡す必要がある | 公開鍵が本物かを確かめる必要がある |
| 例 | AES | RSA、ECDSA、Ed25519 |

公開鍵暗号の2つの使い方:

| 用途 | 使う鍵 | 目的 |
|---|---|---|
| 暗号化 | 相手の **公開鍵** で暗号化 → 相手の **秘密鍵** で復号 | 相手だけが読めるようにする |
| 署名 | 自分の **秘密鍵** で署名 → 自分の **公開鍵** で検証 | 本人が作ったこと、改ざんされていないことを示す |

秘密鍵は絶対に他人に渡しません。公開鍵は配ってかまいません。

### 2. SSH の公開鍵認証

**［図3　SSH の公開鍵認証］**

| 場所 | ファイル | 内容 |
|---|---|---|
| クライアント | `~/.ssh/id_ed25519` など | ユーザーの秘密鍵。外に出さない |
| サーバー | `~/.ssh/authorized_keys` | ログインを許可するユーザーの公開鍵を登録する |
| クライアント | `~/.ssh/known_hosts` | 接続したことのあるサーバーの公開鍵(ホスト鍵)を記録する |
| サーバー | `/etc/ssh/ssh_host_*_key` | サーバー自身の鍵(ホスト鍵) |

SSH の認証は2段階あります。

| 認証 | 確かめること | 使うファイル |
|---|---|---|
| ホスト認証 | 接続先が本物のサーバーか | クライアントの `known_hosts` |
| ユーザー認証 | 接続してきたのが本人か | サーバーの `authorized_keys`、またはパスワード |

公開鍵認証で、2 つの認証が行われる順番を図にします。

```text
1. ホスト認証(known_hosts で、本物のサーバーか確かめる)
   [サーバー] --> [クライアント]: ホスト鍵(公開鍵)を送る

2. ユーザー認証(authorized_keys で、本人か確かめる)
   [クライアント] --> [サーバー]: 秘密鍵で作った署名を送る
```

初めて接続するときに表示されるフィンガープリント(鍵の指紋)の確認が、ホスト認証です。`yes` と答えると `known_hosts` に記録されます。サーバーの鍵が変わると、次の接続で警告が出ます。

### 3. ssh-keygen

鍵ペアを作ります。

``` bash
ssh-keygen -t ed25519
ssh-keygen -t rsa -b 4096
ssh-keygen -t ecdsa -b 521
```

| オプション | 意味 |
|---|---|
| `-t` | 鍵の種類(rsa、ecdsa、ed25519) |
| `-b` | 鍵の長さ(ビット) |
| `-f` | 保存するファイル名 |
| `-C` | コメント |
| `-p` | パスフレーズを変更する |
| `-l` | フィンガープリントを表示する |
| `-R ホスト` | `known_hosts` からそのホストの鍵を削除する |

| ファイル | 内容 | パーミッション |
|---|---|---|
| `~/.ssh/` | ディレクトリ | 700 |
| `~/.ssh/id_rsa` | RSA の秘密鍵 | 600 |
| `~/.ssh/id_rsa.pub` | RSA の公開鍵 | 644 |
| `~/.ssh/id_ecdsa`、`.pub` | ECDSA の鍵ペア | |
| `~/.ssh/id_ed25519`、`.pub` | Ed25519 の鍵ペア | |
| `~/.ssh/authorized_keys` | 許可する公開鍵の一覧 | 600 |
| `~/.ssh/config` | クライアントの個人の設定 | 600 |

- 鍵を作るときにパスフレーズを設定すると、秘密鍵が暗号化されます。鍵のファイルを盗まれても、すぐには使われません。
- 公開鍵を登録するには、サーバーの `authorized_keys` に `.pub` の中身を1行追記します。`ssh-copy-id ユーザー@ホスト` で自動化できます。

> **【ひっかけ】**
>
> `.pub` が付いているのが公開鍵です。サーバーに登録するのは **公開鍵** で、秘密鍵は手元から動かしません。パーミッションが緩いと、SSH は鍵を使うことを拒否します。

### 4. 鍵のアルゴリズム

| 種類 | 特徴 |
|---|---|
| `rsa` | 古くから使われ、対応する環境が最も多い。安全性は鍵の長さで決まる(2048 ビット以上。推奨は 3072 や 4096) |
| `dsa` | 古い方式。今は使うことが推奨されず、新しい OpenSSH では無効になっている |
| `ecdsa` | 楕円曲線暗号。短い鍵で RSA と同じくらいの強さがある。鍵の長さは 256、384、521 ビット |
| `ed25519` | エドワーズ曲線を使う新しい方式。速く、安全。鍵の長さは 256 ビットに固定。現在の推奨 |

### 5. ssh-agent と ssh-add

パスフレーズ付きの秘密鍵は、使うたびにパスフレーズの入力が必要です。`ssh-agent` は、復号した秘密鍵をメモリに保持して、入力を1回で済ませます。

``` bash
# エージェントを起動する
eval $(ssh-agent)
# 鍵を登録する(パスフレーズを入力する)
ssh-add
ssh-add ~/.ssh/id_ed25519
# 登録した鍵を表示する
ssh-add -l
# 削除する
ssh-add -d ~/.ssh/id_ed25519
ssh-add -D
```

| コマンド | 意味 |
|---|---|
| `ssh-agent bash` | エージェントの下で新しいシェルを起動する |
| `eval $(ssh-agent)` | いまのシェルでエージェントを使えるようにする |
| `ssh-add` | 既定の鍵を登録する |
| `ssh-add -l` | 登録した鍵の一覧 |
| `ssh-add -d` / `-D` | 指定した鍵を削除 / すべて削除する |

`ssh -A` でエージェントの転送を使うと、踏み台のサーバーの先でも、手元の鍵で認証できます。

### 6. OpenSSH のクライアントの設定と使い方

``` bash
ssh sato@server
ssh -p 2222 sato@server
ssh -i ~/.ssh/id_work sato@server
ssh sato@server "uptime"
scp file.txt sato@server:/tmp/
sftp sato@server
```

| 設定ファイル | 対象 |
|---|---|
| `~/.ssh/config` | クライアント(ユーザーごと) |
| `/etc/ssh/ssh_config` | クライアント(システム全体) |
| `/etc/ssh/sshd_config` | **サーバー** |

``` bash
# ~/.ssh/config
Host web
    HostName 192.168.1.20
    User sato
    Port 2222
    IdentityFile ~/.ssh/id_work
```

この設定があれば、`ssh web` だけで接続できます。

> **【ひっかけ】**
>
> `ssh_config` はクライアントの設定、`sshd_config` はサーバーの設定です。d は daemon(デーモン)の d です。

サーバー側(`sshd_config`)の代表的な項目:

| 項目 | 意味 |
|---|---|
| `Port` | 待ち受けるポート |
| `PermitRootLogin no` | root での直接のログインを禁止する |
| `PasswordAuthentication no` | パスワードでの認証を禁止する(鍵だけにする) |
| `PubkeyAuthentication yes` | 公開鍵での認証を許可する |

### 7. SSH のポート転送

SSH の暗号化された経路(トンネル)を通して、別の通信を運ぶ仕組みです。

**［図4　ローカルポート転送(-L)］**

`ssh -L 8080:192.168.1.20:80 sato@gateway` を実行すると、クライアントの `localhost:8080` への接続が、SSH で暗号化されて gateway(SSH サーバー)に届き、そこから `192.168.1.20:80` へ転送されます。クライアントから直接は届かない接続先に、SSH サーバーを経由して到達できます。

```text
localhost:8080 ===> gateway ---> 192.168.1.20:80
^                   ^            ^
|                   |            +-- 接続先
|                   +-- SSH サーバー(gateway)
+-- 手元のクライアント

===> SSH で暗号化される区間
---> 暗号化されない区間(gateway から接続先まで)
```

| 種類 | 書き方 | 動作 |
|---|---|---|
| ローカル転送 | `-L 手元のポート:接続先:接続先のポート` | **手元** のポートへの接続を、SSH サーバーを経由して接続先へ送る |
| リモート転送 | `-R サーバーのポート:接続先:接続先のポート` | **SSH サーバー** のポートへの接続を、手元を経由して接続先へ送る |
| ダイナミック転送 | `-D 手元のポート` | 手元に SOCKS プロキシを作る |

| オプション | 意味 |
|---|---|
| `-N` | 相手側でコマンドを実行しない(転送だけをする) |
| `-f` | バックグラウンドで実行する |
| `-X` | X11 の転送(相手側の GUI を手元に表示する) |

接続先は「SSH サーバーから見た」ホスト名です。`-L 8080:localhost:80` の localhost は、SSH サーバー自身を指します。

### 8. GnuPG(gpg)

ファイルの暗号化と電子署名を行うツールです。OpenPGP という規格の実装です。

``` bash
# 鍵ペアを作る
gpg --gen-key
# 鍵の一覧
gpg --list-keys
gpg --list-secret-keys
# 公開鍵を書き出す・取り込む
gpg --export -a sato > sato.asc
gpg --import suzuki.asc
```

``` bash
# 相手の公開鍵で暗号化する
gpg -e -r suzuki file.txt
# 自分の秘密鍵で復号する
gpg -d file.txt.gpg > file.txt
# パスフレーズだけで暗号化する(共通鍵)
gpg -c file.txt
```

``` bash
# 署名する
gpg --sign file.txt
gpg --clearsign file.txt
gpg --detach-sign file.txt
# 署名を検証する
gpg --verify file.txt.sig file.txt
```

| オプション | 意味 |
|---|---|
| `--gen-key` | 鍵ペアを作る |
| `--list-keys`(`-k`) | 公開鍵の一覧 |
| `--list-secret-keys`(`-K`) | 秘密鍵の一覧 |
| `--export` / `--import` | 公開鍵の書き出し / 取り込み |
| `-a`(`--armor`) | ASCII の形式で出力する |
| `-e`(`--encrypt`) | 暗号化する |
| `-r`(`--recipient`) | 受取人を指定する |
| `-d`(`--decrypt`) | 復号する |
| `-c`(`--symmetric`) | 共通鍵(パスフレーズ)で暗号化する |
| `-s`(`--sign`) | 署名する |
| `--clearsign` | 本文を読める形のまま、署名を付ける |
| `-b`(`--detach-sign`) | 署名だけを別のファイル(.sig)に出力する |
| `--verify` | 署名を検証する |
| `--gen-revoke` | 失効証明書(鍵を無効にするための証明書)を作る |

| 名前 | 内容 |
|---|---|
| `~/.gnupg/` | 鍵と設定を保存するディレクトリ。パーミッションは 700 |
| `~/.gnupg/pubring.kbx` | 公開鍵の鍵束(古い版は `pubring.gpg`) |
| `~/.gnupg/trustdb.gpg` | 信頼の度合いのデータベース |
| `~/.gnupg/gpg.conf` | 設定ファイル |
| `gpg-agent` | 秘密鍵とパスフレーズを管理するデーモン。gpg が自動で起動する。ssh-agent の役割も兼ねられる |

> **【ひっかけ】**
>
> 暗号化は **相手の公開鍵** で、署名は **自分の秘密鍵** で行います。逆にしないように注意します。

> **【1.10.3 まとめ】**
>
> - 暗号化は相手の公開鍵で、復号は相手の秘密鍵で行う
> - 署名は自分の秘密鍵で、検証は自分の公開鍵で行う
> - `ssh-keygen -t ed25519` で鍵を作り、公開鍵(.pub)をサーバーの authorized_keys に登録する
> - known_hosts は、サーバーのホスト鍵の記録
> - rsa は互換性、ecdsa は楕円曲線、ed25519 は現在の推奨
> - `ssh-agent` が鍵を保持し、`ssh-add` で登録する
> - `-L` はローカル転送、`-R` はリモート転送
> - gpg は `-e -r` で暗号化、`-d` で復号、`--sign` と `--verify` で署名
> - 鍵は ~/.gnupg/ に保存され、gpg-agent が秘密鍵を管理する

## 1.10.4 クラウドセキュリティの基礎 (重要度3)

### 1. オンプレミスとパブリッククラウド

| | オンプレミス(自社で機器を持つ) | パブリッククラウド |
|---|---|---|
| 機器の所有と設置 | 自社 | クラウド事業者 |
| 物理的な保護 | 自社で行う | 事業者が行う |
| 管理の経路 | 社内のネットワーク、現地での作業 | **インターネット経由の管理コンソール** |
| サーバーの作成と削除 | 機器の調達が必要 | 画面や API の操作ですぐにできる |
| 外部への公開 | 自社で経路を作らない限り、外からは届かない | 設定によっては、すぐインターネットに公開される |

クラウドでは、設定を1つ間違えるだけで、サーバーやデータが外部に公開されてしまいます。物理的には事業者が守っていても、設定の責任は利用者にあります。

### 2. 責任の分担

**［図5　責任の分担(仮想サーバーの場合)］**

| 層 | 責任を負う側 |
|---|---|
| データ、アカウント、アクセス権 | 利用者 |
| アプリケーション、ミドルウェア | 利用者 |
| OS(更新、設定、OS の中のファイアウォール) | 利用者 |
| 仮想化の基盤 | クラウド事業者 |
| 物理サーバー、ネットワーク、施設 | クラウド事業者 |

仮想サーバーを借りる形(IaaS)では、OS から上はすべて利用者の責任です。OS の更新をしなかったために侵入されても、事業者の責任にはなりません。

### 3. クラウドの管理機能と Linux サーバーの機能の分担

同じ働きをする機能が、クラウド側とサーバー側の両方にあります。

| 機能 | クラウドの管理機能 | Linux サーバーの機能 |
|---|---|---|
| ファイアウォール | セキュリティグループなど。サーバーの **外側** で通信を制限する | firewalld、iptables。サーバーの **中** で制限する |
| ルーティング | 仮想ネットワークのルートテーブル、ゲートウェイ | `ip route` で見えるサーバーの中の経路 |
| 起動・停止・再起動 | 管理コンソールから操作する | `systemctl reboot` など |
| コンソール | 管理コンソールから使うシリアルコンソール | 普通のログイン |
| バックアップ | スナップショット | tar、rsync など |

- ファイアウォールは二重になっています。通信は、クラウド側と **サーバー側の両方** で許可されて初めて通ります。つながらないときは、両方を確認します。
- クラウド側のファイアウォールは、サーバーに侵入されても書き換えられません。サーバー側だけに頼らないようにします。
- 経路の設定はクラウド側で行います。サーバーの中の経路は、普通は DHCP で自動で設定されます。

### 4. リージョン

リージョンは、データセンターが置かれている **地理的な地域** で、利用者が選びます。

| 観点 | 内容 |
|---|---|
| 法令 | データは、置かれた国の法律の適用を受ける。海外のリージョンでは、現地の当局からデータの開示を求められることがある。個人情報を国外に置くことに制約がある場合もある |
| 遅延 | 利用者に近いリージョンほど、応答が速い |
| 災害対策 | 複数のリージョンに分散すれば、広い地域の災害にも耐えられる |
| 料金と機能 | リージョンによって、価格や使えるサービスが違う |

リージョンの選択は、性能だけの問題ではありません。国内外の法律の制約も含めて決めます。

### 5. 揮発性ストレージ

仮想サーバーに付いている、一時的なディスクです。サーバーを **停止・削除すると中身が消えます**。ホストの障害でも失われます。

| 種類 | サーバーを停止した後 | 用途 |
|---|---|---|
| 揮発性ストレージ | 消える | 一時的なファイル、キャッシュ、スワップ |
| 永続ストレージ | 残る | OS、データベース、ログなど残すべきもの |

- 速いことが多く、一時的な作業の場所には向いています。
- 消えて困るデータは置きません。必要なら、永続ストレージや別の保存先へ定期的に移しておきます。
- OS の再起動(reboot)では消えないことが多いですが、停止(stop)では消えます。事業者ごとの仕様を確認します。

### 6. クラウド事業者の都合による制約

事業者の都合で、利用者のサーバーに影響が出ることがあります。

| 制約 | 内容 |
|---|---|
| メンテナンス | 基盤の保守の作業が、事業者の予定で行われる。事前に通知される |
| 再起動 | 保守や障害によって、サーバーが再起動されたり、別のホストに移されたりすることがある |
| 使い方の制限 | メールの送信(25 番ポート)の制限、侵入テストの事前の申請など |

備え方:

- 再起動されても自動で元に戻るようにします。必要なサービスは `systemctl enable` で自動起動を有効にしておきます。
- 複数のサーバーや区画(ゾーン)に分散し、1台が止まってもサービスが続くようにします。
- 事業者からの通知を確認します。

### 7. 管理コンソールへのアクセスと認証

管理コンソール(Web の管理画面)は、**インターネットを通して、どこからでも** アクセスできます。ここを乗っ取られると、すべてのサーバーの削除、データの持ち出し、高額な不正利用まで可能になります。サーバーの root より強い権限なので、認証が最後の守りになります。

| 項目 | 内容 |
|---|---|
| アクセスの経路 | インターネット(HTTPS)。接続元の IP アドレスを制限できる場合もある |
| 認証の方式 | クラウド事業者が提供する。ID とパスワードに、多要素認証を加える |
| 権限の分離 | 管理者のアカウントを普段は使わない。作業する人ごとにアカウントを作り、必要最小限の権限を与える |
| API キー | プログラム用の認証情報。ソースコードに書かない。漏れると、管理コンソールを乗っ取られたのと同じ被害が出る |

**認証の3つの要素**

| 要素 | 例 |
|---|---|
| 知識(知っていること) | パスワード、暗証番号 |
| 所持(持っているもの) | スマートフォン、ハードウェアトークン、IC カード |
| 生体(本人の特徴) | 指紋、顔 |

| 用語 | 意味 |
|---|---|
| 多要素認証(MFA) | **異なる要素** を2つ以上組み合わせる。パスワードとスマートフォンのコードなど |
| 多段階認証 | 認証を複数回行う。要素が同じ場合も含む。パスワードと秘密の質問は、どちらも知識なので、多段階だが多要素ではない |
| ワンタイムパスワード(OTP) | **1回だけ**、または短い時間だけ使えるパスワード |

OTP の方式:

| 方式 | 仕組み |
|---|---|
| TOTP | 現在の時刻から計算する。認証アプリが 30 秒ごとに新しい値を表示する |
| HOTP | カウンタ(使った回数)から計算する |
| SMS・メール | サーバーが作った値を送る |

パスワードが漏れても、OTP を作る端末がなければログインできません。

**サーバーそのものへのアクセス**

- SSH は公開鍵認証にします。クラウドの仮想サーバーは、最初からパスワード認証が無効になっていることが多いです。
- SSH の接続元の IP アドレスを、クラウド側のファイアウォールで限定します。
- SSH でつながらなくなったときは、管理コンソールのシリアルコンソールから操作します。

> **【1.10.4 まとめ】**
>
> - OS から上は利用者の責任。基盤と施設は事業者の責任
> - ファイアウォールはクラウド側とサーバー側の二重。両方での許可が必要
