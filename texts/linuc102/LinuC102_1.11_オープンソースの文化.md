# LinuC 102 テキスト 1.11 オープンソースの文化

## 1.11.1 オープンソースの概念とライセンス （重要度2）

### 1. オープンソースとは

ソースコードが公開され、誰でも利用、改変、再配布できるソフトウェア。OSS（Open Source Software）と略す。Linuxも、その上で動く多くのソフトウェアもOSS。

| 用語               | 提唱                            | 重視する点           |
|--------------------|---------------------------------|----------------------|
| フリーソフトウェア | FSF（Free Software Foundation） | 利用者の**自由**     |
| オープンソース     | OSI（Open Source Initiative）   | 開発手法としての利点 |

「フリー」は**無料ではなく自由**の意味。OSSを有料で販売することは禁じられていない。

**フリーソフトウェアの4つの自由**（FSF）

| 番号 | 自由                                             |
|------|--------------------------------------------------|
| 0    | どんな目的でも実行する自由                       |
| 1    | 仕組みを調べ、改変する自由（ソースコードが必要） |
| 2    | 複製を再配布する自由                             |
| 3    | 改変したものを配布する自由（ソースコードが必要） |

**オープンソースの定義**（OSI。10項目）

| 番号 | 項目                                                       |
|------|------------------------------------------------------------|
| 1    | 再頒布の自由                                               |
| 2    | ソースコードの公開                                         |
| 3    | 派生ソフトウェアの作成と配布を認める                       |
| 4    | 作者のソースコードの完全性（改変版には別名を求めてもよい） |
| 5    | 個人やグループに対する差別の禁止                           |
| 6    | 利用する分野に対する差別の禁止                             |
| 7    | ライセンスの分配（再配布を受けた人にも同じ権利）           |
| 8    | 特定の製品でのみ有効なライセンスの禁止                     |
| 9    | 他のソフトウェアを制限するライセンスの禁止                 |
| 10   | ライセンスは技術的に中立であること                         |

ソースコードが読めるだけでは、オープンソースとは呼ばない。改変や再配布の自由があり、利用目的で差別しないことが条件。

### 2. オープンソースの特徴

| 特徴                   | 内容                                                                   |
|------------------------|------------------------------------------------------------------------|
| 自由                   | 利用、改変、再配布が認められている                                     |
| ソースコード           | 公開されている。誰でも中身を確認し、直せる                             |
| 著作物                 | **著作権は放棄されていない**。著作権者がライセンスで利用を許諾している |
| 無保証                 | 動作の保証も、損害への責任もない。利用は自己責任                       |
| 継続した開発           | コミュニティにより改良が続く。ただし開発が止まることもある             |
| 多くのライセンスが存在 | ライセンスごとに条件が違う。使う前に確認が必要                         |

> **【ひっかけ】**
>
> OSSは「著作権がない」のではない。著作権があるからこそ、ライセンスで条件を付けられる。著作権がないのはパブリックドメイン。

無保証を補うため、企業が有償でサポートを提供するディストリビューションもある（Red Hat Enterprise Linux など）。

### 3. コピーレフト

「改変したものを配布するときは、**同じライセンス**で、ソースコードも公開する」という考え方。著作権（copyright）を使って、自由が失われないようにする仕組み。

| 分類                     | 派生物への要求                                     | ライセンス       |
|--------------------------|----------------------------------------------------|------------------|
| 強いコピーレフト         | リンクしたプログラム全体に、同じライセンスを求める | GPL、AGPL        |
| 弱いコピーレフト         | 改変した部分にだけ求める                           | LGPL、MPL        |
| 非コピーレフト（寛容型） | 求めない。独自ライセンスの製品に組み込める         | BSD、MIT、Apache |

**［図1　ライセンスの制約の強さ］**

制約の強い順：**AGPL ＞ GPL**（強いコピーレフト） ＞ **LGPL、MPL**（弱いコピーレフト） ＞ **Apache、BSD、MIT**（寛容型） ＞ **パブリックドメイン**（制約なし）。左ほど、派生物に同じ条件を求める。

### 4. 主要なライセンス

| ライセンス         | 特徴                                                                                                                                 | 例                                      |
|--------------------|--------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------|
| GPL                | 強いコピーレフト。派生物を配布するなら、GPLでソースコードを公開する。リンクしたプログラムも対象                                      | Linuxカーネル、GCC、Bash                |
| AGPL               | GPLに加えて、**ネットワーク越しにサービスとして提供する場合**もソースコードの公開を求める                                            | MongoDB（旧版）、Mastodon               |
| LGPL               | ライブラリ向け。LGPLのライブラリを**リンクして使うだけ**のプログラムは、別のライセンスにできる。ライブラリ自体を改変したら公開が必要 | glibc                                   |
| MPL                | ファイル単位のコピーレフト。MPLのファイルを改変したら、そのファイルは公開する。別ファイルは独自ライセンスにできる                    | Firefox                                 |
| BSD                | 寛容型。著作権表示とライセンス文を残せば、改変・再配布・商用利用が自由。ソースコードの公開義務なし                                   | FreeBSD                                 |
| MIT                | 寛容型。BSDとほぼ同じ内容で、非常に短い                                                                                              | jQuery、Node.js                         |
| Apache License 2.0 | 寛容型。**特許の利用許諾**を明記している。改変した場合は、その旨を示す                                                               | Apache HTTP Server、Kubernetes、Android |
| パブリックドメイン | 著作権が放棄された、または消滅した状態。ライセンスではない。制約なし                                                                 | SQLite                                  |

GPLには版がある。Linuxカーネルは GPLv2。GPLv3 は特許や、改変版を実行できない機器（Tivo化）への対策を加えた。

> **【覚え方】**
>
> GPL は「全体に伝わる」。LGPL は「ライブラリを使うだけなら伝わらない」。AGPL は「サービス提供でも伝わる」。BSD、MIT、Apache は「表示を残せば自由」。Apache は特許の条項つき。

### 5. 改変と再配布

| ライセンス         | 改変 | 再配布 | 改変版のソース公開           | 独自ライセンス製品への組み込み |
|--------------------|------|--------|------------------------------|--------------------------------|
| GPL                | 可   | 可     | **必要**                     | 不可（全体がGPLになる）        |
| AGPL               | 可   | 可     | **必要**（サービス提供でも） | 不可                           |
| LGPL               | 可   | 可     | ライブラリ部分は必要         | リンクして使うなら可           |
| MPL                | 可   | 可     | 改変したファイルは必要       | 可                             |
| BSD、MIT           | 可   | 可     | 不要                         | 可                             |
| Apache 2.0         | 可   | 可     | 不要                         | 可                             |
| パブリックドメイン | 可   | 可     | 不要                         | 可                             |

- どのライセンスでも、**改変と再配布そのものは認められる**。違いは、再配布するときの条件。
- GPLの公開義務が生じるのは、**配布するとき**。社内で使うだけなら、改変しても公開の義務はない。
- AGPLは、配布しなくても、ネットワーク越しに利用させれば公開の義務が生じる。
- 寛容型でも、著作権表示とライセンス文は残す必要がある。
- ライセンスどうしには相性がある（互換性）。条件が両立しないライセンスのコードは、1つのプログラムに混ぜて配布できない。
- 1つのソフトウェアを複数のライセンスで提供する形もある（デュアルライセンス）。

> **【ひっかけ】**
>
> 「GPLのソフトウェアは商用利用できない」は誤り。販売も業務利用もできる。求められるのは、配布時のソースコード公開と、同じライセンスの適用。

> **【1.11.1 まとめ】**
>
> - オープンソースは、利用・改変・再配布の自由があるソフトウェア。無料という意味ではない
> - 著作物であり、著作権は放棄されていない。無保証
> - GPL は強いコピーレフト。派生物もGPLで公開
> - AGPL はネットワーク越しのサービス提供でも公開を求める
> - LGPL はライブラリ向け。リンクするだけなら別ライセンスでよい
> - MPL はファイル単位
> - BSD、MIT、Apache は寛容型。Apache は特許条項つき
> - パブリックドメインは著作権がない状態

## 1.11.2 オープンソースのコミュニティとエコシステム （重要度1）

### 1. コミュニティの構成

OSSは、コミュニティ（開発者と利用者の集まり）によって開発、維持される。

| 役割             | 内容                                                         |
|------------------|--------------------------------------------------------------|
| メンテナ         | プロジェクトの責任者。方針を決め、変更を取り込むかを判断する |
| コミッタ         | リポジトリに直接書き込む権限を持つ開発者                     |
| コントリビュータ | 修正や機能を提案する人。権限はなく、提案をメンテナに送る     |
| ユーザー         | 使う人。バグ報告や質問を通じて参加する                       |

個人だけでなく、企業の従業員が業務として参加することも多い。中立的な運営のため、非営利の団体（Linux Foundation、Apache Software Foundation など）がプロジェクトを支える例もある。

### 2. 開発体制

| 項目             | 内容                                                                                         |
|------------------|----------------------------------------------------------------------------------------------|
| バザール方式     | 多数の開発者が公開の場で協力して開発する。少人数で閉じて開発する方式（伽藍方式）と対比される |
| 実力主義         | 貢献の実績によって、発言力や権限が決まる                                                     |
| 意思決定         | 創始者が最終決定する形、投票で決める形、運営委員会を置く形などがある                         |
| リリース         | 安定版と開発版を分ける。長期サポート版（LTS）を出すプロジェクトもある                        |
| アップストリーム | 開発元のこと。修正は開発元に取り込んでもらうのが望ましい                                     |

Linuxカーネルでは、各部分の担当メンテナが変更を審査し、最終的に統括者が取り込む階層的な体制をとる。

### 3. コミュニティで使われる道具

| 道具                 | 用途                                                 |
|----------------------|------------------------------------------------------|
| メーリングリスト     | 議論、告知、パッチの投稿。記録が公開され、検索できる |
| 掲示板（フォーラム） | 質問と回答、情報交換                                 |
| 開発サイト           | ソースコードの管理と共同作業。GitHub、GitLab など    |
| バグ管理システム     | 不具合や要望の登録と追跡。Bugzilla、各サイトの Issue |
| チャット             | 即時の相談                                           |
| Wiki、ドキュメント   | 手順や仕様の共有                                     |

開発サイトでは、リポジトリを複製（フォーク）し、変更を提案（プルリクエスト、マージリクエスト）し、審査（レビュー）を経て取り込まれる流れが一般的。

### 4. 参加の方法

開発だけが参加ではない。

| 段階               | 内容                                                   |
|--------------------|--------------------------------------------------------|
| 使用               | 使う。利用者が増えること自体が、プロジェクトの力になる |
| 紹介               | 使い方や事例を、ブログ、勉強会、SNSで広める            |
| バグ報告           | 見つけた不具合を報告する                               |
| 質問への回答       | 掲示板やメーリングリストで他の利用者を助ける           |
| 翻訳、ドキュメント | メッセージや文書を翻訳、整備する                       |
| パッチの提供       | 修正や機能追加のコードを提案する                       |
| 寄付、支援         | 資金や設備を提供する                                   |

**よいバグ報告**

- 先に、同じ報告がすでにないか検索する。
- 決められた場所（バグ管理システムなど）に出す。
- バージョンと環境（OS、ディストリビューション）を書く。
- 再現する手順を書く。
- 期待した結果と、実際の結果を書く。
- エラーメッセージやログを添える。

### 5. エコシステム

開発者、利用者、企業、ディストリビュータが互いに利益を得ながら、全体が発展していく関係。生態系になぞらえてこう呼ぶ。

| 参加者             | 得るもの                           | 返すもの                         |
|--------------------|------------------------------------|----------------------------------|
| 利用者             | 無償で高品質なソフトウェア         | バグ報告、紹介、利用実績         |
| 開発者             | 技術の向上、評価、自分に必要な機能 | コード、レビュー                 |
| 企業               | 開発費の削減、標準技術の利用       | 開発者の人件費、資金、修正の還元 |
| ディストリビュータ | 製品の素材                         | 統合と検証、サポート、修正の還元 |

使うだけで何も返さない利用者が増えすぎると、開発は続かない。使用、紹介、バグ報告のような小さな関わりでも、エコシステムへの貢献になる。

> **【1.11.2 まとめ】**
>
> - コミュニティは、メンテナ、コミッタ、コントリビュータ、ユーザーで構成される
> - 道具は、メーリングリスト、掲示板、開発サイト、バグ管理システム
> - 参加の入口は、使用、紹介、バグ報告。開発だけが貢献ではない
> - バグ報告には、バージョン、環境、再現手順、期待と実際の結果を書く
> - エコシステムは、参加者が互いに利益を得て発展する関係
