# LinuC 102 テキスト 1.11 オープンソースの文化

Linux を支えるオープンソースの考え方、ライセンスの違い、コミュニティへの参加の仕方を学びます。

## 1.11.1 オープンソースの概念とライセンス (重要度2)

### 1. オープンソースとは

オープンソースソフトウェア(OSS)は、ソースコードが公開されていて、誰でも利用、改変、再配布できるソフトウェアです。Linux も、その上で動く多くのソフトウェアも OSS です。

| 用語 | 提唱した団体 | 重視する点 |
|---|---|---|
| フリーソフトウェア | FSF(Free Software Foundation) | 利用者の **自由** |
| オープンソース | OSI(Open Source Initiative) | 開発の方法としての利点 |

「フリー」は **無料ではなく自由** という意味です。OSS を有料で販売することは禁じられていません。

**フリーソフトウェアの4つの自由**(FSF)

| 番号 | 自由 |
|---|---|
| 0 | どんな目的でも実行する自由 |
| 1 | 仕組みを調べ、改変する自由(ソースコードが必要) |
| 2 | 複製を再配布する自由 |
| 3 | 改変したものを配布する自由(ソースコードが必要) |

**オープンソースの定義**(OSI。10 項目)

| 番号 | 項目 |
|---|---|
| 1 | 再頒布(再配布)の自由 |
| 2 | ソースコードの公開 |
| 3 | 派生したソフトウェアの作成と配布を認める |
| 4 | 作者のソースコードの完全性(改変した版には別の名前を求めてもよい) |
| 5 | 個人やグループに対する差別の禁止 |
| 6 | 利用する分野に対する差別の禁止 |
| 7 | ライセンスの分配(再配布を受けた人にも同じ権利がある) |
| 8 | 特定の製品の中でだけ有効なライセンスの禁止 |
| 9 | 他のソフトウェアを制限するライセンスの禁止 |
| 10 | ライセンスが特定の技術に依存しないこと |

ソースコードが読めるだけでは、オープンソースとは呼びません。改変や再配布の自由があり、利用する目的で差別しないことが条件です。

### 2. オープンソースの特徴

| 特徴 | 内容 |
|---|---|
| 自由 | 利用、改変、再配布が認められている |
| ソースコード | 公開されている。誰でも中身を確かめ、直せる |
| 著作物 | **著作権は放棄されていない**。著作権者がライセンスで利用を許諾している |
| 無保証 | 動作の保証も、損害への責任もない。自分の責任で使う |
| 継続した開発 | コミュニティによって改良が続く。ただし、開発が止まることもある |
| 多くのライセンスがある | ライセンスごとに条件が違う。使う前に確認が必要 |

> **【ひっかけ】**
>
> OSS は「著作権がない」のではありません。著作権があるからこそ、ライセンスで条件を付けられるのです。著作権がないのはパブリックドメインです。

無保証であることを補うため、企業が有料でサポートを提供するディストリビューションもあります(Red Hat Enterprise Linux など)。

### 3. コピーレフト

コピーレフトは、「改変したものを配布するときは、**同じライセンス** で、ソースコードも公開する」という考え方です。著作権(copyright)の仕組みを使って、ソフトウェアの自由が失われないようにします。

| 分類 | 派生物への求め | ライセンス |
|---|---|---|
| 強いコピーレフト | リンクしたプログラム全体に、同じライセンスを求める | GPL、AGPL |
| 弱いコピーレフト | 改変した部分にだけ求める | LGPL、MPL |
| 非コピーレフト(寛容型) | 求めない。独自のライセンスの製品に組み込める | BSD、MIT、Apache |

**［図1　ライセンスの制約の強さ］**

制約の強い順に、**AGPL ＞ GPL**(強いコピーレフト)＞ **LGPL、MPL**(弱いコピーレフト)＞ **Apache、BSD、MIT**(寛容型)＞ **パブリックドメイン**(制約なし)です。左のものほど、派生物に同じ条件を求めます。

### 4. 主なライセンス

| ライセンス | 特徴 | 例 |
|---|---|---|
| GPL | 強いコピーレフト。派生物を配布するなら、GPL でソースコードを公開する。リンクしたプログラムも対象になる | Linux カーネル、GCC、Bash |
| AGPL | GPL の条件に加えて、**ネットワーク越しにサービスとして提供する場合** にもソースコードの公開を求める | MongoDB(古い版)、Mastodon |
| LGPL | ライブラリ向け。LGPL のライブラリを **リンクして使うだけ** のプログラムは、別のライセンスにできる。ライブラリそのものを改変したら公開が必要 | glibc |
| MPL | ファイル単位のコピーレフト。MPL のファイルを改変したら、そのファイルは公開する。別のファイルは独自のライセンスにできる | Firefox |
| BSD | 寛容型。著作権の表示とライセンスの文を残せば、改変、再配布、商用利用が自由。ソースコードを公開する義務はない | FreeBSD |
| MIT | 寛容型。BSD とほぼ同じ内容で、とても短い | jQuery、Node.js |
| Apache License 2.0 | 寛容型。**特許の利用の許諾** を明記している。改変した場合は、そのことを示す | Apache HTTP Server、Kubernetes、Android |
| パブリックドメイン | 著作権が放棄された、または消滅した状態。ライセンスではなく、制約もない | SQLite |

GPL にはいくつかの版があります。Linux カーネルは GPLv2 です。GPLv3 では、特許の問題や、改変した版を実行できない機器(Tivo 化)への対策が加えられました。

> **【覚え方】**
>
> GPL は「全体に伝わる」。LGPL は「ライブラリを使うだけなら伝わらない」。AGPL は「サービスとして提供しても伝わる」。BSD、MIT、Apache は「表示を残せば自由」。Apache は特許の条項付きです。

### 5. 改変と再配布

| ライセンス | 改変 | 再配布 | 改変した版のソースの公開 | 独自のライセンスの製品への組み込み |
|---|---|---|---|---|
| GPL | できる | できる | **必要** | できない(全体が GPL になる) |
| AGPL | できる | できる | **必要**(サービスとして提供する場合も) | できない |
| LGPL | できる | できる | ライブラリの部分は必要 | リンクして使うならできる |
| MPL | できる | できる | 改変したファイルは必要 | できる |
| BSD、MIT | できる | できる | 不要 | できる |
| Apache 2.0 | できる | できる | 不要 | できる |
| パブリックドメイン | できる | できる | 不要 | できる |

- どのライセンスでも、**改変と再配布そのものは認められています**。違うのは、再配布するときの条件です。
- GPL の公開の義務が生じるのは、**配布するとき** です。社内で使うだけなら、改変しても公開の義務はありません。
- AGPL は、配布しなくても、ネットワーク越しに使わせれば公開の義務が生じます。
- 寛容型のライセンスでも、著作権の表示とライセンスの文は残す必要があります。
- ライセンス同士には相性(互換性)があります。条件が両立しないライセンスのコードは、1つのプログラムに混ぜて配布できません。
- 1つのソフトウェアを、複数のライセンスで提供する形もあります(デュアルライセンス)。

> **【ひっかけ】**
>
> 「GPL のソフトウェアは商用利用できない」は誤りです。販売も業務での利用もできます。求められるのは、配布するときのソースコードの公開と、同じライセンスの適用です。

> **【1.11.1 まとめ】**
>
> - オープンソースは、利用、改変、再配布の自由があるソフトウェア。無料という意味ではない
> - 著作物であり、著作権は放棄されていない。無保証
> - GPL は強いコピーレフト。派生物も GPL で公開する
> - AGPL はネットワーク越しのサービスの提供でも公開を求める
> - LGPL はライブラリ向け。リンクするだけなら別のライセンスでよい
> - MPL はファイル単位
> - BSD、MIT、Apache は寛容型。Apache は特許の条項付き
> - パブリックドメインは著作権がない状態

## 1.11.2 オープンソースのコミュニティとエコシステム (重要度1)

### 1. コミュニティの構成

OSS は、コミュニティ(開発者と利用者の集まり)によって開発され、維持されています。

| 役割 | 内容 |
|---|---|
| メンテナ | プロジェクトの責任者。方針を決め、変更を取り込むかを判断する |
| コミッタ | リポジトリに直接書き込む権限を持つ開発者 |
| コントリビュータ | 修正や機能を提案する人。書き込む権限はなく、提案をメンテナに送る |
| ユーザー | 使う人。バグの報告や質問を通して参加する |

個人だけでなく、企業の社員が仕事として参加することもよくあります。中立的に運営するため、非営利の団体(Linux Foundation、Apache Software Foundation など)がプロジェクトを支える例もあります。

### 2. 開発の体制

| 項目 | 内容 |
|---|---|
| バザール方式 | 多数の開発者が、公開の場で協力して開発する。少人数が閉じた場で開発する方式(伽藍方式)と対比される |
| 実力主義 | 貢献した実績によって、発言力や権限が決まる |
| 意思決定 | 創始者が最終的に決める形、投票で決める形、運営委員会を置く形などがある |
| リリース | 安定版と開発版を分ける。長期サポート版(LTS)を出すプロジェクトもある |
| アップストリーム | 開発元のこと。修正は、開発元に取り込んでもらうのが望ましい |

Linux カーネルでは、各部分を担当するメンテナが変更を審査し、最終的に統括者が取り込む、階層的な体制をとっています。

### 3. コミュニティで使われる道具

| 道具 | 用途 |
|---|---|
| メーリングリスト | 議論、告知、パッチの投稿。過去のやり取りが公開され、検索できる |
| 掲示板(フォーラム) | 質問と回答、情報の交換 |
| 開発サイト | ソースコードの管理と共同での作業。GitHub、GitLab など |
| バグ管理システム | 不具合や要望の登録と追跡。Bugzilla、各サイトの Issue |
| チャット | その場での相談 |
| Wiki、ドキュメント | 手順や仕様の共有 |

開発サイトでは、リポジトリを複製(フォーク)し、変更を提案(プルリクエスト、マージリクエスト)し、審査(レビュー)を経て取り込まれる、という流れが一般的です。

### 4. 参加の方法

開発することだけが参加ではありません。

| 段階 | 内容 |
|---|---|
| 使う | 使うこと。利用者が増えること自体が、プロジェクトの力になる |
| 紹介する | 使い方や事例を、ブログ、勉強会、SNS で広める |
| バグを報告する | 見つけた不具合を報告する |
| 質問に答える | 掲示板やメーリングリストで、他の利用者を助ける |
| 翻訳、ドキュメント | メッセージや文書を翻訳し、整える |
| パッチを送る | 修正や機能の追加のコードを提案する |
| 寄付、支援 | お金や設備を提供する |

**よいバグ報告**

- 先に、同じ報告がすでにないかを検索します。
- 決められた場所(バグ管理システムなど)に出します。
- バージョンと環境(OS、ディストリビューション)を書きます。
- 再現する手順を書きます。
- 期待した結果と、実際の結果を書きます。
- エラーのメッセージやログを添えます。

### 5. エコシステム

開発者、利用者、企業、ディストリビュータが、互いに利益を得ながら全体として発展していく関係を、生態系になぞらえてエコシステムと呼びます。

| 参加者 | 得るもの | 返すもの |
|---|---|---|
| 利用者 | 無料で質の高いソフトウェア | バグの報告、紹介、利用の実績 |
| 開発者 | 技術の向上、評価、自分に必要な機能 | コード、レビュー |
| 企業 | 開発費の削減、標準の技術の利用 | 開発者の人件費、資金、修正の還元 |
| ディストリビュータ | 製品の材料 | 統合と検証、サポート、修正の還元 |

使うだけで何も返さない利用者ばかりになると、開発は続きません。使う、紹介する、バグを報告する、といった小さな関わりも、エコシステムへの貢献になります。

> **【1.11.2 まとめ】**
>
> - コミュニティは、メンテナ、コミッタ、コントリビュータ、ユーザーで構成される
> - 道具は、メーリングリスト、掲示板、開発サイト、バグ管理システムなど
> - 参加の入口は、使う、紹介する、バグを報告する。開発だけが貢献ではない
> - バグ報告には、バージョン、環境、再現の手順、期待した結果と実際の結果を書く
> - エコシステムは、参加者が互いに利益を得ながら発展していく関係
