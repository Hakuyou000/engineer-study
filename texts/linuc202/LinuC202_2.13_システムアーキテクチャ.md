# LinuC 202 テキスト 2.13 システムアーキテクチャ

止まりにくいシステムの作り方(高可用性)、利用者が増えても耐える作り方(スケーラビリティ)、クラウド上の構成、よくある構成の型を学びます。

## 2.13.1 高可用システムの実現方式 (重要度2)

### 1. 可用性と、止まる原因

**可用性**(アベイラビリティー)は、システムが使える状態にある度合いです。**高可用性**(HA、High Availability)は、止まりにくく、止まっても早く戻る作りのことです。

システムが止まる原因には、次のようなものがあります。

| 種類 | 例 |
|---|---|
| 物理の故障 | ディスク、メモリ、電源、ネットワーク機器、ケーブルの故障。停電。災害 |
| 論理の故障 | ソフトウェアのバグ、設定の誤り、ディスクの満杯、証明書の期限切れ、プロセスの停止 |
| 計画停止 | 前もって知らせて行う、更新や交換のための停止(計画メンテナンス) |
| 緊急停止 | 障害や脆弱性への対応のために、急いで行う停止 |

- 計画停止は、利用者の少ない時間帯に行い、前もって知らせます。止めなくてもよい作りにするのが理想です。
- 論理の故障は、機器を増やしても防げません。変更の手順や、設定のレビューも大事です。

### 2. 単一障害点と冗長化

**単一障害点**(SPOF、Single Point of Failure)は、そこが壊れるとシステム全体が止まってしまう部分です。1 台しかないサーバー、1 本しかない回線、1 つしかないスイッチ、1 台しかないデータベースなどです。

SPOF は、**冗長化**(同じ役割のものを複数用意すること)でなくします。見つけるには、システムの図を描いて、「この部品が 1 つ壊れたら、全体が止まるか」を 1 つずつ確かめます。

```text
[A: one of each]
  user --> [web x1] --> [db x1]
  どちらが壊れても、全体が止まる

[B: redundant]
                 +--> [web 1]
  user --> [LB] -+
                 +--> [web 2] --> [db primary] ==> [db standby]
```

- 上の図の B でも、LB(ロードバランサー、2.13.2 で学ぶ)が 1 台なら、そこが新しい SPOF になります。LB も 2 台にします。
- 電源、回線、ラックなど、サーバーの外にも SPOF はあります。

### 3. 冗長化の方式

| 方式 | 内容 |
|---|---|
| アクティブ / スタンバイ | 1 台が処理し、もう 1 台は待機する。故障したら待機側に切り替える(フェイルオーバー) |
| アクティブ / アクティブ | 複数台がすべて処理する。1 台が壊れたら、残りで続ける |

- 待機側は、処理していないぶん資源が無駄になります。そのかわり、設計は単純です。
- アクティブ / アクティブは、資源を無駄にしません。ただし、1 台が壊れたときに、残りで全部の負荷を受けられる余裕が必要です。

### 4. クラスターと Pacemaker、Corosync

**クラスター**は、複数のサーバー(ノード)を 1 つのシステムのように動かす仕組みです。Linux の高可用性クラスターでは、次の 2 つの部品をよく使います。

| 部品 | 役割 |
|---|---|
| Corosync | ノード同士が通信して、「どのノードが生きているか」を確かめ合う(ハートビート)。クラスターの仲間の管理を受け持つ |
| Pacemaker | 何を、どのノードで動かすかを決める(クラスターのリソースの管理)。ノードが落ちたら、サービスを別のノードで起動する |

Pacemaker が管理する対象を**リソース**と呼びます。サービス(Apache など)、仮想 IP アドレス、共有ストレージなどです。

```text
[node 1] <-- heartbeat (Corosync) --> [node 2]
  Pacemaker                             Pacemaker
  runs the virtual IP and Web           standby

node 1 stops --> node 2 notices --> node 2 starts the virtual IP and Web
```

- 利用者は**仮想 IP アドレス**(クラスターが付け替える IP アドレス)にアクセスします。ノードが入れ替わっても、アドレスは変わりません。
- 通信が切れて、両方のノードが「相手が落ちた」と思い、両方が動き出す事故を**スプリットブレイン**と呼びます。データが壊れるおそれがあります。
- 防ぐために、過半数のノードが見えるときだけ動く(**クォーラム**)ようにします。落ちたはずのノードを強制的に止める**フェンシング**(STONITH)も使います。
- 設定の道具は、RHEL 系では `pcs`、Debian 系では `crmsh` や `pcs` を使います。【要確認】

### 5. 稼働率を見るための言葉

稼働率や障害の対策を話し合うための言葉です。計算式は問われません。意味と、数字の大小の関係を押さえます。

| 言葉 | 意味 | 良い方向 |
|---|---|---|
| 稼働率 | 使える状態にある時間の割合 | 大きいほどよい |
| MTBF | 故障と故障の間の平均の時間(Mean Time Between Failures)。壊れにくさ | 長いほどよい |
| MTTR | 故障してから復旧するまでの平均の時間(Mean Time To Repair)。直しやすさ | 短いほどよい |
| SLA | サービスの提供者が、利用者に約束する水準。守れないときの補償を含む(Service Level Agreement) | ― |

- 稼働率を上げるには、MTBF を長くする(壊れにくくする)か、MTTR を短くする(早く直す)かのどちらかです。冗長化は、部品が 1 つ壊れても全体が止まらないようにします。システム全体として見ると、止まる回数が減る(全体の MTBF が長くなる)ので、稼働率が上がります。
- SLA の稼働率が「99.9%」でも、メンテナンスの時間を含むかどうかは、契約で違います。【要確認】

### 6. 障害からの復旧の目標

| 言葉 | 意味 | 例 |
|---|---|---|
| RPO | どの時点までのデータを失ってよいか(Recovery Point Objective)。データの損失の限度 | RPO 1 時間なら、1 時間ごとのバックアップが要る |
| RTO | 障害から、どれだけの時間で復旧するか(Recovery Time Objective)。停止の時間の限度 | RTO 4 時間なら、4 時間以内に戻す |

```text
past <------------------- time -------------------> future

  last backup            failure            recovered
      |                     |                   |
      |<------ RPO -------->|<------ RTO ------>|
  RPO はデータを失う範囲、RTO はサービスが止まる時間
```

- RPO が小さいほど、データを細かく複製する必要があります。RTO が小さいほど、待機している機器が必要です。どちらも小さくするほど費用がかかります。

### 7. 物理と地理の分散

- 1 つの建物にすべてを置くと、火災、停電、地震で全部止まります。**拠点を分けて**(地理的な分散)置くと、拠点全体の障害に耐えられます。
- 拠点が遠いほど災害には強くなりますが、通信が遅れ、データの複製が難しくなります。
- クラウドでは、データセンターの単位(AWS のアベイラビリティーゾーンなど)に分けて置くのが基本です。

## 2.13.2 キャパシティプランニングとスケーラビリティの確保 (重要度2)

### 1. キャパシティプランニング

**キャパシティプランニング**は、将来の負荷を見積もって、必要な資源(CPU、メモリ、ディスク、ネットワーク)を前もって用意する計画です。

見る観点は、次のとおりです。

| 観点 | 例 |
|---|---|
| 今の使用量 | CPU の使用率、メモリ、ディスクの空き、ネットワークの帯域、接続の数 |
| 増え方 | 月ごとの伸び、ボーナスやセールなどの山 |
| 余裕 | ピークでも余裕が残るか。故障で 1 台が抜けても耐えるか |
| 限界 | 何を超えると、応答が遅くなるか(負荷試験で確かめる) |
| 費用と納期 | 買い足しや発注に、どれだけかかるか |

- 監視のデータ(sar、Zabbix など)を溜めて、増え方から読みます。
- 余裕を取りすぎると費用が無駄になり、足りないと止まります。

### 2. スケールアップとスケールアウト

| 言葉 | 向き | 内容 |
|---|---|---|
| スケールアップ(縦) | 1 台を強くする | CPU、メモリ、ディスクを増やす。大きなサーバーに替える |
| スケールダウン | 1 台を弱くする | 資源を減らす |
| スケールアウト(横) | 台数を増やす | 同じ役割のサーバーを足して、負荷を分ける |
| スケールイン | 台数を減らす | サーバーを減らす |

| | スケールアップ | スケールアウト |
|---|---|---|
| アプリの変更 | 要らないことが多い | 複数台で動く作りが要る |
| 限界 | 1 台の上限がある | 台数を増やせば上がる |
| 障害 | 1 台なので SPOF のまま | 1 台が壊れても残りで続けられる |
| 止める必要 | 物理の増設は止めることが多い | 動かしたまま足せる |

### 3. スケールアウトできるアプリの作り方

台数を増やしたとき、どのサーバーに当たっても同じように動くことが必要です。

- **ステートレス**は、サーバーが利用者ごとの状態を持たない作りです。どのサーバーでも同じ答えが返せるので、台数を自由に増減できます。
- **セッション**は、ログインの状態など、利用者ごとに続く情報です。サーバーの中に持つと、別のサーバーに当たったときに、ログインが切れます。
- 対策は、次のとおりです。
  - セッション情報を、共通のストア(Redis、Memcached、データベース)に置く。
  - 同じ利用者を、同じサーバーに振り分ける(セッション維持、スティッキーセッション)。ただし、そのサーバーが落ちると失われる。
  - 状態を、利用者側(Cookie や署名付きトークン)に持たせる。
- アップロードされたファイルも、サーバー内のディスクに置かず、共有のストレージに置きます。
- **データベース**は、状態を持つので、単純には増やせません。読み取りを複製に分ける(2.13.4)、データを分割する(シャーディング)などの工夫が要ります。

```text
[state in the server: hard to scale]
  user A --> [web 1: has A's session]
  user A --> [web 2: does not know A]  --> ログインが切れる

[state in a shared place: easy to scale]
  [web 1] --+
  [web 2] --+--> [session store (Redis etc.)]
  [web 3] --+
```

### 4. 台数の増減

- 台数を足すときは、手作業で設定すると時間がかかり、ミスも出ます。次のどちらかで、同じ状態のサーバーを作ります。
  - 設定管理の道具(Ansible など)で、新しいサーバーの設定を自動で行う。
  - 設定済みの **VM イメージ**(テンプレート)から、サーバーを起動する。
- 足したサーバーは、ロードバランサーの振り分け先に登録します。減らすときは、先に振り分けから外し、処理中のものが終わってから止めます。

### 5. ロードバランサーと DNS ラウンドロビン

| | ロードバランサー | DNS ラウンドロビン |
|---|---|---|
| 仕組み | 通信を受けて、サーバーに振り分ける装置やソフト | 1 つの名前に、複数の IP アドレスを登録して、順に返す |
| 故障の検知 | ヘルスチェックで見つけて、外せる | できない。落ちたサーバーの IP アドレスも返してしまう |
| 振り分け | 接続の数や重みなどで調整できる | 順番に返すだけ |
| 注意 | LB 自身が SPOF になるので冗長化する | DNS のキャッシュの間は、変更が反映されない |

- ここでの DNS ラウンドロビンは、BIND などの一般的な DNS サーバーで、同じ名前に複数の A レコードを登録するものです。クラウドの DNS には、ヘルスチェックで落ちたサーバーを外せるもの(AWS の Route 53 など)もあります。
- ロードバランサーの例は、HAProxy、nginx、Apache、LVS、クラウドのロードバランサー(AWS の ELB など)です。
- 振り分けの方式には、順番に回す(ラウンドロビン)、つなぎ中の数が少ないところへ送る(最小接続)、送信元ごとに同じ先へ送る(ハッシュ)などがあります。
- DNS ラウンドロビンは、簡単で安くできます。拠点をまたいだ大まかな分散や、補助的な使い方に向きます。

## 2.13.3 クラウドサービス上のシステム構成 (重要度2)

### 1. IaaS 中心の構成

**IaaS**(Infrastructure as a Service)は、仮想マシン、ネットワーク、ストレージを、必要な量だけ借りる形のクラウドです。OS から上を、利用者が管理します。(AWS の EC2、OpenStack など)

- 借りるものは、**インスタンス**(仮想マシン)、ネットワーク、ストレージ、ファイアウォールの規則などです。
- 台数や容量を、画面や API で、すぐに増やしたり減らしたりできます。使った分だけ払います。
- オンプレミス(自社で機器を持つ)と違い、発注や設置を待たずに、資源を足せます。

### 2. ストレージの種類

| 種類 | 内容 | インスタンスを消すと |
|---|---|---|
| 一時ストレージ(エフェメラル) | インスタンスと一緒に作られるディスク | 消える |
| ブロックストレージ(ボリューム) | 独立したディスク。インスタンスにつないで使う(AWS の EBS、OpenStack の Cinder) | 残る(永続) |
| オブジェクトストレージ | HTTP の API で、ファイルをオブジェクトとして出し入れする。ブロックデバイスではないので、ファイルシステムを作って使うことはできない(mount する道具はあるが、ふつうは HTTP の API で使う)(AWS の S3、OpenStack の Swift) | 残る(永続) |

- 大事なデータは、**永続ストレージ**(ボリュームやオブジェクトストレージ)に置きます。一時ストレージには、消えてもよいものだけを置きます。
- オブジェクトストレージは、容量を気にせず、画像やバックアップを置くのに向きます。

### 3. ネットワークの種類

| 種類 | 内容 |
|---|---|
| テナントネットワーク | 利用者(テナント)ごとに分けられた、専用の仮想のネットワーク。ほかの利用者からは見えない |
| 外部ネットワーク | インターネットなど、クラウドの外とつながるネットワーク |

- **テナント**は、クラウドを使う利用者やプロジェクトの単位です。
- インスタンスには、テナントネットワークの**固定 IP アドレス**(プライベートアドレス。インスタンスの間は変わらない)が付きます。
- 外から入れるようにするときは、**フローティング IP アドレス**(外に見せる IP アドレス)を、インスタンスに付け替えられる形で割り当てます。インスタンスを作り直しても、アドレスを新しいインスタンスに付け替えれば、利用者から見て変わりません。(AWS の Elastic IP に近い)

### 4. ネットワークのセキュリティ

**セキュリティグループ**は、インスタンスに付ける、通信の許可の規則の集まりです。

- 許可する通信(プロトコル、ポート、相手の IP アドレス)を書きます。書いていない通信は、拒否されます。
- 例: Web インスタンスには、80 と 443 を全体から許可する。DB には、3306 を Web のグループからだけ許可する。
- 22(SSH)は、管理者の IP アドレスだけに許可します。全体に開けません。
- OS のファイアウォール(firewalld、ufw)と、二重に守ります。

### 5. 使われる主な技術

| 技術 | 内容 |
|---|---|
| オートスケール(オートスケーラー) | 負荷の指標(CPU など)で、台数を自動で増減する(AWS の Auto Scaling) |
| メッセージキュー | 処理の依頼を一時的に溜める待ち行列。送る側と処理する側を切り離す(RabbitMQ、AWS の SQS) |
| オブジェクトストレージ | 前の節の説明のとおり |
| 設定管理や、イメージからの起動 | 同じ構成を、短時間で再現する |

- オートスケールは、台数の下限と上限を決めておきます。上限がないと、費用が増え続けます。
- OpenStack は、IaaS を作るためのオープンソースのソフトウェアです。LinuC では、特定の製品の細かい操作ではなく、考え方が問われます。

## 2.13.4 典型的なシステムアーキテクチャ (重要度3)

### 1. LAMP と LAPP

小さな Web システムの、よくある組み合わせです。

| 名前 | L | A | M / P | P |
|---|---|---|---|---|
| LAMP | Linux | Apache HTTP Server | MySQL(または MariaDB) | PHP |
| LAPP | Linux | Apache HTTP Server | PostgreSQL | PHP |

- 1 台に全部を入れると、構成は簡単ですが、1 台の故障で全部止まります。
- 最後の P は、PHP のほか Perl や Python を指すこともあります。【要確認】

### 2. 3 層構成

役割ごとに 3 つに分ける構成です。

| 層 | 役割 | 例 |
|---|---|---|
| プレゼンテーション層(Web) | 画面を返す。静的なファイルを返す | nginx、Apache HTTP Server |
| アプリケーション層(AP) | 業務の処理 | PHP、Java、Python のアプリ |
| データ層(DB) | データを保存する | MySQL、PostgreSQL |

- 層ごとに、台数を変えたり、強くしたりできます。層の間の通信は、必要なところだけ許可します。DB は、外から直接つなげない場所に置きます。

### 3. 冗長にした 3 層構成

```text
          [user]
             |
     [LB 1]  [LB 2]          keepalived (VRRP) などで冗長にする
             |
   [web 1] [web 2] [web 3]
             |
      [AP 1]  [AP 2]
             |
   [db primary] ==> [db standby]     レプリケーション
```

- 各層で、最低 2 台にします。ロードバランサーも、冗長にします。
- **レプリケーション**は、データベースの内容を、別のサーバーに自動で複製することです。更新を受ける主(プライマリ、MySQL では source)から、読み取り用の副(レプリカ)に写します。
- 主が壊れたら、副を主に昇格します(フェイルオーバー)。MySQL にも PostgreSQL にも、レプリケーションの機能があります。
- 副は、読み取りを引き受けて、主の負荷を軽くするのにも使います。非同期のレプリケーションは、副が少し遅れるので、RPO が 0 にならないことがあります。

### 4. 台数を増やせる Web 構成

- 手前にロードバランサーか、DNS ラウンドロビンを置き、Web サーバーを横に並べます。
- Web サーバーはステートレスにして、台数を増減します(スケールアウト)。状態は DB や共通のストアに置きます。
- 負荷が上がるときだけ台数を増やす(オートスケール)と、費用を抑えられます。

### 5. プロキシのキャッシュと CDN

| 仕組み | 内容 | 例 |
|---|---|---|
| プロキシのキャッシュ | 手前のプロキシが、1 度取ったデータを覚えておき、同じ要求に、元のサーバーに行かずに返す。元の負荷が減る | Squid、Varnish、nginx のキャッシュ |
| リバースプロキシ | サーバーの前に置き、要求を受けて中のサーバーへ渡す(キャッシュや LB も兼ねる) | nginx、HAProxy |
| CDN | 世界中の拠点に、画像やファイルのコピーを置き、利用者に近い拠点から返す(Content Delivery Network) | Akamai、AWS の CloudFront |

- キャッシュに向くのは、変わらない静的なファイル(画像、CSS、JavaScript)です。
- 元のデータを変えたのに、古いキャッシュが残ることがあります。有効期限(TTL)を決めたり、キャッシュを消したりします。

### 6. メッセージキューによる非同期の処理

**同期**の処理は、依頼を出して、終わるまで待ちます。**非同期**の処理は、依頼を**メッセージキュー**に入れたら、すぐに次へ進みます。別のワーカー(処理する側)が、キューから取って処理します。

```text
[sync]
  [web] --request--> [heavy job] --result--> [web]
  終わるまで待つ

[async]
  [web] --> [message queue] --> [worker 1]
    |                      `--> [worker 2]
    |
  すぐ「受け付けました」と返す
```

- 画像の変換、メールの送信、集計など、時間のかかる処理に向きます。
- アクセスが急に増えても、キューに溜まるだけで、受け付けは止まりません。ワーカーの台数を増やして、溜まりを減らします。
- ワーカーが落ちても、メッセージはキューに残ります。同じメッセージが 2 回処理されても困らないように作ります。
