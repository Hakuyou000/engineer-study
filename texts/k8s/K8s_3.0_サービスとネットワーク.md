# K8s テキスト 3.0 サービスとネットワーク(20%)

Pod 同士の通信の仕組み、Service、NetworkPolicy、外からの通信の入口(Ingress と Gateway API)、CoreDNS を学びます。

## 3.1 Pod の間の通信

### 1. Kubernetes のネットワークのモデル〔CKA〕

- **すべての Pod は、それぞれ固有の IP を持ちます**。
- どのノードの Pod とも、**NAT なしで直接通信できます**(既定では全部が通信できる)。
- 同じ Pod の中のコンテナは、ネットワークを共有し、`localhost` で通信します。
- この仕組みを実際に作るのは **CNI プラグイン**(Calico、Cilium、Flannel など)です。CNI がないと Pod に IP が付かず、ノードは NotReady です。

| 範囲 | 決めるもの |
|---|---|
| Pod の IP の範囲 | `kubeadm init --pod-network-cidr` と CNI の設定 |
| Service の IP の範囲 | API サーバーの `--service-cluster-ip-range`(既定 10.96.0.0/12) |

NetworkPolicy を使うには、それに対応した CNI(Calico、Cilium など)が必要です。Flannel だけでは NetworkPolicy は効きません。

## 3.2 Service とエンドポイント

### 1. Service が必要な理由〔CKA〕

Pod は作り直されるたびに IP が変わります。**Service** は、ラベルで選んだ Pod の集まりに、**変わらない仮想 IP と DNS 名**を与え、通信を振り分けます。

```yaml
apiVersion: v1
kind: Service
metadata: { name: web }
spec:
  type: ClusterIP
  selector:
    app: web            # このラベルの Pod に振り分ける
  ports:
    - port: 80          # Service のポート
      targetPort: 8080  # Pod(コンテナ)のポート
```

```bash
kubectl expose deployment web --port=80 --target-port=8080
kubectl expose deployment web --type=NodePort --port=80 --target-port=8080
```

Service が通信を Pod に振り分ける様子です。

```text
[client Pod]
    |
    v
[Service web]    仮想 IP と DNS 名は変わらない。port: 80
    |
    +----------------+----------------+
    |                |                |
    v                v                v
[Pod A]          [Pod B]          [Pod C]       app=web のラベルを持つ Ready の Pod。targetPort: 8080
```

### 2. Service の種類〔CKA〕

| type | 届く範囲 | 動き |
|---|---|---|
| **ClusterIP**(既定) | クラスタの中だけ | 仮想 IP を割り当てる |
| **NodePort** | クラスタの外から | 全ノードの同じポート(既定 30000〜32767)で受け、ClusterIP に転送する |
| **LoadBalancer** | 外から | クラウドのロードバランサーを作り、NodePort に流す(クラウドの連携が必要) |
| ExternalName | - | クラスタの外の DNS 名の別名(CNAME)を返す |
| ヘッドレス(`clusterIP: None`) | - | 仮想 IP を作らず、DNS で各 Pod の IP を返す(StatefulSet で使う) |

LoadBalancer ⊃ NodePort ⊃ ClusterIP の関係です(LoadBalancer を作ると NodePort と ClusterIP も作られる)。

```text
LoadBalancer  [cloud LB] --> [NodeIP:NodePort] --> [ClusterIP] --> [Pod]
NodePort                     [NodeIP:NodePort] --> [ClusterIP] --> [Pod]
ClusterIP                                          [ClusterIP] --> [Pod]
```

矢印は type の包含関係を表します。実際のパケットは ClusterIP の IP を通らず、kube-proxy のルールで Pod に振り分けられます。

### 3. エンドポイント〔CKA〕

- Service の selector に合い、**Ready の Pod の IP とポート**の一覧が、**EndpointSlice** に記録されます。kube-proxy はこれを見て振り分けます。
- 古い Endpoints の API は v1.33 で非推奨になり、EndpointSlice が使われます。

```bash
kubectl get endpointslices -l kubernetes.io/service-name=web
kubectl describe svc web          # Endpoints の欄も表示される
```

**エンドポイントが空なら**、Service は通信を届けられません。原因は次のどれかです。

- selector と Pod のラベルが合っていない
- Pod が Ready になっていない(readinessProbe の失敗など)
- Pod がない

## 3.3 NetworkPolicy

### 1. 基本〔CKA〕

- 既定では、すべての Pod が互いに通信できます。
- ある Pod を選ぶ NetworkPolicy が 1 つでもできると、その Pod は**ポリシーで許可した通信だけ**を受け付ける(送る)ようになります。
- ルールは**許可だけ**です。複数のポリシーは足し算(どれかで許可されれば通る)。
- `policyTypes` に `Ingress`(受信)と `Egress`(送信)を書きます。

### 2. 例〔CKA〕

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: db-allow-api, namespace: prod }
spec:
  podSelector:
    matchLabels: { app: db }          # このポリシーが守る Pod
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels: { app: api } # 同じ Namespace の api の Pod から
      ports:
        - protocol: TCP
          port: 5432
```

### 3. from の書き方の違い〔CKA〕

```yaml
# (1) 2 つの要素: どちらか(OR)
- from:
    - namespaceSelector: { matchLabels: { team: a } }
    - podSelector: { matchLabels: { app: api } }

# (2) 1 つの要素の中に両方: 両方(AND)
- from:
    - namespaceSelector: { matchLabels: { team: a } }
      podSelector: { matchLabels: { app: api } }
```

| 書き方 | 意味 |
|---|---|
| (1) `-` が 2 つ | team=a の Namespace の全 Pod、**または**、このポリシーと同じ Namespace の app=api の Pod |
| (2) `-` が 1 つ | team=a の Namespace の中の、app=api の Pod だけ |

`-` の位置 1 つで意味が大きく変わるので、試験でよく問われます。

### 4. よく使うポリシー〔CKA〕

```yaml
# Namespace のすべての Pod の受信を拒否する(default deny)
spec:
  podSelector: {}         # 空 = Namespace のすべての Pod
  policyTypes: [Ingress]  # ingress のルールがない = 何も許可しない
```

- 送信(Egress)を拒否すると、**DNS(UDP/TCP 53 番)も止まり**、名前解決ができなくなります。Egress を絞るときは、kube-system の CoreDNS への 53 番を許可します。

## 3.4 Ingress と Gateway API

### 1. Ingress〔CKA〕

HTTP/HTTPS の通信を、ホスト名やパスで Service に振り分けます。**Ingress のリソースだけでは動かず、Ingress コントローラーが必要です**。

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: web }
spec:
  ingressClassName: nginx
  tls:
    - hosts: [shop.example.com]
      secretName: shop-tls
  rules:
    - host: shop.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service: { name: api, port: { number: 80 } }
          - path: /
            pathType: Prefix
            backend:
              service: { name: web, port: { number: 80 } }
```

| pathType | 意味 |
|---|---|
| Prefix | パスの先頭が一致(`/api` は `/api/v1` にも一致) |
| Exact | 完全一致 |

Ingress のコントローラーが、リクエストを Service に振り分ける様子です。

```text
[client]
    |  https://shop.example.com/api/v1
    v
[Ingress controller]
    |
    +-- host: shop.example.com, path: /api  --> [Service api] --> [Pod]    /api/v1 はここ(長く一致した方が選ばれる)
    |
    +-- host: shop.example.com, path: /     --> [Service web] --> [Pod]
```

```bash
kubectl create ingress web --class=nginx --rule="shop.example.com/api*=api:80"
```

### 2. Gateway API〔CKA〕

Ingress の後継として作られた、より表現力のある API です。役割ごとにリソースが分かれています。

| リソース | 作る人 | 役割 |
|---|---|---|
| **GatewayClass** | インフラの提供者 | どのコントローラーの実装を使うか |
| **Gateway** | クラスタの運用者 | 入口(リスナー: ポート、プロトコル、ホスト名、TLS) |
| **HTTPRoute** | アプリの開発者 | どのホスト・パスを、どの Service に送るか(重み付けもできる) |

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata: { name: shop-gw }
spec:
  gatewayClassName: example
  listeners:
    - name: http
      protocol: HTTP
      port: 80
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: shop }
spec:
  parentRefs:
    - name: shop-gw          # どの Gateway につなぐか
  hostnames: [shop.example.com]
  rules:
    - matches:
        - path: { type: PathPrefix, value: /api }
      backendRefs:
        - name: api-v1
          port: 80
          weight: 90
        - name: api-v2
          port: 80
          weight: 10         # 1 割だけ新しい版へ(カナリア)
```

- Gateway API の CRD とコントローラーを入れて使います(Kubernetes 本体には CRD が入っていない)。
- 別の Namespace の Service を参照するには、相手の Namespace に **ReferenceGrant** が必要です。

### 3. Ingress NGINX の終了〔実務〕

- 広く使われていたコミュニティ版の Ingress NGINX コントローラー(kubernetes/ingress-nginx)は、**2026 年 3 月に保守が終了**しました。これ以降、脆弱性の修正も出ません。
- Ingress の API 自体は残りますが、新しい構成では **Gateway API** を使うのが推奨されます。既存のものは移行を計画します(Ingress を Gateway API に変換する ingress2gateway というツールもある)。

## 3.5 CoreDNS

### 1. 名前の形〔CKA〕

| 対象 | 名前 |
|---|---|
| Service | `<Service 名>.<Namespace>.svc.cluster.local` |
| 同じ Namespace から | `<Service 名>` だけでよい |
| 別の Namespace から | `<Service 名>.<Namespace>`(以上) |
| ヘッドレス Service の各 Pod(StatefulSet) | `<Pod 名>.<Service 名>.<Namespace>.svc.cluster.local` |
| Pod | `<IP のドットをハイフンにしたもの>.<Namespace>.pod.cluster.local` |

Pod の `/etc/resolv.conf` には、CoreDNS の Service の IP(kube-dns、例: 10.96.0.10)と、検索ドメイン(`<ns>.svc.cluster.local svc.cluster.local cluster.local`)が書かれています。

### 2. ndots と名前の問い合わせ〔実務〕

Pod の `/etc/resolv.conf` には `options ndots:5` も書かれています。

- 名前のドットが 5 つ未満なら、まず検索ドメインを順に付けて問い合わせます。そのため、`web` だけで同じ Namespace の Service を引けます。
- その代わり、`api.example.com`(ドットは 2 つ)のような外部の名前でも、`api.example.com.prod.svc.cluster.local` などの無駄な問い合わせを先に何回も行います。

- 外部の名前の問い合わせが多いアプリでは、次のどちらかで減らします。
  - 名前の最後にドットを付けて、完全な名前(FQDN)にする: `api.example.com.`
  - Pod の `dnsConfig` で ndots を小さくする

```yaml
spec:
  dnsConfig:
    options:
      - name: ndots
        value: "2"
```

Namespace が prod の Pod が `api.example.com` を引くときの順番です。

```text
1. api.example.com.prod.svc.cluster.local   見つからない
2. api.example.com.svc.cluster.local        見つからない
3. api.example.com.cluster.local            見つからない
4. api.example.com                          見つかる
```

ノードの `/etc/resolv.conf` の検索ドメインも足されることがあり、そのときは問い合わせがさらに増えます。

### 3. 設定と調査〔CKA〕

- CoreDNS は kube-system の Deployment で、設定は ConfigMap `coredns` の **Corefile** です。
- 名前解決を確かめるには、一時的な Pod から調べます。

```bash
kubectl run dnstest --rm -it --image=busybox:1.37 --restart=Never -- nslookup web.prod
kubectl -n kube-system get pods -l k8s-app=kube-dns
kubectl -n kube-system logs -l k8s-app=kube-dns
```

### まとめ: よく出る判断

| 問われ方 | 答え |
|---|---|
| Service の既定の type | ClusterIP |
| 全ノードの決まったポートで外から受ける | NodePort(30000〜32767) |
| Service のエンドポイントが空 | selector とラベルの不一致、Pod が Ready でない |
| `port` と `targetPort` | Service のポート / Pod のポート |
| NetworkPolicy が効かない | CNI が対応していない(Flannel だけなど) |
| Egress を絞ったら名前解決ができない | DNS(53 番)を許可していない |
| `-` が 1 つで namespaceSelector と podSelector | AND |
| Ingress が動かない | Ingress コントローラーがない、ingressClassName の誤り |
| Gateway API のアプリ側のリソース | HTTPRoute |
| 別の Namespace の Service の名前 | `<svc>.<ns>` |
