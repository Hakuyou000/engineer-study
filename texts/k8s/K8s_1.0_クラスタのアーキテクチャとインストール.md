# K8s テキスト 1.0 クラスタのアーキテクチャ、インストール、設定(25%)

Kubernetes のクラスタがどんな部品でできているか、kubectl とマニフェストの扱い方、権限(RBAC)、kubeadm でのクラスタの構築と更新、Helm と Kustomize、拡張の仕組みを学びます。

## 1.1 クラスタの構成要素

### 1. コントロールプレーンとワーカーノード〔CKA〕

```
            ┌──────────── コントロールプレーン ────────────┐
kubectl ──▶ │ kube-apiserver ◀──▶ etcd                     │
            │   ▲     ▲                                      │
            │   │     └─ kube-scheduler                      │
            │   └─────── kube-controller-manager             │
            └──────────────────────────────────────────────┘
                      ▲ (すべて API サーバーを通す)
            ┌──── ワーカーノード ────┐
            │ kubelet ── コンテナランタイム(containerd) │
            │ kube-proxy                │
            └───────────────────────────┘
```

| 部品 | 場所 | 役割 |
|---|---|---|
| **kube-apiserver** | コントロールプレーン | すべての操作の入口。認証・認可をして、etcd に読み書きする唯一の部品 |
| **etcd** | コントロールプレーン | クラスタのすべての状態を保存するキーバリューストア。失うとクラスタを失う |
| **kube-scheduler** | コントロールプレーン | 新しい Pod をどのノードに置くかを決める(決めるだけで、起動はしない) |
| **kube-controller-manager** | コントロールプレーン | Deployment、ReplicaSet、Node などのコントローラーを動かし、あるべき状態に近づける |
| cloud-controller-manager | コントロールプレーン | クラウドのロードバランサーやノードとの連携(クラウドの場合) |
| **kubelet** | 各ノード | API サーバーから割り当てられた Pod を、コンテナランタイムで起動し、状態を報告する |
| **kube-proxy** | 各ノード | Service の仮想 IP への通信を、Pod に振り分けるルール(iptables / IPVS / nftables)を作る |
| コンテナランタイム | 各ノード | containerd、CRI-O など。CRI で kubelet とつながる |

- 部品同士は直接話さず、**すべて API サーバーを通します**。
- Kubernetes は「あるべき状態(spec)」と「今の状態(status)」を比べ、差をなくし続けます(**調整ループ**)。

### 2. 静的 Pod〔CKA〕

kubeadm のクラスタでは、API サーバー、etcd、スケジューラー、コントローラーマネージャーは、**静的 Pod** として動いています。

- kubelet が、ノードの **`/etc/kubernetes/manifests/`** の YAML を直接読んで起動する Pod です。API サーバーがなくても動きます。
- このディレクトリの YAML を編集すると、kubelet が自動で Pod を作り直します。削除すると Pod が止まります。
- `kubectl get pods -n kube-system` で見えますが(ミラー Pod)、kubectl で削除しても kubelet が作り直します。

### 3. 主なリソースの関係〔CKA〕

| リソース | 役割 |
|---|---|
| Namespace | クラスタの中の区切り(チームや環境ごと) |
| Pod | コンテナを動かす最小の単位 |
| Deployment → ReplicaSet → Pod | ステートレスなアプリ。ローリングアップデート |
| Service | Pod の集まりへの安定した入口 |
| ConfigMap / Secret | 設定と秘密情報 |
| PersistentVolumeClaim | ストレージの要求 |

## 1.2 kubectl とマニフェスト

### 1. 命令的な方法と宣言的な方法〔CKA〕

| 方法 | 例 | 向いている場面 |
|---|---|---|
| 命令的 | `kubectl create deployment web --image=nginx:1.27 --replicas=3` | すばやく作る、下書きを作る |
| 宣言的 | `kubectl apply -f web.yaml` | Git で管理し、差分を適用する(本番の基本) |

試験では、YAML を一から書かずに下書きを作ると速く解けます。

```bash
kubectl create deployment web --image=nginx:1.27 --replicas=3 --dry-run=client -o yaml > web.yaml
kubectl run tmp --image=busybox:1.37 --restart=Never --dry-run=client -o yaml -- sleep 3600
kubectl expose deployment web --port=80 --target-port=8080 --dry-run=client -o yaml
```

| コマンド | 用途 |
|---|---|
| `kubectl apply -f` | 作る・更新する(宣言的) |
| `kubectl create -f` | 作る(すでにあるとエラー) |
| `kubectl replace --force -f` | 削除して作り直す(変えられない項目を変えるとき) |
| `kubectl edit` | 動いているリソースをエディターで直す |
| `kubectl delete` | 削除する |
| `kubectl explain pod.spec.containers` | フィールドの説明(ドキュメントを開かずに書き方を調べる) |
| `kubectl api-resources` | リソースの種類、短い名前、Namespace の単位かどうか |

### 2. 出力と絞り込み〔CKA〕

```bash
kubectl get pods -o wide                      # ノードと IP も表示
kubectl get pod web-0 -o yaml                 # 全部の項目
kubectl get pods -l app=web                   # ラベルで絞る
kubectl get pods -A                           # 全 Namespace
kubectl get nodes -o jsonpath='{.items[*].status.addresses[?(@.type=="InternalIP")].address}'
kubectl get pods --sort-by=.metadata.creationTimestamp
```

### 3. kubeconfig とコンテキスト〔CKA〕

- kubectl の接続先と認証情報は **kubeconfig**(既定は `~/.kube/config`、環境変数 `KUBECONFIG`)に書きます。
- **コンテキスト** = クラスタ + ユーザー + Namespace の組み合わせです。

```bash
kubectl config get-contexts
kubectl config use-context prod-cluster
kubectl config set-context --current --namespace=web
```

試験では問題ごとに使うコンテキストが指定されます。**必ず切り替えてから作業します**。

## 1.3 RBAC(ロールベースのアクセス制御)

### 1. 4 つのリソース〔CKA〕

| リソース | 範囲 | 役割 |
|---|---|---|
| **Role** | 1 つの Namespace | 何に何をしてよいか(権限の一覧) |
| **ClusterRole** | クラスタ全体 | 同上。ノードなどクラスタ単位のリソースや、全 Namespace に使う権限 |
| **RoleBinding** | 1 つの Namespace | Role(または ClusterRole)を、ユーザー・グループ・ServiceAccount に結び付ける |
| **ClusterRoleBinding** | クラスタ全体 | ClusterRole を、クラスタ全体で結び付ける |

```bash
kubectl create role pod-reader --verb=get,list,watch --resource=pods -n dev
kubectl create rolebinding read-pods --role=pod-reader --user=alice -n dev
kubectl create clusterrole node-viewer --verb=get,list --resource=nodes
kubectl create clusterrolebinding view-nodes --clusterrole=node-viewer --serviceaccount=monitoring:agent
```

- RBAC は**許可だけ**です。拒否のルールはなく、何も許可されていなければ拒否されます。
- **RoleBinding に ClusterRole を結び付ける**と、その ClusterRole の権限を、**その Namespace の中だけ**で与えられます(共通の権限を使い回す方法)。
- 権限を確かめるには `kubectl auth can-i` を使います。

```bash
kubectl auth can-i list pods -n dev --as alice
kubectl auth can-i create deployments --as system:serviceaccount:dev:ci -n dev
```

### 2. ServiceAccount〔CKA〕

- Pod の中のプログラムが API サーバーに接続するときの ID です。Namespace ごとに `default` があります。
- Pod の `spec.serviceAccountName` で指定します。トークンは、有効期限のある投影されたトークンとして Pod に自動でマウントされます(不要なら `automountServiceAccountToken: false`)。
- 必要な権限だけを Role で与え、RoleBinding で ServiceAccount に結び付けます(`--serviceaccount=Namespace:名前`)。

## 1.4 kubeadm によるクラスタの構築と管理

### 1. 準備するもの〔CKA〕

| 項目 | 内容 |
|---|---|
| スワップ | 既定では無効にする(kubelet の要件) |
| カーネルの設定 | `overlay` と `br_netfilter` のモジュール、`net.ipv4.ip_forward = 1` |
| コンテナランタイム | containerd など。**cgroup ドライバーを kubelet と同じ systemd にそろえる** |
| パッケージ | kubeadm、kubelet、kubectl(`pkgs.k8s.io` のマイナーバージョンごとのリポジトリ) |
| ポート | 6443(API サーバー)、2379-2380(etcd)、10250(kubelet)など |

### 2. 構築の流れ〔CKA〕

```bash
# コントロールプレーンで
sudo kubeadm init --pod-network-cidr=10.244.0.0/16
mkdir -p $HOME/.kube && sudo cp /etc/kubernetes/admin.conf $HOME/.kube/config
kubectl apply -f <CNI プラグインのマニフェスト>     # これを入れるまでノードは NotReady

# ワーカーノードで(init の最後に表示されたコマンド)
sudo kubeadm join 192.168.1.10:6443 --token … --discovery-token-ca-cert-hash sha256:…
```

- join のトークンの有効期限は既定で 24 時間です。新しく作るには `kubeadm token create --print-join-command` を使います。
- **CNI プラグインを入れるまで、ノードは NotReady**、CoreDNS は Pending のままです。

### 3. アップグレード〔CKA〕

マイナーバージョンは**1 つずつ**上げます(1.35 → 1.36 → 1.37)。コントロールプレーンから先に上げ、kubelet は API サーバーより新しくしてはいけません。

| 手順 | コントロールプレーン(1 台目) | ワーカーノード |
|---|---|---|
| 1 | パッケージのリポジトリを新しいマイナーに変え、kubeadm を上げる | kubeadm を上げる |
| 2 | `kubeadm upgrade plan` で確認 | |
| 3 | `kubeadm upgrade apply v1.36.x` | `kubeadm upgrade node` |
| 4 | `kubectl drain <ノード> --ignore-daemonsets` | `kubectl drain <ノード> --ignore-daemonsets`(コントロールプレーンから実行) |
| 5 | kubelet と kubectl を上げ、`systemctl daemon-reload && systemctl restart kubelet` | 同じ |
| 6 | `kubectl uncordon <ノード>` | 同じ |

2 台目以降のコントロールプレーンは `kubeadm upgrade apply` ではなく `kubeadm upgrade node` を使います。

### 4. ノードの保守〔CKA〕

| コマンド | 動き |
|---|---|
| `kubectl cordon ノード` | 新しい Pod を置かないようにする(既存の Pod はそのまま) |
| `kubectl drain ノード --ignore-daemonsets` | cordon して、Pod を退避させる(DaemonSet の Pod は残す)。emptyDir のデータを持つ Pod があると `--delete-emptydir-data` が必要 |
| `kubectl uncordon ノード` | 再び Pod を置けるようにする |

### 5. etcd のバックアップと復元〔CKA〕

```bash
ETCDCTL_API=3 etcdctl snapshot save /backup/etcd.db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key

etcdutl snapshot restore /backup/etcd.db --data-dir /var/lib/etcd-restore
```

- 接続には、エンドポイントと 3 つの証明書(CA、クライアントの証明書、鍵)が必要です。値は `/etc/kubernetes/manifests/etcd.yaml` で確かめられます。
- 復元は新しいディレクトリに行い、**etcd の静的 Pod の YAML の `hostPath`(データのディレクトリ)を新しいディレクトリに変えます**。
- 復元には `etcdutl` が推奨です(`etcdctl snapshot restore` は非推奨)。

### 6. 証明書〔CKA〕

- kubeadm が作る証明書の有効期限は 1 年です。`kubeadm certs check-expiration` で確かめ、`kubeadm certs renew all` で更新します(アップグレードのときにも自動で更新される)。
- 証明書は `/etc/kubernetes/pki/` にあります。

### 7. 高可用性のコントロールプレーン〔CKA〕

| 構成 | 内容 |
|---|---|
| 積み重ね型(stacked etcd) | 各コントロールプレーンのノードに etcd も置く。台数が少なくて済む |
| 外部 etcd | etcd を別のノード群に置く。障害の影響を分けられるが台数が増える |

- コントロールプレーンは **3 台以上の奇数**にします。etcd は過半数(3 台なら 2 台)が動いていないと書き込めません(クォーラム)。
- 複数の API サーバーの前にロードバランサーを置き、`kubeadm init --control-plane-endpoint=LB のアドレス:6443 --upload-certs` で作ります。

### 8. マネージドの Kubernetes〔実務〕

本番では、EKS(AWS)、GKE(Google Cloud)、AKS(Azure)などのマネージドのサービスを使うことが多くなります。

| | kubeadm(自前) | マネージド(EKS など) |
|---|---|---|
| コントロールプレーンの運用 | 自分(etcd のバックアップ、証明書、アップグレード) | クラウドが行う |
| ノード | 自分 | マネージドのノードグループや Fargate も選べる |
| 学ぶ価値 | 仕組みが分かる(CKA の範囲) | 実務の多くはこちら |

マネージドでも、ワークロード、RBAC、ネットワーク、トラブルシューティングの知識はそのまま使えます。

## 1.5 Helm と Kustomize

### 1. Helm〔CKA〕

**Helm** は Kubernetes のパッケージマネージャーです。**チャート**(テンプレートと既定値の集まり)に値を渡して、マニフェストを作って入れます。入れたものを**リリース**と呼びます。

```bash
helm repo add podinfo https://stefanprodan.github.io/podinfo
helm repo update
helm search repo podinfo
helm show values podinfo/podinfo > values.yaml          # 設定できる値を確かめる
helm install web podinfo/podinfo -n web --create-namespace -f values.yaml
helm install web podinfo/podinfo --set replicaCount=3 --version <チャートのバージョン>
helm list -A
helm upgrade web podinfo/podinfo -f values.yaml
helm rollback web 1                                    # リビジョン 1 に戻す
helm uninstall web -n web
helm template web podinfo/podinfo -f values.yaml         # 入れずにマニフェストだけを表示
```

- `--set` と `-f` で値を上書きします。`--set` が `-f` より優先されます。
- `helm history リリース` でリビジョンの履歴を見られます。

### 2. Kustomize〔CKA〕

**Kustomize** は、テンプレートを使わず、元の YAML(base)に**差分(overlay)**を重ねて環境ごとのマニフェストを作ります。kubectl に組み込まれています。

```
app/
├── base/
│   ├── deployment.yaml
│   ├── service.yaml
│   └── kustomization.yaml      # resources: [deployment.yaml, service.yaml]
└── overlays/
    └── prod/
        ├── kustomization.yaml  # resources: [../../base]、replicas、images、patches
        └── replica-patch.yaml
```

```yaml
# overlays/prod/kustomization.yaml
resources:
  - ../../base
namespace: prod
namePrefix: prod-
labels:
  - pairs:
      env: prod
images:
  - name: myapp
    newTag: "1.4.2"
replicas:
  - name: web
    count: 5
patches:
  - path: replica-patch.yaml
```

```bash
kubectl kustomize overlays/prod          # 結果を表示する
kubectl apply -k overlays/prod           # 適用する
```

| | Helm | Kustomize |
|---|---|---|
| 方式 | テンプレート + 値 | 元の YAML + 差分 |
| 配布 | チャートとして配る(リポジトリ) | ディレクトリ |
| 履歴と戻し | リリースのリビジョンで rollback | なし(Git で管理) |
| 向き | 他人が作ったソフトを入れる | 自分のアプリの環境ごとの差 |

## 1.6 拡張のインターフェース、CRD、オペレーター

### 1. 拡張のインターフェース〔CKA〕

| インターフェース | 役割 | 実装の例 |
|---|---|---|
| **CRI**(Container Runtime Interface) | kubelet とコンテナランタイムをつなぐ | containerd、CRI-O |
| **CNI**(Container Network Interface) | Pod のネットワーク(IP の割り当て、Pod 同士の通信) | Calico、Cilium、Flannel |
| **CSI**(Container Storage Interface) | ストレージ(ボリュームの作成とマウント) | AWS EBS CSI ドライバー など |

インターフェースが決まっているので、Kubernetes 本体を変えずに実装を入れ替えられます。Docker Engine を直接使う dockershim は v1.24 で削除されました。

### 2. CRD とオペレーター〔CKA〕

- **CRD**(CustomResourceDefinition)で、Kubernetes に**新しい種類のリソース**を追加できます(例: `Certificate`、`PostgresCluster`)。
- CRD だけではデータを保存するだけです。そのリソースを見て実際の処理をするのが**カスタムコントローラー**で、運用の知識を組み込んだものを**オペレーター**と呼びます(例: データベースの作成、バックアップ、フェイルオーバーを自動で行う)。

```bash
kubectl get crd
kubectl get crd certificates.cert-manager.io -o yaml
kubectl explain certificate.spec            # CRD のフィールドも explain できる
kubectl get certificates -A
```

オペレーターは、Helm のチャートやマニフェストで入れるのが一般的です。CRD を先に入れないと、そのカスタムリソースは作れません(`no matches for kind`)。

### まとめ: よく出る判断

| 問われ方 | 答え |
|---|---|
| Pod をどのノードに置くか決める部品 | kube-scheduler |
| クラスタの状態を保存する部品 | etcd |
| Pod を実際に起動する部品 | kubelet(コンテナランタイムを使う) |
| 静的 Pod の YAML の場所 | `/etc/kubernetes/manifests/` |
| Namespace の中だけで、ClusterRole の権限を与える | RoleBinding で ClusterRole を結び付ける |
| 権限を確かめる | `kubectl auth can-i … --as …` |
| アップグレードの順番 | 1 マイナーずつ、コントロールプレーン → ワーカー。drain → 上げる → uncordon |
| etcd のバックアップに必要なもの | エンドポイント、CA、証明書、鍵 |
| CNI を入れる前のノード | NotReady |
| 入れずにマニフェストだけを見る | `helm template` / `kubectl kustomize` |
