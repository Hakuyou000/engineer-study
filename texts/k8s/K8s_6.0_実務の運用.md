# K8s テキスト 6.0 実務の運用(試験の範囲外)

CKA の範囲ではありませんが、本番の Kubernetes を運用するときに必ず出てくる知識です。この分野はすべて〔実務〕です。

## 6.1 デプロイの戦略と GitOps

### 1. デプロイの戦略〔実務〕

| 戦略 | 方法 | 特徴 |
|---|---|---|
| ローリングアップデート | Deployment の既定。少しずつ入れ替える | 追加の資源が少ない。新旧が混ざる時間がある |
| Recreate | 全部止めてから新しいものを起動 | 停止時間がある。新旧を同時に動かせないアプリ向け |
| ブルー/グリーン | 新しい環境(グリーン)を丸ごと用意し、Service の selector や Gateway の向き先を一度に切り替える | 戻すのが速い。資源が 2 倍要る |
| カナリア | 新しい版に一部の通信(例: 5%)だけを流し、問題がなければ増やす | 影響を小さく試せる。Gateway API の重みや、Argo Rollouts などで行う |

### 2. GitOps〔実務〕

**GitOps** は、クラスタのあるべき状態を **Git のリポジトリ**に置き、クラスタの中のツールが Git と同じ状態に自動で合わせ続ける運用です。

| 項目 | 内容 |
|---|---|
| 代表的なツール | **Argo CD**、Flux |
| 方式 | **プル型**。クラスタの中のツールが Git を見に行って適用する(CI からクラスタに kubectl apply するプッシュ型と違い、CI にクラスタの強い権限を渡さなくて済む) |
| 利点 | 変更はすべてプルリクエストで残る。手作業の変更(ドリフト)を検出・自動で戻せる。戻すのは Git の revert |

```text
開発者
  |  プルリクエストを出し、マージする
  v
Git(マニフェスト)
  ^
  |  Argo CD が監視して、変更を取り込む(同期)
  |
Argo CD(クラスタの中)
  |  クラスタに適用する
  v
クラスタ
```

マニフェストは、Helm のチャートや Kustomize の overlay として Git に置くのが一般的です。

Secret の値は、Base64 にしただけでは誰でも元に戻せるので、そのまま Git に置きません。次のどれかを使います。

| 方法 | 内容 |
|---|---|
| External Secrets Operator | 外部の保管庫(AWS Secrets Manager、Vault など)の値から Secret を作る。Git には参照だけを書く |
| Sealed Secrets | クラスタの公開鍵で暗号化した値(SealedSecret)を Git に置き、クラスタの中のコントローラーが復号する |
| SOPS | ファイルの値を KMS などの鍵で暗号化して Git に置き、適用のときに復号する(Argo CD や Flux のプラグインで使う) |

## 6.2 可観測性(オブザーバビリティ)

### 1. 3 つの柱〔実務〕

| 種類 | 内容 | 代表的なツール |
|---|---|---|
| メトリクス | 数値の時系列(CPU、リクエストの数、エラーの率、遅延) | **Prometheus**、Grafana、kube-state-metrics、node-exporter |
| ログ | 出来事の記録 | Fluent Bit / Fluentd で集め、Loki、Elasticsearch、CloudWatch Logs に送る |
| トレース | 1 つのリクエストが複数のサービスを通る様子 | OpenTelemetry、Jaeger、Tempo |

### 2. Prometheus のしくみ〔実務〕

- Prometheus は、対象の `/metrics` を**定期的に取りに行く(プル型)**方式で、メトリクスを集めます。
- Kubernetes では、kube-prometheus-stack(Helm のチャート)で、Prometheus、Alertmanager、Grafana、各種の exporter をまとめて入れるのが一般的です。
- **metrics-server と Prometheus の違い**: metrics-server は今の CPU とメモリだけを持ち、`kubectl top` と HPA のためのもの。Prometheus は長期間の、あらゆるメトリクスを保存して、ダッシュボードとアラートに使います。

| exporter | 取るもの |
|---|---|
| node-exporter | ノードの CPU、メモリ、ディスク |
| kube-state-metrics | Kubernetes のリソースの状態(Deployment の希望の数と実際の数、Pod の再起動の回数など) |
| cAdvisor(kubelet に組み込み) | コンテナごとの資源の使用量 |

### 3. 何を監視するか〔実務〕

- 利用者から見た症状を中心にします: **RED**(Rate: リクエストの数、Errors: エラー、Duration: 遅延)、**4 つのゴールデンシグナル**(遅延、トラフィック、エラー、飽和)。
- 原因に近いものも見ます: Pod の再起動の回数、OOMKilled、Pending の Pod、ノードの NotReady、PVC の空き、証明書の期限。
- アラートは「人がすぐ対応すべきこと」だけにし、SLO に基づいて決めます。

| 用語 | 意味 | 例 |
|---|---|---|
| SLI(Service Level Indicator) | 信頼性を計る指標 | 成功したリクエストの割合、遅延が 300 ms 以内の割合 |
| SLO(Service Level Objective) | SLI の目標 | 30 日間で 99.9% のリクエストが成功する |
| SLA(Service Level Agreement) | 利用者との契約。守れないと返金などがある | 99.5% を下回ったら料金の一部を返す |
| エラーバジェット | SLO で許される失敗の量(100% − SLO) | 99.9% なら 0.1% |

エラーバジェットを消費する速さ(バーンレート)でアラートを出すのが代表的な方法です。

## 6.3 信頼性を高める設定

### 1. PodDisruptionBudget(PDB)〔実務〕

ノードの drain やクラスタのアップグレードのような**計画的な中断**のときに、同時に止めてよい Pod の数を制限します。

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: web-pdb }
spec:
  minAvailable: 2          # または maxUnavailable: 1
  selector:
    matchLabels: { app: web }
```

- drain は、PDB を守れない場合、Pod の退避を待ちます(途中で止まる)。
- **ノードの故障のような計画外の停止は防げません**。
- `minAvailable` を replicas と同じにすると、drain が永遠に終わらなくなります。

### 2. 分散して置く〔実務〕

同じアプリの Pod が 1 つのノードやゾーンに偏ると、そこが止まったときに全部止まります。**topologySpreadConstraints** でゾーンやノードに均等に散らします。

```yaml
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels: { app: web }
```

### 3. 安全な停止(graceful shutdown)〔実務〕

Pod が削除されるとき:

1. Pod が Terminating になり、Service のエンドポイントから外される(並行して進む)
2. `preStop` のフックを実行する
3. コンテナに SIGTERM を送る
4. `terminationGracePeriodSeconds`(既定 30 秒)たっても終わらなければ SIGKILL

エンドポイントから外れる前に SIGTERM でアプリが止まると、一部のリクエストがエラーになります。`preStop` で数秒待つ、アプリで SIGTERM を受けたら新しい受け付けを止めて処理中のものを終える、が定石です。

### 4. requests と limits の決め方〔実務〕

| 指針 | 理由 |
|---|---|
| requests は実際の使用量(Prometheus で測る)に合わせる | 少なすぎるとノードに詰め込まれて遅くなる。多すぎると無駄な費用 |
| メモリは requests = limits にすることが多い | メモリは使いすぎると OOMKilled。予測しやすくする |
| CPU の limits は付けないこともある | 付けるとスロットリングで遅延が増えることがある。チームの方針で決める |
| 重要なものは Guaranteed の QoS にする | 資源が足りないときに追い出されにくい |

## 6.4 セキュリティ

### 1. Pod Security Standards〔実務〕

古い PodSecurityPolicy は v1.25 で削除されました。今は **Pod Security Admission** で、Namespace のラベルにより 3 つの基準を適用します。

| 基準 | 内容 |
|---|---|
| privileged | 制限なし |
| baseline | 明らかに危険なもの(特権コンテナ、hostNetwork など)を禁止 |
| restricted | さらに厳しく(root で動かさない、ケーパビリティを外す など) |

```bash
kubectl label namespace prod pod-security.kubernetes.io/enforce=restricted
```

モードには enforce(拒否する)、audit(記録する)、warn(警告する)があります。

### 2. securityContext〔実務〕

```yaml
securityContext:
  runAsNonRoot: true
  runAsUser: 1000
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
  capabilities:
    drop: ["ALL"]
  seccompProfile:
    type: RuntimeDefault
```

### 3. 秘密情報と権限〔実務〕

| 対策 | 内容 |
|---|---|
| 外部のシークレット管理 | AWS Secrets Manager や Vault の値を、External Secrets Operator などで Secret として同期する。Git に秘密を置かない |
| etcd の暗号化 | Secret を etcd に暗号化して保存する |
| 最小の権限 | ServiceAccount ごとに必要な RBAC だけ。`cluster-admin` を配らない |
| クラウドの権限 | Pod ごとに IAM ロールを与える(EKS の IRSA / Pod Identity など)。ノードの権限を全 Pod に使わせない |
| イメージ | 信頼できるレジストリだけ、スキャン、署名の検証(アドミッションで強制) |
| NetworkPolicy | default deny から始め、必要な通信だけを許可する |

## 6.5 マネージドの Kubernetes とコスト

### 1. マネージドのサービス〔実務〕

| サービス | 特徴 |
|---|---|
| Amazon EKS | AWS。VPC CNI で Pod に VPC の IP。ノードは EC2 のマネージドノードグループ、Karpenter、Fargate |
| Google GKE | Autopilot モードではノードの管理も任せられる |
| Azure AKS | Azure の ID やネットワークと連携 |

コントロールプレーンの運用(etcd、証明書、可用性)はクラウドが行いますが、**バージョンのアップグレードは利用者が計画して行う**必要があります(サポートの期間が決まっている)。

### 2. ノードの自動の増減とコスト〔実務〕

| 仕組み | 動き |
|---|---|
| Cluster Autoscaler | Pending の Pod があるとノードグループのノードを増やし、空いたノードを減らす |
| Karpenter | Pending の Pod に合うインスタンスの種類を選んでノードを直接作る。スポットインスタンスも使いやすい |

コストを下げる主な方法:

- requests を実際の使用量に合わせる(過大な requests がノードを無駄に増やす)
- 止めてよい処理にはスポットインスタンスを使い、PDB と複数の種類のインスタンスで中断に備える
- 開発環境は夜間や週末に縮小する

コストを Namespace、ラベル、チームごとに按分して見えるようにするには、**Kubecost** や **OpenCost** を使います。Pod の requests や使用量とノードの料金から計算します。

### まとめ: よく出る判断

| 問われ方 | 答え |
|---|---|
| 一部の通信だけ新しい版に流す | カナリア |
| Git を正として、クラスタの中のツールが同期する | GitOps(Argo CD、Flux) |
| 長期間のメトリクスとアラート | Prometheus(metrics-server ではない) |
| Deployment の希望の数と実際の数のメトリクス | kube-state-metrics |
| drain のときに同時に止める数を制限する | PodDisruptionBudget |
| ゾーンに均等に散らす | topologySpreadConstraints |
| 削除のときにリクエストを落とさない | preStop で待つ + SIGTERM で処理を終える |
| PodSecurityPolicy の後継 | Pod Security Admission(Pod Security Standards) |
| Pending の Pod に合わせてノードを作る | Cluster Autoscaler / Karpenter |
