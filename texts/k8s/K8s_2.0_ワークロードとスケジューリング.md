# K8s テキスト 2.0 ワークロードとスケジューリング(15%)

アプリを動かすためのリソース(Deployment など)、設定の渡し方、自己修復の仕組み、Pod をどのノードに置くかの決め方、オートスケーリングを学びます。

## 2.1 Deployment とローリングアップデート、ロールバック

### 1. Pod、ReplicaSet、Deployment〔CKA〕

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:                 # ここから下が Pod の雛形
    metadata:
      labels:
        app: web            # selector と一致させる
    spec:
      containers:
        - name: web
          image: nginx:1.27
          ports:
            - containerPort: 80
```

| リソース | 役割 |
|---|---|
| Pod | 1 つ以上のコンテナ。IP とボリュームを共有する。単体で作ると、消えても作り直されない |
| ReplicaSet | 指定した数の Pod を保つ |
| Deployment | ReplicaSet を管理し、ローリングアップデートとロールバックを行う |

上の Deployment を作ったときの、リソースの親子の関係です。

```text
Deployment web(replicas: 3)
  |
  +-- ReplicaSet web-<ハッシュ>(Pod の数を 3 に保つ)
        |
        +-- Pod web-<ハッシュ>-<ランダム>
        +-- Pod web-<ハッシュ>-<ランダム>
        +-- Pod web-<ハッシュ>-<ランダム>
```

- `selector.matchLabels` と `template.metadata.labels` は一致させる必要があります(違うと作成がエラー)。
- Deployment の selector は作成後に変えられません。

### 2. ローリングアップデート〔CKA〕

`template` の中(イメージなど)を変えると、新しい ReplicaSet が作られ、古い Pod と少しずつ入れ替わります。

```yaml
spec:
  strategy:
    type: RollingUpdate      # 既定。もう 1 つは Recreate(全部消してから作る)
    rollingUpdate:
      maxSurge: 25%          # 希望の数を超えて追加で作ってよい数(既定 25%)
      maxUnavailable: 25%    # 希望の数より減ってよい数(既定 25%)
```

例: `replicas: 4`、`maxSurge: 1`、`maxUnavailable: 0` なら、Pod は常に 4 個以上が動き、最大 5 個まで増えながら 1 個ずつ入れ替わります。

入れ替わる様子です。old は古い ReplicaSet の Pod の数、new は新しい ReplicaSet の Pod の数、total はその合計です。

```text
step  old  new  total
  1     4    0      4   最初の状態
  2     4    1      5   新しい Pod を 1 個追加する(maxSurge: 1 まで)
  3     3    1      4   新しい Pod が Ready になったら、古い Pod を 1 個減らす
  4     3    2      5
  5     2    2      4
  6     2    3      5
  7     1    3      4
  8     1    4      5
  9     0    4      4   完了
```

total は 4 から 5 の間にあり、Ready の Pod が 4 個を下回りません。

```bash
kubectl set image deployment/web web=nginx:1.28     # コンテナ名=新しいイメージ
kubectl rollout status deployment/web
kubectl rollout history deployment/web
kubectl rollout undo deployment/web                  # 1 つ前に戻す
kubectl rollout undo deployment/web --to-revision=2
kubectl rollout restart deployment/web               # 設定は変えずに Pod を入れ替える
kubectl rollout pause / resume deployment/web
kubectl scale deployment/web --replicas=5
```

- `replicas` だけを変えても、新しい ReplicaSet は作られません(ロールアウトにならない)。
- 履歴の理由を残すには、`kubernetes.io/change-cause` の注釈を付けます。

## 2.2 ConfigMap と Secret

### 1. 作り方〔CKA〕

```bash
kubectl create configmap app-config --from-literal=LOG_LEVEL=info --from-file=app.properties
kubectl create secret generic db-cred --from-literal=username=app --from-literal=password='s3cr3t'
kubectl create secret tls web-tls --cert=tls.crt --key=tls.key
kubectl create secret docker-registry regcred --docker-server=… --docker-username=… --docker-password=…
```

### 2. Pod での使い方〔CKA〕

```yaml
spec:
  containers:
    - name: app
      image: myapp:1.0
      env:
        - name: LOG_LEVEL
          valueFrom:
            configMapKeyRef: { name: app-config, key: LOG_LEVEL }
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef: { name: db-cred, key: password }
      envFrom:
        - configMapRef: { name: app-config }    # 全部のキーを環境変数に
      volumeMounts:
        - name: config
          mountPath: /etc/app
  volumes:
    - name: config
      configMap:
        name: app-config                        # キーごとにファイルになる
```

| 渡し方 | ConfigMap を更新したとき |
|---|---|
| 環境変数 | **反映されない**(Pod を作り直す必要がある) |
| ボリューム | しばらくして自動で反映される(`subPath` でマウントしたものは反映されない) |

### 3. Secret の注意〔CKA〕

- Secret の値は **Base64 で書かれているだけで、暗号化ではありません**。`kubectl get secret -o yaml` を見られる人は中身を読めます。
- RBAC で Secret の参照を絞り、etcd の保存時の暗号化(EncryptionConfiguration)を有効にします。
- YAML で書くとき、`data:` には Base64 にした値、`stringData:` にはそのままの文字列を書きます。

## 2.3 自己修復するアプリの部品

### 1. ワークロードの種類〔CKA〕

| リソース | 用途 | 特徴 |
|---|---|---|
| Deployment | ステートレスな Web アプリ | Pod は入れ替え可能。名前はランダム |
| **StatefulSet** | データベースなど、状態を持つもの | Pod の名前が固定(`db-0`、`db-1`)。順番に作る。Pod ごとに PVC(`volumeClaimTemplates`)。ヘッドレス Service と組み合わせる |
| **DaemonSet** | 各ノードに 1 つずつ(ログの収集、監視のエージェント、CNI) | ノードが増えると自動で追加される |
| **Job** | 一回だけの処理 | 成功するまで再実行(`backoffLimit`)。`completions`、`parallelism` |
| **CronJob** | 定期的な処理 | cron 形式の `schedule` で Job を作る |

### 2. 再起動の方針(restartPolicy)〔CKA〕

| 値 | 使う場所 |
|---|---|
| `Always`(既定) | Deployment など。終わっても必ず再起動 |
| `OnFailure` | Job。失敗したときだけ |
| `Never` | Job。再起動しない |

再起動を繰り返す Pod は `CrashLoopBackOff` になり、待ち時間を延ばしながら再起動されます。

### 3. プローブ〔CKA〕

| プローブ | 失敗したとき | 使い方 |
|---|---|---|
| **livenessProbe** | コンテナを**再起動**する | 固まって応答しなくなったときの自動の復旧 |
| **readinessProbe** | Service の振り分け先から**外す**(再起動はしない) | 起動中や一時的に処理できないとき |
| **startupProbe** | 成功するまで liveness と readiness を止める | 起動の遅いアプリ |

```yaml
readinessProbe:
  httpGet: { path: /ready, port: 8080 }
  periodSeconds: 5
livenessProbe:
  httpGet: { path: /healthz, port: 8080 }
  initialDelaySeconds: 10
  failureThreshold: 3
```

方法は `httpGet`、`tcpSocket`、`exec`、`grpc` です。

### 4. 初期化コンテナとサイドカー〔CKA〕

- **initContainers**: メインのコンテナの前に、順番に実行して終わるコンテナ(設定ファイルの準備、依存先の待ち合わせ)。全部が成功しないとメインは起動しません(`Init:0/1` の表示)。
- **サイドカー**: initContainers に `restartPolicy: Always` を付けると、メインのコンテナと一緒に動き続けるサイドカーになります(v1.33 で GA)。ログの転送、プロキシなど。

## 2.4 Pod の受け入れとスケジューリング

### 1. リソースの requests と limits〔CKA〕

```yaml
resources:
  requests: { cpu: "250m", memory: "256Mi" }   # スケジューラーが使う。確保する量
  limits:   { cpu: "500m", memory: "512Mi" }   # 上限
```

| 項目 | 意味 | 超えたとき |
|---|---|---|
| requests | スケジューリングで、ノードの空きと比べる量 | 空きのあるノードがなければ Pending |
| limits の CPU | 上限 | 絞られる(スロットリング)。止まらない |
| limits のメモリ | 上限 | **OOMKilled**(コンテナが強制終了される) |

`250m` は 0.25 コア、`Mi` は 2 の 20 乗バイトです。

QoS クラス(ノードのメモリが足りなくなったときに追い出す順番に影響):

| クラス | 条件 |
|---|---|
| Guaranteed | 全コンテナで requests = limits(CPU とメモリ) |
| Burstable | 一部だけ設定 |
| BestEffort | 何も設定しない(最初に追い出される) |

### 2. LimitRange と ResourceQuota〔CKA〕

| リソース | 役割 |
|---|---|
| LimitRange | Namespace の中で、コンテナの既定の requests/limits と、最小・最大を決める |
| ResourceQuota | Namespace 全体で使える合計(CPU、メモリ、Pod の数など)を決める。超える作成は拒否される |

ResourceQuota で CPU やメモリの合計を決めた Namespace では、requests/limits のない Pod は作れません(LimitRange で既定値を与えれば作れる)。

### 3. ノードを選ぶ〔CKA〕

| 方法 | 書き方 | 意味 |
|---|---|---|
| nodeName | `nodeName: node1` | スケジューラーを通さず直接置く |
| nodeSelector | `nodeSelector: { disktype: ssd }` | そのラベルのノードだけ |
| nodeAffinity | `requiredDuringSchedulingIgnoredDuringExecution` / `preferred…` | 必須の条件 / できれば、の条件。`In`、`NotIn`、`Exists` などで書ける |
| podAffinity / podAntiAffinity | `topologyKey: kubernetes.io/hostname` | 特定の Pod と同じ(違う)ノードやゾーンに置く |

```bash
kubectl label node node1 disktype=ssd
```

### 4. taint と toleration〔CKA〕

- **taint** はノードに付ける「近寄るな」の印、**toleration** は Pod に付ける「それでも平気」の印です。
- taint のあるノードには、合う toleration を持つ Pod しか置かれません。**toleration があっても、そのノードに置かれるとは限りません**(引き寄せるのは nodeSelector や affinity)。

```bash
kubectl taint nodes node1 dedicated=gpu:NoSchedule
kubectl taint nodes node1 dedicated=gpu:NoSchedule-     # 外す(最後に -)
```

```yaml
tolerations:
  - key: dedicated
    operator: Equal
    value: gpu
    effect: NoSchedule
```

| effect | 意味 |
|---|---|
| NoSchedule | 新しい Pod を置かない(既存の Pod はそのまま) |
| PreferNoSchedule | できるだけ置かない |
| NoExecute | 置かず、既存の合わない Pod も追い出す |

node1 に `dedicated=gpu:NoSchedule` の taint を付けたときの、置かれ方です。Pod-A は toleration を持たず、Pod-B は持っています。

```text
[Pod-A] --X--> [node1]   toleration がないので、置かれない
[Pod-B] -----> [node1]   toleration があるので、置ける(置かれるとは限らない)
[Pod-B] -----> [node2]   taint のないノードにも置ける
```

kubeadm のコントロールプレーンのノードには `node-role.kubernetes.io/control-plane:NoSchedule` が付いているので、普通の Pod は置かれません。

### 5. 優先度〔CKA〕

PriorityClass で Pod に優先度を付けると、資源が足りないとき、優先度の低い Pod を追い出して(プリエンプション)高い Pod を置きます。

## 2.5 ワークロードのオートスケーリング

### 1. HorizontalPodAutoscaler(HPA)〔CKA〕

Pod の数を、CPU の使用率などに合わせて自動で増減します。

```bash
kubectl autoscale deployment web --cpu-percent=70 --min=2 --max=10
kubectl get hpa
```

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: web }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: web }
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 70 }
```

- 使用率は **requests に対する割合**です。**requests を設定していないと計算できません**(`<unknown>` と表示される)。
- CPU とメモリの値は **metrics-server** から取ります。入っていないと動きません。
- 計算: 希望の数 = ceil(今の数 × 今の使用率 ÷ 目標の使用率)。例: 4 個で平均 90%、目標 60% → ceil(4 × 90 ÷ 60) = 6 個。

### 2. そのほかのスケーリング〔実務〕

| 仕組み | 増やすもの |
|---|---|
| VerticalPodAutoscaler(VPA) | Pod の requests/limits(縦に大きくする)。別に入れるアドオン |
| Cluster Autoscaler / Karpenter | ノードの数。Pending の Pod があるとノードを足す |
| KEDA | キューの長さなど、外部のイベントで Pod の数を増減する(0 まで減らせる) |

v1.35 で、動いている Pod の CPU とメモリを、作り直さずに変える **in-place の resize** が GA になりました。

### まとめ: よく出る判断

| 問われ方 | 答え |
|---|---|
| 1 つ前のバージョンに戻す | `kubectl rollout undo deployment/名前` |
| 環境変数で渡した ConfigMap を変えた | Pod を作り直さないと反映されない |
| Secret は暗号化されているか | Base64 なだけ。暗号化ではない |
| 各ノードに 1 つずつ動かす | DaemonSet |
| 名前が固定され、Pod ごとにストレージが要る | StatefulSet |
| readiness が失敗すると | Service の振り分け先から外れる(再起動しない) |
| liveness が失敗すると | コンテナが再起動される |
| メモリの limits を超えると | OOMKilled |
| taint のノードに置けるようにする | Pod に toleration を付ける |
| HPA の使用率が `<unknown>` | requests がない、または metrics-server がない |
