# K8s テキスト 4.0 ストレージ(10%)

Pod のデータを置く場所と、永続的なストレージを要求して使う仕組み(PV、PVC、StorageClass)を学びます。

## 4.1 ボリュームの種類、アクセスモード、回収の方針

### 1. 主なボリューム〔CKA〕

| 種類 | 寿命 | 用途 |
|---|---|---|
| **emptyDir** | **Pod と同じ**(Pod が消えると消える。コンテナの再起動では残る) | 同じ Pod のコンテナ同士でのファイルの共有、一時ファイル |
| **hostPath** | ノードに残る | ノードのファイルを見せる(ログの収集など)。Pod が別のノードに移ると見えない。セキュリティの危険があるので、普通のアプリでは使わない |
| configMap / secret | - | 設定ファイルとしてマウント |
| projected | - | 複数(ConfigMap、Secret、ServiceAccount のトークン)を 1 つのディレクトリにまとめる |
| **persistentVolumeClaim** | PVC が残る限り | 永続的なデータ |

```yaml
spec:
  containers:
    - name: app
      image: busybox:1.37
      command: ["sh", "-c", "echo hi > /cache/a; sleep 3600"]
      volumeMounts:
        - name: cache
          mountPath: /cache
  volumes:
    - name: cache
      emptyDir: {}            # medium: Memory でメモリの上に置く
```

### 2. アクセスモード〔CKA〕

| モード | 略 | 意味 |
|---|---|---|
| ReadWriteOnce | RWO | **1 つのノード**から読み書き(同じノードの複数の Pod は使える) |
| ReadOnlyMany | ROX | 多くのノードから読み取りだけ |
| ReadWriteMany | RWX | 多くのノードから読み書き(NFS、EFS など、対応したストレージだけ) |
| ReadWriteOncePod | RWOP | **1 つの Pod** だけが読み書き |

ブロックストレージ(AWS EBS など)は、普通 RWO だけに対応しています。複数のノードの Pod で共有したいなら、RWX に対応したファイルストレージを使います。

### 3. 回収の方針(reclaimPolicy)〔CKA〕

PVC を削除したときに、PV と実際のストレージをどうするか:

| 方針 | 動き |
|---|---|
| **Delete** | PV と実際のストレージ(ディスク)も削除する。**動的プロビジョニングの既定** |
| **Retain** | PV とデータを残す。PV は `Released` になり、そのままでは別の PVC に結び付かない。手で片付けるか、再利用の手順を踏む |
| Recycle | 非推奨(中身を消して再利用) |

本番のデータベースでは、誤って PVC を消してもデータが残るよう、Retain を選ぶことがあります。

## 4.2 PV と PVC

### 1. 役割〔CKA〕

| リソース | 範囲 | 作る人 | 内容 |
|---|---|---|---|
| **PersistentVolume(PV)** | クラスタ全体 | 管理者(または自動) | 実際のストレージ(容量、アクセスモード、場所) |
| **PersistentVolumeClaim(PVC)** | Namespace | 利用者 | 「この容量とモードのストレージがほしい」という要求 |

PVC を作ると、条件(容量、アクセスモード、StorageClass)に合う PV と**1 対 1 で結び付きます**(Bound)。Pod は PVC を名前で指定して使います。

```yaml
apiVersion: v1
kind: PersistentVolume
metadata: { name: pv-data }
spec:
  capacity: { storage: 10Gi }
  accessModes: [ReadWriteOnce]
  persistentVolumeReclaimPolicy: Retain
  storageClassName: manual
  hostPath: { path: /mnt/data }       # 練習用
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: data, namespace: app }
spec:
  accessModes: [ReadWriteOnce]
  resources:
    requests: { storage: 5Gi }
  storageClassName: manual
---
# Pod での使い方
spec:
  volumes:
    - name: data
      persistentVolumeClaim: { claimName: data }
```

- 5Gi の要求に 10Gi の PV が結び付くと、PVC の容量は 10Gi になります(PV を分けて使うことはできない)。
- PVC と Pod は同じ Namespace にある必要があります。

Pod から実際のストレージまでのつながりです。

```text
[Pod]
  |  volumes の claimName: data
  v
[PVC data]       Namespace の中のリソース。利用者の要求
  |
  |  Bound(1 対 1)
  v
[PV pv-data]     クラスタ全体のリソース。ストレージの情報
  |
  v
実際のストレージ(ディスク、NFS など)
```

### 2. 状態〔CKA〕

| 対象 | 状態 | 意味 |
|---|---|---|
| PVC | Pending | 合う PV がない(容量、アクセスモード、StorageClass の不一致)、または WaitForFirstConsumer で Pod を待っている |
| PVC / PV | Bound | 結び付いた |
| PV | Available | どの PVC にも結び付いていない |
| PV | Released | PVC が削除された(Retain のとき) |

Pod が使っている PVC を削除しても、Pod が使い終わるまで実際には削除されません(保護のための finalizer)。

StatefulSet の `volumeClaimTemplates` で作られた PVC は、StatefulSet を削除しても、Pod の数を減らしても、既定で**残ります**(データを誤って失わないため)。一緒に消したい場合は、StatefulSet の `persistentVolumeClaimRetentionPolicy`(`whenDeleted`、`whenScaled` に `Delete` か `Retain`)で決めます。〔実務〕

### 3. 容量を増やす〔CKA〕

StorageClass に `allowVolumeExpansion: true` があれば、PVC の `spec.resources.requests.storage` を増やして拡張できます。減らすことはできません。

## 4.3 StorageClass と動的プロビジョニング

### 1. 動的プロビジョニング〔CKA〕

PV を管理者が先に作っておく代わりに、PVC を作ったときに **StorageClass** の設定で PV と実際のディスクを**自動で作る**仕組みです。

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"   # 既定の StorageClass
provisioner: ebs.csi.aws.com          # どの CSI ドライバーで作るか
parameters:
  type: gp3
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
```

| 項目 | 意味 |
|---|---|
| `provisioner` | ディスクを作る CSI ドライバー |
| `parameters` | ドライバーに渡す設定(ディスクの種類など) |
| `reclaimPolicy` | 作った PV の回収の方針(既定 Delete) |
| `volumeBindingMode: Immediate` | PVC を作ったらすぐに PV を作る |
| `volumeBindingMode: WaitForFirstConsumer` | **PVC を使う Pod がスケジュールされるまで待つ**。Pod が置かれるゾーンにディスクを作れる |

- PVC に `storageClassName` を書かないと、**既定の StorageClass** が使われます。
- `storageClassName: ""`(空)を書くと、動的プロビジョニングを使わず、StorageClass のない PV に結び付きます。

動的プロビジョニングの流れです。`WaitForFirstConsumer` のときは、Pod がスケジュールされてから、この流れが始まります。

```text
利用者が PVC を作る(storageClassName: fast)
  |
  v
[CSI driver (provisioner)]    PVC を見つけ、StorageClass fast の provisioner と parameters を読む
  |
  +--> ディスクを作る
  |
  +--> [PV] を作る
  |
  v
PVC と PV が Bound になる
```

```bash
kubectl get storageclass          # (default) と表示されるものが既定
kubectl get pvc,pv
kubectl describe pvc data         # Pending の理由が Events に出る
```

### 2. ボリュームのスナップショット〔実務〕

CSI のドライバーが対応していれば、VolumeSnapshot のリソースでディスクのスナップショットを作り、そこから新しい PVC を作れます(バックアップや複製)。クラスタ全体のバックアップには Velero などの道具も使われます。

### まとめ: よく出る判断

| 問われ方 | 答え |
|---|---|
| Pod と寿命が同じボリューム | emptyDir |
| 1 つのノードからだけ読み書き | ReadWriteOnce |
| 1 つの Pod だけが読み書き | ReadWriteOncePod |
| PVC を消したらディスクも消える | reclaimPolicy: Delete(動的プロビジョニングの既定) |
| PVC を消してもデータを残す | Retain |
| PVC が Pending | 合う PV や StorageClass がない、WaitForFirstConsumer で Pod 待ち |
| Pod が置かれるゾーンにディスクを作る | WaitForFirstConsumer |
| storageClassName を書かない PVC | 既定の StorageClass を使う |
| PVC を大きくする | StorageClass の allowVolumeExpansion が必要 |
