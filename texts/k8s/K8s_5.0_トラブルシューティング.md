# K8s テキスト 5.0 トラブルシューティング(30%)

CKA で最も配点の大きい分野です。ノード、クラスタの部品、資源の使用量、ログ、サービスとネットワークの順に、障害の見つけ方と直し方を学びます。

## 5.1 クラスタとノードの障害

### 1. 調べる順番〔CKA〕

```bash
kubectl get nodes                       # Ready か NotReady か
kubectl describe node node2             # Conditions と Events
ssh node2
sudo systemctl status kubelet           # kubelet は動いているか
sudo journalctl -u kubelet -n 100       # kubelet のエラー
sudo systemctl status containerd        # コンテナランタイム
```

### 2. ノードが NotReady のよくある原因〔CKA〕

| 原因 | 確かめ方 | 直し方 |
|---|---|---|
| **kubelet が止まっている** | `systemctl status kubelet` が inactive / failed | `systemctl enable --now kubelet` |
| kubelet の設定の誤り | `journalctl -u kubelet` にエラー(証明書のパス、設定ファイル、cgroup ドライバー) | `/var/lib/kubelet/config.yaml` や `/etc/kubernetes/kubelet.conf` を直して再起動 |
| コンテナランタイムが止まっている | `systemctl status containerd` | 起動する |
| CNI が入っていない / 壊れている | kubelet のログに `network plugin is not ready` | CNI を入れる、CNI の Pod を直す |
| 資源の不足 | `describe node` の Conditions に MemoryPressure、DiskPressure、PIDPressure | 不要なものを消す、容量を増やす |
| ノードの停止、ネットワークの断 | ノードに ssh できない | ノードを起動、ネットワークを直す |

kubelet は**systemd のサービス**として動いています(Pod ではない)。そのため `kubectl` ではなく、ノードに入って `systemctl` と `journalctl` で調べます。

### 3. Conditions の読み方〔CKA〕

| Condition | 正常な値 |
|---|---|
| Ready | True |
| MemoryPressure / DiskPressure / PIDPressure | False |
| NetworkUnavailable | False |

Ready が `Unknown` なのは、kubelet からの報告が途絶えていることを表します(kubelet の停止、ノードの停止)。

## 5.2 クラスタの部品の障害

### 1. コントロールプレーンの部品〔CKA〕

kubeadm のクラスタでは、API サーバー、etcd、スケジューラー、コントローラーマネージャーは静的 Pod です。

```bash
kubectl get pods -n kube-system
kubectl -n kube-system logs kube-apiserver-cp1
kubectl -n kube-system describe pod kube-scheduler-cp1
ls /etc/kubernetes/manifests/
sudo crictl ps -a                       # API サーバーが止まって kubectl が使えないとき
sudo crictl logs <コンテナ ID>
```

| 症状 | 疑う部品 |
|---|---|
| `kubectl` が `connection refused`(6443) | kube-apiserver(静的 Pod の YAML の誤り、証明書、etcd に接続できない) |
| 新しい Pod が **Pending のまま**、Events に何も出ない | **kube-scheduler** が止まっている |
| Deployment を作っても Pod ができない、replicas を変えても増えない | **kube-controller-manager** が止まっている |
| API サーバーが起動を繰り返す、データが読めない | etcd |

### 2. 静的 Pod の YAML の誤り〔CKA〕

- 試験では、`/etc/kubernetes/manifests/kube-apiserver.yaml` などの**コマンドの引数やパスをわざと間違えた**問題がよく出ます(存在しない証明書のパス、ポートの誤り、綴りの誤り)。
- YAML を直して保存すると、kubelet が自動で Pod を作り直します。
- API サーバーが動いていないと kubectl が使えないので、`crictl ps -a` と `crictl logs`、または `/var/log/pods/` と `/var/log/containers/` のログを見ます。

### 3. kube-system の Pod〔CKA〕

| Pod | 役割 | 止まると |
|---|---|---|
| kube-proxy(DaemonSet) | Service の振り分けのルール | Service の IP に届かない |
| CoreDNS(Deployment) | クラスタの DNS | 名前解決ができない |
| CNI の Pod(DaemonSet) | Pod のネットワーク | Pod に IP が付かない、ノードが NotReady |

## 5.3 クラスタとアプリの資源の使用量の監視

### 1. kubectl top〔CKA〕

```bash
kubectl top nodes
kubectl top pods -n prod --sort-by=memory
kubectl top pods --containers
```

- **metrics-server** が必要です。入っていないと `Metrics API not available` になります。
- 表示されるのは今の使用量(数十秒ごとの値)です。長期間の推移は見られません(Prometheus などが必要。分野 6)。

### 2. Pod の状態の見方〔CKA〕

| 状態 | よくある原因 | 確かめ方 |
|---|---|---|
| **Pending** | 資源の空きがない、nodeSelector や affinity に合うノードがない、taint、PVC が Bound でない | `kubectl describe pod` の Events(`FailedScheduling: 0/3 nodes are available: …`) |
| **ImagePullBackOff / ErrImagePull** | イメージ名やタグの誤り、プライベートレジストリの認証(imagePullSecrets) | Events の `Failed to pull image` |
| **CrashLoopBackOff** | アプリが起動してすぐ終わる(設定の誤り、コマンドの誤り、依存先がない、liveness の失敗) | `kubectl logs --previous`、`describe` の Last State と Exit Code |
| **OOMKilled** | メモリの limits を超えた | `describe` の Last State: Terminated, Reason: OOMKilled、Exit Code 137 |
| **CreateContainerConfigError** | 参照している ConfigMap や Secret(やそのキー)がない | Events |
| Running だが READY が 0/1 | readinessProbe が失敗している | `describe` の Events の `Readiness probe failed` |
| Terminating のまま | finalizer、ノードの停止 | `describe`、ノードの状態 |
| Evicted | ノードの資源(ディスク、メモリ)の不足で追い出された | `describe pod` の Message |

**まず `kubectl describe pod` の一番下の Events を見る**のが基本です。

## 5.4 コンテナの出力(ログ)を管理し評価する

### 1. kubectl logs〔CKA〕

```bash
kubectl logs web-7d9f8 -n prod
kubectl logs web-7d9f8 -c sidecar           # 複数のコンテナがあるときはコンテナを指定
kubectl logs web-7d9f8 --previous           # 再起動する前のコンテナのログ(CrashLoopBackOff の原因)
kubectl logs -f deploy/web                  # Deployment の Pod の 1 つを追いかける
kubectl logs -l app=web --all-containers --tail=50
kubectl logs web-7d9f8 --since=1h > /tmp/web.log
```

- ログは、コンテナの**標準出力と標準エラー出力**です。kubelet がノードの `/var/log/pods/` に保存します。
- Pod を削除するとログも消えます。長く残すには、ログを集める仕組み(Fluent Bit などで外に送る)が必要です(分野 6)。
- **CrashLoopBackOff の原因は、`--previous` で前のコンテナのログを見る**と分かることが多いです。

### 2. イベント〔CKA〕

```bash
kubectl get events -n prod --sort-by=.metadata.creationTimestamp
kubectl get events -A --field-selector type=Warning
```

イベントは既定で 1 時間ほどしか残りません。

### 3. 中に入って調べる〔CKA〕

```bash
kubectl exec -it web-7d9f8 -- sh
kubectl debug -it web-7d9f8 --image=busybox:1.37 --target=web    # シェルのないイメージの Pod に、調査用のコンテナを足す
kubectl debug node/node2 -it --image=busybox:1.37                 # ノードを調べる Pod を作る
```

distroless のようにシェルのないイメージには `kubectl exec` で入れないので、`kubectl debug` で一時的なコンテナ(ephemeral container)を足します。

## 5.5 サービスとネットワークの障害

### 1. 外側から順に調べる〔CKA〕

1. **Pod は動いて Ready か**: `kubectl get pods -o wide`
2. **Service のエンドポイントがあるか**: `kubectl get endpointslices -l kubernetes.io/service-name=web`、`kubectl describe svc web`
   - 空なら、selector と Pod のラベルが合っているか(`kubectl get pods --show-labels`)、Pod が Ready か
3. **ポートは合っているか**: Service の `targetPort` と、コンテナが実際に待ち受けるポート
4. **クラスタの中から直接つながるか**:

```bash
kubectl run tmp --rm -it --image=busybox:1.37 --restart=Never -- sh
wget -qO- http://10.244.1.5:8080      # Pod の IP に直接
wget -qO- http://web.prod:80          # Service の名前で
nslookup web.prod                     # 名前解決
```

5. **NetworkPolicy で止められていないか**: `kubectl get networkpolicy -n prod`
6. **kube-proxy と CoreDNS は動いているか**: `kubectl -n kube-system get pods`

### 2. 症状と原因〔CKA〕

| 症状 | よくある原因 |
|---|---|
| Pod の IP には届くが、Service の名前では届かない | CoreDNS の障害、名前の誤り(別の Namespace なのに `<svc>` だけ) |
| Service の IP に届かない | エンドポイントが空(ラベルの不一致、Ready でない)、targetPort の誤り、kube-proxy の障害 |
| 特定の Pod からだけ届かない | NetworkPolicy |
| NodePort に外から届かない | ノードのファイアウォール、クラウドのセキュリティグループ |
| Ingress / Gateway で 404 や 503 | ホスト名やパスの不一致、backend の Service やポートの誤り、エンドポイントが空 |

### まとめ: よく出る判断

| 問われ方 | 答え |
|---|---|
| ノードが NotReady。最初に確かめる | ノードで `systemctl status kubelet` と `journalctl -u kubelet` |
| 新しい Pod が Pending で Events に何もない | kube-scheduler の停止 |
| Pod が Pending。理由を知る | `kubectl describe pod` の Events |
| CrashLoopBackOff の原因 | `kubectl logs --previous` |
| Exit Code 137、Reason OOMKilled | メモリの limits を超えた |
| kubectl が使えない時にコンテナを調べる | ノードで `crictl ps -a`、`crictl logs` |
| `kubectl top` が使えない | metrics-server がない |
| シェルのないコンテナを調べる | `kubectl debug` |
| Service につながらない。最初に見る | エンドポイント(selector とラベル、Ready) |
