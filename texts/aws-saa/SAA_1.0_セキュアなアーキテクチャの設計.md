# AWS SAA テキスト 1.0 セキュアなアーキテクチャの設計(30%)

対象: SAA-C03

最も配点が大きい分野です。「誰が何にアクセスできるか(1.1)」「ネットワークとアプリケーションをどう守るか(1.2)」「データをどう守るか(1.3)」の3つに分かれます。

## 1.1 AWS リソースへの安全なアクセスを設計する

出題範囲: 責任共有モデル、グローバルインフラストラクチャ、IAM(ユーザー・グループ・ロール・ポリシー)、ルートユーザーと MFA、STS とクロスアカウントアクセス、IAM Identity Center とフェデレーション、Directory Service、Organizations と SCP、Control Tower、リソースベースのポリシー、RAM。

### 1. 責任共有モデル

セキュリティの責任は、AWS と利用者で分担します。

| 担当 | 内容 | 例 |
|---|---|---|
| AWS(クラウド **の** セキュリティ) | データセンター、ハードウェア、仮想化基盤、マネージドサービスの基盤 | 建物の入退室管理、物理サーバーの廃棄 |
| 利用者(クラウド **における** セキュリティ) | データ、IAM の設定、OS とアプリケーション(EC2 の場合)、ネットワーク設定、暗号化の選択 | EC2 の OS へのパッチ適用、セキュリティグループの設定 |

どこまでを利用者が担うかは、サービスの種類で変わります。

- **EC2**(IaaS): OS のパッチ、ミドルウェア、ファイアウォール設定まで利用者の責任です。
- **RDS**: OS とデータベースエンジンのパッチは AWS が行います。利用者はデータベースのユーザー、ネットワークのアクセス制御、暗号化の有効化を担当します。
- **S3、Lambda、DynamoDB**: 基盤はすべて AWS が管理します。利用者はアクセス権限とデータの扱いに責任を持ちます。

### 2. グローバルインフラストラクチャとセキュリティ

- **リージョン**: データはリージョンの外に自動では出ません。法律で「国内にデータを置く」必要があるなら、そのリージョンだけを使います。
- **AZ**: リージョン内で独立したデータセンター群です。高可用性のために複数の AZ を使います。
- SCP で「指定したリージョン以外は使わせない」という制限をかけることもできます(後述)。

### 3. IAM の基本

IAM(Identity and Access Management)は、AWS の操作を「誰に」「何を」許可するかを管理するサービスです。料金はかかりません。

| 要素 | 説明 |
|---|---|
| IAM ユーザー | 人やアプリケーションを表す、長期的な認証情報(パスワード、アクセスキー)を持つ ID |
| IAM グループ | ユーザーの集まり。グループにポリシーを付けると、所属する全員に適用されます。グループの入れ子はできません |
| IAM ロール | 一時的に「なりきる(引き受ける)」ための ID。長期的な認証情報を持たず、使うたびに一時的な認証情報が発行されます |
| IAM ポリシー | 許可・拒否のルールを書いた JSON 文書 |

ポリシーの例です。`mybucket` の中身の読み取りだけを許可します。

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject"],
      "Resource": "arn:aws:s3:::mybucket/*"
    }
  ]
}
```

- `Effect`: `Allow`(許可)か `Deny`(拒否)
- `Action`: 対象の操作。`s3:GetObject` は「S3 のオブジェクトを取得する」
- `Resource`: 対象のリソースを ARN(AWS のリソースを一意に表す名前)で書きます
- `Condition`: 条件(送信元 IP、MFA の有無、タグなど)を追加できます

#### ポリシーの評価ルール

1. 最初はすべて **暗黙の拒否**(何も許可されていない状態)です。
2. どこかに `Allow` があれば許可されます。
3. どこかに **明示的な `Deny`** があれば、`Allow` があっても必ず拒否されます。

つまり「明示的な拒否 > 許可 > 暗黙の拒否」の順に強いです。

上の3つのルールを、判断の順に並べた図です。yes は「はい」、no は「いいえ」です。

```text
リクエスト
  |
  v
(1) 明示的な Deny がある?
  |
  +-- yes --> 拒否(Allow があっても拒否)
  |
  v  no
(2) Allow がある?
  |
  +-- yes --> 許可
  |
  v  no
暗黙の拒否(何も許可されていないので拒否)
```

#### ポリシーの種類

| 種類 | 付ける先 | 役割 |
|---|---|---|
| アイデンティティベースのポリシー | ユーザー、グループ、ロール | その ID ができることを決める |
| リソースベースのポリシー | S3 バケット、SQS キュー、KMS キーなど | そのリソースに「誰が」アクセスできるかを決める。別アカウントの ID も指定できる |
| アクセス許可の境界(Permissions Boundary) | ユーザー、ロール | 付与できる権限の **上限** を決める。これだけでは何も許可しない |
| SCP(サービスコントロールポリシー) | Organizations のアカウントや OU | アカウント全体の権限の上限を決める。これだけでは何も許可しない |
| セッションポリシー | ロールを引き受けるときに渡す | そのセッションだけ権限をさらに絞る |

AWS 管理ポリシー(AWS が用意したもの)と、カスタマー管理ポリシー(自分で作るもの)、インラインポリシー(1つの ID に埋め込むもの)があります。再利用しやすいのはカスタマー管理ポリシーです。

### 4. ルートユーザーと IAM のベストプラクティス

ルートユーザーは、AWS アカウントを作ったときのメールアドレスでログインする、すべての権限を持つ ID です。権限を制限できないため、普段は使いません。

- ルートユーザーに **MFA(多要素認証)** を設定します。
- ルートユーザーの **アクセスキーは作りません**(あれば削除します)。
- 日常の作業は、IAM Identity Center のユーザーか、必要な権限だけを持つ IAM ユーザー・ロールで行います。
- ルートユーザーでしかできない作業(アカウントの解約、サポートプランの変更など)のときだけ使います。

その他のベストプラクティス:

- **最小権限の原則**: 仕事に必要な操作だけを許可します。最初は狭く与え、必要に応じて広げます。
- 長期的なアクセスキーの代わりに、**IAM ロールの一時的な認証情報** を使います。
- EC2 上のアプリケーションには、アクセスキーを書き込まず、**インスタンスプロファイル** で IAM ロールを付けます。Lambda には実行ロール、ECS のタスクにはタスクロールを付けます。
- パスワードポリシー(長さ、文字種、有効期限)を設定します。
- **IAM Access Analyzer** で、外部と共有されているリソースや、使われていない権限を見つけます。
- **IAM 認証情報レポート** で、全ユーザーのパスワードやアクセスキーの状態を確認できます。

### 5. IAM ロールと STS

**AWS STS**(Security Token Service)は、一時的な認証情報(アクセスキー、シークレットキー、セッショントークン)を発行するサービスです。IAM ロールを引き受ける(`AssumeRole`)と、STS から有効期限付きの認証情報が返ります。

ロールには2つのポリシーがあります。

- **信頼ポリシー**: 誰がこのロールを引き受けてよいか(例: EC2 サービス、別のアカウント)
- **アクセス許可ポリシー**: ロールを引き受けた人が何をできるか

ロールの主な使い方:

| 場面 | 方法 |
|---|---|
| EC2 から S3 を読む | EC2 に IAM ロールを付ける(インスタンスプロファイル) |
| 別アカウントのリソースを操作する(クロスアカウントアクセス) | 相手アカウントにロールを作り、信頼ポリシーで自分のアカウントを許可する。自分側は `sts:AssumeRole` を許可する |
| 外部の業者に自社アカウントを操作させる | クロスアカウントロールに **外部 ID**(ExternalId)の条件を付け、なりすましを防ぐ |
| コンソールで一時的に管理者権限に切り替える | **ロールの切り替え(スイッチロール)** |
| 社内の ID で AWS にログインする | フェデレーション(後述) |

別アカウントのロールを引き受けて操作するときの流れです。A が自分のアカウント、B が相手のアカウントです。

```text
Account A の利用者
  |
  |  1. sts:AssumeRole を呼ぶ(A 側のポリシーで許可が必要)
  v
STS
  |
  |  2. Account B の IAM ロールの信頼ポリシーが、A を許可しているかを確かめる
  |
  |  3. STS が、有効期限付きの一時的な認証情報を返す
  v
Account A の利用者が、その認証情報で B のリソースを操作する
```

### 6. フェデレーションと IAM Identity Center

**フェデレーション** とは、AWS の外にある ID(社内の Active Directory、Google、Okta など)で AWS にログインできるようにする仕組みです。利用者ごとに IAM ユーザーを作る必要がなくなります。

- **SAML 2.0**: 企業の ID 基盤(IdP)と AWS をつなぐ標準規格です。IdP で認証した人が、IAM ロールを引き受けて AWS を操作します。
- **OIDC(OpenID Connect)**: Web やモバイルの ID 連携で使われる規格です。

**AWS IAM Identity Center**(旧 AWS SSO)は、複数の AWS アカウントへのシングルサインオンをまとめて管理するサービスです。AWS が推奨する、人がログインするための方法です。

- Organizations と連携し、全アカウントへのアクセスを一か所で管理します。
- **アクセス許可セット** を作り、「このグループは、このアカウントで、この権限」と割り当てます。
- ID の保存先として、Identity Center 自身のディレクトリ、Active Directory、外部の IdP(Okta、Microsoft Entra ID など)を選べます。
- 利用者はポータルにログインし、使うアカウントとロールを選びます。

### 7. AWS Directory Service

AWS で Microsoft Active Directory(AD)を使うためのサービスです。

| 種類 | 使いどころ |
|---|---|
| AWS Managed Microsoft AD | AWS 上に本物の AD を立てる。オンプレミスの AD と信頼関係を結べる。AD が必要なアプリ(Windows、SQL Server、FSx for Windows)に使う |
| AD Connector | オンプレミスの AD への **中継(プロキシ)**。AWS 側にディレクトリのデータを置かずに、既存の AD で認証したいとき |
| Simple AD | 小規模向けの簡易な AD 互換ディレクトリ。信頼関係などの高度な機能はない |

「既存のオンプレミス AD の ID で AWS コンソールにログインさせたい」場合は、IAM Identity Center と AD Connector(または Managed Microsoft AD)を組み合わせます。

### 8. 複数アカウントの管理

本番、開発、セキュリティ、ログ保管などをアカウントごとに分けると、障害や設定ミスの影響範囲を小さくできます。

#### AWS Organizations

- 複数のアカウントを **組織** にまとめます。**管理アカウント** が1つあり、他は **メンバーアカウント** です。
- アカウントを **OU(組織単位)** というフォルダのような単位でまとめます。
- **一括請求(Consolidated Billing)**: 請求を管理アカウントにまとめます。使用量が合算されるため、ボリューム割引が効きやすく、リザーブドインスタンスや Savings Plans の割引をアカウント間で共有できます。
- **SCP(サービスコントロールポリシー)**: OU やアカウントに付けて、そのアカウント内の **全員(ルートユーザーを含む)** ができることの上限を決めます。
  - SCP は権限を与えません。IAM ポリシーでの許可と SCP の許可が **両方** 必要です。
  - 管理アカウントには SCP が効きません。
  - 例: 「東京と大阪以外のリージョンを禁止する」「CloudTrail の停止を禁止する」
- タグポリシー、バックアップポリシーなども一括で適用できます。

Organizations と SCP の関係を、木の形で表した図です。名前は例です。

```text
Root
  +-- 管理アカウント(SCP が効かない)
  +-- OU: Prod       <-- SCP: 東京と大阪以外のリージョンを禁止
  |     +-- メンバーアカウント prod-app
  |     +-- メンバーアカウント prod-db
  +-- OU: Dev
        +-- メンバーアカウント dev-1
```

SCP は上限を決めるだけで、権限は与えません。IAM ポリシーの許可と SCP の許可が両方あるときだけ、操作できます。

#### AWS Control Tower

ベストプラクティスに沿った複数アカウント環境(**ランディングゾーン**)を自動で作るサービスです。Organizations、IAM Identity Center、CloudTrail、Config などを組み合わせて設定してくれます。

- **コントロール(旧ガードレール)**:
  - 予防的コントロール: SCP で違反する操作を止める
  - 検出的コントロール: AWS Config で違反を見つける
  - プロアクティブコントロール: CloudFormation でリソースを作る前に確認する
- **Account Factory**: 決められた設定の新しいアカウントを素早く作ります。
- 「多数のアカウントをすばやく、統制の取れた状態で用意したい」場合に選びます。

#### AWS Service Catalog

管理者が承認した構成(CloudFormation テンプレートなど)を **製品** として登録し、社員が決められた選択肢の中から **セルフサービスで起動** できるようにするサービスです。社員に広い権限を与えずに、統制の取れたリソースを使わせられます。

#### AWS RAM(Resource Access Manager)

リソースを別のアカウントと共有するサービスです。例: VPC のサブネット、Transit Gateway、Route 53 Resolver のルールを、組織内の他のアカウントに共有します。リソースをコピーせずに共有できるので、管理が一か所で済みます。

### 9. リソースベースのポリシーを使う場面

リソースベースのポリシーは、リソース側に「誰がアクセスできるか」を書きます。

- **S3 バケットポリシー**: 別アカウントからの読み取りを許可する、HTTPS 以外の通信を拒否する(`aws:SecureTransport` 条件)、特定の VPC エンドポイント経由だけ許可する、など。
- **KMS キーポリシー**: キーを使える人を決めます。KMS ではキーポリシーが必須です。
- **SQS キューポリシー、SNS トピックポリシー**: 他のサービスや他アカウントからの送信を許可します。
- **Lambda の関数ポリシー**: S3 や API Gateway が関数を呼び出すことを許可します。

クロスアカウントで S3 を使う方法は、「相手のロールを引き受ける」方法と「バケットポリシーで相手アカウントを直接許可する」方法の2通りがあります。

### 10. まとめ: よく出る判断

| 要件 | 選ぶもの |
|---|---|
| EC2 のアプリから AWS API を呼ぶ | IAM ロール(インスタンスプロファイル)。アクセスキーを埋め込まない |
| 複数アカウントに社員がログイン | IAM Identity Center |
| 全アカウントで特定の操作を禁止 | SCP |
| 開発者が作るロールの権限に上限を付ける | アクセス許可の境界 |
| 外部の業者に自社アカウントを触らせる | クロスアカウントロール + 外部 ID |
| 統制の取れたアカウントをすぐ増やす | Control Tower(Account Factory) |
| サブネットを他アカウントと共有 | RAM |

## 1.2 セキュアなワークロードとアプリケーションを設計する

出題範囲: VPC の設計(サブネット、ルートテーブル、セキュリティグループ、ネットワーク ACL、NAT ゲートウェイ)、VPC エンドポイント、外部との接続(VPN、Direct Connect)、認証情報の管理(Secrets Manager、Parameter Store)、Cognito、WAF、Shield、GuardDuty、Macie、Inspector などのセキュリティサービス、DDoS や SQL インジェクションへの対策。

### 1. VPC の基本

**VPC**(Virtual Private Cloud)は、AWS の中に作る自分専用の仮想ネットワークです。リージョン単位で作り、IP アドレスの範囲(CIDR、例: `10.0.0.0/16`)を決めます。

| 部品 | 説明 |
|---|---|
| サブネット | VPC を分割した範囲。**1つの AZ に属します**。各サブネットでは先頭4つと最後の1つ、計 **5つの IP アドレスを AWS が予約** します |
| ルートテーブル | パケットの行き先を決める表。サブネットごとに1つ関連付けます |
| インターネットゲートウェイ(IGW) | VPC とインターネットをつなぐ出入口。VPC に1つ付けます |
| NAT ゲートウェイ | プライベートサブネットの機器が、インターネットへ **出ていく** ための装置。外からの接続は受け付けません |
| Elastic IP アドレス | 固定のパブリック IPv4 アドレス |
| Egress-Only インターネットゲートウェイ | IPv6 で、外向きの通信だけを許す出入口 |

#### パブリックサブネットとプライベートサブネット

- **パブリックサブネット**: ルートテーブルに「`0.0.0.0/0` → IGW」がある。Web サーバーの前に置くロードバランサー、NAT ゲートウェイ、踏み台サーバーを置きます。
- **プライベートサブネット**: IGW への経路がない。アプリケーションサーバーやデータベースを置き、インターネットから直接届かないようにします。外向きの通信が必要なら「`0.0.0.0/0` → NAT ゲートウェイ」の経路を足します。

典型的な 3 層構成(CIDR は例):

![典型的な 3 層構成の VPC の図。リージョンの中に VPC があり、VPC の CIDR は例の 10.0.0.0/16。2 つの AZ、AZ-a と AZ-c があり、それぞれにパブリックサブネット、アプリ用のプライベートサブネット、データベース用のプライベートサブネットがある。サブネットの CIDR も例。インターネットゲートウェイ IGW が VPC とインターネットをつなぐ。パブリックサブネットのルートテーブルは 0.0.0.0/0 を IGW へ向け、ここに ALB(複数の AZ にまたがる)と、AZ ごとの NAT ゲートウェイを置く。アプリ用のプライベートサブネットのルートテーブルは 0.0.0.0/0 を同じ AZ の NAT ゲートウェイへ向け、EC2 を置く。データベース用のプライベートサブネットには RDS を置き、IGW への経路はない。](images/1-2-vpc-overview.svg)

NAT ゲートウェイは **1つの AZ に属します**。可用性を高めるには、AZ ごとに NAT ゲートウェイを置き、各 AZ のプライベートサブネットから同じ AZ の NAT ゲートウェイへ向けます。

### 2. セキュリティグループとネットワーク ACL

| 項目 | セキュリティグループ(SG) | ネットワーク ACL(NACL) |
|---|---|---|
| 適用先 | インスタンス(正確には ENI = ネットワークインターフェース) | サブネット |
| ルール | **許可だけ** | 許可と拒否 |
| 状態 | **ステートフル**: 許可した通信の戻りは自動で通る | **ステートレス**: 戻りの通信も別に許可が必要 |
| 評価 | すべてのルールを見て、1つでも許可があれば通す | ルール番号の小さい順に見て、最初に一致したものを使う |
| 既定 | 受信はすべて拒否、送信はすべて許可 | 既定の NACL はすべて許可 |

- SG のルールでは、送信元として **別の SG を指定** できます。例: 「DB の SG は、アプリの SG からの 3306 番ポートだけを許可する」。IP アドレスが変わっても設定を直す必要がありません。
- NACL はステートレスなので、戻りの通信用に **エフェメラルポート**(一時的なポート。例: 1024〜65535)を許可する必要があります。
- 特定の IP アドレスを **拒否** したいときは、SG ではできないため NACL を使います(または WAF)。

### 3. 認証情報の安全な管理

アプリケーションのコードや設定ファイルに、データベースのパスワードや API キーを直接書いてはいけません。

| サービス | 特徴 |
|---|---|
| **AWS Secrets Manager** | 秘密情報を暗号化して保存。**自動ローテーション**(定期的なパスワード変更)ができる。RDS、Aurora、Redshift などと連携。有料 |
| **Systems Manager Parameter Store** | 設定値や秘密情報を保存。`SecureString` で KMS 暗号化できる。標準パラメータは無料。ローテーション機能は組み込まれていない |

「パスワードを定期的に自動で変更したい」なら Secrets Manager を選びます。

アプリケーションは IAM ロールの権限で、実行時に Secrets Manager から値を取得します。

### 4. AWS サービスへのプライベートな接続(VPC エンドポイント)

プライベートサブネットの EC2 から S3 などの AWS サービスを使うとき、通常は NAT ゲートウェイと IGW を通り、サービスのパブリックのエンドポイントにつなぎます。**VPC エンドポイント** を使うと、NAT ゲートウェイも IGW も通らずに、VPC の中から直接つなげます。

| 種類 | 対応サービス | 仕組み | 料金 |
|---|---|---|---|
| **ゲートウェイエンドポイント** | **S3 と DynamoDB だけ** | ルートテーブルに経路を追加 | 無料 |
| **インターフェースエンドポイント**(AWS PrivateLink) | 多くの AWS サービス、他社のサービス | サブネットに ENI(プライベート IP)を作る | 時間料金 + データ処理料金 |

- エンドポイントにはエンドポイントポリシーを付けて、使えるバケットなどを絞れます。
- S3 のバケットポリシーで `aws:SourceVpce` 条件を使うと、「特定のエンドポイント経由のアクセスだけ許可」できます。
- インターフェースエンドポイントは、Direct Connect や VPN 経由でオンプレミスからも使えます。

プライベートサブネットの EC2 から S3 を使うときの、通り道の違いです。

```text
(a) NAT ゲートウェイ経由: パブリック IP で IGW を通る。NAT の料金がかかる
  EC2 --> [NAT GW] --> [IGW] --> S3 パブリックのエンドポイント

(b) ゲートウェイエンドポイント: AWS のネットワーク内で完結する
  EC2 --> [Gateway Endpoint] --> S3
  ルートテーブルに、エンドポイントへの経路を追加する

(c) インターフェースエンドポイント: サブネットに ENI を作る
  EC2 --> [ENI (private IP)] --> AWS のサービス
```

### 5. EC2 への安全なログイン

- **Systems Manager Session Manager**: SSH のポートを開けず、踏み台サーバーも置かずに、ブラウザや CLI から EC2 にログインできます。操作の記録も残せます。「インバウンドのポートを開けたくない」場合の第一候補です。
- **踏み台サーバー(Bastion Host)**: パブリックサブネットに置いた中継用の EC2 です。SG で接続元 IP を絞ります。
- **EC2 Instance Connect**: 一時的な SSH 鍵を使ってログインします。

### 6. 外部ネットワークとの安全な接続

| 方法 | 特徴 |
|---|---|
| **AWS Site-to-Site VPN** | インターネット上に IPsec で暗号化したトンネルを張り、オンプレミスと VPC をつなぐ。すぐに用意でき、安い。1つの接続に2本のトンネルがある |
| **AWS Client VPN** | 個々の PC(リモートワークの社員など)から VPC に接続するための VPN |
| **AWS Direct Connect** | オンプレミスと AWS を **専用線** でつなぐ。帯域が安定し、遅延が少ない。開通までに数週間以上かかることがある。**それ自体は暗号化されない** |

- Direct Connect で暗号化が必要なら、Direct Connect の上に Site-to-Site VPN を張るか、MACsec(対応する接続で利用可能)を使います。
- VPC 側の終端には、仮想プライベートゲートウェイ(VGW)か Transit Gateway を使います。

### 7. アプリケーションのユーザー認証: Amazon Cognito

Web アプリやモバイルアプリに、サインアップやサインインの機能を追加するサービスです。

| 機能 | 役割 |
|---|---|
| **ユーザープール** | ユーザーの登録・ログインを管理し、トークン(JWT)を発行する。Google、Facebook、SAML などの外部 ID でのログインにも対応 |
| **ID プール** | ログインしたユーザー(またはゲスト)に、AWS の **一時的な認証情報** を渡す。アプリから直接 S3 や DynamoDB を使わせたいときに使う |

API Gateway や ALB と組み合わせると、ログイン済みのユーザーだけが API を呼べるようにできます。

### 8. 外部からの攻撃への対策

| 攻撃 | 内容 | 対策 |
|---|---|---|
| DDoS | 大量の通信でサービスを止める | Shield、CloudFront、Route 53、Auto Scaling で吸収する |
| SQL インジェクション | 入力欄に SQL 文を混ぜてデータベースを不正に操作する | WAF の SQL インジェクション対策ルール。アプリ側でも入力を正しく扱う |
| クロスサイトスクリプティング(XSS) | 悪意のあるスクリプトを Web ページに埋め込む | WAF の XSS 対策ルール |
| 特定の IP や国からの不正アクセス | | WAF の IP セット、地域一致(ジオマッチ)ルール、CloudFront の地理的制限 |
| 大量のリクエスト(ボット、総当たり) | | WAF のレートベースルール(一定時間内のリクエスト数で制限) |

#### AWS WAF

Web アプリケーションファイアウォールです。HTTP/HTTPS のリクエストの中身(URL、ヘッダー、本文)を見て、許可・拒否します。

- 付けられる場所: **CloudFront、ALB、API Gateway、AppSync、Cognito ユーザープール** など。NLB や EC2 には直接付けられません。
- **Web ACL** にルールを並べます。AWS や販売者が用意した **マネージドルール** も使えます。

#### AWS Shield

DDoS 攻撃からの保護サービスです。

| 種類 | 内容 |
|---|---|
| Shield Standard | すべての利用者に **無料** で自動適用。一般的なネットワーク層(L3/L4)の攻撃を防ぐ |
| Shield Advanced | 有料。より高度な検知と緩和、AWS の DDoS 対応チーム(SRT)の支援、攻撃で増えた利用料の補償。CloudFront、Route 53、ELB、Global Accelerator、Elastic IP などを保護 |

#### AWS Firewall Manager

Organizations の全アカウントに、WAF のルール、Shield Advanced、セキュリティグループ、Network Firewall のポリシーを **一括で適用・管理** するサービスです。新しいアカウントやリソースにも自動で適用されます。

#### AWS Network Firewall

VPC の中に置くマネージドなファイアウォールです。ステートフルな検査、ドメイン名でのフィルタリング(例: 許可したドメインにだけ外向き通信を許す)、侵入検知・防止(IDS/IPS)ができます。SG や NACL より細かい制御が必要なときに使います。

### 9. 脅威の検出と調査

| サービス | 何をするか |
|---|---|
| **Amazon GuardDuty** | CloudTrail、VPC フローログ、DNS ログなどを機械学習で分析し、**不審な動き**(不正な API 呼び出し、暗号通貨のマイニング、悪意のある IP との通信)を検出する。エージェント不要 |
| **Amazon Macie** | **S3** のデータを調べ、**個人情報(PII)などの機密データ** を見つける |
| **Amazon Inspector** | EC2、ECR のコンテナイメージ、Lambda 関数の **脆弱性**(古いソフトウェアなど)を自動でスキャンする |
| **Amazon Detective** | GuardDuty などの検出結果をもとに、関連するログをつなげて **原因を調査** する |
| **AWS Security Hub** | 各サービスの検出結果を **一か所に集約** し、セキュリティ基準(CIS など)への準拠状況をチェックする |

区別のコツ: 「脅威の検出」は GuardDuty、「S3 の個人情報」は Macie、「脆弱性」は Inspector、「調査」は Detective、「集約」は Security Hub です。

### 10. まとめ: よく出る判断

| 要件 | 選ぶもの |
|---|---|
| DB をインターネットから隠す | プライベートサブネット + SG で アプリ SG からのみ許可 |
| プライベートサブネットからソフトウェアの更新を取得 | NAT ゲートウェイ(パブリックサブネットに置く) |
| プライベートサブネットから S3 へ、インターネットを通らずに | S3 のゲートウェイエンドポイント |
| 特定の IP アドレスを遮断 | NACL の拒否ルール、または WAF の IP セット |
| SQL インジェクションを防ぐ | WAF |
| DB パスワードの自動ローテーション | Secrets Manager |
| SSH のポートを開けずに EC2 を操作 | Session Manager |
| アプリにサインイン機能 | Cognito ユーザープール |
| S3 の中の個人情報を見つける | Macie |

## 1.3 適切なデータセキュリティ管理を決定する

出題範囲: 保存時の暗号化(KMS、CloudHSM)、転送時の暗号化(ACM と TLS)、キーのポリシーとローテーション、証明書の更新、データのバックアップとレプリケーション、データのライフサイクルと保持、データの分類とガバナンス、コンプライアンス(Artifact、Config、CloudTrail)。

### 1. 暗号化の2種類

| 種類 | 意味 | 主な方法 |
|---|---|---|
| **保存時の暗号化**(at rest) | ディスクや S3 に保存されたデータを暗号化する | KMS を使ったサーバー側暗号化(S3、EBS、RDS、DynamoDB など) |
| **転送時の暗号化**(in transit) | ネットワークを流れるデータを暗号化する | TLS(HTTPS)、VPN |

### 2. AWS KMS(Key Management Service)

暗号化に使う **キー** を作成・管理するサービスです。多くの AWS サービスと連携しています。キーの操作はすべて CloudTrail に記録されます。

#### キーの種類

| 種類 | 管理者 | 特徴 |
|---|---|---|
| AWS 所有キー | AWS | 利用者からは見えない。追加料金なし |
| AWS マネージドキー | AWS | `aws/s3` のような名前。サービスごとに自動で作られる。ポリシーの変更やローテーション設定はできない(自動で毎年ローテーション) |
| **カスタマーマネージドキー** | 利用者 | 自分で作る。**キーポリシーで使える人を細かく決められる**。ローテーションの有無と周期を選べる。無効化・削除も可能 |

- **キーポリシー**: KMS のキーに付けるリソースベースのポリシーです。誰がキーを管理でき、誰が暗号化・復号に使えるかを書きます。管理する人と使う人を分けるのが良い設計です。
- **自動ローテーション**: カスタマーマネージドキーで有効にすると、定期的に新しいキー素材が作られます。古いキー素材も保持されるため、以前に暗号化したデータもそのまま復号できます。
- **エンベロープ暗号化**: KMS のキーで直接大きなデータを暗号化するのではなく、データ用のキー(データキー)を作ってデータを暗号化し、そのデータキーを KMS のキーで暗号化します。大きなデータも効率よく暗号化できます。
- **マルチリージョンキー**: 複数のリージョンで同じキーを使えます。別リージョンへ複製したデータを復号するときに便利です。
- 外部で作ったキー素材を取り込む(インポート)こともできます。この場合、自動ローテーションは使えません。

エンベロープ暗号化の手順です。

```text
1. KMS がデータキーを作る(平文と、KMS のキーで暗号化したものの 2 つが返る)
     |
     v
2. 平文のデータキーで、データを暗号化する
     |
     v
3. 平文のデータキーを捨てる
     |
     v
4. 暗号化されたデータと、暗号化されたデータキーを、一緒に保存する
```

復号するときは逆の順です。KMS のキーでデータキーを復号し、そのデータキーでデータを復号します。

#### AWS CloudHSM

専用の **HSM**(ハードウェアセキュリティモジュール。キーを安全に保管する専用機器)を AWS 上で使うサービスです。

- HSM は利用者専用(シングルテナント)で、キーは利用者だけが管理します。AWS もキーを見られません。
- 「規制により、専用のハードウェアでキーを完全に自分で管理する必要がある」場合に選びます。
- 通常の用途なら、運用が簡単な KMS で十分です。

### 3. 各サービスの暗号化

| サービス | ポイント |
|---|---|
| **S3** | 新しいオブジェクトは既定で SSE-S3 により暗号化される。SSE-KMS(KMS のキー)、DSSE-KMS(二重暗号化)、SSE-C(利用者が渡したキー)、クライアント側暗号化も選べる。バケットポリシーで暗号化方式を強制できる |
| **EBS** | ボリューム、スナップショット、インスタンスとの通信がまとめて暗号化される。リージョン単位で「既定で暗号化」を有効にできる |
| **RDS** | 作成時に暗号化を有効にする。**既存の暗号化されていない DB は直接暗号化できない**。スナップショットを取り、暗号化してコピーし、そこから復元する |
| **DynamoDB** | 保存データは常に暗号化される。キーの種類を選べる |
| **EFS** | 保存時の暗号化は作成時に選ぶ。転送時は TLS でマウントする |

暗号化されていない EBS ボリュームを暗号化したい場合も、スナップショットを暗号化してコピーし、そこから新しいボリュームを作ります。

### 4. 転送時の暗号化と AWS Certificate Manager(ACM)

**ACM** は、TLS(HTTPS)に使う **SSL/TLS 証明書** を発行・管理するサービスです。

- ACM が発行するパブリック証明書は、ELB、CloudFront、API Gateway などで使う場合、**無料** です。
- **自動更新** されます。DNS 検証を選び、検証用の DNS レコードを残しておけば、更新の手間はかかりません。
- **CloudFront で使う証明書は、バージニア北部リージョン(us-east-1)の ACM で作成** します。
- ALB で HTTPS を終端し、ALB から EC2 までは HTTP にする構成(TLS 終端)がよく使われます。全区間を暗号化したい場合は、EC2 側にも証明書を入れます。
- 外部の認証局で買った証明書を ACM に取り込む(インポート)こともできますが、その場合は自動更新されないため、期限切れに注意します。

S3 への通信を HTTPS に限定したい場合は、バケットポリシーで `aws:SecureTransport` が `false` のリクエストを拒否します。

### 5. データのバックアップとレプリケーション

| 方法 | 内容 |
|---|---|
| **AWS Backup** | EC2、EBS、RDS、Aurora、DynamoDB、EFS、FSx、S3 などのバックアップを **一元管理**。バックアップ計画(頻度、保持期間)を作り、タグで対象を選ぶ。別リージョン・別アカウントへのコピーもできる |
| **AWS Backup Vault Lock** | バックアップを **削除・変更できないように** する(WORM: 一度書いたら変更できない)。ランサムウェア対策やコンプライアンス用 |
| EBS スナップショット | 増分バックアップ。別リージョンにコピーできる |
| RDS 自動バックアップ | 保持期間内の任意の時点に戻せる(ポイントインタイムリカバリ) |
| **S3 レプリケーション** | 別リージョン(CRR)や同じリージョン(SRR)のバケットへ自動で複製する。**両方のバケットでバージョニングが必要** |

### 6. データの保護とライフサイクル(S3)

| 機能 | 内容 |
|---|---|
| **バージョニング** | 上書きや削除をしても以前のバージョンが残る。誤操作からの復旧に使う |
| **MFA Delete** | バージョンの完全削除やバージョニングの停止に MFA を必須にする |
| **S3 Object Lock** | 指定した期間、オブジェクトの削除・上書きを禁止する(WORM)。バージョニングが必要 |
| ライフサイクルルール | 一定期間後に安いストレージクラスへ移す、または削除する |
| ブロックパブリックアクセス | バケットやアカウント全体で、公開設定を一括で禁止する。既定で有効 |
| 署名付き URL | 期限付きで、特定のオブジェクトへのアクセスを一時的に許可する |

S3 Object Lock の2つのモード:

| モード | 内容 |
|---|---|
| ガバナンスモード | 特別な権限を持つユーザーなら、保持設定を解除・削除できる |
| コンプライアンスモード | **ルートユーザーを含め誰も** 保持期間中は削除・変更できない。規制で「絶対に消せない」保存が必要なとき |

保持期間とは別に、期間を決めずに削除を止める **リーガルホールド** もあります。

### 7. データの分類とガバナンス

- **データの分類**: データを機密度(公開、社内、機密など)で分け、それぞれに合った保護をかけます。Macie で S3 の機密データを自動で見つけられます。
- **タグ**: リソースに「分類: 機密」のようなタグを付け、IAM ポリシーの条件で使えます(ABAC: 属性ベースのアクセス制御)。
- **AWS Lake Formation**: データレイクのデータに、テーブル・列・行の単位でアクセス権限を設定できます(3.5 で扱います)。

### 8. コンプライアンスと監査

| サービス | 何をするか |
|---|---|
| **AWS CloudTrail** | 「誰が、いつ、どの API を呼んだか」を記録する。組織全体の証跡を1つの S3 バケットに集められる。ログファイルの整合性検証で改ざんを検出できる |
| **AWS Config** | リソースの **設定の変更履歴** を記録し、ルールに **準拠しているか** を評価する。違反時に Systems Manager で自動修復できる |
| **AWS Artifact** | AWS 自身のコンプライアンスレポート(SOC、PCI DSS、ISO など)をダウンロードできる |
| **AWS Audit Manager** | 監査に必要な証拠を自動で集める(参考) |

区別のコツ: 「誰が操作したか」は CloudTrail、「設定がどう変わったか・ルールに合っているか」は Config、「AWS の認証レポートが欲しい」は Artifact です。

### 9. まとめ: よく出る判断

| 要件 | 選ぶもの |
|---|---|
| キーの使用者を細かく管理、使用履歴も監査 | KMS のカスタマーマネージドキー + キーポリシー |
| 専用ハードウェアでキーを自分だけで管理 | CloudHSM |
| HTTPS 証明書を無料で、自動更新 | ACM |
| 既存の暗号化されていない RDS を暗号化 | スナップショット → 暗号化コピー → 復元 |
| 削除できないバックアップ | AWS Backup Vault Lock、S3 Object Lock(コンプライアンスモード) |
| 別リージョンにデータを自動で複製 | S3 クロスリージョンレプリケーション |
| 設定がルールに合っているか継続的に確認 | AWS Config |
| API 操作の監査ログ | CloudTrail |
