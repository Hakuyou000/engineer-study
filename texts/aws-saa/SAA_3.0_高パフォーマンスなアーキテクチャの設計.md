# AWS SAA テキスト 3.0 高パフォーマンスなアーキテクチャの設計(24%)

対象: SAA-C03

要件に合った「速さ」と「伸びしろ」を持つサービスと構成を選ぶ分野です。ストレージ(3.1)、コンピューティング(3.2)、データベース(3.3)、ネットワーク(3.4)、データの取り込みと分析(3.5)の5つに分かれます。

## 3.1 高パフォーマンスでスケーラブルなストレージを決定する

出題範囲: S3、EBS、インスタンスストア、EFS、FSx の性能と使い分け、ハイブリッドストレージ(Storage Gateway)、将来の増加に耐えるストレージ。

### 1. Amazon S3 の性能

S3 は容量に上限がなく、自動でスケールするオブジェクトストレージです。

- **プレフィックス**(キーの先頭部分、例: `logs/2026/`)ごとに、1秒あたり多くのリクエストを処理できます。キーを複数のプレフィックスに分けると、全体の処理量を増やせます。
- **マルチパートアップロード**: 大きなファイルを分割して並列にアップロードします。100 MB を超えるファイルで推奨され、5 GB を超えるファイルでは必須です。途中で失敗しても、失敗した部分だけやり直せます。
- **S3 Transfer Acceleration**: 遠く離れた場所からのアップロードを、近くのエッジロケーション経由で AWS のネットワークに乗せて速くします。
- **バイト範囲の取得**(Range GET): ファイルの一部だけを並列にダウンロードします。
- **S3 Express One Zone**: 1つの AZ に置く、非常に低遅延なストレージクラスです。機械学習の学習データのように、同じ AZ の計算資源から高頻度に読む用途に使います。
- S3 は **強い整合性** を持ちます。書き込みの直後に読んでも、最新のデータが返ります。
- **S3 Select**: ファイル全体ではなく、SQL で必要な部分だけを取り出します(新規利用は制限されている場合があります)。

### 2. Amazon EBS の性能

EBS は EC2 に接続するブロックストレージ(仮想ディスク)です。**同じ AZ の EC2 にだけ** 接続できます。

| 種類 | 区分 | 特徴 | 使いどころ |
|---|---|---|---|
| **gp3** | SSD(汎用) | 容量と別に IOPS とスループットを指定できる。基本の性能が保証されている | 多くのワークロードの既定。起動ボリューム |
| gp2 | SSD(汎用) | 容量に比例して IOPS が決まる。古い世代 | gp3 への移行が推奨 |
| **io2 Block Express / io1** | SSD(プロビジョンド IOPS) | 高い IOPS を安定して出す。**マルチアタッチ**(複数の EC2 から同時接続)に対応 | 大規模な DB、遅延に厳しい処理 |
| **st1** | HDD(スループット最適化) | 大きなデータを順番に読み書きするのが得意 | ビッグデータ、ログ処理、データウェアハウス |
| **sc1** | HDD(コールド) | 最も安い。アクセスが少ないデータ向け | 低頻度のアーカイブ |

- **IOPS**: 1秒あたりの読み書きの回数。小さなデータをたくさん読み書きする(DB など)場合に重要です。
- **スループット**: 1秒あたりに転送できるデータ量(MB/s)。大きなファイルを順番に読む場合に重要です。
- HDD 系(st1、sc1)は **起動ボリュームにできません**。
- **EBS 最適化インスタンス**: EBS 専用の帯域を持ち、他の通信の影響を受けにくくします(現在の多くのインスタンスは既定で有効)。
- ボリュームのサイズや種類は、多くの場合 **動かしたまま変更** できます(Elastic Volumes)。

### 3. インスタンスストア

EC2 のホストに物理的に付いているディスクです。

- **非常に高速**(高い IOPS、低遅延)です。
- EC2 を **停止・終了するとデータが消えます**(再起動では残ります)。
- キャッシュ、一時ファイル、複数台で複製しているデータ(分散 DB など)に使います。大事なデータは置きません。

### 4. ファイルストレージ

| サービス | プロトコル | OS | 特徴 |
|---|---|---|---|
| **Amazon EFS** | NFS | Linux | 複数の AZ の多数の EC2・コンテナ・Lambda から同時にマウントできる。容量は自動で増減 |
| **FSx for Windows File Server** | SMB | Windows | Active Directory と連携。Windows の共有フォルダをそのまま移行できる |
| **FSx for Lustre** | Lustre | Linux | **HPC(高性能計算)・機械学習** 向けの超高速な並列ファイルシステム。S3 のデータと連携できる |
| **FSx for NetApp ONTAP** | NFS、SMB、iSCSI | 両方 | NetApp の機能(スナップショット、重複排除など)。オンプレミスの NetApp からの移行 |
| **FSx for OpenZFS** | NFS | Linux | ZFS の機能。オンプレミスの ZFS からの移行 |

EBS、インスタンスストア、EFS の、EC2 との結び付き方の違いです。

```text
EC2 (AZ-a)
  +-- EBS: 仮想ディスク。同じ AZ の EC2 にだけ接続できる
  +-- Instance Store: ホストの物理ディスク。停止・終了でデータが消える

EC2 (AZ-a) --+
EC2 (AZ-c) --+--> [EFS]: 複数の AZ の EC2 から、同時にマウントできる
EC2 (AZ-c) --+
```

#### EFS の設定

| 設定 | 選択肢 |
|---|---|
| スループットモード | **Elastic**(使った分だけ自動で伸縮。おすすめ)、プロビジョンド(一定の性能を確保)、バースト(容量に応じて変わる) |
| パフォーマンスモード | 汎用(低遅延。通常はこれ)、最大 I/O(非常に多くの並列アクセス向け) |
| ストレージクラス | 標準、低頻度アクセス(IA)、アーカイブ。ライフサイクル管理で自動的に移動 |
| 可用性 | リージョン(複数 AZ)、1ゾーン(安いが1つの AZ だけ) |

### 5. ハイブリッドストレージ: AWS Storage Gateway

オンプレミスのサーバーから、AWS のストレージを「ローカルのストレージのように」使えるようにするサービスです。オンプレミスに仮想マシン(またはハードウェア)として置きます。

| 種類 | オンプレミスからの見え方 | 保存先 | 使いどころ |
|---|---|---|---|
| **S3 File Gateway** | NFS / SMB のファイル共有 | S3 | ファイルを S3 に保存し、クラウドでも分析したい |
| **FSx File Gateway** | SMB のファイル共有 | FSx for Windows | 支社から FSx の共有フォルダを低遅延で使う(新規提供の状況は公式で確認) |
| **Volume Gateway** | iSCSI のディスク | S3(EBS スナップショット) | キャッシュ型: データは AWS、よく使う分だけ手元に。保管型: データは手元、非同期で AWS にバックアップ |
| **Tape Gateway** | 仮想テープライブラリ(VTL) | S3、S3 Glacier | 既存のテープバックアップソフトをそのまま使い、物理テープをやめる |

### 6. 将来の増加に耐えるストレージ

- 容量の見積もりが難しいなら、**自動で伸びるサービス**(S3、EFS、Aurora、DynamoDB)を選びます。
- EBS は容量を指定するため、増える前に拡張が必要です。CloudWatch で使用率を監視します。
- RDS の **ストレージの自動スケーリング** を有効にすると、空きが少なくなったときに自動で容量が増えます。

### 7. まとめ: よく出る判断

| 要件 | 選ぶもの |
|---|---|
| 多数の Linux サーバーでファイルを共有 | EFS |
| Windows の共有フォルダ、AD 連携 | FSx for Windows File Server |
| HPC で超高速な共有ストレージ | FSx for Lustre |
| DB 用に高い IOPS を安定して | EBS io2 Block Express |
| 一般的なディスク、性能と容量を別に調整 | EBS gp3 |
| 大量のログを順番に読む、安く | EBS st1 |
| 最速の一時領域、消えてもよい | インスタンスストア |
| 遠隔地から S3 へのアップロードを速く | S3 Transfer Acceleration、マルチパートアップロード |
| オンプレミスから NFS で S3 に保存 | S3 File Gateway |
| テープバックアップをクラウドへ | Tape Gateway |

## 3.2 高パフォーマンスで伸縮自在なコンピューティングを設計する

出題範囲: EC2 のインスタンスタイプの選び方、プレイスメントグループ、Auto Scaling とスケーリングのメトリクス、Lambda のメモリ設定、Fargate、ECS・EKS、AWS Batch、Amazon EMR、ワークロードの分離(デカップリング)、エッジでの分散処理。

### 1. EC2 のインスタンスタイプ

インスタンスタイプは `m7g.large` のような名前です。

- `m` … **ファミリー**(用途)
- `7` … 世代(数字が大きいほど新しく、性能あたりの価格が良い)
- `g` … 追加の特徴(`g` は AWS Graviton(Arm)プロセッサ、`i` は Intel、`a` は AMD、`n` はネットワーク強化、`d` はインスタンスストア付き)
- `large` … サイズ(`nano`、`micro`、`small`、`medium`、`large`、`xlarge`、`2xlarge` …)

| ファミリー | 種類 | 使いどころ |
|---|---|---|
| **M** | 汎用 | Web サーバー、一般的なアプリ |
| **T** | 汎用(バースト可能) | 普段は低負荷で、ときどき CPU を使うもの。CPU クレジットを貯めて使う |
| **C** | コンピューティング最適化 | CPU を多く使う処理(バッチ、動画エンコード、科学計算、ゲームサーバー) |
| **R、X** | メモリ最適化 | インメモリ DB、大きなキャッシュ、メモリを多く使う分析 |
| **I、D** | ストレージ最適化 | 高速なローカルディスクが必要な DB、データ処理 |
| **P、G、Inf、Trn** | 高速化コンピューティング(GPU など) | 機械学習の学習・推論、画像処理 |

- **AWS Graviton** を使うインスタンスは、同じ性能の x86 インスタンスより安く、電力効率が良い傾向があります。アプリが Arm で動くことが条件です。
- **AWS Compute Optimizer** は、実際の使用状況から、ちょうど良いインスタンスタイプとサイズを推奨します。

### 2. プレイスメントグループ

EC2 をどのように物理的に配置するかを決めます。

| 種類 | 配置 | 使いどころ |
|---|---|---|
| **クラスター** | 1つの AZ の中で、近くにまとめる | ノード間の **低遅延・高帯域** が必要な HPC |
| **分散**(スプレッド) | 別々のハードウェアに分ける(AZ ごとに最大7台) | 少数の重要なインスタンスを、同時故障から守る |
| **パーティション** | パーティション(ラック)単位で分ける | Hadoop、Cassandra、Kafka のような大規模な分散システム |

### 3. スケーリングのメトリクスと条件

- **CPU 使用率**: 計算が重い処理の目安です。
- **ALB のターゲットあたりのリクエスト数**: Web アプリの負荷の目安です。
- **SQS キューのメッセージ数**(1台あたりのメッセージ数): キューを処理するワーカーの台数の目安です。
- **カスタムメトリクス**: アプリが独自の値(処理待ちの件数など)を CloudWatch に送り、それでスケールします。
- メモリ使用率でスケールしたいときは、CloudWatch エージェントでメモリのメトリクスを送ります。

決まった時刻に負荷が上がる(例: 毎朝の始業時)なら **スケジュールされたスケーリング** や **予測スケーリング** で事前に増やし、突発的な負荷には **ターゲット追跡** で対応します。

### 4. Lambda のリソース設定

- Lambda では **メモリ** だけを設定し、CPU はメモリに比例して割り当てられます。CPU を多く使う処理が遅いときは、**メモリを増やす** と速くなります。実行時間が短くなるため、料金が下がることもあります。
- 実行時間が15分を超える処理は、Lambda ではなく Fargate、ECS、AWS Batch などを使います。
- 一時的な作業領域(`/tmp`)は最大10 GB まで設定できます。
- 大量の同時実行が必要なときは、同時実行数のクォータの引き上げを申請します。

### 5. 処理の分離(デカップリング)

処理を部品に分け、間に SQS、SNS、Kinesis などを挟むと、**部品ごとに独立してスケール** できます。

例: 動画のアップロードを受け付ける部分と、変換する部分を SQS で分けると、変換処理だけを GPU インスタンスで増やせます。

### 6. 目的別のコンピューティングサービス

| サービス | 内容 | 使いどころ |
|---|---|---|
| **AWS Batch** | バッチ処理のジョブを、必要な量の EC2(スポットも可)や Fargate で自動実行する。ジョブのキューと優先度を管理 | 大量の計算ジョブ、夜間処理、15分を超える処理 |
| **Amazon EMR** | Hadoop、Spark、Hive、Presto などのビッグデータ処理基盤のマネージドサービス | 大規模なデータの加工・分析 |
| **AWS Fargate** | サーバーなしでコンテナを動かす | 常時稼働のコンテナ、長時間の処理 |
| **AWS Lambda** | イベントでコードを実行 | 短時間の処理、イベント駆動 |
| **ECS / EKS** | コンテナのオーケストレーション(配置、スケール、自己修復) | マイクロサービス |

### 7. エッジでの分散処理

| サービス | 内容 |
|---|---|
| **Lambda@Edge / CloudFront Functions** | CloudFront のエッジでコードを動かし、リクエストやレスポンスを書き換える(ヘッダーの追加、URL の書き換え、簡単な認証) |
| **AWS Wavelength** | 5G 通信事業者のネットワーク内に AWS の計算資源を置き、スマートフォンなどから **超低遅延** で使う |
| **AWS Outposts** | AWS のハードウェアを **自社のデータセンターに設置** し、AWS と同じ API で使う。データを社内に置く必要がある場合や、オンプレミスとの低遅延が必要な場合 |
| **AWS Local Zones** | 大都市の近くに置かれた AWS の拠点。特定の地域の利用者に低遅延で提供する |
| **VMware Cloud on AWS** | オンプレミスの VMware 環境を、そのまま AWS 上で動かす |

### 8. まとめ: よく出る判断

| 要件 | 選ぶもの |
|---|---|
| CPU を多く使うバッチ | C ファミリー、AWS Batch |
| 大きなインメモリ処理 | R / X ファミリー |
| 機械学習の学習 | P ファミリー(GPU)、Trn |
| HPC でノード間の遅延を最小 | クラスタープレイスメントグループ |
| 重要なインスタンスを同時故障から守る | 分散プレイスメントグループ |
| Lambda の処理が CPU 不足で遅い | メモリを増やす |
| Spark でビッグデータ処理 | EMR |
| キューの溜まり具合で台数を変える | SQS のメッセージ数を使ったスケーリング |
| 5G のモバイル端末に超低遅延 | Wavelength |
| 自社データセンターで AWS を使う | Outposts |

## 3.3 高パフォーマンスなデータベースを決定する

出題範囲: リレーショナルと非リレーショナル、RDS・Aurora・DynamoDB・ElastiCache・Redshift などの使い分け、読み取り中心と書き込み中心、容量の計画(キャパシティユニット、インスタンスタイプ、プロビジョンド IOPS)、接続とプロキシ、リードレプリカ、キャッシュの組み込み、エンジンの選び方、同種・異種の移行。

### 1. データベースの種類

| 種類 | 特徴 | AWS のサービス |
|---|---|---|
| **リレーショナル**(RDB) | 表と SQL。結合やトランザクションが得意 | RDS、Aurora |
| **キーバリュー / ドキュメント** | キーで高速に読み書き。スキーマが柔軟。水平に無限にスケール | DynamoDB、DocumentDB(MongoDB 互換) |
| **インメモリ** | メモリ上で動き、マイクロ秒〜ミリ秒の応答 | ElastiCache(Valkey、Redis OSS、Memcached)、MemoryDB |
| **グラフ** | つながり(友人関係、推薦、不正検知)をたどる | Neptune |
| **ワイドカラム** | Apache Cassandra 互換 | Amazon Keyspaces |
| **時系列** | 時刻つきのデータ(センサー、メトリクス) | Amazon Timestream |
| **データウェアハウス**(列指向) | 大量のデータを集計・分析する | Redshift |

### 2. Amazon RDS と Aurora の性能

- **RDS** で使えるエンジン: MySQL、PostgreSQL、MariaDB、Oracle、SQL Server、Db2。
- **Aurora** は MySQL / PostgreSQL 互換で、標準の MySQL / PostgreSQL より高い性能を目指して作られています。
- インスタンスクラス(例: `db.r7g`)で CPU とメモリを決め、ストレージの種類(gp3、プロビジョンド IOPS)で I/O 性能を決めます。
- **Aurora Serverless v2**: 負荷に応じて容量(ACU)が細かく自動で増減します。負荷の予測が難しい、または変動が大きい場合に向きます。
- RDS の OS へのログインはできません(RDS Custom を除く)。OS レベルの設定が必要なら、EC2 に自分で DB を入れます。

エンジンの選び方:

| 状況 | 選び方 |
|---|---|
| 既存の Oracle / SQL Server のライセンスや機能が必要 | RDS for Oracle / SQL Server |
| オープンソースで高い性能と可用性 | Aurora(MySQL / PostgreSQL 互換) |
| 高度な SQL、拡張機能(地理情報の PostGIS など) | PostgreSQL |
| 広く使われていて情報が多い、シンプルな Web アプリ | MySQL |

### 3. 読み取りと書き込みの性能

| 状況 | 対策 |
|---|---|
| **読み取り** が多い | リードレプリカ、ElastiCache、DAX、CloudFront |
| **書き込み** が多い | インスタンスを大きくする、プロビジョンド IOPS、DynamoDB(水平にスケール)、SQS で書き込みを平準化する |

### 4. Amazon DynamoDB の性能

フルマネージドの NoSQL データベースです。どれだけデータが増えても、ミリ秒単位の応答を保ちます。

- **パーティションキー**(必須)と **ソートキー**(任意)でデータを特定します。パーティションキーは値がよく散らばるもの(ユーザー ID など)を選び、特定のキーにアクセスが集中しないようにします。
- **キャパシティモード**:

| モード | 内容 | 向いている場合 |
|---|---|---|
| **オンデマンド** | リクエストの数だけ課金。容量の設定不要 | 負荷が読めない、急に増減する、新しいアプリ |
| **プロビジョンド** | 1秒あたりの読み取り(RCU)と書き込み(WCU)の量を決める。Auto Scaling で調整可能 | 負荷が安定して予測できる(安くなる) |

- **キャパシティユニット**: 1 RCU は 4 KB までの強い整合性のある読み取りを1秒に1回(結果整合性なら2回)、1 WCU は 1 KB までの書き込みを1秒に1回です。
- **グローバルセカンダリインデックス(GSI)**: パーティションキー以外の属性で検索するためのインデックスです。
- **DAX**(DynamoDB Accelerator): DynamoDB 専用のインメモリキャッシュです。読み取りを **マイクロ秒** に速くします。アプリの変更がほとんど不要です。
- **DynamoDB Streams**: 項目の追加・変更・削除を順番に記録し、Lambda などで処理できます。
- **TTL**: 指定した時刻を過ぎた項目を自動で削除します(追加料金なし)。
- 1つの項目の最大サイズは 400 KB です。大きなデータは S3 に置き、DynamoDB には場所(キー)を保存します。

### 5. Amazon ElastiCache

インメモリのキャッシュ・データストアのマネージドサービスです。

| エンジン | 特徴 |
|---|---|
| **Valkey / Redis OSS** | レプリケーション、Multi-AZ の自動フェイルオーバー、データの永続化、バックアップ、多様なデータ型(ソート済みセットでランキングなど)、Pub/Sub |
| **Memcached** | シンプル、マルチスレッド。レプリケーションや永続化はない。単純なキャッシュ向け |

キャッシュの書き方:

| 方式 | 動き | 長所 | 短所 |
|---|---|---|---|
| **遅延読み込み**(キャッシュアサイド) | 読むときにキャッシュを見て、なければ DB から読んでキャッシュに入れる | 必要なデータだけがキャッシュされる | 初回は遅い。データが古くなることがある |
| **ライトスルー** | DB に書くときに、同時にキャッシュにも書く | キャッシュが常に新しい | 使われないデータもキャッシュされる |

- **TTL**(有効期限)を付けて、古いデータが残り続けないようにします。
- セッション情報の保存先としてもよく使われます。

遅延読み込み(キャッシュアサイド)の流れです。

```text
アプリが読み取る
  |
  v
キャッシュにデータがある?
  |
  +-- yes --> キャッシュの値を返す(速い)
  |
  +-- no  --> DB から読む
              |
              v
            キャッシュに書いてから、値を返す
```

### 6. 接続とプロキシ

- データベースの接続数には上限があります。Lambda のように多数の短い接続を作ると、上限に達してしまいます。
- **RDS Proxy** が接続をプールして使い回すことで、DB の負荷を下げ、接続あふれを防ぎます。
- Aurora では、書き込みは **クラスターエンドポイント**、読み取りは **リーダーエンドポイント** に接続します。用途別にレプリカを分けたいときは **カスタムエンドポイント** を作ります。

Aurora で、書き込みと読み取りの接続先を分ける構成です。

```text
App --write--> [Cluster endpoint] ---> [Primary]

App --read---> [Reader endpoint] ---+--> [Replica 1]
                                    +--> [Replica 2]
```

### 7. リードレプリカの設定

- 分析用の重いクエリを、本番のプライマリではなくリードレプリカで実行すると、本番の性能を守れます。
- 世界中に利用者がいる場合、**別リージョンのリードレプリカ** で、近いリージョンから読み取れます。
- リードレプリカは非同期なので、書き込み直後のデータが反映されていないことがあります。必ず最新が必要な読み取りはプライマリで行います。

### 8. データベースの移行

| 用語 | 意味 | 例 |
|---|---|---|
| **同種移行**(ホモジニアス) | 同じエンジンへの移行 | オンプレミスの MySQL → RDS for MySQL |
| **異種移行**(ヘテロジニアス) | 別のエンジンへの移行 | Oracle → Aurora PostgreSQL |

- **AWS DMS**(Database Migration Service): データを移行します。移行中も元の DB を動かしたまま、変更を継続的に反映できます(CDC: 変更データキャプチャ)。停止時間を最小にできます。
- **AWS SCT**(Schema Conversion Tool)/ **DMS Schema Conversion**: 異種移行のとき、テーブル定義やストアドプロシージャを、移行先のエンジンに合わせて変換します。
- 同種移行では、スキーマの変換は不要で、エンジン付属のツール(ダンプとリストア)も使えます。

### 9. まとめ: よく出る判断

| 要件 | 選ぶもの |
|---|---|
| SQL と結合が必要、高性能・高可用 | Aurora |
| 負荷の変動が大きいリレーショナル DB | Aurora Serverless v2 |
| どこまでも増えるデータ、ミリ秒応答、キーで読む | DynamoDB |
| DynamoDB の読み取りをマイクロ秒に | DAX |
| DB の前にキャッシュ、ランキング | ElastiCache(Valkey / Redis OSS) |
| 友人関係・推薦などのつながり | Neptune |
| MongoDB からの移行 | DocumentDB |
| Cassandra からの移行 | Keyspaces |
| センサーの時系列データ | Timestream |
| 大量データの集計・分析 | Redshift |
| Oracle → Aurora PostgreSQL | SCT(スキーマ変換)+ DMS(データ移行) |

## 3.4 高パフォーマンスでスケーラブルなネットワークを決定する

出題範囲: CloudFront、Global Accelerator、VPC の設計(サブネットの階層、ルーティング、IP アドレスの設計)、ロードバランサーの選び方、VPN・Direct Connect・PrivateLink、VPC ピアリングと Transit Gateway、リソースの配置。

### 1. Amazon CloudFront

世界中のエッジロケーションでコンテンツをキャッシュする CDN です。

- **オリジン**(元のデータの置き場所): S3、ALB、EC2、任意の HTTP サーバー。
- **キャッシュ動作**: パスごとに、キャッシュの時間やオリジンを変えられます(例: `/images/*` は長くキャッシュ、`/api/*` はキャッシュしない)。
- **OAC**(オリジンアクセスコントロール): S3 バケットを公開せず、**CloudFront 経由のアクセスだけを許可** します(古い方式は OAI)。

OAC を使った、S3 を CloudFront の裏に置く構成です。

```text
User --> [CloudFront] --> [S3 bucket]    OAC で、CloudFront からだけ許可する
User --> [S3 bucket]                      直接のアクセスは拒否される
```
- **署名付き URL / 署名付き Cookie**: 有料会員だけが動画を見られる、のように、許可した人だけに配信します。複数のファイルをまとめて許可するなら署名付き Cookie が便利です。
- **地理的制限**: 特定の国からのアクセスを許可・拒否します。
- **オリジンフェイルオーバー**: オリジングループを作り、プライマリが応答しないときにセカンダリから配信します。
- **フィールドレベル暗号化**: フォームの特定の項目(カード番号など)を、エッジで暗号化します。
- 動的なコンテンツ(キャッシュできないもの)でも、AWS のネットワークを通るため速くなることがあります。

### 2. AWS Global Accelerator

**2つの固定のエニーキャスト IP アドレス** を提供し、利用者の通信を最寄りのエッジから AWS のネットワークに乗せて、最適なリージョンのエンドポイント(ALB、NLB、EC2、Elastic IP)に届けます。

| 比較 | CloudFront | Global Accelerator |
|---|---|---|
| キャッシュ | する | **しない** |
| プロトコル | HTTP / HTTPS(WebSocket も可) | **TCP / UDP**(HTTP 以外も) |
| IP アドレス | 変わる | **固定**(2つ) |
| 使いどころ | Web コンテンツの配信 | ゲーム、IoT、VoIP、固定 IP が必要、**リージョン間の素早いフェイルオーバー** |

### 3. VPC のネットワーク設計

- **CIDR の設計**: 将来の拡張を考えて、VPC には十分に大きな範囲(例: `/16`)を割り当てます。**オンプレミスや他の VPC と重ならない範囲** にします(重なると VPC ピアリングや VPN で接続できません)。VPC には後から CIDR を追加することもできます。
- **サブネットの階層**: パブリック(ロードバランサー)、プライベート(アプリ)、データ(DB)のように、役割ごとにサブネットを分け、各 AZ に同じ構成を作ります。
- **サブネットの大きさ**: 各サブネットで5つの IP アドレスが予約されることを考慮します。例: `/24` は 256 − 5 = **251個** が使えます。Auto Scaling やコンテナ(タスクごとに IP を使う)で IP が足りなくならないよう、余裕を持たせます。
- **IPv6**: VPC に IPv6 の範囲を追加できます。IPv6 で外向きの通信だけを許可するには Egress-Only インターネットゲートウェイを使います。

### 4. VPC 同士の接続

| 方法 | 特徴 |
|---|---|
| **VPC ピアリング** | 2つの VPC を1対1でつなぐ。**推移的ではない**(A–B、B–C がつながっていても、A–C は通信できない)。CIDR の重複は不可。別リージョン、別アカウントとも可 |
| **AWS Transit Gateway** | 多数の VPC とオンプレミス(VPN、Direct Connect)を **ハブ** でまとめてつなぐ。推移的なルーティングができる。リージョン間のピアリングも可。RAM で他アカウントと共有できる |
| **AWS PrivateLink** | 自分の VPC のサービス(NLB の後ろ)を、他の VPC に **インターフェースエンドポイント** として公開する。VPC 全体をつながずに、特定のサービスだけを提供できる。CIDR が重なっていてもよい |

VPC ピアリングと Transit Gateway の、つなぎ方の違いです。

```text
VPC ピアリング: 1対1でつなぐ
  [VPC A] ---- [VPC B] ---- [VPC C]
  A と C は直接つないでいないので、通信できない

Transit Gateway: ハブでまとめる
  [VPC A] ----+
  [VPC B] ----+---- [Transit Gateway] ---- [On-premises]
  [VPC C] ----+
```

VPC が数個ならピアリング、数十個以上やオンプレミスも含めて集約するなら Transit Gateway です。

### 5. オンプレミスとの接続の性能

| 方法 | 帯域・性能 | 開通までの時間 |
|---|---|---|
| Site-to-Site VPN | インターネットを通るため、帯域と遅延は安定しない | 短い(すぐ作れる) |
| **Accelerated Site-to-Site VPN** | Global Accelerator のネットワークを使い、安定性を上げる(Transit Gateway が必要) | 短い |
| **Direct Connect** | 専用線で安定。1 Gbps、10 Gbps、100 Gbps などの専用接続、またはパートナー経由のホスト型接続 | 長い(数週間〜) |

- **Direct Connect ゲートウェイ**: 1つの Direct Connect 接続から、**複数のリージョンの VPC** に接続できます。
- **仮想インターフェース(VIF)**: プライベート VIF(VPC へ)、パブリック VIF(S3 などの公開エンドポイントへ)、トランジット VIF(Transit Gateway へ)。
- **回復性**: 重要な接続は、Direct Connect を **2本以上、別々の拠点(ロケーション)** で用意します。コストを抑えるなら、Direct Connect + VPN をバックアップにします。
- VPN は1本のトンネルの帯域に上限があります。帯域を増やすには、Transit Gateway で複数の VPN を **ECMP**(等コストマルチパス)で束ねます。

### 6. ロードバランサーの選び方

| 要件 | 選ぶもの |
|---|---|
| HTTP の内容(パス、ホスト、ヘッダー)で振り分け | ALB |
| 1台のロードバランサーで複数のドメインの証明書を使う | ALB / NLB(SNI) |
| TCP / UDP、毎秒数百万のリクエスト、超低遅延 | NLB |
| 固定 IP アドレスが必要 | NLB(または ALB の前に Global Accelerator) |
| 送信元のクライアント IP をそのまま渡す | NLB(ALB は `X-Forwarded-For` ヘッダーで渡す) |
| ファイアウォールなどのアプライアンスに通す | GWLB |
| gRPC、HTTP/2 | ALB |

### 7. リソースの配置

- **利用者の近くに置く**: 利用者が多い地域のリージョンを選び、CloudFront や Global Accelerator で世界中から速くします。
- **データの置き場所の規制**: 法令で国内保存が必要なら、そのリージョンを使います。
- **同じ AZ に置く**: AZ をまたぐ通信は少し遅く、料金もかかります。遅延が重要な処理は同じ AZ に置きます(ただし可用性とのバランスを考えます)。
- **クラスタープレイスメントグループ**: HPC のノード間の遅延を最小にします。

### 8. まとめ: よく出る判断

| 要件 | 選ぶもの |
|---|---|
| 世界中に静的コンテンツを速く配信 | CloudFront |
| S3 を直接公開せず CloudFront 経由だけに | CloudFront + OAC |
| 有料会員だけに配信 | 署名付き URL / Cookie |
| UDP のゲームを世界中から低遅延、固定 IP | Global Accelerator |
| 50個の VPC とオンプレミスをまとめてつなぐ | Transit Gateway |
| 自社のサービスだけを他社の VPC に提供 | PrivateLink(NLB + エンドポイントサービス) |
| 安定した広帯域でオンプレミスとつなぐ | Direct Connect |
| 1本の専用線で複数リージョンの VPC へ | Direct Connect ゲートウェイ |
| VPN の帯域を増やす | Transit Gateway + 複数 VPN の ECMP |

## 3.5 高パフォーマンスなデータの取り込みと変換を決定する

出題範囲: データの取り込みの頻度と方法、転送サービス(DataSync、Snow ファミリー、Storage Gateway、Transfer Family)、ストリーミング(Kinesis、MSK)、変換(Glue)、データレイク(S3、Lake Formation)、分析(Athena、EMR、Redshift、OpenSearch)、可視化(Amazon Quick)、形式の変換(CSV から Parquet)。

### 1. データの取り込みのパターン

| 頻度 | 例 | サービス |
|---|---|---|
| **リアルタイム(ストリーミング)** | クリックの記録、IoT センサー、ログ | Kinesis Data Streams、Amazon Data Firehose、MSK |
| **定期的なバッチ** | 毎晩のファイル転送 | DataSync、Transfer Family、Glue のジョブ |
| **一度だけの大量移行** | データセンターの閉鎖 | Snow ファミリー、DataSync、Direct Connect |

### 2. データ転送サービス

| サービス | 内容 |
|---|---|
| **AWS DataSync** | オンプレミス(NFS、SMB、HDFS、オブジェクトストレージ)や他のクラウドから、S3、EFS、FSx へ **オンラインで高速に転送** する。スケジュール実行、差分転送、整合性の検証、帯域の制限ができる。AWS のストレージ同士の転送にも使える |
| **AWS Snow ファミリー**(Snowball Edge) | 物理的な機器を送ってもらい、データを入れて返送する。**ネットワークが遅い、または転送に何週間もかかる大量データ** 向け。機器で簡単な計算処理もできる(エッジコンピューティング)。提供されている機種は公式で確認 |
| **AWS Storage Gateway** | オンプレミスから AWS のストレージを継続的に使う(3.1 参照) |
| **AWS Transfer Family** | SFTP / FTPS / FTP / AS2 で、取引先などから S3 や EFS へファイルを受け渡す |
| **Amazon AppFlow** | Salesforce、SAP、Slack などの SaaS と S3、Redshift の間でデータを転送する |
| **AWS DMS** | データベースからの移行・継続的な複製 |

転送方法の目安: 回線の速さで計算して、転送に何日もかかる量なら Snow ファミリー、そうでなければ DataSync(または Direct Connect + DataSync)です。

### 3. ストリーミングデータ

| サービス | 内容 |
|---|---|
| **Amazon Kinesis Data Streams** | リアルタイムのデータを受け取り、**保存しておき(既定24時間、最大365日)**、複数のアプリが読む。**シャード** の数(またはオンデマンドモード)で処理量が決まる。シャード内では順序が保たれる。独自の処理アプリ(Lambda、KCL)を作る場合に使う |
| **Amazon Data Firehose**(旧 Kinesis Data Firehose) | ストリーミングデータを受け取り、S3、Redshift、OpenSearch、Splunk などへ **自動で届ける**。サーバー管理不要。バッファリング(一定量・一定時間ためてから書く)、Lambda での変換、**Parquet / ORC への変換**、圧縮ができる。ほぼリアルタイム(数十秒程度の遅れ) |
| **Amazon Managed Service for Apache Flink** | ストリーミングデータを SQL や Java などでリアルタイムに分析する |
| **Amazon MSK** | Apache Kafka のマネージドサービス。既存の Kafka を使うアプリの移行に向く |
| **Amazon Kinesis Video Streams** | カメラなどの動画ストリームを取り込み、保存・分析する |

選び方: 「データを S3 などに届けるだけで、コードを書きたくない」なら Data Firehose、「複数のアプリでリアルタイムに処理する、再読み込みしたい」なら Kinesis Data Streams です。

### 4. データレイク

**データレイク** は、さまざまな形式のデータを、加工前のままでも **S3 に一元的に** 貯めておく仕組みです。

- **AWS Glue**:
  - **Glue データカタログ**: S3 などのデータの「表の定義(メタデータ)」を管理します。Athena、EMR、Redshift Spectrum から共通で使えます。
  - **クローラー**: S3 のデータを自動で調べ、カタログにテーブルを作ります。
  - **Glue ETL ジョブ**: サーバーレスでデータを抽出・変換・ロード(ETL)します。CSV を Parquet に変換する、などに使います。
  - Glue DataBrew: コードを書かずに、画面の操作でデータを整えます。
- **AWS Lake Formation**: データレイクの構築を簡単にし、**データベース・テーブル・列・行の単位** でアクセス権限を一元管理します。「部署ごとに見られる列を変えたい」場合に使います。

S3 に貯めたデータが、カタログと分析サービスにつながる流れです。

```text
データの元(ログ、DB、ファイル)
  |
  |  Firehose、DMS、DataSync などで取り込む
  v
[S3]: データレイク。加工前のデータも置く
  |
  +-- Crawler --> Data Catalog: 表の定義(メタデータ)を作って管理する
  |
  +-- Glue ETL ジョブ: CSV を Parquet に変換するなど
  |
  v
Athena、EMR、Redshift Spectrum が、S3 のデータを分析する
```

データレイクを守るポイント: S3 の暗号化、ブロックパブリックアクセス、Lake Formation の権限、VPC エンドポイント経由のアクセス、CloudTrail での監査。

### 5. データ形式の変換

| 形式 | 特徴 |
|---|---|
| CSV、JSON | 行単位。人が読みやすいが、サイズが大きく、分析で全体を読む必要がある |
| **Parquet**、ORC | **列指向**。圧縮が効き、必要な列だけを読める。分析が速く、Athena のスキャン量(料金)が減る |

CSV を Parquet に変換するには、Glue ETL ジョブ、Data Firehose の形式変換、EMR などを使います。さらに、日付などで **パーティション**(フォルダ分け、例: `year=2026/month=11/`)を作ると、クエリで読む範囲を絞れます。

### 6. 分析サービス

| サービス | 内容 | 使いどころ |
|---|---|---|
| **Amazon Athena** | S3 のデータに **SQL で直接** 問い合わせる。サーバーレス。**スキャンしたデータ量** で課金 | ログの調査、ときどきの分析 |
| **Amazon Redshift** | 列指向のデータウェアハウス。大量データの集計が速い。Redshift Serverless もある | BI、定常的な大規模分析 |
| **Redshift Spectrum** | Redshift から S3 のデータも一緒に問い合わせる | DWH と データレイクの両方を使う |
| **Amazon EMR** | Spark、Hadoop などで大規模なデータ処理 | 複雑な加工、機械学習の前処理 |
| **Amazon OpenSearch Service** | 全文検索、ログの分析と可視化(OpenSearch Dashboards) | サイト内検索、ログ分析 |
| **Amazon Quick**(旧 Amazon QuickSight を含む) | ダッシュボードやグラフで **可視化** する BI サービス | 経営者向けのダッシュボード |
| AWS Data Exchange | 他社が提供するデータセットを購読して使う | 外部データの活用 |
| AWS Data Pipeline | データの移動と処理を定期実行する(古いサービス。新規には Glue や Step Functions が推奨) | |

### 7. 取り込み口の保護とサイズ・速度

- 取り込み口(Kinesis、Firehose、API Gateway、S3)には、IAM で送信元を限定し、**転送時は TLS**、保存時は KMS で暗号化します。VPC エンドポイントを使えば、インターネットを通りません。
- **処理量の計算**: 1秒あたりのデータ量とレコード数から、Kinesis のシャード数や、転送にかかる日数を見積もります。

### 8. まとめ: よく出る判断

| 要件 | 選ぶもの |
|---|---|
| ストリーミングデータを S3 に、コードを書かずに | Amazon Data Firehose |
| リアルタイムに複数のアプリで処理 | Kinesis Data Streams |
| 既存の Kafka を移行 | MSK |
| S3 のログを SQL で、サーバーなし | Athena |
| Athena を速く・安く | Parquet に変換し、パーティションを作る |
| CSV → Parquet の変換 | Glue ETL ジョブ |
