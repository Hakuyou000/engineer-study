# AWS SAA テキスト 4.0 コストを最適化したアーキテクチャの設計(20%)

対象: SAA-C03

「要件を満たしたうえで、最も安く」する分野です。ストレージ(4.1)、コンピューティング(4.2)、データベース(4.3)、ネットワーク(4.4)の4つに分かれます。どのタスクにも共通するコスト管理のツールを、最初の 4.1 で説明します。

## 4.1 コストを最適化したストレージを設計する

出題範囲: コスト管理ツール(Cost Explorer、Budgets、Cost and Usage Report)、コスト配分タグ、一括請求、S3 のストレージクラスとライフサイクル、S3 Intelligent-Tiering、リクエスタ支払い、EBS のボリュームタイプとサイズ、バックアップとアーカイブ、データ転送の方法(DataSync、Snow ファミリー、Transfer Family、Storage Gateway)、ストレージの自動拡張。

### 1. コスト管理のツール(全タスク共通)

| ツール | 何をするか |
|---|---|
| **AWS Cost Explorer** | 過去の費用をグラフで見る、サービス別・タグ別に分ける、今後の **費用を予測** する。リザーブドインスタンスや Savings Plans の購入の推奨も出す |
| **AWS Budgets** | 予算を決めて、**超えそう・超えたときに通知** する。予算アクションで、超えたときに IAM ポリシーを適用したり、EC2 を止めたりできる |
| **AWS Cost and Usage Report(CUR)** | 時間単位・リソース単位の **最も詳しい** 利用明細を S3 に出力する。Athena や Amazon Quick で分析する(現在はデータエクスポート機能から作成) |
| **コスト配分タグ** | リソースのタグ(例: `Project=ShopA`)で費用を分ける。**請求コンソールでタグを有効化** してから集計に使える |
| **一括請求**(Organizations) | 複数アカウントの請求をまとめる。使用量の合算で割引が効き、RI / Savings Plans の割引を共有できる |
| **AWS Compute Optimizer** | EC2、EBS、Lambda などのサイズが適切かを分析し、推奨する |
| **AWS Trusted Advisor** | 使われていないリソースなど、コスト削減の機会を知らせる(参考) |

覚え方: 「分析・予測」は Cost Explorer、「通知・上限」は Budgets、「最も細かい明細」は CUR です。

### 2. S3 のストレージクラス

| クラス | 取り出し | 最低保存期間 | 使いどころ |
|---|---|---|---|
| **S3 Standard** | すぐ | なし | 頻繁にアクセスするデータ |
| **S3 Intelligent-Tiering** | すぐ(アーカイブ層を有効にした場合は除く) | なし | **アクセスの頻度が分からない・変わる** データ。アクセス状況を見て自動で安い層に移す。少額の監視料金がかかる |
| **S3 Standard-IA** | すぐ | 30日 | アクセスは少ないが、必要なときはすぐ読みたい(取り出しに料金) |
| **S3 One Zone-IA** | すぐ | 30日 | Standard-IA より安いが **1つの AZ だけ**。作り直せるデータ、別にコピーがあるデータ |
| **S3 Glacier Instant Retrieval** | **ミリ秒** | 90日 | 四半期に1回程度しか読まないが、読むときはすぐ必要(医療画像など) |
| **S3 Glacier Flexible Retrieval** | 数分〜数時間(迅速: 1〜5分、標準: 3〜5時間、大容量: 5〜12時間) | 90日 | 年に数回のアーカイブ |
| **S3 Glacier Deep Archive** | 12時間以内(標準)、48時間以内(大容量) | 180日 | **最も安い**。法令で長期間保存するが、ほとんど読まない |

- IA 系のクラスには、最低のオブジェクトサイズ(128 KB)の課金があります。小さなファイルが大量にある場合は注意します。
- 最低保存期間より前に削除・移動すると、残りの期間分の料金がかかります。

### 3. S3 ライフサイクル

ライフサイクルルールで、オブジェクトを **自動で安いクラスに移動(移行)** したり、**削除(有効期限)** したりできます。

例: ログを「30日後に Standard-IA、90日後に Glacier Flexible Retrieval、365日後に削除」。

- プレフィックスやタグで対象を絞れます。
- バージョニングが有効なバケットでは、**古いバージョン(非現行バージョン)** にも移行・削除のルールを設定できます。設定しないと古いバージョンが溜まり続け、費用が増えます。
- **未完了のマルチパートアップロード** を一定期間後に削除するルールも設定します(途中で止まったアップロードの断片にも料金がかかるため)。
- **S3 Storage Lens** と **ストレージクラス分析** で、アクセスの傾向を調べ、ルールを決める参考にします。

### 4. アクセス方法とコスト

- **リクエスタ支払い**: バケットの所有者ではなく、**データを取得する側が** 転送料金とリクエスト料金を払います。大きなデータセットを他の組織に提供するときに使います。
- **まとめてアップロード**: 小さなファイルを大量に個別アップロードすると、リクエスト料金がかさみます。まとめて(圧縮して)アップロードすると安くなることがあります。
- S3 へのデータの **受信(アップロード)の転送料金は無料** です。取り出し(インターネットへの送信)に料金がかかります。

### 5. EBS のコスト

- **gp2 から gp3 への移行**: 多くの場合、同じ性能でも gp3 のほうが安くなります。gp3 は容量と IOPS を別々に決められるため、「IOPS のために容量を大きくする」必要がありません。
- **HDD 系(st1、sc1)**: 大きなデータを順番に読む用途なら、SSD より大幅に安くなります。
- **適切なサイズ**: 使っていない容量にも料金がかかります。使用率を見て、必要な分だけにします。
- **未使用のボリューム**: EC2 を終了してもボリュームが残っていることがあります(「終了時に削除」の設定による)。定期的に確認して削除します。
- **スナップショット**: 増分で保存されます。古いスナップショットは削除し、長期保存は **EBS スナップショットアーカイブ**(安いが復元に時間がかかる)を使います。Amazon Data Lifecycle Manager で作成と削除を自動化できます。

### 6. ファイルストレージのコスト

- **EFS**: ライフサイクル管理で、アクセスされないファイルを **IA やアーカイブのクラスに自動で移動** します。1つの AZ でよければ **EFS One Zone** で安くなります。
- **FSx**: 用途(Windows、Lustre、ONTAP、OpenZFS)に合わせて選び、データの重複排除や圧縮の機能で容量を減らします。FSx for Lustre には、一時的な処理用の安い「スクラッチ」と、長期用の「永続」があります。

### 7. バックアップとアーカイブ

- **AWS Backup** のバックアップ計画で、保持期間を決め、古いバックアップを自動で削除します。長期保存はコールドストレージに移せます。
- テープ装置の運用をやめたい: **Tape Gateway** で仮想テープを S3 Glacier / Deep Archive に保存します。
- 法令で7年保存するが読まない: S3 Glacier Deep Archive。

### 8. データ転送の最も安い方法

| 状況 | 方法 |
|---|---|
| 大量のデータ(数十 TB〜PB)、回線が細い | **Snow ファミリー**(物理デバイス) |
| 継続的・定期的な転送、回線に余裕がある | **DataSync** |
| 取引先から SFTP で受け取る | **Transfer Family** |
| オンプレミスのアプリからそのまま S3 を使う | **Storage Gateway** |
| すでに Direct Connect がある | Direct Connect 経由で DataSync(インターネットより送信料金が安い) |

計算の例: 100 TB を 100 Mbps の回線で送ると、理論上でも約93日かかります。この場合は Snow ファミリーが現実的です。

### 9. ストレージの自動拡張

- 容量を前もって確保すると、使っていない分にも料金がかかります。**使った分だけ** 課金される S3、EFS、Aurora、DynamoDB を選ぶと、無駄がありません。
- RDS では **ストレージの自動スケーリング** を有効にして、最初は小さく作り、必要に応じて増やします。
- EBS は自動では増えないため、監視して必要なときに拡張します。

### 10. まとめ: よく出る判断

| 要件 | 選ぶもの |
|---|---|
| アクセス頻度が予測できない | S3 Intelligent-Tiering |
| 30日後はほとんど読まないが、すぐ読める必要がある | S3 Standard-IA(ライフサイクルで移行) |
| 作り直せるデータを安く | S3 One Zone-IA |
| 長期保存、ほぼ読まない、最安 | S3 Glacier Deep Archive |
| ミリ秒で取り出せるアーカイブ | S3 Glacier Instant Retrieval |
| データの取得料金を利用者に払わせる | リクエスタ支払い |
| 予算を超えそうなら通知 | AWS Budgets |
| 部署ごとの費用を見る | コスト配分タグ + Cost Explorer |
| gp2 のコストを下げる | gp3 に変更 |
| 数百 TB を回線が細い拠点から移行 | Snow ファミリー |

## 4.2 コストを最適化したコンピューティングを設計する

出題範囲: 購入オプション(オンデマンド、Savings Plans、リザーブドインスタンス、スポットインスタンス、Dedicated Hosts)、インスタンスのファミリーとサイズの選び方(ライトサイジング)、Lambda・Fargate・EC2 の使い分け、コンテナとサーバーレスによる利用効率の向上、Auto Scaling と休止、ロードバランサーの選び方、本番と本番以外の可用性、Outposts などのハイブリッド、エッジ処理。

### 1. EC2 の購入オプション

| オプション | 割引の目安 | 特徴 | 向いている場合 |
|---|---|---|---|
| **オンデマンド** | なし | 秒単位の課金。いつでも開始・停止 | 短期、予測できない、試験的な利用 |
| **Savings Plans** | 大きい | **1年または3年**、1時間あたりの利用金額を約束する | 長期間の安定した利用 |
| **リザーブドインスタンス(RI)** | 大きい | 1年または3年、特定のインスタンスの利用を約束する | 長期間の安定した利用(特定の構成) |
| **スポットインスタンス** | **最大90%** | AWS の余っている容量を使う。**2分前の通知で中断** されることがある | 中断に強い処理(バッチ、CI、データ処理、ステートレスな Web) |
| **Dedicated Hosts** | なし(高い) | 物理サーバーを1台まるごと専有。ソケット数・コア数が見える | **サーバー単位のソフトウェアライセンス**(BYOL)、規制 |
| Dedicated Instances | なし(高い) | 自分専用のハードウェアで動くが、物理サーバーの指定はできない | 他の利用者とハードウェアを共有できない規制 |
| オンデマンドキャパシティ予約 | なし | 特定の AZ で容量を確保する(割引はないが Savings Plans と組み合わせ可) | 確実に起動したい期間がある(イベント、DR) |

#### Savings Plans の種類

| 種類 | 柔軟性 | 割引 |
|---|---|---|
| **Compute Savings Plans** | インスタンスファミリー、サイズ、リージョン、OS を問わず、**EC2、Fargate、Lambda** に適用 | やや小さい |
| **EC2 Instance Savings Plans** | 特定のリージョンの、特定のインスタンスファミリーに限定(サイズや OS は変更可) | 大きい |

#### リザーブドインスタンスの種類

| 種類 | 内容 |
|---|---|
| スタンダード RI | 割引が最も大きい。インスタンスファミリーなどの変更に制限がある |
| コンバーティブル RI | 別のインスタンスファミリーなどに交換できる。割引はやや小さい |

- 支払い方法: **全額前払い** が最も割引が大きく、一部前払い、前払いなし の順に割引が小さくなります。
- 「将来インスタンスの種類を変えるかもしれない」なら、Compute Savings Plans かコンバーティブル RI を選びます。

#### スポットインスタンスの使い方

- **中断されても問題ない処理** に使います。中断時の通知を受け取り、処理の途中経過を保存します。
- Auto Scaling で **オンデマンドとスポットを組み合わせ**(混合インスタンスポリシー)、複数のインスタンスタイプを指定すると、中断の影響を小さくできます。
- データベースや、止められない1台だけのサーバーには使いません。

### 2. インスタンスの選び方(ライトサイジング)

- **ファミリー**: 処理の特徴(CPU、メモリ、ディスク、GPU)に合ったものを選びます(3.2 参照)。
- **サイズ**: CPU やメモリの使用率が常に低いなら、小さいサイズに変えます。**Compute Optimizer** の推奨を使います。
- **世代**: 新しい世代のほうが、同じ価格で性能が高いことが多いです。
- **Graviton**: Arm に対応したアプリなら、Graviton インスタンスで費用を下げられます。
- **バースト可能(T 系)**: 普段は低負荷のサーバーを安く動かせます。

### 3. Lambda、Fargate、EC2 の使い分け

| サービス | 費用の特徴 | 安くなる場合 |
|---|---|---|
| **Lambda** | リクエスト数と実行時間だけ。**使っていない時間は0円** | アクセスが少ない、または不定期。イベント駆動 |
| **Fargate** | コンテナの vCPU とメモリを秒単位で課金 | サーバー管理をなくしたい、中程度の負荷のコンテナ |
| **EC2** | インスタンスの稼働時間 | 常に高負荷が続く。RI / Savings Plans / スポットで大きく割引できる |

- **コンテナ** にまとめると、1台の EC2 で複数のアプリを動かし、リソースの無駄を減らせます。
- **マイクロサービス** にすると、負荷の高い部分だけをスケールできます。

### 4. スケーリングと休止

- **Auto Scaling**: 需要に合わせて台数を減らし、使わない時間の費用を下げます。
- **スケジュールされたスケーリング**: 夜間や週末に台数を減らします。
- **開発環境の停止**: 業務時間外は EC2 を停止します(Instance Scheduler、EventBridge Scheduler + Lambda / Systems Manager)。停止中は EC2 の料金がかからず、EBS の料金だけになります。
- **EC2 の休止**(ハイバネーション): メモリの内容を EBS の起動ボリュームに保存して停止します。再開すると、アプリを最初から起動し直さずに前の状態から再開できます。起動に時間がかかるアプリを、使わない時間だけ止めたい場合に使います。起動ボリュームの暗号化が必要です。

### 5. 本番と本番以外の可用性

| 環境 | 可用性の考え方 |
|---|---|
| 本番 | 複数 AZ、Multi-AZ の DB、十分な台数 |
| 開発・テスト | 1つの AZ でよい、Multi-AZ なし、小さいサイズ、スポット、業務時間外は停止 |

すべての環境を本番と同じにすると、費用が無駄になります。

### 6. ロードバランサーの選び方とコスト

| 種類 | 層 | 使いどころ |
|---|---|---|
| ALB | L7 | HTTP の内容で振り分ける。1つの ALB で、ホスト名やパスごとに複数のアプリを扱える(ロードバランサーの数を減らせる) |
| NLB | L4 | TCP / UDP、高性能 |
| GWLB | L3 | セキュリティアプライアンス |

必要な機能だけを持つものを選び、1つのロードバランサーで複数のアプリを扱うと費用を抑えられます。

### 7. ハイブリッドとエッジ

- **AWS Outposts**: データを社内に置く必要がある、オンプレミスのシステムと超低遅延でつなぐ必要がある場合に、自社のデータセンターで AWS を使います。
- **エッジ処理**: CloudFront Functions(軽い処理を安く)、Lambda@Edge(より複雑な処理)で、オリジンまで行かずにエッジで処理すると、オリジン側の計算資源と転送量を減らせます。
- **AWS License Manager**: ソフトウェアライセンスの使用状況を管理し、ライセンス違反や買いすぎを防ぎます。

### 8. まとめ: よく出る判断

| 要件 | 選ぶもの |
|---|---|
| 3年間、安定して動く EC2 を最も安く | 3年の Savings Plans / RI(全額前払い) |
| 将来、インスタンスの種類やサービスを変えるかも | Compute Savings Plans |
| 中断してもよいバッチを最も安く | スポットインスタンス |
| サーバー単位のライセンスを持ち込む | Dedicated Hosts |
| 1日に数回だけ動く短い処理 | Lambda |
| CPU 使用率がいつも10%程度 | 小さいサイズに変更(Compute Optimizer) |
| 開発環境を夜間と週末に止める | スケジュールで停止、Auto Scaling の台数を0に |
| 起動に時間がかかるアプリを途中の状態で止める | EC2 の休止 |
| 1つの ALB で複数のアプリ | ALB のホスト / パスベースルーティング |

## 4.3 コストを最適化したデータベースを設計する

出題範囲: DynamoDB と RDS の使い分け、サーバーレス DB、キャパシティモード、リザーブド DB インスタンス、キャッシュによるコスト削減、接続とプロキシ、リードレプリカ、バックアップと保持期間(スナップショットの頻度)、エンジンの選び方、時系列・列指向の DB、DB の移行。

### 1. データベースの費用の考え方

| 選択 | 費用の特徴 |
|---|---|
| **RDS / Aurora(プロビジョンド)** | インスタンスの稼働時間 + ストレージ + I/O(Aurora の構成による)。常に動いている |
| **Aurora Serverless v2** | 使った容量(ACU)の分だけ。負荷が変動する、ときどきしか使わない DB で安くなる |
| **DynamoDB オンデマンド** | リクエストの数だけ。アクセスが少ない、または予測できないときに安い |
| **DynamoDB プロビジョンド** | 決めた容量の分。負荷が安定していれば安い。Auto Scaling と、予約容量(リザーブドキャパシティ)でさらに安くなる |

- 安定して動く RDS / Aurora は、**リザーブド DB インスタンス**(1年または3年)で割引されます。
- 開発用の RDS は、使わない時間に **停止** できます(停止は最大7日間で、その後は自動で起動します)。長期間使わないなら、スナップショットを取って削除します。

### 2. DynamoDB と RDS の使い分け

| 観点 | DynamoDB | RDS / Aurora |
|---|---|---|
| データの形 | キーで読み書きする、柔軟な項目 | 表と表の結合、複雑な SQL |
| スケール | 自動で水平に無限 | インスタンスのサイズとレプリカ |
| 運用 | サーバーレス、パッチ不要 | マネージドだがインスタンスを選ぶ |
| 向いている例 | セッション、ショッピングカート、ゲームの状態、IoT | 会計、在庫管理、既存の業務システム |

### 3. キャッシュでコストを下げる

- 読み取りの多い DB の前に **ElastiCache** を置くと、DB のインスタンスを大きくしなくても済みます。大きな DB インスタンスより、キャッシュのほうが安いことが多いです。
- DynamoDB では **DAX** で読み取りの容量(RCU)を減らせます。
- CloudFront や API Gateway のキャッシュで、そもそも DB まで届くリクエストを減らします。

### 4. 接続とレプリカ

- **RDS Proxy** で接続をまとめると、接続数のために DB インスタンスを大きくする必要がなくなります。
- 読み取りの負荷はリードレプリカに分散し、プライマリを必要以上に大きくしないようにします。ただし、レプリカごとに費用がかかります。必要な台数だけにします。
- 別リージョンへのレプリケーションには、データ転送の料金がかかります。

### 5. バックアップと保持期間

- RDS の自動バックアップは、DB のサイズまでは追加料金なしで保存されます。それを超える分と、手動スナップショットには料金がかかります。
- **保持期間とスナップショットの頻度は、要件(RPO と法令)から決めます**。必要以上に長く・多く保存しないようにします。
- AWS Backup で、保持期間を過ぎたバックアップを自動で削除し、長期保存分はコールドストレージへ移します。
- DynamoDB の TTL で、不要になった項目を自動で削除すると、ストレージの費用が下がります(削除に料金はかかりません)。
- **データ保持ポリシー**: 古いデータは、DB から S3(Parquet など)に移し、必要なときだけ Athena で読むと安くなります。

### 6. エンジンと種類の選び方

- **商用ライセンス**(Oracle、SQL Server)は費用が高くなります。オープンソースのエンジン(MySQL、PostgreSQL、Aurora)に移行すると、ライセンス費用をなくせます。
- **時系列データ**(センサー、メトリクス): **Amazon Timestream** のような時系列 DB は、時刻で集計する処理が得意で、古いデータを安い層へ自動で移します。
- **列指向**(分析): **Redshift** は、必要な列だけを読むため、大量データの集計を少ない資源で処理できます。ときどきの分析なら Redshift Serverless や Athena で、使った分だけ払います。

### 7. データベースの移行

- **AWS DMS**: 移行元を動かしたままデータを移します。移行用のレプリケーションインスタンスの料金がかかります(サーバーレスのオプションもあります)。
- **SCT / DMS Schema Conversion**: 異種移行のとき、スキーマとコードを変換します。
- 例: 「オンプレミスの Oracle を、ライセンス費用を減らすために Aurora PostgreSQL に移したい」→ SCT でスキーマ変換、DMS でデータ移行。
- 別のリージョンやアカウントへの移行には、スナップショットのコピーや、リードレプリカの昇格も使えます。

### 8. まとめ: よく出る判断

| 要件 | 選ぶもの |
|---|---|
| ときどきしか使わない、負荷が読めない RDB | Aurora Serverless v2 |
| アクセスが予測できない NoSQL | DynamoDB オンデマンド |
| 負荷が安定した NoSQL を安く | DynamoDB プロビジョンド + Auto Scaling |
| 3年間動き続ける RDS | リザーブド DB インスタンス |
| 読み取りが多く DB を大きくしたくない | ElastiCache |
| 期限の切れたデータを自動で消す | DynamoDB TTL |
| Oracle のライセンス費用をなくす | Aurora PostgreSQL へ移行(SCT + DMS) |
| 時系列データ | Timestream |
| 大量データの集計 | Redshift(列指向) |

## 4.4 コストを最適化したネットワークを設計する

出題範囲: データ転送料金の仕組み、NAT ゲートウェイと NAT インスタンス、NAT ゲートウェイの配置、VPC エンドポイント、Direct Connect・VPN・インターネットの使い分け、帯域の選び方、Transit Gateway と VPC ピアリング、CloudFront によるエッジキャッシュ、Global Accelerator、DNS、スロットリング、既存ワークロードのネットワークの見直し。

### 1. データ転送料金の基本

| 通信 | 料金 |
|---|---|
| インターネット → AWS(受信) | **無料** |
| AWS → インターネット(送信) | **有料**(量が多いほど単価が下がる) |
| 同じ AZ の中(プライベート IP) | 無料 |
| **AZ をまたぐ** | **有料**(送信側・受信側の両方) |
| **リージョンをまたぐ** | **有料** |
| CloudFront → インターネット | 有料だが、オリジンから直接送るより安いことが多い。オリジン → CloudFront は無料 |
| VPC → S3(同じリージョン、ゲートウェイエンドポイント経由) | 無料 |

ポイント:

- 通信の多いサーバー同士は、可用性の要件を満たす範囲で **同じ AZ** に置くと、転送料金が下がります。
- パブリック IP や Elastic IP を通して同じリージョンの別のサーバーと通信すると、料金がかかることがあります。**プライベート IP** で通信します。
- パブリック IPv4 アドレスには、使っているかどうかにかかわらず時間料金がかかります。不要なものは解放します。

### 2. NAT ゲートウェイのコスト

NAT ゲートウェイには、**時間料金** と、**処理したデータ量の料金** がかかります。

| 比較 | NAT ゲートウェイ | NAT インスタンス |
|---|---|---|
| 管理 | AWS が管理。自動でスケール | 自分で EC2 を管理(パッチ、冗長化、スケール) |
| 可用性 | AZ 内で冗長化されている | 自分で作る必要がある |
| 費用 | 高め | 小さいインスタンスなら安い(運用の手間がかかる) |

NAT ゲートウェイの配置:

| 構成 | 費用 | 可用性 |
|---|---|---|
| **1つの NAT ゲートウェイを全 AZ で共有** | 安い。ただし他の AZ からの通信に AZ 間の転送料金がかかる | その AZ が止まると、全 AZ の外向き通信が止まる |
| **AZ ごとに NAT ゲートウェイ** | 高い | AZ 障害の影響がその AZ だけ |

本番は AZ ごと、開発環境は1つで共有、のように使い分けます。

NAT ゲートウェイの費用を下げる方法:

- S3 と DynamoDB への通信は、**ゲートウェイエンドポイント**(無料)を使い、NAT ゲートウェイを通さない。
- 他の AWS サービスへの通信が多いなら、インターフェースエンドポイントのほうが安くなることがあります(料金を比較して決めます)。

### 3. オンプレミスとの接続の選び方

| 方法 | 費用 | 性能 | 向いている場合 |
|---|---|---|---|
| インターネット(HTTPS) | 最も安い | 不安定 | 少量で、暗号化された通信で足りる |
| **Site-to-Site VPN** | 安い(時間料金 + 送信データ) | インターネット経由なので不安定 | 早く・安くつなぎたい、Direct Connect のバックアップ |
| **Direct Connect** | ポートの時間料金 + 送信データ(インターネット経由より単価が安い) | 安定、広帯域 | 大量のデータを継続的に送る、安定性が必要 |

- **帯域の選び方**: 必要な帯域に合わせて、Direct Connect の速度(ホスト型接続なら 50 Mbps などの小さい単位も選べる)や VPN の本数を決めます。大きすぎる帯域は無駄になります。
- 大量のデータを毎月 AWS から送り出す(オンプレミスへ戻す)なら、Direct Connect のほうが送信料金が安くなり、全体の費用が下がることがあります。

### 4. VPC 同士の接続とコスト

| 方法 | 費用の特徴 |
|---|---|
| **VPC ピアリング** | 接続自体は無料。AZ やリージョンをまたぐデータ転送に料金。少数の VPC なら安い |
| **Transit Gateway** | 接続(アタッチメント)ごとの時間料金 + 処理したデータ量の料金。多数の VPC を管理しやすい |
| **PrivateLink** | エンドポイントの時間料金 + データ処理料金。特定のサービスだけを共有 |
| **共有 VPC**(RAM でサブネットを共有) | 複数のアカウントで1つの VPC を使うため、接続や NAT ゲートウェイを減らせる |

少数の VPC で大量の通信をするならピアリング、多数の VPC やオンプレミスを集約するなら Transit Gateway です。

### 5. CDN とエッジキャッシュ

- **CloudFront** でキャッシュすると、オリジン(EC2、S3)からの送信が減り、オリジンの台数も減らせます。
- **価格クラス**: CloudFront で使うエッジロケーションの地域を絞ると、費用を下げられます(利用者がいない地域を除く)。
- 静的なサイトは、EC2 を使わず **S3 + CloudFront** で配信すると、サーバーの費用がかかりません。

### 6. ルーティングで転送料金を減らす

| 見直す点 | 対策 |
|---|---|
| プライベートサブネットから S3 へ大量の通信 | S3 のゲートウェイエンドポイント |
| 別の AZ の DB やキャッシュに大量の通信 | 同じ AZ に置く、AZ を意識した接続先 |
| 別リージョンへの不要な複製 | 必要なデータだけを複製する |
| 世界中の利用者への配信 | CloudFront |
| プライベートな通信を、パブリックを経由して送っている | プライベート IP、VPC エンドポイント |
| グローバルな TCP / UDP | Global Accelerator(性能が上がるが、追加料金がかかる点も考える) |

### 7. DNS

- **Route 53 のエイリアスレコード** で AWS リソース(ELB、CloudFront、S3 など)を指すと、その問い合わせは無料です。
- TTL を長くすると、問い合わせの回数が減ります(ただし、切り替えの反映は遅くなります)。

### 8. スロットリングの戦略

- **API Gateway のスロットリングと使用量プラン** で、顧客ごとのリクエスト数を制限し、バックエンドが不要に大きくなるのを防ぎます。
- **SQS** で急な負荷を受け止め、処理側は一定の台数で処理します(ピークに合わせた台数を用意しなくて済みます)。
- **WAF のレートベースルール** で、ボットなどの大量のリクエストを止め、無駄な処理と転送を減らします。

### 9. 既存ワークロードの見直し

- **VPC フローログ** で、どこからどこへ、どれくらい通信しているかを調べます。
- **Cost Explorer** で「データ転送」の費用を、使用タイプ別に確認します(AZ 間、リージョン間、インターネットなど)。
- 費用の大きい通信から、エンドポイント、配置の変更、キャッシュで減らします。

### 10. まとめ: よく出る判断

| 要件 | 選ぶもの |
|---|---|
| NAT ゲートウェイ経由の S3 通信の費用を減らす | S3 ゲートウェイエンドポイント |
| 開発環境の NAT を安く | NAT ゲートウェイを1つにして共有 |
| 本番で AZ 障害に備える | AZ ごとの NAT ゲートウェイ |
| 毎月大量のデータをオンプレミスへ送る | Direct Connect |
| すぐに・安く暗号化した接続 | Site-to-Site VPN |
| 少数の VPC 同士を安く | VPC ピアリング |
| 多数の VPC を集約 | Transit Gateway |
| オリジンからの送信料金を減らす | CloudFront |
| 利用者のいない地域のエッジを使わない | CloudFront の価格クラス |
| 顧客ごとに API の利用量を制限 | API Gateway の使用量プラン |
