# AWS SAA テキスト 2.0 弾力性に優れたアーキテクチャの設計(26%)

対象: SAA-C03

「負荷が増えても、部品が壊れても、サービスを止めない」設計を扱います。2.1 は「スケールできて、部品同士が依存しすぎない設計」、2.2 は「壊れても動き続ける設計と災害対策」です。

## 2.1 スケーラブルで疎結合なアーキテクチャを設計する

出題範囲: 水平・垂直スケーリング、ELB、Auto Scaling、多層アーキテクチャ、ステートレスな設計、SQS・SNS・EventBridge・MQ によるメッセージング、イベント駆動、Lambda・Fargate などのサーバーレス、ECS・EKS によるコンテナ、Step Functions、API Gateway、キャッシュ戦略、CloudFront、ストレージの種類、リードレプリカ、目的別のマネージドサービス。

### 1. スケーリングの考え方

| 方式 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **垂直スケーリング**(スケールアップ) | インスタンスタイプを大きくする | アプリの変更が不要 | 上限がある。変更時に停止が必要なことが多い |
| **水平スケーリング**(スケールアウト) | インスタンスの台数を増やす | 上限がほぼない。1台壊れても他が動く | アプリが台数の増減に耐える必要がある |

クラウドでは水平スケーリングが基本です。そのためには、アプリケーションを **ステートレス** にします。

- **ステートフル**: サーバーがユーザーのセッション情報などを自分の中に持つ。別のサーバーに振り分けられると、ログイン状態が消えてしまう。
- **ステートレス**: 状態をサーバーの外(ElastiCache、DynamoDB など)に置く。どのサーバーに振り分けられても同じように処理できる。

ロードバランサーの **スティッキーセッション**(同じユーザーを同じサーバーに振り分け続ける機能)でもログイン状態は保てますが、そのサーバーが壊れるとセッションが失われます。セッションは外部に置くのが望ましい設計です。

### 2. Elastic Load Balancing(ELB)

複数のターゲット(EC2、コンテナ、IP、Lambda)に通信を振り分けるサービスです。複数の AZ にまたがって動き、**ヘルスチェック** で異常なターゲットを外します。

| 種類 | 層 | 特徴 | 使いどころ |
|---|---|---|---|
| **ALB**(Application Load Balancer) | L7(HTTP/HTTPS) | URL のパスやホスト名、ヘッダーで振り分け先を変えられる。WAF、Cognito 認証と連携。Lambda をターゲットにできる | Web アプリ、マイクロサービス |
| **NLB**(Network Load Balancer) | L4(TCP/UDP/TLS) | 非常に高速・大量の接続。**AZ ごとに固定 IP**(Elastic IP も可)。送信元 IP を保持 | ゲーム、IoT、固定 IP が必要な場合、PrivateLink |
| **GWLB**(Gateway Load Balancer) | L3 | 他社のファイアウォールや IDS などの仮想アプライアンスに通信を通す | セキュリティアプライアンスの集約 |

- **パスベースルーティング**: `/api/*` はコンテナ群へ、`/images/*` は別のサーバー群へ、のように振り分けます(ALB)。
- **ホストベースルーティング**: `shop.example.com` と `blog.example.com` を1つの ALB で振り分けます(ALB)。
- **登録解除の遅延**(旧 Connection Draining): ターゲットを外すとき、処理中のリクエストが終わるまで待ちます。
- **クロスゾーン負荷分散**: すべての AZ のターゲットに均等に振り分けます。ALB では既定で有効です。

### 3. Amazon EC2 Auto Scaling

需要に応じて EC2 の台数を自動で増減するサービスです。

- **起動テンプレート**: 起動する EC2 の設定(AMI、インスタンスタイプ、SG など)。
- **最小・最大・希望の台数** を決めます。最小台数を2以上にして複数 AZ に分散すれば、1台が壊れても自動で入れ替わります(自己修復)。
- ヘルスチェックの種類を **ELB** にすると、アプリが応答しないインスタンスも入れ替わります(EC2 のヘルスチェックだけでは、OS が動いていればアプリが止まっていても正常とみなされます)。

| スケーリングポリシー | 内容 |
|---|---|
| **ターゲット追跡** | 「CPU 使用率を平均50%に保つ」のように目標値を決めるだけ。最もよく使う |
| ステップスケーリング | アラームの値の大きさに応じて、増やす台数を段階的に変える |
| シンプルスケーリング | アラームで決まった台数を増減する。クールダウン期間を待つ |
| **スケジュール** | 「毎朝9時に10台にする」のように時刻で変える。予測できる負荷に使う |
| **予測スケーリング** | 過去の傾向から負荷を予測し、事前に台数を増やす |

- **ウォームプール**: 起動に時間がかかるアプリのために、準備済みのインスタンスを止めた状態で待機させます。
- **ライフサイクルフック**: 起動時や終了時に、ログの退避などの処理を差し込みます。
- **AWS Auto Scaling**(サービス名): EC2 だけでなく、ECS、DynamoDB、Aurora のレプリカなど複数のリソースのスケーリングをまとめて設定できます。

### 4. 疎結合: キューとメッセージング

**密結合** とは、部品同士が直接呼び合い、片方が止まるともう片方も止まる状態です。**疎結合** にすると、部品ごとに独立してスケールでき、障害の影響が広がりません。

#### Amazon SQS(Simple Queue Service)

メッセージを一時的に溜める **キュー** です。送る側(プロデューサー)はキューに入れるだけで、受ける側(コンシューマー)は自分のペースで取り出します。

| 種類 | 順序 | 重複 | 処理量 |
|---|---|---|---|
| **標準キュー** | おおむね順序どおりだが保証なし | まれに同じメッセージが2回以上届く(少なくとも1回の配信) | ほぼ無制限 |
| **FIFO キュー** | **送った順序を保証** | **重複なし**(1回だけ処理) | 標準より少ない |

重要な設定:

- **可視性タイムアウト**: コンシューマーが受け取ったメッセージは、一定時間ほかのコンシューマーから見えなくなります。時間内に削除されないと、再び見えるようになり、別のコンシューマーが処理します。処理時間より長く設定します。
- **メッセージの保持期間**: 既定は4日、最大14日です。
- **ロングポーリング**: キューが空のとき、最大20秒までメッセージの到着を待ちます。空の応答が減り、コストが下がります。
- **デッドレターキュー(DLQ)**: 何度処理しても失敗するメッセージを別のキューに移し、後で調べられるようにします。
- **遅延キュー**: メッセージを入れてから、一定時間見えないようにします。

使い方の例: Web サーバーが注文を SQS に入れ、処理サーバー群が取り出して処理する。注文が急増しても Web サーバーは止まらず、処理サーバーは **キューに溜まったメッセージの数** を見て Auto Scaling で台数を増やします。

#### Amazon SNS(Simple Notification Service)

**パブリッシュ/サブスクライブ**(Pub/Sub)型の通知サービスです。トピックに1回送ると、購読しているすべての宛先(SQS、Lambda、HTTP、メール、SMS)に同時に届きます。

- **ファンアウト**: SNS トピックに複数の SQS キューを購読させ、1つのイベントを複数のシステムで並行して処理します。
- **メッセージフィルタリング**: 購読ごとに条件を付けて、必要なメッセージだけを受け取ります。
- FIFO トピックもあります。

SQS は「1つのメッセージを1つのコンシューマーが処理する(引き取る)」、SNS は「1つのメッセージを全購読者に配る(押し出す)」と覚えます。

#### Amazon EventBridge

**イベントバス** を使って、イベントを条件に応じて振り分けるサービスです。

- AWS のサービスで起きたこと(EC2 の状態変化、S3 へのアップロードなど)、自作アプリのイベント、SaaS(Zendesk、Datadog など)のイベントを受け取れます。
- **ルール** でイベントの内容を条件にし、ターゲット(Lambda、Step Functions、SQS など)に送ります。
- **EventBridge Scheduler**: 決まった日時や間隔で処理を起動します(cron のような使い方)。

#### Amazon MQ

Apache ActiveMQ や RabbitMQ のマネージドサービスです。**既存のアプリが AMQP、MQTT、STOMP などの標準プロトコルを使っている場合**、コードを書き換えずに AWS へ移行できます。新しく作るなら SQS や SNS が第一候補です。

### 5. イベント駆動アーキテクチャ

「何かが起きたら、それをきっかけに処理が動く」設計です。

例: S3 に画像がアップロードされる → S3 のイベント通知で Lambda が起動 → サムネイル画像を作って別のバケットに保存。

- サーバーを常に動かしておく必要がなく、イベントの数に応じて自動でスケールします。
- S3 のイベント通知の送り先は、Lambda、SQS、SNS、EventBridge です。

### 6. サーバーレス

#### AWS Lambda

コードを置くだけで、イベントに応じて実行されるサービスです。

- サーバーの管理は不要で、**実行回数と実行時間(メモリ量に比例)** で課金されます。
- 1回の実行は **最大15分** までです。それより長い処理には向きません。
- メモリは 128 MB〜10,240 MB で設定し、**CPU はメモリに比例して割り当てられます**。
- **同時実行数** には上限があります。重要な関数には **予約済み同時実行** で枠を確保できます。
- 初回起動の遅れ(コールドスタート)を避けたいときは、**プロビジョニング済み同時実行** を使います。
- VPC 内のリソース(RDS など)にアクセスする設定もできます。その場合、インターネットへ出るには NAT ゲートウェイが必要です。

#### AWS Fargate

コンテナを、サーバー(EC2)を管理せずに動かすサービスです。ECS や EKS と一緒に使います。15分を超える長い処理や、常に動き続けるコンテナに向いています。

### 7. コンテナ

| サービス | 内容 |
|---|---|
| **Amazon ECS** | AWS 独自のコンテナ管理サービス。シンプルで AWS のサービスとの連携が強い |
| **Amazon EKS** | Kubernetes のマネージドサービス。すでに Kubernetes を使っている、または他の環境と同じ仕組みで動かしたい場合 |
| **Amazon ECR** | コンテナイメージを保存するレジストリ。脆弱性スキャンもできる |
| ECS Anywhere / EKS Anywhere | オンプレミスのサーバーでも ECS / EKS の仕組みでコンテナを動かす |
| EKS Distro | EKS と同じ Kubernetes のディストリビューションを自分の環境で使う |

ECS / EKS でコンテナを動かす場所(起動タイプ)は2つあります。

| 起動タイプ | 管理 | 向いている場合 |
|---|---|---|
| **Fargate** | サーバー管理が不要 | 運用の手間を減らしたい |
| **EC2** | EC2 を自分で管理 | GPU が必要、細かい調整が必要、大量の常時稼働でコストを下げたい |

**AWS Proton** は、プラットフォームチームが用意したテンプレートで、開発者がコンテナやサーバーレスのアプリを決められた構成でデプロイできるようにするサービスです(提供の状況は公式で確認してください)。

**既存のアプリをコンテナに移行する** ときは、アプリと必要なライブラリをコンテナイメージにまとめ、ECR に保存し、ECS や EKS で動かします。設定値や秘密情報は、イメージに含めず、環境変数や Secrets Manager から渡します。

### 8. AWS Step Functions(ワークフローの制御)

複数の処理を順番・分岐・並列・リトライ付きでつなぐ **ステートマシン** を作るサービスです。

- 「注文を受ける → 在庫を確認 → 決済 → 発送の手配」のような手順を、図のように定義できます。
- エラー時の再試行や、失敗したときの代替処理を、コードを書かずに設定できます。
- 人の承認を待つ処理や、長時間(最大1年)かかるワークフローにも使えます(Standard ワークフロー)。大量・短時間の処理には Express ワークフローを使います。

Lambda の中で別の Lambda を呼び出して長い処理をつなぐより、Step Functions で制御するほうが管理しやすくなります。

### 9. Amazon API Gateway

API を作成・公開・管理するサービスです。バックエンドに Lambda、HTTP エンドポイント、AWS のサービスをつなげます。

| API の種類 | 特徴 |
|---|---|
| REST API | 多機能(API キーと使用量プラン、キャッシュ、リクエストの検証など) |
| HTTP API | シンプルで安く、低遅延 |
| WebSocket API | チャットなどの双方向通信 |

- **スロットリング**: 1秒あたりのリクエスト数に上限を設け、バックエンドを守ります。
- **使用量プランと API キー**: 顧客ごとにリクエスト数の上限や割り当てを決めます。
- **キャッシュ**: 同じリクエストへの応答を一定時間保存し、バックエンドの負荷を下げます(REST API)。
- **認証**: IAM、Cognito ユーザープール、Lambda オーソライザー(独自の認証処理)を使えます。
- エンドポイントの種類: エッジ最適化(CloudFront 経由)、リージョン、プライベート(VPC 内からのみ)。

「API Gateway + Lambda + DynamoDB」は、サーバーを管理しない Web API の定番構成です。

### 10. キャッシュ戦略

よく使うデータを、速い場所に一時的に保存しておくことを **キャッシュ** と言います。

| 場所 | サービス | 例 |
|---|---|---|
| 利用者に近いエッジ | CloudFront | 画像、動画、静的ファイル、API の応答 |
| API の手前 | API Gateway のキャッシュ | API の応答 |
| アプリとデータベースの間 | ElastiCache、DynamoDB Accelerator(DAX) | データベースの検索結果、セッション |

**Amazon CloudFront** は、世界中のエッジロケーションにコンテンツをキャッシュする CDN(コンテンツ配信ネットワーク)です。利用者は近くのエッジから受け取れるので速く、元のサーバー(オリジン)の負荷も下がります。詳しくは 3.4 で扱います。

### 11. 多層アーキテクチャ

Web 層、アプリケーション層、データ層に分ける構成です。各層を独立してスケールでき、層ごとにセキュリティグループで通信を制限できます。

```text
CloudFront --> ALB --> EC2 --> RDS
                        |
                        +----> ElastiCache

EC2: Auto Scaling で、複数の AZ に置く
RDS: Multi-AZ にする
ElastiCache: セッションとキャッシュを置く
```

### 12. ストレージの種類

| 種類 | サービス | 特徴 | 例 |
|---|---|---|---|
| **ブロック** | EBS、インスタンスストア | ディスクとして使う。1台の EC2 に接続(EBS は同じ AZ 内)。低遅延 | OS、データベース |
| **ファイル** | EFS、FSx | 複数のサーバーから同時にマウントして共有できる | 共有フォルダ、Web コンテンツの共有 |
| **オブジェクト** | S3 | HTTP でファイル単位に読み書き。容量無制限。高い耐久性 | 画像、バックアップ、データレイク |

### 13. リードレプリカ

データベースの **読み取り専用のコピー** です。読み取りのリクエストをレプリカに分散させ、本体(プライマリ)の負荷を下げます。

- RDS、Aurora で作れます。別リージョンにも作れます。
- レプリケーションは **非同期** なので、わずかな遅れがあります。
- 「読み取りが多くて DB が重い」ならリードレプリカ、「DB が壊れても止めたくない」なら Multi-AZ です(2.2 で扱います)。

### 14. 目的別のマネージドサービス

自分でサーバーを立てて作るより、目的に合ったマネージドサービスを使うほうが、運用の手間が少なくなります。

| やりたいこと | サービス |
|---|---|
| SFTP / FTPS / FTP で S3 や EFS にファイルを受け渡す | **AWS Transfer Family** |
| 秘密情報の保存とローテーション | Secrets Manager |
| メッセージの受け渡し | SQS、SNS |
| SaaS(Salesforce など)と AWS のデータ連携 | Amazon AppFlow |
| Web / モバイルアプリの開発とホスティング | AWS Amplify |
| 公開済みのサーバーレスアプリを組み込む | AWS Serverless Application Repository |
| Web アプリをコードを置くだけで動かす | AWS Elastic Beanstalk |
| モバイルアプリや Web アプリを、多数の実機の端末やブラウザでテストする | AWS Device Farm |

**AWS Elastic Beanstalk** は、アプリケーションのコードをアップロードすると、EC2、ELB、Auto Scaling などを自動で用意してくれるサービスです。インフラを細かく設計せずに Web アプリを動かしたいときに使います。

### 15. まとめ: よく出る判断

| 要件 | 選ぶもの |
|---|---|
| 処理の急増に耐え、受付と処理を分ける | SQS + Auto Scaling(キューの長さでスケール) |
| 順序どおり、重複なしで処理 | SQS FIFO キュー |
| 1つのイベントを複数システムに配る | SNS + 複数の SQS(ファンアウト) |
| SaaS のイベントで処理を起動、定期実行 | EventBridge |
| 既存アプリが AMQP / MQTT を使う | Amazon MQ |
| 15分以内の短い処理をイベントで実行 | Lambda |
| サーバー管理なしでコンテナ | ECS + Fargate |
| Kubernetes を使い続けたい | EKS |
| 複数の処理を順序・分岐・リトライ付きでつなぐ | Step Functions |
| URL のパスで振り分け | ALB |
| 固定 IP、TCP/UDP、超大量の接続 | NLB |
| ログイン状態をサーバーの外に置く | ElastiCache、DynamoDB |
| SFTP で取引先からファイルを受け取る | Transfer Family |

## 2.2 高可用性・耐障害性のあるアーキテクチャを設計する

出題範囲: 複数 AZ・複数リージョンの設計、単一障害点の排除、Route 53 のルーティングとフェイルオーバー、DR 戦略(バックアップと復元、パイロットライト、ウォームスタンバイ、マルチサイト)と RPO / RTO、RDS Multi-AZ、Aurora、DynamoDB グローバルテーブル、RDS Proxy、ストレージの耐久性とレプリケーション、バックアップ、イミュータブルインフラストラクチャと自動化、サービスクォータとスロットリング、X-Ray と CloudWatch による可視化、レガシーアプリの信頼性向上、AI サービス。

### 1. 高可用性と耐障害性

| 用語 | 意味 |
|---|---|
| **高可用性** | 障害が起きても、短時間で復旧し、サービスを使える時間が長いこと |
| **耐障害性** | 障害が起きても、サービスが止まらずに動き続けること |
| **単一障害点(SPOF)** | そこが壊れると全体が止まる部分。これをなくすのが設計の基本 |

単一障害点をなくす例:

| 単一障害点 | 対策 |
|---|---|
| 1台の EC2 | Auto Scaling で複数台を **複数 AZ** に置き、ELB で振り分ける |
| 1つの NAT ゲートウェイ | AZ ごとに NAT ゲートウェイを置く |
| 1台の DB | RDS Multi-AZ、Aurora のレプリカ |
| 1本の専用線 | Direct Connect を2本(別の拠点)にする、または VPN をバックアップにする |
| 1つのリージョン | 別リージョンにも環境を用意し、Route 53 で切り替える |

### 2. グローバルインフラストラクチャと Amazon Route 53

**Route 53** は AWS の DNS サービスです。ドメイン名を IP アドレスに変換し、**ヘルスチェック** の結果で応答を変えられます。

| ルーティングポリシー | 内容 | 使いどころ |
|---|---|---|
| シンプル | 1つのレコードを返す | 単一のサーバー |
| **加重** | 指定した割合で振り分ける | 新バージョンへ10%だけ流す(カナリアリリース) |
| **レイテンシー** | 利用者から最も遅延が小さいリージョンを返す | 世界中の利用者を最速のリージョンへ |
| **フェイルオーバー** | 正常ならプライマリ、異常ならセカンダリを返す | アクティブ/パッシブ構成の DR |
| **位置情報**(ジオロケーション) | 利用者の国・大陸で返す先を決める | 国ごとのコンテンツ、法令対応 |
| 地理的近接性 | 地理的な距離で返す先を決め、バイアスで範囲を調整できる | 拠点ごとの割り当てを細かく調整 |
| 複数値回答 | 正常なレコードを最大8つ返す | 簡易的な負荷分散 |
| IP ベース | 利用者の IP アドレスの範囲で返す先を決める | 特定の ISP の利用者を特定の拠点へ |

- **エイリアスレコード**: ELB、CloudFront、S3 の静的サイトなどの AWS リソースを指すレコードです。ドメインの頂点(`example.com` そのもの)にも設定でき、AWS リソースへの問い合わせは無料です。頂点には CNAME レコードを置けないので、エイリアスを使います。
- **プライベートホストゾーン**: VPC の中だけで使う名前を管理します。
- **Route 53 Resolver エンドポイント**: オンプレミスと VPC の間で DNS の名前解決をつなぎます(インバウンド: オンプレミス → AWS、アウトバウンド: AWS → オンプレミス)。

### 3. 災害対策(DR)戦略

**RPO**(どこまでのデータを失ってよいか)と **RTO**(どれくらいで復旧するか)の要件で、戦略を選びます。上ほど安く、下ほど速く復旧します。

| 戦略 | 内容 | RPO / RTO | コスト |
|---|---|---|---|
| **バックアップと復元** | 別リージョンにバックアップを置き、障害時に環境を作り直して復元する | 時間単位 | 最も安い |
| **パイロットライト** | データベースなど中核部分だけを別リージョンに複製しておく。アプリのサーバーは止めておき、障害時に起動する | 数十分 | 安い |
| **ウォームスタンバイ** | 縮小版の環境一式を別リージョンで常に動かしておく。障害時にスケールアップして本番を引き継ぐ | 数分 | 中 |
| **マルチサイト(アクティブ/アクティブ)** | 複数のリージョンで本番と同じ規模を常に動かし、両方で処理する | ほぼゼロ | 最も高い |

覚え方: パイロットライト(種火)は「火種だけ残しておく」、ウォームスタンバイは「小さく温めておく」です。

DR の設計で忘れやすい点:

- **サービスクォータ**: 待機側のリージョンでも、本番と同じ台数を起動できるよう、事前に **上限緩和を申請** しておきます。
- AMI やスナップショットは **リージョンごと** です。待機側のリージョンにコピーしておきます。
- 切り替え手順を自動化し、定期的に訓練します。

**AWS Elastic Disaster Recovery** を使うと、サーバーを継続的に別リージョンへ複製し、短い RPO / RTO で復旧できます(参考)。

### 4. データベースの高可用性

#### Amazon RDS

| 機能 | 目的 | 仕組み |
|---|---|---|
| **Multi-AZ 配置(スタンバイ1台)** | **可用性**。障害時の自動フェイルオーバー | 別の AZ にスタンバイを作り、**同期** レプリケーションする。スタンバイは読み取りに使えない。DNS 名は変わらずに自動で切り替わる |
| **Multi-AZ DB クラスター** | 可用性 + 読み取り | 読み取りもできるスタンバイ2台(対応エンジンのみ) |
| **リードレプリカ** | **読み取りの負荷分散** | **非同期** レプリケーション。別リージョンにも作れる。手動でプライマリに昇格できる(DR にも使える) |

- **自動バックアップ**: 保持期間(最大35日)内の任意の時点に戻せます(ポイントインタイムリカバリ)。
- **手動スナップショット**: 自分で削除するまで残ります。別リージョンにコピーできます。

#### Amazon Aurora

AWS が作った MySQL / PostgreSQL 互換のデータベースです。

- データは **3つの AZ に6つのコピー** として保存され、ストレージは自動で拡張されます。
- **Aurora レプリカ** を最大15台作れ、プライマリに障害があるとレプリカが自動で昇格します。
- **リーダーエンドポイント**: 複数のレプリカに読み取りを自動で振り分けます。
- **Aurora Global Database**: 別リージョンにほぼリアルタイム(通常1秒未満の遅れ)で複製します。リージョン障害時、待機側を短時間で昇格できます。RPO と RTO が小さい DR に使います。

#### Amazon DynamoDB

- データは自動で **複数の AZ** に複製されます。
- **グローバルテーブル**: 複数のリージョンに複製し、**どのリージョンでも読み書き** できます(マルチアクティブ)。世界中の利用者に低遅延で提供し、リージョン障害にも耐えます。
- **ポイントインタイムリカバリ(PITR)**: 過去35日の任意の時点に戻せます。

#### Amazon RDS Proxy

アプリとデータベースの間に入る、**データベース接続のプール**(使い回し)を管理するサービスです。

- Lambda のように **短時間に大量の接続を作る** アプリで、DB の接続数があふれるのを防ぎます。
- フェイルオーバーのとき、接続を保ったまま切り替えるため、**アプリから見た停止時間が短く** なります。
- Secrets Manager や IAM 認証と連携できます。
- **アプリのコードをほとんど変えずに**、接続先を Proxy にするだけで使えます。

### 5. ストレージの耐久性とレプリケーション

| サービス | 耐久性・可用性の仕組み |
|---|---|
| **S3** | 耐久性 99.999999999%(9が11個)。標準では3つ以上の AZ に保存。One Zone 系のクラスは1つの AZ だけ |
| S3 レプリケーション | 別リージョン(CRR)や同じリージョン(SRR)へ自動複製 |
| **EBS** | 同じ AZ の中で複製される。**AZ 障害には耐えない**。スナップショット(S3 に保存)で守る |
| **EFS** | 標準では複数の AZ に保存。別リージョンへのレプリケーションも可能 |
| インスタンスストア | EC2 を止めるとデータが消える。一時データ用 |

### 6. バックアップ

- **AWS Backup** でバックアップ計画を作り、複数のサービスのバックアップを一元管理します。別リージョン・別アカウントへのコピーで、リージョン障害やアカウントの乗っ取りにも備えます。
- 復元の手順を実際に試しておかないと、いざというときに復元できないことがあります。

### 7. 自動化とイミュータブルインフラストラクチャ

- **AWS CloudFormation**: インフラを **コード(テンプレート)** で定義し、同じ環境を何度でも正確に作れます(IaC: Infrastructure as Code)。DR 用のリージョンに同じ環境を素早く作るのにも使えます。
  - **スタックセット**: 複数のアカウント・リージョンに同じスタックを展開します。
  - **ドリフト検出**: テンプレートと実際の設定の違いを見つけます。
  - **変更セット**: 変更を実行する前に、何が変わるかを確認します。
- **イミュータブルインフラストラクチャ**: 動いているサーバーを直接修正せず、**新しいサーバーを作って入れ替える** 考え方です。設定のずれや「なぜか動く/動かない」状態を防ぎます。
  - **ブルー/グリーンデプロイ**: 新しい環境(グリーン)を用意し、確認後に通信を切り替えます。問題があれば元の環境(ブルー)に戻せます。
  - Auto Scaling の **インスタンスの更新** で、新しい AMI のインスタンスに順次入れ替えます。
- **AWS Systems Manager**: パッチ適用(Patch Manager)、コマンドの一括実行(Run Command)、自動化の手順(Automation)などで、サーバーの状態を一定に保ちます。

### 8. サービスクォータとスロットリング

- AWS のサービスには、アカウントごとの **上限(クォータ)** があります。例: リージョンごとの EC2 の vCPU 数、Lambda の同時実行数。
- **Service Quotas** で現在の上限を確認し、引き上げを申請します。CloudWatch のアラームで上限に近づいたことを知ることもできます。
- **スロットリング**: 上限を超えたリクエストが拒否されることです。アプリ側では、**エクスポネンシャルバックオフ**(待ち時間を少しずつ延ばしながら再試行する方法)で対処します。
- SQS を間に挟むと、急な増加をキューで吸収でき、後ろのシステムがスロットリングされにくくなります。

### 9. 可視化と監視

| サービス | 内容 |
|---|---|
| **Amazon CloudWatch** | メトリクス(CPU 使用率など)、ログ、アラーム、ダッシュボード。アラームで Auto Scaling や SNS 通知を起動する |
| CloudWatch エージェント | EC2 の **メモリ使用率やディスク使用率** を集める(標準のメトリクスには含まれない) |
| CloudWatch Synthetics | 定期的に Web サイトを外から確認する(カナリア) |
| **AWS X-Ray** | 1つのリクエストが複数のサービスをどう通ったかを **追跡(トレース)** し、遅い箇所やエラーの箇所を見つける。マイクロサービスで有効 |
| AWS Health Dashboard | AWS 側の障害や、自分のリソースに影響するメンテナンス情報 |
| Amazon Managed Grafana / Managed Service for Prometheus | オープンソースの監視ツールのマネージド版 |

高可用性のための **メトリクスは、ビジネスの要件から選びます**。例: 「注文の完了率」「API の応答時間」「エラー率」。CPU 使用率だけでは、利用者が困っているかどうかが分からないことがあります。

### 10. レガシーアプリケーションの信頼性を上げる

アプリのコードを変更できない場合でも、インフラ側で信頼性を上げられます。

| 課題 | 対策(コード変更なし) |
|---|---|
| 1台のサーバーで動いている | AMI を作って Auto Scaling(最小1台でも自動復旧)、ELB の後ろに置く |
| DB の接続が多すぎる、フェイルオーバーに弱い | RDS Proxy |
| DB サーバーが壊れたら止まる | RDS Multi-AZ に移行 |
| サーバーのローカルディスクにファイルを保存している | EFS をマウントして共有する |
| 固定 IP でしか接続を受けられない取引先がいる | NLB(固定 IP)、Elastic IP |
| EC2 自体の障害 | CloudWatch アラームの **EC2 自動復旧** アクション |

### 11. オンプレミスからの移行

| サービス | 内容 |
|---|---|
| **AWS Application Discovery Service** | 移行の計画のために、オンプレミスのサーバーの構成、使用率、サーバー同士の依存関係を調べる |
| **AWS Application Migration Service** | オンプレミスのサーバーを AWS に継続的に複製し、短い停止時間で EC2 に切り替える(リフトアンドシフト)。アプリの変更は不要 |
| AWS DMS | データベースの移行(3.3 参照) |
| AWS DataSync、Snow ファミリー | ファイルやデータの移行(3.5 参照) |

### 12. 目的別の AI サービス

機械学習の専門知識がなくても、API を呼ぶだけで使える AI サービスがあります。自分でモデルを作るより、可用性やスケールを AWS に任せられます。

| サービス | できること |
|---|---|
| **Amazon Comprehend** | 文章の感情分析、キーワードや固有名詞の抽出、個人情報の検出(自然言語処理) |
| **Amazon Polly** | 文章を音声に変換(読み上げ) |
| **Amazon Transcribe** | 音声を文字に変換(文字起こし) |
| **Amazon Translate** | 文章の翻訳 |
| **Amazon Lex** | チャットボットや音声ボットの作成 |
| **Amazon Rekognition** | 画像・動画から物体、顔、文字、不適切な内容を検出 |
| **Amazon Textract** | 書類のスキャン画像から文字、表、フォームの項目を抽出 |
| **Amazon SageMaker AI** | 独自の機械学習モデルを作成・学習・デプロイする |

### 13. まとめ: よく出る判断

| 要件 | 選ぶもの |
|---|---|
| AZ 障害でも Web サービスを止めない | 複数 AZ の Auto Scaling + ELB |
| DB の自動フェイルオーバー | RDS Multi-AZ |
| DB の読み取りが多い | リードレプリカ、ElastiCache |
| リージョン障害でも DB を素早く復旧 | Aurora Global Database、DynamoDB グローバルテーブル |
| 世界中で読み書きを低遅延に | DynamoDB グローバルテーブル |
| 正常ならメイン、異常なら待機側へ DNS で切り替え | Route 53 フェイルオーバールーティング |
| 最も安い DR | バックアップと復元 |
| DB だけ複製し、他は障害時に起動 | パイロットライト |
| 縮小版を常に動かし数分で切り替え | ウォームスタンバイ |
| Lambda から RDS への接続があふれる | RDS Proxy |
| リクエストが複数サービスのどこで遅いか調べる | X-Ray |
| 同じ環境を別リージョンにすぐ作る | CloudFormation |
| 音声を文字にする / 文字を音声にする | Transcribe / Polly |
