# Terraform テキスト 1.0 Infrastructure as Code(IaC)と Terraform

対象: Terraform Associate(004)

この分野では、IaC という考え方そのものと、Terraform がその中でどんな位置にあるかが問われます。コマンドの細かい使い方よりも、「なぜコードでインフラを管理するのか」を説明できることが目標です。

## 1.1 IaC とは何か

出題範囲: IaC の定義、手作業での管理との違い、宣言的と手続き的、Terraform の位置づけ。

### 1. IaC の定義

**Infrastructure as Code(IaC)** は、サーバー、ネットワーク、データベースなどのインフラを、画面での手作業ではなく、**コード(設定ファイル)で定義して作る**方法です。コードはテキストファイルなので、アプリケーションのコードと同じように Git で管理し、レビューし、何度でも同じように実行できます。

| 手作業(画面やコマンドを1つずつ実行) | IaC |
|---|---|
| 手順書を見ながら作業する | コードを実行すると、書いたとおりの環境ができる |
| 人によって結果が少しずつ違う | 何度実行しても同じ結果になる |
| 誰がいつ何を変えたか分かりにくい | Git の履歴に残る |
| 同じ環境をもう1つ作るのに時間がかかる | 同じコードを別の環境に使える |

### 2. 宣言的と手続き的

IaC のツールには、書き方の考え方が 2 つあります。

| 方式 | 書くもの | 例 |
|---|---|---|
| **宣言的(declarative)** | 「最終的にこうなっていてほしい」という**あるべき状態** | Terraform、AWS CloudFormation |
| 手続き的(imperative / procedural) | 「この順番でこれを実行する」という**手順** | シェルスクリプト、多くの CLI 操作 |

Terraform は**宣言的**です。たとえば「EC2 を 3 台」と書いておけば、今 1 台なら 2 台を追加し、今 5 台なら 2 台を減らします。今の状態からの差分を計算して、何をすればよいかは Terraform が決めます。

```hcl
resource "aws_instance" "web" {
  count         = 3
  ami           = "ami-0abcdef1234567890"
  instance_type = "t3.micro"
}
```

> `ami-0abcdef1234567890` は説明用の架空の ID です。実際の AMI の ID はリージョンと時期で変わるので、そのままでは動きません。実際に使うときは、data ブロックの `aws_ami` で最新の ID を探します(4.1 の「2. data ブロック」)。

### 3. Terraform とは

- HashiCorp が開発した IaC のツールです。設定は **HCL(HashiCorp Configuration Language)** という言語で `.tf` ファイルに書きます(JSON でも書けます)。
- AWS、Azure、Google Cloud などのクラウド、Kubernetes、GitHub、DNS など、API があるものなら**プロバイダー**を通して何でも管理できます。
- 実行するのは `terraform` という 1 つの CLI(コマンド)です。Terraform 本体は無料で使えます(Community Edition)。チームで使うための有料の機能は HCP Terraform(分野 8)で提供されます。

### 4. 構成管理ツールとの違い

| 種類 | 主な役割 | 例 |
|---|---|---|
| プロビジョニング(インフラを作る) | サーバー、ネットワーク、データベースなどを作る | Terraform、CloudFormation |
| 構成管理(サーバーの中を設定する) | OS のパッケージ、設定ファイル、サービスを整える | Ansible、Chef、Puppet |

Terraform はインフラそのものを作るのが得意です。サーバーの中のソフトウェアの設定は、構成管理のツールや、あらかじめ作ったマシンイメージ(Packer など)と組み合わせるのが一般的です。

### 5. まとめ: よく出る判断

| 問われ方 | 答え |
|---|---|
| Terraform は宣言的か手続き的か | 宣言的。あるべき状態を書く |
| IaC にするとまず何がよくなるか | 同じ環境を何度でも同じように作れる。変更を Git で管理できる |
| Terraform の設定の言語 | HCL(JSON でも書ける) |

## 1.2 IaC の利点

出題範囲: 再現性、バージョン管理、レビュー、自動化、ドキュメントとしてのコード、変更の事前確認。

### 1. 主な利点

| 利点 | 内容 |
|---|---|
| **再現性と一貫性** | 同じコードから、開発・検証・本番の環境を同じ構成で作れます。手作業による設定の漏れや違いがなくなります |
| **バージョン管理** | コードを Git で管理すると、誰がいつ何を変えたかが履歴に残り、問題があれば前の版に戻せます |
| **レビューと共同作業** | 変更をプルリクエストにして、他の人に確認してもらってから適用できます |
| **変更の事前確認** | Terraform は `terraform plan` で「何が作られ、何が変わり、何が消えるか」を実行の前に表示します |
| **自動化** | CI/CD のパイプラインから実行でき、作業の時間と人による誤りを減らせます |
| **ドキュメントになる** | コードを読めば、今のインフラがどんな構成かが分かります |
| **再利用** | よく使う構成をモジュールにまとめ、何度も使えます(分野 5) |

### 2. 冪等性(べきとうせい)

同じ操作を何度実行しても、結果が同じになる性質を**冪等性**と呼びます。Terraform では、設定と実際のインフラが一致していれば、`terraform apply` を何度実行しても何も変更されません(「No changes」と表示されます)。

### 3. イミュータブルなインフラ

一度作ったサーバーに後から手を加えるのではなく、**変更が必要なときは新しいものを作って入れ替える**考え方を、イミュータブル(変更不可能な)インフラと呼びます。Terraform では、作った後に変えられない引数(たとえば EC2 の AMI)を変えると、リソースを作り直します。これにより、手作業での変更が積み重なって環境ごとに状態がずれる「構成のずれ」を防げます。

### 4. 注意点

IaC にしても、Terraform の外(管理画面など)で手作業の変更をすると、コードと実際のインフラがずれます(**ドリフト**。分野 6)。IaC の効果を得るには、変更はコードを通して行うという運用のルールが必要です。

## 1.3 マルチクラウド、ハイブリッドクラウド、サービスに依存しないワークフロー

出題範囲: プロバイダーによる抽象化、1つのワークフローで複数のクラウドを扱う、ハイブリッドクラウド、クラウド以外のサービス。

### 1. 1つのワークフローで何でも管理する

Terraform は、管理する対象ごとに**プロバイダー**というプラグインを使います。どのプロバイダーを使っても、書き方(HCL)とワークフロー(`init` → `plan` → `apply`)は同じです。

| 対象 | プロバイダーの例 |
|---|---|
| パブリッククラウド | `hashicorp/aws`、`hashicorp/azurerm`、`hashicorp/google` |
| オンプレミス・仮想化 | `vmware/vsphere`、`hashicorp/vsphere` |
| コンテナ | `hashicorp/kubernetes`、`hashicorp/helm`、`kreuzwerker/docker` |
| SaaS・その他 | `integrations/github`、`DataDog/datadog`、`cloudflare/cloudflare` |

### 2. マルチクラウド

複数のクラウドを組み合わせて使うことを**マルチクラウド**と呼びます。Terraform では、1 つの設定の中に AWS と Azure のリソースを一緒に書けます。それぞれのクラウド専用のツール(CloudFormation、Azure Resource Manager など)を覚え分ける必要がなく、同じ手順で扱えます。

- 障害への耐性: 1つのクラウドの障害の影響を小さくできます。
- 依存の分散: 特定のクラウドだけに頼らずに済みます。

注意: Terraform を使っても、**AWS のリソースの書き方がそのまま Azure で使えるわけではありません**。リソースの種類と引数はプロバイダーごとに違います。共通なのは言語とワークフローです。

### 3. ハイブリッドクラウド

オンプレミスのデータセンターとパブリッククラウドを組み合わせることを**ハイブリッドクラウド**と呼びます。Terraform は vSphere などのオンプレミス向けのプロバイダーとクラウドのプロバイダーを同じ設定で使えるので、両方の環境を同じ方法で管理できます。

### 4. サービスに依存しない(service-agnostic)ワークフロー

インフラだけでなく、DNS のレコード、監視の設定、GitHub のリポジトリやチームなど、**API で操作できるもの**なら Terraform で管理できます。インフラとその周りの設定を 1 つのワークフローでまとめて扱えるのが Terraform の強みです。

### 5. まとめ: よく出る判断

| 問われ方 | 答え |
|---|---|
| Terraform がマルチクラウドを扱える仕組み | クラウドごとのプロバイダー。言語とワークフローは共通 |
| AWS 用の設定を Azure にそのまま使えるか | 使えない。リソースの種類と引数はプロバイダーごとに違う |
| クラウド以外を管理できるか | できる。API があれば、プロバイダーを通して管理できる |
