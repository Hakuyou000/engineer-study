# AWS DOP 3.0 耐障害性の高いクラウドソリューション(15%)

対象: DOP-C02

「止まりにくい構成(3.1)」「負荷に合わせて伸び縮みする構成(3.2)」「止まったときに目標時間内で戻す仕組み(3.3)」の 3 つに分かれます。SAA で学んだ Multi-AZ や Auto Scaling を前提に、複数リージョン、自動化、復旧の手順まで踏み込みます。

## 3.1 可用性の高いソリューションを実装する

出題範囲: Multi-AZ と複数リージョンの構成、SLA、ステートフルなサービスのレプリケーションとフェイルオーバー、単一障害点の発見と解消、ロードバランサーのクロス AZ 構成、Route 53・CloudFront・S3・DynamoDB・RDS のリージョン間の機能。

### 1. 要件を技術に直す

ビジネスの要件は「止まってよい時間」と「失ってよいデータ」で表します。

| 用語 | 意味 | 例 |
|---|---|---|
| RTO(Recovery Time Objective) | 障害から復旧するまでに許される時間 | 「1 時間以内に再開」 |
| RPO(Recovery Point Objective) | 失ってよいデータの時間幅 | 「直近 5 分までのデータは失ってよい」 |
| SLA | AWS がサービスごとに示す稼働率の約束(下回ると利用料の一部を返金) | 数値はサービスごとに異なるので、AWS の SLA のページで確認する |

構成の目安です。

- 1 つの AZ の障害に耐える: Multi-AZ にします。
- リージョン全体の障害に耐える: 複数リージョンにします。費用と複雑さが増えます。
- 求める RTO と RPO が短いほど、費用は上がります。

### 2. 単一障害点(SPOF)を探す

単一障害点は、そこが壊れると全体が止まる部分です。次を確認します。

- 1 台だけの EC2 インスタンス、1 つの AZ にだけあるサブネット
- 単一 AZ の RDS、1 つの NAT ゲートウェイ(AZ ごとに置く)
- 1 つのリージョンだけにあるデータ(S3、DynamoDB、データベース)
- 手作業でしか切り替えられない DNS や設定

### 3. コンピュートの高可用性

- **Elastic Load Balancing(ELB。トラフィックを複数のターゲットに振り分けるサービス)** は、ターゲットのヘルスチェックに失敗したものを振り分け先から外します。
- **クロスゾーン負荷分散**: 各ロードバランサーのノードが、すべての AZ のターゲットに振り分ける機能です。AZ ごとのターゲット数が違っても、偏りません。

| ロードバランサー | クロスゾーン負荷分散の既定 |
|---|---|
| Application Load Balancer(ALB) | 常に有効。ロードバランサーのレベルでは無効にできない(ターゲットグループのレベルでは無効にできる) |
| Network Load Balancer(NLB) | 無効(有効にできる。有効にすると AZ をまたぐ通信料がかかる) |

- **Amazon EC2 Auto Scaling グループ** を複数の AZ のサブネットにまたがらせます。1 つの AZ が使えなくなると、残りの AZ でインスタンスを起動して台数を保ちます。
- ヘルスチェックの種類を ELB にすると、アプリケーションの応答がないインスタンスも置き換えます(既定の EC2 ヘルスチェックは、インスタンスの状態だけを見ます)。

### 4. データ層の高可用性

| サービス | 同じリージョン内の可用性 | 複数リージョン |
|---|---|---|
| Amazon RDS | Multi-AZ 配置。スタンバイが同期レプリケーションで待機し、障害時に自動で切り替わる | クロスリージョンのリードレプリカ。非同期。昇格すると単独のデータベースになる |
| Amazon Aurora | データは 3 つの AZ に 6 つのコピーで保存される。リーダーが 1 つ以上あると、障害時に昇格する | **Aurora グローバルデータベース**。専用のストレージレベルのレプリケーションで、通常 1 秒未満の遅延 |
| Amazon DynamoDB | 自動で複数の AZ に保存される | **グローバルテーブル**。複数リージョンのどこにでも書き込める(マルチアクティブ)。同じ項目を同時に更新すると、最後の書き込みが勝つ |
| Amazon S3 | 複数の AZ に保存される(S3 One Zone-IA を除く) | **クロスリージョンレプリケーション(CRR)**。バージョニングが必要。**S3 Replication Time Control(RTC)** で、オブジェクトの 99.9% を 15 分以内に複製する(SLA つき) |

RDS の Multi-AZ には 2 種類あります。

| 種類 | スタンバイ | 特徴 |
|---|---|---|
| Multi-AZ DB インスタンス | 1 つ。読み取りに使えない | 切り替えは通常 60〜120 秒。大きなトランザクションがあると長くなる |
| Multi-AZ DB クラスター | 2 つ。読み取りに使える | 切り替えが速い。読み取りの負荷分散もできる |

**Amazon RDS Proxy** は、データベースへの接続をまとめて保つサービスです。フェイルオーバー中も、アプリケーションからの接続を保てるため、切り替え時間を短くできます。

### 5. 複数リージョンへの切り替え

DNS で切り替える方法と、エッジで切り替える方法があります。

| 方法 | 内容 |
|---|---|
| Amazon Route 53 のフェイルオーバールーティング | プライマリのヘルスチェックが失敗すると、セカンダリのレコードを返す |
| Route 53 のレイテンシールーティング、加重ルーティング | 利用者に近いリージョンへ、または比率を決めて振り分ける。ヘルスチェックと組み合わせると、異常なリージョンを外せる |
| Amazon CloudFront の **オリジングループ** | プライマリのオリジンが 5xx などを返したら、セカンダリのオリジンに自動で切り替える |
| **S3 マルチリージョンアクセスポイント** | 1 つのグローバルな名前で、複数のリージョンのバケットにアクセスする。近いバケットへ自動でルーティングする。リージョンの障害時は、フェイルオーバーコントロールで、リクエストを処理するリージョンを切り替える |
| AWS Global Accelerator | 固定の Anycast IP を使い、正常なエンドポイントへルーティングする。DNS キャッシュの影響を受けない |

DNS の切り替えは、TTL の長さの分だけ遅れます。早く切り替えたいときは TTL を短くします。

### まとめ: よく出る判断

| 要件 | 選ぶもの |
|---|---|
| AZ の障害に自動で耐える RDS | Multi-AZ 配置 |
| 別リージョンの読み取り専用のコピー | クロスリージョンのリードレプリカ |
| リージョン間で遅延が 1 秒未満のレプリケーション | Aurora グローバルデータベース |
| 複数リージョンのどこにでも書き込める | DynamoDB グローバルテーブル |
| S3 のオブジェクトを 15 分以内に別リージョンへ複製 | CRR + S3 Replication Time Control |
| プライマリのオリジンが異常なら別のオリジンへ | CloudFront のオリジングループ |
| ヘルスチェックの結果で DNS の回答を切り替える | Route 53 のフェイルオーバールーティング |
| DNS キャッシュの影響なしで切り替える | AWS Global Accelerator |
| フェイルオーバー中も接続を保つ | RDS Proxy |

## 3.2 スケーラブルなソリューションを実装する

出題範囲: スケーリングの指標、疎結合と分散アーキテクチャ、サーバーレス、コンテナ基盤(ECS、EKS)、Auto Scaling、ロードバランシング、キャッシュ、複数リージョンでのスケール。

### 1. スケーリングの方式

| 方式 | 内容 | 向く場面 |
|---|---|---|
| ターゲット追跡スケーリング | 指標を目標値に保つように、台数を自動で増減する(例: CPU 使用率 50%) | まず選ぶ方式 |
| ステップスケーリング | 指標のしきい値の超え方に応じて、増やす台数を変える | 負荷の変化が大きいとき |
| スケジュールスケーリング | 決まった時刻に台数を変える | 毎日の決まった時間に負荷が増える |
| 予測スケーリング | 過去の負荷から予測して、先に台数を増やす | 周期的な負荷 |

ほかに、**ウォームプール**(あらかじめ初期化して待機させたインスタンスを用意し、起動を早める)と、**ライフサイクルフック**(起動や終了の途中で処理を差し込む)があります。

### 2. 適切な指標を選ぶ

スケーリングの指標は、台数を増やすと**値が下がる**ものにします。

| 処理の形 | 指標 |
|---|---|
| Web アプリ | ALB の `RequestCountPerTarget`、CPU 使用率 |
| SQS のキューから取り出すワーカー | 「キューの長さ ÷ インスタンス数」(1 台あたりの滞留数)のカスタム指標 |
| メモリが律速のアプリ | CloudWatch エージェントで集めたメモリ使用率(EC2 の標準指標にはない) |

SQS のキューの長さ(`ApproximateNumberOfMessagesVisible`)だけを指標にすると、台数を増やしても値が下がるとは限りません。1 台あたりの滞留数にすると、台数に応じて下がります。

### 3. 疎結合にする

同期の呼び出しで直接つなぐと、片方の障害や遅延がもう片方に伝わります。間にキューやイベントを置くと、つなぎ目で負荷を吸収できます。

| サービス | 役割 |
|---|---|
| Amazon SQS | メッセージを溜めるキュー。処理側が自分のペースで取り出す |
| Amazon SNS | 1 つのメッセージを複数の宛先へ配る(ファンアウト) |
| Amazon EventBridge | イベントをルールで振り分ける |
| AWS Step Functions | 複数の処理の順序とエラー処理を管理する |

### 4. サーバーレスとコンテナ

- **AWS Lambda(コードを実行するサービス)**: リクエストに応じて自動で同時実行数が増えます。
  - **予約された同時実行**: その関数が使える同時実行数の上限と確保量を決めます。ほかの関数が枠を使い切るのを防げます。
  - **プロビジョニング済み同時実行**: 実行環境をあらかじめ用意し、コールドスタートを減らします。
- **Amazon API Gateway(API を公開するサービス)**: スロットリング(秒間リクエスト数の制限)とキャッシュで、バックエンドを守れます。
- **Amazon ECS(コンテナを動かすサービス)**
  - サービスのオートスケーリング: タスク数を増減します。
  - **キャパシティプロバイダー**: タスクを置く先(EC2 の Auto Scaling グループか Fargate)を決めます。EC2 の場合は、マネージドスケーリングで、タスクの数に合わせてインスタンスの数も増減します。
- **AWS Fargate**: サーバーを管理せずにコンテナを動かします。
- **Amazon EKS(Kubernetes を動かすサービス)**
  - Horizontal Pod Autoscaler(HPA): Pod の数を増減します。
  - Cluster Autoscaler や Karpenter: ノードの数を増減します。

### 5. キャッシュ

| 場所 | サービス | 内容 |
|---|---|---|
| エッジ | Amazon CloudFront | 静的なコンテンツを利用者の近くで返す。オリジンの負荷を減らす |
| アプリケーションの前 | API Gateway のキャッシュ | API の応答を保持する |
| データベースの前 | Amazon ElastiCache(Redis OSS、Memcached) | 頻繁に読むデータをメモリに置く |
| DynamoDB の前 | Amazon DynamoDB Accelerator(DAX) | 読み取りをマイクロ秒で返す、DynamoDB 専用のキャッシュ。アプリのコードの変更は、DAX クライアントへの差し替えだけ |

### 6. 複数リージョンでのスケール

世界中の利用者に使わせるには、リージョンごとに同じ構成を作り、Route 53 のレイテンシールーティングで近いリージョンへ向けます。データはグローバルテーブルや Aurora グローバルデータベースで共有します。構成の複製には CloudFormation の StackSets を使います。

### まとめ: よく出る判断

| 要件 | 選ぶもの |
|---|---|
| 指標を目標値に保つように自動で増減 | ターゲット追跡スケーリング |
| 毎朝 9 時の急な負荷に間に合わせる | スケジュールスケーリング、またはウォームプール |
| SQS のワーカーを滞留数で増減 | 1 台あたりの滞留数のカスタム指標 + ターゲット追跡 |
| Lambda のコールドスタートを減らす | プロビジョニング済み同時実行 |
| ある Lambda 関数が他の関数の枠を奪わないようにする | 予約された同時実行 |
| ECS の EC2 のインスタンス数をタスクに合わせる | キャパシティプロバイダーのマネージドスケーリング |
| DynamoDB の読み取りを最小の変更で高速化 | DAX |
| サーバー管理なしでコンテナを動かす | ECS または EKS + Fargate |

## 3.3 RTO と RPO を満たす復旧の自動化を実装する

出題範囲: 災害対策(DR)の考え方、バックアップと復旧の戦略(バックアップとリストア、パイロットライト、ウォームスタンバイ、マルチサイト)、AWS Backup、フェイルオーバーのテスト、ロードバランサーによるバックエンド障害からの復旧、Systems Manager による手順の自動化。

### 1. DR の 4 つの戦略

左ほど安く、復旧が遅いです。右ほど高く、復旧が速いです。

| 戦略 | DR リージョンの状態 | RTO・RPO の目安 |
|---|---|---|
| バックアップとリストア | バックアップだけ置く。障害時にリソースを作って復元する | 時間単位 |
| パイロットライト | データは常に複製する。アプリのサーバーは止めておく(または最小) | 数十分〜 |
| ウォームスタンバイ | 縮小した完全な構成を常に動かす。障害時に拡大する | 分単位 |
| マルチサイト(アクティブ/アクティブ) | 全リージョンが本番として動く | ほぼゼロ |

どの戦略でも、切り替えの手順は自動化し、定期的に訓練します。手作業の手順書は、障害時に失敗しやすいためです。

### 2. AWS Backup

**AWS Backup(バックアップを一元管理するサービス)** は、EC2、EBS、RDS、Aurora、DynamoDB、EFS、S3 などのバックアップを、1 つのポリシーで管理します。

| 機能 | 内容 |
|---|---|
| バックアッププラン | 頻度、保持期間、保存先を決める |
| リソースの割り当て | タグでリソースを選ぶ(例: `backup=daily` のタグのついたものすべて) |
| クロスリージョンコピー | バックアップを別のリージョンへ自動でコピーする |
| クロスアカウントコピー | バックアップを別のアカウントのボールトへコピーする。同じ AWS Organizations の組織のアカウントで、管理アカウントが機能を有効にしておく。アカウントの侵害や誤削除に備える |
| Backup Vault Lock | 保持期間の前の削除や変更をできなくする。ガバナンスモード(権限のある人は外せる)と、コンプライアンスモード(猶予期間の後は誰も外せない)がある |
| 継続的バックアップ | RDS や S3 などで、ある時点への復元(PITR)ができる |
| AWS Organizations との連携 | 組織全体のバックアップポリシーを一括で適用する |

そのほかの復旧の手段です。

- **Amazon RDS のスナップショットのコピー**、Aurora のクラスタースナップショットのクロスリージョンコピー
- **AMI のコピー**: AMI を別のリージョンへコピーしておくと、そこでインスタンスを起動できます。
- **AWS Elastic Disaster Recovery(DRS)**: オンプレミスや EC2 のサーバーを、低コストのステージング領域へ継続的にレプリケーションし、障害時に数分で起動します。

### 3. フェイルオーバーのテスト

- **Amazon RDS**: 「フェイルオーバーを伴って再起動」で、Multi-AZ の切り替えを試せます。
- **Amazon Aurora**: クラスターのフェイルオーバーを手動で起動できます。グローバルデータベースは、計画的な切り替え(スイッチオーバー)で、リージョンを切り替えて訓練できます。
- **Route 53**: ヘルスチェックを意図的に失敗させて、DNS の回答が変わるか確かめます。
- **AWS Fault Injection Service(FIS)**: インスタンスの停止やネットワークの遅延などの障害を、制御された形で注入するサービスです。復旧の仕組みが動くかを確かめます。

### 4. 手順の自動化

**AWS Systems Manager Automation** は、復旧の手順を「ランブック」として定義し、実行するサービスです。承認の手順、条件分岐、エラー時の処理を含められます。EventBridge、CloudWatch アラーム、AWS Config のルールから起動できます。

DR の例です。

1. CloudWatch アラームか、人の判断で起動する。
2. Automation が、DR リージョンのデータベースを昇格する。
3. Auto Scaling グループの希望台数を増やす。
4. Route 53 のレコードを切り替える。

### 5. ロードバランサーでバックエンドの障害から回復する

- ターゲットグループのヘルスチェックで、異常なターゲットへのリクエストを止めます。
- Auto Scaling グループのヘルスチェックの種類を ELB にすると、異常なインスタンスが自動で置き換わります。
- ヘルスチェックの設定で、判定の速さが変わります。
  - 間隔(秒)が短く、異常と判定する連続失敗の回数が少ないほど、早く外れます。
  - ただし、厳しすぎると、一時的な遅れで外れてしまいます。
- **ALB の低速スタート**(スロースタートモード): 新しいターゲットへのリクエストを徐々に増やします。起動直後のターゲットに、負荷が集中するのを防げます。
- **登録解除の遅延**: 外すターゲットが、処理中のリクエストを終えるまで待ちます。

### まとめ: よく出る判断

| 要件 | 選ぶもの |
|---|---|
| 最も安い DR(復旧は数時間でよい) | バックアップとリストア |
| データは複製。サーバーは止めておき、障害時に起動する | パイロットライト |
| 縮小した構成を常に動かし、障害時に拡大する | ウォームスタンバイ |
| RTO がほぼゼロ | マルチサイト(アクティブ/アクティブ) |
| バックアップを別リージョンと別アカウントへ自動で置く | AWS Backup のクロスリージョン・クロスアカウントコピー |
| バックアップを保持期間中は誰にも削除させない | Backup Vault Lock |
| オンプレミスのサーバーを DR 用に継続レプリケーション | AWS Elastic Disaster Recovery |
| 障害に対する復旧の仕組みを、制御された状態で確かめる | AWS Fault Injection Service |
| 復旧の手順を、承認や分岐を含めて自動化 | Systems Manager Automation |
