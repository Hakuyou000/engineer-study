# FE テキスト 5.0 システムの開発・運用

システムやソフトウェアを、要件定義から運用、廃棄まで、どう作り、どう動かすかを学びます。基本情報技術者試験だけにある分野で、テスト、開発手法、アルゴリズムなど、仕組みの理解と計算まで問われます。

## 5.1 システムライフサイクルプロセス

### 1. 開発プロセスの概要

システムやソフトウェアは、作って終わりではありません。企画、要件定義、設計、実装、テスト、導入、運用、保守、廃棄までを、一生(ライフサイクル)として考えます。

| 用語 | 意味 |
|---|---|
| ライフサイクルプロセス | ライフサイクルで行う作業(プロセス)を整理したもの |
| システムライフサイクルプロセス | ハードウェア、ソフトウェア、人を含む、システム全体のプロセス |
| ソフトウェアライフサイクルプロセス(SLCP) | ソフトウェアに絞った、作業と成果物の共通の枠組み。発注者と開発者が同じ言葉で話せる |
| テクニカルプロセス | 要件定義、設計、実装、統合、検証、運用など、技術的な作業のまとまり |
| 対象システム(SoI) | 作る、または運用する、対象のシステム |
| イネーブリングシステム | 対象システムのライフサイクルを支えるシステム(開発環境、テスト環境、ビルドの仕組みなど) |

### 2. システム要件定義とソフトウェア要件定義

**システム要件の定義**では、システムとして実現することを決めます。

| 要件 | 内容 |
|---|---|
| 機能要件 | システムが何をするか |
| 性能要件 | 応答時間、処理件数など |
| データベース要件 | 保存するデータの種類や量、保管の期間 |
| テスト要件 | どんなテストを、どこまでするか |
| セキュリティ要件 | 認証、暗号化、アクセス制御など |
| 移行要件 | 旧システムからのデータ移行、切り替えの方法 |
| 運用要件 | 監視、バックアップ、問い合わせ対応など |
| 保守要件 | 稼働後の修正の体制、期間 |
| システム構成要件 | ハードウェアやネットワークの構成 |
| 設計及び実装の制約条件 | 使う技術や予算など、守らなければならない条件 |

このほか、UX(使いやすさ)を考慮した要件の定義、適格性確認要件(完成したシステムが要件を満たすと確かめる方法)の定義、開発環境の検討を行い、定義した要件を評価し、レビューします。

機能以外の品質に関する要件(性能、可用性、セキュリティ、運用のしやすさなど)を**非機能要件**といいます。

**ソフトウェア要件の定義**では、システム要件のうち、ソフトウェアで実現する部分を詳しくします。

- ソフトウェアの機能仕様、インタフェース仕様を決めます。
- サブシステムに分割します。
- 実装の制約条件、品質特性を決めます。
- 業務モデルとデータモデルを作ります。
- ソフトウェア要件を評価し、レビューします。

**トレーサビリティマトリクス**は、要件と、設計、実装、テストの対応を表にしたものです。要件の漏れや、要件を変えたときの影響の範囲を確かめられます。

### 3. 設計

#### システム設計

システム設計では、要件を、ハードウェア、ソフトウェア、データベースなどの構成に割り当てます。機能要件と非機能要件の両方を満たす構成にします。

| 処理方式 | 特徴 |
|---|---|
| 集中処理 | 1 台の大きなコンピューターに処理を集める |
| 分散処理 | 複数のコンピューターで処理を分担する |
| クライアントサーバシステム | 要求するクライアントと、処理するサーバに分ける |
| Web システム | ブラウザから、Web サーバ上のアプリケーションを使う |
| マイクロサービスアーキテクチャ | 小さなサービスを組み合わせて作る。サービスごとに独立して開発、変更、配備できる |
| サーバレスアーキテクチャ | サーバの管理をクラウド事業者に任せ、関数などの単位で実行する。使った分だけ課金される |

システム設計では、ハードウェア構成、ソフトウェア構成、データベース方式も決め、システム統合テストの設計も行います。

#### ソフトウェア設計

ソフトウェアの構造と、ソフトウェアの要素(ソフトウェアユニット)を設計します。ユニットは、テストできる最小の単位です。このとき、インタフェースの設計と、テストの設計(ユニットのテスト、ソフトウェア統合テストの設計と仕様)も行います。

**ソフトウェア要素の分割**では、ファイルの統合と分割、レコード処理、処理の周期を決めます。プログラムを分割する基準は、分かりやすさ、安全性、開発の生産性、運用性、処理能力、保守性、再利用性です。

#### ソフトウェア品質

品質は、モデルで整理します。

| モデル | 見るもの | 例 |
|---|---|---|
| 製品品質モデル(品質特性モデル) | ソフトウェア自体の品質 | 機能適合性、性能効率性、互換性、インタラクション能力(旧: 使用性)、信頼性、セキュリティ、保守性、柔軟性(旧: 移植性)、安全性 |
| 利用時品質モデル | 実際の利用者が目標を達成できるか | 有効性、効率性、満足性など |

製品品質の特性は、ISO/IEC 25010 の 2023 年版の分類です。2011 年版(JIS X 25010:2013)には安全性がなく、特性は 8 つです。

#### モジュール設計

モジュールを分ける技法です。

| 技法 | 分け方 |
|---|---|
| STS 分割 | 入力(Source)、変換(Transform)、出力(Sink)に分ける |
| トランザクション分割 | 処理するデータ(取引)の種類ごとに分ける |
| 共通機能分割 | 複数の箇所で使う共通の機能を取り出す |

モジュールの分け方の良さは、2 つの基準で見ます。

- **モジュール強度**: 1 つのモジュールの中の結びつき。強いほどよい。
- **モジュール結合度**: モジュール同士の結びつき。弱いほどよい。

強度は、強い順に、機能的、情報的、連絡的、手順的、時間的、論理的、暗合的です(文献によっては、逐次的、通信的、偶発的という名前や並びも使います)。結合度は、強い順に、内容、共通、外部、制御、スタンプ、データです。

#### ソフトウェアの部品化と再利用

| 用語 | 意味 |
|---|---|
| コンポーネントウェア | 部品(コンポーネント)を組み合わせて、ソフトウェアを作る方法 |
| クラスライブラリ | 再利用できるクラスを、まとめたもの |
| デザインパターン | よくある設計の問題への、定番の解決策 |
| COTS(Commercial Off-The-Shelf) | 市販の、既製のソフトウェアを、そのまま、または少し手を加えて使うこと |

#### レビュー

| 種類 | 内容 |
|---|---|
| コードレビュー | ソースコードを読んで、誤りや改善点を見つける |
| ピアレビュー | 同じ立場の仲間(同僚)が行う |
| デザインレビュー | 設計の内容を確認する |
| インスペクション | 議長などの役割と手順が決まった、公式なレビュー |
| ウォークスルー | 作成者が説明して、参加者が指摘する、軽いレビュー |

### 4. 実装・構築

#### ソフトウェアユニットの作成

**コーディング標準**は、読みやすく、保守しやすいコードにするための決まりです。字下げ(インデンテーション)、ネストの深さ、命名規則、使用禁止命令などを決めます。

コーディングを支援する手法には、コード補完、オートインデント、コードエディター、シンタックスハイライト(色分け)、ブレークポイント(実行を止める位置)があります。

構造化プログラミングは、順次、選択、繰返しの 3 つの構造で、プログラムを組み立てる考え方です。モジュール分割と、モジュールの仕様の決定も行います。

コードを確認する方法には、次のものがあります。

- コードレビュー(コードインスペクション、ウォークスルー)
- サイクロマティック複雑度: プログラムの分岐の数で、複雑さを数える指標。大きいほど、テストと保守が難しい。

**デバッグ**(誤りの発見と修正)の方法です。

| 方法 | 内容 |
|---|---|
| 静的解析 | プログラムを動かさずに、ソースコードを解析する |
| 動的テスト | プログラムを動かして、結果を確かめる |
| アサーション | 「ここでは、この条件が成り立つはず」という表明を、コードに書き、破れたら検出する |

ソフトウェアコードとテスト結果の評価基準には、追跡可能性(要件からたどれる)、外部一貫性(上位の文書と矛盾しない)、内部一貫性(それ自体に矛盾がない)、テスト網羅性(テストがどこまで確かめたか)があります。

#### ソフトウェアユニットのテスト

テストの前に、テストの範囲を決め、準備をし、チェックシートを作ります。

| 用語 | 意味 |
|---|---|
| テストケース | テストの入力と、期待する結果の組 |
| テストオラクル | 結果が正しいかどうかを判断する基準(期待される結果) |
| デバッガ | 誤りを調べるために、実行を止めたり、変数を見たりするツール |
| テストデータジェネレーター | テストデータを自動で作るツール |
| メトリクス計測 | 規模、複雑さなどを数値で測る |

テストの設計と管理には、バグ曲線(見つけたバグの数の推移)、エラー除去、バグ管理図を使い、バグの収束を確かめます。

**テストの技法**は、ホワイトボックステストとブラックボックステストに分かれます。

| 種類 | 見るもの | 技法 |
|---|---|---|
| ホワイトボックステスト | プログラムの内部の構造 | 命令網羅、条件網羅、判定条件網羅、複数条件網羅 |
| ブラックボックステスト | 入力と出力(仕様) | 同値分割法、限界値分析法、原因結果グラフ法 |

| 網羅基準 | 内容 |
|---|---|
| 命令網羅 | すべての命令を、1 回以上実行する |
| 判定条件網羅 | 各判定が、真と偽の両方になる |
| 条件網羅 | 判定の中の各条件が、真と偽の両方になる |
| 複数条件網羅 | 判定の中の条件の、真偽の組合せをすべて試す |

- **同値分割法**: 入力を、同じ扱いになるグループに分け、各グループから代表値を選ぶ。
- **限界値分析法**: グループの境界と、その両側の値を選ぶ。誤りは境界で起きやすい。
- **原因結果グラフ法**: 入力の条件(原因)と、結果の関係を図にして、テストケースを作る。
- **エラー埋込法**: わざとバグを埋めて、見つかった割合から、残りのバグの数を推定する。
- **実験計画法**: 少ない組合せで、効率よく要因の影響を調べる。

### 5. 統合・テスト

#### ソフトウェア統合とソフトウェア検証

ソフトウェア統合では、統合計画を作り、統合する順序を決めて、ユニットを組み合わせてテストします。変更のあとで、どの範囲を、どの時点で再テストするかの方針を、回帰戦略(シラバスでは再帰戦略(回帰戦略))といいます。

| 統合テスト | 内容 | 使うもの |
|---|---|---|
| トップダウンテスト | 上位のモジュールから順に統合する | スタブ(未完成の下位の代わり) |
| ボトムアップテスト | 下位のモジュールから順に統合する | ドライバ(未完成の上位の代わり) |

トップダウンテストとボトムアップテストで、足りない部分を何で補うかを表した図です。

```text
トップダウンテスト: 上位から統合する。未完成の下位の代わりに、スタブを置く
  [Module A]
    +-- [Module B]
    `-- [Stub]      未完成の下位モジュールの代わり

ボトムアップテスト: 下位から統合する。未完成の上位の代わりに、ドライバを置く
  [Driver]          未完成の上位モジュールの代わり
    +-- [Module B]
    `-- [Module C]
```

**ソフトウェア検証テスト**では、次のテストを行います。

| テスト | 内容 |
|---|---|
| 機能テスト | 機能が、仕様どおりに動くか |
| 非機能要件テスト | 性能、セキュリティなど、非機能要件を満たすか |
| 性能テスト | 処理の速さ、応答時間 |
| 負荷テスト | 大量のアクセスなど、負荷をかけたときの動作 |
| セキュリティテスト | 脆弱性がないか |
| 回帰テスト(リグレッションテスト) | 修正のあとで、既存の機能が壊れていないか |
| ファジング | 不正なデータやランダムなデータを大量に入力して、異常を見つける |

#### システム統合とシステム検証

システム統合では、計画を作り、ソフトウェアとハードウェアを組み合わせて、システム統合テストを行います。システム検証テストの種類は、機能テスト、非機能要件テスト、性能テスト、負荷テスト、セキュリティテスト、回帰テストのほか、**探索的テスト**(担当者が動かしながら考えて、設計と実行を同時に進める)があります。

### 6. 導入・受入れ支援

#### 導入

導入では、導入の要件、導入してよいかの判断基準、移行リハーサル(本番と同じ手順で試す)、導入の手順と体制を決めます。利用部門、システム運用部門、利用者への支援も計画します。

#### 受入れ支援

| 用語 | 意味 |
|---|---|
| 受入れ手順、受入れ基準 | 受け入れてよいかを判断する手順と基準 |
| 受入れテスト | 発注側が、要件を満たしているかを確かめて、受け入れるかを判断する |
| 教育訓練計画 | 利用者への教育の計画 |
| 利用者用文書類 | ウィザード、学習書(チュートリアル)、オンラインヘルプなど |

#### 妥当性確認テスト

妥当性確認テストは、完成したシステムが、利用者の本来の目的に合っているかを確かめるテストです。テストの目的、成功基準(期待される結果)、使う技法を決めます。不具合が見つかったら、根本原因を調べ、是正処置と欠陥の修正を行います。

### 7. 運用

システム運用では、日常の運用計画と、障害が起きたときの運用計画を立てます。システムの運用管理と、運用の資源(人的資源、技術的資源など)の管理も行います。

**バックアップ**の種類です。

| 種類 | 内容 | 復元に必要なもの |
|---|---|---|
| フルバックアップ | すべてのデータを保存する | フルバックアップだけ |
| 差分バックアップ | フルバックアップからの変更分を保存する | フルバックアップと、最新の差分 |
| 増分バックアップ | 直前のバックアップからの変更分を保存する | フルバックアップと、それ以降の増分すべて |

増分は、バックアップの量が少なくて済みますが、復元に手間がかかります。差分は、復元が簡単ですが、日がたつほど量が増えます。

### 8. 保守・廃棄

#### 保守

保守では、保守の手順、体制、保守テストを決めます。リバースエンジニアリングは、できあがったソフトウェアから、設計の情報を取り出す方法で、設計書がない古いシステムの保守で使われます。保守契約も結びます。

| 保守のタイプ | 内容 |
|---|---|
| 是正保守 | 見つかった不具合を直す |
| 予防保守 | 将来の不具合を、起きる前に防ぐ |
| 適応保守 | OS や法律など、環境の変化に合わせて直す |
| 完全化保守 | 機能の追加や性能の向上など、より良くする |

#### 廃棄

廃棄では、次のことを行います。

- 運用の停止(不活性化)と、除去。
- 廃棄の処分の方法の選択。
- データと知的財産を保持するか、破棄するかを決める。
- 記憶媒体から、ソフトウェアとデータを完全に消去する(専用ツールでの上書き、物理的な破壊など)。通常の削除や初期化では、データが残ることがある。
- 運用の担当者の撤退と、操作の知識の記録。

## 5.2 開発・運用の方法論

### 1. 開発の手法・方法論

#### 開発手法の種類と特徴

| 手法 | 特徴 |
|---|---|
| ウォーターフォールモデル | 要件定義から順に、前の工程が終わってから次へ進める。計画を立てやすいが、後戻りは大変 |
| プロトタイピングモデル | 試作品を作って、利用者に見せながら要求を確かめる |
| アジャイル | 短い期間で、動くソフトウェアを作って見せ、変化に対応しながら進める |
| DevOps | 開発(Dev)と運用(Ops)が協力して、素早く安全に届ける |
| マッシュアップ | 既存の複数のサービスやデータを組み合わせて、新しいサービスを作る |

マッシュアップには、画面を組み合わせるプレゼンテーションマッシュアップ、データを組み合わせるデータマッシュアップ、処理を組み合わせるロジックマッシュアップがあります。

#### アジャイル開発

**アジャイルソフトウェア開発宣言**は、4 つの価値を示しています。

- プロセスやツールよりも、個人との対話を
- 包括的なドキュメントよりも、動くソフトウェアを
- 契約交渉よりも、顧客との協調を
- 計画に従うことよりも、変化への対応を

右側にも価値はあるが、左側をより重視する、という意味です。宣言には、12 の原則があります。チームは、自己組織化して、仕事のやり方を自分たちで決めます。

| 用語 | 意味 |
|---|---|
| ペルソナ | 利用者を代表する、架空の人物像 |
| ユーザーストーリー | 「〜として、〜したい。なぜなら〜」の形で書く、利用者の要望 |
| モブプログラミング | チーム全員で、1 つの画面を見ながら、一緒にプログラムを書く |
| リファクタリング | 外から見た動作を変えずに、内部の構造を整理する |
| ふりかえり(レトロスペクティブ) | 進め方を振り返って、改善を決める |
| KPT | Keep(続けること)、Problem(問題)、Try(次に試すこと)に分けて、ふりかえる手法 |

**エクストリームプログラミング(XP)**のプラクティスです。

- テスト駆動開発(TDD): 先に失敗するテストを書き、通すコードを書き、整理する。
- ペアプログラミング: 2 人で 1 台を使って書く。
- リファクタリング
- ソースコードの共同所有: 誰でも、どのコードも直してよい。
- 継続的インテグレーション(CI): こまめに結合して、自動でテストする。
- YAGNI(You Aren't Gonna Need It): 今必要でないものは、作らない。

**スクラム**は、決まった期間(スプリント)で、少しずつ作る枠組みです。

| 役割 | 内容 |
|---|---|
| プロダクトオーナー | 作る製品の価値に責任を持ち、プロダクトバックログを管理する |
| 開発者 | 自己組織化して、インクリメントを作る |
| スクラムマスター | スクラムが正しく行われるよう、チームを支援する |

| イベントと成果物 | 内容 |
|---|---|
| スプリント | 1 か月以内の、決まった期間 |
| スプリントプランニング | スプリントで何を作るか決める |
| デイリースクラム | 毎日の短い打合せ |
| スプリントレビュー | 成果物(インクリメント)を関係者に見せて、フィードバックを受ける |
| スプリントレトロスペクティブ | チームの進め方を振り返る |
| プロダクトバックログ | 製品に必要なことの、順位つきの一覧 |
| スプリントバックログ | スプリントで取り組む作業の一覧 |
| インクリメント | スプリントで完成した、使える成果物 |

スクラムの 1 回のスプリントの流れを、成果物とイベントで表した図です。

```text
[プロダクトバックログ] 製品に必要なことの、順位つきの一覧
  |
  v
スプリント(1 か月以内の決まった期間)の中で、次を行う
  +-- スプリントプランニング: 何を作るか決め、取り組む作業の一覧(スプリントバックログ)を作る
  +-- デイリースクラム: 毎日、進み具合を確かめる
  +-- スプリントレビュー: 関係者に見せて、フィードバックを受ける
  `-- スプリントレトロスペクティブ: チームの進め方を振り返る
  |
  v
[インクリメント] スプリントで完成した、使える成果物
  |
  v
次のスプリントへ
```

#### DevOps

| 用語 | 内容 |
|---|---|
| SRE(サイト信頼性エンジニアリング) | 運用を、ソフトウェアの技術と自動化で行う。信頼性の目標(SLO)を決めて、変更の速さとのバランスをとる |

継続的インテグレーション(CI)から、継続的デリバリーと継続的デプロイへの流れを表した図です。

```text
  |
  v
[CI] こまめに結合し、自動でビルドとテストを行う
  |
  +-- 継続的デリバリー: いつでも本番へ出せる状態を保つ。反映は人が判断する
  `-- 継続的デプロイ: テストに通れば、本番への反映まで自動で行う
```

| 用語 | 意味 |
|---|---|

**ソフトウェア設計原則(SOLID)**は、次の 5 つの原則です。

- 単一責任の原則: クラスの責任は、1 つにする。
- オープン・クローズドの原則: 拡張に対して開き、修正に対して閉じる。
- リスコフの置換原則: サブクラスは、スーパークラスの代わりに使える。
- インタフェース分離の原則: 使わない機能への依存を、強制しない。
- 依存性逆転の原則: 具体的な実装ではなく、抽象に依存する。

**UML の図**です。

| 種類 | 図 |
|---|---|

| 振る舞いを表す | ユースケース図、アクティビティ図、ステートマシン図、シーケンス図、コミュニケーション図、相互作用概要図、タイミング図 |

シーケンス図は、メッセージの順番を、時間に沿って表します。コミュニケーション図は、オブジェクトの間のつながりを中心に表します。

### 6. フィジカルコンピューティング

#### 信号処理・制御の仕組み

- **A/D 変換**: アナログ信号を、標本化、量子化、符号化の順に、ディジタル信号へ変える。D/A 変換は、その逆。
- **制御の方式**です。

| 方式 | 内容 |
|---|---|
| オープンループ制御 | 結果を測らず、決めた指令どおりに動かす |
| クローズドループ制御(フィードバック制御) | 結果を測って、目標との差を小さくする |
| シーケンス制御 | 決めた順序で、段階的に動作を進める |

- リアルタイム OS: 決められた時間内に、処理を終えることを重視する OS。

#### ハードウェア設計

論理回路は、入力が 0 か 1 かで、出力が決まります。論理式、真理値表で表します。

| 回路 | 出力が 1 になるとき |
|---|---|
| AND | どちらも 1 |
| OR | どちらかが 1 |
| NAND | AND の反転。どちらも 1 のとき以外 |
| NOR | OR の反転。どちらも 0 のときだけ |
| XOR | 2 つが異なるとき |

フリップフロップは、1 ビットの値を記憶する回路です。正論理は、高い電圧を 1 とし、負論理は、低い電圧を 1 とします。

### 7. オペレーティングシステム

#### オペレーティングシステムの機能

- **カーネル**: OS の中心。**モノリシックカーネル**は、機能を 1 つにまとめる。**マイクロカーネル**は、最小限だけをカーネルに置く。
- ミドルウェア: OS とアプリケーションの間で、共通の機能を提供する。
- カーネルモード(スーパーバイザーモード、特権モード)と、非特権モード: 特権モードだけが、ハードウェアを直接操作できる。
- サービスプログラム: 補助のための、OS の付属のプログラム。
- 記憶管理、仮想記憶管理: 実メモリより大きな空間を、使えるようにする。
- 割込み: 処理の途中で、別の処理へ制御を移す仕組み。
- 多重プログラミング: 複数のプログラムを主記憶に置き、入出力を待つ間に、別のプログラムへ CPU を切り替えて、並行して実行する。CPU の空き時間が減る。
- ブートストラップ: 電源を入れて、OS を起動する処理。マルチブートは、複数の OS から選んで起動する。

#### ジョブ管理・タスク管理

| 用語 | 意味 |
|---|---|
| ジョブスケジューラー | ジョブの実行の順番と時間を管理する |
| マスタスケジューラー | オペレーターからの指示を受け付け、ジョブの実行を監視、制御する【要確認】 |
| バッチ処理 | データをまとめて、順に処理する |
| タスクの状態 | 実行可能状態、実行状態、待ち状態の間を移る |
| プロセス、スレッド | 実行の単位。スレッドは、プロセスの中の、より小さな単位 |
| プリエンプティブ方式 | OS が、強制的に CPU を切り替える |
| ノンプリエンプティブ方式 | タスクが、自分から CPU を手放すまで、切り替えない |
| タイムクウォンタム | 1 回に使える、CPU の時間 |
| SVC(SuperVisor Call)割込み | プログラムが、OS の機能を呼ぶときの割込み |
| ディスパッチ | 実行可能なタスクに、CPU を割り当てる |

#### 入出力管理・記憶管理

チャネルは、CPU に代わって入出力を制御する装置です。入出力割込みは、入出力の完了を CPU へ知らせます。スワップイン、スワップアウトは、プログラムを、主記憶と補助記憶の間で、出し入れします。

**仮想記憶管理**です。

| 用語 | 意味 |
|---|---|
| ページング方式 | 固定の大きさのページで、記憶を管理する |
| セグメント方式 | プログラムの意味のまとまり(セグメント)で管理する |
| セグメントページング方式 | セグメントを、さらにページに分ける |
| ページフォールト | 必要なページが主記憶になくて、補助記憶から読む |
| ページイン、ページアウト | 補助記憶から主記憶へ読む、主記憶から補助記憶へ追い出す |
| スラッシング | ページフォールトが多発して、処理が進まなくなる |

### 8. 施設管理技術

データセンターなどの設備です。電気設備には、UPS(無停電電源装置)と自家発電設備があります。空調設備では、エアフロー(空気の流れ)を管理し、冷たい空気を吸い込む面を向かい合わせるコールドアイルと、熱い空気を出す面を向かい合わせるホットアイルを作ります。通信設備には、MDF(主配線盤)、IDF(中間配線盤)などがあります。

## 5.3 アルゴリズム・プログラミング

### 1. 情報理論

#### 数値表現

**基数の変換**: 2 進数、10 進数、16 進数を、行き来できるようにします。16 進数の 1 桁は、2 進数の 4 桁です。16 進数の A から F は、10 から 15 です。例えば、16 進数の 2F は、2 × 16 + 15 = 47 です。

**補数表現**: 負の数を表す方法です。2 の補数は、すべてのビットを反転して、1 を足します。8 ビットで、-5 は、00000101 を反転(11111010)して 1 を足した、11111011 です。8 ビットの 2 の補数で表せる範囲は、-128 から 127 です。

**固定小数点数と浮動小数点数**: 固定小数点数は、小数点の位置を固定します。浮動小数点数は、仮数と指数で表し(仮数 × 2 の指数乗)、非常に大きな数や小さな数も表せます。

**シフト演算**です。

| 種類 | 動かし方 |
|---|---|
| 論理シフト | 空いたビットに、0 を入れる |
| 算術シフト | 符号ビットを保つ。左へ n ビットは 2 の n 乗倍、右へ n ビットは 2 の n 乗で割る |

**計算の誤差**です。

| 用語 | 意味 |
|---|---|
| 桁落ち | ほぼ等しい 2 つの数を引き算して、有効な桁数が減る |
| 情報落ち | 絶対値が大きく異なる 2 つの数の加減算で、小さい方が反映されない |
| 丸め(丸め誤差) | 桁が足りずに、値を丸める |
| 打切り(打切り誤差) | 計算を途中で打ち切る |
| オーバーフロー(あふれ) | 表現できる最大値を超える |
| アンダーフロー | 表現できる最小の絶対値より、小さくなる |

#### 集合論

| 用語 | 意味 |
|---|---|
| 和集合、積集合、補集合 | どちらか、両方、含まれない |
| 部分集合 | 集合の一部になっている集合 |
| ベン図 | 集合の関係を、図にしたもの |
| 命題、命題論理 | 真か偽かが決まる文と、その組合せの論理 |

**排他的論理和(XOR)**は、2 つが異なるときだけ 1 になります。**否定論理和(NOR)**は、OR の反転です。

**ド・モルガンの法則**は、NOT (A AND B) = (NOT A) OR (NOT B)、NOT (A OR B) = (NOT A) AND (NOT B) です。2 つの集合の和集合の要素数は、A の数 + B の数 - 両方に含まれる数です。カルノー図は、論理式を、表で簡単にする方法です。

#### 応用数学

| 用語 | 意味 |
|---|---|
| 線形代数、スカラ、ベクトル、テンソル、行列、逆行列 | 数を、配列や表の形で扱う数学。スカラは 1 つの数、ベクトルは数の並び、行列は表、テンソルはその拡張 |
| 等差数列、等比数列 | 差が一定、比が一定の数の並び |
| 対数 | ある数が、底の何乗かを表す。底が 2 なら、log₂1,024 = 10 |
| 数値解析、オイラー法、数値積分、ニュートン法 | 計算機で、近似的に値を求める方法 |
| 絶対誤差、相対誤差 | 絶対誤差は、測定値と真の値の差。相対誤差は、絶対誤差を真の値で割った割合 |
| グラフ理論 | 頂点と辺で表した、構造の理論 |
| 待ち行列理論 | 待ちの長さや時間を、計算する理論 |

**待ち行列理論**(M/M/1 の場合)では、利用率を ρ とすると、平均待ち時間は、ρ ÷ (1 - ρ) × 平均サービス時間です。利用率が 1 に近づくと、待ち時間が急に増えます。

#### 符号理論・計算量

- **文字コード**: シフト JIS コードは日本語用です。Unicode は世界の文字を扱う規格で、その符号化方式の 1 つが UTF-8 です。UTF-8 は、1 文字を 1〜4 バイトで表し、ASCII の文字は 1 バイトです。
- **逆ポーランド表記法**: 演算子を、被演算子のあとに書く。(3 + 4) × 5 は、3 4 + 5 × です。スタックで計算できます。
- 符号理論、形式言語、オートマトン: 情報の符号化、言語の規則、状態を移る仕組みを、数学で扱います。
- **計算量(オーダ記法)**: データの量 n が増えたとき、処理の量がどう増えるかを表します。小さい順に、O(1)、O(log n)、O(n)、O(n log n)、O(n²) です。時間計算量は、処理の時間(回数)で見ます。

### 2. データ構造

| 構造 | 特徴 |
|---|---|
| 配列(多次元配列) | 同じ型の要素を並べる。位置の番号(添字)で、直接アクセスできる |
| リスト(線形リスト) | 要素が、次の要素へのポインタを持つ。途中への挿入、削除が簡単 |
| 単方向リスト、双方向リスト | 次だけを指す、前と次の両方を指す |
| スタック | 最後に入れたものを、最初に取り出す(LIFO) |
| キュー | 最初に入れたものを、最初に取り出す(FIFO) |
| 木構造 | 親と子の階層構造 |
| 2 分木 | 子が最大 2 つの木 |
| 2 分探索木 | 左の部分木の値はすべて節点より小さく、右の部分木の値はすべて大きい。左、節点、右の順にたどると、昇順 |
| B 木 | 多数の子を持ち、葉が同じ深さ。データベースの索引に使う |
| B+ 木 | データを葉だけに持たせた B 木 |
| ハッシュ表 | キーに、ハッシュ関数を適用して、格納位置を決める。探索が速い |
| グラフ | 頂点と辺で、つながりを表す |

ハッシュ関数が、異なるキーに同じ値を出すことを、衝突といいます。衝突したら、同じ位置に鎖でつなぐ(チェイン法)、空いている別の位置を探す(オープンアドレス法)、で解決します。

### 3. アルゴリズム

#### アルゴリズムの種類

- **再帰**: 関数が、自分自身を呼び出す。終わりの条件が必要。例えば、n の合計は、f(n) = n + f(n - 1)、f(0) = 0。
- **分割統治**: 問題を小さく分けて解き、結果を組み合わせる。
- **文字列処理のアルゴリズム(文字列照合)**: テキストの中から、パターンと一致する位置を探す。
- 自然言語処理のアルゴリズム: 人の言葉を、コンピューターで処理する(単語に分ける、意味を調べるなど)。

#### 整列・併合・探索のアルゴリズム

| アルゴリズム | 方法 | 計算量 |
|---|---|---|
| 選択ソート | 最小値を選んで、先頭から並べる | O(n²) |
| バブルソート | 隣り合う要素を比べて、交換する。1 回で最大が右端へ | O(n²) |
| 挿入ソート | 整列済みの部分に、1 つずつ挿入する。整列済みに近いと速い | O(n²) |
| シェルソート | 離れた要素から挿入ソートを繰り返す | 挿入ソートより速い |
| マージソート | 半分に分けて整列し、併合する | O(n log n) |
| クイックソート | 基準値で、小さい値と大きい値に分ける | 平均 O(n log n)、最悪 O(n²) |
| ヒープソート | ヒープ(最大値を取り出しやすい木)を使う | O(n log n) |

併合のアルゴリズムは、整列済みの 2 つの列を、1 つの整列済みの列にまとめます。

| 探索 | 方法 | 計算量 |
|---|---|---|
| 線形探索法 | 先頭から順に調べる。整列不要 | O(n) |
| 2 分探索法 | 整列済みの配列で、範囲を半分にしていく | O(log n) |

2 分探索法は、1,000,000 件でも、およそ 20 回の比較で足ります。

#### グラフのアルゴリズム

| アルゴリズム | 内容 |
|---|---|
| 深さ優先探索 | 行けるところまで進んでから、戻る。スタック(再帰)を使う |
| 幅優先探索 | 始点に近い頂点から、順に調べる。キューを使う |
| 最短経路探索 | 2 つの頂点の間で、重みの合計が最小の経路を求める |
| ダイクストラ法 | 辺の重みが負でないときの、最短経路の方法 |
| ベルマンフォード法 | 負の重みの辺があっても、使える |

### 4. プログラミング

#### コーディング標準

- 字下げ(インデンテーション)、ネストの深さ(浅くする)、コメントの記述規則を決める。
- **命名規則**: キャメルケース(userName)、スネークケース(user_name)など。
- 使用禁止命令: goto 文、グローバル変数、マクロの使い方の制限、直接メモリアクセスの制限など。
- 目的は、機能適合性、性能効率性、使用性、保守性を高めること。

#### プログラム構造・データ型

- モジュール分割と独立性: 独立性が高いほど、保守しやすい。
- メインルーチンは、全体の流れを制御し、サブルーチンは、部分の処理を行う。
- **オーバーライド**: サブクラスで、同じ名前と引数のメソッドを定義し直す。**オーバーロード**: 同じ名前で、引数が異なるメソッドを複数定義する。
- プログラムの特性です。

| 特性 | 意味 |
|---|---|
| 再入可能 | 複数のタスクから同時に呼ばれても、正しく動く |
| 再配置可能 | 主記憶のどこに置いても、動く |
| 再使用可能 | 一度実行したあと、再び読み込まずに、続けて実行できる |

- データ型: 整数型、実数型、論理型、文字型。

#### プログラム言語

| 分野 | 言語の例 |
|---|---|
| 業務システム、基幹系 | Java、C#、COBOL |
| Web アプリケーション | JavaScript(ECMAScript)、TypeScript、PHP、Python、Ruby |
| システム記述、組込み | C、C++、Go |
| データ分析、AI | Python、R |
| 科学技術計算 | Fortran、Julia |

プログラミングのパラダイムです。

| パラダイム | 特徴 |
|---|---|
| 手続型 | 手順を順に書き、変数の値を変えながら進める |
| 構造化 | 順次、選択、繰返しで組み立てる |
| オブジェクト指向 | データと処理を、クラスにまとめる |
| 関数型 | 関数を値のように扱い、副作用のない関数を組み合わせる |
| 多重パラダイム | 複数のパラダイムを、併せて使える |
