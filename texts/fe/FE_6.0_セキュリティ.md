# FE テキスト 6.0 セキュリティ

情報システムを狙う脅威と攻撃、組織で守る仕組み(マネジメント)、対策の技術、暗号と認証の仕組み、安全なシステムを作る実装の技術を学びます。基本情報技術者試験では、用語の意味に加えて、「なぜその対策が効くのか」という仕組みの理解が問われます。

## 6.1 情報セキュリティの脅威

### 1. 脅威の種類

**脅威**は、情報資産に損害を与えるおそれのある原因です。代表的なものを整理します。

| 脅威 | 内容 |
|---|---|
| 侵入 | 許可なくシステムやネットワークに入り込む |
| 盗聴 | 通信の途中で、内容を盗み見る |
| なりすまし | 他人の ID や名前を使って、本人のふりをする |
| 改ざん | データやプログラムを、許可なく書き換える |
| アクセス権の誤設定 | 公開してはいけないデータを、誰でも見られる状態にする |
| 情報漏えい | 重要な情報が、外部へ出てしまう |
| 踏み台 | 乗っ取った機器を、別の攻撃の中継に使う |
| ソーシャルエンジニアリング | 人の心理や行動の隙を突いて、情報を聞き出す。電話で管理者を装う、肩越しに画面をのぞく、ごみ箱から書類を拾う、など |

ソーシャルエンジニアリングは、技術の弱点ではなく**人の弱点**を狙うので、教育と手順(本人確認の方法など)で防ぎます。

### 2. マルウェア・不正プログラム

**マルウェア**は、悪意のあるプログラムの総称です。

| 種類 | 特徴 |
|---|---|
| マクロウイルス | 文書ファイルのマクロ機能を悪用して、感染する |
| ボット | 感染した端末を、外部の指令(C&C サーバー)で操る。操られた端末の集まりを**ボットネット**といい、DDoS 攻撃や迷惑メールの送信に使う |
| トロイの木馬 | 有用なソフトウェアに見せかけて入り込み、裏で不正な動作をする。自分では増えず、利用者が実行して入り込む |
| ワーム | ネットワークを通じて、自分で複製して広がる |
| スパイウェア | 利用者の情報を、本人に気づかれないように外部へ送る |
| ランサムウェア | ファイルを暗号化し、元に戻すための身代金を要求する。盗んだデータの公開で脅す手口もある |
| キーロガー | キーボードの入力を記録して、パスワードなどを盗む |
| ルートキット | 侵入後に、攻撃者のプロセス、ファイル、通信の痕跡を隠す |
| バックドア | 攻撃者が、後から再び侵入するために仕掛ける裏口 |
| ファイルレスマルウェア | OS に標準で入っている正規のツール(PowerShell など)を悪用して、主にメモリ上で動く。ディスクにファイルが残りにくく、ファイルの検査だけでは見つけにくい |

### 3. 脆弱性

**脆弱性**(セキュリティホール)は、設計や実装にある、攻撃に悪用される弱点です。

- 不適切な入力確認: 入力の長さや内容を確かめず、バッファオーバーフローやインジェクションを許す。
- 認可・権限・アクセス制御の不備: URL の番号を変えるだけで、他人の情報が見られるなど。
- **シャドー IT**: 組織が許可していない機器やクラウドサービスを、社員が業務に使うこと。管理の外にあるので、更新や監視が届かない。

脆弱性が公表され、修正プログラムが出る前に突く攻撃を**ゼロデイ攻撃**といいます。

### 4. 不正の動機とメカニズム

**不正のトライアングル**は、不正が起きる条件を、**動機**(やむを得ない事情)、**機会**(できる状況)、**正当化**(自分への言い訳)の 3 つで説明します。組織は、権限の分離やログの監視で**機会**を減らします。

**ダークウェブ**は、通常の検索では見つからず、特別なソフトウェアでアクセスする領域です。盗まれた情報の売買に使われます。**リークサイト**は、ランサムウェアの攻撃者が、盗んだ情報を公開して脅すために使うサイトです。

### 5. 攻撃のライフサイクル

**サイバーキルチェーン**(ロッキード・マーティン社が提唱)は、攻撃を偵察、武器化、配送、攻撃(エクスプロイト)、インストール、遠隔操作(C&C)、目的の実行の 7 段階で表す考え方です。ここでは、攻撃の大まかな流れを次の 4 つにまとめます。

| 段階 | 内容 |
|---|---|
| 偵察 | **フットプリンティング**で、標的の公開情報(ドメイン、IP アドレス、社員名)を集める。**ポートスキャン**で、開いているポートと動いているサービスを調べる |
| 侵入 | 脆弱性やメールで入り込む |
| 権限昇格 | 一般ユーザーの権限から、管理者の権限を得る |
| 目的の実行 | 情報の持ち出し、暗号化、改ざんなど |

どの段階でも、見つけて止められるように、複数の対策を重ねます。

### 6. 資格情報とセッションを狙う攻撃

| 攻撃 | 内容 |
|---|---|
| ブルートフォース攻撃(総当たり攻撃) | 1 つの ID に対して、パスワードの候補を総当たりで試す |
| リバースブルートフォース攻撃 | パスワードを固定し、ID を変えながら試す。1 つの ID に対する失敗の回数が少ないので、ロックアウトで検知しにくい |
| クレデンシャルスタッフィング | 他のサービスから流出した ID とパスワードの組を使って、ログインを試す。パスワードの使い回しを狙う |
| セッションハイジャック | ログイン後のセッション ID を盗んだり、推測したりして、本人になりすます |

対策は、パスワードの使い回しをやめること、多要素認証、試行の回数の制限、セッション ID の保護です。

### 7. アプリケーションの不備を狙う攻撃

| 攻撃 | 仕組み |
|---|---|
| SQL インジェクション | 入力に SQL を紛れ込ませ、データベースの操作を不正に変える |
| OS コマンドインジェクション | 入力に OS のコマンドを紛れ込ませ、サーバーで実行させる |
| HTTP ヘッダインジェクション | 入力に改行を入れて、応答のヘッダを不正に挿入する |
| クロスサイトスクリプティング(XSS) | 入力を含むページに、スクリプトを埋め込み、利用者のブラウザで実行させる |
| クロスサイトリクエストフォージェリ(CSRF) | ログイン中の利用者のブラウザに、意図しないリクエストを送らせる |
| ディレクトリトラバーサル | `../` で上のディレクトリをたどり、公開していないファイルを読む |
| バッファオーバーフロー | 確保した領域を超えてデータを書き込み、プログラムの動作を乗っ取る |
| クリックジャッキング | 透明にしたページを重ねて、利用者に意図しないクリックをさせる |
| ドライブバイダウンロード | Web サイトを閲覧しただけで、不正プログラムをダウンロードさせる |

SQL インジェクションの例です。入力がそのまま文字列として連結されるとき、利用者名に `admin' --` を入れると、`--` 以降が(`--` をコメントとして扱う DBMS で)コメントになり、パスワードの条件が無効になります。

```sql
SELECT * FROM users WHERE name = 'admin' --' AND password = '…'
```

### 8. 信頼を悪用する攻撃

- **DNS キャッシュポイズニング**: DNS のキャッシュサーバーに、偽の応答を覚えさせ、利用者を偽のサイトへ誘導する。
- **標的型攻撃**: 特定の組織や人を狙う。**APT**(Advanced Persistent Threat)は、長期にわたって、目立たないように続ける高度な標的型攻撃の総称。
  - **水飲み場型攻撃**: 標的がよく使う Web サイトを改ざんして、待ち受ける。
  - **やり取り型攻撃**: メールを何度かやり取りして、信用させてから、不正なファイルを開かせる。

### 9. サービスの妨害を狙う攻撃

- **DoS 攻撃**: 大量のリクエストで、サービスを使えなくする。
- **DDoS 攻撃**: 多数の機器(ボットネットなど)から、同時に DoS 攻撃をする。
- **DNS 水責め攻撃**: 存在しないサブドメインを大量に問い合わせ、DNS サーバーを過負荷にする。
- **クリプトジャッキング**: 他人の計算資源を、無断で暗号資産の採掘に使う。

### 10. AI システムに対する攻撃

| 攻撃 | 内容 |
|---|---|
| プロンプトインジェクション | AI への入力に細工をして、本来の指示を上書きさせる |
| ジェイルブレイク | 指示を工夫して、AI の安全のための制限を回避する |
| 敵対的サンプル(Adversarial Examples) | 人には分からない細工を入力に加え、学習済みのモデルに誤った判断をさせる |
| データポイズニング | 学習データに不正なデータを混ぜて、モデルの判断を歪める |

### 11. その他の特殊な攻撃

- **ゼロデイ攻撃**: 修正プログラムが出る前の脆弱性を突く。
- **サイドチャネル攻撃**: 暗号の処理時間や消費電力など、実装から漏れる副次的な情報から、鍵を推測する。
- **オープンリゾルバの悪用**: 外部の誰にでも応答する DNS サーバーに、送信元を標的に偽った問合せを送り、大きな応答を標的へ向かわせる(反射・増幅)。対策は、問合せを受け付ける範囲を限ること。

## 6.2 情報セキュリティマネジメント

### 1. 情報セキュリティの考え方

**3 つの特性**です。

| 特性 | 意味 |
|---|---|
| 機密性 | 許可された者だけが、情報を使える |
| 完全性 | 情報が正確で、改ざんされていない |
| 可用性 | 必要なときに、情報やシステムを使える |

3 つに加えて、**信頼性**(システムが意図したとおりに、確実に動く)も重視します。

- **ゼロトラスト**: 社内と社外の区別なく、アクセスのたびに、利用者と端末を確かめる。
- **セキュリティバイデザイン**: 企画や設計の段階から、セキュリティを組み込む。
- **プライバシーバイデザイン**: 個人情報の保護を、設計の段階から組み込む。

### 2. 情報セキュリティマネジメントの考え方

- **need-to-know の原則**: 業務に必要な人に、必要な情報だけを知らせる。アクセス権は必要最小限にし、異動や退職で見直す。
- **クラウドサービスの責任共有モデル**: 事業者と利用者が、役割を分けて責任を持つ。IaaS では、物理設備、ハイパーバイザーまでが事業者、ゲスト OS のパッチ、アプリケーション、データ、アクセスの設定が利用者。SaaS に近づくほど、利用者の責任は小さくなる。

### 3. 情報資産とリスク

- **情報資産**: データ、ソフトウェア、機器、文書、人の知識など。守る対象を、**情報資産台帳**に記録し、重要度で分類する。
- **オペレーショナルリスク**: 業務の運用、人のミス、システムの障害などから生じるリスク。
- **サプライチェーンリスク**: 委託先や部品の供給元を経由して、自社に被害が及ぶリスク。

### 4. リスクアセスメントと対応

**リスクアセスメント**は、次の 3 つのプロセスです。

| プロセス | 内容 |
|---|---|
| リスク特定 | どんなリスク(リスク源、事象)があるかを洗い出す |
| リスク分析 | 発生可能性と影響を見積もり、**リスクレベル**を決める |
| リスク評価 | **リスク基準**と比べ、対応が必要かを判断する |

リスクレベルは、「発生可能性 × 影響度」で求めることが多く、**リスクマトリックス**(縦横の表)に当てはめて、優先度を決めます。リスクには**リスク所有者**(責任と権限を持つ人)を決め、**リスク登録簿**に記録します。

**リスク対応の選択肢**です。

| 選択肢 | 内容 | 例 |
|---|---|---|
| リスク回避 | 原因になる活動をやめる | リスクの高いサービスを廃止する |
| リスク低減(軽減) | 対策で、発生可能性や影響を下げる | パッチの適用、暗号化 |
| リスク移転(共有) | 損害や責任を、他者と分ける | 保険、外部委託 |
| リスク保有(受容) | 理解したうえで、受け入れる | 影響が小さいので、何もしない |

対応しても残るリスクを**残留リスク**といい、受け入れられるかを、リスク所有者が判断します。

### 5. 情報セキュリティポリシーと組織・制度

- **情報セキュリティポリシー**: 組織の方針と基準の文書。**基本方針**(取り組みの方針)と、**情報セキュリティ対策基準**(守るべき具体的な基準)でできている。対策基準を実際の手順にしたものが、実施手順。**情報セキュリティ目的**は、達成したい目標。
- **CSIRT**: インシデントが起きたときの対応を取りまとめるチーム。
- **SOC**(Security Operation Center): ログなどを監視して、脅威を検知する部門。
- **エシカルハッカー**: 許可を得て、攻撃の技術でシステムの弱点を探す技術者。
- **サイバーセキュリティ戦略本部**: 国のサイバーセキュリティ戦略の案を作り、その実施を進める政府の組織。戦略は閣議で決定する。
- **JPCERT コーディネーションセンター**(JPCERT/CC): 国内のセキュリティ情報の収集、注意喚起、インシデントの調整をする組織。
- **CRYPTREC**: 電子政府で使う暗号の安全性を評価、監視し、推奨する暗号のリストを作る取組み。

### 6. 情報セキュリティマネジメントシステム(ISMS)

**ISMS** は、組織が**適用範囲**を決め、リスクアセスメントに基づいて**管理策**を選んで運用し、**継続的改善**をする仕組みです(PDCA の考え方)。

- **JIS Q 27001**(ISO/IEC 27001): ISMS の要求事項の規格。
- **JIS Q 27002**(ISO/IEC 27002): 管理策の実践の指針の規格。
- **ISMS 適合性評価制度**: 第三者が審査し、基準に合えば **ISMS 認証**を与える制度。個人ではなく、組織の仕組みに対する認証。

管理策は、**組織的、人的、物理的、技術的**の 4 つに分けます。

### 7. 情報セキュリティ管理策

| 分類 | 内容の例 |
|---|---|
| 組織的管理策 | アクセス制御(認証情報、アクセス権)、供給者関係における情報セキュリティ、ICT サプライチェーンの管理、クラウドサービスの利用における情報セキュリティ |
| 人的管理策 | 意識向上、教育、訓練、リモートワークの規則 |
| 物理的管理策 | 物理的セキュリティ境界、クリアデスク(机に書類を放置しない)・クリアスクリーン(離席で画面をロックする)、装置の設置と保護、記憶媒体の扱い、ケーブル配線のセキュリティ、装置の保守、装置の安全な処分や再利用 |
| 技術的管理策 | 情報へのアクセス制限、ソースコードへのアクセス、マルウェアに対する保護、構成管理、**データマスキング**、運用システムへのソフトウェアの導入、ウェブフィルタリング、アプリケーションセキュリティの要求事項、セキュリティに配慮したコーディング、**テスト用情報**の保護 |

テストに本番のデータを使うときは、氏名や番号を別の値に置き換え(データマスキング)、アクセスを制限して、使い終えたら削除します。

## 6.3 情報セキュリティ対策

### 1. インシデント管理と事業継続

**インシデントハンドリング**は、一般に、次の順に進みます。検知と報告、**トリアージ**(影響と緊急度で、優先順位を決める)、封じ込め(被害の拡大を止める)、根絶(原因を取り除く)、復旧、事後の振り返りです。

**代替サイト**は、災害時の再開に使います。

| 種類 | 内容 | 再開までの時間 | 費用 |
|---|---|---|---|
| ホットサイト | 本番と同等の設備を動かし、データも同期する | 短い | 高い |
| コールドサイト | 場所と最低限の設備だけ。機器とデータは災害後に用意する | 長い | 安い |

### 2. 人的、物理的な対策

- **組織における内部不正防止ガイドライン**(IPA): 内部不正の機会を減らす(権限の最小化、操作の記録と監視)、不正が見つかる状況を作る、など。
- **情報セキュリティ訓練**: 標的型メールに関する訓練など。繰り返して、意識を保つ。
- **セキュリティゾーニング**: 区画を重要度で分け、重要な区画ほど入退室の管理を厳しくする。
- **入退管理システム**: ID カードや生体認証で、入退室を制御し、記録する。
- **アンチパスバック**: 入室の記録がない ID での退室や、退室していない ID での再入室を拒否して、共連れや ID の使い回しを防ぐ。
- **モバイル機器**(ノート PC、スマートフォン、タブレット端末)のセキュリティ: 画面ロック、暗号化、紛失の対策。**MDM**(Mobile Device Management)は、端末を一元的に管理し、設定の強制や、遠隔でのロックと消去(リモートワイプ)ができる。

### 3. 情報へのアクセス制限

- **最小特権**: プログラムや利用者に、必要最小限の権限だけを与える。Web サーバーのプログラムを root ではなく一般ユーザーで動かせば、脆弱性を突かれても被害を小さくできる。
- **セキュア OS**: 強制アクセス制御などで、root でも権限を細かく制限できる OS。
- **データベース暗号化**: 保存するデータを暗号化し、媒体の盗難や不正な持ち出しでも、内容を読めなくする。

### 4. 認証と署名

- **メッセージダイジェスト**: ハッシュ関数で作る、データの要約(固定長の値)。データが 1 ビットでも変わると、値が大きく変わる。
- **メッセージ認証**: 共通鍵を混ぜたハッシュ値(メッセージ認証コード、HMAC など)で、改ざんと送信元を確認する。ハッシュ値だけでは、改ざんする者が、ハッシュ値も作り直せる。
- **デジタル署名**: 送信者が、文書のハッシュ値を、自分の**秘密鍵**で暗号化(署名)する。受信者は、送信者の**公開鍵**で検証する。改ざんの検出、本人の確認、否認の防止ができる。
- **DNSSEC**: DNS の応答にデジタル署名を付け、応答の正当性を検証する。DNS キャッシュポイズニングによる、偽の応答の受け入れを防ぐ。

デジタル署名を作る流れと、検証する流れを表した図です。

```text
送信者: 文書のハッシュ値を、自分の秘密鍵で暗号化して、署名にする
  [Document] --(hash)--> [Hash A] --(private key)--> [Signature]

受信者: 署名を送信者の公開鍵で戻し、文書から作ったハッシュ値と比べる
  [Signature] --(public key)--> [Hash A]
  [Document]  --(hash)--------> [Hash B]
  [Hash A] == [Hash B] なら、改ざんされていない
```

利用者の認証、認可、ID 連携です。

| 用語 | 内容 |
|---|---|
| 多要素認証 | 知識(パスワード)、所持(スマートフォン、IC カード)、生体(指紋、顔)のうち、異なる種類を 2 つ以上組み合わせる |
| リスクベース認証 | 場所、端末、時間などから、リスクが高いときだけ、追加の認証を求める |
| シングルサインオン(SSO) | 1 回の認証で、複数のサービスを使えるようにする |
| AAA | 認証(誰か)、認可(何をしてよいか)、アカウンティング(利用の記録)の 3 つ |
| eKYC | オンラインで、本人確認を行う仕組み |
| EMV 3-D セキュア(3D セキュア 2.0) | クレジットカードのオンライン決済で、取引のリスクに応じて、追加の認証をする |

**生体認証**には、静脈パターン、虹彩、顔、網膜などの身体的特徴を使います。精度は、2 つの割合で表します。

- **本人拒否率(FRR)**: 本人を、誤って拒否する割合。
- **他人受入率(FAR)**: 他人を、誤って受け入れる割合。

判定を厳しくすると FAR が下がって FRR が上がり、緩めると逆になります。両方を同時に下げるのは難しいので、用途で決めます。

**パスワードレス認証**の **FIDO**(パスキー)は、端末の中で秘密鍵を作り、公開鍵だけをサービスに登録します。ログインのときは、サービスが送るチャレンジに、秘密鍵で署名して返します。パスワードがネットワークに流れず、偽のサイトでは署名ができないので、フィッシングに強い方式です。

### 5. マルウェア、データ、ログの管理

- **ヒューリスティック法**: プログラムの構造や振る舞いが、マルウェアに似ているかを調べる。パターンファイルにない未知のマルウェアも見つけられるが、誤検知もある。パターンマッチング法は、既知のマルウェアの特徴と比べる。
- **ランサムウェア対策**: データのバックアップを、本番から分離して持つ(バックアップ分離)。一定の期間は、変更も削除もできない(**イミュータブルバックアップ**)ようにする。
- **脆弱性管理**: 情報を集め、自社の資産に当てはめ、検証してから、OS の更新や、脆弱性修正プログラム(セキュリティパッチ)の適用をする(**パッチ管理**)。サポートが終わった製品は使わない。
- **DLP**(Data Loss Prevention): 重要な情報が、外部へ持ち出されるのを検知、防止する。
- **SIEM**(Security Information and Event Management): 多くの機器のログを集めて、相関を分析し、異常の兆候を検知する。
- **EDR**(Endpoint Detection and Response): 端末の挙動を監視し、脅威の検知と、対応(隔離など)を行う。

### 6. ネットワークセキュリティ

境界における通信の制御です。

| 用語 | 内容 |
|---|---|
| ファイアウォール | IP アドレス、ポート番号などで、通信を許可、遮断する |
| IDS(侵入検知システム) | 不正な通信を検知して、通知する |
| IPS(侵入防止システム) | 不正な通信を検知して、自動で遮断する。誤検知で正常な通信を止めることがある |
| VPN | 暗号化した通信路を作り、インターネット上で安全につなぐ |

そのほかの制御です。

- **検疫ネットワーク**: 接続する端末の状態(パッチ、ウイルス対策)を検査し、基準に合わない端末は隔離したネットワークにつなぐ。
- **MAC アドレスフィルタリング**: 登録した MAC アドレスの端末だけを、接続させる。MAC アドレスは偽装できる。端末の状態は検査しない。
- **リバースプロキシ**: 公開するサーバーの前に置き、代理で応答する。内部のサーバーを隠し、負荷の分散や検査ができる。
- **DDoS 対策**: 大量の通信を、遮断、分散して、サービスを守る。
- **Bot 対策(CAPTCHA)**: 人間かどうかを、文字の読み取りや画像の選択で判別する。
- **WAF**(Web Application Firewall): HTTP の通信の内容を検査して、SQL インジェクションや XSS を遮断する。
- **許可リスト**(アローリスト、パスリスト): 許可した通信だけを通す。
- **拒否リスト**(ブロックリスト): 禁止する通信だけを遮断する。

技術規格とプロトコルです。

| 用語 | 内容 |
|---|---|
| TLS | 通信の暗号化と、サーバーの認証。ハンドシェイクで、サーバー証明書により認証し、セッション鍵を共有する。本体は共通鍵暗号 |
| IPsec | IP のレベルで、通信の暗号化と認証をする。VPN に使う |
| QUIC | UDP の上で、TLS 1.3 と同等の暗号化を組み込んだプロトコル |
| WPA3 | 無線 LAN の暗号化の規格。パスワードの推測への耐性を高めた SAE という認証を採用 |
| SMTP-AUTH | メールを送るときの、利用者の認証 |
| OP25B | ISP が、自社のメールサーバーを経由しない 25 番ポートの外向きの通信を制限する。迷惑メールの送信を防ぐ。利用者は、サブミッションポート(587 番)で SMTP-AUTH を使う |
| 送信ドメイン認証 | **SPF**: 送信元の IP アドレスを、ドメインの DNS で確認する。**DKIM**: メールに電子署名を付け、DNS の公開鍵で検証する |
| S/MIME(Secure MIME) | 利用者の証明書で、メールを暗号化、署名する |

### 7. 暗号技術

**共通鍵暗号方式**は、暗号化と復号に、同じ鍵を使います。速いのですが、鍵を安全に渡す方法(鍵配送)が課題です。また、通信する組ごとに鍵が必要で、n 人が相互に通信するときは n(n − 1) ÷ 2 本です(20 人で 190 本)。

**公開鍵暗号方式**は、対になる公開鍵と秘密鍵を使います。**RSA 暗号**が代表的で、素因数分解の難しさを利用します。公開鍵で暗号化したものは、対応する秘密鍵でしか復号できません。1 人が 1 組を持てばよい(20 人で 20 組)のですが、処理は重くなります。

| | 共通鍵暗号 | 公開鍵暗号 |
|---|---|---|
| 鍵 | 同じ鍵 | 公開鍵と秘密鍵の対 |
| 速度 | 速い | 遅い |
| 鍵の配送 | 課題 | 公開鍵は公開してよい |
| 例 | AES | RSA |

**ハイブリッド暗号**は、本文を共通鍵暗号で暗号化し、その共通鍵を、相手の公開鍵で暗号化して送ります。両方の長所を使います。TLS も、公開鍵暗号の技術で共通鍵を共有し、本文を共通鍵暗号で暗号化する点で、同じ考え方です(TLS 1.3 では、共通鍵を公開鍵で暗号化して送らず、鍵交換の ECDHE などで共有します)。

ハイブリッド暗号で、本文と共通鍵がどう送られ、どう戻されるかを表した図です。

```text
送信者: 本文を共通鍵で暗号化し、その共通鍵を、受信者の公開鍵で暗号化して送る
  1. 本文を、共通鍵で暗号化して、暗号化した本文にする
  2. 共通鍵を、受信者の公開鍵で暗号化して、暗号化した鍵にする
  3. 暗号化した本文と、暗号化した鍵を、受信者へ送る

受信者: 自分の秘密鍵で共通鍵を取り出し、その共通鍵で本文を戻す
  1. 暗号化した鍵を、自分の秘密鍵で戻して、共通鍵を取り出す
  2. 暗号化した本文を、その共通鍵で戻して、本文にする
```

共通鍵暗号には、**ブロック暗号**と**ストリーム暗号**があります。**AES**(Advanced Encryption Standard)は、ブロック暗号で、128 ビットのブロックごとに暗号化し、鍵の長さは 128、192、256 ビットです。ストリーム暗号は、データを 1 ビットや 1 バイトずつ順に暗号化します。

**鍵のライフサイクル**は、生成、保管、使用、廃棄です。鍵が漏えいした疑い(**危殆化**)があるときは、直ちに失効させ、新しい鍵に置き換えます。

### 8. 公開鍵基盤(PKI)

**公開鍵基盤(PKI)**は、公開鍵の持ち主を保証する仕組みです。

- **認証局(CA)**: 公開鍵と持ち主を結びつけて、**デジタル証明書**(公開鍵証明書)に、自分の秘密鍵で署名して発行する。
- **ルート証明書**: 信頼の起点になる CA の証明書。OS やブラウザに入っている。中間 CA を含む連鎖をたどって、検証する。
- **証明書失効リスト(CRL)**: 認証局が公開する、失効した証明書の一覧。
- **OCSP**: 個々の証明書の失効の状態を、応答サーバーに問い合わせる。

証明書の連鎖を、ルート証明書からサーバー証明書へたどる向きで表した図です。

```text
ルート証明書: 信頼の起点。OS やブラウザに入っている
  |
  | ルート CA が、自分の秘密鍵で署名して発行する
  v
中間 CA の証明書
  |
  | 中間 CA が、自分の秘密鍵で署名して発行する
  v
サーバー証明書

検証は、下から上へ、署名を上の証明書の公開鍵で確かめていく。ブラウザは、この連鎖をルートまでたどる
```

ブラウザは、サーバー証明書を、次のように検証します。
① 署名を、ルート証明書までの連鎖で検証します。
② 有効期間の内であることを確認します。
③ 証明書のドメイン名が、接続先と一致することを確認します。
④ 失効していないことを、CRL や OCSP で確認します。

## 6.4 セキュリティ実装技術・評価

### 1. セキュリティに配慮したシステム構築

**ゼロトラストアーキテクチャ(ZTA)**の設計は、次のとおりです。
① すべてのアクセスで、利用者と端末の状態を確認します(認証、認可)。
② 権限は、必要最小限にします。
③ ネットワークを細かく分け(マイクロセグメンテーション)、侵入されても被害の広がりを抑えます。
④ 認証した後も、継続的に状況を確認します。

**AI を使ったセキュリティ技術(AI for Security)**は、AI をセキュリティの対策に使うことです。例は、大量のログから、機械学習で普段と異なる振る舞いを検出することです。

**AI システムを守るための対策(Security for AI)**は、AI のシステム自体を守ります。

- **プロンプトインジェクション対策**: 入力されたプロンプトの検証(不正な指示の除去)。
- **RAG** 用のデータやデータストアへのアクセス制御: 検索の段階で、質問した利用者の権限に応じて、取り出せる文書を制限する。
- 学習データの出どころの確認(データポイズニング対策)。

### 2. アプリケーション開発のセキュリティ

**セキュアプログラミング**は、脆弱性を作らないように、安全なコードを書くことです。指針に、IPA の「**安全なウェブサイトの作り方**」があります。脆弱性の種類ごとに、根本的な解決策と、保険的な対策を示しています。

| 脆弱性 | 実装上の対策 |
|---|---|
| クロスサイトスクリプティング | 出力するときに、`<`、`>`、`&`、`"` などを、文字参照に置き換える(**エスケープ**)。出力する場所に合った方法を使う |
| SQL インジェクション | **プレースホルダ**を使い、SQL 文の構造と値を分けて、データベースへ渡す |
| バッファオーバーフロー | 入力の長さを確認し、領域の大きさの範囲に、コピーのサイズを制限する。境界を検査する関数や言語を使う |

### 3. ブラウザが備える防御機構

| 機構 | 内容 |
|---|---|
| 同一オリジンポリシー | 別のオリジン(スキーム、ホスト、ポートの組)のリソースを、スクリプトから読ませない |
| **CORS**(オリジン間リソース共有) | サーバーが `Access-Control-Allow-Origin` ヘッダで、読み取りを許すオリジンを指定する。`*` は安易に使わない |
| **HSTS**(HTTP Strict Transport Security) | `Strict-Transport-Security` ヘッダで、一定の期間、そのサイトには HTTPS だけで接続するよう、ブラウザに指示する |
| **CSP**(Content Security Policy) | `Content-Security-Policy` ヘッダで、スクリプトなどを読み込める取得元を制限し、XSS の被害を軽減する |

### 4. クラウド、コンテナのセキュリティ

- **責任共有モデル**に基づく役割分担を理解して、利用者の責任の部分を管理する。
- **クラウドの設定不備**(公開設定、権限設定)は、情報漏えいの大きな原因。既定で非公開にし、最小限の権限にし、定期的に点検する。
- **コンテナイメージの脆弱性管理**: 信頼できる提供元のベースイメージを使い、ビルドのときと運用中にスキャンし、修正したイメージで置き換える。不要なパッケージは入れない。root で動かさない。

### 5. ハードウェア、IoT のセキュリティ

- **TPM**(Trusted Platform Module): 機器に実装されたセキュリティチップ。暗号鍵の生成と保管、起動時の完全性の検査、ディスクの暗号化の鍵の保護に使う。
- **耐タンパ性**: 物理的な解析や、改ざんに耐える性質。
- **IoT のセキュリティ**: 初期パスワードを変更させる(または機器ごとに変える)、不要なポートを公開しない、など。
- **ファームウェアのセキュアアップデート**: 更新の仕組みを備え、署名を検証して、改ざんされた更新を適用しない。
- **IT 製品の調達におけるセキュリティ要件リスト**: 調達のときに、更新、認証、ログなどの必要な機能を確認する。
