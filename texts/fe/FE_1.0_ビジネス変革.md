# FE テキスト 1.0 ビジネス変革

組織の DX(デジタルを使った変革)に参加するために必要な、変革の方法、経営戦略、ビジネスモデル、サービスマネジメント、プロジェクトマネジメント、デザインのアプローチを学びます。基本情報技術者試験では、用語の意味に加えて、稼働率やクリティカルパス、EVM などの計算が出ます。

## 1.1 ビジネス変革の方法論

### 1. 社会の変化

| 用語 | 意味 |
|---|---|
| データ駆動型社会 | データを集めて分析し、その結果をもとに判断や活動を行う社会 |
| DX(デジタルトランスフォーメーション) | デジタル技術とデータを使って、製品、サービス、業務、組織、企業文化を変え、競争の上での強みをつくること。IT で今の業務を速くするだけでは、DX とは言えません |
| AX(AI トランスフォーメーション) | AI を前提に、業務や事業のやり方を変えること |
| カーボンニュートラル | 温室効果ガスの排出量から、吸収や除去の量を引いた合計をゼロにすること |
| カーボントレーシング | 製品の材料の調達から廃棄までの、各段階の温室効果ガスの排出量を追跡し、見える形にすること |
| AI 言語モデルのスケーリング則 | モデルの大きさ、学習データの量、計算の量を増やすと、性能が予測できる形で上がるという経験則 |
| フロンティア AI | その時点で最先端の、能力の高い AI。能力が高い分、社会への影響も大きく、安全性の確認が課題になります |

デジタル技術の活用で、競争の相手が変わります。たとえば、異業種の企業がデータとプラットフォームで参入し、既存の企業の市場を奪うことがあります。

### 2. イノベーションマネジメント

イノベーションマネジメントの原理原則(国際規格 ISO 56000 シリーズで示されている)は、次の 8 つです。

| 原則 | 内容 |
|---|---|
| 価値の実現 | イノベーションで、組織と利害関係者に価値を生み出す |
| 未来志向リーダー | 経営層が、将来を見据えて導く |
| 戦略的方向性 | イノベーションの活動を、組織の戦略に合わせる |
| 組織文化 | 創造性や挑戦を受け入れる文化をつくる |
| 洞察の活用 | 顧客や市場から得た気づきを活かす |
| 不確実性のマネジメント | 先が読めないことを前提に、リスクを管理しながら進める |
| 柔軟性 | 状況の変化に合わせて、計画や進め方を変える |
| システムアプローチ | 組織全体を、つながった仕組みとして捉える |

### 3. イノベーション戦略の理論

| 用語 | 意味 |
|---|---|
| オープンイノベーション | 組織の外の知識や技術を取り入れて、新しい価値をつくる |
| イノベーションのジレンマ | 優れた企業が、既存の顧客の要望に応える改良(持続的イノベーション)に集中し、後から出てきた安くて単純な新技術(破壊的イノベーション)に負けること |
| リーンスタートアップ | 小さな製品を素早く作り、顧客の反応で学び、方向を直しながら進める方法 |
| API エコノミー | 自社のサービスの機能を API で公開し、他社とつないで、新しい価値や収益を生む経済圏 |
| イノベータ理論 | 新しい商品を受け入れる人を、5 つの層に分ける理論 |
| MOT(技術経営) | 技術を、事業の価値につなげるための経営の考え方 |
| 技術の S カーブ | 技術の性能が、時間(投資)とともに、ゆっくり、急に、ゆるやかにと S 字に伸びること |
| キャズム | イノベータ理論で、初期の市場(アーリーアダプタまで)と、一般の市場(アーリーマジョリティ)の間にある深い溝 |
| 魔の川 | 研究から開発に進む段階での壁 |
| 死の谷 | 開発から事業化に進む段階での壁 |
| ダーウィンの海 | 事業化した後、市場で競争に勝ち残る段階での壁 |

イノベータ理論の 5 つの層と、全体に占める割合です。

| 層 | 割合 | 特徴 |
|---|---|---|
| イノベータ(革新者) | 2.5% | 新しいものを真っ先に試す |
| アーリーアダプタ(初期採用者) | 13.5% | 流行に敏感で、周りへの影響力がある |
| アーリーマジョリティ(前期追随者) | 34% | 慎重だが、平均より早く採用する |
| レイトマジョリティ(後期追随者) | 34% | 周りが使ってから採用する |
| ラガード(遅滞者) | 16% | 最後まで採用しない |

### 4. 変革活動のマネジメント

チェンジマネジメントは、変革で影響を受ける人々が、変化を受け入れて定着するように支援する活動です。レベルは 3 つあります。

| レベル | 対象 |
|---|---|
| 個人のチェンジマネジメント | 1 人ひとりが、変化を理解し、新しいやり方に慣れる |
| プロジェクトのチェンジマネジメント | 変革のプロジェクトを、人の面から支える |
| 組織のチェンジマネジメント | 組織全体の、能力、文化、体制を変える |

- 移行計画: 古いやり方から新しいやり方へ、いつ、どの順で切り替えるかの計画。
- 定着支援: 研修や相談の窓口、効果の確認などで、新しいやり方が使い続けられるようにする。

## 1.2 経営戦略・デジタル戦略

### 1. 経営戦略の策定

| 用語 | 意味 |
|---|---|
| MVV(ミッション、ビジョン、バリュー) | 使命(存在する意義)、目指す将来の姿、大切にする価値観 |
| 機能別戦略 | 研究開発、生産、販売、人事、情報システムなど、機能ごとの戦略 |
| 多角化 | 新しい事業や市場に進出すること |
| シナジー効果 | 複数の事業や資源を組み合わせて、足し算以上の効果を出すこと |
| 規模の経済 | 生産量が増えるほど、1 つ当たりの費用が下がること |
| 範囲の経済 | 複数の事業で、設備や人、ノウハウを共有して、費用を下げること |
| サーキュラーエコノミー(循環経済) | 資源を使い捨てにせず、再利用や再生をして、循環させる経済 |
| VUCA | 変動、不確実、複雑、曖昧が重なった、先の読めない状況(Volatility、Uncertainty、Complexity、Ambiguity) |

全体戦略(会社全体の戦略)の用語です。

| 用語 | 意味 |
|---|---|
| ドメイン | 事業を行う領域(顧客、提供する価値、技術の範囲) |
| プロダクトポートフォリオマネジメント(PPM) | 市場の成長率と、自社の相対的な市場シェアの 2 軸で事業を 4 つに分け、資源の配分を決める手法 |
| コアコンピタンス | 他社が真似しにくい、自社の中心的な強み |
| シェアードサービス | 経理や人事などの間接業務を、グループで 1 か所に集めて効率化する |

PPM の 4 つの区分です。

| 区分 | 市場の成長率 | 相対的な市場シェア | 方針 |
|---|---|---|---|
| 花形 | 高い | 高い | 地位を保つために投資する |
| 金のなる木 | 低い | 高い | 利益を出し、ほかの事業に回す |
| 問題児 | 高い | 低い | 伸ばすか、やめるかを判断する |
| 負け犬 | 低い | 低い | 撤退を検討する |

### 2. ビジネス戦略の策定

| 用語 | 意味 |
|---|---|
| ファイブフォース分析 | 業界の競争の厳しさを、5 つの力(新規参入の脅威、代替品の脅威、買い手の交渉力、売り手の交渉力、業界内の競争)で分析する |
| SWOT 分析 | 内部環境の強み(S)と弱み(W)、外部環境の機会(O)と脅威(T)で整理する |
| バリューチェーン分析 | 事業の活動(調達、製造、出荷、販売、サービスなど)を価値の連鎖として捉え、どこで価値が生まれ、費用がかかるかを分析する |
| 成長マトリクス(アンゾフ) | 製品と市場の 2 軸で、市場浸透、新市場開拓、新製品開発、多角化の 4 つに分ける |
| 同質化戦略 | 業界の首位の企業が、他社の差別化を真似して、優位を打ち消す |
| ブルーオーシャン戦略 | 競争のない新しい市場(青い海)をつくる |
| バランススコアカード | 財務、顧客、業務プロセス、学習と成長の 4 つの視点で、戦略を指標にして管理する |
| CSF(重要成功要因) | 目標の達成に欠かせない要因 |
| KGI(重要目標達成指標) | 最終の目標を測る指標 |
| KPI(重要業績評価指標) | 目標に向かう途中の達成度を測る指標 |
| バリューエンジニアリング | 製品の機能を下げずに、費用を下げて、価値(機能÷費用)を高める |

- KGI と KPI の関係の例: 売上 1 億円を目標とする(KGI)。そのために、問い合わせの数や成約率(KPI)を管理する。

### 3. デジタル戦略

| 用語 | 意味 |
|---|---|
| DX 戦略 | デジタルを使って、事業や組織をどう変えるかの戦略 |
| 最新技術の活用 | 生成 AI(文章や画像などを作る AI)や、AI エージェント(目的に向かって、自分で手順を考え、道具を使う AI)などを、業務や事業に取り入れる |
| デジタルガバナンス・コード | 経済産業省が示す、企業がデジタル技術による変革に取り組むときの、経営者の対応の指針 |

デジタル活用促進(普及啓発)の方法です。

| 方法 | 内容 |
|---|---|
| 業務マニュアル | 手順を文書にして、誰でも同じようにできるようにする |
| e-ラーニング | ネットワークで学ぶ。時間と場所を選ばない |
| 講習会 | 集まって学ぶ。その場で質問できる |
| 人材育成計画 | 必要なスキルを持つ人を、いつまでに、どう育てるか |
| ゲーミフィケーション | ゲームの要素(得点、ランキング、バッジ)を取り入れて、意欲を高める |
| デジタルディバイド | デジタル技術を使える人と、使えない人の間に生まれる格差(情報格差) |

### 4. 情報システム戦略

| 用語 | 意味 |
|---|---|
| 情報システム戦略 | 経営戦略を実現するための、情報システムの方針 |
| 情報システム化基本計画 | 情報システム戦略をもとに、どのシステムを、どの順で作るかを決める計画 |
| 情報システム投資計画 | 情報システムにかける費用と、その効果の計画 |

システム化計画では、次のことを決めます。

- システム化構想の立案(目的と範囲の大枠)、システム化計画の立案、システムの適用範囲、プロジェクトの推進体制、全体開発スケジュール、要員の教育計画。
- 開発投資対効果(IT ポートフォリオ): 複数の IT への投資を、効果と危険を見て、組み合わせて管理する。

| 用語 | 意味 |
|---|---|
| SoR(Systems of Record) | 記録のためのシステム。受注、会計など、正確さが大切な基幹系 |
| SoE(Systems of Engagement) | 顧客とのつながりのためのシステム。アプリ、SNS など |
| SoI(Systems of Insight) | 洞察のためのシステム。データを分析して、判断に役立てる |
| Fit to Standard | パッケージの標準の機能に、業務を合わせる考え方。作り込み(カスタマイズ)を減らす |

要件定義は、システムに求めることを決める作業です。

| 種類 | 内容 |
|---|---|
| 業務要件定義 | 業務として何をどうしたいか |
| 機能要件定義 | システムが持つ機能 |
| 非機能要件定義 | 性能、可用性、セキュリティなど、機能以外の品質 |

手法に、DFD(データの流れの図)、決定表(条件と動作の組み合わせの表)、UML(モデリングの記法)などを使います。

調達の用語です。

| 用語 | 意味 |
|---|---|
| 内外作基準 | 自社で作る(内製)か、外部に任せる(外注)かの判断の基準 |
| アウトソーシング | 業務や開発を外部に委託する |
| ソフトウェアのサプライチェーンマネジメント | 利用するソフトウェアの部品(OSS を含む)の出どころや、安全性を管理する |
| 企画競争入札 | 提案の内容を比べて、発注先を決める |
| 一般競争入札 | 条件を公開して、広く募り、条件に合う中で最も有利な相手に決める |
| RFI(情報提供依頼書) | 技術や製品の情報を、業者に求める |
| RFP(提案依頼書) | 要件を示して、具体的な提案を求める |
| RFQ(見積依頼書) | 費用と納期の見積りを求める |
| グリーン調達 | 環境への負担が小さい製品やサービスを、優先して買う |

順番は、RFI で情報を集め、RFP で提案を受け、RFQ で見積りをもらうのが一般的です。

### 5. エンタープライズアーキテクチャ(EA)

EA は、組織全体のシステムと業務を、全体最適の視点で設計する考え方です。4 つの層で整理します。

| 層 | 内容 |
|---|---|
| ビジネスアーキテクチャ | 業務、組織、情報の流れ |
| データアーキテクチャ | 業務に必要なデータの構造 |
| アプリケーションアーキテクチャ | 業務を支えるアプリケーションの構成 |
| テクノロジアーキテクチャ | 基盤となる、ハードウェア、ソフトウェア、ネットワーク |

EA の 4 つの層を、業務に近い側から、基盤に近い側へ並べた図です。

```text
1. ビジネスアーキテクチャ: 業務、組織、情報の流れ
   |
   v
2. データアーキテクチャ: 業務に必要なデータの構造
   |
   v
3. アプリケーションアーキテクチャ: 業務を支えるアプリケーションの構成
   |
   v
4. テクノロジアーキテクチャ: 基盤となるハードウェア、ソフトウェア、ネットワーク
```

- アーキテクチャモデル: これらの層を図や表で表したもの。
- ザックマンフレームワーク: システムを、「何を、どのように、どこで、誰が、いつ、なぜ」の 6 つの疑問と、立場(視点)の表で整理する枠組み。

## 1.3 ビジネスモデル・ビジネスプロセス

### 1. ビジネス調査・ビジネス分析

| 手法 | 内容 |
|---|---|
| 3C 分析 | 顧客(Customer)、競合(Competitor)、自社(Company)の 3 つで、市場を分析する |
| PEST 分析 | 外部環境を、政治(Politics)、経済(Economy)、社会(Society)、技術(Technology)で分析する |
| 市場調査(マーケティングリサーチ) | アンケートやインタビューなどで、市場の情報を集める |
| STP 分析 | 市場を分け(セグメンテーション)、狙う層を決め(ターゲティング)、自社の立ち位置を決める(ポジショニング) |
| コンジョイント分析 | 商品の属性(価格、機能など)の組み合わせを見せ、どれが選ばれるかから、各属性の重要度を推定する |
| 実験法 | 条件を変えて試し、結果の違いから、因果関係を調べる(A/B テストなど) |

### 2. ビジネスモデル

ビジネスモデルは、どのように価値を提供し、どのように収益を得るかの仕組みです。収益を得る仕組みを、マネタイズモデルと呼びます。

| モデル | 内容 |
|---|---|
| ライセンスモデル | 使用の権利を売る |
| サブスクリプションモデル | 期間ごとに、継続して料金を取る |
| フリーミアム | 基本の機能は無料で提供し、高度な機能に課金する |

| 用語 | 意味 |
|---|---|
| データマネタイズ | データを活用して、収益を得る |
| OtoO(Online to Offline) | ネットから、実店舗への来店や購入につなげる |
| OMO(Online Merges with Offline) | ネットと実店舗を区別せず、顧客の体験を 1 つにつなげる |
| ロングテール | 売れる数が少ない商品も、品ぞろえを増やして、合計で大きな売上にする(ネット販売で成り立ちやすい) |

- ビジネスモデルキャンバス: ビジネスモデルを、9 つの要素(顧客セグメント、価値提案、チャネル、顧客との関係、収益の流れ、主要なリソース、主要な活動、主要なパートナー、コスト構造)で 1 枚に描く図。
- 仮説検証: 「こうすれば売れるはず」という仮説を立て、小さく試して確かめ、直す。

### 3. ビジネスプロセス

ビジネスプロセスは、業務の一連の流れです。設計と改善の進め方は、可視化、標準化、自動化の順が基本です。

| 手順 | 内容 |
|---|---|
| 可視化 | 今の流れを図にして、無駄や問題を見つける |
| 標準化 | やり方をそろえて、誰がやっても同じ品質にする |
| 自動化 | 決まった手順を、システムに任せる |

- RPA(Robotic Process Automation): パソコンでの定型の操作を、ソフトウェアのロボットが自動で行う。

## 1.4 サービスマネジメント

### 1. サービスとサービスマネジメント

- サービス: 顧客が達成したい成果を実現しやすくすることで、顧客に価値を提供する手段。
- サービスマネジメント: サービスを、安定して提供し、改善し続けるための、組織の活動と仕組み。
- SLA(サービスレベルアグリーメント): サービスの提供者と顧客の間で、サービスの内容と水準(稼働率、応答時間、復旧時間など)を合意した文書。

### 2. サービス事業の確立、維持及び改善

| 用語 | 意味 |
|---|---|
| 事業関係管理 | 顧客や利害関係者との関係を管理し、要望を把握する |
| サービス満足度 | 顧客が、サービスにどれだけ満足しているか |
| サービスレベル管理 | SLA で決めた水準を、守れているかを監視して管理する |
| 供給者管理 | サービスに使う、他の組織の提供するものを管理する。供給者は、外部供給者(外部の組織)と、内部供給者(自社内の別の部門)に分かれる |
| サービスポートフォリオ管理 | 提供しているサービス、開発中のサービス、廃止するサービスを、全体として管理する |
| サービスカタログ管理 | 顧客に見せるサービスの一覧(カタログ)を、最新に保つ |
| サービスの報告 | 実績を、利害関係者に報告する |
| 継続的改善 | サービスと管理の仕組みを、繰り返し見直して改善する |
| サービスの要求事項 | 顧客などが、サービスに求めること |

### 3. サービスの設計、構築及び移行

| 用語 | 意味 |
|---|---|
| 変更管理 | 変更を、影響を評価して承認し、計画的に行う。変更の依頼は、変更要求(RFC)で出す |
| サービスの設計及び移行 | 新しいサービスや、変更を、設計して、本番の環境に移す |
| サービス受入れ基準 | 新しいサービスを、本番にしてよいかを判断する基準 |
| リリース及び展開管理 | 変更を、本番の環境に、計画的に展開する |
| 資産管理 | ハードウェア、ソフトウェア、ライセンスなどの資産を管理する |
| 構成管理 | サービスを構成する要素(構成品目、CI)と、その関係を、記録して最新に保つ |
| サービスの予算業務及び会計業務 | サービスにかかる費用を計画し、記録し、管理する |
| 需要管理 | サービスの需要(利用の量)を把握し、予測する |
| 容量・能力管理 | 需要を満たす、処理の能力や容量(CPU、ディスクなど)を確保する。パフォーマンス(処理の速さ)も対象 |

### 4. サービス要求の実現

| 用語 | 意味 |
|---|---|
| サービスデスク | 利用者の問い合わせの窓口。SPOC(Single Point Of Contact)とも呼ばれ、連絡の窓口を 1 つにする |
| インシデント | サービスの中断や、品質の低下を、実際に起こしている、または起こしそうな出来事 |
| インシデント管理 | インシデントから、できるだけ早く、サービスを回復させる。原因の特定は目的ではない |
| 重大なインシデント | 影響が大きく、緊急の対応が必要なインシデント |
| エスカレーション | 解決できないときに、上位の担当者や管理者に引き継ぐ |
| サービス要求 | 利用者からの、パスワードの再設定やアクセス権の追加などの依頼(障害ではない) |
| サービス要求管理 | サービス要求を、決めた手順で処理する |
| 問題 | 1 つ以上のインシデントの、原因 |
| 問題管理 | 問題の根本の原因を調べ、再発を防ぐ |
| 既知の誤り | 根本の原因が分かっているか、影響を減らす方法(回避策)がある、まだ恒久的には解決していない問題 |
| モニタリング | サービスの状態を、監視する |

インシデント管理と問題管理が、それぞれ何を目指すかを表した図です。

```text
インシデント: サービスの中断や、品質の低下が起きている
  |
  +-- インシデント管理: できるだけ早く、サービスを回復させる
  |
  `-- 問題管理: 原因(問題)を調べ、再発を防ぐ
        |
        +-- 根本の原因を取り除く
        |
        `-- すぐには直せないとき: 既知の誤りとして、回避策を記録する
```

- インシデント管理は「早く元に戻す」、問題管理は「原因を取り除いて再発を防ぐ」。目的が違います。
- 既知の誤りには、回避策(一時的な対処)を記録しておき、同じインシデントが起きたときに素早く対応します。

### 5. サービスの保証

#### 5-1. 可用性と稼働率

サービス可用性管理は、必要なときに、サービスが使える状態を保つ活動です。

| 用語 | 意味 |
|---|---|
| MTBF(平均故障間隔) | 修理が終わってから、次に故障するまでの、正常に動いている時間の平均 |
| MTTR(平均修復時間) | 故障してから、直るまでの、平均の時間 |

稼働率は、全体の時間のうち、動いている時間の割合です。

```
稼働率 = MTBF ÷ (MTBF + MTTR)
```

例: MTBF が 900 時間、MTTR が 100 時間のとき、稼働率は 900 ÷ (900 + 100) = 0.9(90%)です。

複数の装置を組み合わせたときの稼働率です。各装置の稼働率を A1、A2 とします。

| 構成 | 動く条件 | 稼働率 |
|---|---|---|
| 直列 | すべてが動いている | A1 × A2 |
| 並列 | どれか 1 つが動いている | 1 − (1 − A1) × (1 − A2) |

直列と並列の構成を、図にしたものです。A1 と A2 は、各装置の稼働率です。

```text
直列: どちらも動いていないと、全体が動かない
  --[A1]--[A2]--

並列: どちらか 1 つが動いていれば、全体が動く
       +--[A1]--+
  -----+        +-----
       +--[A2]--+
```

- 直列は、装置を足すほど、稼働率が下がります(0.9 × 0.9 = 0.81)。
- 並列は、装置を足すほど、稼働率が上がります(1 − 0.1 × 0.1 = 0.99)。
- 並列と直列が混ざった構成は、まとまりごとに計算し、1 つの装置として扱います。

#### 5-2. 予備の機器(スタンバイ)

| 方式 | 予備の状態 | 切り替えの速さ | 費用 |
|---|---|---|---|
| ホットスタンバイ | 電源が入り、システムも動いていて、すぐ引き継げる | 速い | 高い |
| ウォームスタンバイ | 電源は入っているが、一部のソフトだけが動いている | 中間 | 中間 |
| コールドスタンバイ | 電源が切れていて、障害のときに起動して設定する | 遅い | 低い |

#### 5-3. サービス継続管理

サービス継続管理は、災害などで、サービスが止まっても、事業を続けられるように準備する活動です。次の 3 つの目標を決めます。

| 用語 | 意味 | 例 |
|---|---|---|
| 目標復旧時間(RTO) | 止まってから、どれだけの時間で復旧するか | 4 時間以内 |
| 目標復旧時点(RPO) | どの時点のデータまで戻すか(どれだけのデータ損失を許すか) | 前日の夜のバックアップの時点 |
| 目標復旧レベル(RLO) | どの水準まで、機能を復旧するか | 主要な機能だけ、先に復旧 |

RPO と RTO が、時間の上のどの範囲を表すかを示した図です。

```text
 [A]                    [B]                  [C]
  |                      |                    |
--+----------------------+--------------------+------> time
  |<-------- RPO ------->|<------ RTO ------->|

[A]: 最後のバックアップの時点(データを戻す先)
[B]: 障害が起きた時点
[C]: サービスが復旧した時点
```

RPO は、障害のときに、どこまで古いデータに戻ってよいかの目標です。RTO は、止まってから復旧するまでの時間の目標です。

- RPO を短くする(データを最新に近づける)には、バックアップの頻度を上げるか、リアルタイムの複製(レプリケーション)が必要です。費用が増えます。

#### 見積りの手法

| 手法 | 内容 |
|---|---|
| 類推見積り | 似た過去のプロジェクトの実績を使う。速いが、精度は低い |
| パラメトリック見積り | 規模などの数値に、単価を掛けて計算する |
| 三点見積り(PERT) | 楽観値(a)、最頻値(m)、悲観値(b)から、期待値を (a + 4m + b) ÷ 6 で求める |
| ボトムアップ見積り | WBS の細かい作業ごとに見積り、積み上げる。精度は高いが、手間がかかる |

- ファンクションポイント法: 画面、帳票、ファイルなど、機能の数と複雑さに重みを付けて、システムの規模を見積もる。
- COCOMOⅡ: ソフトウェアの規模(行数など)と、各種の要因から、工数と期間を見積もるモデル。

#### スケジュールの手法

| 手法 | 内容 |
|---|---|
| ガントチャート | 横軸を日付にして、作業の期間を棒で表す。作業の順序の関係は分かりにくい |
| アローダイアグラム | 作業を矢印で、作業の間の結合点を丸で表し、作業の順序を表す |
| プレシデンスダイアグラム | 作業を四角で表し、作業の先行の関係を矢印で表す |
| PERT | 作業の順序と所要の期間から、全体の日程を管理する手法 |
| クリティカルパス法 | 最も長い経路(クリティカルパス)を求め、そこを重点的に管理する |

- クリティカルパス: 開始から終了までの経路のうち、日数の合計が最も長いもの。ここが遅れると、全体が遅れる。
- 余裕のある作業は、遅れてもすぐには全体に影響しない。クリティカルパス上の作業には、余裕がない。
- クラッシング: 資源(人員、費用)を追加して、期間を短くする。費用は増える。
- ファストトラッキング: 順番に行う作業を、並行して行い、期間を短くする。手戻りの危険が増える。

アローダイアグラムの例です。作業 A(3 日)の後に、B(4 日)と C(2 日)が並行して始まり、D(5 日)は B と C が終わった後に始まります。

上の例を、アローダイアグラムのように並べた図です。括弧の中の数字は、作業の日数です。

```text
          +--> B(4) --+
          |           |
A(3) -----+           +--> D(5)
          |           |
          +--> C(2) --+
```

| 経路 | 日数 |
|---|---|
| A → B → D | 3 + 4 + 5 = 12 日 |
| A → C → D | 3 + 2 + 5 = 10 日 |

クリティカルパスは A → B → D で、全体は 12 日です。C は、2 日の余裕があります。

#### アーンドバリューマネジメント(EVM)

EVM は、費用と進み具合を、金額で測る手法です。

| 略称 | 名前 | 意味 |
|---|---|---|
| BAC | 完成時総予算 | プロジェクト全体の予算 |
| PV | 計画価値 | 今の時点で、終わっているはずの作業の予算額 |
| EV | 出来高 | 今の時点で、実際に終わった作業の予算額 |
| AC | 実コスト | 今の時点で、実際にかかった費用 |

| 指標 | 式 | 見方 |
|---|---|---|
| SV(スケジュール差異) | EV − PV | 0 より小さければ、遅れている |
| CV(コスト差異) | EV − AC | 0 より小さければ、予算の超過 |
| SPI(スケジュール効率指数) | EV ÷ PV | 1 より小さければ、遅れている |
| CPI(コスト効率指数) | EV ÷ AC | 1 より小さければ、予算の超過 |
| EAC(完成時総コスト見積り) | BAC ÷ CPI | 今の効率が続くと仮定した、最終の費用の見込み |

例: BAC が 1,000 万円、PV が 400 万円、EV が 300 万円、AC が 500 万円のとき、SV は −100 万円(遅れ)、CV は −200 万円(超過)、SPI は 0.75、CPI は 0.6 です。EAC は 1,000 ÷ 0.6 = 約 1,667 万円です。

## 1.6 デザインのアプローチ

### 1. 考え方と方法論

| 用語 | 意味 |
|---|---|
| UX デザインの五段階モデル | 利用者の体験(UX)を、5 つの層で設計する。下から、戦略(目的と利用者の要求)、要件(必要な機能と内容)、構造(情報や操作の構成)、骨格(画面の配置)、表層(見た目) |
| UX タイムスパン | 体験を、時間の長さで 4 つに分ける。予期的 UX(使う前の期待)、一時的 UX(使っているその時)、エピソード的 UX(使った後の振り返り)、累積的 UX(長く使い続けた全体の印象) |
| CX デザイン | 顧客が、購入の前から後まで、企業と関わるすべての場面で得る体験(顧客体験)を設計する |
| 人間中心設計 | 利用者のことを理解し、利用者を設計の過程に関わらせ、評価を繰り返して改善する |
| サービスデザイン | 顧客だけでなく、サービスを提供する側も含め、サービス全体の体験を設計する |
| デザイン思考 | 利用者に共感し、課題を定義し、アイデアを出し、試作し、試す(5 段階)。何度も繰り返す |
| ペルソナ | 想定する利用者を、名前や年齢、行動などの具体的な人物像で表したもの |

- UX デザインの五段階モデルは、下の層(戦略)から決めます。表層から先に決めると、後で直しが増えます。

### 2. 顧客理解・ユーザー理解

| 用語 | 意味 |
|---|---|
| 要求分析 | 利用者や関係者が、システムに求めることを、集めて整理する |
| ユーザーニーズ調査 | インタビューやアンケートで、利用者の要望や困りごとを調べる |
| 現状分析 | 今の業務や製品の状況を調べる |
| 課題定義 | 解くべき課題を、はっきりさせる |
| 要求仕様書 | 要求を、まとめた文書 |
| 要求工学 | 要求を、集め、分析し、仕様にして、管理する、体系的な方法 |

### 3. 仮説・構想の手法

| 手法 | 内容 |
|---|---|
| クリエイティブシンキング | 既存の枠にとらわれず、新しい発想をする |
| バリュープロポジションキャンバス | 顧客の側(顧客の作業、悩み、得たいもの)と、提供する側(製品、悩みの解消、利得の創出)を並べて、価値が合っているかを確かめる |
| カスタマージャーニーマップ | 顧客が、サービスを知ってから使い終わるまでの行動、考え、感情を、時間の順に描いた図 |
| サービスブループリント | サービスを、顧客から見える部分(フロントステージ)と、見えない裏方の部分(バックステージ)に分けて、全体の流れを描いた設計図 |
| 構造化シナリオ法 | 利用者の利用場面を、決まった形で書いて、要求を引き出す |

### 4. プロトタイプの手法

| 手法 | 内容 |
|---|---|
| ペーパープロトタイプ | 紙に画面を描いて、試す。安く、すぐ作れる |
| サービスプロトタイプ | サービスの流れを、寸劇などで試す |
| ファンクショナルプロトタイプ | 実際に動く機能を持つ試作 |
| デザインプロトタイプ | 見た目や操作感を確かめる試作 |
| ストーリーテリング | 利用の場面を、物語にして伝える |
| デスクトップウォークスルー | 試作や図を机に広げ、関係者が、利用の流れを順にたどって確かめる |

### 5. 評価の手法

| 手法 | 内容 |
|---|---|
| 思考発話法 | 利用者に、考えていることを声に出しながら、操作してもらい、つまずきの理由を探る |
| ヒューリスティック評価法 | 専門家が、使いやすさの経験則(ヒューリスティクス)に照らして、問題を見つける。利用者は必要ない |
| ユーザビリティテスト | 実際の利用者に、課題を行ってもらい、使いやすさを調べる |
