# 問題の反対レビュー

書いた人は、自分の問題を「正しい」と思って読む。このレビューは逆に、**問題が壊れている証拠**を探す。CLAUDE.md 7 章のとおり、書いたのとは別のエージェント(Opus)に任せる。

## 1. 対象を決める

- 引数がファイルなら、そのファイルの問題すべて。
- 引数が問題 ID なら、その問題だけ。
- 引数がなければ、`git diff main...HEAD -- content/` で足したり変えたりした問題。差分がなければ、そう伝えて終わる。

先に `npm run gen` を実行する。内容の検査(`src/lib/contentLint.ts`)で見つかるものは、ここで直す。レビューは、機械では見つからないものに使う。

## 2. レビューを任せる

Agent ツールで、新しいエージェント(subagent_type は general-purpose、model は opus)を起こす。問題が 30 問を超えるときは、ファイルごとに分けて並行に起こす。プロンプトには次をそのまま入れ、対象のファイルと問題 ID を足す。書いた側の意図や、この会話の結論は渡さない。

```
あなたは、資格試験の問題集の反対レビュー役です。目的は、問題が壊れている証拠を見つけることです。問題がよくできているかどうかの感想は要りません。

対象: <ファイルのパスと問題 ID>
書式: 問題は「**問N** `ID` 問題文」と「- A. 選択肢」、解答は「### 問N」の下の「**正解**:」と解説です。入力問題は選択肢がなく、正解に認める答えが並びます。

1 問ずつ、次の 5 つを試してください。

1. 別の正解: 正解でない選択肢を 1 つずつ取り上げ、「この選択肢が正しいと言える、現実にありうる条件」を探す。問題文がその条件を除いていなければ、前提の不足として指摘する(例: swap の有無、版の違い、既定値を変えた環境、クラウドとオンプレの違い)。
2. 正解が誤り: 正解と解説の事実を疑う。コマンドのオプション、既定値、上限、版、料金、サービスの仕様は、公式の文書(man ページ、公式ドキュメント、試験ガイド)で確かめる。確かめられなければ「要確認」とする。記憶だけで「正しい」としない。
3. 別解の不足: 入力問題と「入力の別解」のある問題で、正しいのに不正解になる答えを挙げる(長い形のオプション、表記の揺れ、同じ結果になる別のコマンド、引数の順番)。
4. 古い情報: 廃止された機能、名前の変わったサービス、古い版の前提がないか。
5. 解説の不足: 誤りの選択肢に、なぜ誤りかの説明がない。問題文や解説が、ほかの問題を前提にしている。

指摘のない問題は書かないでください。見つからなければ「指摘なし」とだけ書いてください。

出力は次の表だけにしてください。
| 問題 ID | 種類 | 問題点 | 根拠 | 修正案 |
種類は 前提の不足 / 事実の誤り / 別解の不足 / 版の不一致 / 他問参照 / 選択肢の記号 のどれかです。根拠には、確かめた公式の文書の URL か、反例の具体的な条件を書いてください。
```

## 3. 指摘を確かめて直す

- 指摘をそのまま信じない。1 件ずつ、根拠の文書や反例を自分でも確かめ、正しいものだけを直す。誤った指摘は「却下」として理由を残す。
- 直したら `npm run gen` と `npx vitest run` を通す。
- 問題 ID と番号は変えない。

## 4. 記録する

- 直した指摘を、`docs/改善ログ.md` の「記録」に 1 行ずつ足す。経路は「レビュー」、分類は表の種類。
- 同じ分類が 2 回目なら、CLAUDE.md 9 章のとおり、検査(`src/lib/contentLint.ts`)か CLAUDE.md 4 章の規則に足す。
- ユーザーには、指摘の数、直した数、却下した数と、直した問題 ID を伝える。
