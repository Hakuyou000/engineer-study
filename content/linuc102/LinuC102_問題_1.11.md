## 解答・解説

### 問1 `LinuC102-1.11-001`

**正解**: B

**テキスト**: 1. オープンソースとは

フリーソフトウェアの「フリー」は「無料」ではなく「自由」の意味です。FSF(フリーソフトウェア財団)は、ソフトウェアを実行、調査、改変、再配布する利用者の自由を重視しています。

### 問2 `LinuC102-1.11-002`

**正解**: C

**テキスト**: 2. オープンソースの特徴

オープンソースソフトウェアも著作物で、著作権は放棄されていません。著作権者がライセンスで利用を許諾しているのです。販売は禁じられておらず、一般に動作の保証はありません(無保証)。

### 問3 `LinuC102-1.11-003`

**正解**: C

**テキスト**: 4. 主なライセンス

AGPL は GPL の条件に加えて、ネットワーク越しにサービスとして提供する場合にも、利用者へのソースコードの公開を求めます。GPL は配布する場合にだけ公開を求めます。LGPL と MPL は GPL より条件の緩いライセンスです。

### 問4 `LinuC102-1.11-004`

**正解**: A

**テキスト**: 4. 主なライセンス

Apache License 2.0 は寛容型のライセンスで、特許の利用の許諾を明記しています。MIT と BSD も寛容型ですが、特許についての条項はありません。GPLv2 はコピーレフト型で、寛容型ではありません。

### 問5 `LinuC102-1.11-005`

**正解**: B

**テキスト**: 5. 改変と再配布

GPL でソースコードの公開義務が生じるのは、ソフトウェアを外部に配布するときです。社内だけで使うなら、改変していても公開の義務はありません。ただし AGPL の場合は、サービスとして外部に提供するだけでも公開が求められます。

### 問6 `LinuC102-1.11-006`

**正解**: D

**テキスト**: 4. 主なライセンス

LGPL は主にライブラリ向けのライセンスで、そのライブラリをリンクして使うだけのプログラムは、別のライセンス(独自のライセンスなど)にできます。ただし、ライブラリそのものを改変して配布する場合は、改変部分の公開が必要です。

### 問7 `LinuC102-1.11-007`

**正解**: A

**テキスト**: 4. 主なライセンス

MPL は、改変したファイルだけに同じライセンスでの公開を求めます。新しく追加した別のファイルは、独自のライセンスにできます。BSD は寛容型、LGPL はライブラリ単位、AGPL はプログラム全体にコピーレフトを適用します。

### 問8 `LinuC102-1.11-008`

**正解**: B

**テキスト**: 3. コピーレフト

制約の強さは、AGPL ＞ GPL(強いコピーレフト)＞ LGPL や MPL(弱いコピーレフト)＞ Apache、BSD、MIT(寛容型)の順です。AGPL はサービスとしての提供にも条件があるので最も強く、MIT はほとんど条件がありません。

### 問9 `LinuC102-1.11-009`

**正解**: D

**テキスト**: 5. 改変と再配布

GPL は、販売も業務での利用も認めています。配布するときに、ソースコードを公開し、同じ GPL を適用することが求められるだけです。条件なく自由に扱えるわけではありません。

### 問10 `LinuC102-1.11-010`

**正解**: D

**テキスト**: 1. オープンソースとは

オープンソースの定義には、再頒布の自由、ソースコードの公開、利用する人や分野の差別の禁止などが含まれますが、無償で提供することは条件ではありません。オープンソースのソフトウェアを有料で販売することもできます。

### 問11 `LinuC102-1.11-011`

**正解**: D

**テキスト**: 4. 主なライセンス

パブリックドメインは、著作権が放棄された、または保護期間が過ぎて消滅した状態のことで、ライセンスではありません。誰でも自由に使えます。

### 問12 `LinuC102-1.11-012`

**正解**: D

**テキスト**: 1. コミュニティの構成

コミッタは、リポジトリに直接変更を書き込む(コミットする)権限を持つ開発者です。コントリビュータは書き込み権限を持たず、修正の提案(パッチやプルリクエスト)をメンテナなどに送ります。メンテナはプロジェクトの管理者です。

### 問13 `LinuC102-1.11-013`

**正解**: A、C

**テキスト**: 4. 参加の方法

よいバグ報告には、使っているバージョンと環境(OS やディストリビューション)、再現する手順、期待した結果と実際の結果を書きます。報告する前に同じ報告がないかを検索し、開発者個人ではなく、決められたバグ管理システムなどに出します。

### 問14 `LinuC102-1.11-014`

**正解**: C

**テキスト**: 2. 開発の体制

バザール方式は、多数の開発者が公開の場で協力して開発する方法で、Linux の開発がその代表です。少数の開発者が閉じた場で開発する方法は、伽藍(がらん)方式と呼ばれます。

### 問15 `LinuC102-1.11-015`

**正解**: A

**テキスト**: 2. 開発の体制

アップストリームは、ソフトウェアの開発元のことです。ディストリビューションなどで見つけたバグの修正は、アップストリームに送って取り込んでもらうと、すべての利用者の役に立ちます。

### 問16 `LinuC102-1.11-016`

**正解**: B

**テキスト**: 4. 参加の方法

開発に参加しなくても、ソフトウェアを使う、他の人に紹介する、バグを報告する、といった小さな関わりも貢献になります。寄付やドキュメントの翻訳なども貢献の方法です。

### 問17 `LinuC102-1.11-017`

**正解**: B

**テキスト**: 3. コミュニティで使われる道具

メーリングリストは、議論や告知、パッチの投稿に使われ、過去のやり取りが公開アーカイブとして残り、検索できます。チャットはその場での相談、Wiki は手順や仕様の共有、バグ管理システムは不具合や要望の追跡に使われます。

### 問18 `LinuC102-1.11-018`

**正解**: A

**テキスト**: 2. オープンソースの特徴

オープンソースのソフトウェアは、コミュニティによって改良が続けられます。ただし無保証で、開発者がいなくなって開発が止まることもあります。採用するときは、開発が活発に続いているかも確認します。
