## 解答・解説

### 問1 `Terraform-1.0-001`

**正解**: B

IaC は、インフラをコードで定義し、そのコードを実行して作る方法です。コードはテキストなので、Git で管理し、レビューし、同じものを何度でも作れます。構成図や手順書、操作の録画は、インフラを作る手段ではありません。

### 問2 `Terraform-1.0-002`

**正解**: B

Terraform は宣言的なツールで、「最終的にこうなっていてほしい」というあるべき状態を書きます。今の状態との差分を計算し、何をすればよいかは Terraform が決めます。実行するコマンドを順番に書くのは手続き的な方式(シェルスクリプトなど)です。

### 問3 `Terraform-1.0-003`

**正解**: C

宣言的なツールなので、あるべき状態(3 台)と今の状態(5 台)を比べ、差の 2 台を削除します。
8 台にすると考えるのは、設定を「3 台を追加する」という手順だと読んだ誤りです。Terraform は台数を減らすこともでき、差分だけを変えるので、全部を作り直すこともありません。

### 問4 `Terraform-1.0-004`

**正解**: A

Terraform の設定は HCL で `.tf` ファイルに書きます。プログラムで生成しやすいように、同じ内容を JSON(`.tf.json`)で書くこともできます。YAML、Python、PowerShell は Terraform の設定の言語ではありません。

### 問5 `Terraform-1.0-005`

**正解**: C

Terraform は、サーバー、ネットワーク、データベースなどのインフラそのものを作るのが得意です。サーバーの中の OS のパッケージや設定ファイルは、Ansible などの構成管理ツールで整えるのが一般的で、両方を組み合わせて使えます。

### 問6 `Terraform-1.0-006`

**正解**: A、E

IaC では同じコードから同じ構成の環境を何度でも作れ、変更を Git などで管理して履歴を残せます。費用がなくなったり、クラウドの障害が防げたりするわけではありません。管理画面での手作業の変更も自動では禁止されないので、運用のルールが必要です。

### 問7 `Terraform-1.0-007`

**正解**: D

`terraform plan` は、設定と state と実際のインフラを比べ、実行したら何が作られ(`+`)、何が変わり(`~`)、何が削除されるか(`-`)を表示します。インフラは変更しません。`fmt` は書式の整形、`version` はバージョンの表示、`login` は HCP Terraform へのログインです。

### 問8 `Terraform-1.0-008`

**正解**: B

同じ操作を何度実行しても結果が同じになる性質を冪等性と呼びます。設定と実際のインフラが一致していれば、Terraform は「No changes」と表示し、何も変更しません。

推移性は「A と B、B と C が成り立てば A と C も成り立つ」性質です。機密性と可用性は情報セキュリティの要素(許可した人だけが見られる、使いたいときに使える)で、繰り返しの実行とは関係ありません。

### 問9 `Terraform-1.0-009`

**正解**: C

Terraform の外での変更は、コードにも state にも反映されません。コードと実際のインフラがずれた状態をドリフトと呼び、次の `apply` で、手作業の変更が設定の内容に戻されるなど、意図しない変更が起きるおそれがあります。Terraform がコードを自動で書き換えたり、管理画面をロックしたりすることはありません。

### 問10 `Terraform-1.0-010`

**正解**: B

作った後のサーバーに手を加えず、変更が必要なら新しいものを作って入れ替える考え方を、イミュータブル(変更不可能な)インフラと呼びます。環境ごとの状態のずれを防げます。作った後に手を加え続けるのはミュータブルなインフラで、その結果、1台ずつ構成が違ってしまったサーバーをスノーフレークサーバーと呼びます。

### 問11 `Terraform-1.0-011`

**正解**: A

Terraform 本体は、サービスごとのプロバイダー(プラグイン)を通して各サービスの API を呼び出します。`terraform init` で必要なプロバイダーをダウンロードします。本体にすべての API を組み込んでいるわけではなく、各クラウドの CLI や管理画面を操作しているわけでもありません。

### 問12 `Terraform-1.0-012`

**正解**: C

どのプロバイダーを使っても、HCL という同じ言語と、`init` → `plan` → `apply` という同じワークフローで管理できます。クラウドごとに専用のツールを覚え分ける必要がありません。リソースの種類と引数はクラウドごとに違うので、設定がそのまま使えたり、違いが自動で吸収されたりはしません。料金の自動の切り替えもありません。

### 問13 `Terraform-1.0-013`

**正解**: D

共通なのは言語とワークフローで、リソースの種類(`aws_instance`、`azurerm_linux_virtual_machine` など)と引数はプロバイダーごとに違います。別のクラウドに移すには、そのクラウドのリソースで書き直す必要があります。Terraform は Azure にも `azurerm` プロバイダーで対応しています。

### 問14 `Terraform-1.0-014`

**正解**: B

Terraform は、vSphere のようなオンプレミス向けのプロバイダーと、AWS などのクラウドのプロバイダーを、同じ設定の中で一緒に使えます。これにより、ハイブリッドクラウドを同じ方法で管理できます。クラウドへの移行や、特定の製品は必要ありません。

### 問15 `Terraform-1.0-015`

**正解**: A、B

Terraform は、API があるものならプロバイダーを通して管理できます。GitHub のリポジトリやチーム(`integrations/github`)、DNS のレコード(Route 53、Cloudflare など)も対象です。API のない機器、パソコンの中のファイルの内容、人の手順書は管理できません。
