## 解答・解説

### 問1 `Docker-2.0-001`

**正解**: B

**テキスト**: 2. 主な命令

`EXPOSE` は、コンテナが待ち受けるポートを示す説明で、それだけではホストに公開されません。ホストからつなぐには、`docker run -p 8000:8000` のように公開します。80 番に自動で公開されることも、エラーになることもありません。

### 問2 `Docker-2.0-002`

**正解**: A

**テキスト**: 4. CMD と ENTRYPOINT

ENTRYPOINT と CMD を両方書くと、ENTRYPOINT がコマンド、CMD が既定の引数になります。
① 引数なしなら `ping -c 3 localhost` です。
② `docker run` に引数 `example.com` を渡すと、**CMD だけが置き換わります**。
③ そのため `ping -c 3 example.com` です。

ENTRYPOINT ごと置き換わると考えるのは CMD だけの場合との混同で、引数が後ろに足されると考えるのは CMD が残ると誤解したものです。

### 問3 `Docker-2.0-003`

**正解**: D

**テキスト**: 4. CMD と ENTRYPOINT

ENTRYPOINT がないイメージで `docker run` に引数を渡すと、その引数が CMD を**置き換えます**。そのため `echo hello` が実行されます。引数が CMD の後ろに足されるのは、ENTRYPOINT がある場合の動きです。

### 問4 `Docker-2.0-004`

**正解**: C

**テキスト**: 4. CMD と ENTRYPOINT

`CMD` を複数書くと、最後の 1 つだけが有効になります(`ENTRYPOINT` も同じ)。順番に全部が実行されることはなく、ビルドもエラーにはなりません。複数のコマンドを動かしたいなら、スクリプトにまとめます。

### 問5 `Docker-2.0-005`

**正解**: C

**テキスト**: 3. exec 形式と shell 形式

shell 形式の CMD は `/bin/sh -c` で起動されるので、PID 1 はシェルになります。`docker stop` が送る SIGTERM をシェルが受け取ってもアプリに届かず、10 秒の待ち時間の後に SIGKILL で強制終了されます。exec 形式にすると、アプリが PID 1 になり、SIGTERM を受け取れます。

### 問6 `Docker-2.0-006`

**正解**: B

**テキスト**: 2. 主な命令

`ARG` はビルドのときだけ使える変数で、`--build-arg` で値を渡します。実行中のコンテナには環境変数として残りません。`ENV` はビルド中と実行中の両方で使える環境変数です。ただし、`ARG` の値も `docker history` に残ることがあるので、秘密の値には使いません。

### 問7 `Docker-2.0-007`

**正解**: A

**テキスト**: 2. 主な命令

ローカルのファイルのコピーには `COPY` を使うのが推奨です。`ADD` は URL からの取得や tar の自動展開もするため、意図しない動きを避けるため必要なときだけ使います。`RUN cp` ではビルドコンテキストのファイルを扱えません。

### 問8 `Docker-2.0-008`

**正解**: A

**テキスト**: 2. ビルドキャッシュ

ビルドキャッシュは、ある層が変わるとそれより後の層もすべて作り直しになります。
① 今は `COPY . .` でソースコードを全部コピーしているので、1 行変えるとこの層が変わります。
② その後の `pip install` もやり直しになります。
③ 変わりにくい `requirements.txt` だけを先に COPY して `pip install` すると、ソースコードを変えても `pip install` の層はキャッシュを使えます。

`--no-cache` はキャッシュを使わないので、さらに遅くなります。

### 問9 `Docker-2.0-009`

**正解**: D

**テキスト**: 1. レイヤー

イメージは層を重ねたものなので、前の `RUN` で入ったファイルは、後の `RUN` で削除しても前の層に残ります。後の層では「削除した」という記録が増えるだけです。インストールと削除は、同じ `RUN` の中で `&&` でつないで行います。

### 問10 `Docker-2.0-010`

**正解**: D

**テキスト**: 2. ビルドキャッシュ

ある命令のキャッシュが使えなくなると、それより後の命令はすべて作り直しになります。`COPY` は、コピーするファイルの中身が変わるとキャッシュが使えなくなります。キャッシュはビルドのときのもので、`docker run` では使いません。

### 問11 `Docker-2.0-011`

**正解**: A、C

**テキスト**: 4. .dockerignore

`.dockerignore` に書いたファイルはビルドコンテキストから除かれます。デーモンに送るファイルが減ってビルドが速くなり、`.env` や秘密鍵が `COPY . .` で誤ってイメージに入るのも防げます。コンテナの実行の速さや、Git のリポジトリそのものには影響しません。

### 問12 `Docker-2.0-012`

**正解**: D

**テキスト**: 1. レイヤー

`docker history` は、イメージの各層を作った命令と、その層の大きさを表示します。`docker logs` はコンテナのログ、`docker diff` はコンテナの書き込み層の変更、`docker top` はコンテナの中のプロセスです。

### 問13 `Docker-2.0-013`

**正解**: D

**テキスト**: 1. マルチステージビルド

マルチステージビルドでは、最後の段階だけが最終のイメージになります。
① 1 つ目の段階 `build` で、Go のコンパイラを使ってバイナリを作ります。
② 2 つ目の段階は distroless から始まり、`COPY --from=build` でバイナリだけをコピーします。
③ 最終のイメージには、distroless とバイナリだけが入ります。

コンパイラやソースコードは最終のイメージに入りません。`COPY --from` は、同じ Dockerfile の段階の名前にも使えます。

### 問14 `Docker-2.0-014`

**正解**: D

**テキスト**: 1. マルチステージビルド

`docker build --target 段階の名前` で、その段階までをビルドできます。テスト用の段階や、開発用の段階を作るときに使います。`--stage` や `--from` というビルドのオプションはなく、`-f` は Dockerfile のパスの指定です。

### 問15 `Docker-2.0-015`

**正解**: B、E

**テキスト**: 2. ベースイメージの選び方

小さいベースイメージは、転送と起動が速く、入っているソフトウェアが少ないので、脆弱性の数も減ります。互換性の問題がなくなるわけではなく(alpine の musl など)、CPU の性能やログの量は変わりません。

### 問16 `Docker-2.0-016`

**正解**: C

**テキスト**: 2. ベースイメージの選び方

distroless は、シェルやパッケージマネージャーを含まず、アプリの実行に必要なものだけを入れたイメージです。攻撃に使える道具が少なく、安全です。`-slim` は Debian から不要なものを減らしたもので、シェルなどは含みます。

### 問17 `Docker-2.0-017`

**正解**: B

**テキスト**: 2. ベースイメージの選び方

alpine は、C ライブラリに一般的な glibc ではなく musl を使っています。glibc を前提にしたバイナリや一部のライブラリは、正しく動かないことがあります。その場合は `-slim` などの Debian ベースのイメージを使います。alpine にはシェル(sh)があり、64 ビットとネットワークにも対応しています。

### 問18 `Docker-2.0-018`

**正解**: A

**テキスト**: 1. docker build の主なオプション

最後の引数はビルドコンテキストです。このディレクトリの中身が Docker デーモンに送られ、Dockerfile の `COPY` で使えます。イメージの名前は `-t` で付け、作られたイメージはデーモンのローカルの保存場所に置かれます。

### 問19 `Docker-2.0-019`

**正解**: D

**テキスト**: 2. イメージの名前

レジストリを省略すると Docker Hub(`docker.io`)、公式イメージは名前空間の `library/` が省略されています。タグを省略すると `latest` です。そのため `docker.io/library/nginx:latest` です。

### 問20 `Docker-2.0-020`

**正解**: B

**テキスト**: 2. イメージの名前

`latest` は、タグを省略したときに使われる既定の名前にすぎません。最も新しく push されたものを自動で指すわけではなく、付ける人が付けたイメージを指します。公式イメージ以外にも付けられ、別のイメージに付け替えることもできます。

### 問21 `Docker-2.0-021`

**正解**: D

**テキスト**: 2. イメージの名前

ダイジェストは、イメージの中身から計算したハッシュ値なので、中身が違えば必ず変わります。ダイジェストで指定すれば、確実に同じイメージを使えます。タグは後から付け替えられるので、`1.4` でも中身が変わる可能性があります。

`latest` と `stable` も、`1.4` と同じくタグなので、後から別のイメージに付け替えられます。特に `latest` は、新しいイメージを push するたびに変わります。

### 問22 `Docker-2.0-022`

**正解**: D

**テキスト**: 1. docker build の主なオプション

`docker build --platform linux/amd64` で、ホストと違う CPU アーキテクチャ向けのイメージをビルドできます(複数をまとめて作るなら `docker buildx build --platform linux/amd64,linux/arm64`)。`--arch` というオプションはなく、`--cpus` はコンテナの CPU の量の制限です。

### 問23 `Docker-2.0-023`

**正解**: D

**テキスト**: 2. イメージの名前

`docker tag` は、同じイメージに別の名前を追加するだけで、イメージを複製しません。元の名前も残ります。レジストリに送るには、その後に `docker push` を実行します。

### 問24 `Docker-2.0-024`

**正解**: B

**テキスト**: 1. docker build の主なオプション

`ARG` には、`docker build --build-arg 名前=値` で値を渡します。`-e` と `--env-file` は `docker run` で環境変数を渡すオプションです。`docker run` には `--build-arg` はありません。

### 問25 `Docker-2.0-025`

**正解**: B

**テキスト**: 3. キャッシュのマウントと CI のキャッシュ

`--mount=type=cache` は BuildKit の機能で、`target` のディレクトリを、その `RUN` の間だけキャッシュの置き場所としてマウントします。中身はビルドのキャッシュとしてホストに残り、次のビルドで同じ場所にマウントされます。層のキャッシュが使えないとき(依存関係の一覧が変わったとき)にも、パッケージのダウンロードをやり直さずに済みます。

- A. マウントしたディレクトリはイメージの層に入りません。イメージの大きさは変わりません。
- C. 層のキャッシュの規則は変わりません。前の層や `COPY` したファイルが変われば作り直されます。
- D. `--no-cache` は層のキャッシュを使わないためのオプションで、この書き方とは関係ありません。

### 問26 `Docker-2.0-026`

**正解**: C

**テキスト**: 3. キャッシュのマウントと CI のキャッシュ

ビルドキャッシュは、既定ではビルドしたホストにだけ残ります。`--cache-to` でキャッシュを外に書き出し、次のビルドの `--cache-from` で読み込むと、別のマシンでもキャッシュが使えます。置き場所はレジストリ(`type=registry,ref=…`)のほか、GitHub Actions のキャッシュ(`type=gha`)などがあります。`mode=max` にすると、途中のステージの層もキャッシュに入ります。

- A. 命令をまとめても、キャッシュのないマシンでは結局すべてを実行します。むしろキャッシュの単位が粗くなります。
- B. `--no-cache` はキャッシュを使わないオプションで、逆の効果です。
- D. `latest` はキャッシュとは関係がなく、再現性を下げるだけです。
