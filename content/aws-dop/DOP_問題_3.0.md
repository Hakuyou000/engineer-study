## 解答・解説

### 問1 `DOP-3.0-001`

**正解**: B

AZ の障害に耐えるには、EC2 とデータベースの両方を、複数の AZ に置きます。Auto Scaling グループを 2 つ以上の AZ にまたがらせ、ALB で振り分けます。RDS は Multi-AZ 配置にすると、障害時に自動で切り替わります。

- A. 大きさを上げても、1 つの AZ の障害には耐えられません。バックアップからの復元は、手間と時間がかかります。
- C. 別のリージョンは、AZ の障害には過剰です。手作業のコピーは、データも古くなります。
- D. 手作業の付け替えは、運用の手間が大きく、切り替えも遅くなります。データベースも単一 AZ のままです。

### 問2 `DOP-3.0-002`

**正解**: C

Network Load Balancer のクロスゾーン負荷分散は、既定で無効です。無効のあいだは、各 AZ のロードバランサーのノードが、自分の AZ のターゲットにだけ振り分けます。AZ ごとのターゲット数が違うと、少ない側に負荷が偏ります。有効にすると、すべての AZ のターゲットへ均等に振り分けます。

- A. 登録解除の遅延は、ターゲットを外すときに、処理中のリクエストが終わるまで待つ設定です。偏りは直りません。
- B. ヘルスチェックの間隔は、異常なターゲットを見つける速さを決めます。偏りは直りません。
- D. スティッキーセッションは、同じ利用者を同じターゲットに送ります。偏りを強めることもあります。

### 問3 `DOP-3.0-003`

**正解**: A

Aurora グローバルデータベースは、ストレージのレベルで別のリージョンへ複製します。遅延は通常 1 秒未満です。リージョンの障害のときは、別のリージョンのクラスターを、書き込みができるクラスターに昇格します。

- B. 毎日のスナップショットのコピーでは、失うデータが最大で 1 日分になります。
- C. 1 時間ごとの差分の複製では、複製の遅れが小さくなりません。
- D. 同じリージョンのレプリカは、リージョン全体の障害に耐えられません。

### 問4 `DOP-3.0-004`

**正解**: A、C

クロスリージョンレプリケーションは、複製元と複製先の両方のバケットで、バージョニングが必要です。また、S3 が複製のためにオブジェクトを読み書きするので、S3 が引き受ける IAM ロールを用意します。

- B. バケットの名前は、全世界で一意です。同じ名前にはできません。
- D. Object Lock は、複製の必須条件ではありません。
- E. 複製先をパブリックにする必要はありません。むしろ、パブリックアクセスはブロックしておきます。

### 問5 `DOP-3.0-005`

**正解**: D

グローバルテーブルの既定(マルチリージョン結果整合)では、同じ項目が複数のリージョンで同時に更新されると、項目ごとに、内部のタイムスタンプが最も新しい更新が選ばれます。すべてのレプリカが、最終的に、その内容に収束します。

- A. 属性ごとのマージは行われません。項目ごとに、最後の書き込みが残ります。
- B. 書き込みは、どのリージョンでも成功します。先の書き込みを守る動きにはなりません。
- C. 競合しても、項目は削除されません。最後の書き込みが残ります。

なお、作成時に選ぶマルチリージョン強整合(MRSC)では、別のリージョンで更新中の項目への書き込みは、エラーになります。このモードは、作成後に変更できません。

### 問6 `DOP-3.0-006`

**正解**: B

CloudFront のオリジングループは、プライマリのオリジンが、指定した HTTP のステータスコード(5xx など)を返したときに、セカンダリのオリジンへ自動で切り替えます。設定だけで済みます。

- A. Lambda@Edge で書き換える方法は、コードの作成と保守が必要です。運用の手間が増えます。
- C. 加重ルーティングは、正常なほうだけを返すヘルスチェックなしでは、障害時に半分のリクエストが失敗します。そもそも CloudFront のオリジンの切り替えではありません。
- D. レプリケーションは、データを複製するだけです。オリジンが失敗したときに、配信元を切り替える機能ではありません。

### 問7 `DOP-3.0-007`

**正解**: C

フェイルオーバールーティングは、プライマリが正常なあいだは、プライマリを返します。プライマリに関連付けたヘルスチェックが失敗すると、セカンダリを返します。

- A. ヘルスチェックがないと、異常なリージョンを外せません。レイテンシーが小さいほうへ向けるだけです。
- B. ヘルスチェックがないと、異常なほうにも半分のリクエストが向かいます。
- D. 手作業の書き換えは、自動の切り替えではありません。

### 問8 `DOP-3.0-008`

**正解**: D

キューのメッセージ数だけを目標にすると、稼働中の台数を考えないので、キューが減る間も、必要以上に台数を増やします。1 台あたりの滞留数にすると、台数に比例した指標になります。目標値は、許容できる遅れ ÷ 1 件の平均処理時間で決めます。メトリクス計算を使うと、カスタム指標を送る費用と手間が要りません。

- A. 目標値を小さくすると、さらに台数が増えやすくなります。台数を考えない点は、変わりません。
- B. キューの長さに固定のしきい値を付けても、台数が考慮されず、増えすぎや不足を防げません。
- C. 最小と最大を同じにすると、スケーリングしなくなります。負荷に合わせた増減になりません。

### 問9 `DOP-3.0-009`

**正解**: A

負荷が増える時刻が決まっていて、準備に時間がかかるなら、スケジュールスケーリングで、先に台数を増やします。指標に反応する方式は、負荷が増えてから動くので、8 分の準備の間は、足りない状態が続きます。

- B. ターゲット追跡は、CPU が上がってから増やします。インスタンスが使えるまでの 8 分間は、不足したままです。
- C. クールダウンを長くすると、増やす動作が、さらに遅くなります。
- D. 最大台数を上げても、増やす時刻は変わりません。

### 問10 `DOP-3.0-010`

**正解**: C

予約された同時実行を設定すると、その関数のために、その数の同時実行が確保されます。ほかの関数に使い切られません。同時に、その関数が使える上限にもなります。

- A. メモリを増やしても、同時実行の枠は確保できません。
- B. タイムアウトを延ばすと、1 回の実行が長くなり、枠を使う時間が増えます。
- D. デッドレターキューは、失敗した非同期呼び出しの保存先です。スロットリングは防げません。

### 問11 `DOP-3.0-011`

**正解**: A、D

Auto Scaling グループを ECS のキャパシティプロバイダーにし、マネージドスケーリングを有効にすると、ECS がタスクの数に合わせて、グループの台数を増減します。起動待ちのタスクがあれば、インスタンスが増えます。
