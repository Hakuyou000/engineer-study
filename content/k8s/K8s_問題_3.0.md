## 解答・解説

### 問1 `K8s-3.0-001`

**正解**: D

**テキスト**: 1. Kubernetes のネットワークのモデル〔CKA〕

Kubernetes のネットワークのモデルでは、すべての Pod が NAT なしで、ほかの Pod と Pod の IP アドレスで通信できることが求められます。これを実現するのが CNI プラグインです。Pod の IP アドレスは作り直すと変わるので、安定した宛先には Service を使います。同じ Pod のコンテナは IP アドレスを共有します。

### 問2 `K8s-3.0-002`

**正解**: A

**テキスト**: 1. Kubernetes のネットワークのモデル〔CKA〕

同じ Pod のコンテナは、ネットワークの名前空間(IP アドレスとポート)を共有しているので、`localhost` で通信できます。そのため、同じ Pod の中で同じポートを 2 つのコンテナが使うことはできません。

### 問3 `K8s-3.0-003`

**正解**: D

**テキスト**: 1. Kubernetes のネットワークのモデル〔CKA〕

CNI プラグイン(Calico、Cilium、Flannel など)が、Pod のネットワークのインターフェースを作り、IP アドレスを割り当て、ノードをまたぐ経路を作ります。CoreDNS は名前の解決、CSI はストレージです。

### 問4 `K8s-3.0-004`

**正解**: C

**テキスト**: 1. Service が必要な理由〔CKA〕

`kubectl expose` は、Deployment の selector を使って Service を作ります。type の既定は ClusterIP で、クラスタの中からだけ使えます。`--port` は Service のポート、`--target-port` は Pod のポートです。NodePort はノードのポートで外部に公開します。

### 問5 `K8s-3.0-005`

**正解**: A

**テキスト**: 3. エンドポイント〔CKA〕

Service は `selector` に合うラベルの Pod を探し、そのうち Ready の Pod をエンドポイントにします。エンドポイントが空なら、selector とラベルが合っていないか、Pod が Ready でないことが多い原因です。`kubectl get pods --show-labels` でラベルを確かめます。

### 問6 `K8s-3.0-006`

**正解**: D

**テキスト**: 1. Service が必要な理由〔CKA〕

NodePort の Service は、すべてのノードの `nodePort`(30080)で受け、Pod の `targetPort`(8080)に届けます。
① クラスタの外 → ノードの IP:30080
② クラスタの中 → ClusterIP:80(`port`)
③ どちらも Pod の 8080 に届きます。

NodePort の範囲は既定で 30000〜32767 で、80 は使えません。

### 問7 `K8s-3.0-007`

**正解**: A、E

**テキスト**: 2. Service の種類〔CKA〕

ClusterIP はクラスタの中だけで使える仮想の IP アドレス、LoadBalancer はクラウドのロードバランサーを作って外部に公開します。NodePort はノードのポートで公開するもので、Pod の IP アドレスを公開するものではありません。外部の DNS 名を返すのは ExternalName です。

### 問8 `K8s-3.0-008`

**正解**: C

**テキスト**: 1. Service が必要な理由〔CKA〕

`port` は Service(ClusterIP)が受け付けるポート、`targetPort` は届け先の Pod のコンテナのポートです。省略すると `targetPort` は `port` と同じ値になります。ノードのポートは `nodePort` です。

### 問9 `K8s-3.0-009`

**正解**: B

**テキスト**: 2. Service の種類〔CKA〕

`clusterIP: None` のヘッドレスの Service は、仮想の IP アドレスを持たず、DNS で Pod の IP アドレスを直接返します。StatefulSet の `serviceName` にこの Service を指定すると、`Pod名.Service名.Namespace.svc.cluster.local` の名前が作られます。

### 問10 `K8s-3.0-010`

**正解**: A

**テキスト**: 4. よく使うポリシー〔CKA〕

`podSelector: {}` は Namespace のすべての Pod を選び、policyTypes が Ingress で、許可のルールが 1 つもないので、すべての受信が拒否されます。送信(Egress)は policyTypes に入っていないので、そのままです。NetworkPolicy は自分の Namespace の Pod にだけ効きます。

### 問11 `K8s-3.0-011`

**正解**: B

**テキスト**: 1. 基本〔CKA〕

NetworkPolicy を実際に守らせるのは CNI プラグインです。Flannel のように対応していないプラグインだと、NetworkPolicy を作ってもエラーにならず、何も起きません。Calico や Cilium は対応しています。

### 問12 `K8s-3.0-012`

**正解**: B

**テキスト**: 3. from の書き方の違い〔CKA〕

1 つの項目(`-` が 1 つ)の中に `namespaceSelector` と `podSelector` を並べると、両方を満たす(AND)という意味になります。
① Namespace にラベル `team: web` がある
② その中の Pod にラベル `role: frontend` がある
③ 両方を満たす Pod からの受信だけが許可されます。

### 問13 `K8s-3.0-013`

**正解**: A

**テキスト**: 3. from の書き方の違い〔CKA〕

`from` の下で `-` を 2 つに分けると、別々の項目になり、どちらかに合えば許可される(OR)という意味になります。`team: web` の Namespace のすべての Pod と、同じ Namespace の `role: frontend` の Pod が許可され、範囲が広がります。`-` が 1 つあるかないかで意味が変わるので、注意が必要です。

### 問14 `K8s-3.0-014`

**正解**: B

**テキスト**: 4. よく使うポリシー〔CKA〕

送信をすべて拒否すると、DNS の問い合わせ(CoreDNS への 53 番)も拒否されるので、名前を解決できなくなります。送信を拒否するときは、kube-system の CoreDNS への UDP と TCP の 53 番を許可するルールを足します。

- A. Pod の IP アドレスが変わっても、IP アドレスでの通信が通っているので原因ではありません。
- C. kube-proxy が止まると ClusterIP への通信ができなくなりますが、名前の解決の失敗とは別の症状です。
- D. Service がなければ IP アドレスでも Service につながりません。名前だけが失敗するのは DNS の問題です。

### 問15 `K8s-3.0-015`

**正解**: B

**テキスト**: 1. Ingress〔CKA〕

Ingress はルールを書いたリソースで、実際に通信を受けて振り分けるのは Ingress コントローラーです。コントローラーがないと、Ingress を作っても何も起きず、ADDRESS も空のままです。Ingress の後ろの Service は ClusterIP で問題ありません。

### 問16 `K8s-3.0-016`

**正解**: A

**テキスト**: 1. Ingress〔CKA〕

1 つの Ingress の rules に、host とその下の複数の paths を書けます。Prefix の一致では、より長いパス(`/api`)が優先されるので、`/api` は api に、それ以外は web に届きます。

### 問17 `K8s-3.0-017`

**正解**: A

**テキスト**: 2. Gateway API〔CKA〕

Gateway API は役割ごとに部品が分かれています。GatewayClass(どの実装を使うか)はインフラの提供者、Gateway(どのポートとアドレスで受けるか)はクラスタの運用者、HTTPRoute(どのパスをどの Service に送るか)はアプリの開発者が管理します。

### 問18 `K8s-3.0-018`

**正解**: A

**テキスト**: 2. Gateway API〔CKA〕

HTTPRoute の `backendRefs` には複数の Service を書け、`weight` で通信の割合を決めます。90 と 10 なら、9 対 1 に振り分けられます。replicas の比率は、Service の後ろで Pod が混ざる場合のおおよその割合で、正確な割合の制御はできません。

### 問19 `K8s-3.0-019`

**正解**: A

**テキスト**: 3. Ingress NGINX の終了〔実務〕

Kubernetes のプロジェクトは、Ingress NGINX(kubernetes/ingress-nginx)の開発とセキュリティの修正を 2026 年 3 月で終えると発表しました。新しく作るなら、Gateway API の実装(Envoy Gateway、Cilium など)や、ほかの Ingress コントローラーを選びます。Ingress のリソース自体は今も使えます。

### 問20 `K8s-3.0-020`

**正解**: D

**テキスト**: 1. 名前の形〔CKA〕

ほかの Namespace の Service は、`Service名.Namespace名` で引けます(完全な名前は `db.prod.svc.cluster.local`)。`db` だけだと、自分の Namespace(`dev`)の Service を探してしまいます。

### 問21 `K8s-3.0-021`

**正解**: A、E

**テキスト**: 3. 設定と調査〔CKA〕

名前の解決ができないときは、まず CoreDNS の Pod が動いているか、ログにエラーがないかを確かめます。次に Pod の `/etc/resolv.conf` の nameserver が、kube-system の kube-dns の Service の ClusterIP になっているかを確かめます。kube-dns の Service のエンドポイントも確かめるとよいです。

### 問22 `K8s-3.0-022`

CoreDNS の設定(Corefile)は、kube-system の ConfigMap `coredns` にあります。編集すると、CoreDNS が設定を読み直します(reload のプラグイン)。CoreDNS は静的 Pod ではなく Deployment で動いています。

### 問23 `K8s-3.0-023`

**正解**: A

**テキスト**: 2. ndots と名前の問い合わせ〔実務〕

`ndots:5` は、名前のドットが 5 つ未満なら、まず search のドメインを順に付けて問い合わせる、という意味です。そのため `web` は `web.default.svc.cluster.local` として引けます。

その代わり、`api.example.com`(ドット 2 つ)のような外部の名前も、先に search のドメインを付けた問い合わせが何回も行われます。

### 問24 `K8s-3.0-024`

**正解**: D

**テキスト**: 2. ndots と名前の問い合わせ〔実務〕

名前の最後にドットを付けると完全な名前(FQDN)として扱われ、search のドメインを付けた無駄な問い合わせが行われません。Pod の `dnsConfig.options` で ndots を小さく(例: 2)するのも方法です。NodeLocal DNSCache で問い合わせをノードでキャッシュする方法もあります。

### 問25 `K8s-3.0-025`

**正解**: A

**テキスト**: 2. ndots と名前の問い合わせ〔実務〕

`ndots` は、名前を完全な名前として扱うのに必要なドットの数です。Pod の既定は 5 なので、`api.example.com`(ドットが 2 つ)のような外の名前も、まず `api.example.com.default.svc.cluster.local` などの search のドメインを付けて問い合わせます。外の名前を多く引くアプリでは、名前の最後に `.` を付けるか、Pod の `dnsConfig` で `ndots` を小さくすると、余計な問い合わせが減ります。

- B. `timeout` は、1 回の問い合わせの応答を待つ秒数です。
- C. `attempts` は、問い合わせを繰り返す回数です。
- D. `rotate` は、複数の DNS のサーバーを順番に使う設定です。

### 問26 `K8s-3.0-026`

**正解**: `targetPort`

**テキスト**: 1. Service が必要な理由〔CKA〕

`port` は Service の側のポート、`targetPort` は届け先の Pod(コンテナ)のポートです。`targetPort` を省くと `port` と同じ値になります。type が NodePort なら、ノードのポートを `nodePort` で指定します。

### 問27 `K8s-3.0-027`

**正解**: `NodePort`

**テキスト**: 2. Service の種類〔CKA〕

`NodePort` は、すべてのノードの決まったポート(既定の範囲は 30000〜32767)で受け、Service に届けます。`nodePort` を書かなければ自動で選ばれます。クラスタの中からだけなら `ClusterIP`(既定)、クラウドのロードバランサーを作るなら `LoadBalancer` です。

### 問28 `K8s-3.0-028`

**正解**: `{}`、`{ }`

**テキスト**: 4. よく使うポリシー〔CKA〕

空の `podSelector: {}` は、その Namespace のすべての Pod を選びます。`ingress` のルールを 1 つも書かないので、選んだ Pod への受信はすべて拒否されます。この後、必要な通信だけを許可する NetworkPolicy を足します。

### 問29 `K8s-3.0-029`

**正解**: `Prefix`

**テキスト**: 1. Ingress〔CKA〕

`Prefix` は、パスを `/` で区切った単位で前方一致させます(`/api` は `/api` と `/api/v1` に一致し、`/apis` には一致しません)。`Exact` は完全に一致するものだけです。`ImplementationSpecific` は Ingress コントローラーに任せます。
