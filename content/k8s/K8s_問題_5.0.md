## 解答・解説

### 問1 `K8s-5.0-001`

**正解**: A

ノードの状態は kubelet が API サーバーに報告しているので、NotReady のときは、まず kubelet が動いているか、ログにエラーがないかを確かめます。kubelet が止まっていれば `systemctl start kubelet`、設定の誤りならログに表示されます。コンテナランタイム(containerd)の状態も確かめます。

### 問2 `K8s-5.0-002`

**正解**: C

ログの `no such file or directory` は、指定したファイルがないことを表します。CA のファイルのパスが `ca.crtx` と誤っているので、kubelet の設定(`/var/lib/kubelet/config.yaml` の `clientCAFile` など)を `ca.crt` に直します。CA のファイルを読めないと kubelet が起動しません。

### 問3 `K8s-5.0-003`

**正解**: A

kubelet は systemd のサービスで動いているので、設定を変えたら `systemctl daemon-reload`(ユニットのファイルを変えた場合に必要)の後、`systemctl restart kubelet` で再起動します。kubelet の設定ファイルは Kubernetes のリソースではないので、`kubectl apply` は使えません。

### 問4 `K8s-5.0-004`

**正解**: B

MemoryPressure や DiskPressure が True になると、ノードに taint(`node.kubernetes.io/memory-pressure` など)が付き、新しい Pod が置かれにくくなります。資源がしきい値を下回ると、kubelet が優先度の低い Pod から追い出します(BestEffort が先)。

### 問5 `K8s-5.0-005`

**正解**: B

6443 番は kube-apiserver のポートです。接続が拒否されるなら、kube-apiserver が動いていません。kubeadm のクラスタでは静的 Pod なので、kubelet が動いているか、`crictl ps -a` で kube-apiserver のコンテナの状態を、`crictl logs` や `/var/log/pods/` でログを確かめます。YAML の誤りや etcd に接続できないことが多い原因です。

### 問6 `K8s-5.0-006`

**正解**: C

`crictl` は、CRI に対応したコンテナランタイム(containerd など)を直接操作するツールです。API サーバーが止まっていても、`crictl ps -a` でコンテナの一覧、`crictl logs コンテナID` でログを見られます。

### 問7 `K8s-5.0-007`

**正解**: B

Pod には既定で、`node.kubernetes.io/not-ready` と `node.kubernetes.io/unreachable` の taint に対する toleration が、`tolerationSeconds: 300` で付きます。ノードが NotReady になってから 300 秒たつと、Pod が追い出され、ほかのノードで作り直されます。Pod ごとに短くすることもできます。

### 問8 `K8s-5.0-008`

**正解**: A

スケジューラーが CrashLoopBackOff なら、静的 Pod の YAML(`/etc/kubernetes/manifests/kube-scheduler.yaml`)の誤りが多い原因です。コマンドの名前や引数、`--kubeconfig` のパスなどを確かめ、`kubectl logs -n kube-system` や `crictl logs` でエラーを見ます。直して保存すると kubelet が作り直します。

### 問9 `K8s-5.0-009`

**正解**: A

Deployment から ReplicaSet を作り、ReplicaSet から Pod を作るのは、kube-controller-manager の中のコントローラーです。これが止まっていると、Deployment を作っても何も作られません。Pod が作られたのに Pending なら、スケジューラーを疑います。

### 問10 `K8s-5.0-010`

**正解**: A

kube-proxy は、各ノードで iptables や IPVS のルールを作り、Service の ClusterIP への通信を Pod に振り分けます。Pod の IP アドレスに直接つながるのに ClusterIP につながらないなら、kube-proxy(kube-system の DaemonSet)を疑います。Cilium のように kube-proxy の代わりをする CNI もあります。

### 問11 `K8s-5.0-011`

**正解**: B

`kubectl top pod` は、metrics-server から Pod の CPU とメモリの使用量を表示します。`--sort-by=memory` で使用量の多い順に並べられます。`kubectl get` の `--sort-by` は、リソースのフィールドで並べるもので、使用量では並べられません。

### 問12 `K8s-5.0-012`

**正解**: B

`kubectl top` は、metrics-server が提供する Metrics API から値を取ります。metrics-server が入っていない、または動いていないと、このエラーになります。Prometheus は別の監視の仕組みで、`kubectl top` は使いません。

### 問13 `K8s-5.0-013`

**正解**: D

`kubectl describe node` の Allocated resources に、そのノードの Pod の requests と limits の合計と、割り当て可能な量に対する割合が表示されます。スケジューラーは requests の合計で空きを判断するので、Pending の調査に役立ちます。

### 問14 `K8s-5.0-014`

**正解**: A

`kubectl logs --previous`(`-p`)は、再起動する前のコンテナのログを表示します。CrashLoopBackOff では、今のコンテナはすぐ終わってしまうので、前回のログで落ちた原因を確かめます。`--follow`(`-f`)は、ログを流し続けて見るオプションです。

### 問15 `K8s-5.0-015`

**正解**: C

複数のコンテナがある Pod では、`-c コンテナ名` でコンテナを指定します。すべてのコンテナのログをまとめて見るなら `--all-containers` です。

### 問16 `K8s-5.0-016`

**正解**: C

ImagePullBackOff は、イメージの pull に失敗して、待ってから再試行している状態です。イメージの名前やタグの誤り、非公開のレジストリの認証の情報(imagePullSecrets)の不足、ノードからレジストリに届かないことが原因です。`kubectl describe pod` の Events に詳しい理由が出ます。

### 問17 `K8s-5.0-017`

**正解**: D

OOMKilled(終了コード 137)は、コンテナがメモリの limits を超えて強制終了されたことを表します。実際の使用量を `kubectl top` などで確かめ、limits を引き上げるか、アプリのメモリの使用量を減らします。CPU の設定やイメージのタグは関係ありません。

### 問18 `K8s-5.0-018`

**正解**: B

`kubectl get events` で、その Namespace の Event(スケジューリング、pull、probe の失敗など)を一覧できます。`--sort-by=.metadata.creationTimestamp` で時刻の順に並べられます。1 つの Pod の Event は `kubectl describe pod` の最後にも表示されます。

### 問19 `K8s-5.0-019`

**正解**: D

`kubectl debug` は、動いている Pod に一時的なコンテナ(エフェメラルコンテナ)を足して調べられます。`--target` で、調べたいコンテナのプロセスの名前空間を共有できます。シェルのないイメージでは `kubectl exec -- sh` は使えません。

### 問20 `K8s-5.0-020`

**正解**: B

`kubectl logs` で見られるのはノードに残っているログだけで、Pod が削除されたりノードがなくなったりすると消えます。本番では、ログを標準出力に書き、DaemonSet のエージェントで外部の基盤に集めて保存し、検索できるようにします。

### 問21 `K8s-5.0-021`

**正解**: B

Event は API サーバーに保存されますが、保存の期間は短く、既定で 1 時間です(`--event-ttl`)。障害の後の調査のために、Event を外部(ログの基盤など)に集める仕組みを作っておきます。

### 問22 `K8s-5.0-022`

**正解**: C

Service につながらないときは、内側から順に調べます。
① エンドポイントがあるか(selector とラベル、Pod が Ready か)
② `targetPort` がコンテナの待ち受けのポートと合っているか
③ DNS で名前を引けるか
④ NetworkPolicy で拒否されていないか

エンドポイントが空なら、その先を調べても意味がないので、最初に確かめます。

### 問23 `K8s-5.0-023`

**正解**: D

Service は selector で Pod を選ぶので、エンドポイントは作られます。しかし、届け先のポート 80 でコンテナが待ち受けていないので、接続は拒否されます。`targetPort` を 8080 にするか、コンテナの `containerPort` に付けた名前で指定します。

### 問24 `K8s-5.0-024`

**正解**: B

`kubectl run` に `--rm -it --restart=Never` を付けると、一時的な Pod を作って対話し、終わると削除します。`--` の後のコマンドが Pod の中で実行されます。クラスタの中からの DNS と Service の動作を確かめるのに便利です。

### 問25 `K8s-5.0-025`

**正解**: A

`kubectl port-forward svc/web 8080:80` は、手元の 8080 番を、Service の後ろの Pod の 80 番につなぎます。`http://localhost:8080` で接続できます。外部に公開するものではなく、一時的な確認のための方法です。

### 問26 `K8s-5.0-026`

**正解**: C

Egress の NetworkPolicy があると、許可されていない送信はすべて拒否されます。外部の API のアドレス(ipBlock)とポート、そして名前の解決のための DNS(53 番)が許可されているかを確かめます。
