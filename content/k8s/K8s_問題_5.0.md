## 解答・解説

### 問1 `K8s-5.0-001`

**正解**: A

ノードの状態は kubelet が API サーバーに報告しているので、NotReady のときは、まず kubelet が動いているか、ログにエラーがないかを確かめます。kubelet が止まっていれば `systemctl start kubelet`、設定の誤りならログに表示されます。コンテナランタイム(containerd)の状態も確かめます。

- B. ノード 1 台の NotReady のために、クラスタ全体のデータを戻すのは過剰で、ほかの変更も失われます。
- C. CoreDNS は名前の解決をする Pod で、ノードの Ready の報告には関わりません。
- D. ノードを消すと、原因が分からないまま、そのノードの情報も失われます。

### 問2 `K8s-5.0-002`

**正解**: C

ログの `no such file or directory` は、指定したファイルがないことを表します。CA のファイルのパスが `ca.crtx` と誤っているので、kubelet の設定(`/var/lib/kubelet/config.yaml` の `clientCAFile` など)を `ca.crt` に直します。CA のファイルを読めないと kubelet が起動しません。

- A. メモリ不足では、ファイルがないというエラーにはなりません。`MemoryPressure` として現れます。
- B. CNI がないときはノードが NotReady になりますが、kubelet そのものは起動します。
- D. Pod の数が多くても、kubelet の起動のときに CA のファイルのエラーは出ません。

### 問3 `K8s-5.0-003`

**正解**: A

kubelet は systemd のサービスで動いているので、設定を変えたら `systemctl daemon-reload`(ユニットのファイルを変えた場合に必要)の後、`systemctl restart kubelet` で再起動します。kubelet の設定ファイルは Kubernetes のリソースではないので、`kubectl apply` は使えません。

### 問4 `K8s-5.0-004`

**正解**: B

MemoryPressure や DiskPressure が True になると、ノードに taint(`node.kubernetes.io/memory-pressure` など)が付き、新しい Pod が置かれにくくなります。資源がしきい値を下回ると、kubelet が優先度の低い Pod から追い出します(BestEffort が先)。

### 問5 `K8s-5.0-005`

**正解**: B

6443 番は kube-apiserver のポートです。接続が拒否されるなら、kube-apiserver が動いていません。kubeadm のクラスタでは静的 Pod なので、kubelet が動いているか、`crictl ps -a` で kube-apiserver のコンテナの状態を、`crictl logs` や `/var/log/pods/` でログを確かめます。YAML の誤りや etcd に接続できないことが多い原因です。

- A. Ingress コントローラーはアプリへの通信の入口で、kubectl の接続先(6443 番)ではありません。
- C. HPA は Pod の数を変える仕組みで、API サーバーの起動には関わりません。
