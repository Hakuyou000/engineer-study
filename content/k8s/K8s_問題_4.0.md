# K8s 問題 4.0 ストレージ

## 問題

### 4.2 PV と PVC

```yaml
  name: pv-data
spec:
  capacity:
    storage: 5Gi
  accessModes: [ReadWriteOnce]
  storageClassName: manual
  hostPath:
    path: /data
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-data
spec:
  accessModes: [ReadWriteOnce]
  storageClassName: manual
  resources:
    requests:
      storage: 10Gi
```

- B. storageClassName が同じである

## 解答・解説

### 問1 `K8s-4.0-001`

**正解**: D

emptyDir は Pod が作られたときに空で作られ、Pod のすべてのコンテナから使え、Pod が削除されると消えます。コンテナの間の一時的なファイルの共有やキャッシュに向いています。データを残したいなら PVC を使います。

### 問2 `K8s-4.0-002`

**正解**: A

ReadWriteOnce は、1 つのノードから読み書きでマウントできるモードです。同じノードにある複数の Pod からは使えます。1 つの Pod だけに限定したい場合は ReadWriteOncePod を使います。

### 問3 `K8s-4.0-003`

**正解**: A

ReadWriteMany(RWX)は、複数のノードから同時に読み書きでマウントできるモードです。NFS や Amazon EFS のようなファイルのストレージが対応しています。ブロックのストレージ(Amazon EBS など)は、ふつう RWO だけです。

### 問4 `K8s-4.0-004`

**正解**: C

hostPath は、Pod の置かれたノードのパスをマウントします。Pod が別のノードに移ると、別のデータを見ることになります。ノードのファイルに触れるので、セキュリティの危険もあり、Pod Security の baseline でも禁止されています。

### 問5 `K8s-4.0-005`

**正解**: B

reclaimPolicy が Delete なら、PVC を削除すると PV も、その後ろのストレージも削除されます。動的プロビジョニングで作られた PV の既定は、ふつう Delete です。データを残したいなら Retain にします。

### 問6 `K8s-4.0-006`

**正解**: C

Retain では、PVC を削除しても PV とデータが残り、PV は Released になります。前のデータが残っているので、そのままでは別の PVC に結び付きません。管理者がデータを整理し、PV を作り直す(または `claimRef` を消す)必要があります。

### 問7 `K8s-4.0-007`

**正解**: D

PVC は、容量、アクセスモード、storageClassName などの条件を満たす PV にだけ結び付きます。
① storageClassName は両方 manual で一致しています。
② accessModes も一致しています。
③ PVC の要求 10Gi が PV の 5Gi より大きいので、条件を満たさず Pending のままです。

### 問8 `K8s-4.0-008`

**正解**: C

PVC は、要求以上の容量の PV に結び付き、結び付くと PV の全体(10Gi)を使います。PV を分割して残りを別の PVC に使うことはできません。

### 問9 `K8s-4.0-009`

**正解**: D

Pod の `spec.volumes` で、ボリュームの名前と `persistentVolumeClaim.claimName` を書き、コンテナの `volumeMounts` で、そのボリュームの名前と `mountPath` を指定します。2 か所に書く必要があります。

### 問10 `K8s-4.0-010`

**正解**: C、E

PV はクラスタ全体のリソースで、Namespace に属しません。PVC は Namespace に属し、同じ Namespace の Pod から使います。PV と PVC は 1 対 1 で結び付くので、1 つの PV を 2 つの PVC で使うことはできません。

### 問11 `K8s-4.0-011`

**正解**: A

`FailedAttachVolume` や `FailedMount` は、ボリュームをノードに接続(アタッチ)やマウントできていないことを表します。RWO のボリュームが別のノードの Pod でまだ使われている、ゾーンが合わない、CSI ドライバーの不具合などが原因です。イメージの誤りなら ImagePullBackOff になります。

### 問12 `K8s-4.0-012`

**正解**: C

動的プロビジョニングでは、PVC に StorageClass を指定すると、プロビジョナー(CSI ドライバー)が自動でストレージと PV を作ります。管理者が先に PV を作っておく方法が、静的プロビジョニングです。

### 問13 `K8s-4.0-013`

**正解**: A

`storageClassName` を書かないと、既定の StorageClass(アノテーション `storageclass.kubernetes.io/is-default-class: "true"`)が使われます。既定がない場合は、StorageClass を持たない PV にだけ結び付きます。`storageClassName: ""` と空を明示すると、既定は使われません。

### 問14 `K8s-4.0-014`

**正解**: D

WaitForFirstConsumer では、PVC を使う Pod が作られ、ノードが決まってから PV を作ります。ブロックのストレージは 1 つのゾーンにしか接続できないので、Pod と同じゾーンにディスクを作れます。Immediate(既定)だと、Pod と違うゾーンにディスクが作られることがあります。

### 問15 `K8s-4.0-015`

**正解**: C

PVC の容量は、StorageClass に `allowVolumeExpansion: true` があり、ドライバーが対応していれば、`spec.resources.requests.storage` を増やして拡張できます。容量を減らすことはできません。

### 問16 `K8s-4.0-016`

**正解**: B

CSI(Container Storage Interface)は、ストレージの製品を Kubernetes につなぐための標準のインターフェースです。各社が CSI ドライバーを提供します。CNI はネットワーク、CRI はコンテナランタイムです。

### 問17 `K8s-4.0-017`

**正解**: D

VolumeSnapshot は、CSI ドライバーの機能で、PVC のスナップショットを取る仕組みです。VolumeSnapshotClass を用意し、VolumeSnapshot を作ります。スナップショットから新しい PVC を作って復元できます。CRD と snapshot-controller が必要です。

### 問18 `K8s-4.0-018`

**正解**: C

StatefulSet を削除したり Pod を減らしたりしても、`volumeClaimTemplates` で作られた PVC は既定で残ります。データを誤って失わないための動作です。`persistentVolumeClaimRetentionPolicy` で、削除のときにも一緒に消すように変えられます。
