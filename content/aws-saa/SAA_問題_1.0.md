## 解答・解説

| 問 | 正解 | 解説 |
|---|---|---|
| 1 | B | EC2 は「仮想サーバーを借りる」サービスなので、その中の OS やソフトウェアの更新は利用者の仕事です。データセンターの入退室、物理ホストの交換、ハイパーバイザーの保守は、AWS が担当する「クラウドそのもの」のセキュリティです。 |
| 2 | C | RDS はマネージドサービスなので、OS とデータベースエンジンのパッチは AWS が適用します。データベースのユーザー権限、セキュリティグループ、暗号化を有効にするかどうかは、利用者が決めて設定するものです。 |
| 3 | C | ルートユーザーはすべての権限を持ち、制限できません。そのため MFA で守り、普段は使わないのが基本です。ルートのアクセスキーは作らないことが推奨され、パスワードの共有は誰が操作したか分からなくなります。ルートユーザーはアカウントそのものなので削除できません。 |
| 4 | A | IAM ロールを EC2 に付けると、アプリは自動で更新される一時的な認証情報を使えます。設定ファイルや環境変数にアクセスキーを書くと、漏えいの危険があり、ルートのキーはなおさら危険です。バケットを公開すると誰でも読めてしまいます。 |
| 5 | B | IAM の評価の順序に当てはめます。<br>① まず、リクエストに一致する明示的な拒否(Deny)があるかを調べます。ユーザー自身のポリシーに `s3:DeleteObject` の Deny があり、削除の操作に一致します。<br>② 明示的な拒否が 1 つでもあれば、その時点で拒否が確定します。<br>③ グループの `s3:*` の Allow は、拒否が確定した後なので使われません。<br>④ そのため削除できません。<br>グループのポリシーが優先されると考えるのは、付け先(グループかユーザーか)で優先順位が決まると誤解したものです。付けた順番も関係ありません。矛盾しても無効にはならず、拒否が勝ちます。 |
| 6 | C | アクセス許可の境界は、ユーザーやロールが持てる権限の上限を決める機能です。開発者が作るロールに境界を必ず付けさせると、強すぎる権限を作れなくなります。SCP はアカウント全体の上限、バケットポリシーは S3 の権限、パスワードポリシーはパスワードの規則で、目的が違います。 |
| 7 | D | SCP は組織の管理アカウント側で設定し、メンバーアカウントの管理者(ルートユーザーを含む)も変更や回避ができません。各アカウントの IAM ポリシーは、そのアカウントの管理者が外せてしまいます。Config と Budgets は検出や通知だけで、使用そのものは止められません。 |
| 8 | B | SCP は「このアカウントでできることの上限」を決めるだけで、実際に操作するには IAM ポリシーでの許可も必要です。SCP は管理アカウントには効かず、メンバーアカウントではルートユーザーにも効きます。 |
| 9 | A | IAM Identity Center は、Organizations の複数アカウントへのシングルサインオンを一元管理するサービスで、外部の SAML 2.0 の ID 基盤と接続できます。アカウントごとの IAM ユーザーは管理が大変で、同じパスワードやルートの共有は危険です。Cognito は自社のアプリの利用者向けで、社員の AWS ログイン用ではありません。 |
| 10 | B | クロスアカウントロールを使うと、A 社は STS から一時的な認証情報を受け取って B 社のテーブルを読めます。アクセスキーの受け渡しは長期的な認証情報で、漏えいの危険があります。テーブルの公開やアカウントの統合は、要件に対して大げさで危険です。 |
| 11 | C | 外部 ID は、業者と顧客の間だけで決めた合言葉のような値です。信頼ポリシーで外部 ID の一致を条件にすると、他の顧客が業者を通して自社のロールを引き受けることを防げます。IP、MFA、時刻の条件は、この問題を直接は防げません。 |
| 12 | A | AD Connector は、AWS からオンプレミスの AD へ認証を中継するプロキシです。ディレクトリのデータを AWS に置かずに、既存のユーザーで認証できます。Simple AD は独立した簡易ディレクトリで、既存の AD とはつながりません。Cognito ID プールはアプリ利用者向け、新しい Managed AD に手作業で登録するのは二重管理になります。 |
| 13 | B | Control Tower は、Organizations、IAM Identity Center、CloudTrail、Config などを組み合わせたランディングゾーンを自動で作り、Account Factory で統制の取れたアカウントを作れます。Service Catalog や Config だけでは環境全体は作れず、手作業のテンプレート実行は手間と設定ミスが増えます。 |
| 14 | D | RAM を使うと、VPC のサブネットを他のアカウントと共有でき(共有 VPC)、各アカウントはそのサブネットに自分のリソースを作れます。ピアリングと Transit Gateway は別々の VPC をつなぐ方法で、PrivateLink は特定のサービスを公開する方法です。 |
| 15 | `AssumeRole`、`sts:AssumeRole` | `AssumeRole` を呼ぶと、ロールの信頼ポリシーで許可されていれば、アクセスキー、シークレットキー、セッショントークンからなる一時的な認証情報が返ります。有効期限があるため、漏れても被害を小さくできます。 |
| 16 | B | DB をプライベートサブネットに置くと、インターネットから直接届きません。さらに送信元にアプリの SG を指定すると、アプリサーバーからの接続だけを許可できます。0.0.0.0/0 からの許可やパブリック IP は、インターネットに DB をさらします。NACL で全許可しても、接続元を絞る役には立ちません。 |
| 17 | C | NAT ゲートウェイは、プライベートサブネットからインターネットへ「出ていく」通信だけを中継し、外からの接続は受け付けません。IGW への経路を持つとパブリックサブネットになり、Elastic IP を付けると外から直接届くようになります。Egress-Only インターネットゲートウェイは IPv6 専用です。 |
| 18 | A | SG はステートフルなので、許可した通信の戻りは自動で通ります。ルールは許可だけで、拒否は書けません。NACL はサブネット単位でステートレスなので、戻りの通信も許可が必要で、拒否ルールを書けます。 |
| 19 | B | NACL は拒否ルールを書け、番号の小さい順に評価されます。許可ルールより前に拒否ルールを置けば、その範囲を遮断できます。SG には拒否ルールがありません。IGW への経路を消すと、正常な利用者も含めてすべて止まります。IAM ポリシーはネットワークの通信を止めるものではありません。 |
| 20 | D | 往路と復路のパケットを分けて考えます。<br>① 往路:クライアント(例: ポート 50000)→ サーバーのポート 443。インバウンドの 443 の許可で通ります。<br>② 復路:サーバーのポート 443 → クライアントのポート 50000。あて先ポートは、クライアントが一時的に選んだエフェメラルポートです。<br>③ NACL はステートレスなので、往路を許可しても復路は自動で許可されません。アウトバウンドのルールで、あて先ポートが 50000 の通信を許可する必要があります。<br>④ クライアントが選ぶポートは決まっていないので、エフェメラルポートの範囲(例: 1024〜65535)を許可します。<br>アウトバウンドの 443 だけを許可するのは、復路のあて先ポートも 443 だと考えた誤りです(443 は送信元ポートです)。戻りの通信が自動で許可されるのは、ステートフルなセキュリティグループの場合です。22 番は SSH で無関係です。 |
| 21 | A | Secrets Manager は秘密情報を暗号化して保存し、RDS と連携した自動ローテーションができます。Parameter Store には組み込みのローテーション機能がありません。S3 のファイルやユーザーデータは、秘密情報の管理やローテーションの仕組みを自分で作る必要があり、漏えいもしやすくなります。 |
| 22 | C | S3 のゲートウェイエンドポイントは無料で、ルートテーブルに経路を追加するだけで、S3 への通信を AWS のネットワーク内で送れます。NAT ゲートウェイのデータ処理料金もかからなくなります。インターフェースエンドポイントでも閉じた通信はできますが、料金がかかります。パブリックサブネットへの移動は安全性を下げ、Transfer Acceleration は遠隔地からの転送を速くする機能です。 |
| 23 | B | Session Manager は、EC2 上のエージェントが Systems Manager に外向きに接続する仕組みのため、インバウンドのポートを開ける必要がありません。操作の記録も S3 や CloudWatch Logs に残せます。踏み台、パブリック IP、全社へのポート開放は、要件に反するか、攻撃される入口を増やします。 |
| 24 | D | Cognito ユーザープールは、アプリの利用者の登録とログイン(Google などの外部 ID を含む)を提供します。ID プールは、ログインした利用者に一時的な AWS の認証情報を渡し、ポリシーで自分のフォルダだけに書き込ませられます。利用者ごとの IAM ユーザーは数が多すぎて管理できず、Identity Center は社員向け、Directory Service は AD 用です。 |
| 25 | A | WAF は HTTP リクエストの中身を検査し、SQL インジェクションや XSS のパターンを遮断できます。ALB に直接関連付けられ、マネージドルールですぐに使えます。SG でポートを閉じるとサイト自体が使えなくなります。GuardDuty は脅威の検出、Inspector は脆弱性のスキャンで、攻撃のリクエストを止めるものではありません。 |
| 26 | C | WAF のレートベースルールは、同じ IP アドレスから一定時間内に送られるリクエストの数を数え、上限を超えた IP を自動で遮断します。NACL の手動追加では、変わり続ける攻撃元に追いつけません。Shield Standard はネットワーク層の DDoS 対策で、加重ルーティングは振り分けの割合を決める機能です。 |
| 27 | B | Shield Advanced は有料で、DDoS 対応チーム(SRT)の支援と、攻撃で増えた利用料の補償を受けられます。CloudFront や Route 53 も保護対象です。Shield Standard は無料の基本的な保護で、支援や補償はありません。Macie は機密データの発見、Network Firewall は VPC のファイアウォールです。 |
| 28 | C | Firewall Manager は、Organizations の全アカウントに WAF のルールなどのポリシーを一括で適用し、新しいアカウントやリソースにも自動で適用します。Config は設定の評価、Security Hub は検出結果の集約で、WAF のルールを配布する機能ではありません。手作業は漏れが出やすく、新しいリソースに追いつけません。 |
| 29 | D | GuardDuty は、CloudTrail、VPC フローログ、DNS ログなどを分析して、不審な API の呼び出しやマイニングなどの脅威を検出します。エージェントは不要です。Inspector は脆弱性のスキャン、Macie は S3 の機密データの発見、Artifact は AWS のコンプライアンスレポートの入手に使います。 |
| 30 | A | Macie は機械学習とパターンの照合で、S3 の中にある個人情報などの機密データを自動で見つけます。GuardDuty は脅威の検出、Shield は DDoS 対策、Detective は検出結果の調査に使うサービスです。 |
| 31 | B | Inspector は、EC2、ECR のコンテナイメージ、Lambda 関数のソフトウェアの脆弱性を自動で継続的にスキャンします。Security Hub は各サービスの結果を集約するもので、自分ではスキャンしません。CloudTrail は API の記録、Cognito はアプリの認証です。 |
| 32 | C | Network Firewall は VPC 内のマネージドなファイアウォールで、ドメイン名による通信の制限や、IPS のルールでの検査ができます。SG と NACL は IP アドレスとポートでしか制御できず、ドメイン名は扱えません。Shield Standard は DDoS 対策です。 |
