# 用語集 クラウドと AWS

## クラウドの基本

### クラウド
別名: クラウドコンピューティング
要約: サーバーやストレージを、必要なときに必要なだけネットワーク越しに借りる使い方です。
サーバーやストレージなどを、自分で買わずに、インターネット越しに必要な分だけ借りて使う形です。使った分だけ払い、数分で増やしたり減らしたりできます。
例: AWS、Azure、Google Cloud
注意: 使った分だけ料金がかかるので、止め忘れや消し忘れがそのまま費用になります。
関連: IaaS、オンプレミス

### オンプレミス
要約: 自分の組織でサーバーを用意し、自社の設備で運用する形です。
自社のデータセンターやサーバールームに、自分で機器を置いて運用する形です。クラウドと組み合わせる形をハイブリッドクラウドと呼びます。
例: 自社のデータセンター、社内のサーバールーム
注意: 機器の調達に時間がかかる代わりに、長く同じ量を使うなら安くなることがあります。
関連: クラウド

### IaaS
別名: PaaS、SaaS
要約: サーバー、ネットワーク、ストレージを借り、OS から上を自分で管理する形です。
クラウドの提供の形です。IaaS は仮想マシンやネットワークを借り(EC2)、PaaS はアプリの実行環境を借り(Elastic Beanstalk)、SaaS は完成したアプリを使います(メールのサービスなど)。上に行くほど、利用者の管理の範囲が狭くなります。
例: IaaS: EC2 / PaaS: Elastic Beanstalk / SaaS: Microsoft 365
注意: IaaS では OS のパッチは利用者の責任です。
関連: クラウド、責任共有モデル

### 責任共有モデル
試験: SAA
要約: クラウドの安全を、事業者と利用者で分けて受け持つ考え方です。
クラウドの安全を、事業者と利用者で分担する考え方です。AWS はクラウドそのもの(建物、ハードウェア、基盤)を、利用者はクラウドの中に置くもの(データ、OS の設定、権限、暗号化の設定)を守ります。
例: AWS: 設備、ハードウェア、ハイパーバイザー / 利用者: OS、データ、IAM、セキュリティグループ
注意: マネージドのサービスほど、利用者の受け持ちは小さくなります。
関連: IaaS

### マネージドサービス
要約: 運用の手間(パッチ、バックアップ、冗長化)をクラウドが受け持つサービスです。
運用の手間(サーバーの管理、パッチ、バックアップ、冗長化)の多くを、クラウドの事業者が行うサービスです。RDS、EKS、DynamoDB などがあります。
例: RDS、DynamoDB、EKS、Lambda
注意: 運用は楽になりますが、設定の自由は減り、サービスの制限に合わせる必要があります。
関連: クラウド

### サーバーレス
別名: サーバレス、サーバレスアーキテクチャ、サーバーレスアーキテクチャ
試験: SAA、FE
要約: サーバーを意識せず、使った分だけ料金を払う形のサービスです。
サーバーの用意や管理を利用者がせず、使った分だけ払う形です。Lambda、Fargate、DynamoDB、S3 などがあります。
例: Lambda、Fargate、DynamoDB、S3
注意: 動いていないときは費用がかからない代わりに、最初の呼び出しが遅いこと(コールドスタート)があります。
関連: Lambda

### Well-Architected フレームワーク
試験: SAA
要約: AWS が示す、よい設計の考え方を 6 つの柱にまとめたものです。
AWS が示す、よい設計の考え方です。運用上の優秀性、セキュリティ、信頼性、パフォーマンス効率、コストの最適化、持続可能性の 6 つの柱があります。
例: 運用上の優秀性、セキュリティ、信頼性、パフォーマンス効率、コスト最適化、持続可能性
注意: SAA の問題は、どの柱を重視するかで正解が変わります(問題文の条件をよく読む)。
関連: 責任共有モデル

### コストの最適化
試験: SAA、K8s
要約: 必要な性能を保ったまま、費用を減らすことです。
必要な性能を保ったまま、費用を下げることです。使っていないものを消す、大きさを使用量に合わせる(ライトサイジング)、買い方を選ぶ(Savings Plans、スポット)などがあります。
例: Savings Plans、スポットインスタンス、適切なサイズへの変更、S3 のライフサイクル
注意: 「最も安い」と「運用の手間が最も少ない」は、別の答えになることがあります。
関連: オンデマンドインスタンス、AWS Budgets

### AWS Budgets
別名: Budgets、Cost Explorer
試験: SAA
要約: 予算を決め、超えそうなときに知らせる AWS の機能です。
予算を決め、実際の費用や予測が超えそうなときにメールで知らせるサービスです。費用の内訳は Cost Explorer で見ます。学習用のアカウントでも、最初に設定しておくと安心です。
例: 月 5 ドルの予算、ゼロ支出予算のメール
注意: 知らせるだけで、リソースを止めはしません(アクションを設定すれば一部は止められます)。
関連: コストの最適化

### テナントネットワーク
試験: LinuC202
要約: 利用者(テナント)ごとに分けられた、専用の仮想のネットワークです。
クラウドを使う利用者やプロジェクト(テナント)ごとに作る、仮想のネットワークです。ほかのテナントからは見えません。インスタンスには、このネットワークの中の固定 IP アドレスが付きます。
例: OpenStack のテナントネットワーク 10.0.0.0/24
注意: 外とつなぐには、ルーターとフローティング IP アドレスなどが必要です。
関連: IaaS、セキュリティグループ

### 管理コンソール
別名: クラウドの管理コンソール
試験: LinuC102
要約: クラウドのサーバーなどを、Web の画面から操作する管理の入口です。
インターネット越しに、サーバーの作成、削除、起動、停止ができます。アカウントが乗っ取られると、影響が大きいため、強い認証で守ります。
例: AWS マネジメントコンソール
注意: 管理コンソールは、インターネット経由でつながる管理の経路なので、パスワードだけに頼りません。
関連: 多要素認証、ワンタイムパスワード

### 揮発性ストレージ
試験: LinuC102
要約: サーバーを停止や削除すると、中身が消える、一時的なディスクです。
仮想サーバーに付く、速いことが多い一時的な領域です。ホストの障害でも失われます。消えて困るデータは、永続ストレージに置きます。
例: 一時ファイル、キャッシュ、スワップ
注意: 再起動では残ることが多い一方、停止では消えます。事業者ごとの仕様を確かめます。

## 場所と冗長化

### リージョン
試験: SAA、Terraform
要約: AWS のデータセンターが集まった、地理的な地域です。
AWS のデータセンターが集まった、地理的な地域です(東京は ap-northeast-1、大阪は ap-northeast-3)。データは、選んだリージョンの外には自動では出ません。
例: 東京 `ap-northeast-1`、大阪 `ap-northeast-3`
注意: 多くのサービスはリージョンごとに独立しているので、別のリージョンに作ったものは見えません。
関連: アベイラビリティーゾーン

### アベイラビリティーゾーン
別名: AZ
試験: SAA、K8s
要約: リージョンの中の、互いに離れたデータセンターの集まりです。
リージョンの中の、互いに離れた 1 つ以上のデータセンターの集まりです。電源やネットワークが別なので、複数の AZ に分けて置くと、1 つの AZ の障害でも止まりません。
例: `ap-northeast-1a`、`ap-northeast-1c`
注意: 1 つの AZ の障害に耐えるには、2 つ以上の AZ に分けて置きます。
関連: リージョン、マルチ AZ

### マルチ AZ
別名: Multi-AZ
試験: SAA
要約: 2 つ以上の AZ に分けて置き、1 つの AZ の障害に耐える構成です。
複数のアベイラビリティーゾーンにまたがって、システムやデータベースを置く構成です。RDS のマルチ AZ では、別の AZ に同期で複製した待機のデータベースを置き、障害のときに自動で切り替えます。
例: RDS のマルチ AZ(スタンバイへ自動で切り替え)、ALB と Auto Scaling を複数の AZ に
注意: RDS のマルチ AZ のスタンバイは、普段は読み取りに使えません(読み取りの分散はリードレプリカ)。
関連: アベイラビリティーゾーン、フェイルオーバー

### エッジロケーション
試験: SAA
要約: 利用者の近くで、コンテンツを返すための拠点です。
CloudFront や Route 53 が使う、世界中の拠点です。利用者の近くでコンテンツを返して、速くします。
例: CloudFront、Route 53、Global Accelerator
注意: リージョンや AZ とは別のもので、数はずっと多いです。
関連: CloudFront

### プレイスメントグループ
試験: SAA
要約: EC2 を物理的にどう配置するかを決める機能です。
EC2 の置き方を決める設定です。クラスターは同じ場所にまとめて通信を速くし、分散(スプレッド)は別々のハードウェアに分けて同時の故障を避けます。
例: クラスター(低遅延)、分散(別々のハードウェア)、パーティション
注意: クラスターは 1 つの AZ に集めるので速いですが、AZ の障害には弱いです。
関連: EC2

### フェイルオーバー
試験: SAA、CCNA
要約: 障害のときに、待機していた側へ自動で切り替えることです。
使っているものが止まったときに、待機しているものに自動で切り替えることです。
例: RDS のマルチ AZ、Route 53 のフェイルオーバーのルーティング
注意: 切り替えの間は短い停止があります。アプリは再接続できるように作ります。
関連: 冗長化、マルチ AZ

### RPO
別名: RTO
試験: SAA
要約: 障害のときに、どの時点までのデータを失ってよいかの目標です。
災害の対策の目標です。RPO はどの時点までのデータを失ってよいか(例: 1 時間前まで)、RTO はどれだけの時間で復旧するか(例: 4 時間以内)です。小さくするほど費用がかかります。
例: RPO 1 時間なら、1 時間ごとのバックアップで足りる
注意: RTO は復旧までの時間の目標で、別のものです。
関連: バックアップ、フェイルオーバー

### バックアップ
別名: スナップショット
要約: 障害や誤操作に備えて、データの写しを別に取っておくことです。
データの複製を、別の場所に取っておくことです。定期的に、元に戻せること(リストア)も確かめておきます。ある時点のディスクやボリュームの状態を保存したものをスナップショットと呼びます。
例: EBS のスナップショット、RDS の自動バックアップ、AWS Backup
注意: 戻せることを確かめていないバックアップは、ないのと同じです。
関連: RPO

### AWS Backup
試験: SAA
要約: 複数のサービスのバックアップを、まとめて計画し管理するサービスです。
EBS、RDS、EFS などのバックアップを、まとめて決まった予定で取り、保存の期間を管理するサービスです。
例: バックアッププランで EBS、RDS、EFS、DynamoDB を毎日取る
注意: 別のリージョンやアカウントへのコピーも設定できます。
関連: バックアップ

### AWS Elastic Disaster Recovery
別名: Elastic Disaster Recovery、AWS DRS
試験: DOP
要約: 元のサーバーのデータを、常に AWS の復旧先のリージョンへ複製しておき、災害のときに素早く起動できる AWS のサービスです。
元のサーバーにエージェントを入れ、ディスクの変更を、復旧先のリージョンのステージング領域へ複製し続けます。災害のときは、復旧用のインスタンスを起動して、切り替えます。
例: オンプレミスの業務サーバーを、東京リージョンに複製しておき、被災時に EC2 として起動する
注意: 複製は続けますが、復旧のインスタンスは、起動するまで動いていないので、パイロットライトに近い方式です。
関連: パイロットライト、RPO

## アカウントと権限

### IAM
別名: Identity and Access Management
試験: SAA、Terraform
要約: AWS で、誰が何をしてよいかを管理するサービスです。
AWS の、誰が何をしてよいかを管理する仕組みです。ユーザー、グループ、ロール、ポリシーがあります。
例: ユーザー、グループ、ロール、ポリシー
注意: ルートユーザーは普段使わず、MFA を付けてしまっておきます。
関連: IAM ロール、IAM ポリシー、認可

### IAM ポリシー
別名: ポリシー
試験: SAA
要約: 許可と拒否を JSON で書いた、権限の定義です。
許可や拒否を JSON で書いたものです。Effect(Allow か Deny)、Action(操作)、Resource(対象)、Condition(条件)を書きます。明示的な Deny は、どの Allow よりも優先されます。
例: `{"Effect": "Allow", "Action": "s3:GetObject", "Resource": "arn:aws:s3:::bucket/*"}`
注意: 明示的な Deny は、どの Allow よりも優先されます。
関連: IAM、最小権限の原則

### IAM ロール
試験: SAA、Terraform、K8s
要約: 一時的に引き受けて使う、権限のまとまりです。
一時的な認証情報を受け取って使う、IAM の ID です。EC2 や Lambda、Pod に付けて、アクセスキーを置かずに AWS を使わせます。別のアカウントからの利用にも使います。
例: EC2 のインスタンスプロファイル、Lambda の実行ロール、別のアカウントへのアクセス
注意: アプリにアクセスキーを持たせず、ロールを使うのが基本です。
関連: IAM、STS、IRSA

### STS
別名: AssumeRole
試験: SAA
要約: 一時的な認証情報を発行するサービスです。
一時的な認証情報(有効期限の付いたキー)を発行するサービスです。ロールを引き受ける API が `AssumeRole` です。
例: `aws sts get-caller-identity`、`AssumeRole`
注意: 一時的な認証情報には期限があるので、漏れても被害の時間を短くできます。
関連: IAM ロール

### アクセスキー
試験: SAA、Terraform
要約: プログラムから AWS を使うための、長く使える認証情報です。
プログラムから AWS を使うための、長期間有効なキーの組です。漏れると悪用されるので、なるべく使わず、ロールや一時的な認証情報を使います。コードや Git に絶対に書きません。
例: `AKIA…` で始まるキー ID と、シークレット
注意: コードや Git に書かず、なるべく IAM ロールや SSO の一時的な認証情報を使います。
関連: IAM ロール、秘密情報

### AWS Organizations
別名: Organizations、SCP
試験: SAA
要約: 複数の AWS アカウントをまとめて管理するサービスです。
複数の AWS アカウントをまとめて管理するサービスです。SCP(サービスコントロールポリシー)で、アカウントで使える権限の上限を決めます。SCP は権限を与えません。
例: SCP(サービスコントロールポリシー)、一括の請求
注意: SCP は権限の上限を決めるだけで、権限を与えはしません。
関連: IAM ポリシー

### Cognito
別名: Amazon Cognito
試験: SAA
要約: Web やモバイルのアプリに、利用者の登録とログインを付けるサービスです。
Web やモバイルのアプリの、利用者の登録とログインを提供するサービスです。
例: ユーザープール(認証)、ID プール(AWS の一時的な認証情報)
注意: アプリの利用者の管理に使い、AWS を操作する社員の管理は IAM Identity Center を使います。
関連: 認証

### AWS Control Tower
別名: Control Tower
試験: SAA、DOP
要約: 複数の AWS アカウントを、決まった型で作り、まとめて管理する AWS のサービスです。
AWS Organizations の上に、安全な初期設定の型(ランディングゾーン)を作ります。守るべき決まり(コントロール。以前はガードレールと呼ばれていました)を、アカウントにまとめて適用します。
例: 新しい開発チーム用のアカウントを、Account Factory で作り、同じコントロールを適用する
注意: Control Tower は、Organizations や SCP を使って動くもので、Organizations の代わりではありません。
関連: AWS Organizations、Account Factory

### Account Factory
別名: AWS Control Tower Account Factory
試験: DOP
要約: Control Tower で、決まった設定の AWS アカウントを作る機能です。
アカウントの名前やメールアドレスなどを入れると、コントロールとネットワークの型を適用した新しいアカウントが作られます。手作業で作るより、設定のばらつきが減ります。
例: 申請を受けて、決まった設定の開発用のアカウントを用意する
注意: 作られたアカウントの設定を、Control Tower の外で変えると、ずれが出ることがあります。
関連: AWS Control Tower

### IAM Identity Center
別名: AWS IAM Identity Center、AWS SSO、AWS Single Sign-On
試験: SAA、DOP
要約: 複数の AWS アカウントに、1 つのサインインで入れるようにする、AWS のサービスです。
社内のユーザーの情報(自前のディレクトリや外部の ID プロバイダー)と連携し、どのアカウントに何の権限で入れるかを決めます。IAM ユーザーを、アカウントごとに作らずに済みます。
例: 社員が 1 回サインインして、開発と本番の 2 つのアカウントに入る
注意: 権限は、許可セットで決めます。IAM ユーザーの長期のアクセスキーは、使わなくて済みます。
関連: 許可セット、AWS Organizations、IAM ロール

### 許可セット
別名: Permission Set
試験: DOP
要約: IAM Identity Center で、アカウントに入る人に与える権限のひな型です。
IAM のポリシーをまとめたもので、ユーザーやグループとアカウントに割り当てます。割り当てると、そのアカウントに IAM ロールが作られます。
例: 「ReadOnly」の許可セットを、監査担当のグループに、全アカウントで割り当てる
注意: 許可セットは、アカウントごとに IAM ロールとして実体ができるので、変えたら再び適用します。
関連: IAM Identity Center、IAM ポリシー、IAM ロール

### 権限の境界
別名: Permissions Boundary、アクセス許可の境界
試験: DOP
要約: IAM のユーザーやロールに、与えられる権限の上限を決める仕組みです。
境界に入っている権限と、ユーザーに付けたポリシーの、両方にある権限だけが使えます。権限の管理を任された人が、自分より強い権限を作れないようにするときに使います。
例: 開発者が IAM ロールを作れるが、境界で許されたサービスしか使えないようにする
注意: 境界は権限を与えるものではなく、上限を決めるだけで、ポリシーで許可しなければ使えません。
関連: IAM ポリシー、AWS Organizations

### リソースベースのポリシー
別名: Resource-based policy
試験: SAA
要約: S3 のバケットなど、リソースの側に付けて、誰が使えるかを決めるポリシーです。
IAM のユーザーやロールに付けるポリシーは、人の側です。リソースベースのポリシーは、リソースの側に付け、別のアカウントの人にも許可を出せます。
例: S3 のバケットポリシー、KMS のキーポリシー、SQS のキューのポリシー
注意: 同じアカウントの中なら、リソースの側の許可だけで使えます。別のアカウントから使うときは、使う側のアカウントの IAM ポリシーでも許可が要ります。
関連: IAM ポリシー、IAM ロール

### IAM Access Analyzer
別名: AWS IAM Access Analyzer、Access Analyzer
試験: DOP
要約: 外部に公開されているリソースや、使われていない権限を見つける AWS のサービスです。
S3 のバケットや IAM ロールなどが、アカウントの外から使える状態になっていないかを調べます。意図しない公開を、早く見つけられます。
例: 外部のアカウントから使える S3 バケットを、検出結果として一覧にする
注意: 検出するのが役目で、公開を止める操作は、別に行う必要があります。
関連: IAM、GuardDuty

### キーポリシー
別名: Key Policy、キーのアクセスポリシー
試験: SAA
要約: KMS のキーを、誰が使えて、誰が管理できるかを決めるポリシーです。
KMS のキーは、キーポリシーが主な決まりです。キーポリシーが IAM ポリシーでの許可を認めている場合に限り、IAM ポリシーでも許可できます。
例: キーを使って暗号化する人と、キーを管理する人の権限を分ける
注意: キーポリシーで許可がなければ、IAM ポリシーだけでは、そのキーを使えません。
関連: KMS、IAM ポリシー

### キーのローテーション
別名: 自動ローテーション、Key Rotation
試験: SAA
要約: 暗号化のキーの素材を、定期的に新しいものに替えることです。
KMS では、自動ローテーションを有効にすると、キーの素材が定期的に替わります。キーの ID や ARN は変わらないので、使う側は、設定を変えずに済みます。
例: KMS のカスタマー管理キーで、自動ローテーションを有効にする
注意: ローテーションの前に暗号化したデータは、古い素材が残るので、そのまま復号できます。
関連: KMS

### AWS Certificate Manager
別名: ACM
試験: SAA
要約: SSL/TLS の証明書を、取得して管理し、自動で更新する AWS のサービスです。
ロードバランサーや CloudFront などに、証明書を結び付けて使います。ACM が出した証明書は、条件を満たせば、自動で更新されます。
例: ALB に、ACM の証明書を付けて、HTTPS で受ける
注意: 通常の ACM の証明書は、秘密鍵を取り出せないので、EC2 のサーバーの中に直接入れられません。取り出せる公開証明書(エクスポート可能な証明書)は、追加の料金がかかります。
関連: ELB、CloudFront

### AWS Artifact
別名: Artifact
試験: SAA
要約: AWS のセキュリティやコンプライアンスの報告書を、ダウンロードできるサービスです。
第三者の監査の報告書や、認証の資料を、利用者が取り出せます。監査や、取引先への説明のために使います。
例: 監査人に、AWS の第三者による監査報告書を渡す
注意: 利用者自身のシステムを調べるサービスではなく、AWS 側の認証の資料を得るものです。
関連: AWS Audit Manager

### AWS Audit Manager
別名: Audit Manager
試験: DOP
要約: 監査に使う証拠を、自動で集めて整理する AWS のサービスです。
決まりの枠組みに合わせて、AWS の使い方の証拠を、継続して集めます。監査の準備の手間を減らしますが、準拠を保証するものではありません。
例: 監査の枠組みに沿った、設定とログの証拠を集めて、報告書にする
注意: 2026 年 4 月 30 日から、新しいアカウントでは設定できません(保守だけの段階)。AWS は、代わりに AWS Config の適合パックを勧めています。
関連: AWS Config、CloudTrail、AWS Artifact

## ネットワーク

### VPC
別名: Virtual Private Cloud
試験: SAA、Terraform
要約: AWS の中に作る、自分専用の仮想のネットワークです。
AWS の中に作る、自分専用の論理的なネットワークです。CIDR でアドレスの範囲を決め、サブネットに分けます。
例: `10.0.0.0/16` の VPC に、AZ ごとのパブリックとプライベートのサブネット
注意: 作った後に CIDR を変えられないので、他のネットワークと重ならない範囲を最初に決めます。
関連: サブネット、パブリックサブネット、CIDR

### パブリックサブネット
別名: プライベートサブネット
試験: SAA
要約: インターネットゲートウェイへの経路を持つサブネットです。
ルートテーブルに、インターネットゲートウェイへの経路があるサブネットがパブリックサブネットです。ないものがプライベートサブネットで、データベースなど外から直接触らせないものを置きます。
例: ルートテーブルに `0.0.0.0/0 → igw-…`
注意: 名前ではなく、ルートテーブルで決まります。経路がなければプライベートサブネットです。
関連: VPC、インターネットゲートウェイ、NAT ゲートウェイ

### インターネットゲートウェイ
別名: IGW
試験: SAA
要約: VPC とインターネットをつなぐ出入り口です。
VPC とインターネットをつなぐ出入口です。
例: パブリックサブネットのルートテーブルで `0.0.0.0/0` の行き先にする
注意: インスタンスにパブリック IP がないと、IGW があってもインターネットと通信できません。
関連: パブリックサブネット

### NAT ゲートウェイ
試験: SAA
要約: プライベートサブネットから、インターネットへ出られるようにする仕組みです。
プライベートサブネットのサーバーが、外からの接続は受けずに、インターネットへ出られるようにするサービスです。パブリックサブネットに置きます。1 時間あたりの料金と、通った量の料金がかかります。
例: パブリックサブネットに置き、プライベートサブネットのルートテーブルで行き先にする
注意: 置いておくだけで時間の料金がかかります(東京で月 45 ドル前後)。AZ の障害に備えるなら AZ ごとに置きます。
関連: NAT、パブリックサブネット

### Elastic IP
別名: Elastic IP アドレス
試験: SAA
要約: 変わらない、固定のパブリック IPv4 アドレスです。
EC2 などに付ける、変わらないパブリックの IPv4 アドレスです。パブリックの IPv4 アドレスには料金がかかります。
例: NAT ゲートウェイ、外から固定のアドレスで呼ばれるサーバー
注意: パブリック IPv4 はすべて時間の料金がかかるので、使わないものは解放します。
関連: グローバルアドレス、EC2

### セキュリティグループ
別名: SG
試験: SAA、Terraform
要約: インスタンスなどに付ける、ステートフルな仮想のファイアウォールです。
EC2 などに付ける、仮想のファイアウォールです。許可のルールだけを書きます。ステートフルなので、許可した通信の戻りは自動で通ります。送信元に別のセキュリティグループを指定できます。
例: インバウンド: 443 を 0.0.0.0/0 から、5432 を Web のセキュリティグループから
注意: 許可の規則だけを書けます。応答の通信は自動で許可されます(ステートフル)。
関連: ネットワーク ACL、ファイアウォール

### ネットワーク ACL
別名: NACL
試験: SAA
要約: サブネットに付ける、ステートレスな通信の制御です。
サブネットに付ける、通信のルールです。許可と拒否を書け、番号の小さいルールから順に評価します。ステートレスなので、戻りの通信も許可が必要です。
例: 番号の小さい規則から順に評価し、拒否も書ける
注意: ステートレスなので、応答の通信(エフェメラルポート)も明示的に許可する必要があります。
関連: セキュリティグループ、ACL

### VPC エンドポイント
別名: PrivateLink、ゲートウェイエンドポイント
試験: SAA
要約: インターネットを通らずに、VPC から AWS のサービスにつなぐ仕組みです。
インターネットを通らずに、VPC の中から S3 などの AWS のサービスを使う仕組みです。S3 と DynamoDB はゲートウェイ型(無料)、ほかはインターフェース型(PrivateLink)です。
例: ゲートウェイ型(S3、DynamoDB。無料)、インターフェース型(PrivateLink。有料)
注意: S3 への大量の通信を NAT ゲートウェイから外すと、費用を大きく下げられます。
関連: VPC、S3

### VPC ピアリング
別名: Transit Gateway
試験: SAA
要約: 2 つの VPC を、1 対 1 でつなぐ仕組みです。
2 つの VPC を直接つなぐ仕組みです。つながりは推移しない(A–B と B–C をつないでも A と C はつながらない)ので、多くの VPC をつなぐには Transit Gateway を使います。
例: 別のアカウントや別のリージョンの VPC ともつなげる
注意: 推移的にはつながりません。多くの VPC をつなぐなら Transit Gateway を使います。
関連: VPC

### Direct Connect
試験: SAA
要約: 社内のネットワークと AWS を、専用線でつなぐサービスです。
オンプレミスと AWS を、インターネットを通らない専用の回線でつなぐサービスです。帯域が安定し、データの転送の料金も下がります。
例: 安定した帯域、少ない遅延、データ転送の料金の割引
注意: 開通まで数週間かかり、暗号化はされないので、必要なら VPN を重ねます。
関連: VPN、オンプレミス

### Global Accelerator
別名: AWS Global Accelerator
試験: SAA
要約: AWS のネットワークを使って、世界の利用者から速く安定してつなげるサービスです。
世界中の利用者の通信を、AWS のネットワークに近くで入れて、アプリまで速く安定して届けるサービスです。固定の IP アドレスを持ちます。
例: 固定の Anycast IP を 2 つ、TCP と UDP のアプリ
注意: CloudFront はキャッシュで HTTP を速くし、Global Accelerator は経路を速くします。
関連: CloudFront

### フローティング IP アドレス
別名: フローティング IP
試験: LinuC202
要約: インスタンスに付け替えられる、外に見せる IP アドレスです。
OpenStack などの IaaS で、外からの通信を受けるためにインスタンスへ割り当てる IP アドレスです。別のインスタンスに付け替えられるので、作り直しても、利用者から見たアドレスは変わりません。インスタンスの中のアドレス(固定 IP アドレス)に変換されます。
例: フローティング IP 203.0.113.10 を Web インスタンスの固定 IP 10.0.0.11 に対応させる(架空のアドレス)
注意: 固定 IP アドレスは、インスタンスの中のアドレスで、外に見せるものとは別です。
関連: Elastic IP、IP アドレス

### ルートテーブル
別名: Route Table、VPC ルートテーブル
試験: SAA
要約: VPC で、サブネットからの通信を、どこへ送るかを決める表です。
宛先の範囲と、送り先(インターネットゲートウェイ、NAT ゲートウェイなど)の組を並べます。サブネットごとに、1 つのルートテーブルを結び付けます。
例: パブリックサブネットは、0.0.0.0/0 の送り先をインターネットゲートウェイにする
注意: 「パブリックサブネット」は、ルートテーブルにインターネットゲートウェイへの経路があるサブネットのことです。
関連: VPC、インターネットゲートウェイ、NAT ゲートウェイ

### VPC フローログ
別名: VPC Flow Logs、フローログ
試験: DOP
要約: VPC の中を流れる通信の、記録を取る機能です。
ネットワークインターフェースを通る通信の、送信元、宛先、ポート、許可か拒否かなどを記録します。通信の中身は記録しません。記録は CloudWatch Logs、S3、Amazon Data Firehose に送れます。
例: セキュリティグループで拒否された通信の、宛先を調べる
注意: 通信の中身(パケット)の記録ではなく、通信の概要の記録です。
関連: VPC、Amazon CloudWatch Logs、セキュリティグループ

## コンピューティング

### EC2
別名: Amazon EC2
試験: SAA、Terraform
要約: AWS で借りる仮想のサーバーです。
AWS の仮想マシンです。インスタンスタイプで CPU とメモリを、AMI で OS を選びます。
例: `t3.micro`、`m7g.large`(g は Graviton)
注意: 止めても EBS の料金はかかります。消すときはボリュームとスナップショットも確かめます。
関連: AMI、Auto Scaling、仮想マシン

### AMI
別名: Amazon Machine Image
試験: SAA、Terraform
要約: EC2 を起動するための、OS とソフトウェアのひな形です。
EC2 を起動するときの、OS とソフトウェアの入ったひな形です。
例: Amazon Linux 2023、自分で作った AMI(ゴールデンイメージ)
注意: AMI の ID はリージョンごとに違うので、Terraform では data ソースで探します。
関連: EC2

### オンデマンドインスタンス
別名: リザーブドインスタンス、Savings Plans、スポットインスタンス
試験: SAA
要約: 事前の約束なしに、使った時間だけ払う EC2 の料金の形です。
EC2 の買い方です。オンデマンドは使った分だけ。リザーブドインスタンスと Savings Plans は 1 年か 3 年の約束で安くなります。スポットインスタンスは余った容量を大きな割引で使えますが、2 分前の通知で中断されることがあります。
例: オンデマンド、Savings Plans、リザーブド、スポット(最大 90% 引き、中断あり)
注意: スポットは中断の 2 分前に通知されるので、止まってもよい処理に使います。
関連: EC2、コストの最適化

### Auto Scaling
別名: EC2 Auto Scaling
試験: SAA
要約: 負荷に合わせて、EC2 の数を自動で増やしたり減らしたりする仕組みです。
負荷やスケジュールに合わせて、EC2 の台数を自動で増やしたり減らしたりする仕組みです。台数を保つので、壊れたインスタンスの入れ替えも自動で行います。
例: ターゲット追跡(CPU 50% を保つ)、最小 2、最大 10、希望 2
注意: ヘルスチェックで異常なインスタンスを入れ替える働きもあります。
関連: EC2、スケーリング、ELB

### ELB
別名: Elastic Load Balancing、ALB、NLB
試験: SAA
要約: 受けた通信を、複数の EC2 やコンテナに振り分けるロードバランサーです。
AWS のロードバランサーです。ALB は HTTP の層(L7)でパスやホスト名で振り分け、NLB は TCP や UDP の層(L4)で高速に振り分けます。
例: ALB(HTTP、パスやホストで振り分け)、NLB(TCP と UDP、固定 IP)、GWLB
注意: パスで振り分ける、WebSocket は ALB、固定 IP や極めて低い遅延は NLB です。
関連: ロードバランサー、Auto Scaling

### Lambda
別名: AWS Lambda
試験: SAA
要約: 呼ばれたときだけ関数のコードを動かす、サーバーレスのサービスです。
サーバーを用意せず、イベントが起きたときにコードを動かすサービスです(サーバーレス)。1 回の実行は最大 15 分です。動いた時間と回数で課金されます。
例: S3 へのアップロードで起動する、API Gateway の裏で動く
注意: 1 回の実行は最大 15 分です。長い処理には向きません。
関連: サーバーレス

### ECS
別名: Amazon ECS、Fargate
試験: SAA、Docker
要約: AWS のコンテナを動かすサービスです。
AWS のコンテナの実行と管理のサービスです。Fargate を使うと、コンテナを動かすサーバーの管理も AWS に任せられます。
例: タスク定義、サービス、Fargate(サーバーを管理しない)
注意: EC2 の起動タイプでは、ホストの EC2 の管理は利用者の責任です。
関連: コンテナ、EKS、ECR

### EKS
別名: Amazon EKS
試験: SAA、K8s
要約: AWS のマネージドの Kubernetes です。
AWS のマネージドの Kubernetes です。コントロールプレーンの運用は AWS が行い、利用者はノードとアプリ、バージョンのアップグレードを管理します。
例: コントロールプレーンは AWS、ワーカーノードはマネージドノードグループか Fargate
注意: Kubernetes の版には期限があるので、アップグレードは利用者が計画します。
関連: Kubernetes、マネージドサービス

### ECR
別名: Amazon ECR
試験: SAA、Docker
要約: AWS のコンテナイメージのレジストリです。
AWS のコンテナのイメージのレジストリです。IAM で権限を管理し、イメージの脆弱性のスキャンもできます。
例: `aws ecr get-login-password | docker login …`、イメージのスキャン
注意: 古いイメージを消すライフサイクルポリシーを設定しないと、保存の料金が増え続けます。
関連: レジストリ、イメージ

### Elastic Beanstalk
別名: AWS Elastic Beanstalk
試験: SAA
要約: コードを置くだけで、実行の環境を自動で作る PaaS です。
アプリのコードを置くと、EC2、ロードバランサー、Auto Scaling を自動で用意して動かすサービスです(PaaS)。
例: EC2、ELB、Auto Scaling をまとめて作る
注意: 中で作られたリソースは自分のアカウントにあり、裏で細かく設定もできます。
関連: IaaS、EC2

### AWS Batch
別名: Batch
試験: SAA
要約: 大量のバッチ処理を、実行する機械の用意を含めて自動で行う AWS のサービスです。
ジョブを登録すると、必要な計算の資源を用意して、順番に実行します。実行する環境は、EC2 や Fargate です。
例: 夜間に、数千の画像変換のジョブを実行する
注意: 実行環境を、自分で用意しなくて済みますが、リアルタイムの応答向きではありません。
関連: EC2、ECS

### Amazon EMR
別名: EMR、Elastic MapReduce
試験: SAA
要約: Hadoop や Spark などで、大量のデータを分散して処理する AWS のサービスです。
複数のサーバーでクラスターを作り、ビッグデータの処理を行います。S3 に置いたデータを処理して、結果を S3 に戻す使い方が多いです。
例: S3 のログ数 TB を、Spark で集計する
注意: SQL でそのまま調べるだけなら、Athena のほうが手軽です。
関連: S3、Athena、AWS Glue

### EC2 インスタンスタイプ
別名: インスタンスタイプ
試験: SAA
要約: EC2 の、CPU、メモリ、ネットワークなどの組み合わせの種類です。
用途に合わせた系統(インスタンスファミリー)があり、汎用、計算に強いもの、メモリに強いもの、ストレージに強いものなどがあります。処理の性質に合わせて選びます。
例: メモリを多く使うデータベースには、メモリに強い系統を選ぶ
注意: 大きいものを選ぶと速くなりますが、費用も増えるので、実際の使用量から選びます。
関連: EC2、ライトサイジング

### Amazon EC2 Dedicated Hosts
別名: Dedicated Hosts、専有ホスト
試験: SAA
要約: 物理サーバー 1 台を、自分のアカウント専用として借りる EC2 の使い方です。
物理のコアやソケットが見えるので、コアやソケットで決まるライセンスを、持ち込めます。配置するサーバーも指定できます。
例: ソケット数でライセンスが決まる既存のソフトを、EC2 で動かす
注意: 通常のオンデマンドインスタンスより、使う目的が限られ、費用も高くなりがちです。
関連: EC2、オンデマンドインスタンス

### ライトサイジング
別名: Right Sizing、適正サイズ化
試験: SAA
要約: 実際の使用量に合わせて、インスタンスなどの大きさを見直すことです。
CPU やメモリの使用率を見て、余っていれば小さいものに替えます。無駄な費用を減らす基本の方法です。
例: CPU の使用率が常に 10% 以下のインスタンスを、1 つ小さい型に替える
注意: 小さくしすぎると、負荷が高いときに遅くなるので、ピーク時の使用量も見ます。
関連: コストの最適化、EC2 インスタンスタイプ

### Instance Scheduler
別名: Instance Scheduler on AWS
試験: SAA
要約: 決めた時間に、EC2 などを自動で止めたり、起動したりする仕組みです。
AWS が公開しているソリューションで、CloudFormation のテンプレートで自分のアカウントに組み込みます。開発用の環境を、夜間や週末に止めるときに使います。止めている間は、EC2 の利用料がかからず、EBS などの料金だけが残ります。
例: 平日の 9 時から 19 時だけ、開発用の EC2 を動かす
注意: 止めても、EBS の料金などは続きます。
関連: EC2、EBS、コストの最適化

### ライフサイクルフック
別名: Auto Scaling ライフサイクルフック、lifecycle hook
試験: DOP
要約: Auto Scaling で、インスタンスを起動や終了する途中に、いったん待たせて処理を挟む仕組みです。
起動時は Pending:Wait、終了時は Terminating:Wait の状態で待ち、その間に、設定の追加やログの退避などを行います。処理が済むと、続きに進みます。
例: 終了する前に、インスタンスのログを S3 に退避してから、終了させる
注意: 待ち時間を過ぎると、既定の動作(続行か中止)に進みます。
関連: Auto Scaling、ウォームプール

### ウォームプール
別名: Warm Pools、Auto Scaling ウォームプール
試験: DOP
要約: Auto Scaling で、あらかじめ初期化したインスタンスを、待機させておく仕組みです。
増やすときに、ゼロから起動するより早く、使い始められます。待機するインスタンスは、停止の状態などで置けます。
例: 起動に数分かかるアプリのインスタンスを、停止の状態で待たせておく
注意: 待機中のインスタンスにも、EBS などの費用はかかります。
関連: Auto Scaling、ライフサイクルフック

### Auto Scaling のスケーリングポリシー
別名: スケーリングポリシー、scaling policy
試験: DOP
要約: Auto Scaling が、台数をいつ、どれだけ増減するかを決めるルールです。
ターゲット追跡は、指標(CPU の使用率など)を目標の値に近づけるように、自動で増減します。ステップは、指標の大きさに応じて、増減の幅を段階的に決めます。シンプルは、1 回のアラームで決まった台数を増減します。
例: CPU の平均使用率を 50% に保つ、ターゲット追跡のポリシー
注意: ふつうは、設定が簡単なターゲット追跡から検討します。
関連: Auto Scaling、スケーリング

## ストレージ

### S3
別名: Amazon S3、バケット
試験: SAA、Terraform
要約: 容量に上限のない、オブジェクトのストレージです。
ファイル(オブジェクト)を保存するストレージのサービスです。バケットに入れ、とても高い耐久性があります。ストレージクラス(Standard、IA、Glacier など)で料金が変わります。
例: 静的な Web サイト、バックアップ、データレイク
注意: バケットは既定で非公開です。公開するときは、ブロックパブリックアクセスの設定を確かめます。
関連: ストレージクラス、ライフサイクル、VPC エンドポイント

### ストレージクラス
試験: SAA
要約: S3 で、取り出しの頻度と料金に合わせて選ぶ保存の種類です。
S3 の保存の種類です。よく使うものは Standard、ときどき使うものは Standard-IA、ほとんど使わないものは Glacier の各クラスに置くと安くなります。Glacier Deep Archive は取り出しに時間がかかり、最低保存期間は 180 日です。
例: Standard、Intelligent-Tiering、Standard-IA、Glacier Instant / Flexible / Deep Archive
注意: IA や Glacier には最低保存期間と取り出しの料金があります(Deep Archive は 180 日)。
関連: S3、ライフサイクル

### ライフサイクル
別名: ライフサイクルルール、ライフサイクルポリシー
試験: SAA、Docker
要約: S3 のオブジェクトを、日数に応じて別のクラスに移したり消したりする規則です。
決めた日数がたったら、データを安いストレージに移したり、削除したりする規則です。S3 や ECR で使います。
例: 30 日で Standard-IA、90 日で Glacier、365 日で削除
注意: 古い版(バージョニング)も、別に規則を書かないと残り続けます。
関連: ストレージクラス、S3

### EBS
別名: Amazon EBS
試験: SAA、K8s
要約: EC2 につなぐ、ブロックのストレージです。
EC2 に付けるブロックストレージ(ディスク)です。基本は 1 台の EC2 に、同じアベイラビリティーゾーンでつなぎます。スナップショットでバックアップを取れます。
例: gp3(汎用)、io2(高い IOPS)、スナップショット
注意: 同じ AZ の EC2 にしかつなげません。別の AZ へはスナップショットから作ります。
関連: EC2、EFS、バックアップ

### EFS
別名: Amazon EFS
試験: SAA、K8s
要約: 複数の EC2 から同時に使える、NFS のファイルのストレージです。
複数の EC2 やコンテナから同時に使える、ファイルのストレージです(NFS)。Kubernetes では ReadWriteMany のボリュームに使えます。
例: 複数の AZ の Web サーバーで、同じファイルを共有する
注意: Linux 向けです。Windows のファイル共有には FSx for Windows を使います。
関連: EBS、アクセスモード

### FSx
別名: Amazon FSx
試験: SAA
要約: 特定のファイルシステムを、マネージドで使うサービスです。
Windows のファイルサーバー、Lustre(高速な計算向け)などの、ファイルシステムを提供するサービスです。
例: FSx for Windows File Server(SMB)、FSx for Lustre(高性能の計算)、FSx for NetApp ONTAP
注意: 用途(Windows、HPC、既存の NetApp)で選ぶ種類が決まります。
関連: EFS

### Snowball
別名: AWS Snowball、DataSync、Storage Gateway
試験: SAA
要約: 大量のデータを、物理の装置で AWS に運ぶサービスです。
大量のデータを、物理の装置に入れて運び、AWS に取り込むサービスです。ネットワークで移すなら DataSync、オンプレミスから S3 などを使うなら Storage Gateway を使います。
例: 数十 TB を、ネットワークでは何週間もかかるときに使う
注意: 回線の帯域と期間から、ネットワークで送るより速いかを計算して選びます。
関連: S3、オンプレミス

### オブジェクトストレージ
別名: オブジェクト型ストレージ
試験: LinuC202
要約: HTTP の API で、ファイルをオブジェクトとして出し入れするストレージです。
ディスクとして mount せず、HTTP の API でファイルをオブジェクトとして保存し、取り出します。容量を気にせずに置け、画像やバックアップに向きます。
例: Amazon S3、OpenStack の Swift
注意: ブロックストレージのように、ファイルの一部だけを書き換える使い方には向きません。
関連: S3、バックアップ

### リクエスタ支払い
別名: Requester Pays
試験: SAA
要約: S3 のデータを取り出す人が、通信などの料金を払う設定です。
通常は、バケットの持ち主が、データの転送の料金を払います。この設定にすると、リクエストした側が、リクエストとデータ転送の料金を払います。
例: 研究用の大きなデータを公開し、使う人に転送の料金を負担してもらう
注意: リクエストする側は、リクエストにこの設定を使うことを、明示して指定します。
関連: S3、コストの最適化

### S3 Intelligent-Tiering
別名: Intelligent-Tiering
試験: SAA
要約: S3 が、アクセスの頻度に応じて、自動でストレージクラスを入れ替えるクラスです。
アクセスのないデータは、安いほうの階層に自動で移ります。アクセスの頻度が分からないデータや、変わるデータに向きます。
例: 使われ方が予測できない、利用者のアップロードデータを置く
注意: 管理のための小さな料金がかかります。料金は、公式の価格表で確かめます。
関連: ストレージクラス、ライフサイクル

### S3 One Zone-IA
別名: One Zone-IA、S3 One Zone-Infrequent Access
試験: SAA
要約: 1 つの AZ だけにデータを置く、アクセスが少ないデータ向けの安いストレージクラスです。
通常は 3 つ以上の AZ に分けて置きますが、One Zone-IA は 1 つの AZ だけです。その分、安くなりますが、AZ が失われるとデータも失われます。
例: 作り直せる、サムネイルの画像のコピーを置く
注意: 失われると困るデータの、唯一の置き場所にはしません。
関連: ストレージクラス、アベイラビリティーゾーン

### S3 Glacier Instant Retrieval
別名: Glacier Instant Retrieval、Instant Retrieval
試験: SAA
要約: めったに読まないが、読むときはミリ秒で取り出せる、アーカイブ向けのストレージクラスです。
長く置くデータの保管料が安く、読むときに待ち時間がありません。ほかの Glacier のクラスは、取り出しに時間がかかります。
例: 四半期に 1 回しか読まないが、読むときはすぐ必要な医療画像
注意: 取り出しの料金や、最小の保管期間があるので、頻繁に読むデータには向きません。
関連: ストレージクラス、S3

### 非現行バージョン
別名: noncurrent version
試験: SAA
要約: S3 のバージョニングで、最新ではなくなった古い版のオブジェクトです。
バージョニングを有効にすると、上書きや削除のたびに、古い版が残ります。ライフサイクルのルールで、一定の期間のあとに、古い版を安いクラスに移したり、削除したりできます。
例: 非現行バージョンを 30 日後に削除する、ライフサイクルのルール
注意: 古い版を放置すると、保管料が増え続けるので、ライフサイクルで整理します。
関連: S3、ライフサイクル

### S3 Object Lock
別名: Object Lock
試験: DOP
要約: S3 のオブジェクトを、一定の期間、上書きや削除ができないようにする機能です。
書き込みは 1 回だけで、読むのは何度でもできる形(WORM)で保管します。使うには、バージョニングの有効化が要ります。ガバナンスモードは、特別な権限があれば解除できます。コンプライアンスモードは、期間が終わるまで、誰も解除できません。ログの改ざんを防ぐときにも使います。
例: 監査用のログを、7 年間、削除できないように保持する
注意: コンプライアンスモードは、ルートユーザーでも解除できないので、期間を慎重に決めます。
関連: S3、CloudTrail ログファイルの整合性検証

## データベース

### RDS
別名: Amazon RDS
試験: SAA
要約: AWS のマネージドのリレーショナルデータベースです。
AWS のマネージドのリレーショナルデータベースです(MySQL、PostgreSQL など)。バックアップ、パッチ、マルチ AZ の切り替えを AWS が行います。読み取りを分けるにはリードレプリカを使います。
例: MySQL、PostgreSQL、MariaDB、Oracle、SQL Server
注意: 止めても 7 日たつと自動で起動します。長く使わないならスナップショットを取って消します。
関連: Aurora、リードレプリカ、マルチ AZ

### Aurora
別名: Amazon Aurora
試験: SAA
要約: AWS が作った、MySQL と PostgreSQL に互換の高性能なデータベースです。
AWS が作った、MySQL や PostgreSQL と互換のデータベースです。データを 3 つの AZ に 6 つのコピーで保存します。
例: 3 つの AZ に 6 つの写し、Aurora Serverless v2、グローバルデータベース
注意: 書き込みは 1 つのライター、読み取りはリーダーのエンドポイントに分けます。
関連: RDS

### リードレプリカ
試験: SAA
要約: 読み取りの負荷を分けるための、データベースの読み取り専用の写しです。
読み取り専用の、データベースの複製です。非同期で複製され、読み取りの負荷を分けるのに使います。待機用のマルチ AZ とは目的が違います。
例: RDS のリードレプリカ、Aurora のリーダー
注意: 写しは非同期なので、少し古いデータを読むことがあります。
関連: RDS、マルチ AZ

### DynamoDB
別名: Amazon DynamoDB
試験: SAA
要約: AWS のサーバーレスの、キーと値のデータベースです。
AWS の、サーバーの管理が不要なキーバリュー型の NoSQL データベースです。アクセスの量が予測できないときは、オンデマンドモードを使います。
例: パーティションキー、ソートキー、オンデマンドとプロビジョンド、DAX
注意: 決まったキーで引く処理は速いですが、自由な検索や結合は苦手です。
関連: サーバーレス

### ElastiCache
別名: Amazon ElastiCache
試験: SAA
要約: AWS のマネージドのメモリのキャッシュです。
メモリの上に置くキャッシュのサービスです(Redis、Memcached)。データベースの読み取りを減らして速くします。
例: Redis OSS、Valkey、Memcached
注意: セッションの保存やランキングには Redis、単純なキャッシュには Memcached も使えます。
関連: キャッシュ

### キャッシュ
要約: よく使うデータを、速い場所に置いておく仕組みです。
よく使うデータを、速い場所に一時的に置いておくことです。元のデータが変わったときに古い値が残る問題があるので、有効期限(TTL)を決めます。
例: CloudFront、ElastiCache、DNS のキャッシュ
注意: 元のデータを変えても、キャッシュの期限(TTL)が切れるまで古いものが返ることがあります。
関連: ElastiCache、CloudFront、TTL

### DMS
別名: AWS DMS、Database Migration Service
試験: SAA
要約: データベースを、止める時間を少なくして移すサービスです。
データベースを、動かしたまま別のデータベースに移すサービスです。移す間の変更も続けて反映できます。
例: オンプレミスの Oracle から Aurora へ、継続のレプリケーション(CDC)
注意: 種類の違うデータベースへ移すときは、スキーマの変換(SCT)も必要です。
関連: RDS

### レプリケーション
別名: 複製
試験: LinuC202
要約: データベースの内容を、別のサーバーに自動で複製する仕組みです。
更新を受ける主から、副に内容を自動で写します。副は、読み取りを引き受けたり、主が壊れたときの交代先になったりします。
例: MySQL のレプリケーション、PostgreSQL のストリーミングレプリケーション
注意: 非同期の複製では、副が少し遅れます。主が壊れた瞬間のデータが、副にないことがあります。
関連: リードレプリカ、フェイルオーバー、RPO

### Amazon RDS Proxy
別名: RDS Proxy
試験: SAA
要約: アプリと RDS の間で、データベースの接続をまとめて使い回す AWS のサービスです。
Lambda のように、接続を多く作るアプリが、データベースに負荷をかけすぎるのを防ぎます。フェイルオーバーのときの切り替えも、早くなります。
例: Lambda から RDS につなぐときに、RDS Proxy を間に置く
注意: 接続を減らす仕組みで、データベースの速度そのものを上げるものではありません。
関連: RDS、Lambda、Aurora

### DynamoDB グローバルテーブル
別名: Global Tables、DynamoDB Global Tables
試験: DOP
要約: DynamoDB のテーブルを、複数のリージョンで、自動で複製する機能です。
どのリージョンでも読み書きでき、変更が他のリージョンへ複製されます。リージョンの障害や、遠い利用者の遅延への対策になります。
例: 東京とバージニアに、同じテーブルを置いて、利用者に近いほうを使う
注意: 既定の結果整合性の方式では、同じ項目を別のリージョンで同時に更新すると、後に書いたほうが残ります。
関連: DynamoDB、レプリケーション

### Amazon DynamoDB Accelerator
別名: DAX、DynamoDB Accelerator
試験: SAA
要約: DynamoDB の前に置く、メモリの上の高速なキャッシュです。
DynamoDB の API とほぼ同じ形で使え、書き込みも DAX を通して DynamoDB に書けます。同じデータの読み取りを、マイクロ秒の単位に近づけます。読み取りが多いときに向きます。
例: 同じ商品データを何度も読む、EC サイトの一覧
注意: 書き込みが多いデータや、必ず最新の値が要る読み取りには、向きません。
関連: DynamoDB、ElastiCache、キャッシュ

### DynamoDB のキャパシティモード
別名: 読み取り/書き込みキャパシティモード
試験: SAA
要約: DynamoDB の、読み書きの処理能力と料金の決め方です。
オンデマンドは、使った分だけ払い、事前の見積もりが要りません。プロビジョンドは、能力を先に決め、使い方が予測できるときに安くなります。
例: 予測できないアクセスにはオンデマンド、安定したアクセスにはプロビジョンド
注意: 能力を超えたプロビジョンドのリクエストは、スロットリングされます。
関連: DynamoDB、スロットリング

### Amazon Neptune
別名: Neptune
試験: SAA
要約: つながりの関係を、たどって調べるための、グラフ型のデータベースです。
友人関係、推薦、不正の検知のように、データ同士のつながりをたどる処理に向きます。
例: 「友人の友人」を調べる、SNS の推薦
注意: 一般的な表形式のデータには、RDS のほうが向きます。
関連: RDS、DynamoDB

### Amazon Timestream
別名: Timestream
試験: SAA
要約: 時刻の付いたデータを、効率よく保存して調べるための、時系列のデータベースです。
センサーや監視の指標のように、時間とともに増えていくデータに向きます。Timestream for LiveAnalytics と Timestream for InfluxDB の 2 つがあります。
例: 工場のセンサーの値を、1 秒ごとに保存する
注意: Timestream for LiveAnalytics は、2025 年 6 月 20 日から新しい利用者を受け付けていません。新しく使うときは、Timestream for InfluxDB を検討します。
関連: DynamoDB、RDS

### RDS の自動バックアップの保持期間
別名: バックアップ保持期間、backup retention period
試験: SAA
要約: RDS が自動でとるバックアップを、何日間残すかの設定です。
保持期間の内なら、時点を指定して復元(ポイントインタイムリカバリ)できます。期間を 0 にすると、自動バックアップは行われません。
例: 保持期間を 7 日にして、5 日前の状態に戻す
注意: 自動バックアップは、期間が過ぎると消え、既定ではインスタンスを削除したときも消えます。長く残すときは、手動のスナップショットを使います。
関連: RDS、バックアップ、AWS Backup

## 配信と連携

### CloudFront
別名: Amazon CloudFront、CDN
試験: SAA
要約: AWS の CDN で、利用者の近くからコンテンツを返します。
世界中のエッジロケーションからコンテンツを配る CDN のサービスです。S3 や ALB の前に置き、速くし、元のサーバーの負荷を減らします。
例: S3 の静的なサイトの配信、OAC で S3 を直接見せない
注意: 中身を変えたら、キャッシュの無効化か、ファイル名を変えて反映させます。
関連: エッジロケーション、キャッシュ

### Route 53
別名: Amazon Route 53
試験: SAA
要約: AWS の DNS のサービスです。
AWS の DNS のサービスです。ヘルスチェックと組み合わせて、障害のときに別のリージョンへ切り替える(フェイルオーバー)こともできます。
例: エイリアスレコード、加重、レイテンシー、フェイルオーバー、位置情報のルーティング
注意: ゾーンの頂点で ALB などを指すには、CNAME ではなくエイリアスレコードを使います。
関連: DNS、フェイルオーバー

### API Gateway
別名: Amazon API Gateway
試験: SAA
要約: API の入口を作り、認証、制限、Lambda などへの中継を受け持つサービスです。
API の入口を作るサービスです。認証、リクエストの数の制限(スロットリング)、Lambda などへの振り分けを行います。
例: REST API、HTTP API、WebSocket API
注意: スロットリング(秒あたりの数の制限)で、裏のシステムを守れます。
関連: Lambda、API

### SQS
別名: Amazon SQS、キュー
試験: SAA
要約: メッセージを一時的に溜める、マネージドのキューです。
メッセージをためておくキューのサービスです。送る側と受け取る側を切り離し(疎結合)、受け取る側が遅れても失わずに処理できます。
例: 標準キュー(順番の保証なし、重複あり)、FIFO キュー、デッドレターキュー
注意: 処理の側は、同じメッセージが 2 回届いても困らないように作ります。
関連: 疎結合、SNS

### SNS
別名: Amazon SNS
試験: SAA
要約: 1 つのメッセージを、複数の受け手にまとめて送るサービスです。
1 つのメッセージを、複数の購読者(SQS、Lambda、メール)に一度に送るサービスです(ファンアウト)。
例: SNS → 複数の SQS(ファンアウト)、メール、Lambda
注意: SNS は溜めないので、受け手が止まっていても後で受け取れるようにするには SQS を挟みます。
関連: SQS

### EventBridge
別名: Amazon EventBridge、Step Functions
試験: SAA
要約: イベントを受け取り、規則に合わせて送り先に振り分けるサービスです。
AWS のサービスやアプリのイベントを受け、ルールに合うものを別のサービスに送るサービスです。決まった時刻の実行もできます。複数の処理を順番や分岐でつなぐには Step Functions を使います。
例: EC2 の状態の変化で Lambda を呼ぶ、決まった時刻に実行する(スケジューラー)
注意: SNS より細かい条件で振り分けられ、SaaS のイベントも受け取れます。
関連: Lambda、疎結合

### 疎結合
試験: SAA
要約: 部品同士を直接つながず、片方の障害や遅れが他方に広がりにくくする設計です。
部品同士が、相手の状態に強く依存しないようにつなぐことです。間にキューを置くと、片方が止まったり遅れたりしても、もう片方に影響しにくくなります。
例: Web とバッチの間に SQS を挟む
注意: キューに溜めて非同期にすると、急な負荷を平らにできます。
関連: SQS

### Kinesis
別名: Amazon Kinesis、Data Firehose
試験: SAA
要約: 大量のデータを、流れたまま集めて処理するサービスです。
大量のデータ(ログ、クリック、センサーの値)を、リアルタイムに受け取って処理するサービスです。S3 などに届けるだけなら Data Firehose を使います。
例: Kinesis Data Streams、Amazon Data Firehose(S3 などへ自動で届ける)
注意: Data Streams のデータの保持は既定で 24 時間、最大 365 日です。
関連: S3

### Athena
別名: Amazon Athena、Redshift
試験: SAA
要約: S3 のデータに、サーバーなしで SQL を実行するサービスです。
S3 に置いたデータを、サーバーを用意せずに SQL で検索するサービスです。大量のデータを分析するデータウェアハウスは Redshift です。
例: ALB や CloudTrail のログを SQL で調べる
注意: 読んだデータの量で料金がかかるので、パーティションと圧縮(Parquet)で減らします。
関連: S3、サーバーレス

### メッセージキュー
別名: メッセージ待ち行列
試験: LinuC202
要約: 処理の依頼を一時的に溜めて、送る側と処理する側を切り離す仕組みです。
送る側が依頼(メッセージ)を入れ、処理する側(ワーカー)が取り出して処理します。非同期の処理ができ、アクセスが急に増えても受け付けは止まりません。
例: RabbitMQ、Amazon SQS
注意: 同じメッセージが 2 回届くことがあるので、処理は 2 回行っても困らないように作ります。
関連: SQS、疎結合

### CloudFront の価格クラス
別名: Price Class、価格クラス
試験: SAA
要約: CloudFront が使うエッジロケーションの地域を絞って、費用を下げる設定です。
利用者のいない地域のエッジを使わないことで、料金を下げられます。そのかわり、絞った地域の外の利用者は、遠いエッジから配信されるので、遅くなることがあります。
例: 利用者が北米と欧州だけなら、その地域に絞った Price Class 100 にする
注意: 費用と、世界中での速さの、どちらを優先するかで決めます。
関連: CloudFront、エッジロケーション

### デッドレターキュー
別名: DLQ、Dead Letter Queue
試験: DOP
要約: 何度やっても処理できなかったメッセージを、取り分けておくキューです。
SQS では、受信の回数が上限を超えたメッセージを、別のキューに移します。原因を調べたり、あとで処理し直したりできます。
例: 5 回失敗した注文のメッセージを、デッドレターキューに移す
注意: デッドレターキューに入ったメッセージは、見ていないと、気づかれないままになるので、アラームで知らせます。
関連: SQS、CloudWatch アラーム

### Lambda の送信先
別名: Lambda Destinations、非同期呼び出しの送信先
試験: DOP
要約: Lambda の非同期の呼び出しが、成功や失敗したときに、結果を送る先の設定です。
SQS、SNS、EventBridge、別の Lambda などを、成功のときと失敗のときで分けて指定できます。デッドレターキューより、情報が多く渡せます。
例: 失敗した呼び出しの内容を、SQS に送って、あとで調べる
注意: 対象は主に非同期の呼び出しです。同期の呼び出しの失敗は、呼び出した側に返ります。
関連: Lambda、SQS、デッドレターキュー

## 運用と監視

### CloudWatch
別名: Amazon CloudWatch
試験: SAA
要約: AWS のメトリクス、ログ、アラームのサービスです。
AWS の監視のサービスです。メトリクスを集め、しきい値でアラームを出し、ログ(CloudWatch Logs)も保存します。
例: CPU の使用率のアラーム、CloudWatch Logs、CloudWatch エージェント
注意: EC2 のメモリやディスクの使用率は、エージェントを入れないと取れません。
関連: 監視、メトリクス

### CloudTrail
別名: AWS CloudTrail
試験: SAA
要約: AWS の API の呼び出しを記録するサービスです。
AWS のアカウントで、誰がいつどの API を呼んだかを記録するサービスです(監査ログ)。
例: 誰がいつセキュリティグループを変えたかを調べる
注意: すべてのリージョンの記録を、別のアカウントの S3 に送って守ります。
関連: 監査ログ

### AWS Config
試験: SAA
要約: リソースの設定とその変化を記録し、規則に合うかを調べるサービスです。
AWS のリソースの設定と、その変化を記録し、ルールに合っているかを確かめるサービスです。
例: 暗号化されていない EBS を見つける、公開された S3 を見つける
注意: CloudTrail は「誰が何をしたか」、Config は「設定がどう変わったか」を記録します。
関連: 監査ログ、ドリフト

### GuardDuty
別名: Amazon GuardDuty、Inspector、Macie、Security Hub
試験: SAA
要約: ログから、不審な動きを自動で見つける脅威検出のサービスです。
アカウントの通信や API の記録から、怪しい動きを見つけるサービスです。ソフトウェアの脆弱性は Inspector、S3 の中の個人情報は Macie が見つけ、Security Hub がそれらの結果をまとめます。
例: 見知らぬ国からの API の呼び出し、暗号通貨の採掘の通信
注意: 見つけるだけで止めはしないので、EventBridge で通知や自動の対処につなげます。
関連: CloudTrail、脆弱性スキャン

### Systems Manager
別名: AWS Systems Manager、Session Manager
試験: SAA
要約: EC2 などを、まとめて管理する道具の集まりです。
EC2 などのサーバーを、まとめて管理するサービスです。Session Manager を使うと、SSH のポートを開けずにサーバーに入れます。
例: Session Manager(SSH なしでログイン)、Patch Manager、Parameter Store
注意: Session Manager を使うと、22 番を開けずに済みます。
関連: EC2、SSH

### Shield
別名: AWS Shield
試験: SAA
要約: AWS の DDoS 攻撃への守りのサービスです。
DDoS 攻撃から守るサービスです。Standard は無料で自動で有効、Advanced は有料で、専門のチームの支援や費用の補償があります。
例: Shield Standard(無料、自動)、Shield Advanced(有料、専門のチームの支援)
注意: アプリの層の攻撃(HTTP)は WAF と組み合わせて守ります。
関連: DDoS 攻撃、WAF

### KMS
別名: AWS KMS
試験: SAA
要約: 暗号化の鍵を作り、管理するサービスです。
暗号化の鍵を作り、管理するサービスです。S3 や EBS、RDS の保存時の暗号化に使います。誰が鍵を使えるかはキーポリシーで決めます。
例: S3 の SSE-KMS、EBS の暗号化、キーポリシー
注意: カスタマーマネージドキーなら、誰が使えるかを決められ、使った記録が CloudTrail に残ります。
関連: 暗号化

### Secrets Manager
別名: AWS Secrets Manager、Parameter Store
試験: SAA、K8s
要約: パスワードなどの秘密情報を保存し、自動で替えるサービスです。
パスワードなどの秘密情報を保存し、自動で入れ替える(ローテーション)サービスです。入れ替えが不要で少数なら、Systems Manager の Parameter Store も使えます。
例: RDS のパスワードの自動ローテーション
注意: 自動のローテーションが要らない設定値なら、Systems Manager の Parameter Store でも足ります。
関連: 秘密情報

### CloudFormation
別名: AWS CloudFormation
試験: SAA、Terraform
要約: AWS のリソースを、テンプレート(YAML や JSON)で作る IaC のサービスです。
AWS の IaC のサービスです。JSON や YAML のテンプレートで、AWS のリソースをまとめて作ります。Terraform と違い、AWS 専用です。
例: スタック、変更セット、ドリフトの検出
注意: AWS だけが対象です。複数のクラウドや SaaS をまとめるなら Terraform を使います。
関連: IaC、Terraform

### AWS CodePipeline
別名: CodePipeline
試験: DOP
要約: ソースの取得から、ビルド、テスト、デプロイまでの流れを、自動でつなぐ AWS のサービスです。
流れを、ステージとアクションに分けて作ります。コードの変更を見つけて、自動で最後まで進めます。
例: ソース、ビルド、承認、デプロイの 4 つのステージを作る
注意: CodePipeline は流れをつなぐもので、ビルドは CodeBuild、デプロイは CodeDeploy が行います。
関連: AWS CodeBuild、AWS CodeDeploy、CI/CD

### AWS CodeBuild
別名: CodeBuild
試験: DOP
要約: ソースのビルドやテストを、サーバーを持たずに実行する AWS のサービスです。
`buildspec.yml` に、実行する手順を書きます。実行した分だけ料金がかかり、終わると環境は消えます。
例: `buildspec.yml` に、`npm test` を実行する手順を書く
注意: ビルドの環境は毎回新しくなるので、速くするには、キャッシュを設定します。
関連: AWS CodePipeline、CI/CD

### AWS CodeCommit
別名: CodeCommit
試験: DOP
要約: AWS が提供する、Git のリポジトリのサービスです。
IAM で認証します。CodePipeline の、ソースとして使えます。
例: CodeCommit のリポジトリの変更で、パイプラインを始める
注意: 2024 年 7 月に新しい利用者の受け付けを止めましたが、2025 年 11 月 24 日に、通常の提供に戻りました。
関連: AWS CodePipeline

### 手動承認アクション
別名: 手動承認、Manual approval
試験: DOP
要約: CodePipeline で、人が承認するまで、流れを止めておく仕組みです。
本番へのデプロイの前などに入れます。通知を受けた人が、承認か却下を選びます。
例: 本番のデプロイの前に、責任者の承認を入れる
注意: 承認の通知は、SNS などで送り、承認する権限を持つ人だけに、IAM で許可します。
関連: AWS CodePipeline、SNS

### AWS CodeArtifact
別名: CodeArtifact
試験: DOP
要約: npm や PyPI などのパッケージを、保管して配る AWS のサービスです。
外部の公開リポジトリを、上流につなげることができます。社内で作ったパッケージの共有にも使えます。
例: 社内のチームで使う Python のパッケージを、CodeArtifact で共有する
注意: コンテナのイメージは ECR、ビルドの成果物は S3 と、置く場所が分かれます。
関連: AWS CodeBuild、ECR

### AWS CodeDeploy
別名: CodeDeploy
試験: DOP
要約: アプリを、EC2、オンプレミス、Lambda、ECS にデプロイする AWS のサービスです。
デプロイの方式を選べます。EC2 ではインプレースやブルー/グリーン、Lambda と ECS ではブルー/グリーンのほか、カナリアなどがあります。
例: `appspec.yml` に、配置の手順を書いて、EC2 にデプロイする
注意: 対象によって、使える方式が違います。
関連: インプレースデプロイ、カナリアリリース、AWS CodePipeline

### インプレースデプロイ
別名: In-place deployment、インプレース
試験: DOP
要約: 今動いているサーバーの上で、そのままアプリを新しい版に入れ替える方式です。
新しいサーバーは作りません。入れ替え中は、サーバーを止めるので、一部ずつ進めるなどで、サービスを止めない工夫をします。
例: 10 台のうち 2 台ずつ、順番に新しい版にする
注意: 戻すときは、もう一度、古い版をデプロイし直すので、ブルー/グリーンより戻しに時間がかかります。
関連: AWS CodeDeploy、カナリアリリース

### CloudFormation の変更セット
別名: 変更セット、Change Set
試験: DOP
要約: スタックを更新する前に、何が変わるかを確かめる仕組みです。
更新の内容を作って、追加、変更、削除されるリソースを一覧で見られます。確認してから、実行できます。
例: データベースが置き換えられると分かったので、実行をやめる
注意: 変更セットは、置き換えが起きるかを教えますが、実行するまでは、何も変わりません。
関連: CloudFormation、ネストされたスタック

### ネストされたスタック
別名: Nested Stacks
試験: DOP
要約: CloudFormation のテンプレートの中から、別のスタックを呼び出す方法です。
共通の部品(ネットワークなど)を、別のテンプレートにして、使い回せます。1 つのテンプレートが大きくなるのを防ぎます。
例: VPC のテンプレートを、複数のシステムから呼び出す
注意: 親のスタックを通して更新し、子のスタックを直接変えないようにします。
関連: CloudFormation、CloudFormation の変更セット

### CloudFormation StackSets
別名: StackSets、スタックセット
試験: DOP
要約: 1 つのテンプレートを、複数のアカウントやリージョンにまとめて展開する機能です。
Organizations と組み合わせると、新しいアカウントにも、自動で展開できます。
例: 全アカウントに、同じ監査用の IAM ロールを配る
注意: 1 つのアカウントの中の、スタックの分け方を整理する、ネストされたスタックとは目的が違います。
関連: CloudFormation、AWS Organizations

### AWS CDK
別名: CDK、AWS Cloud Development Kit
試験: DOP
要約: プログラミング言語で、AWS の構成を書ける、IaC の道具です。
TypeScript や Python などで書くと、CloudFormation のテンプレートが作られます。繰り返しや条件を、言語の機能で書けます。
例: TypeScript で VPC を書き、`cdk deploy` で作る
注意: CDK が作るのは CloudFormation のテンプレートで、実際の展開は CloudFormation が行います。
関連: CloudFormation

### DeletionPolicy
別名: 削除ポリシー
試験: DOP
要約: CloudFormation で、スタックを消したときに、リソースを残すかどうかを決める属性です。
Delete は削除し、Retain は残し、Snapshot はスナップショットをとってから消します。データベースなど、消したくないリソースに付けます。
例: データベースに `DeletionPolicy: Snapshot` を付ける
注意: スタックを消す前に、スタックの更新で付けておきます。置き換えで古いリソースが消えるのを防ぐのは、別の属性の UpdateReplacePolicy です。
関連: CloudFormation、スタックポリシー

### スタックポリシー
別名: Stack Policy
試験: DOP
要約: CloudFormation のスタックの、特定のリソースの更新を、禁止する仕組みです。
重要なリソースが、更新で変わったり置き換わったりするのを防ぎます。終了保護(スタックそのものの削除を防ぐ設定)とは、別のものです。
例: データベースへの更新を、スタックポリシーで拒否する
注意: スタックポリシーは更新を防ぎ、終了保護は、スタックの削除を防ぎます。
関連: CloudFormation、DeletionPolicy

### Run Command
別名: Systems Manager Run Command
試験: DOP
要約: Systems Manager で、複数のサーバーに、同じコマンドをまとめて実行する機能です。
SSH でログインせずに、タグなどで対象を選んで実行できます。実行の結果は、記録に残ります。
例: タグが付いた全サーバーで、パッチの適用のコマンドを実行する
注意: 対象のサーバーに、SSM エージェントと、そのための権限が要ります。
関連: Systems Manager、State Manager

### State Manager
別名: Systems Manager State Manager
試験: DOP
要約: サーバーを、決めた状態に保つ、Systems Manager の機能です。
決めた設定を、定期的に適用して、ずれたら、元に戻します。
例: 全サーバーで、エージェントが入っている状態を保つ
注意: 一度だけ実行するのは Run Command、状態を保ち続けるのは State Manager です。
関連: Systems Manager、Run Command

### メンテナンスウィンドウ
別名: Maintenance Windows
試験: DOP
要約: Systems Manager で、作業をしてよい時間帯を決めて、その間に作業を実行する機能です。
パッチの適用など、サービスに影響が出る作業を、決めた時間にまとめて実行します。
例: 毎週日曜の深夜に、パッチを適用する
注意: 時間帯を決めるものなので、何を実行するかは、別に指定します。
関連: Systems Manager、Run Command

### Systems Manager Automation
別名: SSM Automation、AWS Systems Manager Automation
試験: DOP
要約: 運用の手順を、自動で実行する Systems Manager の機能です。
手順を、ランブック(Automation のドキュメント)として書き、実行します。EC2 の再起動や、AMI の作成などを自動で行えます。
例: アラームが鳴ったら、Automation で、インスタンスを再起動する
注意: 1 つのコマンドを実行する Run Command と違い、複数の手順をつなげられます。
関連: Systems Manager、自動修復

### Amazon CloudWatch Logs
別名: CloudWatch Logs
試験: DOP
要約: アプリやサービスのログを、集めて保管し、調べられる CloudWatch の機能です。
ログは、ロググループとログストリームに分けて入ります。保持する期間を、ロググループごとに決められます。
例: Lambda のログが、自動でロググループに入る
注意: 保持期間を決めないと、ログは消えずに残り続け、保管の費用が増えます。
関連: CloudWatch、CloudWatch Logs Insights

### メトリクスフィルター
別名: Metric Filter
試験: DOP
要約: ログの中の特定の文字を数えて、メトリクスにする CloudWatch Logs の機能です。
ログに「ERROR」が出た回数を数えて、メトリクスにし、アラームを付けられます。
例: ログの ERROR の回数を、メトリクスにして、アラームを付ける
注意: 設定したあとに出たログだけが対象で、過去のログは数えません。
関連: Amazon CloudWatch Logs、CloudWatch アラーム

### カスタムメトリクス
別名: Custom Metrics
試験: DOP
要約: AWS が最初から用意していない、自分のアプリのメトリクスを、CloudWatch に送ることです。
`PutMetricData` の API で送るか、ログに決まった形の JSON(埋め込みメトリクスフォーマット、EMF)を書いて、メトリクスに変えてもらいます。
例: アプリが、注文の件数を、メトリクスとして送る
注意: メトリクスの種類が増えると、費用も増えます。
関連: CloudWatch、Amazon CloudWatch Logs

### サブスクリプションフィルター
別名: Subscription Filter
試験: DOP
要約: CloudWatch Logs のログを、ほかのサービスや別のアカウントに、リアルタイムで流す設定です。
Kinesis や Lambda などに送れ、複数のアカウントのログを、1 つのアカウントに集めるのにも使います。
例: 複数のアカウントのログを、集約用のアカウントの Kinesis に流す
注意: 設定したあとに出たログから流れ、過去のログは流れません。
関連: Amazon CloudWatch Logs、Kinesis

### CloudWatch アラーム
別名: CloudWatch Alarm
試験: DOP
要約: メトリクスが決めた条件になったとき、通知や動作を起こす CloudWatch の機能です。
しきい値を超えたときに、SNS で通知したり、Auto Scaling を動かしたりします。状態は、OK、ALARM、INSUFFICIENT_DATA のどれかです。
例: CPU の使用率が 80% を 5 分続けて超えたら、SNS で通知する
注意: データが足りないと INSUFFICIENT_DATA になり、異常とは限りません。
関連: CloudWatch、SNS、複合アラーム

### 複合アラーム
別名: Composite Alarm
試験: DOP
要約: 複数のアラームを、AND や OR で組み合わせて、1 つのアラームにする機能です。
たとえば、CPU が高い、かつ、エラーが多いときだけ知らせる、という条件を作れます。通知の数を減らせます。
例: 2 つのアラームが両方 ALARM のときだけ、通知する
注意: 複合アラームは、基になるアラームの状態を組み合わせるもので、メトリクスを直接見るのではありません。
関連: CloudWatch アラーム

### CloudWatch の異常検出
別名: CloudWatch Anomaly Detection
試験: DOP
要約: メトリクスの、ふだんの動きを学んで、外れた動きを見つける CloudWatch の機能です。
固定のしきい値の代わりに、時間帯や曜日の違いを学んだ、正常な範囲を作ります。範囲を外れるとアラームにできます。
例: 平日と週末で、アクセスの量が違うシステムに使う
注意: 学習に時間がかかり、使い始めは、うまく検出できないことがあります。
関連: CloudWatch アラーム

### CloudWatch Logs Insights
別名: Logs Insights
試験: DOP
要約: CloudWatch Logs のログを、専用の問い合わせの言葉で調べる機能です。
フィールドで絞り込み、件数を集計し、時間ごとの変化を見られます。複数のロググループを、まとめて調べられます。
例: エラーのログを、5 分ごとに集計する
注意: 調べたログの量で料金がかかるので、期間とロググループを絞ります。
関連: Amazon CloudWatch Logs

### CloudWatch Synthetics
別名: Synthetics、Synthetics Canary
試験: DOP
要約: 決めた手順で、定期的にサイトや API にアクセスして、動いているかを確かめる機能です。
利用者の代わりに、外から決まった操作をして、応答や画面を確かめます。利用者が気づく前に、障害を見つけられます。
例: ログインから購入までの流れを、5 分ごとに確かめる
注意: 実際の利用者の通信ではなく、決めたスクリプトの結果なので、本物の利用者の状況とは、完全には同じではありません。
関連: 外形監視、CloudWatch アラーム

### AWS Health
別名: AWS Health Dashboard
試験: DOP
要約: AWS のサービスの障害や、利用者の資源に関わる予定を知らせる AWS のサービスです。
AWS 側の障害や、メンテナンス、非推奨の予定などを、アカウントの影響と合わせて見られます。EventBridge で、通知や自動化に使えます。
例: 自分の EC2 の、メンテナンスの予定のイベントを、EventBridge で通知する
注意: 利用者自身のアプリの障害ではなく、AWS 側の出来事を知らせます。
関連: EventBridge、CloudWatch

### AWS X-Ray
別名: X-Ray
試験: SAA、DOP
要約: リクエストが、複数のサービスをどう通ったかを追跡する AWS のサービスです。
サービス間のつながりを図にした「サービスマップ」で、どこで遅れているか、どこでエラーが出ているかが見えます。
例: API Gateway から Lambda、DynamoDB までの、リクエストの時間を見る
注意: 追跡するには、アプリや Lambda などの設定で、X-Ray を有効にする必要があります。X-Ray の SDK とデーモンは 2026 年 2 月 25 日から保守だけの段階で、新しく組み込むときは OpenTelemetry が勧められています。
関連: トレース、可観測性

### スロットリング
別名: Throttling、ThrottlingException
試験: SAA、DOP
要約: AWS の API やサービスが、一度に来すぎたリクエストを、一部断る動作です。
決められた上限を超えると、リクエストが拒否されます。再試行する間隔を空ける(指数バックオフ)ことで、対処します。
例: Lambda の同時実行の上限を超えて、呼び出しが拒否される
注意: 上限が足りないときは、再試行の工夫に加えて、サービスクォータの引き上げも検討します。
関連: サービスクォータ、API Gateway

### サービスクォータ
別名: Service Quotas、サービスの上限
試験: SAA
要約: AWS のサービスごとに決まっている、使える量の上限です。
上限の多くは、申請して引き上げられます。システムの規模が大きくなると、上限に当たる前に、確認しておく必要があります。
例: 同時に動かせる EC2 のオンデマンドインスタンスの vCPU の数の上限
注意: 引き上げには時間がかかることがあるので、前もって申請します。
関連: スロットリング

### AWS Incident Manager
別名: AWS Systems Manager Incident Manager、Incident Manager
試験: DOP
要約: インシデントの対応を、連絡の順番や手順とあわせて管理する AWS のサービスです。
アラームなどをきっかけに、対応の窓口と、連絡の順番(エスカレーションプラン)を決めておきます。
例: アラームが鳴ったら、担当者に連絡し、応答がなければ次の人に回す
注意: 2025 年 11 月 7 日から、新しい利用者を受け付けていません。すでに使っているアカウントでは、続けて使えます。
関連: インシデント、オンコール

### Amazon Q Developer in chat applications
別名: AWS Chatbot
試験: DOP
要約: AWS の通知を、Slack や Microsoft Teams などのチャットに送る AWS のサービスです。
SNS 経由の通知を、チャットで受け取り、チャットから一部の操作もできます。運用チームがすぐ気づけます。
例: CloudWatch アラームの通知を、Slack のチャンネルに送る
注意: 2025 年 2 月に、AWS Chatbot から今の名前に変わりました。試験や古い資料では、AWS Chatbot と書かれていることがあります。
関連: SNS、CloudWatch アラーム

### Amazon Detective
別名: Detective
試験: DOP
要約: セキュリティの検出結果の、原因を調べるのを助ける AWS のサービスです。
GuardDuty などの検出結果について、関わるリソースや、時間の流れをたどれます。
例: GuardDuty の警告の、元の IP アドレスの動きを調べる
注意: 検出はしません。検出は GuardDuty の役目で、Detective は、原因の調査です。
関連: GuardDuty

### CloudTrail ログファイルの整合性検証
別名: ログファイルの検証、log file integrity validation
試験: DOP
要約: CloudTrail のログが、あとから書き換えられていないかを確かめる機能です。
有効にすると、ログのハッシュを入れたダイジェストファイルが作られます。コマンドで確かめると、改ざんや削除を見つけられます。
例: 監査のときに、ログが改ざんされていないことを示す
注意: 改ざんを防ぐのではなく、見つけるものです。防ぐには、S3 Object Lock などを使います。
関連: CloudTrail、S3 Object Lock

## データ分析と機械学習

### AWS Glue
別名: Glue
試験: SAA
要約: データの形を整えて移す(ETL)と、データの一覧(カタログ)を持つ、AWS のサービスです。
S3 などにあるデータの、形の情報をカタログに登録し、Athena などから使えるようにします。サーバーを持たずに、データの変換ができます。
例: S3 の CSV を Glue で Parquet に変換して、Athena で調べる
注意: カタログの登録と、変換の処理は、別の役目です。
関連: Athena、S3、データレイク

### AWS Lake Formation
別名: Lake Formation
試験: SAA
要約: データレイクを作り、データごとの利用の権限を、まとめて管理する AWS のサービスです。
S3 のデータに対して、表や列の単位で、誰が見られるかを決めます。複数のサービスから使われるデータの権限を、1 か所で管理できます。
例: 営業のチームには、個人情報の列を除いて見せる
注意: データを分析するサービスではなく、権限の管理の役目です。
関連: データレイク、AWS Glue、S3

### Parquet
別名: Apache Parquet
試験: SAA
要約: データを、列ごとにまとめて保存する(列指向の)、分析向けのファイル形式です。
必要な列だけを読めるので、読む量が減り、Athena のような、読んだ量で料金がかかるサービスで、安く速くなります。圧縮もよく効きます。
例: CSV のログを Parquet に変換して、Athena の料金を減らす
注意: 行ごとに読み書きする業務のデータには向きません。
関連: Athena、AWS Glue

### Amazon AppFlow
別名: AppFlow
試験: SAA
要約: SaaS のアプリと AWS の間で、データを自動でやり取りする AWS のサービスです。
コードを書かずに、SaaS から S3 などへデータを移す流れを作れます。
例: Salesforce のデータを、毎日 S3 に取り込む
注意: 自作のアプリのデータの移行ではなく、SaaS との連携に使います。
関連: S3

### Amazon Comprehend
別名: Comprehend
試験: SAA
要約: 文章を解析して、感情や、人名、場所などを取り出す、AWS の AI のサービスです。
機械学習の知識がなくても、API で文章の分析ができます。
例: 顧客のレビューから、良い評価か悪い評価かを判定する
注意: 文章を解析するもので、音声や画像を扱うものではありません。
関連: Amazon Polly

### Amazon Polly
別名: Polly
試験: SAA
要約: 文章を、自然な音声に変える AWS のサービスです。
テキストを渡すと、音声のデータが返ります。ニュースの読み上げや、案内の音声に使えます。
例: ブログの記事を、音声で聞けるようにする
注意: 音声を文字にするのは、Polly ではなく、別のサービス(Amazon Transcribe)です。
関連: Amazon Comprehend
