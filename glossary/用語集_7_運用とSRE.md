# 用語集 運用と SRE

## 信頼性の指標

### SRE
別名: Site Reliability Engineering
要約: ソフトウェアの技術で、サービスの信頼性を運用する考え方と職種です。
ソフトウェアの技術で、サービスの信頼性を保つ運用の考え方と仕事です。SLO を決め、手作業(トイル)を自動化し、障害から学んで仕組みを直します。
例: SLO、エラーバジェット、トイルの削減、ポストモーテム
注意: 「止めない」ことではなく、決めた信頼性を、変化の速さと釣り合わせて保つことが目的です。
関連: SLO、トイル、ポストモーテム

### SLI
別名: Service Level Indicator
要約: サービスの信頼性を測る指標です。
サービスの信頼性を計る指標です。成功したリクエストの割合や、決めた時間の中で返った割合などです。
例: 成功したリクエストの割合、300 ms 以内に返したリクエストの割合
注意: 利用者の体験に近いもの(エラー率、遅延)を選びます。CPU の使用率は SLI に向きません。
関連: SLO

### SLO
別名: Service Level Objective
要約: SLI について決めた目標の値です。
SLI の目標です(例: 30 日間で 99.9% のリクエストが成功する)。100% を目指さず、利用者が満足する水準に決めます。
例: 30 日間で、リクエストの 99.9% が成功する
注意: 100% は目標にしません。変更の余地(エラーバジェット)がなくなるためです。
関連: SLI、SLA、エラーバジェット

### SLA
別名: Service Level Agreement
要約: 利用者との契約として約束する信頼性と、守れなかったときの補償です。
利用者との契約で約束する水準です。守れないと、返金などの補償があります。普通は SLO より低くします。
例: 月間の稼働率 99.9% を下回ったら、料金の一部を返す
注意: SLO は社内の目標で、SLA より厳しく決めておきます。
関連: SLO

### エラーバジェット
要約: SLO の範囲で許される失敗の量です。
SLO で許される失敗の量です(100% − SLO。99.9% なら 0.1%)。残っていれば新しい機能を出し、使い切りそうなら信頼性の改善を優先する、という判断に使います。
例: 99.9% なら 30 日で約 43 分の停止まで
注意: 使い切ったら、新しい機能より信頼性の改善を優先する、と事前に決めておきます。
関連: SLO、バーンレート

### バーンレート
要約: エラーバジェットを使う速さです。
エラーバジェットを消費する速さです。速く消費しているときにアラートを出すと、利用者への影響が大きい問題だけを知らせられます。
例: バーンレート 1 なら期間のちょうど終わりに使い切る、14.4 なら 1 時間で 2% を使う
注意: アラートは、エラーの数ではなくバーンレートで決めると、誤報が減ります。
関連: エラーバジェット、アラート

### 可用性
別名: アベイラビリティー
要約: サービスが使える状態にある時間の割合です。
サービスが使える状態にある時間の割合です。99.9% なら、1 か月で約 43 分止まってよいことになります。
例: 99.9%(年に約 8.8 時間の停止)、99.99%(年に約 53 分)
注意: 9 が 1 つ増えるごとに、止まってよい時間は 10 分の 1 になり、費用は大きく増えます。
関連: 冗長化、SLO

### MTTR
別名: MTBF
要約: 障害から復旧するまでにかかる時間の平均です。
障害から復旧するまでの平均の時間です(Mean Time To Recovery)。故障と故障の間の平均の時間は MTBF です。障害を減らすだけでなく、早く直せる仕組みも大事です。
例: MTTR(復旧の時間)、MTBF(故障の間隔)
注意: 障害を減らすだけでなく、早く見つけて早く直すことでも可用性は上がります。
関連: インシデント、可用性

## 設計と冗長化

### 冗長化
別名: 冗長構成
要約: 同じ役割のものを複数用意して、1 つが壊れても止まらないようにすることです。
同じ役割のものを複数用意し、1 つが壊れても続けられるようにすることです。1 つしかなく、止まると全体が止まる箇所を単一障害点(SPOF)と呼びます。
例: マルチ AZ、複数のレプリカ、HSRP、RAID
注意: 冗長化しても、切り替えを試していなければ、障害のときに動かないことがあります。
関連: 可用性、フェイルオーバー、単一障害点

### 単一障害点
別名: SPOF
試験: SAA
要約: そこが壊れるとシステム全体が止まる部分です。
そこが止まるとシステム全体が止まる箇所です。冗長化してなくします。
例: 1 台だけのデータベース、1 つの AZ だけの NAT ゲートウェイ
注意: 設定、証明書、DNS、人(1 人しか分からない作業)も単一障害点になります。
関連: 冗長化

### スケーリング
別名: スケールアウト、スケールアップ
要約: 負荷に合わせて、資源を増やしたり減らしたりすることです。
負荷に合わせて能力を変えることです。台数を増やすのがスケールアウト(水平)、1 台を大きくするのがスケールアップ(垂直)です。
例: スケールアウト(台数を増やす)、スケールアップ(性能を上げる)
注意: スケールアウトするには、サーバーに状態を持たせない(ステートレス)設計にします。
関連: Auto Scaling、HPA

### キャパシティプランニング
要約: 将来の負荷を見積もり、必要な資源を前もって用意することです。
今後の利用の伸びを見込んで、必要な資源(サーバー、ストレージ、ネットワーク)を前もって計画することです。
例: 過去の使用量の伸びから、半年後のディスクの容量を見積もる
注意: ピーク(セール、月末)と、成長の両方を考えます。
関連: スケーリング

### グレースフルシャットダウン
別名: graceful shutdown
試験: K8s、Docker
要約: 処理中のリクエストを終えてから、プロセスを止めることです。
止める合図(SIGTERM)を受けたら、新しい受け付けをやめ、処理中のものを終えてから終わることです。受け付けの途中のリクエストを落とさずに済みます。
例: SIGTERM を受けたら新しい受け付けを止め、処理中のものを終えてから終了する
注意: Kubernetes では、preStop で数秒待ち、Service から外れるのを待つのが一般的です。
関連: シグナル

### カオスエンジニアリング
要約: わざと障害を起こして、システムが耐えられるかを確かめる方法です。
本番に近い環境で、わざと障害を起こし、システムが期待どおりに耐えるかを確かめる方法です。
例: Pod やノードを止める、遅延を入れる、AWS Fault Injection Service
注意: 影響の範囲を小さくし、すぐ止められる準備をしてから行います。
関連: 冗長化、可用性

### Pacemaker
試験: LinuC202
要約: 高可用性クラスターで、サービスを動かすノードを決める管理ソフトです。
クラスターのリソース(サービス、仮想 IP アドレス、共有ストレージなど)を、どのノードで動かすかを決めます。ノードが落ちると、別のノードでリソースを起動します。ノードの生死の確認は Corosync に任せます。
例: `pcs status`、`pcs resource create web ocf:heartbeat:apache`
注意: Pacemaker はノード同士の通信を受け持ちません。通信は Corosync の役割です。
関連: Corosync、フェイルオーバー、冗長化

### Corosync
試験: LinuC202
要約: クラスターのノード同士が通信して、仲間の生死を確かめ合う仕組みです。
クラスターのノード同士が、ハートビートの通信で互いの状態を確かめ合います。どのノードがクラスターの仲間かを管理し、Pacemaker に伝えます。
例: `corosync-cfgtool -s`、`/etc/corosync/corosync.conf`
注意: ハートビートが途切れると、スプリットブレインが起きるおそれがあります。
関連: Pacemaker、スプリットブレイン

### スプリットブレイン
別名: split brain
試験: LinuC202
要約: クラスターの通信が途切れ、両方のノードが自分だけが生きていると思い込む状態です。
両方のノードがサービスを動かし、同じデータを同時に書くと、データが壊れるおそれがあります。過半数のノードが見えるときだけ動くようにする(クォーラム)、相手のノードを強制的に止める(フェンシング)などで防ぎます。
例: 2 台のノードを結ぶ 1 本のケーブルが抜けて、両方が仮想 IP アドレスを持った
注意: ノード間の通信を複数の経路にしないと、通信の障害だけで起きます。
関連: Pacemaker、Corosync、冗長化

### ステートレス
試験: LinuC202
要約: サーバーが、利用者ごとの状態を持たない作りです。
サーバーが、ログインの状態などを自分の中に持たない作りです。どのサーバーに当たっても同じように動くので、台数を自由に増減できます。状態は、データベースや Redis などの共通のストアに置きます。
例: セッション情報を Redis に置く Web サーバー
注意: 状態をサーバーのメモリに持つと、台数を増やしたときにログインが切れます。
関連: スケーリング、ロードバランサー

### 3 層構成
別名: 三層構成、3 層アーキテクチャ
試験: LinuC202
要約: システムを、Web、アプリケーション、データの 3 つの層に分ける構成です。
画面を返す Web 層、業務の処理をするアプリケーション層、データを保存するデータ層に分けます。層ごとに台数や性能を変えられ、層の間の通信も必要なところだけ許可できます。
例: nginx(Web)、PHP のアプリ(AP)、MySQL(DB)
注意: 外から直接つなげるのは Web 層だけにし、データ層は外から届かない場所に置きます。
関連: ロードバランサー、冗長化

### LAMP
別名: LAPP
試験: LinuC202
要約: Linux、Apache、MySQL、PHP を組み合わせた、Web システムの定番の構成です。
Linux、Apache HTTP Server、MySQL(または MariaDB)、PHP の頭文字です。データベースが PostgreSQL の組み合わせは LAPP と呼びます。
例: LAMP の 1 台構成の Web サーバー
注意: 1 台にすべてを入れると、その 1 台が単一障害点になります。
関連: 3 層構成、単一障害点

### フェンシング
別名: STONITH
試験: LinuC3PS
要約: 故障や孤立が疑われるノードを、電源を切るなどして、確実に止める仕組みです。
2 つのノードが、同時に同じデータに書いてしまうこと(スプリットブレイン)を防ぎます。クラスタの管理ソフト(Pacemaker など)が行います。
例: IPMI で、相手のサーバーの電源を切る
注意: 相手が本当に止まったことを確かめてから、引き継ぎます。
関連: スプリットブレイン、Pacemaker

### 仮想 IP アドレス
別名: VIP
試験: LinuC3PS
要約: 複数の機器で共有し、持っている機器が入れ替わる IP アドレスです。
利用者はいつも同じアドレスへ接続し、そのアドレスを持つ機器が故障すると、別の機器がアドレスを引き継ぎます。keepalived(VRRP)や Pacemaker の `IPaddr2` で付け替えます。
例: `192.0.2.100/24` を lb1 と lb2 で共有する
注意: 引き継いだあと、周りの機器が古い MAC アドレスを覚えていると、つながりません。付け替えのときに、ARP でお知らせ(GARP)を出します。
関連: HSRP、フェイルオーバー、冗長化

### keepalived
試験: LinuC3PS
要約: VRRP で仮想 IP アドレスを持ち回り、IPVS の設定とヘルスチェックもできるソフトです。
`/etc/keepalived/keepalived.conf` に、`vrrp_instance` で VRRP のグループを、`vrrp_script` で動作の確認を、`virtual_server` で IPVS の設定を書きます。優先度が最も高い機器が MASTER になり、仮想 IP アドレスを持ちます。
例: `systemctl enable --now keepalived`、`journalctl -u keepalived`
注意: `vrrp_script` の `weight` が小さすぎると、失敗しても優先度が相手より下がらず、切り替わりません。
関連: 仮想 IP アドレス、HSRP、IPVS

### クォーラム
別名: quorum
試験: LinuC3PS
要約: クラスタが動いてよいと決める、過半数の票です。
N 台のクラスタで、過半数(N ÷ 2 の切り上げ。3 台なら 2、5 台なら 3)の票が見えるノードだけが、リソースを動かせます。分断されたとき、片方だけが動くので、スプリットブレインを防げます。
例: 5 台が 3 台と 2 台に分かれると、3 台の側だけが動く
注意: 2 台のクラスタは、1 台が見えなくなると過半数に届きません。`two_node: 1` で特別に扱い、STONITH を併用します。
関連: スプリットブレイン、Corosync、Pacemaker

### リソースエージェント
別名: OCF、resource agent
試験: LinuC3PS
要約: Pacemaker が、サービスの起動、停止、確認をするための、決まった形のスクリプトです。
`標準:提供元:名前` の形で指定します。仮想 IP アドレスは `ocf:heartbeat:IPaddr2`、ファイルシステムは `ocf:heartbeat:Filesystem`、PostgreSQL は `ocf:heartbeat:pgsql` です。systemd のサービスは `systemd:httpd` のように指定します。
例: `pcs resource create vip ocf:heartbeat:IPaddr2 ip=192.0.2.100 cidr_netmask=24`
注意: パラメータは、エージェントごとに違います。`pcs resource describe ocf:heartbeat:IPaddr2` で確かめます。
関連: Pacemaker、仮想 IP アドレス

## 監視と可観測性

### 監視
別名: モニタリング
要約: システムの状態を見張り、異常を見つけることです。
システムの状態を計り続け、問題を見つけることです。利用者から見た症状(エラー、遅延)を中心に見ます。
例: 死活監視、メトリクスのしきい値、外からの合成監視
注意: 何を見張るかは、利用者への影響(SLI)から決めます。
関連: メトリクス、アラート、可観測性

### 可観測性
別名: オブザーバビリティ
要約: 外に出した情報から、システムの中で何が起きているかを分かるようにする性質です。
外から見えるデータ(メトリクス、ログ、トレース)で、システムの中で何が起きているかを理解できる度合いです。
例: メトリクス、ログ、トレース(3 つの柱)
注意: 監視は既知の問題を見つけ、可観測性は未知の問題の原因を探すのに役立ちます。
関連: メトリクス、トレース、監視

### メトリクス
試験: K8s、SAA
要約: 時間ごとに記録する数値の指標です。
CPU の使用率、リクエストの数、エラーの率、遅延のような、時系列の数値のデータです。
例: CPU の使用率、リクエストの数、エラー率、遅延の p99
注意: 平均ではなくパーセンタイル(p95、p99)で遅延を見ると、一部の利用者の遅さに気づけます。
関連: 可観測性、Prometheus

### ログ
要約: 出来事を時刻とともに記録したものです。
出来事の記録です。いつ、何が起きたかを後から調べるのに使います。サーバーやコンテナが消えても残るよう、外の基盤(CloudWatch Logs、Loki など)に集めます。
例: アプリのログ、アクセスログ、`journalctl`、CloudWatch Logs
注意: JSON などの構造化したログにすると、検索と集計がしやすくなります。
関連: 可観測性、標準出力

### トレース
別名: 分散トレーシング
要約: 1 つのリクエストが通ったサービスと、それぞれの時間を記録したものです。
1 つのリクエストが、どのサービスをどの順で通り、それぞれにどれだけ時間がかかったかの記録です。OpenTelemetry で計測します。
例: OpenTelemetry、Jaeger、Grafana Tempo、AWS X-Ray
注意: 複数のサービスをまたぐ遅延の場所を探すのに使います。
関連: 可観測性

### ゴールデンシグナル
別名: RED
要約: 監視で最初に見るべき 4 つの指標です。
監視で特に見るべき 4 つの値です。遅延、トラフィック(量)、エラー、飽和(資源の使い切りの度合い)です。リクエストの数(Rate)、エラー(Errors)、時間(Duration)の 3 つを見る RED という考え方もあります。
例: 遅延、トラフィック、エラー、飽和度(リソースの使い切り具合)
注意: エラーの応答の遅延は、成功の遅延と分けて見ます。
関連: 監視、遅延

### 遅延
別名: レイテンシ
試験: CCNA、SAA、K8s、Docker
要約: リクエストを送ってから応答が返るまでの時間です。
リクエストを送ってから応答が返るまでの時間です。平均だけでなく、遅いほうの値(99 パーセンタイルなど)も見ます。
例: p50、p95、p99、ネットワークの RTT
注意: 平均だけを見ると、一部の遅いリクエストが隠れます。
関連: メトリクス

### Prometheus
別名: Grafana
試験: K8s
要約: メトリクスを定期的に集めて保存し、検索する監視の道具です。
メトリクスを集めて保存し、検索やアラートに使う監視の道具です。対象の `/metrics` を定期的に取りに行きます。Grafana はダッシュボードを作る道具で、組み合わせて使います。
例: PromQL `rate(http_requests_total{code=~"5.."}[5m])`、Alertmanager、Grafana
注意: Prometheus から取りに行く方式(プル型)です。短い処理のジョブは Pushgateway を使います。
関連: メトリクス、metrics-server

### ダッシュボード
要約: 大事な指標を 1 つの画面にまとめたものです。
メトリクスなどをグラフにして、一目で状態が分かるようにまとめた画面です。
例: Grafana、CloudWatch のダッシュボード
注意: 見る人(オンコール、開発、経営)ごとに、必要な指標に絞ります。
関連: Prometheus、メトリクス

### アラート
要約: 異常を、人や仕組みに知らせることです。
監視の結果から、人に対応を知らせることです。すぐに人が対応すべきものだけにしないと、多すぎて大事なものを見逃します(アラート疲れ)。
例: Alertmanager、CloudWatch のアラーム、PagerDuty
注意: 対応が要らないアラートは減らします。鳴りすぎると、本当の異常を見落とします。
関連: 監視、オンコール

### Zabbix
試験: LinuC201
要約: 収集、保存、画面、グラフ、通知まで 1 つで扱う、監視のツールです。
エージェントや SNMP で値を集め、データベースに溜めます。しきい値を超えると、アラートを出します。
例: Zabbix の画面で、サーバーごとの CPU のグラフを見る、ディスクの空きが少なくなったら通知する
注意: Nagios や Icinga2 とは別の製品です。
関連: SNMP、監視、アラート

### 死活監視
試験: LinuC201
要約: 対象が、動いているか(生きているか)を、確かめる監視です。
`ping` の応答、ポートへの接続、HTTP の応答、プロセスがいるか、などを確かめます。止まったら、すぐに通知します。
例: `ping` の応答の確認、HTTP が 200 を返すかの確認
注意: 動いていることと、正しく動いていることは違います。中身を確かめる監視も要ります。
関連: 監視、ヘルスチェック

### ローレベルディスカバリ
別名: LLD、Low-Level Discovery
試験: LinuC3PS
要約: Zabbix で、ホストの中にある数が決まっていないものを、自動で見つけて監視を作る機能です。
ファイルシステムやネットワークインターフェースなどを見つけ、アイテムとトリガーのプロトタイプから、見つかった数だけ作ります。`{#FSNAME}` のようなマクロに名前が入ります。
例: `vfs.fs.discovery`、`net.if.discovery`
注意: ホストそのものを見つけるのは、ネットワークディスカバリと自動登録です。
関連: Zabbix、監視

## 障害対応

### オンコール
要約: 決まった時間、障害の知らせに対応できるように待機することです。
障害の対応のために、決まった時間に呼び出しを受けられるようにしておく当番です。
例: 当番のローテーション、エスカレーションの手順
注意: 夜中に起こされる数を数えて、減らす改善につなげます。
関連: アラート、インシデント

### インシデント
要約: サービスの停止や品質の低下など、対応が必要な出来事です。
サービスが止まったり、遅くなったりして、利用者に影響が出ている(出そうな)出来事です。まず影響を止めて(復旧)、原因の調査はその後に行います。
例: 重大度(SEV1〜3)、インシデントの指揮官、状況の共有
注意: 最初は原因の究明より、影響を止めること(切り戻し、切り替え)を優先します。
関連: ポストモーテム、オンコール

### ポストモーテム
別名: 振り返り
要約: 障害の後に、原因と再発防止を振り返って書く文書です。
インシデントの後に、何が起きて、なぜ起きて、どう防ぐかをまとめる文書と会です。個人を責めず(ブレームレス)、仕組みを直すことを目的にします。
例: 時系列、影響、根本原因、うまくいったこと、対策と担当と期限
注意: 個人を責めない(ブレームレス)形で書き、仕組みの問題として扱います。
関連: インシデント、SRE

### 手順書
別名: Runbook、ランブック
要約: 決まった作業や障害対応の手順を書いた文書です。
決まった作業や、障害のときの対応の手順をまとめた文書です。誰が見ても同じ作業ができるように書き、自動化の元にもします。
例: ランブック、作業手順書、切り戻しの手順
注意: 手順書が古いと事故のもとになるので、作業のたびに直し、できるものは自動にします。
関連: トイル、インシデント

### トイル
要約: 手作業で、繰り返し、自動にできて、価値が長く残らない作業です。
手作業で、繰り返し発生し、自動化でき、価値が長く残らない作業です。SRE は、トイルを減らして、改善に時間を使います。
例: 手でのサーバーの再起動、毎回の証明書の手での更新
注意: SRE では、トイルを仕事の半分以下に抑え、残りを自動化に使うことを目安にします。
関連: SRE

## 変更と配布

### 本番環境
別名: 開発環境、ステージング環境
要約: 実際の利用者が使っている環境です。
利用者が実際に使う環境が本番環境です。開発用の開発環境、本番と同じ構成で最後の確認をするステージング環境と分けて、本番を守ります。
例: 開発 → 検証(ステージング)→ 本番
注意: 検証の環境は本番にできるだけ近づけないと、本番だけで起きる問題を見逃します。
関連: 変更管理

### デプロイ
要約: 新しい版のアプリを、環境に配置して動かすことです。
作ったアプリや変更を、環境に配置して動かすことです。
例: ローリング、ブルーグリーン、カナリア
注意: 戻す手順(ロールバック)を、デプロイの前に決めておきます。
関連: CI/CD、ローリングアップデート、カナリアリリース

### カナリアリリース
別名: カナリア、ブルーグリーンデプロイ
試験: K8s
要約: 新しい版を一部の利用者にだけ出し、問題がなければ広げる方法です。
新しい版を一部の通信にだけ出し、問題がなければ割合を増やす出し方です。新旧の 2 つの環境を用意して一度に切り替える方法は、ブルーグリーンデプロイと呼びます。
例: 5% → 25% → 100%、Argo Rollouts、Flagger
注意: 比べる指標(エラー率、遅延)と、止める条件を事前に決めておきます。
関連: ローリングアップデート、ロールバック

### 変更管理
要約: 本番への変更を、記録し、確かめ、承認してから行う仕組みです。
本番への変更を、記録し、レビューし、影響と戻し方を決めてから行うことです。障害の多くは変更をきっかけに起きるので、IaC とプルリクエストで管理します。
例: プルリクエストのレビュー、変更の申請、作業の時間帯の決まり
注意: 障害の多くは変更が原因なので、小さく頻繁に、戻せる形で変更します。
関連: IaC、プルリクエスト、ロールバック
