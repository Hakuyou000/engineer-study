# 用語集 セキュリティ

## 認証と認可

### 認証
別名: Authentication
要約: 相手が本人かどうかを確かめることです。
「あなたは誰か」を確かめることです。パスワード、鍵、証明書、多要素認証などで確かめます。認証の後に、何をしてよいかを決めるのが認可です。
例: パスワード、SSH の鍵、クライアント証明書、MFA
注意: 認証(誰か)と認可(何をしてよいか)は別のものです。HTTP の 401 は認証、403 は認可の失敗です。
関連: 認可、多要素認証

### 認可
別名: Authorization
要約: 認証した相手に、何をしてよいかを決めることです。
認証で分かった相手に、「何をしてよいか」を決めることです。AWS の IAM ポリシーや、Kubernetes の RBAC が認可の仕組みです。
例: IAM ポリシー、Kubernetes の RBAC、Linux のパーミッション
注意: 認証が通っても、認可されていない操作は拒否されます。
関連: 認証、最小権限の原則、RBAC

### 多要素認証
別名: MFA、二要素認証
要約: 知っているもの、持っているもの、本人の特徴のうち、2 つ以上を組み合わせる認証です。
知っているもの(パスワード)、持っているもの(スマートフォン、鍵の装置)、本人の特徴(指紋)のうち、2 つ以上を組み合わせて認証することです。パスワードが漏れても、乗っ取られにくくなります。
例: パスワード + スマートフォンのワンタイムパスワード、パスキー
注意: パスワードを 2 回聞くのは、同じ種類の要素なので多要素認証ではありません。
関連: 認証

### 最小権限の原則
別名: 最小特権
要約: 仕事に必要な最小の権限だけを与える考え方です。
仕事に必要な最小限の権限だけを与える、という考え方です。乗っ取られたり誤って操作したりしたときの被害を小さくできます。
例: 読むだけの人には読み取りの権限だけ、`automountServiceAccountToken: false`
注意: 権限を広く与えると、乗っ取られたときや誤操作のときの被害が大きくなります。
関連: 認可、IAM ポリシー

### トークン
別名: アクセストークン
要約: 認証の後に渡される、一時的な通行証です。
認証が済んだことを表す、一時的な文字列です。パスワードの代わりに API を呼ぶときに使います。漏れると、持ち主のふりをされます。
例: OAuth のアクセストークン、JWT、AWS STS の一時的な認証情報
注意: トークンもパスワードと同じく秘密情報で、ログや URL に出してはいけません。
関連: 認証、秘密情報

### PAM
別名: Pluggable Authentication Modules
試験: LinuC202
要約: 認証の仕組みを部品(モジュール)に分け、組み合わせを選べるようにした仕組みです。
設定は `/etc/pam.d/` のプログラムごとのファイルに、「タイプ、制御フラグ、モジュール、引数」の形で書きます。ログインや ssh、sudo が、認証をこの仕組みに任せます。
例: `auth required pam_unix.so`、`session required pam_limits.so`
注意: 制御フラグは書く順番に意味があります。`requisite` は失敗で即終了、`sufficient` は成功で即終了です。
関連: 認証、SSSD

### SSSD
別名: System Security Services Daemon、sssd.conf、pam_sss
試験: LinuC202
要約: LDAP などの認証の情報を取りに行き、手元に覚えておくデーモンです。
設定は `/etc/sssd/sssd.conf` に書きます。NSS(`sss`)と PAM(`pam_sss`)の両方を通して使います。サーバーにつながらなくても、覚えた情報でログインできます。
例: `systemctl enable --now sssd`、`getent passwd taro`
注意: `sssd.conf` の権限は `0600` にします。ゆるいと sssd は起動しません。
関連: PAM、LDAP、NSS

### NSS
別名: Name Service Switch、nsswitch.conf
試験: LinuC202
要約: ユーザー、グループ、ホスト名などの情報を、どこから調べるかを決める仕組みです。
設定は `/etc/nsswitch.conf` です。`passwd: files sss` のように、調べる場所を左から順に並べます。`files` はローカルのファイル、`sss` は SSSD です。
例: `passwd: files sss`、`hosts: files dns`、`getent passwd`
注意: NSS は「そのユーザーがいるか」を決め、PAM は「認証してよいか」を決めます。役割が違います。
関連: PAM、SSSD

### Basic 認証
別名: HTTP Basic 認証、mod_auth_basic
試験: LinuC202
要約: ブラウザーが利用者名とパスワードを聞く、簡単な HTTP の認証です。
Apache では `mod_auth_basic` と `htpasswd` で作ったパスワードのファイルを使います。パスワードは暗号化されず、base64 で符号化されるだけで送られます。
例: `htpasswd -c /etc/httpd/.htpasswd alice`、`AuthType Basic`、`AuthUserFile /etc/httpd/.htpasswd`
注意: 必ず HTTPS と組み合わせます。HTTP のままでは、通信を見られるとパスワードが分かります。
関連: HTTP、TLS

### SMTP 認証
別名: SASL、SMTP AUTH、SMTP-AUTH
試験: LinuC202
要約: メールを送るときに、ユーザー名とパスワードで利用者を確かめる仕組みです。
メールを送るときに、ユーザー名とパスワードで利用者を確かめる仕組みです。認証の部品を SASL と呼びます。Postfix は、認証を Dovecot に任せる設定がよく使われます。
例: Postfix の `smtpd_sasl_auth_enable = yes`、`smtpd_sasl_type = dovecot`
注意: パスワードが平文で流れないように、STARTTLS で暗号化してから認証させます。
関連: STARTTLS、オープンリレー、Dovecot

### ホスト鍵
別名: SSH ホスト鍵
試験: LinuC202
要約: SSH のサーバーが、自分が本物だと示すための鍵の組です。
`/etc/ssh/ssh_host_*_key`(秘密鍵)と `.pub`(公開鍵)です。クライアントは `known_hosts` に記録し、次からは同じ鍵かを比べます。
例: `/etc/ssh/ssh_host_ed25519_key`、`ssh-keygen -A`
注意: ホスト鍵が変わると、クライアントに警告が出ます。サーバーの複製のあとは、ホスト鍵を作り直します。
関連: SSH、公開鍵暗号

### authorized_keys
試験: LinuC202
要約: SSH の公開鍵認証で、ログインを許す公開鍵を並べるファイルです。
サーバー側のユーザーの `~/.ssh/authorized_keys` に、公開鍵を 1 行ずつ書きます。クライアントは、対応する秘密鍵で認証します。
例: `ssh-copy-id alice@server1`、`~/.ssh/authorized_keys`
注意: ホームや `~/.ssh` や、このファイルが他人に書き込める状態だと、認証に失敗します。
関連: SSH、公開鍵暗号

### pam_faillock
別名: faillock
試験: LinuC3SS
要約: ログインの失敗を数えて、一定回数でアカウントを一時的にロックする PAM のモジュールです。
`pam_tally2` の後継で、RHEL 9 系で使います。回数や時間は `/etc/security/faillock.conf` に書きます(`deny`、`fail_interval`、`unlock_time`)。解除は `faillock` コマンドです。
例: `faillock --user taro`、`faillock --user taro --reset`、`authselect enable-feature with-faillock`
注意: `even_deny_root` を有効にすると root もロックされるので、コンソールから入れなくなる危険があります。
関連: PAM、authselect

### authselect
試験: LinuC3SS
要約: RHEL 9 系で、PAM と nsswitch.conf の設定をプロファイルで管理する道具です。
`/etc/pam.d/system-auth` などは、`/etc/authselect/` の下のファイルへのリンクです。直接編集せず、プロファイルと機能(`with-faillock` など)で変えます。
例: `authselect current`、`authselect select sssd with-faillock`、`authselect check`
注意: `system-auth` を直接編集すると、次に `authselect` を実行したときに元に戻ります。
関連: PAM、SSSD、pam_faillock

### Kerberos
試験: LinuC3SS
要約: パスワードをネットワークに流さずに、チケットで認証する仕組みです。
KDC(鍵配布センター)が、最初にパスワードで認証したユーザーに TGT を渡します。以降は TGT で、各サービスのチケットをもらい、シングルサインオンができます。
例: `kinit taro`、`klist`、`kdestroy`
注意: クライアントと KDC の時刻のずれが 5 分(既定)を超えると、認証に失敗します。
関連: FreeIPA、SSSD、LDAP

### FreeIPA
別名: IdM、Identity Management、ipa-server-install、ipa-client-install、ipa コマンド
試験: LinuC3SS
要約: LDAP、Kerberos、認証局、DNS、NTP をまとめた、Linux 向けの統合認証の製品です。
Red Hat 版は IdM といいます。サーバーは `ipa-server-install`、クライアントは `ipa-client-install` で構成し、`ipa` コマンドや管理画面で、ユーザー、グループ、ホスト、アクセスの規則を管理します。
例: `ipa-server-install`、`ipa user-add taro`、`ipa hbactest`
注意: FQDN のホスト名と DNS、時刻の同期が前提です。そろっていないと、導入や `kinit` で失敗します。
関連: Kerberos、LDAP、SSSD、Dogtag、HBAC

### HBAC
別名: Host-Based Access Control
試験: LinuC3SS
要約: FreeIPA で、どのユーザーが、どのホストの、どのサービスに入ってよいかを決める規則です。
認証に成功したあと、アクセスを許すかどうかを決めます。既定の `allow_all` は全員を許可するので、実運用では無効にして、必要な規則だけを足します。
例: `ipa hbacrule-add`、`ipa hbacrule-disable allow_all`、`ipa hbactest`
注意: `allow_all` を無効にする前に、必要な規則を入れて `ipa hbactest` で確かめないと、自分も入れなくなります。
関連: FreeIPA、Kerberos

### Keycloak
試験: LinuC3SS
要約: ログイン画面、シングルサインオン、ユーザーの管理、認可を提供する、オープンソースの認証認可のサーバーです。
OpenID Connect、OAuth 2.0、SAML に対応します。ユーザーをまとめる単位がレルムで、アプリケーションをクライアントとして登録します。17 以降は Quarkus で動き、起動は `kc.sh` です。
例: `kc.sh start-dev`、`kc.sh build`、`kc.sh start --optimized`
注意: `start-dev` は試すだけのモードです。本番では HTTPS とホスト名を設定して `start` で起動します。
関連: OpenID Connect、OAuth 2.0、SAML、WebAuthn

### OAuth 2.0
別名: OAuth
試験: LinuC3SS
要約: アプリケーションに、API を呼ぶ権限を渡すための、認可の決まりです。
ユーザーのパスワードを渡さずに、アクセストークンで権限を渡します。ログインしたのがだれかを表す仕組みは、OAuth 2.0 にはありません。
例: 認可コードフロー、アクセストークン、リフレッシュトークン
注意: OAuth 2.0 は認可の決まりで、認証ではありません。認証には OpenID Connect を使います。
関連: OpenID Connect、トークン、Keycloak

### OpenID Connect
別名: OIDC
試験: LinuC3SS
要約: OAuth 2.0 の上に、ユーザーの認証を足した決まりです。
ID トークン(JWT)で、だれがいつどのように認証したかをアプリに伝えます。`/.well-known/openid-configuration` に、接続に必要な情報が公開されます。
例: `/realms/corp/.well-known/openid-configuration`
注意: ID トークンはクライアントのためのものです。API の認可には、アクセストークンを使います。
関連: OAuth 2.0、SAML、Keycloak

### SAML
別名: SAML 2.0、Security Assertion Markup Language
試験: LinuC3SS
要約: XML のアサーションで、認証の結果と属性を渡す、シングルサインオンの決まりです。
ID プロバイダー(IdP)が認証し、サービス側(SP)にアサーションを渡します。古い企業のシステムや SaaS で、よく使われます。
例: `/realms/corp/protocol/saml/descriptor`
注意: SAML は XML、OpenID Connect は JSON の形式です。新しいアプリは、OpenID Connect を選ぶことが多いです。
関連: OpenID Connect、Keycloak

### WebAuthn
別名: FIDO2
試験: LinuC3SS
要約: セキュリティキーや生体認証で、公開鍵の方式で認証する、ブラウザの規格です。
サイトの URL にひもづいて動くので、偽のサイトでは認証できず、フィッシングに強いです。パスワードなしのログインにも使えます。
例: セキュリティキー、端末の指紋認証、Keycloak の WebAuthn Policy
注意: 端末をなくしたときのために、復旧の手段を用意します。
関連: 多要素認証、Keycloak

### パスキー
試験: LinuC3SS、ITPassport、FE
要約: パスワードの代わりに、端末に保存した鍵で本人を確かめる認証の仕組みです。
FIDO の規格(WebAuthn など)に基づく、公開鍵暗号を使う認証です。秘密鍵は端末に置かれ、指紋や PIN で端末のロックを解いて使います。
例: スマートフォンの指紋認証で Web サイトにログインする
注意: サーバーには公開鍵だけが置かれるので、サーバーから漏れてもなりすましに使えません。
関連: WebAuthn、多要素認証

### リスクベース認証
試験: ITPassport、FE
要約: リスクが高いと判断したときだけ、追加の認証を求める方式です。
場所、端末、時間などが普段と違うときに、追加の認証を求めます。普段どおりのときは、利用者の手間を増やしません。
例: 普段と違う国からのログインで、追加の確認コードを求める。
注意: すべてのログインで追加の認証を求める方式ではありません。
関連: 多要素認証

### 多段階認証
試験: ITPassport
要約: 認証を、何段階かに分けて行う方式です。
種類が同じ要素でも構いません。パスワードと秘密の質問のように、どちらも記憶の要素でも、多段階認証です。
例: パスワードを入力した後に、秘密の質問に答える。
注意: 多要素認証は、種類の違う要素を 2 つ以上組み合わせます。同じ種類の要素の組合せは、多要素認証ではありません。
関連: 多要素認証

### ワンタイムパスワード
別名: OTP
試験: ITPassport、LinuC102、LinuC3SS
要約: 1 回しか使えないパスワードです。
一度使うと無効になります。盗まれても、再利用できません。スマートフォンのアプリや専用の機器で表示します。
例: 認証アプリに表示される、数字 6 桁のコード。
注意: 盗まれてすぐに使われるおそれはあるため、偽サイトに入力させる攻撃には、対策が別に必要です。
関連: 多要素認証

### IC カード
別名: ICカード
試験: ITPassport
要約: 情報を記録した IC チップを埋め込んだ、カードです。
認証の要素のうち、持っているもの(所有)にあたります。入退室や、ログインの認証に使います。
例: 社員証のカードで、部屋に入る。
注意: 紛失すると、拾った人が使えるため、PIN などと組み合わせます。
関連: 多要素認証、入退管理システム

### 生体認証
別名: バイオメトリクス認証、静脈認証、虹彩認証、顔認証、指紋認証
試験: ITPassport
要約: 指紋、静脈、虹彩、顔など、本人の身体の特徴で認証する方式です。
身体的特徴のほか、筆跡やキーボードを打つリズムなどの行動的特徴も使います。忘れたり、盗まれたりしにくい方式です。
例: 指の静脈のパターンで、本人を確かめる。
注意: 誤って他人を受け入れることや、本人を拒否することがあるため、判定の厳しさを調整します。
関連: 本人拒否率、他人受入率、多要素認証

### 本人拒否率
別名: FRR、False Rejection Rate
試験: ITPassport
要約: 登録された本人を、誤って拒否してしまう割合です。
生体認証の精度を表す、2 つの割合の一つです。判定を厳しくすると、上がります。
例: 本人なのに、認証に失敗する。
注意: 他人を誤って受け入れる割合は、他人受入率(FAR)です。
関連: 他人受入率、生体認証

### 他人受入率
別名: FAR、False Acceptance Rate
試験: ITPassport
要約: 他人を、誤って本人と受け入れてしまう割合です。
生体認証の精度を表す、2 つの割合の一つです。判定を厳しくすると、下がります。
例: 他人なのに、認証に成功してしまう。
注意: 判定を厳しくすると、FAR は下がり、本人拒否率(FRR)は上がります。
関連: 本人拒否率、生体認証

### シングルサインオン
別名: SSO
試験: ITPassport、FE
要約: 1 回の認証で、複数のサービスを使えるようにする仕組みです。
利用者は、1 回ログインすれば、ほかのサービスで改めて認証しなくて済みます。
例: 社内の複数のシステムに、1 回のログインで入る。
注意: 認証の仕組みが破られると、複数のサービスが影響を受けるため、多要素認証と組み合わせます。
関連: 多要素認証、SAML、OpenID Connect

### eKYC
試験: ITPassport、FE
要約: オンラインで、本人確認を行う仕組みです。
本人確認書類の画像や、顔の撮影などで、窓口に行かずに本人を確認します。
例: スマートフォンで、運転免許証と顔を撮影して、本人確認をする。
注意: 偽造した書類やなりすましを見抜く仕組みが、必要です。
関連: 認証

### 3D セキュア
別名: 3Dセキュア、EMV 3-D セキュア、3D セキュア 2.0
試験: FE
要約: クレジットカードのオンライン決済で、追加の認証をする仕組みです。
取引のリスクに応じて、追加の認証を求めます。カード番号が盗まれても、不正な利用を防ぎやすくなります。
例: カード決済のときに、スマートフォンで確認する。
注意: カード番号の入力だけでなく、追加の認証が求められる点が特徴です。
関連: リスクベース認証、多要素認証

### 特権 ID
別名: 特権ID、特権アカウント
試験: FE
要約: 管理者の権限を持つ ID です。
システムの設定を変えられる、強い権限を持ちます。使う人と時間を限って使わせ、操作を記録します。
例: サーバーの管理者のアカウント。
注意: 使われていない特権 ID は、乗っ取られても気付きにくいため、棚卸しで見つけます。
関連: アカウントの棚卸し、最小権限の原則

### アカウントの棚卸し
別名: アカウント棚卸し
試験: FE
要約: アカウントの一覧を確かめて、不要なものや過大な権限を見つける作業です。
定期的に行います。退職者のアカウントが残っていないか、権限が大きすぎないかを確かめます。
例: 在籍者の一覧とアカウントの一覧を突き合わせる。
注意: 手続きに無効化がないと、退職者のアカウントが残ります。手続きの見直しも必要です。
関連: 特権 ID、最小権限の原則

### pam_unix
試験: LinuC202
要約: 通常のパスワード認証を行う、PAM のモジュールです。
`/etc/passwd` や `/etc/shadow` を使って、パスワードを確かめます。多くのログインの設定で、使われています。
例: `auth  sufficient  pam_unix.so`
注意: 設定の行の順と、制御フラグによって、効き方が変わります。
関連: PAM、認証

### pam_pwquality
試験: LinuC202、LinuC3SS
要約: パスワードの強さを検査する、PAM のモジュールです。
短すぎる、辞書の語に近いなどの弱いパスワードを、はねます。`pam_cracklib` の後継で、設定は `/etc/security/pwquality.conf` に書きます。
例: `password  requisite  pam_pwquality.so retry=3`
注意: `pam_cracklib` は、新しい Linux-PAM では削除されています。
関連: PAM、pam_unix

### pam_limits
試験: LinuC202
要約: ログインしたユーザーに、資源の上限を適用する、PAM のモジュールです。
`/etc/security/limits.conf` に書いた、プロセスの数や開けるファイルの数の上限を適用します。`session` で使います。
例: `session  required  pam_limits.so`
注意: すでにログインしているセッションには、効きません。
関連: PAM、ulimit

### pam_listfile
試験: LinuC202
要約: ファイルに書いたユーザーなどで、許可と拒否を決める、PAM のモジュールです。
ファイルにユーザー、グループ、ホストを書き、それに合うかで許可や拒否をします。
例: `auth  required  pam_listfile.so item=user sense=deny file=/etc/denyusers onerr=succeed`
注意: ファイルに書く名前の種類(`item=`)と、許可か拒否か(`sense=`)を間違えないようにします。
関連: PAM、認可

### sshd
試験: LinuC202
要約: SSH の接続を受け付ける、サーバー側のデーモンです。
設定は `sshd_config` に書きます。`sshd -t` で、設定の書き方を検査できます。
例: `sudo sshd -t && sudo systemctl reload sshd`
注意: 設定を誤ったまま再起動すると、つなげなくなります。先に `sshd -t` で検査します。
関連: SSH、ホスト鍵、ssh-keygen

### PAM のコントロールフラグ
別名: control フラグ、requisite
試験: LinuC3SS
要約: PAM の設定で、各モジュールの結果を、全体の認証の結果にどう反映するかを決める指定です。
`required` は、失敗しても残りのモジュールを実行したうえで、最後に失敗にします。`requisite` は、失敗したらすぐに失敗を返します。`sufficient` は、成功したら(それまでに required の失敗がなければ)すぐに成功を返します。`optional` は、ほかにモジュールがないときだけ結果に影響します。
例: `auth required pam_faillock.so preauth`、`auth sufficient pam_unix.so`
注意: 並べる順番で結果が変わります。`sufficient` を先頭に置くと、後ろの必須の検査が使われないことがあります。
関連: PAM、pam_faillock、PAM モジュール

### PAM モジュール
別名: pam_securetty、pam_localuser、pam_deny、pam_permit、pam_faildelay、pam_succeed_if、pam_nologin、pam_tty_audit、pam_env、pam_systemd、pam_keyinit
試験: LinuC3SS
要約: PAM の中で、1 つの検査や処理を受け持つ部品です。
`pam_deny` は常に失敗、`pam_permit` は常に成功を返します。`pam_securetty` は root のログインできる端末を制限し、`pam_nologin` は `/etc/nologin` があるとき一般ユーザーを断ります。`pam_faildelay` は失敗後の待ち時間を入れ、`pam_succeed_if` は UID などの条件で判断します。`pam_localuser` は `/etc/passwd` にあるユーザーかを見ます。`pam_tty_audit` は端末の入力を監査し、`pam_env` は環境変数を設定し、`pam_systemd` はセッションを systemd-logind に登録し、`pam_keyinit` はカーネルの鍵のリングを用意します。
例: `auth required pam_deny.so`、`account required pam_nologin.so`
注意: 設定ファイルは `/etc/pam.d/` にあります。誤って書くと、ログインできなくなります。別のセッションを開いたまま試します。
関連: PAM、PAM のコントロールフラグ、pam_faillock

### pam_access
別名: /etc/security/access.conf
試験: LinuC3SS
要約: ユーザーとログイン元(端末やホスト)の組で、ログインを許可、拒否する PAM のモジュールです。
`/etc/security/access.conf` に、`+`(許可)と `-`(拒否)の規則を書きます。上から順に調べ、最初に合ったものが使われます。
例: `-:ALL EXCEPT admin:ALL`
注意: 規則の最後に、`-:ALL:ALL` のような拒否を置かないと、書いていない相手は通ります。
関連: PAM、PAM モジュール

### FreeIPA の ID 範囲
別名: ID 範囲、ipa idrange-add、ipa idrange-find
試験: LinuC3SS
要約: ドメインごとに割り当てる UID と GID の範囲です。
範囲が重なると、別のユーザーに同じ UID がつき、ファイルのアクセス権の事故になります。AD と信頼関係を結ぶときも、AD 側の範囲を別に決めます。
例: `ipa idrange-find`、`ipa idrange-add`
注意: ほかのドメインと重ならないように決めます。
関連: FreeIPA、UID、SSSD

### Keycloak のレルム
試験: LinuC3SS
要約: Keycloak で、ユーザー、クライアント、認証の設定をまとめて分ける単位です。
レルムが違えば、ユーザーも設定も完全に別です。1 つの Keycloak で、会社や環境ごとにレルムを分けて使います。
例: レルム `corp` と、レルム `test` を作って、ユーザーを分ける
注意: 最初からある `master` レルムは、Keycloak 自体の管理用です。業務のユーザーは別のレルムに置きます。
関連: Keycloak、Keycloak のクライアント

### Keycloak のクライアント
試験: LinuC3SS
要約: Keycloak にログインを任せるアプリケーションを登録したものです。
アプリケーションごとに、クライアント ID、リダイレクト先の URL、使うプロトコル(OpenID Connect か SAML)を決めます。
例: Web アプリを、OpenID Connect のクライアントとして登録する
注意: リダイレクト先の URL を広く許可しすぎると、トークンを奪われるおそれがあります。
関連: Keycloak、OpenID Connect、SAML

### ABAC
別名: 属性ベースのアクセス制御、Attribute-Based Access Control
試験: LinuC3SS
要約: ユーザーやリソース、状況の属性を条件にして、アクセスを許可する方式です。
役割(ロール)だけで決める RBAC より、細かく決められます。たとえば、「所属が経理で、勤務時間内で、社内のネットワークから」のような条件を使えます。
例: 部署が経理のユーザーだけが、給与データを読める
注意: 条件が増えると、設定が複雑になり、なぜ許可されたかを説明しにくくなります。
関連: RBAC、認可

### ユーザーフェデレーション
試験: LinuC3SS
要約: Keycloak が、LDAP や Active Directory にあるユーザーを、そのまま使えるようにする機能です。
ユーザーの情報は、元のディレクトリに置いたままです。Keycloak は、その情報を参照して認証します。取り込む方式や、書き込みを許すかを選べます。
例: 社内の Active Directory のユーザーで、Keycloak にログインする
注意: ディレクトリへの接続は、LDAPS や STARTTLS で暗号化します。
関連: Keycloak、LDAP、Active Directory

### ID プロバイダー
別名: IdP
試験: LinuC3SS
要約: ユーザーの認証をして、その結果をほかのサービスに伝える側のシステムです。
Keycloak は、自分が ID プロバイダーになることも、ほかの ID プロバイダー(別の Keycloak や外部のサービス)に認証を任せることもできます。後者を、ID プロバイダー連携と呼びます。
例: 外部の ID サービスのアカウントで、社内のアプリにログインする
注意: 認証を任せた先の ID プロバイダーが止まると、ログインできなくなります。
関連: SAML、OpenID Connect、Keycloak

## 暗号と証明書

### 暗号化
要約: データを、鍵がないと読めない形に変えることです。
データを、鍵がないと読めない形に変えることです。通信の途中を守るもの(転送中の暗号化、TLS)と、保存したデータを守るもの(保存時の暗号化、KMS など)があります。
例: 保存時の暗号化(EBS、S3 の SSE)、転送時の暗号化(TLS)
注意: 暗号化しても、鍵の管理が甘ければ守れません。
関連: 共通鍵暗号、公開鍵暗号、TLS

### 共通鍵暗号
別名: 対称鍵暗号
要約: 暗号化と復号に同じ鍵を使う方式です。
暗号化と復号に同じ鍵を使う方式です。速いので大量のデータに向きますが、鍵を安全に渡す方法が問題になります。AES が代表です。
例: AES
注意: 速いですが、鍵を相手に安全に渡す方法が問題になります。
関連: 公開鍵暗号、暗号化

### 公開鍵暗号
別名: 非対称鍵暗号、公開鍵、秘密鍵
要約: 公開鍵と秘密鍵の組を使う暗号の方式です。
公開してよい公開鍵と、本人だけが持つ秘密鍵の組を使う方式です。公開鍵で暗号化したものは秘密鍵でしか復号できません。SSH の鍵認証、TLS、電子署名で使います。秘密鍵は絶対に渡しません。
例: RSA、ECDSA、Ed25519、SSH の鍵の組
注意: 公開鍵で暗号化したものは秘密鍵でしか復号できません。秘密鍵は渡しません。
関連: 共通鍵暗号、電子署名、証明書

### ハッシュ
別名: ハッシュ値、ダイジェスト、ハッシュ関数、メッセージダイジェスト
要約: データから決まった長さの値を計算する、元に戻せない関数です。
データから計算する、決まった長さの値です。元のデータが少しでも変わると値が大きく変わり、値から元のデータには戻せません。改ざんの検出や、パスワードの保存に使います。SHA-256 が代表です。
例: `sha256sum file`、パスワードの保存、イメージのダイジェスト
注意: MD5 と SHA-1 は衝突が見つかっているので、安全が必要な用途には使いません。
関連: 電子署名

### 電子署名
別名: デジタル署名
要約: 秘密鍵で署名し、公開鍵で確かめて、作った人と改ざんのないことを示す仕組みです。
秘密鍵でデータのハッシュに署名し、公開鍵で確かめる仕組みです。作った人が本人であることと、途中で改ざんされていないことを確かめられます。
例: パッケージの GPG の署名、コンテナのイメージの Cosign の署名
注意: 署名は中身を隠しません。秘密を守るには暗号化が別に必要です。
関連: 公開鍵暗号、ハッシュ、イメージの署名

### 証明書
別名: サーバー証明書、デジタル証明書、X.509、サーバ証明書
要約: 公開鍵と持ち主を、認証局が保証した電子的な書類です。
公開鍵と、その持ち主の情報に、認証局(CA)が署名したものです。Web サイトが本物であることを確かめるのに使います。有効期限があり、切れると接続がエラーになります。
例: `openssl x509 -in cert.pem -noout -dates -subject`
注意: 期限切れは障害の原因として多いので、期限を監視して自動で更新します。
関連: 認証局、TLS、公開鍵暗号

### 認証局
別名: CA
要約: 証明書に署名して、持ち主を保証する組織や仕組みです。
証明書を発行し、署名する機関や仕組みです。ブラウザや OS は、信頼する認証局の一覧を持っています。Kubernetes のクラスタも、自分の CA を持ちます。
例: Let's Encrypt、AWS Certificate Manager、Kubernetes のクラスタの CA
注意: 自分で作った CA の証明書は、相手に信頼させる設定をしないとエラーになります。
関連: 証明書

### TLS
別名: SSL
要約: 通信を暗号化し、相手のサーバーが本物かを確かめる仕組みです。
通信を暗号化し、相手が本物かを証明書で確かめるプロトコルです。HTTPS は HTTP を TLS で守ったものです。SSL は古い名前で、今は TLS 1.2 か 1.3 を使います。
例: HTTPS、`curl -v https://example.com`、TLS 1.2 と 1.3
注意: SSL は古い名前で、SSL 3.0 や TLS 1.0、1.1 は使ってはいけません。
関連: 証明書、HTTP、暗号化

### 鍵のローテーション
別名: ローテーション
試験: SAA、K8s
要約: 鍵やパスワードを、決まった間隔で新しいものに替えることです。
暗号化の鍵やパスワードを、定期的に新しいものに入れ替えることです。漏れていても、使える期間を短くできます。
例: KMS の自動ローテーション、IAM のアクセスキーの更新
注意: 替えても古い鍵を使う場所が残っていると止まるので、切り替えの手順を決めておきます。
関連: 暗号化、秘密情報

### 秘密情報
別名: シークレット、機密情報
要約: パスワード、鍵、トークンのように、漏れると困る情報です。
パスワード、API のキー、トークン、秘密鍵のような、漏れると困る情報です。コードや Git、イメージに書かず、専用の保管庫(Secrets Manager、Vault など)に置きます。
例: AWS Secrets Manager、Kubernetes の Secret、`.env` を `.gitignore` に入れる
注意: Git の履歴に一度入ったら、消すだけでなく、その値を無効にして替えます。
関連: Secrets Manager、Secret

### TSIG
別名: Transaction SIGnature
試験: LinuC202
要約: 共有の秘密鍵で DNS のメッセージに署名し、相手を確かめる仕組みです。
2 つの DNS サーバーが同じ鍵を持ち、ゾーン転送、動的更新、通知のメッセージに署名します。鍵は `tsig-keygen` で作れます。
例: `key "transfer-key" { algorithm hmac-sha256; secret "…"; };`、`allow-transfer { key transfer-key; };`
注意: TSIG は署名だけで、内容は暗号化しません。応答の署名で改ざんを見つける DNSSEC とは別のものです。
関連: ゾーン転送、DNSSEC、ハッシュ

### DNSSEC
別名: DNSKEY、RRSIG、DS レコード
試験: LinuC202
要約: DNS の答えが改ざんされていないことを、電子署名で確かめる仕組みです。
ゾーンのレコードに署名(RRSIG)を付け、検証用の公開鍵(DNSKEY)を載せます。親のゾーンの DS レコードが、子の鍵を保証して、ルートからの信頼のつながりを作ります。
例: `dnssec-keygen`、`dnssec-signzone`、`dig +dnssec www.example.com`(`ad` のフラグ)
注意: 署名で改ざんを見つけるだけです。問い合わせの内容は暗号化されません。
関連: DNS、電子署名、公開鍵暗号、DANE

### DANE
別名: TLSA レコード
試験: LinuC202
要約: サーバーの証明書の情報を DNS に載せ、証明書を確かめられるようにする仕組みです。
証明書(または公開鍵)のハッシュを、TLSA レコードとして DNS に載せます。クライアントは、つながった相手の証明書が、この記録と合うかを確かめます。
例: `_443._tcp.www.example.com. IN TLSA 3 1 1 <ハッシュ>`
注意: DNSSEC で署名されていることが前提です。署名がないと、TLSA の答えが改ざんされるおそれがあります。
関連: DNSSEC、証明書、ハッシュ

### CSR(サーバー証明書の申請)
別名: Certificate Signing Request(Web サーバー)
試験: LinuC202
要約: 認証局にサーバー証明書の署名を頼む、申請の書類です。
サーバーの公開鍵と、名前(CN)や組織の情報が入っています。秘密鍵そのものは入っていません。秘密鍵から作り、CA に送ります。
例: `openssl req -new -key server.key -out server.csr`
注意: 秘密鍵は CA に渡しません。送るのは CSR だけです。
関連: 証明書、認証局

### 自己署名証明書
別名: オレオレ証明書、セルフサイン証明書
試験: LinuC202
要約: 認証局ではなく、自分の秘密鍵で署名した証明書です。
通信を暗号化できますが、信頼された CA の署名がないので、ブラウザーが警告を出します。検証や社内の試験に使います。
例: `openssl req -x509 -newkey rsa:2048 -nodes -keyout server.key -out server.crt -days 365`
注意: 公開するサイトには使いません。利用者に警告を無視する習慣が付きます。
関連: 証明書、認証局

### 中間 CA
別名: 中間認証局、中間証明書
試験: LinuC202
要約: ルート CA とサーバー証明書の間をつなぐ、認証局の証明書です。
サーバー証明書は、中間 CA が署名することが多いです。サーバーは、サーバー証明書の後ろに中間 CA の証明書を続けて送ります。
例: `SSLCertificateFile` のファイルに、サーバー証明書、中間 CA の証明書の順で書く
注意: 中間 CA の証明書を付け忘れると、一部のクライアントだけで、検証のエラーになります。
関連: 証明書、認証局

### OpenSSL
別名: openssl
試験: LinuC202
要約: 暗号と証明書を扱うライブラリとコマンドです。
鍵や CSR、自己署名証明書を作ったり、証明書の中身を見たり、サーバーの TLS 接続を確かめたりできます。
例: `openssl x509 -in server.crt -noout -dates`、`openssl s_client -connect example.com:443`
注意: サブコマンド(`req`、`x509`、`verify`、`s_client`)で動きが変わります。
関連: 証明書、TLS、CSR(サーバー証明書の申請)

### STARTTLS
試験: LinuC202
要約: 平文でつないだあとに、通信を TLS の暗号化に切り替える命令です。
平文でつないだあとに、通信を TLS の暗号化に切り替える命令です。SMTP、IMAP、POP3 で使います。
例: 587 番で `STARTTLS` を送ってから SMTP 認証をする
注意: 最初から TLS にする 465、993、995 番の方式とは違います。
関連: TLS、SMTP、SMTP 認証

### LUKS
別名: Linux Unified Key Setup
試験: LinuC3SS
要約: ディスクの暗号化で、鍵の管理をする形式です。
デバイスの先頭のヘッダーに、複数のパスフレーズ(キースロット)を記録します。LUKS1 と LUKS2 があり、今の既定は LUKS2 です。`cryptsetup` で操作します。
例: `cryptsetup luksFormat /dev/vdb1`、`cryptsetup luksDump /dev/vdb1`
注意: ヘッダーが壊れると、パスフレーズが分かっていても復号できません。
関連: dm-crypt、cryptsetup、キースロット

### dm-crypt
試験: LinuC3SS
要約: ブロックデバイスを暗号化する、Linux カーネルの仕組みです。
device-mapper の仕組みの 1 つで、`/dev/mapper/` の下のデバイスを通すと、自動で暗号化と復号をします。鍵の管理の形式として、LUKS を組み合わせて使うのがふつうです。
例: `cryptsetup open /dev/vdb1 secure`(`/dev/mapper/secure` ができる)
注意: dm-crypt はカーネルの仕組みで、LUKS は鍵の管理の形式です。
関連: LUKS、cryptsetup

### cryptsetup
別名: luksFormat、luksOpen、luksAddKey、luksDump
試験: LinuC3SS
要約: dm-crypt と LUKS のデバイスを操作するコマンドです。
初期化(luksFormat)、開く(open)、閉じる(close)、パスフレーズの追加(luksAddKey)、ヘッダーの表示(luksDump)などをします。
例: `cryptsetup open /dev/vdb1 secure`、`cryptsetup close secure`
注意: `luksFormat` は、中のデータを使えなくします。
関連: LUKS、dm-crypt、キースロット

### キースロット
別名: key slot
試験: LinuC3SS
要約: LUKS のヘッダーの中の、パスフレーズを入れる枠です。
どのキースロットのパスフレーズでも、同じデータの鍵が取り出せます。LUKS1 は 8 個、LUKS2 は最大 32 個です。
例: `cryptsetup luksAddKey /dev/vdb1`、`cryptsetup luksKillSlot /dev/vdb1 1`
注意: 最後の 1 つを消すと、二度と開けません。
関連: LUKS、cryptsetup

### fscrypt
試験: LinuC3SS
要約: ディレクトリ単位でファイルを暗号化する、ファイルシステムの機能です。
ext4 や F2FS などが対応しています。ファイル名と内容が暗号化され、ユーザーごとに別の鍵を使えます。ファイルのサイズなどは暗号化されません。
例: `fscrypt encrypt /data/private`、`fscrypt unlock /data/private`
注意: 暗号化するディレクトリは、空でなければなりません。
関連: LUKS、ext4

### ACME
別名: Automatic Certificate Management Environment
試験: LinuC3SS
要約: 証明書の申請、確認、発行、更新を自動で行うための、決まりごとです。
RFC 8555 で決められています。Let's Encrypt が使い、クライアントの `certbot` などが、この手順で証明書を取ります。
例: `certbot certonly --webroot -w /var/www/html -d example.com`
注意: ACME は申請の手順の決まりで、証明書を出す認証局の名前ではありません。
関連: Let's Encrypt、certbot、HTTP-01

### Let's Encrypt
試験: LinuC3SS
要約: ドメインの管理を確かめるだけの DV 証明書を、無料で、自動で出す認証局です。
ACME で申請します。有効期間が短い(2026 年 11 月時点で 90 日)ので、自動更新が前提です。OCSP は 2025 年 8 月に終了し、失効の情報は CRL で出します。
例: `certbot certificates`、`ls /etc/letsencrypt/live/`
注意: 組織の実在は確かめません。有効期間は、今後さらに短くなる予定です(公式のお知らせを確認します)。
関連: ACME、certbot

### certbot
別名: certbot renew、/etc/letsencrypt/live、/var/log/letsencrypt/letsencrypt.log
試験: LinuC3SS
要約: Let's Encrypt などから、ACME で証明書を取り、更新する、代表的なクライアントです。
`--nginx` や `--apache` で、Web サーバーの設定まで自動で書き換えます。`certonly` は、証明書だけを取ります。更新は `certbot renew` で、timer ユニットか cron から実行します。
例: `certbot --nginx -d example.com`、`certbot renew --dry-run`
注意: `renew` で更新したあと、Web サーバーを reload しないと、古い証明書が使われ続けます。
関連: ACME、HTTP-01

### HTTP-01
試験: LinuC3SS
要約: ACME で、ドメインの管理を確かめる 2 つの方法(Web サーバーに置くものと、DNS に置くもの)です。
HTTP-01 は、`/.well-known/acme-challenge/` に置いた内容を、80/tcp で取りに来て確かめます。DNS-01 は、`_acme-challenge` の TXT レコードで確かめます。
例: `certbot certonly --standalone -d example.com`、`certbot certonly --dns-route53 -d '*.example.com'`
注意: ワイルドカード証明書は DNS-01 でだけ取れます。HTTP-01 は 80/tcp が外から届かないと失敗します。
関連: ACME、certbot

### ルート証明書
別名: ルート CA
試験: LinuC3SS
要約: 信頼の出発点になる、認証局の証明書です。OS やブラウザーに最初から入っています。
証明書は、ルート証明書、中間証明書、サーバー証明書の順につながります。クライアントは、ルート証明書までたどれると、サーバー証明書を信頼します。
例: `ls /etc/ssl/certs/`、`openssl s_client -connect example.com:443 -showcerts`
注意: ルート証明書は、サーバーが送る必要はありません。サーバーが送り忘れやすいのは、中間証明書です。
関連: 中間 CA、証明書

### DV 証明書
別名: ドメイン認証証明書
試験: LinuC3SS
要約: 証明書の種類です。DV はドメインの管理、OV は組織の実在、EV はさらに厳しい審査を確かめたものです。
確かめる範囲が違うだけで、通信の暗号の強さは同じです。Let's Encrypt が出すのは DV だけです。
例: `openssl x509 -in cert.pem -noout -subject -issuer`
注意: EV にしても、今のブラウザーは、DV と見た目をほとんど区別しません。
関連: 証明書、Let's Encrypt

### Dogtag
別名: Dogtag Certificate System
試験: LinuC3SS
要約: FreeIPA に含まれる、証明書を発行する認証局(CA)です。
FreeIPA のホストやサービスの証明書を発行します。クライアントでは、certmonger が証明書の期限を見張り、Dogtag に更新を頼みます。
例: `ipa cert-show 1`、`getcert list`
注意: 証明書を発行するのは Dogtag で、期限を見張って更新を頼むのは certmonger です。役割が違います。
関連: FreeIPA、認証局、certmonger

### certmonger
試験: LinuC3SS
要約: 証明書の期限を見張り、近づくと CA に更新を頼む常駐のプログラムです。
FreeIPA のクライアントでは、`ipa-client-install` が設定します。見張っている証明書の状態は `getcert` で見られます。
例: `getcert list`、`getcert request`
注意: 更新に失敗していても、期限が来るまで気づきにくいので、`getcert list` で定期的に確かめます。
関連: FreeIPA、Dogtag、認証局

### Secure Boot
別名: セキュアブート
試験: LinuC3PS
要約: 署名が正しいプログラムだけを、起動のときに動かす仕組みです。
UEFI のファームウェアが、ブートローダーやカーネルの署名を、PK、KEK、db の信頼の鎖で確かめます。VM では OVMF のファームウェアで使えます。
例: `mokutil --sb-state`
注意: 署名のないカーネルモジュールは読み込めません。自分の鍵を MOK に登録します。
関連: UEFI、仮想 TPM

### 仮想 TPM
別名: swtpm、vTPM
試験: LinuC3PS
要約: ソフトウェアで作った、VM 用の TPM です。
TPM は、鍵の保管と起動の状態の記録をする部品です。仮想 TPM は、swtpm で作り、ホストに物理の TPM がなくても、VM に TPM 2.0 を見せられます。
例: `<tpm model='tpm-crb'><backend type='emulator' version='2.0'/></tpm>`
注意: 状態ファイルを失うと、TPM の中の鍵を失います。バックアップに含めます。
関連: Secure Boot、仮想マシン

### メッセージ認証
別名: メッセージ認証コード、HMAC
試験: FE
要約: 共通鍵を混ぜたハッシュ値で、改ざんと送信元を確認する方法です。
共通鍵を知る人だけが、正しい値を作れます。ハッシュ値だけの場合と違い、改ざんする者が値を作り直せません。
例: HMAC で、受け取ったメッセージの値を確認する。
注意: 共通鍵を使うので、電子署名と違い、第三者に対して送信者を証明することはできません。
関連: ハッシュ、電子署名

### ハイブリッド暗号
試験: FE
要約: 共通鍵暗号と公開鍵暗号を、組み合わせる方式です。
本文を共通鍵暗号で暗号化し、その共通鍵を相手の公開鍵で暗号化して送ります。両方の長所を使えます。
例: メールの暗号化で、本文を共通鍵で暗号化し、その鍵を公開鍵で包む。
注意: 公開鍵暗号で本文を暗号化するのではありません。本文は共通鍵暗号で暗号化します。
関連: 共通鍵暗号、公開鍵暗号

### AES
別名: Advanced Encryption Standard
試験: FE
要約: 共通鍵暗号の標準になっている、ブロック暗号です。
128 ビットのブロックごとに暗号化します。鍵の長さは、128、192、256 ビットです。
例: データの暗号化に、AES を使う。
注意: AES は共通鍵暗号で、公開鍵暗号ではありません。
関連: 共通鍵暗号、ストリーム暗号

### ストリーム暗号
試験: FE
要約: データを 1 ビットや 1 バイトずつ、順に暗号化する方式です。
共通鍵暗号には、ブロック暗号とストリーム暗号があります。ブロック暗号は、決まった長さのブロックごとに暗号化します。
例: 通信のデータを、順に暗号化する。
注意: ブロック暗号(AES など)とは、暗号化の単位が違います。
関連: AES、共通鍵暗号

### 耐量子計算機暗号
別名: PQC、耐量子計算機暗号(PQC)、ポスト量子暗号
試験: ITPassport
要約: 量子コンピューターでも、解読が難しいとされる暗号です。
将来、量子コンピューターで現在の公開鍵暗号が解読されるおそれがあるため、それに備えます。
例: 量子コンピューターに耐える新しい暗号方式への移行。
注意: 量子コンピューターを使う暗号ではなく、量子コンピューターの攻撃に耐える暗号です。
関連: 公開鍵暗号

### ブロックチェーン
試験: ITPassport
要約: 取引の記録を、ブロックとしてつなぎ、複数の参加者で共有する技術です。
前のブロックのハッシュ値でつなぐため、過去の記録を書き換えにくくなっています。暗号資産(仮想通貨)の基盤に使われます。
例: 暗号資産の取引の記録。
注意: 暗号化の技術ではなく、記録を書き換えにくくする仕組みです。
関連: ハッシュ

### 公開鍵基盤
別名: PKI、公開鍵基盤(PKI)、Public Key Infrastructure
試験: ITPassport
要約: 公開鍵の持ち主を保証する仕組みです。
認証局がデジタル証明書を発行して、公開鍵が本当にその人のものであることを確かめます。
例: Web サイトの証明書で、本物のサイトかを確かめる。
注意: 公開鍵暗号の仕組みではなく、公開鍵の持ち主を保証する仕組みです。
関連: 認証局、証明書、公開鍵暗号

### クライアント証明書
試験: ITPassport
要約: 利用者や端末が正規であることを、サーバーに示す証明書です。
サーバー証明書が Web サイトの運営者を示すのに対し、クライアント証明書は利用者や端末を示します。
例: 社内システムに、許可された端末だけをつなぐ。
注意: サーバー証明書とは、示す相手が逆です。
関連: 証明書、認証局

### CRL
別名: 証明書失効リスト、証明書失効リスト(CRL)、Certificate Revocation List
試験: ITPassport、FE
要約: 失効した証明書を、一覧にしたものです。
有効期間内でも、秘密鍵の漏えいなどで無効になった証明書が載ります。認証局が公開します。
例: ブラウザが、証明書が CRL に載っていないかを確認する。
注意: 個々の証明書の状態を、問い合わせて確認する方式は OCSP です。
関連: OCSP、証明書、認証局

### OCSP
別名: Online Certificate Status Protocol
試験: FE
要約: 個々の証明書が失効しているかを、問い合わせて確認するプロトコルです。
応答サーバーに、証明書の状態を問い合わせます。CRL の一覧を取得するより、手軽に確認できます。
例: ブラウザが、サーバー証明書の失効の有無を、OCSP で確認する。
注意: 一覧を取得する方式は CRL です。
関連: CRL、証明書

### タイムスタンプ
別名: 時刻認証
試験: ITPassport
要約: 文書が、ある時刻に存在し、その後に改ざんされていないことを証明するものです。
第三者の機関が、時刻と文書のハッシュ値をもとに、証明します。
例: 契約書が、ある日に存在したことを証明する。
注意: 作成者を証明するのは電子署名で、時刻と非改ざんを証明するのがタイムスタンプです。
関連: 電子署名、ハッシュ

### 危殆化
試験: FE
要約: 暗号鍵が漏れた疑いがあり、安全でなくなることです。
鍵や暗号が、解読されるなどして、安全でなくなった状態です。鍵が危殆化したときは、直ちに失効させ、新しい鍵に置き換えます。
例: 秘密鍵が漏れた疑いがあるので、証明書を失効させる。
注意: 鍵のライフサイクルは、生成、保管、使用、廃棄です。
関連: CRL、鍵管理

### 鍵管理
試験: FE
要約: 暗号鍵を、生成から廃棄まで、守って管理することです。
暗号は、鍵が守られていて、初めて意味があります。鍵は、データとは別の場所に置き、使う人を限ります。
例: 鍵を、暗号化したデータとは別の場所に保管する。
注意: 鍵が漏れると、暗号化していても、データを読まれます。
関連: 鍵のローテーション、危殆化

### データベース暗号化
試験: FE
要約: データベースに保存するデータを、暗号化することです。
媒体の盗難や、不正な持ち出しがあっても、内容を読めなくします。
例: 保存するデータを、暗号化して格納する。
注意: 保存時の暗号化は、通信の暗号化とは別の対策です。
関連: 暗号化、鍵管理

### テスト用情報
別名: テスト用情報の保護
試験: FE
要約: システムのテストで使うデータです。
本番のデータを使うときは、個人情報などが漏れないよう、保護が必要です。技術的管理策に含まれます。
例: 本番のデータをテストに使うとき、データマスキングを行う。
注意: テストの環境は本番より管理が甘いことがあり、本番のデータをそのまま使うのは避けます。
関連: データマスキング、技術的管理策

### S/MIME
別名: Secure MIME
試験: FE
要約: 利用者の証明書で、メールを暗号化し、署名する規格です。
メール自体を暗号化して、署名を付けます。通信路を暗号化する TLS とは、守る範囲が違います。
例: 署名付きのメールで、送信者を確かめる。
注意: メールの内容を暗号化するのは S/MIME、通信路を暗号化するのは TLS です。
関連: 証明書、電子署名

### TLS 1.2
別名: TLSv1.2
試験: LinuC3SS
要約: 現在も広く使われている、TLS の版の 1 つです。
暗号の方式の選び方によって、強さが変わります。弱い暗号の組み合わせは、設定で無効にします。TLS 1.0 と 1.1 は、使わないのが一般的です。
例: nginx の `ssl_protocols TLSv1.2 TLSv1.3;`
注意: 古いクライアントを守るため TLS 1.2 を残しても、弱い暗号の方式は残さないようにします。
関連: TLS、TLS 1.3

### TLS 1.3
別名: TLSv1.3
試験: LinuC3SS
要約: TLS の新しい版で、ハンドシェイクが短く、古い弱い方式が取り除かれています。
接続の開始が早くなります。鍵の交換には、前方秘匿性のある方式だけを使います。古い、弱い暗号の方式は選べません。
例: `openssl s_client -connect example.com:443 -tls1_3`
注意: 古いクライアントは、TLS 1.3 に対応していません。サーバーで TLS 1.2 も許可しているかを確かめます。
関連: TLS、TLS 1.2

### openssl s_client
試験: LinuC3SS
要約: サーバーに TLS で接続して、証明書や、使われている版を確かめるコマンドです。
サーバーが送る証明書の連なり(チェーン)、使う TLS の版、暗号の方式が表示されます。STARTTLS にも対応しています。
例: `openssl s_client -connect example.com:443 -servername example.com`
注意: `-servername` を付けないと、仮想ホストの別の証明書が返ることがあります。
関連: OpenSSL、証明書、STARTTLS

### openssl x509
試験: LinuC3SS
要約: 証明書のファイルの中身を表示する、OpenSSL のコマンドです。
発行者、有効期限、名前、指紋(フィンガープリント)などを確かめます。
例: `openssl x509 -in cert.pem -noout -dates -subject -issuer`
注意: `-noout` を付けないと、証明書の本体も表示されます。
関連: OpenSSL、証明書、openssl s_client

### HTTP/3
試験: LinuC3SS
要約: UDP の上の QUIC というプロトコルで動く、HTTP の新しい版です。
接続の開始が早く、パケットが失われても、ほかのやり取りが止まりにくいのが特徴です。暗号化(TLS 1.3)が最初から組み込まれています。通常は UDP の 443 番を使います。
例: ブラウザーの開発者ツールで、プロトコルが `h3` と表示される
注意: UDP を通さないファイアウォールでは、使えません。そのときは、HTTP/2 などに戻ります。
関連: HTTP、TLS 1.3、UDP

### crypttab
別名: /etc/crypttab
試験: LinuC3SS
要約: 起動時に、暗号化したディスクを自動で開くための設定ファイルです。
1 行に、開いた後の名前、元のデバイス、鍵のファイル(または `none`)、オプションを書きます。開いたデバイスを、`/etc/fstab` でマウントします。
例: `data  UUID=xxxxxxxx-xxxx  none  luks`
注意: 鍵のファイルを、暗号化したディスクと同じところに置くと、暗号化の意味がなくなります。
関連: LUKS、cryptsetup、fstab

### certbot のプラグイン
別名: --nginx、--apache
試験: LinuC3SS
要約: certbot が、Web サーバーの設定を読み書きして、証明書の取得と設定を自動で行うための部品です。
`--nginx` と `--apache` を指定すると、認証の作業と、証明書を使う設定の書き換えまで行います。
例: `sudo certbot --nginx -d example.com`
注意: 設定を自動で書き換えます。実行の前に、設定のバックアップを取ります。
関連: certbot、certbot の認証方法

### certbot の認証方法
別名: webroot、standalone
試験: LinuC3SS
要約: certbot が、ドメインの持ち主であることを Let's Encrypt に示す方法です。
`webroot` は、動いている Web サーバーの公開ディレクトリにファイルを置きます。`standalone` は、certbot が一時的な Web サーバーを自分で立てます。
例: `certbot certonly --webroot -w /var/www/html -d example.com`、`certbot certonly --standalone -d example.com`
注意: `standalone` は、80 番ポートが空いている必要があります。Web サーバーが動いていると失敗します。
関連: certbot、HTTP-01、Let's Encrypt

## 脅威と対策

### 脆弱性
別名: CVE、セキュリティホール
要約: ソフトウェアや設定の、攻撃に使われうる弱点です。
ソフトウェアの、悪用できる欠陥です。見つかったものには CVE という番号が付きます。パッケージやイメージを更新して修正を取り込みます。
例: CVE の番号、CVSS の点数
注意: 脆弱性があっても、外から届かない、使っていない機能なら、危険の大きさは下がります。
関連: 脆弱性スキャン、パッチ

### 脆弱性スキャン
試験: Docker、SAA、K8s
要約: 既知の脆弱性がないかを、道具で調べることです。
ソフトウェアやイメージに、既知の脆弱性がないかを調べることです。コンテナのイメージは Trivy や Docker Scout、AWS では Amazon Inspector で調べます。
例: Trivy、Amazon Inspector、Docker Scout
注意: 新しい脆弱性は毎日見つかるので、作ったときだけでなく定期的に調べます。
関連: 脆弱性

### パッチ
別名: セキュリティパッチ
要約: 不具合や脆弱性を直すための更新です。
ソフトウェアの欠陥や脆弱性を直すための更新です。適用を後回しにすると、攻撃される危険が増えます。
例: `dnf update --security`、OS とライブラリの更新
注意: 当てる前に検証の環境で試し、戻す方法を決めておきます。
関連: 脆弱性

### DDoS 攻撃
別名: DDoS
試験: SAA、CCNA
要約: 大量の通信を送り付けて、サービスを止める攻撃です。
多数の機器から大量の通信を送りつけて、サービスを使えなくする攻撃です。AWS では Shield や WAF、CloudFront で防ぎます。
例: AWS Shield、CloudFront、レート制限
注意: 自前のサーバーだけで受け止めるのは難しく、手前の CDN やサービスで吸収します。
関連: WAF

### WAF
別名: Web Application Firewall
試験: SAA
要約: Web アプリへの攻撃(SQL インジェクションなど)を、HTTP の中身を見て止める仕組みです。
Web アプリへの通信の中身を見て、SQL インジェクションのような攻撃や、同じ相手からの多すぎるリクエストを止める仕組みです。
例: AWS WAF を ALB や CloudFront に付ける
注意: WAF はアプリの脆弱性を直すものではなく、手前で防ぐ補助です。
関連: ファイアウォール、DDoS 攻撃

### SQL インジェクション
別名: SQLインジェクション
試験: SAA、ITPassport、FE
要約: 入力に SQL を混ぜて、データベースを不正に操作する攻撃です。
入力の欄に、データベースの命令(SQL)を混ぜて、データを盗んだり壊したりする攻撃です。Web のページに悪いスクリプトを埋め込む攻撃は XSS です。WAF や、入力の正しい扱い方で防ぎます。
例: `' OR '1'='1`
注意: 文字列をつなげて SQL を作らず、プレースホルダー(バインド変数)を使って防ぎます。
関連: WAF

### クロスサイトスクリプティング
別名: XSS
試験: SAA、ITPassport、FE
要約: Web のページに悪いスクリプトを埋め込み、閲覧者のブラウザーで動かす攻撃です。
利用者の入力をそのまま画面に出す Web アプリに、スクリプトを含む文字列を送り込みます。そのページを見た人のブラウザーでスクリプトが動き、Cookie などが盗まれます。
例: 掲示板の書き込みに `<script>…</script>` を入れる
注意: 狙われるのは閲覧者のブラウザーで、データベースを直接操作する SQL インジェクションとは別の攻撃です。
関連: SQL インジェクション、WAF

### 総当たり攻撃
別名: ブルートフォース攻撃
要約: パスワードの候補を片っ端から試す攻撃です。
パスワードを片っ端から試す攻撃です。ログインの失敗の回数の制限、多要素認証、長いパスワードで防ぎます。
例: SSH への大量のログインの試み、`fail2ban`
注意: 鍵の認証にしてパスワードの認証を止める、試行の回数を制限する、MFA を使う、で防ぎます。
関連: 多要素認証、認証

### フィッシング
別名: ソーシャルエンジニアリング
要約: 本物に見せかけたメールやサイトで、パスワードなどをだまし取る攻撃です。
本物そっくりのメールや画面で、パスワードなどを入力させてだまし取る攻撃です。技術ではなく人の油断を突く攻撃をまとめて、ソーシャルエンジニアリングと呼びます。
例: 偽のログインの画面、偽の請求のメール
注意: パスキーや FIDO の鍵は、偽のサイトでは使えないので、フィッシングに強いです。
関連: 多要素認証

### マルウェア
別名: ランサムウェア
要約: 害を与えることを目的に作られたソフトウェアです。
悪意のあるソフトウェアの総称です。データを暗号化して身代金を求めるものをランサムウェアと呼びます。別の場所に、書き換えられないバックアップを持つと復旧できます。
例: ランサムウェア、トロイの木馬、ワーム
注意: ランサムウェアに備えて、書き換えられないバックアップ(別の場所、オフライン)を持ちます。
関連: バックアップ

### ゼロトラスト
別名: ゼロトラストアーキテクチャ
要約: 社内のネットワークも信頼せず、通信のたびに確かめる考え方です。
社内のネットワークだからといって信用せず、すべてのアクセスを毎回確かめる、という考え方です。
例: 端末の状態の確認、利用者ごとの認証と認可、細かいアクセスの制御
注意: 「中は安全」という境界の守りだけに頼らない、という考え方です。
関連: 認証、最小権限の原則

### 監査ログ
要約: 誰が、いつ、何をしたかの記録です。
誰が、いつ、何をしたかの記録です。不正の調査や、規則を守っていることの証明に使います。AWS では CloudTrail、Kubernetes では API サーバーの監査ログがあります。
例: AWS CloudTrail、Linux の auditd、Kubernetes の監査ログ
注意: 記録を消されないように、別のアカウントや書き換えられない場所に送ります。
関連: CloudTrail

### オープンリレー
別名: 第三者中継
試験: LinuC202
要約: 誰からのメールでも中継してしまう、設定を誤ったメールサーバーです。
誰からのメールでも、自分宛てでないドメインへ中継してしまう、設定を誤ったメールサーバーです。迷惑メールの踏み台に使われます。
例: Postfix の `mynetworks` に `0.0.0.0/0` を書いてしまう
注意: 中継は、信頼するネットワークと、SMTP 認証に成功したユーザーに絞ります。
関連: MTA、SMTP 認証

### fail2ban
試験: LinuC202
要約: ログを見て、認証の失敗が続く接続元を、自動でブロックする道具です。
`findtime` の間に `maxretry` 回を超えた接続元を、ファイアウォールの規則で `bantime` の間ブロックします。SSH の総当たり攻撃への対策によく使います。
例: `fail2ban-client status sshd`、`/etc/fail2ban/jail.local`
注意: 設定は `jail.local` に書きます。`jail.conf` は更新で上書きされます。
関連: 総当たり攻撃、ファイアウォール

### IDS
別名: 侵入検知システム、Intrusion Detection System、snort
試験: LinuC202
要約: 不正なアクセスの兆候を見つけて、知らせる仕組みです。
ネットワークを流れるパケット(ネットワーク型。snort など)や、ホストのログとファイルの変化(ホスト型)を調べます。見つけて知らせるだけで、自分では止めません。
例: snort、OSSEC
注意: 止める機能まで持つものは IPS と呼びます。
関連: ファイアウォール、fail2ban

### OpenVAS
別名: Greenbone Vulnerability Management、GVM
試験: LinuC202
要約: ネットワークの上から、既知の脆弱性を調べる脆弱性スキャナーです。
ホストやサービスに、既知の脆弱性が残っていないかを検査し、報告書を作ります。
例: Greenbone の Web 画面、スキャンのタスク
注意: 検査は、自分が管理するホストだけを対象にします。
関連: 脆弱性スキャン、脆弱性

### OpenSCAP
別名: oscap
試験: LinuC202
要約: ホストの設定が、決まったセキュリティ基準に合っているかを検査する道具です。
SCAP という仕組みの基準(プロファイル)に照らして、設定を検査し、報告書を作ります。基準は `scap-security-guide` のパッケージで入ります。
例: `oscap xccdf eval --profile <ID> --report report.html <データストリーム>`
注意: 既知の脆弱性を調べる OpenVAS とは目的が違います。OpenSCAP は設定の適合を調べます。
関連: 脆弱性スキャン、OpenVAS

### JPCERT/CC
別名: JPCERT コーディネーションセンター
試験: LinuC202
要約: 日本のセキュリティ事故の調整センターで、JVN で脆弱性の情報を発信します。
一般社団法人 JPCERT コーディネーションセンターです。注意喚起を出し、脆弱性の情報のポータル JVN を、IPA と運営します。
例: JVN の脆弱性の情報、注意喚起の一覧
注意: 米国の CERT/CC とは別の組織です。
関連: 脆弱性、パッチ

### JVN
別名: Japan Vulnerability Notes
試験: LinuC202、ITPassport、FE
要約: 日本で使われる製品の脆弱性の情報と対策をまとめたポータルサイトです。
JPCERT/CC と IPA が共同で運営する、脆弱性の情報を公開するサイトです。製品ごとに、影響と対策の情報を載せています。
例: 使っているソフトウェアの名前で JVN を検索し、対策の版を確かめる
注意: JVN は情報を公開するサイトの名前で、組織の名前ではありません。
関連: JPCERT/CC、脆弱性

### auditd
別名: /etc/audit/auditd.conf、max_log_file、max_log_file_action、/etc/audit/rules.d
試験: LinuC3SS
要約: Linux の監査(誰が何をしたかの記録)をログに書く、デーモンです。
カーネルが捕まえた事象を、`/var/log/audit/audit.log` に書きます。設定は `/etc/audit/auditd.conf` で、記録する規則は `/etc/audit/rules.d/` に書きます。
例: `service auditd restart`、`auditctl -l`
注意: Red Hat 系では、`systemctl restart auditd` を受け付けないことがあります。
関連: 監査ログ、auditctl

### auditctl
試験: LinuC3SS
要約: 監査の規則を、実行中のカーネルに足したり、見たりするコマンドです。
`-w` でファイルを監視し、`-a always,exit` でシステムコールを記録します。`-l` で一覧、`-s` で状態を見ます。
例: `auditctl -w /etc/passwd -p wa -k identity`、`auditctl -l`
注意: 足した規則は、再起動で消えます。残すには `/etc/audit/rules.d/` に書いて、`augenrules --load` を実行します。
関連: auditd、ausearch

### ausearch
試験: LinuC3SS
要約: 監査ログから、条件に合う記録を探すコマンドです。
キー(`-k`)、記録の種類(`-m`)、ユーザー、ファイル、時刻(`-ts`)などで絞ります。`-i` で数字を名前に直して読みやすくします。
例: `ausearch -k identity -i -ts today`
注意: 規則に `-k` でキーを付けておかないと、後で絞りにくくなります。
関連: auditd、aureport

### aureport
試験: LinuC3SS
要約: 監査ログを集計して、報告にするコマンドです。
ログイン(`-l`)、認証(`--auth`)、ファイル(`-f`)、実行したプログラム(`-x`)などの報告を作ります。`--failed` で失敗だけに絞れます。
例: `aureport -l --failed -ts this-week`、`aureport --auth --summary`
注意: 集計のコマンドで、1 件ずつの詳しい中身を探すには `ausearch` を使います。
関連: auditd、ausearch

### Suricata
試験: LinuC3SS
要約: 通信を規則と照らし合わせて、不審なものを見つける(必要なら止める)ネットワーク型の道具です。
設定は `/etc/suricata/suricata.yaml`、規則は `suricata-update` で取ってきます。ミラーポートで見るだけなら NIDS、経路の途中(インライン)に置いて `drop` の規則を使えば NIPS になります。ログは `fast.log` と `eve.json` です。
例: `suricata -T -c /etc/suricata/suricata.yaml`、`alert http any any -> $HOME_NET any (msg:"..."; sid:1000001; rev:1;)`
注意: 最初は警告だけで動かし、誤検知を確かめてから `drop` にします。
関連: IDS、WAF

### ModSecurity
別名: mod_security、SecRuleEngine
試験: LinuC3SS
要約: Web サーバーに組み込む WAF です。HTTP の要求を調べて、攻撃を止めます。
Apache のモジュールか、Nginx の ModSecurity v3 で使います。`SecRuleEngine` で動きを決めます(`On`、`DetectionOnly`、`Off`)。ルールは `SecRule` で書き、OWASP CRS を使うのが基本です。
例: `SecRuleEngine DetectionOnly`、`SecRule ARGS "@rx (?i)<script" "id:100001,phase:2,deny,status:403"`
注意: 最初は `DetectionOnly` で誤検知を確かめます。誤検知は、ルール ID を指定して例外にします。WAF 全体を止めません。
関連: WAF、OWASP CRS、SQL インジェクション

### OWASP CRS
別名: Core Rule Set、CRS
試験: LinuC3SS
要約: ModSecurity で使う、公開されたルールの集まりです。
SQL インジェクション、XSS、パス・トラバーサルなどの攻撃を、広く見ます。要求ごとに点数(異常スコア)を足して、しきい値を超えたら拒否する方式が基本です。しきい値の既定は、版で違うことがあります。
例: Debian 系の `modsecurity-crs` パッケージ
注意: そのまま入れると、正常な要求を止めることがあります。最初は記録だけにして、調整します。
関連: ModSecurity、WAF

### CVSS
別名: Common Vulnerability Scoring System
試験: LinuC3SS
要約: 脆弱性の深刻さを、0.0 から 10.0 の点数にする仕組みです。
0.1〜3.9 が低、4.0〜6.9 が中、7.0〜8.9 が高、9.0〜10.0 が緊急です。基本評価のほかに、現状評価、環境評価があります。版(v3.1、v4.0 など)で点数が違うことがあります。
例: 基本評価 9.8(緊急)の CVE
注意: 点数だけで優先順位を決めません。自分の環境で、その弱点に届くかを見ます。
関連: 脆弱性、CPE

### CPE
別名: Common Platform Enumeration
試験: LinuC3SS
要約: 製品や版を表す名前の形式です。
`cpe:2.3:a:ベンダー:製品:版:…` の形で書きます。CVE(脆弱性の番号)と組み合わせて、どの製品のどの版が影響を受けるかを表します。
例: `cpe:2.3:a:openssl:openssl:3.0.2:*:*:*:*:*:*:*`
注意: 脆弱性の番号ではありません。番号は CVE です。
関連: 脆弱性、CVSS

### Trivy
別名: trivy
試験: LinuC3SS
要約: コンテナのイメージ、ファイル、リポジトリ、設定ファイルを調べる、オープンソースのスキャナーです。
`trivy image`、`trivy fs`、`trivy repo`、`trivy config` で対象を選びます。既知の脆弱性、設定の不備、埋め込まれた秘密を見つけます。`--severity` で表示を絞り、`--exit-code 1` で見つかったときに失敗させます。
例: `trivy image --severity HIGH,CRITICAL --exit-code 1 myapp:1.0`
注意: 脆弱性のデータベースは毎日更新されます。古いデータベースでは、新しい脆弱性を見逃します。
関連: 脆弱性スキャン、SBOM

### ZAP
別名: ZAP by Checkmarx、OWASP ZAP
試験: LinuC3SS
要約: Web アプリの脆弱性を調べる、オープンソースの診断ツールです。旧 OWASP ZAP です。
プロキシとして通信を見る「パッシブスキャン」と、調べる要求を送る「アクティブスキャン」があります。2023 年 8 月に OWASP のプロジェクトでなくなり、Checkmarx の支援を受けるコミュニティのプロジェクトです。
例: `zap-baseline.py -t https://staging.example.test -r report.html`
注意: アクティブスキャンは、データを変えたり負荷をかけたりすることがあります。自分が管理するか、許可を得た検証環境にだけ行います。
関連: 脆弱性スキャン、SQL インジェクション

### ファイル完全性監視
別名: 改ざんの検知、完全性検査
試験: LinuC3SS
要約: ファイルが、勝手に書き換えられていないかを、定期的に確かめる方法です。
ファイルのハッシュ値や属性を、正しい状態のときに記録しておきます。後で比べて、違うものを見つけます。AIDE が代表的です。
例: `aide --init` で記録を作り、`aide --check` で比べる
注意: 記録の置き場所が書き換えられると、意味がなくなります。読み取り専用の媒体や別のホストに置きます。
関連: AIDE、ハッシュ

### シグネチャ
試験: LinuC3SS
要約: ウイルスや攻撃の、既知の特徴を書いた定義です。
ファイルや通信が、定義と合うかで、有害かを判断します。定義にない新しいものは、見つけられません。定義を、常に新しくしておく必要があります。
例: ClamAV で `freshclam` を使って、定義を更新する
注意: シグネチャで見つけられない新しい攻撃は、別の方法(ふるまいの検知など)で補います。
関連: ClamAV、IDS、マルウェア

### ComplianceAsCode
別名: SCAP Security Guide、scap-security-guide
試験: LinuC3SS
要約: セキュリティの設定基準を、OpenSCAP で使えるデータとして提供するプロジェクトです。
OS ごとの、設定の検査項目(プロファイル)が入っています。`oscap` と組み合わせて、設定が基準に合うかの検査と、報告書の作成ができます。
例: `sudo oscap xccdf eval --profile xccdf_org.ssgproject.content_profile_cis --report report.html /usr/share/xml/scap/ssg/content/ssg-rhel9-ds.xml`
注意: プロファイルの名前とデータのファイルは、OS と版で違います。`oscap info` で確かめます。
関連: OpenSCAP、XCCDF

### アクティブスキャン
試験: LinuC3SS
要約: 対象に実際にパケットを送って、開いているポートや脆弱性を調べる方法です。
OpenVAS や nmap が行います。細かく調べられますが、通信が増え、対象に負荷をかけることがあります。許可を得た範囲だけで行います。
例: `nmap -sV 192.0.2.10`
注意: 許可のない相手へのスキャンは、攻撃とみなされることがあります。
関連: パッシブスキャン、nmap、OpenVAS

### パッシブスキャン
試験: LinuC3SS
要約: 通信を見ているだけで、機器やサービスの情報を集める方法です。
ネットワークを流れる通信を観察し、機器の種類やソフトウェアの版などを推測します。対象に負荷をかけず、通信にも影響しません。
例: ミラーポートで取り込んだ通信から、動いているサービスの一覧を作る
注意: 通信がない機器や、暗号化されている部分は、分かりません。
関連: アクティブスキャン、IDS

## OS の守り

### SELinux
試験: LinuC102、Docker
要約: プロセスがアクセスできるものを、ラベルで強制的に制限する仕組みです。
Linux で、プロセスが触れるファイルや操作を、細かいルールで制限する仕組みです(強制アクセス制御)。root で動くプロセスでも制限できます。
例: `getenforce`、`ls -Z`、`restorecon -Rv /var/www`、`setsebool -P httpd_can_network_connect on`
注意: 困ったからといって無効にせず、ラベルや boolean を直します。
関連: root

### AppArmor
試験: LinuC3SS、Docker
要約: プログラムごとのプロファイルで、使えるファイルや機能を制限する強制アクセス制御の仕組みです。
Linux の強制アクセス制御(MAC)の 1 つで、Ubuntu や SUSE で標準的に使われます。プログラムのパスに結び付けたプロファイルで、読み書きできるファイルなどを決めます。
例: `aa-status` で読み込まれたプロファイルを表示する
注意: SELinux はファイルなどに付けたラベルで判定し、AppArmor はパスで判定します。同じ目的の別の仕組みです。
関連: SELinux

### ケーパビリティ
別名: capabilities
試験: Docker、K8s
要約: root の権限を細かく分けたものです。
root の強い権限を、細かい単位(ネットワークの設定、低い番号のポートの使用など)に分けたものです。コンテナでは、すべて外して(`drop: ALL`)、必要なものだけを足すのが安全です。
例: `CAP_NET_BIND_SERVICE`(1024 未満のポート)、`docker run --cap-drop ALL --cap-add NET_BIND_SERVICE`
注意: `--privileged` はほぼすべてのケーパビリティを与えるので、原則として使いません。
関連: root、最小権限の原則

### chroot
試験: LinuC202
要約: プロセスから見えるルートディレクトリを、別の場所に替える仕組みです。
プロセスにとっての `/` を、指定したディレクトリに替えます。BIND などのサービスを、その中に閉じ込めると、乗っ取られても外のファイルに届きません。
例: `named -t /var/named/chroot -u named`、Red Hat 系の `named-chroot.service`
注意: chroot だけでは完全な隔離にならないので、root 以外のユーザーで動かす設定と合わせます。
関連: BIND

### root_squash
試験: LinuC202
要約: NFS で、クライアントの root を匿名のユーザーに変えるオプションです。
NFS のサーバーで、クライアントの root(UID 0)を、匿名のユーザー(`nobody` など)に変えるオプションです。既定で有効です。すべてのユーザーを匿名にするのは `all_squash`、root をそのまま扱うのは `no_root_squash` です。
例: `/srv/share 192.168.1.0/24(rw,root_squash)`
注意: `no_root_squash` は、クライアントの root が、サーバーのファイルを自由に書き換えられるので、必要なときだけ使います。
関連: NFS

### 強制アクセス制御
別名: MAC、Mandatory Access Control
試験: LinuC3SS
要約: 管理者が決めたルールで、持ち主や root でも変えられないアクセスの制限です。
通常のファイルの権限は、持ち主が変えられます(任意アクセス制御)。強制アクセス制御は、ルールを管理者が決め、root のプロセスでも、ルールで許されないことはできません。Linux では SELinux と AppArmor があります。
例: SELinux(Red Hat 系で既定)、AppArmor(Ubuntu で既定)
注意: 通常の権限(DAC)とは別に判定されます。両方が許したときだけ、アクセスが通ります。
関連: SELinux、最小権限の原則

### セキュリティコンテキスト
別名: SELinux コンテキスト、SELinux ラベル
試験: LinuC3SS
要約: SELinux が、プロセスやファイルに付けるラベルです。
`ユーザー:ロール:タイプ:レベル` の形で、通常は、**タイプ**を見ます。ポリシーが「このタイプのプロセスは、このタイプのファイルを読める」と決めています。表示には `-Z` オプションを使います。
例: `ls -Z /var/www/html`、`ps -eZ`、`restorecon -Rv /var/www/html`
注意: `mv` は元のラベルのまま、`cp` は置き先のラベルになります。移したあとにアクセスできないときは、ラベルを疑います。
関連: SELinux、拡張属性

### SELinux ブール値
別名: ブール値、setsebool
試験: LinuC3SS
要約: SELinux のポリシーを、オンとオフで切り替えるスイッチです。
よくある許可の切り替え(Web サーバーが外へ接続するのを許す、など)を、ルールを書かずに行えます。`getsebool -a` で一覧を見て、`setsebool -P` で恒久的に設定します。
例: `getsebool -a | grep httpd`、`setsebool -P httpd_can_network_connect on`
注意: `-P` を付けない設定は、再起動で元に戻ります。
関連: SELinux、セキュリティコンテキスト

### AVC 拒否
別名: AVC、type=AVC
試験: LinuC3SS
要約: SELinux が、アクセスを拒否したときの記録です。
`/var/log/audit/audit.log` に `type=AVC` の行として残ります。`scontext` が操作したプロセス、`tcontext` が対象、`permissive=0` なら本当に拒否されたことを表します。
例: `ausearch -m AVC -ts recent`、`audit2allow -w`
注意: `dontaudit` のルールが記録を隠すことがあります。記録がないのに拒否されるときは、`semodule -DB` で見えるようにします。
関連: SELinux、監査ログ

### AppArmor プロファイル
別名: aa-genprof、aa-logprof、/etc/apparmor.d
試験: LinuC3SS
要約: AppArmor で、プログラムごとにできることを、パスで書いたものです。
`/etc/apparmor.d/` に置きます。モードは enforce(拒否して記録)と complain(記録だけ)です。`aa-genprof` で作り、`aa-logprof` で育てます。
例: `aa-status`、`aa-complain /usr/sbin/myapp`、`apparmor_parser -r /etc/apparmor.d/usr.sbin.myapp`
注意: ファイルを書き換えただけでは、カーネルの内容は変わりません。`apparmor_parser -r` で読み込み直します。
関連: 強制アクセス制御、SELinux

### seccomp
別名: SECCOMP_MODE_FILTER、SystemCallFilter、SystemCallErrorNumber、SystemCallArchitectures、seccomp-tools
試験: LinuC3SS
要約: プロセスが呼べるシステムコールを、制限する仕組みです。
モードは、`SECCOMP_MODE_DISABLED`、`SECCOMP_MODE_STRICT`、`SECCOMP_MODE_FILTER` の 3 つです。フィルタは BPF プログラムで書きます。systemd では `SystemCallFilter=` で設定します。
例: `grep Seccomp /proc/self/status`、`SystemCallFilter=~@privileged`
注意: 一度付けたフィルタは外せず、子プロセスに引き継がれます。
関連: システムコール、ケーパビリティ

### NoNewPrivileges
別名: no_new_privs
試験: LinuC3SS
要約: プロセスが、新しい権限を得るのを禁止する設定です。
systemd では `NoNewPrivileges=yes` と書きます。`setuid` のビットや、ファイルの Capability によって、権限が上がらなくなります。
例: `NoNewPrivileges=yes`、`AmbientCapabilities=CAP_NET_BIND_SERVICE`
注意: すでに持っている Capability を外す設定ではありません。外すのは `CapabilityBoundingSet=` です。
関連: ケーパビリティ、最小権限の原則

### AIDE
別名: Advanced Intrusion Detection Environment、aide.conf
試験: LinuC3SS
要約: ファイルの状態を記録しておき、あとで比べて、改ざんを見つける道具です。
`aide --init` で正常な状態を記録し、`aide --check` で今の状態と比べます。比べる項目(権限、所有者、サイズ、ハッシュ値)は `aide.conf` に書きます。
例: `aide --init`、`aide --check`、`aide --update`
注意: 記録も改ざんの対象です。読み取り専用の媒体や別のサーバーに置きます。感染したあとで記録を作ると、その状態が正常になります。
関連: IDS、ClamAV

### ClamAV
別名: clamscan、freshclam
試験: LinuC3SS
要約: オープンソースのウイルス対策ソフトです。ファイルをシグネチャと照らし合わせて調べます。
`freshclam` でシグネチャを更新し、`clamscan`(または常駐の `clamd` に調べさせる `clamdscan`)で調べます。終了コードは、0 が見つからない、1 が見つかった、2 がエラーです。
例: `clamscan -r --infected --move=/var/quarantine /srv/uploads`
注意: シグネチャにない新しいものは見つけられません。`--remove` は戻せないので、最初は `--move`(隔離)にします。
関連: YARA、AIDE

### YARA
別名: yara
試験: LinuC3SS
要約: 文字列やバイトの並びの規則を自分で書いて、ファイルを探す道具です。
規則は `strings` と `condition` で書き、`yara -r 規則ファイル ディレクトリ` で調べます。マルウェアの調査でよく使います。
例: `yara -r rules.yar /srv/uploads`、`yara -s rules.yar sample.bin`
注意: 条件が広すぎると、正常なファイルまで合います。正常なファイルの集まりで試してから使います。
関連: ClamAV、AIDE

### XCCDF
別名: Extensible Configuration Checklist Description Format
試験: LinuC3SS
要約: 設定の基準(ルールとプロファイル)を、機械で読める形で書く形式です。
SCAP の仕様の 1 つです。システムの状態を調べる手順は、OVAL という言語で書きます。OpenSCAP は、この 2 つが入ったデータストリームを読み込んで検査します。
例: `oscap xccdf eval --profile ... ds.xml`
注意: XCCDF は基準、OVAL は検査の手順です。役割を取り違えないようにします。
関連: OpenSCAP、脆弱性スキャン

### SELinux のモード
別名: enforcing、permissive、/etc/selinux/config
試験: LinuC3SS
要約: SELinux が、規則に反する操作を、拒否するか、記録だけするかを決める状態です。
`enforcing` は、拒否して記録します。`permissive` は、拒否せず記録だけします。`disabled` は、働きません。永続の設定は `/etc/selinux/config` の `SELINUX=` で決めます。
例: `getenforce`、`sudo setenforce 0`、`sestatus`
注意: `setenforce` の変更は、再起動で戻ります。`disabled` への変更や、再び有効にするときは、再起動が必要です。
関連: SELinux、setenforce、AVC 拒否

### SELinux のポリシータイプ
別名: targeted、minimum、mls
試験: LinuC3SS
要約: SELinux が、どの範囲を保護するかを決める、ポリシーの種類です。
`targeted` は、主なサービスだけを保護し、標準で使われます。`minimum` は、さらに保護する対象を絞ります。`mls` は、機密のレベルで制御します。`/etc/selinux/config` の `SELINUXTYPE=` で決めます。
例: `SELINUXTYPE=targeted`
注意: タイプを変えると、全ファイルへのラベルの付け直しが必要になることがあります。
関連: SELinux、SELinux のモード

### setenforce
試験: LinuC3SS
要約: SELinux のモードを、一時的に切り替えるコマンドです。
`setenforce 0` で permissive、`setenforce 1` で enforcing にします。今の状態は `getenforce` と `sestatus` で確かめます。
例: `sudo setenforce 0`、`getenforce`、`sestatus`
注意: 再起動すると、`/etc/selinux/config` の設定に戻ります。
関連: SELinux のモード、SELinux

### grubby
試験: LinuC3SS
要約: ブートローダーのカーネルの起動の引数を、コマンドで変えるツールです。
RHEL 系で使います。SELinux を完全に無効にするときの `selinux=0` のように、カーネルの引数を追加、削除します。
例: `sudo grubby --update-kernel ALL --args selinux=0`
注意: 引数を変えた後は、再起動が必要です。
関連: SELinux、ブートローダー

### SELinux の -Z オプション
別名: ls -Z、ps -Z、id -Z
試験: LinuC3SS
要約: ファイルやプロセスの、SELinux のセキュリティコンテキストを表示する、コマンドのオプションです。
`ls -Z` はファイル、`ps -Z` はプロセス、`id -Z` は自分のコンテキストを表示します。ラベルが期待と違う場合の確認に使います。
例: `ls -Z /var/www/html`、`ps -eZ | grep httpd`
注意: SELinux が無効だと、コンテキストは表示されません。
関連: セキュリティコンテキスト、SELinux

### AV ルール
別名: allow ルール、アクセスベクタールール、auditallow、dontaudit
試験: LinuC3SS
要約: SELinux のポリシーで、型と型の間の操作を、許すか、記録するかを書く規則です。
`allow` は、「この型のプロセスが、この型のものに、この操作をしてよい」と書きます。`allow` に書かれていない操作は拒否されます。`auditallow` は、許可した操作をログに残します。`dontaudit` は、拒否した操作のログを出さないようにします。
例: `allow httpd_t httpd_sys_content_t:file { read open getattr };`
注意: `dontaudit` があると、拒否されていてもログに出ません。原因が分からないときは、疑います。
関連: SELinux、AVC 拒否、audit2allow

### seinfo
試験: LinuC3SS
要約: SELinux のポリシーの中身(型、役割、規則)を調べるコマンドです。
`seinfo` は、型や役割の一覧を見ます。`sesearch` は、規則を検索します。ポリシーを調べるときに使います。
例: `seinfo -t | grep httpd`、`sesearch -A -s httpd_t -t httpd_sys_content_t`
注意: 実行には、setools のパッケージが必要です。
関連: SELinux、AV ルール

### semanage
別名: semanage fcontext、semanage port
試験: LinuC3SS
要約: SELinux の設定(ファイルのラベルの規則、ポートの型、ユーザーなど)を、永続的に変えるコマンドです。
`semanage fcontext` で、パスとラベルの対応を追加します。`semanage port` で、ポートに型を割り当てます。ラベルは、`restorecon` で実際のファイルへ反映します。
例: `sudo semanage fcontext -a -t httpd_sys_content_t "/web(/.*)?"`、`sudo semanage port -a -t http_port_t -p tcp 8081`
注意: `semanage fcontext` は規則を足すだけです。ファイルに反映するには、`restorecon` を実行します。
関連: restorecon、chcon、SELinux

### restorecon
試験: LinuC3SS
要約: ファイルの SELinux のラベルを、ポリシーの規則どおりに直すコマンドです。
`semanage fcontext` などで決めた規則を、ファイルに反映します。移動したファイルのラベルが誤っているときにも使います。
例: `sudo restorecon -Rv /web`
注意: `chcon` で付けたラベルは、`restorecon` で規則のラベルに戻ります。
関連: semanage、chcon、セキュリティコンテキスト

### chcon
試験: LinuC3SS
要約: ファイルの SELinux のラベルを、直接変えるコマンドです。
その場でラベルを変えられますが、規則には記録されません。ファイルシステム全体のラベルの付け直し(relabel)や `restorecon` で、元に戻ります。
例: `sudo chcon -t httpd_sys_content_t /web/index.html`
注意: 恒久的な変更には、`semanage fcontext` と `restorecon` を使います。
関連: semanage、restorecon

### audit2allow
試験: LinuC3SS
要約: SELinux の拒否のログから、許可の規則を作るコマンドです。
AVC 拒否のログを読み、拒否を許す規則を作ります。モジュールにして、読み込めます。
例: `sudo ausearch -m avc -ts recent | audit2allow -M mypol`、`sudo semodule -i mypol.pp`
注意: 出てきた規則を、中身を見ずに読み込むと、必要以上の許可になります。まず、ラベルや boolean で解決できないかを確かめます。
関連: AVC 拒否、ausearch、SELinux ブール値

### AppArmor のモード
別名: enforce モード、complain モード
試験: LinuC3SS
要約: AppArmor のプロファイルが、規則に反する操作を、拒否するか、記録だけするかを決める状態です。
`enforce` は、拒否して記録します。`complain` は、拒否せず記録だけします。プロファイルを作る段階では、complain で動かして、ログから規則を作ります。
例: `sudo aa-complain /usr/sbin/nginx`、`sudo aa-enforce /usr/sbin/nginx`
注意: モードは、プロファイルごとに決まります。システム全体で 1 つではありません。
関連: AppArmor プロファイル、aa-complain

### aa-complain
試験: LinuC3SS
要約: AppArmor のプロファイルのモードを、complain や enforce に切り替えるコマンドです。
`aa-complain` は complain(記録のみ)、`aa-enforce` は enforce(拒否する)にします。
例: `sudo aa-complain /etc/apparmor.d/usr.sbin.nginx`
注意: `aa-complain` にしたままにすると、プロファイルが守りにならない状態が続きます。
関連: AppArmor のモード、aa-status

### aa-status
試験: LinuC3SS
要約: AppArmor の状態と、読み込まれたプロファイルのモードを一覧するコマンドです。
enforce や complain のプロファイルの数と名前、保護されているプロセスを確かめます。
例: `sudo aa-status`
注意: プロファイルを `/etc/apparmor.d` に置いただけでは有効になりません。読み込んでいるかを、このコマンドで確かめます。
関連: AppArmor プロファイル、apparmor_parser

### apparmor_parser
試験: LinuC3SS
要約: AppArmor のプロファイルを、カーネルに読み込む、入れ替える、外すコマンドです。
プロファイルを書き換えた後に、読み込み直して反映します。プロファイルは、`/etc/apparmor.d` に置きます。
例: `sudo apparmor_parser -r /etc/apparmor.d/usr.sbin.nginx`
注意: 構文の誤りがあると、読み込みに失敗します。`-r` の後の表示を確かめます。
関連: AppArmor プロファイル、aa-status

### seccomp のモード
別名: SECCOMP_MODE_STRICT、SECCOMP_MODE_DISABLED
試験: LinuC3SS
要約: seccomp が、プロセスのシステムコールを、どこまで制限するかを表す状態です。
`SECCOMP_MODE_DISABLED` は制限なし、`SECCOMP_MODE_STRICT` は `read`、`write`、`exit`、`sigreturn` だけ許可します。`SECCOMP_MODE_FILTER` は、BPF のフィルターで細かく決めます。
例: `grep Seccomp /proc/self/status`(0 は制限なし、1 は strict、2 は filter)
注意: strict は許される呼び出しが極端に少なく、通常のアプリケーションは動きません。実際には filter を使います。
関連: seccomp、seccomp-bpf、システムコール

### seccomp-bpf
別名: seccomp の BPF フィルター
試験: LinuC3SS
要約: seccomp で、システムコールを許可、拒否する条件を、BPF のプログラムで書く方式です。
システムコールの番号や引数を調べ、許可、エラーを返す、プロセスを終了、などを決めます。Docker や systemd が、この仕組みを使います。
例: systemd のユニットで `SystemCallFilter=@system-service`、`SystemCallErrorNumber=EPERM`
注意: systemd の `SystemCallFilter=` は、既定では、許されないシステムコールを呼んだプロセスを終了させます。`SystemCallErrorNumber=` を書くと、エラーを返す動きにできます。
関連: seccomp、システムコール、seccomp のモード

### ケーパビリティの種類
別名: CAP_SYS_ADMIN、CAP_SYS_TIME、CAP_SYS_BOOT、CAP_SYS_MODULE、CAP_SYS_NICE、CAP_NET_ADMIN、CAP_NET_RAW、CAP_NET_BIND_SERVICE、CAP_DAC_OVERRIDE
試験: LinuC3SS
要約: root の権限を細かく分けた、それぞれの権限の名前です。
`CAP_SYS_ADMIN` は、管理の操作の多くを含む広い権限です。`CAP_SYS_TIME` は時計の変更、`CAP_SYS_BOOT` は再起動、`CAP_SYS_MODULE` はカーネルモジュールの読み込み、`CAP_SYS_NICE` は優先度の変更です。`CAP_NET_ADMIN` はネットワークの設定、`CAP_NET_RAW` は生のソケット(ping など)、`CAP_NET_BIND_SERVICE` は 1024 未満のポートの使用です。`CAP_DAC_OVERRIDE` は、ファイルの権限の検査を無視します。
例: Web サーバーに必要なのは、`CAP_NET_BIND_SERVICE` だけ、という設計にする
注意: `CAP_SYS_ADMIN` を与えると、ほぼ root と同じです。コンテナには与えません。
関連: ケーパビリティ、setcap、ケーパビリティセット

### setcap
試験: LinuC3SS
要約: 実行ファイルに、ケーパビリティを付ける、見るコマンドです。
root でなくても、そのファイルを実行するときだけ、決まった権限を持てます。付けたものは、`getcap` で確かめます。
例: `sudo setcap 'cap_net_bind_service=+ep' /usr/local/bin/myapp`、`getcap -r /usr/local/bin`
注意: SUID を使うより権限を絞れます。ただし、付けたファイルが書き換えられると、悪用されます。
関連: ケーパビリティ、ケーパビリティの種類、SUID

### capsh
試験: LinuC3SS
要約: ケーパビリティを調べ、制限をかけた状態でシェルなどを起動するコマンドです。
今のプロセスのケーパビリティの集合を表示できます。特定のケーパビリティを落として試すときにも使います。
例: `capsh --print`、`capsh --drop=cap_net_raw --`
注意: 実行ファイルに付けるケーパビリティは、`setcap` を使います。
関連: ケーパビリティ、setcap

### systemd のケーパビリティ設定
別名: CapabilityBoundingSet、AmbientCapabilities
試験: LinuC3SS
要約: systemd のユニットで、サービスが持てるケーパビリティを決める設定です。
`CapabilityBoundingSet` は、サービスが持てる権限の上限です。`AmbientCapabilities` は、root でないユーザーで動くサービスに、最初から与える権限です。
例: `CapabilityBoundingSet=CAP_NET_BIND_SERVICE`、`AmbientCapabilities=CAP_NET_BIND_SERVICE`
注意: `AmbientCapabilities` で与える権限は、`CapabilityBoundingSet` の範囲内に限られます。
関連: ケーパビリティ、systemd

### ケーパビリティセット
別名: Permitted、Effective、Inheritable
試験: LinuC3SS
要約: プロセスやファイルが持つ、ケーパビリティの集合の種類です。
Permitted は、持てる権限の上限です。Effective は、実際に検査される権限です。Inheritable は、プログラムを新しく実行するとき、引き継げる権限です。
例: `capsh --print`、`getcap /usr/bin/ping`
注意: Permitted にない権限は、Effective にできません。
関連: ケーパビリティ、capsh、setcap

### kernel.kptr_restrict
別名: kptr_restrict
試験: LinuC3SS
要約: カーネル内部のアドレスを、一般のユーザーにどこまで見せるかを決めるパラメーターです。
`/proc/kallsyms` などに出るアドレスが対象です。値が大きいほど隠します。2 にすると、root にも隠します。攻撃者が、カーネルの場所を知ることを難しくします。
例: `sudo sysctl -w kernel.kptr_restrict=2`
注意: デバッグや性能の調査のツールが、アドレスを読めず動かないことがあります。
関連: ASLR、sysctl

### kernel.yama.ptrace_scope
別名: ptrace_scope
試験: LinuC3SS
要約: プロセスを覗く仕組み(ptrace)を、どこまで許すかを決めるパラメーターです。
0 は同じユーザーなら可です。1 は子孫のプロセスだけ可です。2 は管理者だけ可で、3 は全面禁止です。ほかのプロセスのメモリを読む攻撃を、難しくします。
例: `sudo sysctl -w kernel.yama.ptrace_scope=1`
注意: 値を上げると、`strace -p` や `gdb -p` で、動いているプロセスにつなげなくなります。
関連: sysctl、ケーパビリティ

### ファイル監視ルール
別名: auditctl -w
試験: LinuC3SS
要約: auditd で、特定のファイルやディレクトリへのアクセスを記録する規則です。
`-w` で監視するパスを指定し、`-p` で記録する操作を指定します。`r` は読み取り、`w` は書き込み、`x` は実行、`a` は属性の変更です。
例: `-w /etc/passwd -p wa -k passwd_change`
注意: 監視するパスを広げすぎると、ログが大量に出ます。
関連: auditd、auditctl、監査キー

### 監査キー
別名: audit のキー
試験: LinuC3SS
要約: auditd の規則に付ける目印の文字列で、ログを後で探しやすくします。
`-k` でキーを付けると、規則に合ったログにそのキーが入ります。`ausearch -k` や `aureport` で、キーを指定して探せます。
例: `-w /etc/shadow -p wa -k shadow_change`、`sudo ausearch -k shadow_change`
注意: 規則ごとに、意味の分かるキーを付けます。
関連: auditd、ausearch、ファイル監視ルール

## Web とメールのセキュリティ

### HSTS
別名: HTTP Strict Transport Security、Strict-Transport-Security
試験: LinuC3SS
要約: 「このサイトは HTTPS だけでつなぐ」と、ブラウザーに一定期間覚えさせる HTTP ヘッダーです。
HTTP でつなぐと書き換えられる攻撃を防ぎます。`max-age` で覚える期間を、`includeSubDomains` で、サブドメインも対象にするかを決めます。
例: `add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;`
注意: 一度覚えさせると取り消しにくいので、最初は短い `max-age` で試します。
関連: TLS、セキュリティヘッダー

### セキュリティヘッダー
別名: CSP、Content-Security-Policy、X-Frame-Options、X-Content-Type-Options、Referrer-Policy
試験: LinuC3SS
要約: ブラウザーに、安全な動きを指示するために、Web サーバーが返す HTTP ヘッダーの総称です。
CSP は読み込める取得元を制限し、`X-Frame-Options` は iframe への埋め込みを制限します。`X-Content-Type-Options: nosniff` は MIME スニッフィングを止め、`Referrer-Policy` は参照元の送り方を決めます。
例: `curl -sI https://example.com`
注意: nginx の `add_header` は、下の階層に 1 つでもあると、上の階層のものが引き継がれません。
関連: HSTS、HTTP

### SPF
別名: Sender Policy Framework
試験: LinuC3SS
要約: そのドメインのメールを送ってよいサーバーを、DNS の TXT レコードに書いておく仕組みです。
受信側は、メールを送ってきたサーバーの IP アドレスが、許可されているかを確かめます。見るのは、封筒の送信元(`MAIL FROM`)です。
例: `"v=spf1 mx ip4:192.0.2.25 -all"`、`dig +short TXT example.com`
注意: メールを転送すると、IP アドレスが変わって、失敗しやすくなります。1 つのドメインに SPF の TXT は 1 つだけです。
関連: DKIM、DMARC

### DKIM
別名: DomainKeys Identified Mail、OpenDKIM
試験: LinuC3SS
要約: メールに電子署名を付け、受信側が、DNS の公開鍵で、改ざんされていないかを確かめる仕組みです。
公開鍵は、`<セレクター>._domainkey.<ドメイン>` の TXT レコードに置きます。OpenDKIM は、Postfix にミルターとしてつないで、署名と検証をするソフトです。
例: `opendkim-genkey -b 2048 -d example.com -s 202611`、`opendkim-testkey -d example.com -s 202611 -vvv`
注意: 秘密鍵が他のユーザーに読めると、なりすましの署名ができます。権限は 600 にします。
関連: SPF、DMARC

### DMARC
別名: Domain-based Message Authentication, Reporting and Conformance
試験: LinuC3SS
要約: SPF と DKIM の結果が、`From:` のドメインと合っているかを見て、失敗したときの扱いを決める仕組みです。
`_dmarc.<ドメイン>` の TXT レコードに、`p=none`、`quarantine`、`reject` と、報告の送り先(`rua`)を書きます。
例: `"v=DMARC1; p=none; rua=mailto:dmarc@example.com"`
注意: いきなり `p=reject` にせず、`p=none` で報告を見てから強めます。SPF や DKIM が成功しても、ドメインが `From:` と合っていないと、DMARC は失敗します。
関連: SPF、DKIM

## DNS のセキュリティ

### KSK
別名: 鍵署名鍵、ゾーン署名鍵
試験: LinuC3SS
要約: DNSSEC の 2 種類の鍵です。KSK は DNSKEY の組に署名し、ZSK はほかのレコードに署名します。
KSK のハッシュを、DS として親のゾーンに登録します。KSK は長く使い、ZSK は短い周期で替えます。`dnssec-policy default` は、1 つの鍵で両方をする CSK を使います。
例: `dnssec-keygen -a ECDSAP256SHA256 -f KSK -n ZONE example.com`
注意: KSK を替えると、親の DS も替える必要があります。これを忘れると、検証が失敗します。
関連: DNSSEC、トラストアンカー

### NSEC3
別名: NSEC3PARAM
試験: LinuC3SS
要約: 「その名前は存在しない」ことを署名で示すレコードです。NSEC3 は、名前をハッシュにして示します。
NSEC は、存在する名前を順につなぐので、ゾーンの名前の一覧を集められます。NSEC3 は、これをしにくくします。ハッシュの設定は NSEC3PARAM が持ちます。
例: `dig example.com NSEC3PARAM +short`
注意: ハッシュの繰り返しの回数は 0 にするのが、今の推奨です(RFC 9276)。
関連: DNSSEC、KSK

### トラストアンカー
別名: trust-anchors
試験: LinuC3SS
要約: DNSSEC の検証の出発点にする、信頼できる鍵(またはそのハッシュ)です。
通常は、ルートゾーンの鍵です。BIND の `dnssec-validation auto;` は、組み込みのルートの鍵を使います。内部のゾーンなどは、`trust-anchors` に、`static-key` や `static-ds` で自分で登録します。
例: `trust-anchors { "corp.example.internal" static-ds 12345 13 2 "…"; };`
注意: `static-*` は自動で追従しません。鍵を交換したら、手で更新します。
関連: DNSSEC、KSK

### dnssec-policy
試験: LinuC3SS
要約: BIND で、DNSSEC の鍵の作成、署名、鍵の交換を、自動にする設定です。
BIND 9.16 以降で使えます。`dnssec-policy default;` を `zone` に書きます。9.18 では、静的なゾーンファイルには `inline-signing yes;` も書きます。
例: `rndc dnssec -status example.com`、`rndc reconfig`
注意: DS を親のゾーンに登録するのは、人の作業です。登録したら `rndc dnssec -checkds` で named に伝えます。
関連: DNSSEC、KSK、BIND

### dnssec-keygen
試験: LinuC3SS
要約: DNSSEC の署名に使う鍵を作る、BIND のコマンドです。
ゾーンの署名用の鍵(ZSK)と、鍵を署名する鍵(KSK)を作ります。`dnssec-settime` は、鍵の公開、有効化、失効などの時刻を決めます。
例: `dnssec-keygen -a ECDSAP256SHA256 -n ZONE example.com`、`dnssec-keygen -f KSK -a ECDSAP256SHA256 -n ZONE example.com`
注意: 新しい BIND では、`dnssec-policy` で、鍵の作成と更新を自動で行うのが一般的です。
関連: DNSSEC、KSK、dnssec-policy

### dnssec-signzone
試験: LinuC3SS
要約: ゾーンファイルに DNSSEC の署名を付ける、BIND のコマンドです。
鍵を使って、各レコードに署名(RRSIG)を付けます。`dnssec-verify` は、署名済みのゾーンが正しいかを調べます。
例: `dnssec-signzone -S -o example.com db.example.com`、`dnssec-verify -o example.com db.example.com.signed`
注意: 署名には有効期限があります。期限が切れる前に、署名し直します。
関連: DNSSEC、dnssec-keygen、ゾーン

### dnssec-dsfromkey
試験: LinuC3SS
要約: KSK の公開鍵から、親ゾーンに登録する DS レコードを作るコマンドです。
親ゾーン(`.com` など)の管理者に、この DS レコードを渡します。これで、親から子への信頼の鎖がつながります。
例: `dnssec-dsfromkey Kexample.com.+013+12345.key`
注意: DS レコードを親に登録しないと、検証する側が、信頼の鎖をたどれません。
関連: DNSSEC、KSK

### delv
試験: LinuC3SS
要約: DNSSEC の署名を検証しながら、名前を引くコマンドです。
BIND に付いています。署名が正しければ、検証済みと表示します。`dig +dnssec` は、署名のレコードも付けて返すように求めますが、署名の検証は行いません。
例: `delv @192.0.2.53 example.com A`、`dig +dnssec example.com`
注意: `dig +dnssec` で署名が見えても、検証できたという意味ではありません。検証は `delv` や、検証を行うリゾルバーで確かめます。
関連: DNSSEC、DNS、トラストアンカー

## 情報セキュリティの脅威

### 盗聴
試験: ITPassport、FE
要約: 通信の途中で、内容を盗み見ることです。
ネットワークを流れるデータを、こっそり読み取ることです。暗号化されていない通信では、パスワードや本文がそのまま読まれます。
例: 暗号化していない公衆無線 LAN で、通信の内容を読み取られる。
注意: 盗聴は読み取るだけで、データを書き換える改ざんとは別の脅威です。対策は通信の暗号化(TLS、VPN など)です。
関連: TLS、VPN、改ざん

### なりすまし
試験: ITPassport、FE
要約: 他人の ID や名前を使って、本人のふりをすることです。
盗んだパスワードや偽のメールアドレスなどで、他人になりすまします。なりすました人の権限で、情報を見たり操作したりします。
例: 盗んだ ID とパスワードで、他の社員としてログインする。
注意: 対策は、多要素認証、電子署名、送信ドメイン認証(SPF、DKIM)など、本人かどうかを確かめる仕組みです。
関連: 多要素認証、電子署名、SPF

### 改ざん
試験: ITPassport、FE
要約: データやプログラムを、権限なく書き換えることです。
許可を受けていない人が、データやプログラムの中身を変えてしまうことです。情報セキュリティの特性のうち、完全性が損なわれます。
例: Web サイトの内容を書き換える。見積書の金額を書き換える。
注意: 改ざんは、書き換えを防ぐだけでなく、検知する対策(ハッシュ値、電子署名)も大切です。
関連: 完全性、ハッシュ、電子署名

### 踏み台
試験: FE
要約: 乗っ取った機器を、別の攻撃の中継に使うことです。
攻撃者は、乗っ取った機器を経由して、別の標的を攻撃します。攻撃元が踏み台の機器に見えるため、本当の攻撃者を探しにくくなります。
例: 乗っ取られた Web サーバーから、他社のサーバーへ攻撃が送られる。
注意: 踏み台にされると、自分が被害者であるのに、加害者として扱われるおそれがあります。
関連: ボット、オープンリレー

### 情報漏えい
試験: ITPassport
要約: 秘密にしておくべき情報が、外部に出てしまうことです。
不正アクセスや内部不正のほか、誤送信、紛失、設定ミスなどでも起きます。機密性が損なわれた状態です。
例: 顧客の個人情報を、宛先を間違えてメールで送ってしまう。
注意: 悪意のある攻撃だけでなく、人の誤りや設定の不備も大きな原因です。
関連: 機密性、内部不正

### 内部不正
試験: ITPassport
要約: 組織の内部の人が、権限を使って不正を行うことです。
従業員や委託先の人が、持っている権限で、情報を持ち出したり不正に操作したりすることです。外部からの攻撃と違い、正規の権限を使うので、見つけにくくなります。
例: 退職前の社員が、顧客名簿を持ち出す。
注意: 対策は、権限の最小化、操作の記録と監視、不正が見つかる状況をつくることです。
関連: 不正のトライアングル、内部不正防止ガイドライン、最小権限の原則

### 不正のトライアングル
別名: 不正のトライアングル理論
試験: ITPassport、FE
要約: 不正が起きる条件を、動機、機会、正当化の 3 つで表した考え方です。
3 つがそろうと、不正が起きやすくなります。組織は、権限の分離やログの監視で、とくに機会を減らします。
例: お金に困っている(動機)社員が、チェックのない経理の作業で(機会)、「後で返すから」と考える(正当化)。
注意: ITパスポートでは「動機・プレッシャー」と書かれることがあります。同じ要素を指します。
関連: 内部不正

### SNS の悪用
試験: ITPassport
要約: SNS で、なりすましや偽の情報によって、人をだますことです。
企業や人になりすましたアカウントで、偽の情報を広めたり、不正なサイトに誘導したりします。従業員の書き込みから、機密が漏れることもあります。
例: 企業の公式を装ったアカウントが、偽のキャンペーンの URL を広める。
注意: 組織の側の対策として、ソーシャルメディアガイドラインを決めます。
関連: フィッシング、ソーシャルメディアガイドライン

### 迷惑メール
別名: スパム、迷惑メール(スパム)
試験: ITPassport
要約: 受信者が望んでいないのに、不特定多数に送られるメールです。
広告や詐欺、フィッシングのために、大量に送られます。ボットに感染した端末が、送信に使われることがあります。
例: 当選を知らせると偽る、不審なメール。
注意: 迷惑メールの本文中のリンクや添付ファイルは、開かないようにします。
関連: フィッシング、OP25B、オープンリレー

### ダークウェブ
試験: ITPassport、FE
要約: 専用のソフトで接続する、匿名性の高いネットワークの領域です。
通常の検索では見つからず、特別なソフトウェアでつなぎます。盗まれた情報の売買に使われることがあります。
例: 流出した ID とパスワードの一覧が売られる。
注意: ダークウェブにあること自体が違法なのではなく、盗まれた情報の取引などに使われるのが問題です。
関連: リークサイト

### リークサイト
試験: ITPassport、FE
要約: ランサムウェアの攻撃者が、盗んだ情報を公開するサイトです。
身代金を払わない被害組織の情報を公開して、脅しに使います。ファイルの暗号化に加えて、情報の公開でも脅す手口の一部です。
例: 被害組織の名前と、盗んだファイルの一部が載せられる。
注意: バックアップがあってもデータの公開は防げないため、情報の持ち出しを防ぐ対策も必要です。
関連: マルウェア、ダークウェブ

### サイバー攻撃
試験: ITPassport
要約: コンピューターやネットワークを狙う、悪意のある攻撃の総称です。
不正アクセス、マルウェア、DDoS 攻撃、標的型攻撃などが含まれます。
例: DDoS 攻撃で Web サイトを止める。
注意: 個別の攻撃の名前ではなく、まとめた呼び方です。
関連: DDoS 攻撃、標的型攻撃

### シャドー IT
別名: シャドーIT
試験: ITPassport、FE
要約: 組織が許可していない機器やサービスを、従業員が業務に使うことです。
組織が把握も許可もしていないため、更新や監視が届きません。情報漏えいの原因になります。
例: 個人のクラウドストレージに、業務の資料を置く。
注意: 悪意がなくても、便利さを求めた行動から起きる点が問題です。
関連: 情報漏えい

### 権限昇格
別名: 特権昇格
試験: FE
要約: 一般の利用者の権限から、管理者などの強い権限を得ることです。
脆弱性や設定の不備を使って行います。強い権限を得ると、情報の持ち出しや設定の変更がしやすくなります。
例: 一般ユーザーで入り込み、管理者の権限を得る。
注意: 防ぐには、最小権限の原則と、脆弱性の修正が基本です。
関連: 最小権限の原則、脆弱性

## マルウェアの種類

### ウイルス
別名: コンピュータウイルス、コンピューターウイルス
試験: FE
要約: ほかのファイルに寄生して、自分を複製するマルウェアです。
感染したファイルを実行すると広がります。ワームと違い、広がるには宿主になるファイルが必要です。
例: 文書ファイルのマクロに潜むマクロウイルス。
注意: ネットワークを通じて自分で広がるのは、ウイルスではなくワームです。
関連: ワーム、マルウェア

### ワーム
試験: FE
要約: 単独で動き、ネットワークを通じて自分で広がるマルウェアです。
ほかのファイルに寄生せず、脆弱性などを使って、次々に別の機器に感染します。
例: ネットワーク内の機器に、次々に感染を広げる。
注意: 利用者が実行して入り込むのは、トロイの木馬です。ワームは自分で広がります。
関連: ウイルス、トロイの木馬、マルウェア

### ボット
試験: ITPassport、FE
要約: 外部の指令で遠隔操作される、マルウェアです。
感染した端末は、攻撃者のサーバーの命令で動きます。操られた端末の集まりを、ボットネットといいます。
例: ボットネットから、DDoS 攻撃や迷惑メールの送信が行われる。
注意: ボットに命令を出す側のサーバーが C&C サーバーです。
関連: C&C サーバー、DDoS 攻撃、マルウェア

### C&C サーバー
別名: C2 サーバー、Command and Control サーバー
試験: ITPassport
要約: ボットに命令を出す、攻撃者のサーバーです。
感染した端末は、C&C サーバーから命令を受け取り、攻撃や情報の送信を行います。
例: ボットネットの各端末が、定期的に C&C サーバーへ通信する。
注意: 内側から外へ向かう不審な通信の検知が、対策になります。
関連: ボット

### トロイの木馬
試験: ITPassport、FE
要約: 有用なソフトに見せかけて入り込み、裏で不正な動作をするマルウェアです。
自分では増えず、利用者が実行して入り込みます。便利なソフトやファイルに見せかけます。
例: 無料のツールを装い、実行すると情報を盗むプログラム。
注意: ワームは自分を複製して広がりますが、トロイの木馬は自分では増えません。
関連: ワーム、マルウェア

### スパイウェア
試験: ITPassport、FE
要約: 利用者に気付かれずに、情報を集めて外部に送るマルウェアです。
閲覧の履歴や入力した内容などを、こっそり攻撃者へ送ります。
例: 入力した内容を記録して、外部に送るプログラム。
注意: 感染しても目立つ症状が出にくく、気付きにくい点が特徴です。
関連: キーロガー、マルウェア

### キーロガー
試験: ITPassport、FE
要約: キーボードの入力を記録して、パスワードなどを盗むものです。
入力された文字を記録して、攻撃者に送ります。ソフトウェア型と、機器を取り付けるハードウェア型があります。
例: ネットバンキングのパスワードの入力が、記録される。
注意: ソフトウェアのキーロガーはスパイウェアの一種です。
関連: スパイウェア

### ルートキット
試験: FE
要約: 侵入後に、攻撃者のプロセス、ファイル、通信の痕跡を隠すものです。
管理者に不審な動きを見つけられないように、攻撃の跡を隠します。侵入を長く続けるために使います。
例: 不正なプロセスが、一覧に表示されないようにする。
注意: ルートキット自体が侵入するのではなく、侵入した後の隠ぺいに使われます。
関連: バックドア、マルウェア

### バックドア
試験: ITPassport、FE
要約: 攻撃者が、後から再び侵入するために仕掛ける裏口です。
一度侵入した攻撃者が、パスワードが変えられても入れるように作ります。
例: 攻撃者専用のアカウントや、待ち受けのプログラムを置く。
注意: 侵入された機器は、侵入の入口を直すだけでなく、バックドアの有無も調べます。
関連: ルートキット、マルウェア

### ファイルレスマルウェア
試験: ITPassport、FE
要約: ファイルを残さず、メモリ上や OS の正規の機能で動くマルウェアです。
OS に標準で入っている正規のツールを悪用して、主にメモリ上で動きます。ディスクにファイルが残りにくく、ファイルの検査だけでは見つけにくくなります。
例: OS の標準のスクリプト実行ツールを悪用して、不正な処理をする。
注意: ファイルの検査だけでなく、動作を監視するふるまい検知や EDR が有効です。
関連: ふるまい検知、EDR、マルウェア

### マルウェアの亜種
別名: バリアント、バリアント(亜種)
試験: ITPassport
要約: 既存のマルウェアを少し変えて作られた、別のマルウェアです。
プログラムの一部を変えて、検出されにくくします。AI の悪用で、大量に作られるようになったとされます。
例: 同じ動きで、ファイルの特徴だけが違うマルウェア。
注意: 特徴だけで照らし合わせる検出では、亜種を見逃すことがあります。
関連: パターンファイル、ふるまい検知、マルウェア

## 攻撃の手口

### ゼロデイ攻撃
試験: ITPassport、FE
要約: 修正プログラムが出る前の脆弱性を突く攻撃です。
脆弱性が公表される前や、修正プログラムが出る前に行われます。パッチがないので、防ぐのが難しくなります。
例: 公表直後の脆弱性を突いて、侵入する。
注意: パッチの適用だけでは防げないため、ふるまい検知や権限の最小化などを重ねます。
関連: 脆弱性、パッチ、多層防御

### サイバーキルチェーン
試験: FE
要約: 攻撃を、偵察から目的の実行までの段階に分けて表す考え方です。
偵察、武器化、配送、攻撃、インストール、遠隔操作、目的の実行の 7 段階です。どの段階でも見つけて止められるように、対策を重ねます。
例: 偵察の段階で、公開情報を集められる。
注意: 1 つの段階で止めれば、後の段階は進めません。対策は、複数の段階に置きます。
関連: フットプリンティング、多層防御

### フットプリンティング
試験: ITPassport、FE
要約: 攻撃の準備として、標的の公開情報を集めることです。
ドメイン、IP アドレス、公開サービス、OS、社員名などを調べます。開いているポートを調べるポートスキャンも、準備の一つです。
例: 公開されている情報から、標的の機器の種類を調べる。
注意: 攻撃そのものではなく、準備の段階です。公開する情報を必要最小限にするのが対策です。
関連: サイバーキルチェーン

### リバースブルートフォース攻撃
別名: パスワードスプレー
試験: FE
要約: パスワードを固定して、ID を変えながら試す攻撃です。
1 つの ID に対する失敗の回数が少ないので、アカウントのロックアウトで検知しにくくなります。
例: よくあるパスワード 1 つで、多数の ID にログインを試す。
注意: 1 つの ID に対して試す、通常のブルートフォース攻撃とは、試す対象が逆です。
関連: 総当たり攻撃、多要素認証

### クレデンシャルスタッフィング
別名: パスワードリスト攻撃、リスト型攻撃
試験: ITPassport、FE
要約: 他のサービスから流出した ID とパスワードの組で、ログインを試す攻撃です。
パスワードを複数のサービスで使い回していると、成功します。
例: 流出した ID とパスワードの一覧を使い、別のサービスにログインする。
注意: 対策は、パスワードの使い回しをやめることと、多要素認証です。
関連: 総当たり攻撃、多要素認証

### セッションハイジャック
試験: FE
要約: ログイン後のセッション ID を盗むなどして、本人になりすます攻撃です。
セッション ID を盗んだり、推測したりして、ログインしたままの利用者のふりをします。
例: 盗んだセッション ID で、ログイン済みの画面を操作する。
注意: 対策は、通信の暗号化と、推測されにくいセッション ID です。
関連: なりすまし、TLS

### 中間者攻撃
別名: MITM、MITM 攻撃、中間者攻撃(MITM)
試験: ITPassport
要約: 通信の途中に割り込み、盗聴や改ざんをする攻撃です。
通信する 2 者の間に入り、お互いのふりをして、通信の中身を盗み見たり書き換えたりします。
例: 偽の無線 LAN のアクセスポイントで、通信に割り込む。
注意: 対策は、TLS と証明書の確認です。
関連: 盗聴、改ざん、TLS

### MITB 攻撃
別名: MITB、Man-in-the-browser
試験: ITPassport
要約: ブラウザに潜むマルウェアが、画面や送信内容を書き換える攻撃です。
利用者のブラウザの中で動くため、通信が暗号化されていても、表示や送信の内容を書き換えられます。
例: ネットバンキングで、送金先の口座を書き換える。
注意: 通信の暗号化だけでは防げません。取引内容を、別の経路で確認する対策があります。
関連: マルウェア

### OS コマンドインジェクション
別名: OSコマンドインジェクション
試験: FE
要約: 入力に OS のコマンドを紛れ込ませ、サーバーで実行させる攻撃です。
入力値をそのまま OS のコマンドの一部にするプログラムで起きます。サーバーが乗っ取られるおそれがあります。
例: 入力欄にコマンドを区切る記号を入れて、別のコマンドを実行させる。
注意: 対策は、OS のコマンドを直接呼ばないことと、入力値の検証です。
関連: SQL インジェクション

### CSRF
別名: クロスサイトリクエストフォージェリ、Cross-Site Request Forgery
試験: FE
要約: ログイン中の利用者のブラウザに、意図しないリクエストを送らせる攻撃です。
利用者が罠のページを開くと、ログイン済みのサイトに、勝手に操作が送られます。
例: 罠のページを開いただけで、パスワードの変更が行われる。
注意: XSS はページにスクリプトを埋め込む攻撃で、CSRF は利用者の権限で操作を送らせる攻撃です。
関連: SQL インジェクション、セキュリティヘッダー

### ディレクトリトラバーサル
別名: パストラバーサル
試験: FE
要約: `../` で上のディレクトリをたどり、公開していないファイルを読む攻撃です。
ファイル名の入力に、`../` などを入れて、公開していない場所のファイルを読み出します。
例: URL に `../../etc/passwd` を指定する。
注意: 対策は、入力されたファイル名をそのまま使わないことと、公開範囲の制限です。
関連: OS コマンドインジェクション

### バッファオーバーフロー
試験: ITPassport、FE
要約: 確保した領域を超えてデータを書き込み、プログラムを乱す攻撃です。
想定より長いデータを送ると、隣の領域が書き換わります。プログラムの動作を乗っ取られることがあります。
例: 長すぎる入力で、プログラムが異常終了する。
注意: 対策は、入力の長さの確認と、境界を検査する関数や言語の使用です。
関連: セキュアプログラミング

### クリックジャッキング
試験: FE
要約: 透明にしたページを重ねて、意図しないクリックをさせる攻撃です。
見えているボタンの上に、透明なページを重ねて、利用者に別の操作をさせます。
例: 「再生」のボタンを押したつもりが、別のサイトの「購入」を押している。
注意: 対策に、`X-Frame-Options` や CSP のヘッダーで、ほかのサイトへの埋め込みを禁じる方法があります。
関連: セキュリティヘッダー

### ドライブバイダウンロード
試験: ITPassport、FE
要約: Web サイトを開くだけで、マルウェアをダウンロードさせる攻撃です。
改ざんされたサイトなどを閲覧すると、利用者の操作なしに、ブラウザの脆弱性を突いて入り込みます。
例: 改ざんされたサイトを開いたら、ウイルスに感染する。
注意: クリックしなくても感染するため、ブラウザや OS を最新にするのが基本の対策です。
関連: マルウェア、パッチ

### DNS キャッシュポイズニング
別名: DNSキャッシュポイズニング、DNS キャッシュ汚染
試験: FE
要約: DNS のキャッシュに偽の応答を覚えさせ、偽のサイトに誘導する攻撃です。
キャッシュサーバーに、偽の情報を覚えさせます。利用者は、正しい名前を入力しても、偽のサイトへ導かれます。
例: 銀行のドメイン名に対して、偽サイトの IP アドレスが返る。
注意: 対策は、DNSSEC による応答の検証です。
関連: DNSSEC

### 標的型攻撃
別名: APT、標的型メール攻撃
試験: ITPassport、FE
要約: 特定の組織や人を狙って、長い期間をかけて行う攻撃です。
業務に関係するように見せかけたメールなどで入り込み、目立たないように、情報を盗み続けます。
例: 取引先を装ったメールで、不正なファイルを開かせる。
注意: APT は、長期にわたる高度な標的型攻撃の総称です。
関連: 水飲み場型攻撃、標的型メール訓練

### 水飲み場型攻撃
試験: FE
要約: 標的がよく使う Web サイトを改ざんして、待ち受ける攻撃です。
標的の組織の人が、よく閲覧するサイトにマルウェアを仕掛けます。
例: 業界団体のサイトが改ざんされ、閲覧した人が感染する。
注意: 標的に直接送るメールとは違い、標的が自分でサイトを開くのを待ちます。
関連: 標的型攻撃、ドライブバイダウンロード

### DNS 水責め攻撃
別名: ランダムサブドメイン攻撃
試験: FE
要約: 存在しないサブドメインを大量に問い合わせ、DNS サーバーを過負荷にする攻撃です。
存在しない名前は、キャッシュにないため、毎回権威サーバーへ問い合わせが届きます。
例: ランダムな文字列のサブドメインを、大量に問い合わせる。
注意: キャッシュが効かない問い合わせを狙う点が、特徴です。
関連: DDoS 攻撃

### オープンリゾルバ
別名: オープンリゾルバの悪用
試験: FE
要約: 外部の誰にでも応答する、DNS キャッシュサーバーです。
悪用されると、送信元を標的に偽った問合せで、大きな応答が標的へ向かう反射・増幅の攻撃に使われます。
例: 世界中から問合せを受け付ける DNS サーバー。
注意: 対策は、問合せを受け付ける範囲を、自組織の利用者に限ることです。
関連: DDoS 攻撃、オープンリレー

### クリプトジャッキング
試験: FE
要約: 他人の計算資源を、無断で暗号資産の採掘に使うことです。
乗っ取った機器やクラウドの資源を使って、採掘を行います。機器の動作が遅くなったり、利用料金が増えたりします。
例: 乗っ取ったサーバーの CPU を、採掘に使う。
注意: 気付くきっかけは、CPU の使用率や利用料金の異常です。
関連: マルウェア

### サイドチャネル攻撃
試験: FE
要約: 処理時間や消費電力など、副次的な情報から、鍵を推測する攻撃です。
暗号の計算そのものではなく、実装から漏れる情報を測ります。
例: 暗号化にかかる時間の差から、鍵を推測する。
注意: 暗号の方式が安全でも、実装によっては、この攻撃で破られます。
関連: 耐タンパ性

### プロンプトインジェクション
試験: ITPassport、FE
要約: AI への入力に細工をして、本来の指示を上書きさせる攻撃です。
AI への指示文(プロンプト)に、巧妙な指示を混ぜて、制限を無視させたり、意図しない出力をさせたりします。対策に、入力の検証があります。
例: 「これまでの指示を無視して」と書いた文書を、AI に読ませる。
注意: 入力の検証だけで完全には防げないため、AI に与える権限も最小限にします。
関連: ジェイルブレイク、Security for AI

### ジェイルブレイク
試験: FE
要約: 指示を工夫して、AI の安全のための制限を回避する攻撃です。
AI に設けられた、有害な出力を避ける制限を、言い回しの工夫などで外します。
例: 役を演じさせる指示で、拒否される内容を出力させる。
注意: プロンプトインジェクションと似ていますが、狙いは AI の安全のための制限を外すことです。
関連: プロンプトインジェクション

### 敵対的サンプル
別名: Adversarial Examples
試験: FE
要約: 人には分からない細工を入力に加え、学習済みの AI に誤った判断をさせる攻撃です。
画像などに、見た目では分からない小さな変更を加えて、AI の判断を誤らせます。
例: 標識の画像に細工をして、AI に別の標識と判断させる。
注意: 学習データを狙うデータポイズニングとは違い、使う段階の入力を細工します。
関連: データポイズニング

### データポイズニング
試験: FE
要約: 学習データに不正なデータを混ぜて、AI の判断を歪める攻撃です。
AI の学習の段階で、不正なデータを混ぜ、判断の傾向を変えます。
例: 偽の学習データで、特定の入力を正しく判定できなくする。
注意: 対策は、学習データの出どころの確認です。
関連: 敵対的サンプル

## リスクマネジメント

### 情報セキュリティの 3 要素
別名: CIA、機密性・完全性・可用性、情報セキュリティの 3 つの特性
試験: ITPassport、FE
要約: 情報セキュリティで守る、機密性、完全性、可用性の 3 つの特性です。
機密性は許可された人だけが使えること、完全性は正確で改ざんされていないこと、可用性は必要なときに使えることです。対策を選ぶときは、どの特性を守りたいかを考えます。
例: 情報漏えいは機密性、データの書き換えは完全性、サーバーの停止は可用性が損なわれた例。
注意: バックアップは可用性を守る対策であり、盗み見を防ぐ(機密性)対策ではありません。
関連: 機密性、完全性、可用性

### 機密性
別名: Confidentiality
試験: ITPassport、FE
要約: 許可された人だけが、情報を使えることです。
許可されていない人に、情報が見られたり使われたりしない状態です。損なわれると、情報漏えいになります。
例: アクセス制御、暗号化、認証で守る。
注意: 機密性の対策(暗号化)と、完全性の対策(電子署名)は、目的が違います。
関連: 情報セキュリティの 3 要素、暗号化

### 完全性
別名: Integrity
試験: ITPassport、FE
要約: 情報が正確で、改ざんや欠落がないことです。
情報が、許可なく書き換えられたり消されたりしていない状態です。
例: 電子署名、ハッシュ値、変更の記録で守る。
注意: 「正しい値である」だけでなく、「勝手に変えられていない」ことが完全性です。
関連: 情報セキュリティの 3 要素、ハッシュ、電子署名

### セキュリティバイデザイン
別名: セキュアバイデザイン、Security by Design
試験: ITPassport、FE
要約: 企画や設計の段階から、セキュリティを組み込む考え方です。
できあがった後に対策を足すのではなく、最初から作り込みます。後から直すよりも、費用と手間を抑えられます。
例: 設計の段階で、脅威を洗い出して、対策を要件に入れる。
注意: 運用の段階だけで行う対策ではありません。企画や設計の段階から行います。
関連: プライバシーバイデザイン

### プライバシーバイデザイン
別名: Privacy by Design
試験: ITPassport、FE
要約: 企画や設計の段階から、個人情報の保護を組み込む考え方です。
個人情報の保護を、後から付け足すのではなく、システムの設計に組み込みます。
例: 必要な個人情報だけを集めるように、設計する。
注意: 対象は、個人情報の保護です。セキュリティ全般を組み込む考え方は、セキュリティバイデザインです。
関連: セキュリティバイデザイン

### need-to-know の原則
別名: need-to-know、知る必要の原則
試験: FE
要約: 業務に必要な人に、必要な情報だけを知らせる原則です。
アクセス権は必要最小限にして、異動や退職で見直します。
例: 営業は、自分の担当の顧客の情報だけを見られる。
注意: 最小権限の原則が権限に関する考え方であるのに対し、need-to-know は情報を知らせる範囲についての考え方です。
関連: 最小権限の原則

### 情報資産
試験: ITPassport
要約: 組織が守る対象になる、データ、システム、文書などです。
データ、ソフトウェア、機器、文書、人の知識などが含まれます。重要度に応じて「極秘」「社外秘」「公開」などに区分し、区分ごとに取扱いの規則を決めます。
例: 顧客データベース、設計書、サーバー機器。
注意: 守る対象が分からないと、対策を決められません。まず情報資産を洗い出します。
関連: 情報資産台帳

### 情報資産台帳
試験: ITPassport、FE
要約: 情報資産の名称、管理者、保管場所、重要度などを記録した一覧です。
守る対象を一覧にして、管理します。リスクアセスメントの出発点になります。
例: 資産の名称、管理者、保管場所、重要度の区分を、表にしたもの。
注意: 作って終わりではなく、機器や担当の変更に合わせて、更新します。
関連: 情報資産、リスクアセスメント

### リスクマネジメント
試験: ITPassport
要約: リスクを特定し、評価して、対応する一連の活動です。
リスクアセスメントで、リスクを見つけて評価し、対応を選びます。その後も、見直しを続けます。
例: リスクを洗い出し、対策の優先順位を決めて、実施する。
注意: リスクアセスメントは、リスクマネジメントの一部です。
関連: リスクアセスメント

### リスクアセスメント
別名: リスク特定・分析・評価
試験: ITPassport、FE
要約: リスクを見つけ、見積もり、対応が必要かを判断する活動です。
リスク特定、リスク分析、リスク評価の 3 つの順で進めます。判断には、あらかじめ決めたリスク基準を使います。
例: 特定で見つけた脅威について、分析で起きやすさと影響を見積もり、評価で対応の要否を決める。
注意: リスク対応(回避、低減など)は、リスクアセスメントの後に選ぶ段階です。
関連: リスクマネジメント、リスク基準、リスクレベル

### リスク基準
試験: ITPassport
要約: リスクの大きさを評価し、対応の要否を判断するための基準です。
あらかじめ決めておきます。リスク評価で、見積もったリスクと比べます。
例: 影響が大きく、発生しやすいものは、対応が必要とする。
注意: 基準は組織ごとに決めます。
関連: リスクアセスメント

### リスクレベル
試験: FE
要約: リスクの大きさを表す値です。
発生可能性と影響度を見積もって、決めます。「発生可能性 × 影響度」で求めることが多くなります。
例: 発生可能性が高く、影響度が大きいと、リスクレベルは高い。
注意: リスクレベルが高いからといって、必ず回避するわけではなく、基準と比べて対応を選びます。
関連: リスクマトリックス、リスクアセスメント

### リスクマトリックス
試験: FE
要約: 発生可能性と影響度の表に、リスクを当てはめて、優先度を決める方法です。
縦横の表に、リスクを置きます。リスクレベルが、一目で分かります。
例: 縦軸を発生可能性、横軸を影響度にして、各リスクを置く。
注意: 置き方は一例で、実際はリスク基準と比べて判断します。
関連: リスクレベル、リスク登録簿

### リスク回避
試験: ITPassport、FE
要約: リスクの原因になる活動を、やめることです。
リスクの原因をなくすので、リスクはなくなりますが、その活動で得られる利益もなくなります。
例: リスクの大きなサービスの提供をやめる。
注意: 対策でリスクを小さくするのは、リスク低減です。
関連: リスク低減、リスク共有

### リスク低減
別名: リスク軽減
試験: FE
要約: 対策をして、発生可能性や影響を下げることです。
パッチの適用、暗号化、アクセス権の見直しなどで、リスクを小さくします。
例: 脆弱性にパッチを適用する。
注意: 対策をしても、リスクは残ります。残ったものが残留リスクです。
関連: リスク回避、残留リスク

### リスク共有
別名: リスク移転、リスク共有(移転、分散)
試験: ITPassport、FE
要約: 損害や責任を、他者と分けることです。
保険や外部への委託などで、損害の負担を他者に移します(リスク移転)。拠点や資産を分けて被害を分散させること(リスク分散)も、リスク共有に含めます。
例: サイバー保険に入る。データセンターを複数に分ける。
注意: 責任を相手に移しても、リスクそのものはなくなりません。
関連: リスク回避、リスク低減

### リスク保有
別名: リスク受容
試験: ITPassport、FE
要約: 理解したうえで、リスクをそのまま受け入れることです。
影響が小さく、対策の費用に見合わないときなどに、選びます。
例: 影響が小さいので、対策をしない。
注意: 何もしないのではなく、リスクを理解して、受け入れる判断をしたことが条件です。
関連: リスク低減、残留リスク

### 残留リスク
試験: FE
要約: 対応をしても、残るリスクです。
対策をしても、リスクがゼロになるとは限りません。残ったリスクを、受け入れられるかを、リスク所有者が判断します。
例: パッチを適用しても、未知の脆弱性のリスクは残る。
注意: 残留リスクが受け入れられないときは、追加の対応をします。
関連: リスク低減、リスク保有

### オペレーショナルリスク
試験: FE
要約: 業務の運用、人のミス、システムの障害などから生じるリスクです。
外部の攻撃だけでなく、組織の内部の運用の誤りも、リスクになります。
例: 操作ミスで、本番のデータを消してしまう。
注意: 攻撃などの外部の脅威だけをリスクと考えるのは、不十分です。
関連: サプライチェーンリスク

### サプライチェーンリスク
試験: FE
要約: 委託先や部品の供給元を経由して、自社に被害が及ぶリスクです。
自社の対策が十分でも、取引先が攻撃されると、被害を受けることがあります。
例: 委託先が侵入され、預けた情報が漏れる。
注意: 対策に、供給者との契約と管理があります。
関連: 供給者管理

### 供給者管理
別名: 供給者関係における情報セキュリティ
試験: FE
要約: 委託先や供給元のセキュリティを、契約と点検で管理することです。
情報を預けたり、機器やサービスを調達したりする先に、セキュリティの要求を示します。ISMS では、組織的管理策に含まれます。
例: 委託契約に、セキュリティの要求事項と、監査の条件を入れる。
注意: 委託しても、情報の管理の責任は、委託元に残ります。
関連: サプライチェーンリスク、組織的管理策

### 情報セキュリティ要求事項
試験: FE
要約: 何を、どの程度まで守る必要があるかを、具体的に書いたものです。
守る対象(情報資産)、守りたいこと(機密性、完全性、可用性)、満たしたかを確かめる方法が分かるように書きます。システムの開発や利用の前に提示します。
例: 「営業は、自分の担当の顧客だけ見られるように、役割でアクセスを制限する」。
注意: 「とにかく安全にする」は、確かめられないので、要求事項になりません。
関連: 情報セキュリティの 3 要素

### 多層防御
試験: FE
要約: 複数の対策を重ねて、守る考え方です。
1 つの対策が破られても、ほかの対策で被害を防げるようにします。
例: ファイアウォール、マルウェア対策、アクセス制御、ログの監視を重ねる。
注意: 1 つの対策だけで守りきろうとすると、それが破られたときに被害が出ます。
関連: ファイアウォール、ゼロデイ攻撃

## 組織と規程と制度

### 情報セキュリティポリシー
別名: 情報セキュリティ方針
試験: ITPassport、FE
要約: 組織の情報セキュリティの方針と基準を、まとめた文書です。
経営者が示す基本的な考え方(基本方針)を一番上に置き、その下に対策基準と、実施手順を置きます。
例: 基本方針、対策基準、実施手順の 3 つの階層に分ける。
注意: 方針だけを指す場合と、方針、対策基準、実施手順をまとめて指す場合があります。
関連: 情報セキュリティ対策基準

### 情報セキュリティ対策基準
試験: ITPassport、FE
要約: 方針を実現するための、具体的な守るべき規則です。
パスワードの長さ、持出しの手続きなどを決めます。対策基準を、実際の手順にしたものが、実施手順です。
例: パスワードは 12 文字以上にする。
注意: 方針は考え方、対策基準は具体的な規則です。
関連: 情報セキュリティポリシー

### プライバシーポリシー
別名: 個人情報保護方針
試験: ITPassport
要約: 個人情報を集める目的や取扱いを、社会に向けて示す方針です。
個人情報を集める目的、取扱い、問い合わせ先などを示します。
例: Web サイトに載せている、個人情報の取扱いの案内。
注意: 社内の規則である情報セキュリティポリシーとは違い、社会に向けて示します。
関連: 情報セキュリティポリシー

### ソーシャルメディアガイドライン
別名: SNS 利用ポリシー
試験: ITPassport
要約: 従業員が SNS を使うときの、守ることを定めたものです。
機密を書かない、会社の発言と誤解されないようにする、などを定めます。
例: 業務で知った情報を、投稿しない。
注意: 個人のアカウントでも、会社の信用や機密に関わる点が対象です。
関連: SNS の悪用

### 情報セキュリティ委員会
試験: ITPassport
要約: 経営層や各部門の代表が、方針や重要な事項を決める組織です。
情報セキュリティの方針や、重要な事項を決めます。
例: 年に数回集まり、方針の見直しを決める。
注意: インシデントの対応を担う CSIRT とは役割が違います。
関連: CSIRT

### CSIRT
別名: シーサート、CSIRT(インシデント対応)、Computer Security Incident Response Team
試験: ITPassport、FE
要約: インシデントが起きたときの対応を、取りまとめる組織内のチームです。
報告の受付、原因の調査、復旧の支援、再発の防止を担います。気付いた人は、規程で決めた窓口(CSIRT など)へ、直ちに報告します。
例: 感染の疑いがある端末の報告を受けて、対応を指示する。
注意: 常時の監視は SOC の役割、インシデントの対応は CSIRT の役割と分ける考え方があります。
関連: SOC、インシデントハンドリング

### SOC
別名: Security Operation Center
試験: ITPassport、FE
要約: ネットワークやシステムを常時監視して、脅威を検知する組織や拠点です。
ログなどを監視して、攻撃や異常を見つけ、分析します。
例: SIEM で集めたログを、24 時間体制で監視する。
注意: 監視と検知が中心で、インシデントの対応を取りまとめる CSIRT とは役割が違います。
関連: CSIRT、SIEM

### エシカルハッカー
試験: FE
要約: 許可を得て、攻撃の技術で、システムの弱点を探す技術者です。
攻撃者と同じ技術を使いますが、許可を得て、弱点を見つけて報告します。
例: 依頼を受けて、ペネトレーションテストを行う。
注意: 許可を得ていない行為は、同じ技術でも不正アクセスです。
関連: ペネトレーションテスト

### J-CRAT
別名: サイバーレスキュー隊
試験: ITPassport
要約: 標的型攻撃を受けた組織を、IPA が支援する活動です。
被害の把握、被害の拡大の防止、再発の防止を支援します。
例: 標的型攻撃を受けた組織が、支援を求める。
注意: 民間のセキュリティ会社ではなく、IPA の活動です。
関連: 標的型攻撃

### コンピュータ不正アクセス届出制度
試験: ITPassport
要約: 不正アクセスの被害を、IPA に届け出る制度です。
被害を受けた人が、IPA に届け出ます。被害の状況の把握と、対策に役立てられます。
例: 不正アクセスを受けた組織が、IPA に届け出る。
注意: ウイルスは、別のコンピュータウイルス届出制度で届け出ます。
関連: コンピュータウイルス届出制度

### コンピュータウイルス届出制度
試験: ITPassport
要約: ウイルスの発見や被害を、IPA に届け出る制度です。
ウイルスを発見した人や、被害を受けた人が、IPA に届け出ます。
例: ウイルスを発見した企業が、IPA に届け出る。
注意: 不正アクセスは、コンピュータ不正アクセス届出制度で届け出ます。
関連: コンピュータ不正アクセス届出制度

### コンピュータウイルス対策基準
試験: ITPassport
要約: 組織が取り組むウイルスの対策を、経済産業省が示した基準です。
ウイルスの感染を防ぎ、被害を抑えるための対策を、示しています。
例: ウイルス対策ソフトの導入と、定義ファイルの更新。
注意: 不正アクセスについての基準は、コンピュータ不正アクセス対策基準です。
関連: コンピュータ不正アクセス対策基準

### コンピュータ不正アクセス対策基準
試験: ITPassport
要約: 組織が取り組む不正アクセスの対策を、経済産業省が示した基準です。
不正アクセスを防ぎ、被害を抑えるための対策を、示しています。
例: アクセス権の管理と、ログの確認。
注意: ウイルスについての基準は、コンピュータウイルス対策基準です。
関連: コンピュータウイルス対策基準

### ISMAP
試験: ITPassport
要約: 政府が使うクラウドサービスを、あらかじめ評価して登録する制度です。
政府情報システムのためのセキュリティ評価制度で、政府機関などが、評価済みのクラウドサービスから選べるようにします。
例: 政府機関が、登録されたクラウドサービスを選ぶ。
注意: 政府のための制度で、一般の企業の認証ではありません。
関連: 責任共有モデル

### SECURITY ACTION
試験: ITPassport
要約: 中小企業が、情報セキュリティ対策に取り組むことを、自ら宣言する制度です。
IPA の制度で、取り組みの段階に応じて、宣言します。
例: 中小企業が、自社の取り組みを宣言し、ロゴマークを使う。
注意: 第三者が審査する認証ではなく、自ら宣言する制度です。
関連: 中小企業の情報セキュリティ対策ガイドライン

### サイバーセキュリティ経営ガイドライン
試験: ITPassport
要約: 経営者が認識すべき原則と、実施すべき指示事項を示した指針です。
経済産業省と IPA が示しています。経営者が、リーダーシップをとって対策を進めるための指針です。
例: 経営者が、対策の方針を決めて、担当者に指示する。
注意: 中小企業の担当者向けの手引きは、中小企業の情報セキュリティ対策ガイドラインです。
関連: 中小企業の情報セキュリティ対策ガイドライン

### 中小企業の情報セキュリティ対策ガイドライン
試験: ITPassport
要約: 中小企業が、対策に取り組むための、IPA の指針です。
中小企業の経営者や担当者が、情報セキュリティ対策を進めるための手引きです。
例: 自社の状況に合わせて、対策を選ぶ。
注意: 経営者向けの原則を示す、サイバーセキュリティ経営ガイドラインとは別のものです。
関連: SECURITY ACTION、サイバーセキュリティ経営ガイドライン

### PCI DSS
試験: ITPassport
要約: クレジットカードの会員情報を扱う事業者が守る、国際的なセキュリティ基準です。
カード業界が定めた基準です。カード番号などを扱う事業者が守ります。
例: カード番号を暗号化して保存する。
注意: 法律ではなく、カード業界の基準です。
関連: 暗号化

### CRYPTREC
試験: FE
要約: 電子政府で使う暗号の安全性を評価し、推奨する暗号のリストを作る取組みです。
暗号の安全性を評価、監視します。推奨される暗号のリストを作ります。
例: 電子政府推奨暗号リスト。
注意: 暗号の規格そのものではなく、評価と推奨を行う取組みです。
関連: 暗号化

### ISMS
別名: 情報セキュリティマネジメントシステム
試験: FE
要約: 組織が情報セキュリティを管理して、継続的に改善する仕組みです。
適用範囲を決め、リスクアセスメントに基づいて管理策を選んで運用し、継続的に改善します(PDCA の考え方)。第三者が審査して基準に合えば、ISMS 認証を与える制度が、ISMS 適合性評価制度です。
例: 組織が ISMS 認証を取得する。
注意: ISMS 認証は、個人ではなく、組織の仕組みに対する認証です。
関連: JIS Q 27001、JIS Q 27002

### JIS Q 27001
別名: ISO/IEC 27001
試験: FE
要約: ISMS の要求事項を定めた規格です。
組織が ISMS を作り、運用し、改善するために満たす要求事項を定めます。認証の審査の基準になります。
例: 組織が ISMS 認証を受ける、審査の基準にする。
注意: 管理策の実践の指針を示すのは、JIS Q 27002 です。
関連: ISMS、JIS Q 27002

### JIS Q 27002
別名: ISO/IEC 27002
試験: FE
要約: ISMS の管理策の実践の指針を示した規格です。
管理策の内容と、実践の方法を示します。ISO/IEC 27002:2022(JIS Q 27002:2024)では、管理策を、組織的、人的、物理的、技術的の 4 つに分けています。
例: 管理策を選ぶときの、参考にする。
注意: 認証の要求事項を定めた規格は、JIS Q 27001 です。
関連: ISMS、JIS Q 27001

### 組織的管理策
試験: FE
要約: 規程、役割、手順、供給者との関係などの管理策です。
情報セキュリティの管理策の 4 分類の一つです。ポリシー、アクセス制御の方針、供給者の管理、事故の報告手順などが含まれます。
例: 情報セキュリティポリシーの策定。
注意: 人に関する教育は人的管理策、建物の保護は物理的管理策です。
関連: 人的管理策、物理的管理策、技術的管理策

### 人的管理策
試験: FE
要約: 人に関する決まりと教育の管理策です。
情報セキュリティの管理策の 4 分類の一つです。意識向上、教育、訓練、秘密保持の契約、リモートワークの規則などが含まれます。
例: 入社時のセキュリティ研修。
注意: システムの機能で守る対策は、技術的管理策です。
関連: 組織的管理策、技術的管理策

### 物理的管理策
試験: FE
要約: 建物、部屋、機器を守る管理策です。
情報セキュリティの管理策の 4 分類の一つです。入退管理、施錠、監視カメラ、装置の処分などが含まれます。
例: サーバー室の入退管理。
注意: 暗号化やアクセス制限は、技術的管理策です。
関連: 組織的管理策、技術的管理策

### 技術的管理策
試験: FE
要約: システムの機能で守る管理策です。
情報セキュリティの管理策の 4 分類の一つです。情報へのアクセス制限、認証、暗号化、ログ、マルウェア対策、データマスキングなどが含まれます。
例: ストレージの暗号化。
注意: 入退管理などは、物理的管理策です。
関連: 組織的管理策、物理的管理策

### 内部不正防止ガイドライン
別名: 組織における内部不正防止ガイドライン
試験: FE
要約: 内部不正を防ぐための対策を、IPA が示した指針です。
内部不正の機会を減らす(権限の最小化、操作の記録と監視)、不正が見つかる状況をつくる、などを示します。
例: 操作のログを記録して、監視する。
注意: 技術の対策だけでなく、組織の運用や教育も含まれます。
関連: 内部不正

### 標的型メール訓練
試験: FE
要約: 標的型攻撃のメールを想定して、従業員に行う訓練です。
模擬のメールを送り、開いた人や報告した人を確かめます。繰り返し行って、意識を保ちます。
例: 模擬の不審なメールを送り、報告する手順を確認する。
注意: 開いた人を責めるのではなく、報告の習慣をつけるのが目的です。
関連: 標的型攻撃

### インシデントハンドリング
別名: インシデント対応
試験: FE
要約: インシデントが起きたときの、検知から復旧、振り返りまでの対応です。
一般に、検知と報告、トリアージ、封じ込め、根絶、復旧、事後の振り返りの順に進めます。
例: 感染した端末を、ネットワークから切り離して、被害の拡大を止める。
注意: 勝手に電源を切ったり再起動したりすると、調査に必要な情報が消えることがあります。
関連: トリアージ、CSIRT

### トリアージ
試験: FE
要約: 影響と緊急度から、対応の優先順位を決めることです。
インシデントが複数あるとき、影響と緊急度で順位を付けます。限られた人手で、重要なものから対応するためです。
例: 重要なシステムに関わる報告を、先に対応する。
注意: 優先順位を決める作業で、封じ込めや復旧そのものではありません。
関連: インシデントハンドリング

## 安全なシステムの作り方

### AI for Security
別名: AI を使ったセキュリティ技術
試験: FE
要約: AI を、セキュリティの対策に使うことです。
大量のログから、機械学習で、普段と異なる振る舞いを検出するなどに使います。
例: ログの異常を、AI で検知する。
注意: AI を守る Security for AI とは、向きが逆です。
関連: Security for AI

### Security for AI
別名: AI システムを守るための対策
試験: FE
要約: AI のシステム自体を、守る対策です。
プロンプトインジェクション対策、RAG のデータへのアクセス制御、学習データの出どころの確認などがあります。
例: AI に入力された指示の検証を行う。
注意: AI を対策に使う AI for Security とは、向きが逆です。
関連: AI for Security、プロンプトインジェクション、データポイズニング

### セキュアプログラミング
別名: セキュアコーディング
試験: FE
要約: 脆弱性を作らないように、安全なコードを書くことです。
設計と実装で、脆弱性を作り込まないようにします。指針に、IPA の「安全なウェブサイトの作り方」があります。
例: SQL 文に、プレースホルダを使う。
注意: 後から対策を足すのではなく、書く段階から気を付けます。
関連: プレースホルダ、出力時のエスケープ

### 安全なウェブサイトの作り方
試験: FE
要約: Web サイトの脆弱性を防ぐ対策を、IPA がまとめた資料です。
脆弱性の種類ごとに、根本的な解決策と、保険的な対策を示しています。
例: SQL インジェクションに、プレースホルダを使う。
注意: 根本的な解決と、保険的な対策の、両方を示しています。
関連: セキュアプログラミング

### プレースホルダ
別名: バインド変数
試験: FE
要約: SQL 文の構造と値を分けて、データベースに渡す仕組みです。
SQL 文に、値の場所だけを作り、値は後から渡します。入力値が SQL 文として扱われません。
例: `WHERE name = ?` の `?` に、入力値を渡す。
注意: 入力値を文字列として連結する方法では、SQL インジェクションが起きます。
関連: SQL インジェクション

### 出力時のエスケープ
別名: エスケープ処理
試験: FE
要約: 出力するときに、特別な意味の文字を、別の表記に置き換える対策です。
`<`、`>`、`&`、`"` などを、文字参照に置き換えて、スクリプトとして実行されないようにします。出力する場所に合った方法を使います。
例: `<` を `&lt;` に置き換えて表示する。
注意: 入力時の確認だけでなく、出力するときの置き換えが、XSS の根本的な対策です。
関連: セキュアプログラミング

### CORS
別名: オリジン間リソース共有、Cross-Origin Resource Sharing
試験: FE
要約: 別のオリジンのリソースを、スクリプトから読むことを許可する仕組みです。
サーバーが `Access-Control-Allow-Origin` ヘッダーで、読み取りを許すオリジンを指定します。
例: 別のドメインの画面から、API を呼べるようにする。
注意: `*` で、すべてのオリジンを許可する設定は、安易に使いません。
関連: セキュリティヘッダー

### クラウドの設定不備
試験: FE
要約: 公開設定や権限設定の誤りが、情報漏えいの原因になることです。
クラウドの公開設定や権限設定の誤りで、データが誰でも見られる状態になります。既定で非公開にし、最小限の権限にして、定期的に点検します。
例: 誤って、ストレージを公開設定にする。
注意: 責任共有モデルでは、設定は利用者の責任です。
関連: 責任共有モデル、最小権限の原則

### 耐タンパ性
試験: FE
要約: 物理的な解析や改ざんに、耐える性質です。
機器の中身を調べられたり、書き換えられたりしにくくします。暗号鍵を守るチップなどに、備わっています。
例: 内部を開けると、データが消える仕組み。
注意: ソフトウェアではなく、機器の物理的な性質についての言葉です。
関連: サイドチャネル攻撃、鍵管理

### ファームウェアのセキュアアップデート
試験: FE
要約: 署名を検証して、改ざんされた更新を適用しない、更新の仕組みです。
IoT 機器などで、更新の仕組みを備えます。更新のファイルの署名を検証して、改ざんされたものを適用しません。
例: 署名を確かめてから、機器のファームウェアを更新する。
注意: 更新の仕組みがない機器は、脆弱性を直せません。
関連: 電子署名、パッチ

## 端末とネットワークの対策

### マルウェア対策ソフト
別名: ウイルス対策ソフト、アンチウイルスソフト
試験: ITPassport
要約: マルウェアを検出して、駆除するソフトウェアです。
定義ファイル(パターンファイル)を常に最新に更新して、新しいマルウェアに備えます。
例: 端末にインストールして、定期的にスキャンする。
注意: 定義ファイルが古いと、新しいマルウェアを見逃します。
関連: パターンファイル、マルウェア

### パターンファイル
別名: 定義ファイル、シグネチャファイル
試験: ITPassport、FE
要約: 既知のマルウェアの特徴を記録したファイルです。
マルウェア対策ソフトが、この特徴と照らし合わせて検出します。新しいマルウェアが次々に出るため、常に最新に更新します。
例: ベンダーから配布される、定義ファイルを更新する。
注意: 未知のマルウェアは、パターンファイルにないので見つけにくくなります。
関連: パターンマッチング法、マルウェア対策ソフト

### パターンマッチング法
試験: ITPassport
要約: 既知のマルウェアのパターンと、ファイルを照らし合わせて検出する方法です。
既知のものは確実に検出できますが、未知のものは見つけられません。
例: ファイルの特徴を、パターンファイルと比べる。
注意: 未知のマルウェアも見つけられる可能性があるのは、ふるまい検知やヒューリスティック法です。
関連: パターンファイル、ふるまい検知、ヒューリスティック法

### ふるまい検知
別名: ビヘイビア法、ビヘイビア法(振る舞い検知)、振る舞い検知
試験: ITPassport、FE
要約: プログラムの動きを見て、怪しい動作を検知する方法です。
実行したときの動作を監視して、不審な動作を検出します。未知のマルウェアも、見つけられる可能性があります。
例: 大量のファイルを暗号化する動作を、検知する。
注意: 誤って、正常な動作を検知することもあります。
関連: パターンマッチング法、ヒューリスティック法、EDR

### ヒューリスティック法
試験: ITPassport、FE
要約: プログラムの構造や命令の特徴から、マルウェアらしさを推測する方法です。
パターンファイルにない未知のマルウェアも見つけられる可能性があります。誤検知もあります。
例: 不審な命令を含むプログラムを、マルウェアらしいと判定する。
注意: 実行したときの動作を見るふるまい検知とは、調べる対象が違います。
関連: パターンマッチング法、ふるまい検知

### EDR
別名: Endpoint Detection and Response
試験: ITPassport、FE
要約: 端末の動きを監視して、脅威の検知と対応を行う仕組みです。
パソコンやサーバーなどの端末の挙動を監視して、不審な動きを検知します。調査と、隔離などの対応を支援します。
例: 不審な動きをした端末を、ネットワークから隔離する。
注意: 既知のマルウェアを検出するマルウェア対策ソフトに対し、EDR は不審な動きの検知と対応が中心です。
関連: マルウェア対策ソフト、ふるまい検知

### SIEM
別名: Security Information and Event Management
試験: FE
要約: 多くの機器のログを集めて、相関を分析し、異常の兆候を検知する仕組みです。
複数の機器のログを、突き合わせて分析します。単独のログでは分からない、不審な動きを見つけます。
例: 認証ログと通信ログを突き合わせて、不審なログインを検知する。
注意: ログの取得だけでなく、集めて相関を分析し、通知するのが特徴です。
関連: 監査ログ、SOC

### DLP
別名: Data Loss Prevention
試験: FE
要約: 重要な情報が外部へ持ち出されるのを、検知して防ぐ仕組みです。
メールやファイルの持ち出しを監視します。情報漏えいを防ぎます。
例: 機密のファイルを、メールで社外へ送ろうとすると、止める。
注意: 外部からの侵入を防ぐ仕組みではなく、内部から外への持ち出しを防ぐ仕組みです。
関連: 情報漏えい、内部不正

### MDM
別名: Mobile Device Management、モバイルデバイス管理
試験: FE
要約: 端末を一元的に管理する仕組みです。
設定の強制や、遠隔でのロックと消去(リモートワイプ)ができます。紛失したときの情報漏えいを防ぎます。
例: 紛失したスマートフォンを、遠隔でロックする。
注意: 端末の管理の仕組みで、ネットワークに接続する端末の状態を検査する検疫ネットワークとは別のものです。
関連: 検疫ネットワーク

### セキュアOS
別名: セキュア OS
試験: FE
要約: 強制アクセス制御などで、root でも権限を細かく制限できる OS です。
管理者の権限を持っていても、できる操作を制限できます。
例: 特権を持つユーザーでも、決められた操作だけを許す。
注意: Web サーバーを root でなく一般ユーザーで動かす最小特権とは、別の仕組みです。
関連: 強制アクセス制御、最小権限の原則

### 検疫ネットワーク
試験: FE
要約: 接続する端末の状態を検査し、基準に合わない端末を、隔離する仕組みです。
パッチの適用やウイルス対策の状況を、検査します。基準に合わない端末は、隔離したネットワークにつなぎます。
例: 持ち込んだパソコンを、検査が済むまで隔離したネットワークにつなぐ。
注意: MAC アドレスフィルタリングは登録した端末だけを通し、端末の状態は検査しません。
関連: MAC アドレスフィルタリング、MDM

### MAC アドレスフィルタリング
別名: MACアドレスフィルタリング
試験: FE
要約: 登録した MAC アドレスの端末だけを、接続させる方法です。
無線 LAN などで使います。MAC アドレスは偽装できるので、これだけでは十分ではありません。
例: 登録した端末だけが、無線 LAN につながる。
注意: 端末の状態は検査しません。検査するのは検疫ネットワークです。
関連: 検疫ネットワーク

### CAPTCHA
試験: FE
要約: 人間かどうかを、文字の読み取りや画像の選択で判別する仕組みです。
自動のプログラム(ボット)による、不正な操作を防ぎます。
例: ゆがんだ文字を読み取って、入力する。
注意: 人間の入力と、ボットを区別するための仕組みで、本人確認の認証ではありません。
関連: ボット

### 許可リスト
別名: アローリスト、パスリスト、ホワイトリスト
試験: FE
要約: 許可したものだけを通す方式です。
許可した通信や相手だけを通し、それ以外は拒否します。
例: 許可した IP アドレスからの通信だけを通す。
注意: 禁止するものだけを遮断する方式は、拒否リストです。
関連: 拒否リスト

### 拒否リスト
別名: ブロックリスト、ブラックリスト
試験: FE
要約: 禁止するものだけを遮断する方式です。
禁止した通信や相手だけを遮断し、それ以外は通します。
例: 危険な IP アドレスからの通信を遮断する。
注意: 許可したものだけを通す方式は、許可リストです。載っていない危険なものは通ってしまいます。
関連: 許可リスト

### URL フィルタリング
別名: Web フィルタリング、URLフィルタリング
試験: ITPassport
要約: 閲覧するサイトの URL をもとに、閲覧を制限する仕組みです。
危険なサイトや、業務に関係のないサイトを防ぎます。
例: マルウェアが置かれているサイトに、接続できないようにする。
注意: 通信の中身ではなく、閲覧先の URL をもとに制限します。
関連: ファイアウォール

### OP25B
別名: Outbound Port 25 Blocking
試験: FE
要約: ISP が、25 番ポートの外向きの通信を制限して、迷惑メールを防ぐ対策です。
自社のメールサーバーを経由しない、25 番ポートの外向きの通信を制限します。利用者は、サブミッションポート(587 番)で SMTP-AUTH を使います。
例: 自宅のパソコンから、直接外部のメールサーバーへ送れなくなる。
注意: 利用者がメールを送れなくなるわけではなく、認証付きのポートを使います。
関連: SMTP 認証、迷惑メール

### 脆弱性管理
試験: ITPassport、FE
要約: 脆弱性の情報を集めて、修正プログラムを適用する一連の活動です。
機器とソフトの一覧を持ち、脆弱性の情報を集めて、自社への影響を評価します。検証してから、修正プログラム(パッチ)を適用します。サポートが終わった製品は使いません。
例: 検証用の環境で動作を確認してから、パッチを本番に適用する。
注意: 適用しないまま放置すると、攻撃を受ける危険が続きます。
関連: 脆弱性、パッチ、CVSS

### 脆弱性診断
別名: 脆弱性検査
試験: ITPassport、FE
要約: ツールなどで、システムに脆弱性が残っていないかを調べることです。
専用のツールや、専門家の手作業で、システムに既知の脆弱性が残っていないかを調べます。
例: Web アプリケーションを、診断ツールで調べる。
注意: 攻撃者の立場で侵入を試すのは、ペネトレーションテストです。
関連: ペネトレーションテスト、脆弱性スキャン

### ペネトレーションテスト
試験: FE
要約: 攻撃者の立場で、実際に侵入を試すテストです。
許可を得て、攻撃者と同じ方法で、侵入できるかを試します。
例: 外部から、侵入できるかを試す。
注意: ツールで脆弱性を探す脆弱性診断とは、方法が違います。
関連: 脆弱性診断、エシカルハッカー

## バックアップと事業継続

### バックアップ分離
別名: バックアップの分離
試験: ITPassport、FE
要約: バックアップを、本番から分離して持つ、ランサムウェアへの備えです。
ネットワークから切り離した場所に保管します。つながっていると、本番と一緒に暗号化されるおそれがあるためです。書き換えも削除もできないようにしたものが、イミュータブルバックアップです。
例: オフラインの媒体に、バックアップを保管する。
注意: バックアップを取るだけでなく、取れているものを戻せることの確認(復元テスト)も必要です。
関連: 復元テスト、バックアップ

### 復元テスト
試験: FE
要約: バックアップから、実際に戻せることを確かめるテストです。
定期的に行います。取れているのに戻せないバックアップは、意味がありません。
例: 検証用の環境に、バックアップから復元して、データを確認する。
注意: バックアップの取得に成功しても、復元できるとは限りません。
関連: バックアップ分離、バックアップ

### 3-2-1 ルール
別名: 3-2-1 バックアップルール
試験: FE
要約: コピーを 3 つ、2 種類の媒体に、1 つは遠隔地に置く考え方です。
元のデータとバックアップ 2 つで、コピーが 3 つです。ディスクとテープなど、2 種類の媒体に保存します。1 つは遠隔地に置いて、建物ごとの災害に備えます。
例: 本番のディスクと、別のディスク、遠隔地のテープに保存する。
注意: 3 つのコピーは、元のデータを含めた数です。
関連: バックアップ、バックアップ分離

### ホットサイト
試験: FE
要約: 本番と同等の設備を動かし、データも同期する、代替サイトです。
災害時にすぐ再開できますが、費用が高くなります。
例: 別の拠点で、同じシステムを常に動かしておく。
注意: 場所と最低限の設備だけを用意する、コールドサイトより、早く再開できますが、費用は高くなります。
関連: コールドサイト

### コールドサイト
試験: FE
要約: 場所と最低限の設備だけを用意する、代替サイトです。
機器とデータは、災害の後に用意します。費用は安いですが、再開までの時間が長くなります。
例: 災害時に、機器を運び込んで、再開する。
注意: ホットサイトより、費用は安く、再開は遅くなります。
関連: ホットサイト

## 物理的セキュリティ

### セキュリティゾーニング
試験: FE
要約: 区画を重要度で分け、区域ごとに入れる人を分ける考え方です。
受付、執務室、サーバー室のように分け、重要な区画ほど、入退室の管理を厳しくします。
例: サーバー室には、登録された社員だけが入れる。
注意: ネットワークを区画に分ける考え方にも、似た言葉が使われますが、ここでは建物や部屋の区画のことです。
関連: 物理的セキュリティ境界、入退管理システム

### 物理的セキュリティ境界
試験: FE
要約: 守る領域を、壁や扉で区切った線です。
境界の内側に入れる人を限ります。境界ごとに、入退室を管理します。
例: サーバー室の壁と扉。
注意: ネットワークの境界ではなく、建物や部屋の物理的な境界です。
関連: セキュリティゾーニング

### 入退管理システム
別名: 入退管理
試験: FE
要約: IC カードや生体認証で、入退室を制御し、記録する仕組みです。
許された人だけが入れるようにして、入退室の記録を残します。
例: IC カードで、サーバー室に入る。
注意: カードの貸し借りや共連れは、規程の違反になります。
関連: アンチパスバック、IC カード

### アンチパスバック
試験: FE
要約: 入室の記録がないカードでの退室や、退室していないカードでの再入室を、拒否する仕組みです。
共連れや、中から別の人にカードを渡す行為を、見つけやすくします。
例: 入室の記録がないカードで、退室しようとすると、拒否される。
注意: 認証した人に続いて入る、共連れ自体を防ぐわけではなく、記録の矛盾から見つけやすくします。
関連: 入退管理システム、セキュリティゾーニング

### クリアデスク・クリアスクリーン
別名: クリアデスク、クリアスクリーン
試験: FE
要約: 離席するときに、机の上に書類や媒体を置かず、画面もロックすることです。
書類や媒体を片付けるのがクリアデスク、画面をロックするのがクリアスクリーンです。
例: 離席するときに、書類を引き出しにしまい、画面をロックする。
注意: 机の上だけでなく、画面のロックも含みます。
関連: 物理的管理策

### データの確実な消去
試験: FE
要約: 廃棄や再利用の前に、データを復元できないように消すことです。
ファイルの削除や OS の再インストールでは、データの本体が残ることがあります。専用のツールで消去するか、物理的に破壊し、証明書を受け取ります。
例: HDD は上書きで消去し、SSD は消去機能か物理的な破壊を使う。
注意: SSD は、上書きしても消えない領域があるので、HDD と同じ方法では不十分です。
関連: 物理的管理策
