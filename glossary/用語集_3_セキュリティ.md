# 用語集 セキュリティ

## 認証と認可

### 認証
別名: Authentication
要約: 相手が本人かどうかを確かめることです。
「あなたは誰か」を確かめることです。パスワード、鍵、証明書、多要素認証などで確かめます。認証の後に、何をしてよいかを決めるのが認可です。
例: パスワード、SSH の鍵、クライアント証明書、MFA
注意: 認証(誰か)と認可(何をしてよいか)は別のものです。HTTP の 401 は認証、403 は認可の失敗です。
関連: 認可、多要素認証

### 認可
別名: Authorization
要約: 認証した相手に、何をしてよいかを決めることです。
認証で分かった相手に、「何をしてよいか」を決めることです。AWS の IAM ポリシーや、Kubernetes の RBAC が認可の仕組みです。
例: IAM ポリシー、Kubernetes の RBAC、Linux のパーミッション
注意: 認証が通っても、認可されていない操作は拒否されます。
関連: 認証、最小権限の原則、RBAC

### 多要素認証
別名: MFA、二要素認証
要約: 知っているもの、持っているもの、本人の特徴のうち、2 つ以上を組み合わせる認証です。
知っているもの(パスワード)、持っているもの(スマートフォン、鍵の装置)、本人の特徴(指紋)のうち、2 つ以上を組み合わせて認証することです。パスワードが漏れても、乗っ取られにくくなります。
例: パスワード + スマートフォンのワンタイムパスワード、パスキー
注意: パスワードを 2 回聞くのは、同じ種類の要素なので多要素認証ではありません。
関連: 認証

### 最小権限の原則
別名: 最小特権
要約: 仕事に必要な最小の権限だけを与える考え方です。
仕事に必要な最小限の権限だけを与える、という考え方です。乗っ取られたり誤って操作したりしたときの被害を小さくできます。
例: 読むだけの人には読み取りの権限だけ、`automountServiceAccountToken: false`
注意: 権限を広く与えると、乗っ取られたときや誤操作のときの被害が大きくなります。
関連: 認可、IAM ポリシー

### トークン
別名: アクセストークン
要約: 認証の後に渡される、一時的な通行証です。
認証が済んだことを表す、一時的な文字列です。パスワードの代わりに API を呼ぶときに使います。漏れると、持ち主のふりをされます。
例: OAuth のアクセストークン、JWT、AWS STS の一時的な認証情報
注意: トークンもパスワードと同じく秘密情報で、ログや URL に出してはいけません。
関連: 認証、秘密情報

### PAM
別名: Pluggable Authentication Modules
試験: LinuC202
要約: 認証の仕組みを部品(モジュール)に分け、組み合わせを選べるようにした仕組みです。
設定は `/etc/pam.d/` のプログラムごとのファイルに、「タイプ、制御フラグ、モジュール、引数」の形で書きます。ログインや ssh、sudo が、認証をこの仕組みに任せます。
例: `auth required pam_unix.so`、`session required pam_limits.so`
注意: 制御フラグは書く順番に意味があります。`requisite` は失敗で即終了、`sufficient` は成功で即終了です。
関連: 認証、SSSD

### SSSD
別名: System Security Services Daemon
試験: LinuC202
要約: LDAP などの認証の情報を取りに行き、手元に覚えておくデーモンです。
設定は `/etc/sssd/sssd.conf` に書きます。NSS(`sss`)と PAM(`pam_sss`)の両方を通して使います。サーバーにつながらなくても、覚えた情報でログインできます。
例: `systemctl enable --now sssd`、`getent passwd taro`
注意: `sssd.conf` の権限は `0600` にします。ゆるいと sssd は起動しません。
関連: PAM、LDAP、NSS

### NSS
別名: Name Service Switch、nsswitch.conf
試験: LinuC202
要約: ユーザー、グループ、ホスト名などの情報を、どこから調べるかを決める仕組みです。
設定は `/etc/nsswitch.conf` です。`passwd: files sss` のように、調べる場所を左から順に並べます。`files` はローカルのファイル、`sss` は SSSD です。
例: `passwd: files sss`、`hosts: files dns`、`getent passwd`
注意: NSS は「そのユーザーがいるか」を決め、PAM は「認証してよいか」を決めます。役割が違います。
関連: PAM、SSSD

### Basic 認証
別名: HTTP Basic 認証
試験: LinuC202
要約: ブラウザーが利用者名とパスワードを聞く、簡単な HTTP の認証です。
Apache では `mod_auth_basic` と `htpasswd` で作ったパスワードのファイルを使います。パスワードは暗号化されず、base64 で符号化されるだけで送られます。
例: `htpasswd -c /etc/httpd/.htpasswd alice`、`AuthType Basic`、`AuthUserFile /etc/httpd/.htpasswd`
注意: 必ず HTTPS と組み合わせます。HTTP のままでは、通信を見られるとパスワードが分かります。
関連: HTTP、TLS

### SMTP 認証
別名: SASL、SMTP AUTH
試験: LinuC202
要約: メールを送るときに、ユーザー名とパスワードで利用者を確かめる仕組みです。
メールを送るときに、ユーザー名とパスワードで利用者を確かめる仕組みです。認証の部品を SASL と呼びます。Postfix は、認証を Dovecot に任せる設定がよく使われます。
例: Postfix の `smtpd_sasl_auth_enable = yes`、`smtpd_sasl_type = dovecot`
注意: パスワードが平文で流れないように、STARTTLS で暗号化してから認証させます。
関連: STARTTLS、オープンリレー、Dovecot

### ホスト鍵
別名: SSH ホスト鍵
試験: LinuC202
要約: SSH のサーバーが、自分が本物だと示すための鍵の組です。
`/etc/ssh/ssh_host_*_key`(秘密鍵)と `.pub`(公開鍵)です。クライアントは `known_hosts` に記録し、次からは同じ鍵かを比べます。
例: `/etc/ssh/ssh_host_ed25519_key`、`ssh-keygen -A`
注意: ホスト鍵が変わると、クライアントに警告が出ます。サーバーの複製のあとは、ホスト鍵を作り直します。
関連: SSH、公開鍵暗号

### authorized_keys
試験: LinuC202
要約: SSH の公開鍵認証で、ログインを許す公開鍵を並べるファイルです。
サーバー側のユーザーの `~/.ssh/authorized_keys` に、公開鍵を 1 行ずつ書きます。クライアントは、対応する秘密鍵で認証します。
例: `ssh-copy-id alice@server1`、`~/.ssh/authorized_keys`
注意: ホームや `~/.ssh` や、このファイルが他人に書き込める状態だと、認証に失敗します。
関連: SSH、公開鍵暗号

## 暗号と証明書

### 暗号化
要約: データを、鍵がないと読めない形に変えることです。
データを、鍵がないと読めない形に変えることです。通信の途中を守るもの(転送中の暗号化、TLS)と、保存したデータを守るもの(保存時の暗号化、KMS など)があります。
例: 保存時の暗号化(EBS、S3 の SSE)、転送時の暗号化(TLS)
注意: 暗号化しても、鍵の管理が甘ければ守れません。
関連: 共通鍵暗号、公開鍵暗号、TLS

### 共通鍵暗号
別名: 対称鍵暗号
要約: 暗号化と復号に同じ鍵を使う方式です。
暗号化と復号に同じ鍵を使う方式です。速いので大量のデータに向きますが、鍵を安全に渡す方法が問題になります。AES が代表です。
例: AES
注意: 速いですが、鍵を相手に安全に渡す方法が問題になります。
関連: 公開鍵暗号、暗号化

### 公開鍵暗号
別名: 非対称鍵暗号、公開鍵、秘密鍵
要約: 公開鍵と秘密鍵の組を使う暗号の方式です。
公開してよい公開鍵と、本人だけが持つ秘密鍵の組を使う方式です。公開鍵で暗号化したものは秘密鍵でしか復号できません。SSH の鍵認証、TLS、電子署名で使います。秘密鍵は絶対に渡しません。
例: RSA、ECDSA、Ed25519、SSH の鍵の組
注意: 公開鍵で暗号化したものは秘密鍵でしか復号できません。秘密鍵は渡しません。
関連: 共通鍵暗号、電子署名、証明書

### ハッシュ
別名: ハッシュ値、ダイジェスト
要約: データから決まった長さの値を計算する、元に戻せない関数です。
データから計算する、決まった長さの値です。元のデータが少しでも変わると値が大きく変わり、値から元のデータには戻せません。改ざんの検出や、パスワードの保存に使います。SHA-256 が代表です。
例: `sha256sum file`、パスワードの保存、イメージのダイジェスト
注意: MD5 と SHA-1 は衝突が見つかっているので、安全が必要な用途には使いません。
関連: 電子署名

### 電子署名
別名: デジタル署名
要約: 秘密鍵で署名し、公開鍵で確かめて、作った人と改ざんのないことを示す仕組みです。
秘密鍵でデータのハッシュに署名し、公開鍵で確かめる仕組みです。作った人が本人であることと、途中で改ざんされていないことを確かめられます。
例: パッケージの GPG の署名、コンテナのイメージの Cosign の署名
注意: 署名は中身を隠しません。秘密を守るには暗号化が別に必要です。
関連: 公開鍵暗号、ハッシュ、イメージの署名

### 証明書
別名: サーバー証明書、デジタル証明書、X.509
要約: 公開鍵と持ち主を、認証局が保証した電子的な書類です。
公開鍵と、その持ち主の情報に、認証局(CA)が署名したものです。Web サイトが本物であることを確かめるのに使います。有効期限があり、切れると接続がエラーになります。
例: `openssl x509 -in cert.pem -noout -dates -subject`
注意: 期限切れは障害の原因として多いので、期限を監視して自動で更新します。
関連: 認証局、TLS、公開鍵暗号

### 認証局
別名: CA
要約: 証明書に署名して、持ち主を保証する組織や仕組みです。
証明書を発行し、署名する機関や仕組みです。ブラウザや OS は、信頼する認証局の一覧を持っています。Kubernetes のクラスタも、自分の CA を持ちます。
例: Let's Encrypt、AWS Certificate Manager、Kubernetes のクラスタの CA
注意: 自分で作った CA の証明書は、相手に信頼させる設定をしないとエラーになります。
関連: 証明書

### TLS
別名: SSL
要約: 通信を暗号化し、相手のサーバーが本物かを確かめる仕組みです。
通信を暗号化し、相手が本物かを証明書で確かめるプロトコルです。HTTPS は HTTP を TLS で守ったものです。SSL は古い名前で、今は TLS 1.2 か 1.3 を使います。
例: HTTPS、`curl -v https://example.com`、TLS 1.2 と 1.3
注意: SSL は古い名前で、SSL 3.0 や TLS 1.0、1.1 は使ってはいけません。
関連: 証明書、HTTP、暗号化

### 鍵のローテーション
別名: ローテーション
試験: SAA、K8s
要約: 鍵やパスワードを、決まった間隔で新しいものに替えることです。
暗号化の鍵やパスワードを、定期的に新しいものに入れ替えることです。漏れていても、使える期間を短くできます。
例: KMS の自動ローテーション、IAM のアクセスキーの更新
注意: 替えても古い鍵を使う場所が残っていると止まるので、切り替えの手順を決めておきます。
関連: 暗号化、秘密情報

### 秘密情報
別名: シークレット、機密情報
要約: パスワード、鍵、トークンのように、漏れると困る情報です。
パスワード、API のキー、トークン、秘密鍵のような、漏れると困る情報です。コードや Git、イメージに書かず、専用の保管庫(Secrets Manager、Vault など)に置きます。
例: AWS Secrets Manager、Kubernetes の Secret、`.env` を `.gitignore` に入れる
注意: Git の履歴に一度入ったら、消すだけでなく、その値を無効にして替えます。
関連: Secrets Manager、Secret

### TSIG
別名: Transaction SIGnature
試験: LinuC202
要約: 共有の秘密鍵で DNS のメッセージに署名し、相手を確かめる仕組みです。
2 つの DNS サーバーが同じ鍵を持ち、ゾーン転送、動的更新、通知のメッセージに署名します。鍵は `tsig-keygen` で作れます。
例: `key "transfer-key" { algorithm hmac-sha256; secret "…"; };`、`allow-transfer { key transfer-key; };`
注意: TSIG は署名だけで、内容は暗号化しません。応答の署名で改ざんを見つける DNSSEC とは別のものです。
関連: ゾーン転送、DNSSEC、ハッシュ

### DNSSEC
別名: DNSKEY、RRSIG、DS レコード
試験: LinuC202
要約: DNS の答えが改ざんされていないことを、電子署名で確かめる仕組みです。
ゾーンのレコードに署名(RRSIG)を付け、検証用の公開鍵(DNSKEY)を載せます。親のゾーンの DS レコードが、子の鍵を保証して、ルートからの信頼のつながりを作ります。
例: `dnssec-keygen`、`dnssec-signzone`、`dig +dnssec www.example.com`(`ad` のフラグ)
注意: 署名で改ざんを見つけるだけです。問い合わせの内容は暗号化されません。
関連: DNS、電子署名、公開鍵暗号、DANE

### DANE
別名: TLSA レコード
試験: LinuC202
要約: サーバーの証明書の情報を DNS に載せ、証明書を確かめられるようにする仕組みです。
証明書(または公開鍵)のハッシュを、TLSA レコードとして DNS に載せます。クライアントは、つながった相手の証明書が、この記録と合うかを確かめます。
例: `_443._tcp.www.example.com. IN TLSA 3 1 1 <ハッシュ>`
注意: DNSSEC で署名されていることが前提です。署名がないと、TLSA の答えが改ざんされるおそれがあります。
関連: DNSSEC、証明書、ハッシュ

### CSR(サーバー証明書の申請)
別名: Certificate Signing Request(Web サーバー)
試験: LinuC202
要約: 認証局にサーバー証明書の署名を頼む、申請の書類です。
サーバーの公開鍵と、名前(CN)や組織の情報が入っています。秘密鍵そのものは入っていません。秘密鍵から作り、CA に送ります。
例: `openssl req -new -key server.key -out server.csr`
注意: 秘密鍵は CA に渡しません。送るのは CSR だけです。
関連: 証明書、認証局

### 自己署名証明書
別名: オレオレ証明書、セルフサイン証明書
試験: LinuC202
要約: 認証局ではなく、自分の秘密鍵で署名した証明書です。
通信を暗号化できますが、信頼された CA の署名がないので、ブラウザーが警告を出します。検証や社内の試験に使います。
例: `openssl req -x509 -newkey rsa:2048 -nodes -keyout server.key -out server.crt -days 365`
注意: 公開するサイトには使いません。利用者に警告を無視する習慣が付きます。
関連: 証明書、認証局

### 中間 CA
別名: 中間認証局、中間証明書
試験: LinuC202
要約: ルート CA とサーバー証明書の間をつなぐ、認証局の証明書です。
サーバー証明書は、中間 CA が署名することが多いです。サーバーは、サーバー証明書の後ろに中間 CA の証明書を続けて送ります。
例: `SSLCertificateFile` のファイルに、サーバー証明書、中間 CA の証明書の順で書く
注意: 中間 CA の証明書を付け忘れると、一部のクライアントだけで、検証のエラーになります。
関連: 証明書、認証局

### OpenSSL
別名: openssl
試験: LinuC202
要約: 暗号と証明書を扱うライブラリとコマンドです。
鍵や CSR、自己署名証明書を作ったり、証明書の中身を見たり、サーバーの TLS 接続を確かめたりできます。
例: `openssl x509 -in server.crt -noout -dates`、`openssl s_client -connect example.com:443`
注意: サブコマンド(`req`、`x509`、`verify`、`s_client`)で動きが変わります。
関連: 証明書、TLS、CSR(サーバー証明書の申請)

### STARTTLS
試験: LinuC202
要約: 平文でつないだあとに、通信を TLS の暗号化に切り替える命令です。
平文でつないだあとに、通信を TLS の暗号化に切り替える命令です。SMTP、IMAP、POP3 で使います。
例: 587 番で `STARTTLS` を送ってから SMTP 認証をする
注意: 最初から TLS にする 465、993、995 番の方式とは違います。
関連: TLS、SMTP、SMTP 認証

## 脅威と対策

### 脆弱性
別名: CVE
要約: ソフトウェアや設定の、攻撃に使われうる弱点です。
ソフトウェアの、悪用できる欠陥です。見つかったものには CVE という番号が付きます。パッケージやイメージを更新して修正を取り込みます。
例: CVE の番号、CVSS の点数
注意: 脆弱性があっても、外から届かない、使っていない機能なら、危険の大きさは下がります。
関連: 脆弱性スキャン、パッチ

### 脆弱性スキャン
試験: Docker、SAA、K8s
要約: 既知の脆弱性がないかを、道具で調べることです。
ソフトウェアやイメージに、既知の脆弱性がないかを調べることです。コンテナのイメージは Trivy や Docker Scout、AWS では Amazon Inspector で調べます。
例: Trivy、Amazon Inspector、Docker Scout
注意: 新しい脆弱性は毎日見つかるので、作ったときだけでなく定期的に調べます。
関連: 脆弱性

### パッチ
要約: 不具合や脆弱性を直すための更新です。
ソフトウェアの欠陥や脆弱性を直すための更新です。適用を後回しにすると、攻撃される危険が増えます。
例: `dnf update --security`、OS とライブラリの更新
注意: 当てる前に検証の環境で試し、戻す方法を決めておきます。
関連: 脆弱性

### DDoS 攻撃
別名: DDoS
試験: SAA、CCNA
要約: 大量の通信を送り付けて、サービスを止める攻撃です。
多数の機器から大量の通信を送りつけて、サービスを使えなくする攻撃です。AWS では Shield や WAF、CloudFront で防ぎます。
例: AWS Shield、CloudFront、レート制限
注意: 自前のサーバーだけで受け止めるのは難しく、手前の CDN やサービスで吸収します。
関連: WAF

### WAF
別名: Web Application Firewall
試験: SAA
要約: Web アプリへの攻撃(SQL インジェクションなど)を、HTTP の中身を見て止める仕組みです。
Web アプリへの通信の中身を見て、SQL インジェクションのような攻撃や、同じ相手からの多すぎるリクエストを止める仕組みです。
例: AWS WAF を ALB や CloudFront に付ける
注意: WAF はアプリの脆弱性を直すものではなく、手前で防ぐ補助です。
関連: ファイアウォール、DDoS 攻撃

### SQL インジェクション
別名: XSS、クロスサイトスクリプティング
試験: SAA
要約: 入力に SQL を混ぜて、データベースを不正に操作する攻撃です。
入力の欄に、データベースの命令(SQL)を混ぜて、データを盗んだり壊したりする攻撃です。Web のページに悪いスクリプトを埋め込む攻撃は XSS です。WAF や、入力の正しい扱い方で防ぎます。
例: `' OR '1'='1`
注意: 文字列をつなげて SQL を作らず、プレースホルダー(バインド変数)を使って防ぎます。
関連: WAF

### 総当たり攻撃
別名: ブルートフォース攻撃、パスワードスプレー
要約: パスワードの候補を片っ端から試す攻撃です。
パスワードを片っ端から試す攻撃です。ログインの失敗の回数の制限、多要素認証、長いパスワードで防ぎます。
例: SSH への大量のログインの試み、`fail2ban`
注意: 鍵の認証にしてパスワードの認証を止める、試行の回数を制限する、MFA を使う、で防ぎます。
関連: 多要素認証、認証

### フィッシング
別名: ソーシャルエンジニアリング
要約: 本物に見せかけたメールやサイトで、パスワードなどをだまし取る攻撃です。
本物そっくりのメールや画面で、パスワードなどを入力させてだまし取る攻撃です。技術ではなく人の油断を突く攻撃をまとめて、ソーシャルエンジニアリングと呼びます。
例: 偽のログインの画面、偽の請求のメール
注意: パスキーや FIDO の鍵は、偽のサイトでは使えないので、フィッシングに強いです。
関連: 多要素認証

### マルウェア
別名: ランサムウェア
要約: 害を与えることを目的に作られたソフトウェアです。
悪意のあるソフトウェアの総称です。データを暗号化して身代金を求めるものをランサムウェアと呼びます。別の場所に、書き換えられないバックアップを持つと復旧できます。
例: ランサムウェア、トロイの木馬、ワーム
注意: ランサムウェアに備えて、書き換えられないバックアップ(別の場所、オフライン)を持ちます。
関連: バックアップ

### ゼロトラスト
要約: 社内のネットワークも信頼せず、通信のたびに確かめる考え方です。
社内のネットワークだからといって信用せず、すべてのアクセスを毎回確かめる、という考え方です。
例: 端末の状態の確認、利用者ごとの認証と認可、細かいアクセスの制御
注意: 「中は安全」という境界の守りだけに頼らない、という考え方です。
関連: 認証、最小権限の原則

### 監査ログ
要約: 誰が、いつ、何をしたかの記録です。
誰が、いつ、何をしたかの記録です。不正の調査や、規則を守っていることの証明に使います。AWS では CloudTrail、Kubernetes では API サーバーの監査ログがあります。
例: AWS CloudTrail、Linux の auditd、Kubernetes の監査ログ
注意: 記録を消されないように、別のアカウントや書き換えられない場所に送ります。
関連: CloudTrail

### オープンリレー
別名: 第三者中継
試験: LinuC202
要約: 誰からのメールでも中継してしまう、設定を誤ったメールサーバーです。
誰からのメールでも、自分宛てでないドメインへ中継してしまう、設定を誤ったメールサーバーです。迷惑メールの踏み台に使われます。
例: Postfix の `mynetworks` に `0.0.0.0/0` を書いてしまう
注意: 中継は、信頼するネットワークと、SMTP 認証に成功したユーザーに絞ります。
関連: MTA、SMTP 認証

### fail2ban
試験: LinuC202
要約: ログを見て、認証の失敗が続く接続元を、自動でブロックする道具です。
`findtime` の間に `maxretry` 回を超えた接続元を、ファイアウォールの規則で `bantime` の間ブロックします。SSH の総当たり攻撃への対策によく使います。
例: `fail2ban-client status sshd`、`/etc/fail2ban/jail.local`
注意: 設定は `jail.local` に書きます。`jail.conf` は更新で上書きされます。
関連: 総当たり攻撃、ファイアウォール

### IDS
別名: 侵入検知システム、Intrusion Detection System、snort
試験: LinuC202
要約: 不正なアクセスの兆候を見つけて、知らせる仕組みです。
ネットワークを流れるパケット(ネットワーク型。snort など)や、ホストのログとファイルの変化(ホスト型)を調べます。見つけて知らせるだけで、自分では止めません。
例: snort、OSSEC
注意: 止める機能まで持つものは IPS と呼びます。
関連: ファイアウォール、fail2ban

### OpenVAS
別名: Greenbone Vulnerability Management、GVM
試験: LinuC202
要約: ネットワークの上から、既知の脆弱性を調べる脆弱性スキャナーです。
ホストやサービスに、既知の脆弱性が残っていないかを検査し、報告書を作ります。
例: Greenbone の Web 画面、スキャンのタスク
注意: 検査は、自分が管理するホストだけを対象にします。
関連: 脆弱性スキャン、脆弱性

### OpenSCAP
別名: oscap、SCAP
試験: LinuC202
要約: ホストの設定が、決まったセキュリティ基準に合っているかを検査する道具です。
SCAP という仕組みの基準(プロファイル)に照らして、設定を検査し、報告書を作ります。基準は `scap-security-guide` のパッケージで入ります。
例: `oscap xccdf eval --profile <ID> --report report.html <データストリーム>`
注意: 既知の脆弱性を調べる OpenVAS とは目的が違います。OpenSCAP は設定の適合を調べます。
関連: 脆弱性スキャン、OpenVAS

### JPCERT/CC
別名: JVN、Japan Vulnerability Notes
試験: LinuC202
要約: 日本のセキュリティ事故の調整センターで、JVN で脆弱性の情報を発信します。
一般社団法人 JPCERT コーディネーションセンターです。注意喚起を出し、脆弱性の情報のポータル JVN を、IPA と運営します。
例: JVN の脆弱性の情報、注意喚起の一覧
注意: 米国の CERT/CC とは別の組織です。
関連: 脆弱性、パッチ

## OS の守り

### SELinux
別名: AppArmor
試験: LinuC102、Docker
要約: プロセスがアクセスできるものを、ラベルで強制的に制限する仕組みです。
Linux で、プロセスが触れるファイルや操作を、細かいルールで制限する仕組みです(強制アクセス制御)。root で動くプロセスでも制限できます。
例: `getenforce`、`ls -Z`、`restorecon -Rv /var/www`、`setsebool -P httpd_can_network_connect on`
注意: 困ったからといって無効にせず、ラベルや boolean を直します。
関連: root

### ケーパビリティ
別名: capabilities
試験: Docker、K8s
要約: root の権限を細かく分けたものです。
root の強い権限を、細かい単位(ネットワークの設定、低い番号のポートの使用など)に分けたものです。コンテナでは、すべて外して(`drop: ALL`)、必要なものだけを足すのが安全です。
例: `CAP_NET_BIND_SERVICE`(1024 未満のポート)、`docker run --cap-drop ALL --cap-add NET_BIND_SERVICE`
注意: `--privileged` はほぼすべてのケーパビリティを与えるので、原則として使いません。
関連: root、最小権限の原則

### chroot
試験: LinuC202
要約: プロセスから見えるルートディレクトリを、別の場所に替える仕組みです。
プロセスにとっての `/` を、指定したディレクトリに替えます。BIND などのサービスを、その中に閉じ込めると、乗っ取られても外のファイルに届きません。
例: `named -t /var/named/chroot -u named`、Red Hat 系の `named-chroot.service`
注意: chroot だけでは完全な隔離にならないので、root 以外のユーザーで動かす設定と合わせます。
関連: BIND

### root_squash
別名: all_squash、no_root_squash
試験: LinuC202
要約: NFS で、クライアントの root を匿名のユーザーに変えるオプションです。
NFS のサーバーで、クライアントの root(UID 0)を、匿名のユーザー(`nobody` など)に変えるオプションです。既定で有効です。すべてのユーザーを匿名にするのは `all_squash`、root をそのまま扱うのは `no_root_squash` です。
例: `/srv/share 192.168.1.0/24(rw,root_squash)`
注意: `no_root_squash` は、クライアントの root が、サーバーのファイルを自由に書き換えられるので、必要なときだけ使います。
関連: NFS

## 暗号と鍵

### Secure Boot
別名: セキュアブート
試験: LinuC3PS
要約: 署名が正しいプログラムだけを、起動のときに動かす仕組みです。
UEFI のファームウェアが、ブートローダーやカーネルの署名を、PK、KEK、db の信頼の鎖で確かめます。VM では OVMF のファームウェアで使えます。
例: `mokutil --sb-state`
注意: 署名のないカーネルモジュールは読み込めません。自分の鍵を MOK に登録します。
関連: UEFI、仮想 TPM

### 仮想 TPM
別名: swtpm、vTPM
試験: LinuC3PS
要約: ソフトウェアで作った、VM 用の TPM です。
TPM は、鍵の保管と起動の状態の記録をする部品です。仮想 TPM は、swtpm で作り、ホストに物理の TPM がなくても、VM に TPM 2.0 を見せられます。
例: `<tpm model='tpm-crb'><backend type='emulator' version='2.0'/></tpm>`
注意: 状態ファイルを失うと、TPM の中の鍵を失います。バックアップに含めます。
関連: Secure Boot、仮想マシン
