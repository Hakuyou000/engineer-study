# 用語集 セキュリティ

## 認証と認可

### 認証
別名: Authentication
要約: 相手が本人かどうかを確かめることです。
「あなたは誰か」を確かめることです。パスワード、鍵、証明書、多要素認証などで確かめます。認証の後に、何をしてよいかを決めるのが認可です。
例: パスワード、SSH の鍵、クライアント証明書、MFA
注意: 認証(誰か)と認可(何をしてよいか)は別のものです。HTTP の 401 は認証、403 は認可の失敗です。
関連: 認可、多要素認証

### 認可
別名: Authorization
要約: 認証した相手に、何をしてよいかを決めることです。
認証で分かった相手に、「何をしてよいか」を決めることです。AWS の IAM ポリシーや、Kubernetes の RBAC が認可の仕組みです。
例: IAM ポリシー、Kubernetes の RBAC、Linux のパーミッション
注意: 認証が通っても、認可されていない操作は拒否されます。
関連: 認証、最小権限の原則、RBAC

### 多要素認証
別名: MFA、二要素認証
要約: 知っているもの、持っているもの、本人の特徴のうち、2 つ以上を組み合わせる認証です。
知っているもの(パスワード)、持っているもの(スマートフォン、鍵の装置)、本人の特徴(指紋)のうち、2 つ以上を組み合わせて認証することです。パスワードが漏れても、乗っ取られにくくなります。
例: パスワード + スマートフォンのワンタイムパスワード、パスキー
注意: パスワードを 2 回聞くのは、同じ種類の要素なので多要素認証ではありません。
関連: 認証

### 最小権限の原則
別名: 最小特権
要約: 仕事に必要な最小の権限だけを与える考え方です。
仕事に必要な最小限の権限だけを与える、という考え方です。乗っ取られたり誤って操作したりしたときの被害を小さくできます。
例: 読むだけの人には読み取りの権限だけ、`automountServiceAccountToken: false`
注意: 権限を広く与えると、乗っ取られたときや誤操作のときの被害が大きくなります。
関連: 認可、IAM ポリシー

### トークン
別名: アクセストークン
要約: 認証の後に渡される、一時的な通行証です。
認証が済んだことを表す、一時的な文字列です。パスワードの代わりに API を呼ぶときに使います。漏れると、持ち主のふりをされます。
例: OAuth のアクセストークン、JWT、AWS STS の一時的な認証情報
注意: トークンもパスワードと同じく秘密情報で、ログや URL に出してはいけません。
関連: 認証、秘密情報

## 暗号と証明書

### 暗号化
要約: データを、鍵がないと読めない形に変えることです。
データを、鍵がないと読めない形に変えることです。通信の途中を守るもの(転送中の暗号化、TLS)と、保存したデータを守るもの(保存時の暗号化、KMS など)があります。
例: 保存時の暗号化(EBS、S3 の SSE)、転送時の暗号化(TLS)
注意: 暗号化しても、鍵の管理が甘ければ守れません。
関連: 共通鍵暗号、公開鍵暗号、TLS

### 共通鍵暗号
別名: 対称鍵暗号
要約: 暗号化と復号に同じ鍵を使う方式です。
暗号化と復号に同じ鍵を使う方式です。速いので大量のデータに向きますが、鍵を安全に渡す方法が問題になります。AES が代表です。
例: AES
注意: 速いですが、鍵を相手に安全に渡す方法が問題になります。
関連: 公開鍵暗号、暗号化

### 公開鍵暗号
別名: 非対称鍵暗号、公開鍵、秘密鍵
要約: 公開鍵と秘密鍵の組を使う暗号の方式です。
公開してよい公開鍵と、本人だけが持つ秘密鍵の組を使う方式です。公開鍵で暗号化したものは秘密鍵でしか復号できません。SSH の鍵認証、TLS、電子署名で使います。秘密鍵は絶対に渡しません。
例: RSA、ECDSA、Ed25519、SSH の鍵の組
注意: 公開鍵で暗号化したものは秘密鍵でしか復号できません。秘密鍵は渡しません。
関連: 共通鍵暗号、電子署名、証明書

### ハッシュ
別名: ハッシュ値、ダイジェスト
要約: データから決まった長さの値を計算する、元に戻せない関数です。
データから計算する、決まった長さの値です。元のデータが少しでも変わると値が大きく変わり、値から元のデータには戻せません。改ざんの検出や、パスワードの保存に使います。SHA-256 が代表です。
例: `sha256sum file`、パスワードの保存、イメージのダイジェスト
注意: MD5 と SHA-1 は衝突が見つかっているので、安全が必要な用途には使いません。
関連: 電子署名

### 電子署名
別名: デジタル署名
要約: 秘密鍵で署名し、公開鍵で確かめて、作った人と改ざんのないことを示す仕組みです。
秘密鍵でデータのハッシュに署名し、公開鍵で確かめる仕組みです。作った人が本人であることと、途中で改ざんされていないことを確かめられます。
例: パッケージの GPG の署名、コンテナのイメージの Cosign の署名
注意: 署名は中身を隠しません。秘密を守るには暗号化が別に必要です。
関連: 公開鍵暗号、ハッシュ、イメージの署名

### 証明書
別名: サーバー証明書、デジタル証明書、X.509
要約: 公開鍵と持ち主を、認証局が保証した電子的な書類です。
公開鍵と、その持ち主の情報に、認証局(CA)が署名したものです。Web サイトが本物であることを確かめるのに使います。有効期限があり、切れると接続がエラーになります。
例: `openssl x509 -in cert.pem -noout -dates -subject`
注意: 期限切れは障害の原因として多いので、期限を監視して自動で更新します。
関連: 認証局、TLS、公開鍵暗号

### 認証局
別名: CA
要約: 証明書に署名して、持ち主を保証する組織や仕組みです。
証明書を発行し、署名する機関や仕組みです。ブラウザや OS は、信頼する認証局の一覧を持っています。Kubernetes のクラスタも、自分の CA を持ちます。
例: Let's Encrypt、AWS Certificate Manager、Kubernetes のクラスタの CA
注意: 自分で作った CA の証明書は、相手に信頼させる設定をしないとエラーになります。
関連: 証明書

### TLS
別名: SSL
要約: 通信を暗号化し、相手のサーバーが本物かを確かめる仕組みです。
通信を暗号化し、相手が本物かを証明書で確かめるプロトコルです。HTTPS は HTTP を TLS で守ったものです。SSL は古い名前で、今は TLS 1.2 か 1.3 を使います。
例: HTTPS、`curl -v https://example.com`、TLS 1.2 と 1.3
注意: SSL は古い名前で、SSL 3.0 や TLS 1.0、1.1 は使ってはいけません。
関連: 証明書、HTTP、暗号化

### 鍵のローテーション
別名: ローテーション
試験: SAA、K8s
要約: 鍵やパスワードを、決まった間隔で新しいものに替えることです。
暗号化の鍵やパスワードを、定期的に新しいものに入れ替えることです。漏れていても、使える期間を短くできます。
例: KMS の自動ローテーション、IAM のアクセスキーの更新
注意: 替えても古い鍵を使う場所が残っていると止まるので、切り替えの手順を決めておきます。
関連: 暗号化、秘密情報

### 秘密情報
別名: シークレット、機密情報
要約: パスワード、鍵、トークンのように、漏れると困る情報です。
パスワード、API のキー、トークン、秘密鍵のような、漏れると困る情報です。コードや Git、イメージに書かず、専用の保管庫(Secrets Manager、Vault など)に置きます。
例: AWS Secrets Manager、Kubernetes の Secret、`.env` を `.gitignore` に入れる
注意: Git の履歴に一度入ったら、消すだけでなく、その値を無効にして替えます。
関連: Secrets Manager、Secret

## 脅威と対策

### 脆弱性
別名: CVE
要約: ソフトウェアや設定の、攻撃に使われうる弱点です。
ソフトウェアの、悪用できる欠陥です。見つかったものには CVE という番号が付きます。パッケージやイメージを更新して修正を取り込みます。
例: CVE の番号、CVSS の点数
注意: 脆弱性があっても、外から届かない、使っていない機能なら、危険の大きさは下がります。
関連: 脆弱性スキャン、パッチ

### 脆弱性スキャン
試験: Docker、SAA、K8s
要約: 既知の脆弱性がないかを、道具で調べることです。
ソフトウェアやイメージに、既知の脆弱性がないかを調べることです。コンテナのイメージは Trivy や Docker Scout、AWS では Amazon Inspector で調べます。
例: Trivy、Amazon Inspector、Docker Scout
注意: 新しい脆弱性は毎日見つかるので、作ったときだけでなく定期的に調べます。
関連: 脆弱性

### パッチ
要約: 不具合や脆弱性を直すための更新です。
ソフトウェアの欠陥や脆弱性を直すための更新です。適用を後回しにすると、攻撃される危険が増えます。
例: `dnf update --security`、OS とライブラリの更新
注意: 当てる前に検証の環境で試し、戻す方法を決めておきます。
関連: 脆弱性

### DDoS 攻撃
別名: DDoS
試験: SAA、CCNA
要約: 大量の通信を送り付けて、サービスを止める攻撃です。
多数の機器から大量の通信を送りつけて、サービスを使えなくする攻撃です。AWS では Shield や WAF、CloudFront で防ぎます。
例: AWS Shield、CloudFront、レート制限
注意: 自前のサーバーだけで受け止めるのは難しく、手前の CDN やサービスで吸収します。
関連: WAF

### WAF
別名: Web Application Firewall
試験: SAA
要約: Web アプリへの攻撃(SQL インジェクションなど)を、HTTP の中身を見て止める仕組みです。
Web アプリへの通信の中身を見て、SQL インジェクションのような攻撃や、同じ相手からの多すぎるリクエストを止める仕組みです。
例: AWS WAF を ALB や CloudFront に付ける
注意: WAF はアプリの脆弱性を直すものではなく、手前で防ぐ補助です。
関連: ファイアウォール、DDoS 攻撃

### SQL インジェクション
別名: XSS、クロスサイトスクリプティング
試験: SAA
要約: 入力に SQL を混ぜて、データベースを不正に操作する攻撃です。
入力の欄に、データベースの命令(SQL)を混ぜて、データを盗んだり壊したりする攻撃です。Web のページに悪いスクリプトを埋め込む攻撃は XSS です。WAF や、入力の正しい扱い方で防ぎます。
例: `' OR '1'='1`
注意: 文字列をつなげて SQL を作らず、プレースホルダー(バインド変数)を使って防ぎます。
関連: WAF

### 総当たり攻撃
別名: ブルートフォース攻撃、パスワードスプレー
要約: パスワードの候補を片っ端から試す攻撃です。
パスワードを片っ端から試す攻撃です。ログインの失敗の回数の制限、多要素認証、長いパスワードで防ぎます。
例: SSH への大量のログインの試み、`fail2ban`
注意: 鍵の認証にしてパスワードの認証を止める、試行の回数を制限する、MFA を使う、で防ぎます。
関連: 多要素認証、認証

### フィッシング
別名: ソーシャルエンジニアリング
要約: 本物に見せかけたメールやサイトで、パスワードなどをだまし取る攻撃です。
本物そっくりのメールや画面で、パスワードなどを入力させてだまし取る攻撃です。技術ではなく人の油断を突く攻撃をまとめて、ソーシャルエンジニアリングと呼びます。
例: 偽のログインの画面、偽の請求のメール
注意: パスキーや FIDO の鍵は、偽のサイトでは使えないので、フィッシングに強いです。
関連: 多要素認証

### マルウェア
別名: ランサムウェア
要約: 害を与えることを目的に作られたソフトウェアです。
悪意のあるソフトウェアの総称です。データを暗号化して身代金を求めるものをランサムウェアと呼びます。別の場所に、書き換えられないバックアップを持つと復旧できます。
例: ランサムウェア、トロイの木馬、ワーム
注意: ランサムウェアに備えて、書き換えられないバックアップ(別の場所、オフライン)を持ちます。
関連: バックアップ

### ゼロトラスト
要約: 社内のネットワークも信頼せず、通信のたびに確かめる考え方です。
社内のネットワークだからといって信用せず、すべてのアクセスを毎回確かめる、という考え方です。
例: 端末の状態の確認、利用者ごとの認証と認可、細かいアクセスの制御
注意: 「中は安全」という境界の守りだけに頼らない、という考え方です。
関連: 認証、最小権限の原則

### 監査ログ
要約: 誰が、いつ、何をしたかの記録です。
誰が、いつ、何をしたかの記録です。不正の調査や、規則を守っていることの証明に使います。AWS では CloudTrail、Kubernetes では API サーバーの監査ログがあります。
例: AWS CloudTrail、Linux の auditd、Kubernetes の監査ログ
注意: 記録を消されないように、別のアカウントや書き換えられない場所に送ります。
関連: CloudTrail

## OS の守り

### SELinux
別名: AppArmor
試験: LinuC102、Docker
要約: プロセスがアクセスできるものを、ラベルで強制的に制限する仕組みです。
Linux で、プロセスが触れるファイルや操作を、細かいルールで制限する仕組みです(強制アクセス制御)。root で動くプロセスでも制限できます。
例: `getenforce`、`ls -Z`、`restorecon -Rv /var/www`、`setsebool -P httpd_can_network_connect on`
注意: 困ったからといって無効にせず、ラベルや boolean を直します。
関連: root

### ケーパビリティ
別名: capabilities
試験: Docker、K8s
要約: root の権限を細かく分けたものです。
root の強い権限を、細かい単位(ネットワークの設定、低い番号のポートの使用など)に分けたものです。コンテナでは、すべて外して(`drop: ALL`)、必要なものだけを足すのが安全です。
例: `CAP_NET_BIND_SERVICE`(1024 未満のポート)、`docker run --cap-drop ALL --cap-add NET_BIND_SERVICE`
注意: `--privileged` はほぼすべてのケーパビリティを与えるので、原則として使いません。
関連: root、最小権限の原則
