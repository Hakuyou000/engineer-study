# 用語集 セキュリティ

## 認証と認可

### 認証
別名: Authentication
要約: 相手が本人かどうかを確かめることです。
「あなたは誰か」を確かめることです。パスワード、鍵、証明書、多要素認証などで確かめます。認証の後に、何をしてよいかを決めるのが認可です。
例: パスワード、SSH の鍵、クライアント証明書、MFA
注意: 認証(誰か)と認可(何をしてよいか)は別のものです。HTTP の 401 は認証、403 は認可の失敗です。
関連: 認可、多要素認証

### 認可
別名: Authorization
要約: 認証した相手に、何をしてよいかを決めることです。
認証で分かった相手に、「何をしてよいか」を決めることです。AWS の IAM ポリシーや、Kubernetes の RBAC が認可の仕組みです。
例: IAM ポリシー、Kubernetes の RBAC、Linux のパーミッション
注意: 認証が通っても、認可されていない操作は拒否されます。
関連: 認証、最小権限の原則、RBAC

### 多要素認証
別名: MFA、二要素認証
要約: 知っているもの、持っているもの、本人の特徴のうち、2 つ以上を組み合わせる認証です。
知っているもの(パスワード)、持っているもの(スマートフォン、鍵の装置)、本人の特徴(指紋)のうち、2 つ以上を組み合わせて認証することです。パスワードが漏れても、乗っ取られにくくなります。
例: パスワード + スマートフォンのワンタイムパスワード、パスキー
注意: パスワードを 2 回聞くのは、同じ種類の要素なので多要素認証ではありません。
関連: 認証

### 最小権限の原則
別名: 最小特権
要約: 仕事に必要な最小の権限だけを与える考え方です。
仕事に必要な最小限の権限だけを与える、という考え方です。乗っ取られたり誤って操作したりしたときの被害を小さくできます。
例: 読むだけの人には読み取りの権限だけ、`automountServiceAccountToken: false`
注意: 権限を広く与えると、乗っ取られたときや誤操作のときの被害が大きくなります。
関連: 認可、IAM ポリシー

### トークン
別名: アクセストークン
要約: 認証の後に渡される、一時的な通行証です。
認証が済んだことを表す、一時的な文字列です。パスワードの代わりに API を呼ぶときに使います。漏れると、持ち主のふりをされます。
例: OAuth のアクセストークン、JWT、AWS STS の一時的な認証情報
注意: トークンもパスワードと同じく秘密情報で、ログや URL に出してはいけません。
関連: 認証、秘密情報

### PAM
別名: Pluggable Authentication Modules
試験: LinuC202
要約: 認証の仕組みを部品(モジュール)に分け、組み合わせを選べるようにした仕組みです。
設定は `/etc/pam.d/` のプログラムごとのファイルに、「タイプ、制御フラグ、モジュール、引数」の形で書きます。ログインや ssh、sudo が、認証をこの仕組みに任せます。
例: `auth required pam_unix.so`、`session required pam_limits.so`
注意: 制御フラグは書く順番に意味があります。`requisite` は失敗で即終了、`sufficient` は成功で即終了です。
関連: 認証、SSSD

### SSSD
別名: System Security Services Daemon
試験: LinuC202
要約: LDAP などの認証の情報を取りに行き、手元に覚えておくデーモンです。
設定は `/etc/sssd/sssd.conf` に書きます。NSS(`sss`)と PAM(`pam_sss`)の両方を通して使います。サーバーにつながらなくても、覚えた情報でログインできます。
例: `systemctl enable --now sssd`、`getent passwd taro`
注意: `sssd.conf` の権限は `0600` にします。ゆるいと sssd は起動しません。
関連: PAM、LDAP、NSS

### NSS
別名: Name Service Switch、nsswitch.conf
試験: LinuC202
要約: ユーザー、グループ、ホスト名などの情報を、どこから調べるかを決める仕組みです。
設定は `/etc/nsswitch.conf` です。`passwd: files sss` のように、調べる場所を左から順に並べます。`files` はローカルのファイル、`sss` は SSSD です。
例: `passwd: files sss`、`hosts: files dns`、`getent passwd`
注意: NSS は「そのユーザーがいるか」を決め、PAM は「認証してよいか」を決めます。役割が違います。
関連: PAM、SSSD

### Basic 認証
別名: HTTP Basic 認証
試験: LinuC202
要約: ブラウザーが利用者名とパスワードを聞く、簡単な HTTP の認証です。
Apache では `mod_auth_basic` と `htpasswd` で作ったパスワードのファイルを使います。パスワードは暗号化されず、base64 で符号化されるだけで送られます。
例: `htpasswd -c /etc/httpd/.htpasswd alice`、`AuthType Basic`、`AuthUserFile /etc/httpd/.htpasswd`
注意: 必ず HTTPS と組み合わせます。HTTP のままでは、通信を見られるとパスワードが分かります。
関連: HTTP、TLS

### SMTP 認証
別名: SASL、SMTP AUTH
試験: LinuC202
要約: メールを送るときに、ユーザー名とパスワードで利用者を確かめる仕組みです。
メールを送るときに、ユーザー名とパスワードで利用者を確かめる仕組みです。認証の部品を SASL と呼びます。Postfix は、認証を Dovecot に任せる設定がよく使われます。
例: Postfix の `smtpd_sasl_auth_enable = yes`、`smtpd_sasl_type = dovecot`
注意: パスワードが平文で流れないように、STARTTLS で暗号化してから認証させます。
関連: STARTTLS、オープンリレー、Dovecot

### ホスト鍵
別名: SSH ホスト鍵
試験: LinuC202
要約: SSH のサーバーが、自分が本物だと示すための鍵の組です。
`/etc/ssh/ssh_host_*_key`(秘密鍵)と `.pub`(公開鍵)です。クライアントは `known_hosts` に記録し、次からは同じ鍵かを比べます。
例: `/etc/ssh/ssh_host_ed25519_key`、`ssh-keygen -A`
注意: ホスト鍵が変わると、クライアントに警告が出ます。サーバーの複製のあとは、ホスト鍵を作り直します。
関連: SSH、公開鍵暗号

### authorized_keys
試験: LinuC202
要約: SSH の公開鍵認証で、ログインを許す公開鍵を並べるファイルです。
サーバー側のユーザーの `~/.ssh/authorized_keys` に、公開鍵を 1 行ずつ書きます。クライアントは、対応する秘密鍵で認証します。
例: `ssh-copy-id alice@server1`、`~/.ssh/authorized_keys`
注意: ホームや `~/.ssh` や、このファイルが他人に書き込める状態だと、認証に失敗します。
関連: SSH、公開鍵暗号

### pam_faillock
別名: faillock
試験: LinuC3SS
要約: ログインの失敗を数えて、一定回数でアカウントを一時的にロックする PAM のモジュールです。
`pam_tally2` の後継で、RHEL 9 系で使います。回数や時間は `/etc/security/faillock.conf` に書きます(`deny`、`fail_interval`、`unlock_time`)。解除は `faillock` コマンドです。
例: `faillock --user taro`、`faillock --user taro --reset`、`authselect enable-feature with-faillock`
注意: `even_deny_root` を有効にすると root もロックされるので、コンソールから入れなくなる危険があります。
関連: PAM、authselect

### authselect
試験: LinuC3SS
要約: RHEL 9 系で、PAM と nsswitch.conf の設定をプロファイルで管理する道具です。
`/etc/pam.d/system-auth` などは、`/etc/authselect/` の下のファイルへのリンクです。直接編集せず、プロファイルと機能(`with-faillock` など)で変えます。
例: `authselect current`、`authselect select sssd with-faillock`、`authselect check`
注意: `system-auth` を直接編集すると、次に `authselect` を実行したときに元に戻ります。
関連: PAM、SSSD、pam_faillock

### Kerberos
試験: LinuC3SS
要約: パスワードをネットワークに流さずに、チケットで認証する仕組みです。
KDC(鍵配布センター)が、最初にパスワードで認証したユーザーに TGT を渡します。以降は TGT で、各サービスのチケットをもらい、シングルサインオンができます。
例: `kinit taro`、`klist`、`kdestroy`
注意: クライアントと KDC の時刻のずれが 5 分(既定)を超えると、認証に失敗します。
関連: FreeIPA、SSSD、LDAP

### FreeIPA
別名: IdM、Identity Management
試験: LinuC3SS
要約: LDAP、Kerberos、認証局、DNS、NTP をまとめた、Linux 向けの統合認証の製品です。
Red Hat 版は IdM といいます。サーバーは `ipa-server-install`、クライアントは `ipa-client-install` で構成し、`ipa` コマンドや管理画面で、ユーザー、グループ、ホスト、アクセスの規則を管理します。
例: `ipa-server-install`、`ipa user-add taro`、`ipa hbactest`
注意: FQDN のホスト名と DNS、時刻の同期が前提です。そろっていないと、導入や `kinit` で失敗します。
関連: Kerberos、LDAP、SSSD、Dogtag、HBAC

### HBAC
別名: Host-Based Access Control
試験: LinuC3SS
要約: FreeIPA で、どのユーザーが、どのホストの、どのサービスに入ってよいかを決める規則です。
認証に成功したあと、アクセスを許すかどうかを決めます。既定の `allow_all` は全員を許可するので、実運用では無効にして、必要な規則だけを足します。
例: `ipa hbacrule-add`、`ipa hbacrule-disable allow_all`、`ipa hbactest`
注意: `allow_all` を無効にする前に、必要な規則を入れて `ipa hbactest` で確かめないと、自分も入れなくなります。
関連: FreeIPA、Kerberos

### Keycloak
試験: LinuC3SS
要約: ログイン画面、シングルサインオン、ユーザーの管理、認可を提供する、オープンソースの認証認可のサーバーです。
OpenID Connect、OAuth 2.0、SAML に対応します。ユーザーをまとめる単位がレルムで、アプリケーションをクライアントとして登録します。17 以降は Quarkus で動き、起動は `kc.sh` です。
例: `kc.sh start-dev`、`kc.sh build`、`kc.sh start --optimized`
注意: `start-dev` は試すだけのモードです。本番では HTTPS とホスト名を設定して `start` で起動します。
関連: OpenID Connect、OAuth 2.0、SAML、WebAuthn

### OAuth 2.0
別名: OAuth
試験: LinuC3SS
要約: アプリケーションに、API を呼ぶ権限を渡すための、認可の決まりです。
ユーザーのパスワードを渡さずに、アクセストークンで権限を渡します。ログインしたのがだれかを表す仕組みは、OAuth 2.0 にはありません。
例: 認可コードフロー、アクセストークン、リフレッシュトークン
注意: OAuth 2.0 は認可の決まりで、認証ではありません。認証には OpenID Connect を使います。
関連: OpenID Connect、トークン、Keycloak

### OpenID Connect
別名: OIDC
試験: LinuC3SS
要約: OAuth 2.0 の上に、ユーザーの認証を足した決まりです。
ID トークン(JWT)で、だれがいつどのように認証したかをアプリに伝えます。`/.well-known/openid-configuration` に、接続に必要な情報が公開されます。
例: `/realms/corp/.well-known/openid-configuration`
注意: ID トークンはクライアントのためのものです。API の認可には、アクセストークンを使います。
関連: OAuth 2.0、SAML、Keycloak

### SAML
別名: SAML 2.0、Security Assertion Markup Language
試験: LinuC3SS
要約: XML のアサーションで、認証の結果と属性を渡す、シングルサインオンの決まりです。
ID プロバイダー(IdP)が認証し、サービス側(SP)にアサーションを渡します。古い企業のシステムや SaaS で、よく使われます。
例: `/realms/corp/protocol/saml/descriptor`
注意: SAML は XML、OpenID Connect は JSON の形式です。新しいアプリは、OpenID Connect を選ぶことが多いです。
関連: OpenID Connect、Keycloak

### WebAuthn
別名: FIDO2、パスキー
試験: LinuC3SS
要約: セキュリティキーや生体認証で、公開鍵の方式で認証する、ブラウザの規格です。
サイトの URL にひもづいて動くので、偽のサイトでは認証できず、フィッシングに強いです。パスワードなしのログインにも使えます。
例: セキュリティキー、端末の指紋認証、Keycloak の WebAuthn Policy
注意: 端末をなくしたときのために、復旧の手段を用意します。
関連: 多要素認証、Keycloak

## 暗号と証明書

### 暗号化
要約: データを、鍵がないと読めない形に変えることです。
データを、鍵がないと読めない形に変えることです。通信の途中を守るもの(転送中の暗号化、TLS)と、保存したデータを守るもの(保存時の暗号化、KMS など)があります。
例: 保存時の暗号化(EBS、S3 の SSE)、転送時の暗号化(TLS)
注意: 暗号化しても、鍵の管理が甘ければ守れません。
関連: 共通鍵暗号、公開鍵暗号、TLS

### 共通鍵暗号
別名: 対称鍵暗号
要約: 暗号化と復号に同じ鍵を使う方式です。
暗号化と復号に同じ鍵を使う方式です。速いので大量のデータに向きますが、鍵を安全に渡す方法が問題になります。AES が代表です。
例: AES
注意: 速いですが、鍵を相手に安全に渡す方法が問題になります。
関連: 公開鍵暗号、暗号化

### 公開鍵暗号
別名: 非対称鍵暗号、公開鍵、秘密鍵
要約: 公開鍵と秘密鍵の組を使う暗号の方式です。
公開してよい公開鍵と、本人だけが持つ秘密鍵の組を使う方式です。公開鍵で暗号化したものは秘密鍵でしか復号できません。SSH の鍵認証、TLS、電子署名で使います。秘密鍵は絶対に渡しません。
例: RSA、ECDSA、Ed25519、SSH の鍵の組
注意: 公開鍵で暗号化したものは秘密鍵でしか復号できません。秘密鍵は渡しません。
関連: 共通鍵暗号、電子署名、証明書

### ハッシュ
別名: ハッシュ値、ダイジェスト
要約: データから決まった長さの値を計算する、元に戻せない関数です。
データから計算する、決まった長さの値です。元のデータが少しでも変わると値が大きく変わり、値から元のデータには戻せません。改ざんの検出や、パスワードの保存に使います。SHA-256 が代表です。
例: `sha256sum file`、パスワードの保存、イメージのダイジェスト
注意: MD5 と SHA-1 は衝突が見つかっているので、安全が必要な用途には使いません。
関連: 電子署名

### 電子署名
別名: デジタル署名
要約: 秘密鍵で署名し、公開鍵で確かめて、作った人と改ざんのないことを示す仕組みです。
秘密鍵でデータのハッシュに署名し、公開鍵で確かめる仕組みです。作った人が本人であることと、途中で改ざんされていないことを確かめられます。
例: パッケージの GPG の署名、コンテナのイメージの Cosign の署名
注意: 署名は中身を隠しません。秘密を守るには暗号化が別に必要です。
関連: 公開鍵暗号、ハッシュ、イメージの署名

### 証明書
別名: サーバー証明書、デジタル証明書、X.509
要約: 公開鍵と持ち主を、認証局が保証した電子的な書類です。
公開鍵と、その持ち主の情報に、認証局(CA)が署名したものです。Web サイトが本物であることを確かめるのに使います。有効期限があり、切れると接続がエラーになります。
例: `openssl x509 -in cert.pem -noout -dates -subject`
注意: 期限切れは障害の原因として多いので、期限を監視して自動で更新します。
関連: 認証局、TLS、公開鍵暗号

### 認証局
別名: CA
要約: 証明書に署名して、持ち主を保証する組織や仕組みです。
証明書を発行し、署名する機関や仕組みです。ブラウザや OS は、信頼する認証局の一覧を持っています。Kubernetes のクラスタも、自分の CA を持ちます。
例: Let's Encrypt、AWS Certificate Manager、Kubernetes のクラスタの CA
注意: 自分で作った CA の証明書は、相手に信頼させる設定をしないとエラーになります。
関連: 証明書

### TLS
別名: SSL
要約: 通信を暗号化し、相手のサーバーが本物かを確かめる仕組みです。
通信を暗号化し、相手が本物かを証明書で確かめるプロトコルです。HTTPS は HTTP を TLS で守ったものです。SSL は古い名前で、今は TLS 1.2 か 1.3 を使います。
例: HTTPS、`curl -v https://example.com`、TLS 1.2 と 1.3
注意: SSL は古い名前で、SSL 3.0 や TLS 1.0、1.1 は使ってはいけません。
関連: 証明書、HTTP、暗号化

### 鍵のローテーション
別名: ローテーション
試験: SAA、K8s
要約: 鍵やパスワードを、決まった間隔で新しいものに替えることです。
暗号化の鍵やパスワードを、定期的に新しいものに入れ替えることです。漏れていても、使える期間を短くできます。
例: KMS の自動ローテーション、IAM のアクセスキーの更新
注意: 替えても古い鍵を使う場所が残っていると止まるので、切り替えの手順を決めておきます。
関連: 暗号化、秘密情報

### 秘密情報
別名: シークレット、機密情報
要約: パスワード、鍵、トークンのように、漏れると困る情報です。
パスワード、API のキー、トークン、秘密鍵のような、漏れると困る情報です。コードや Git、イメージに書かず、専用の保管庫(Secrets Manager、Vault など)に置きます。
例: AWS Secrets Manager、Kubernetes の Secret、`.env` を `.gitignore` に入れる
注意: Git の履歴に一度入ったら、消すだけでなく、その値を無効にして替えます。
関連: Secrets Manager、Secret

### TSIG
別名: Transaction SIGnature
試験: LinuC202
要約: 共有の秘密鍵で DNS のメッセージに署名し、相手を確かめる仕組みです。
2 つの DNS サーバーが同じ鍵を持ち、ゾーン転送、動的更新、通知のメッセージに署名します。鍵は `tsig-keygen` で作れます。
例: `key "transfer-key" { algorithm hmac-sha256; secret "…"; };`、`allow-transfer { key transfer-key; };`
注意: TSIG は署名だけで、内容は暗号化しません。応答の署名で改ざんを見つける DNSSEC とは別のものです。
関連: ゾーン転送、DNSSEC、ハッシュ

### DNSSEC
別名: DNSKEY、RRSIG、DS レコード
試験: LinuC202
要約: DNS の答えが改ざんされていないことを、電子署名で確かめる仕組みです。
ゾーンのレコードに署名(RRSIG)を付け、検証用の公開鍵(DNSKEY)を載せます。親のゾーンの DS レコードが、子の鍵を保証して、ルートからの信頼のつながりを作ります。
例: `dnssec-keygen`、`dnssec-signzone`、`dig +dnssec www.example.com`(`ad` のフラグ)
注意: 署名で改ざんを見つけるだけです。問い合わせの内容は暗号化されません。
関連: DNS、電子署名、公開鍵暗号、DANE

### DANE
別名: TLSA レコード
試験: LinuC202
要約: サーバーの証明書の情報を DNS に載せ、証明書を確かめられるようにする仕組みです。
証明書(または公開鍵)のハッシュを、TLSA レコードとして DNS に載せます。クライアントは、つながった相手の証明書が、この記録と合うかを確かめます。
例: `_443._tcp.www.example.com. IN TLSA 3 1 1 <ハッシュ>`
注意: DNSSEC で署名されていることが前提です。署名がないと、TLSA の答えが改ざんされるおそれがあります。
関連: DNSSEC、証明書、ハッシュ

### CSR(サーバー証明書の申請)
別名: Certificate Signing Request(Web サーバー)
試験: LinuC202
要約: 認証局にサーバー証明書の署名を頼む、申請の書類です。
サーバーの公開鍵と、名前(CN)や組織の情報が入っています。秘密鍵そのものは入っていません。秘密鍵から作り、CA に送ります。
例: `openssl req -new -key server.key -out server.csr`
注意: 秘密鍵は CA に渡しません。送るのは CSR だけです。
関連: 証明書、認証局

### 自己署名証明書
別名: オレオレ証明書、セルフサイン証明書
試験: LinuC202
要約: 認証局ではなく、自分の秘密鍵で署名した証明書です。
通信を暗号化できますが、信頼された CA の署名がないので、ブラウザーが警告を出します。検証や社内の試験に使います。
例: `openssl req -x509 -newkey rsa:2048 -nodes -keyout server.key -out server.crt -days 365`
注意: 公開するサイトには使いません。利用者に警告を無視する習慣が付きます。
関連: 証明書、認証局

### 中間 CA
別名: 中間認証局、中間証明書
試験: LinuC202
要約: ルート CA とサーバー証明書の間をつなぐ、認証局の証明書です。
サーバー証明書は、中間 CA が署名することが多いです。サーバーは、サーバー証明書の後ろに中間 CA の証明書を続けて送ります。
例: `SSLCertificateFile` のファイルに、サーバー証明書、中間 CA の証明書の順で書く
注意: 中間 CA の証明書を付け忘れると、一部のクライアントだけで、検証のエラーになります。
関連: 証明書、認証局

### OpenSSL
別名: openssl
試験: LinuC202
要約: 暗号と証明書を扱うライブラリとコマンドです。
鍵や CSR、自己署名証明書を作ったり、証明書の中身を見たり、サーバーの TLS 接続を確かめたりできます。
例: `openssl x509 -in server.crt -noout -dates`、`openssl s_client -connect example.com:443`
注意: サブコマンド(`req`、`x509`、`verify`、`s_client`)で動きが変わります。
関連: 証明書、TLS、CSR(サーバー証明書の申請)

### STARTTLS
試験: LinuC202
要約: 平文でつないだあとに、通信を TLS の暗号化に切り替える命令です。
平文でつないだあとに、通信を TLS の暗号化に切り替える命令です。SMTP、IMAP、POP3 で使います。
例: 587 番で `STARTTLS` を送ってから SMTP 認証をする
注意: 最初から TLS にする 465、993、995 番の方式とは違います。
関連: TLS、SMTP、SMTP 認証

### LUKS
別名: Linux Unified Key Setup
試験: LinuC3SS
要約: ディスクの暗号化で、鍵の管理をする形式です。
デバイスの先頭のヘッダーに、複数のパスフレーズ(キースロット)を記録します。LUKS1 と LUKS2 があり、今の既定は LUKS2 です。`cryptsetup` で操作します。
例: `cryptsetup luksFormat /dev/vdb1`、`cryptsetup luksDump /dev/vdb1`
注意: ヘッダーが壊れると、パスフレーズが分かっていても復号できません。
関連: dm-crypt、cryptsetup、キースロット

### dm-crypt
試験: LinuC3SS
要約: ブロックデバイスを暗号化する、Linux カーネルの仕組みです。
device-mapper の仕組みの 1 つで、`/dev/mapper/` の下のデバイスを通すと、自動で暗号化と復号をします。鍵の管理の形式として、LUKS を組み合わせて使うのがふつうです。
例: `cryptsetup open /dev/vdb1 secure`(`/dev/mapper/secure` ができる)
注意: dm-crypt はカーネルの仕組みで、LUKS は鍵の管理の形式です。
関連: LUKS、cryptsetup

### cryptsetup
試験: LinuC3SS
要約: dm-crypt と LUKS のデバイスを操作するコマンドです。
初期化(luksFormat)、開く(open)、閉じる(close)、パスフレーズの追加(luksAddKey)、ヘッダーの表示(luksDump)などをします。
例: `cryptsetup open /dev/vdb1 secure`、`cryptsetup close secure`
注意: `luksFormat` は、中のデータを使えなくします。
関連: LUKS、dm-crypt、キースロット

### キースロット
別名: key slot
試験: LinuC3SS
要約: LUKS のヘッダーの中の、パスフレーズを入れる枠です。
どのキースロットのパスフレーズでも、同じデータの鍵が取り出せます。LUKS1 は 8 個、LUKS2 は最大 32 個です。
例: `cryptsetup luksAddKey /dev/vdb1`、`cryptsetup luksKillSlot /dev/vdb1 1`
注意: 最後の 1 つを消すと、二度と開けません。
関連: LUKS、cryptsetup

### fscrypt
試験: LinuC3SS
要約: ディレクトリ単位でファイルを暗号化する、ファイルシステムの機能です。
ext4 や F2FS などが対応しています。ファイル名と内容が暗号化され、ユーザーごとに別の鍵を使えます。ファイルのサイズなどは暗号化されません。
例: `fscrypt encrypt /data/private`、`fscrypt unlock /data/private`
注意: 暗号化するディレクトリは、空でなければなりません。
関連: LUKS、ext4

### ACME
別名: Automatic Certificate Management Environment
試験: LinuC3SS
要約: 証明書の申請、確認、発行、更新を自動で行うための、決まりごとです。
RFC 8555 で決められています。Let's Encrypt が使い、クライアントの `certbot` などが、この手順で証明書を取ります。
例: `certbot certonly --webroot -w /var/www/html -d example.com`
注意: ACME は申請の手順の決まりで、証明書を出す認証局の名前ではありません。
関連: Let's Encrypt、certbot、HTTP-01

### Let's Encrypt
別名: ISRG
試験: LinuC3SS
要約: ドメインの管理を確かめるだけの DV 証明書を、無料で、自動で出す認証局です。
ACME で申請します。有効期間が短い(2026 年 11 月時点で 90 日)ので、自動更新が前提です。OCSP は 2025 年 8 月に終了し、失効の情報は CRL で出します。
例: `certbot certificates`、`ls /etc/letsencrypt/live/`
注意: 組織の実在は確かめません。有効期間は、今後さらに短くなる予定です(公式のお知らせを確認します)。
関連: ACME、certbot

### certbot
試験: LinuC3SS
要約: Let's Encrypt などから、ACME で証明書を取り、更新する、代表的なクライアントです。
`--nginx` や `--apache` で、Web サーバーの設定まで自動で書き換えます。`certonly` は、証明書だけを取ります。更新は `certbot renew` で、timer ユニットか cron から実行します。
例: `certbot --nginx -d example.com`、`certbot renew --dry-run`
注意: `renew` で更新したあと、Web サーバーを reload しないと、古い証明書が使われ続けます。
関連: ACME、HTTP-01

### HTTP-01
別名: DNS-01
試験: LinuC3SS
要約: ACME で、ドメインの管理を確かめる 2 つの方法(Web サーバーに置くものと、DNS に置くもの)です。
HTTP-01 は、`/.well-known/acme-challenge/` に置いた内容を、80/tcp で取りに来て確かめます。DNS-01 は、`_acme-challenge` の TXT レコードで確かめます。
例: `certbot certonly --standalone -d example.com`、`certbot certonly --dns-route53 -d '*.example.com'`
注意: ワイルドカード証明書は DNS-01 でだけ取れます。HTTP-01 は 80/tcp が外から届かないと失敗します。
関連: ACME、certbot

### ルート証明書
別名: ルート CA
試験: LinuC3SS
要約: 信頼の出発点になる、認証局の証明書です。OS やブラウザーに最初から入っています。
証明書は、ルート証明書、中間証明書、サーバー証明書の順につながります。クライアントは、ルート証明書までたどれると、サーバー証明書を信頼します。
例: `ls /etc/ssl/certs/`、`openssl s_client -connect example.com:443 -showcerts`
注意: ルート証明書は、サーバーが送る必要はありません。サーバーが送り忘れやすいのは、中間証明書です。
関連: 中間 CA、証明書

### DV 証明書
別名: OV 証明書、EV 証明書、ドメイン認証証明書
試験: LinuC3SS
要約: 証明書の種類です。DV はドメインの管理、OV は組織の実在、EV はさらに厳しい審査を確かめたものです。
確かめる範囲が違うだけで、通信の暗号の強さは同じです。Let's Encrypt が出すのは DV だけです。
例: `openssl x509 -in cert.pem -noout -subject -issuer`
注意: EV にしても、今のブラウザーは、DV と見た目をほとんど区別しません。
関連: 証明書、Let's Encrypt

### Dogtag
別名: Dogtag Certificate System
試験: LinuC3SS
要約: FreeIPA に含まれる、証明書を発行する認証局(CA)です。
FreeIPA のホストやサービスの証明書を発行します。クライアントでは、certmonger が証明書の期限を見張り、Dogtag に更新を頼みます。
例: `ipa cert-show 1`、`getcert list`
注意: 証明書を発行するのは Dogtag で、期限を見張って更新を頼むのは certmonger です。役割が違います。
関連: FreeIPA、認証局、certmonger

### certmonger
試験: LinuC3SS
要約: 証明書の期限を見張り、近づくと CA に更新を頼む常駐のプログラムです。
FreeIPA のクライアントでは、`ipa-client-install` が設定します。見張っている証明書の状態は `getcert` で見られます。
例: `getcert list`、`getcert request`
注意: 更新に失敗していても、期限が来るまで気づきにくいので、`getcert list` で定期的に確かめます。
関連: FreeIPA、Dogtag、認証局

### Secure Boot
別名: セキュアブート
試験: LinuC3PS
要約: 署名が正しいプログラムだけを、起動のときに動かす仕組みです。
UEFI のファームウェアが、ブートローダーやカーネルの署名を、PK、KEK、db の信頼の鎖で確かめます。VM では OVMF のファームウェアで使えます。
例: `mokutil --sb-state`
注意: 署名のないカーネルモジュールは読み込めません。自分の鍵を MOK に登録します。
関連: UEFI、仮想 TPM

### 仮想 TPM
別名: swtpm、vTPM
試験: LinuC3PS
要約: ソフトウェアで作った、VM 用の TPM です。
TPM は、鍵の保管と起動の状態の記録をする部品です。仮想 TPM は、swtpm で作り、ホストに物理の TPM がなくても、VM に TPM 2.0 を見せられます。
例: `<tpm model='tpm-crb'><backend type='emulator' version='2.0'/></tpm>`
注意: 状態ファイルを失うと、TPM の中の鍵を失います。バックアップに含めます。
関連: Secure Boot、仮想マシン

## 脅威と対策

### 脆弱性
別名: CVE
要約: ソフトウェアや設定の、攻撃に使われうる弱点です。
ソフトウェアの、悪用できる欠陥です。見つかったものには CVE という番号が付きます。パッケージやイメージを更新して修正を取り込みます。
例: CVE の番号、CVSS の点数
注意: 脆弱性があっても、外から届かない、使っていない機能なら、危険の大きさは下がります。
関連: 脆弱性スキャン、パッチ

### 脆弱性スキャン
試験: Docker、SAA、K8s
要約: 既知の脆弱性がないかを、道具で調べることです。
ソフトウェアやイメージに、既知の脆弱性がないかを調べることです。コンテナのイメージは Trivy や Docker Scout、AWS では Amazon Inspector で調べます。
例: Trivy、Amazon Inspector、Docker Scout
注意: 新しい脆弱性は毎日見つかるので、作ったときだけでなく定期的に調べます。
関連: 脆弱性

### パッチ
要約: 不具合や脆弱性を直すための更新です。
ソフトウェアの欠陥や脆弱性を直すための更新です。適用を後回しにすると、攻撃される危険が増えます。
例: `dnf update --security`、OS とライブラリの更新
注意: 当てる前に検証の環境で試し、戻す方法を決めておきます。
関連: 脆弱性

### DDoS 攻撃
別名: DDoS
試験: SAA、CCNA
要約: 大量の通信を送り付けて、サービスを止める攻撃です。
多数の機器から大量の通信を送りつけて、サービスを使えなくする攻撃です。AWS では Shield や WAF、CloudFront で防ぎます。
例: AWS Shield、CloudFront、レート制限
注意: 自前のサーバーだけで受け止めるのは難しく、手前の CDN やサービスで吸収します。
関連: WAF

### WAF
別名: Web Application Firewall
試験: SAA
要約: Web アプリへの攻撃(SQL インジェクションなど)を、HTTP の中身を見て止める仕組みです。
Web アプリへの通信の中身を見て、SQL インジェクションのような攻撃や、同じ相手からの多すぎるリクエストを止める仕組みです。
例: AWS WAF を ALB や CloudFront に付ける
注意: WAF はアプリの脆弱性を直すものではなく、手前で防ぐ補助です。
関連: ファイアウォール、DDoS 攻撃

### SQL インジェクション
別名: XSS、クロスサイトスクリプティング
試験: SAA
要約: 入力に SQL を混ぜて、データベースを不正に操作する攻撃です。
入力の欄に、データベースの命令(SQL)を混ぜて、データを盗んだり壊したりする攻撃です。Web のページに悪いスクリプトを埋め込む攻撃は XSS です。WAF や、入力の正しい扱い方で防ぎます。
例: `' OR '1'='1`
注意: 文字列をつなげて SQL を作らず、プレースホルダー(バインド変数)を使って防ぎます。
関連: WAF

### 総当たり攻撃
別名: ブルートフォース攻撃、パスワードスプレー
要約: パスワードの候補を片っ端から試す攻撃です。
パスワードを片っ端から試す攻撃です。ログインの失敗の回数の制限、多要素認証、長いパスワードで防ぎます。
例: SSH への大量のログインの試み、`fail2ban`
注意: 鍵の認証にしてパスワードの認証を止める、試行の回数を制限する、MFA を使う、で防ぎます。
関連: 多要素認証、認証

### フィッシング
別名: ソーシャルエンジニアリング
要約: 本物に見せかけたメールやサイトで、パスワードなどをだまし取る攻撃です。
本物そっくりのメールや画面で、パスワードなどを入力させてだまし取る攻撃です。技術ではなく人の油断を突く攻撃をまとめて、ソーシャルエンジニアリングと呼びます。
例: 偽のログインの画面、偽の請求のメール
注意: パスキーや FIDO の鍵は、偽のサイトでは使えないので、フィッシングに強いです。
関連: 多要素認証

### マルウェア
別名: ランサムウェア
要約: 害を与えることを目的に作られたソフトウェアです。
悪意のあるソフトウェアの総称です。データを暗号化して身代金を求めるものをランサムウェアと呼びます。別の場所に、書き換えられないバックアップを持つと復旧できます。
例: ランサムウェア、トロイの木馬、ワーム
注意: ランサムウェアに備えて、書き換えられないバックアップ(別の場所、オフライン)を持ちます。
関連: バックアップ

### ゼロトラスト
要約: 社内のネットワークも信頼せず、通信のたびに確かめる考え方です。
社内のネットワークだからといって信用せず、すべてのアクセスを毎回確かめる、という考え方です。
例: 端末の状態の確認、利用者ごとの認証と認可、細かいアクセスの制御
注意: 「中は安全」という境界の守りだけに頼らない、という考え方です。
関連: 認証、最小権限の原則

### 監査ログ
要約: 誰が、いつ、何をしたかの記録です。
誰が、いつ、何をしたかの記録です。不正の調査や、規則を守っていることの証明に使います。AWS では CloudTrail、Kubernetes では API サーバーの監査ログがあります。
例: AWS CloudTrail、Linux の auditd、Kubernetes の監査ログ
注意: 記録を消されないように、別のアカウントや書き換えられない場所に送ります。
関連: CloudTrail

### オープンリレー
別名: 第三者中継
試験: LinuC202
要約: 誰からのメールでも中継してしまう、設定を誤ったメールサーバーです。
誰からのメールでも、自分宛てでないドメインへ中継してしまう、設定を誤ったメールサーバーです。迷惑メールの踏み台に使われます。
例: Postfix の `mynetworks` に `0.0.0.0/0` を書いてしまう
注意: 中継は、信頼するネットワークと、SMTP 認証に成功したユーザーに絞ります。
関連: MTA、SMTP 認証

### fail2ban
試験: LinuC202
要約: ログを見て、認証の失敗が続く接続元を、自動でブロックする道具です。
`findtime` の間に `maxretry` 回を超えた接続元を、ファイアウォールの規則で `bantime` の間ブロックします。SSH の総当たり攻撃への対策によく使います。
例: `fail2ban-client status sshd`、`/etc/fail2ban/jail.local`
注意: 設定は `jail.local` に書きます。`jail.conf` は更新で上書きされます。
関連: 総当たり攻撃、ファイアウォール

### IDS
別名: 侵入検知システム、Intrusion Detection System、snort
試験: LinuC202
要約: 不正なアクセスの兆候を見つけて、知らせる仕組みです。
ネットワークを流れるパケット(ネットワーク型。snort など)や、ホストのログとファイルの変化(ホスト型)を調べます。見つけて知らせるだけで、自分では止めません。
例: snort、OSSEC
注意: 止める機能まで持つものは IPS と呼びます。
関連: ファイアウォール、fail2ban

### OpenVAS
別名: Greenbone Vulnerability Management、GVM
試験: LinuC202
要約: ネットワークの上から、既知の脆弱性を調べる脆弱性スキャナーです。
ホストやサービスに、既知の脆弱性が残っていないかを検査し、報告書を作ります。
例: Greenbone の Web 画面、スキャンのタスク
注意: 検査は、自分が管理するホストだけを対象にします。
関連: 脆弱性スキャン、脆弱性

### OpenSCAP
別名: oscap、SCAP
試験: LinuC202
要約: ホストの設定が、決まったセキュリティ基準に合っているかを検査する道具です。
SCAP という仕組みの基準(プロファイル)に照らして、設定を検査し、報告書を作ります。基準は `scap-security-guide` のパッケージで入ります。
例: `oscap xccdf eval --profile <ID> --report report.html <データストリーム>`
注意: 既知の脆弱性を調べる OpenVAS とは目的が違います。OpenSCAP は設定の適合を調べます。
関連: 脆弱性スキャン、OpenVAS

### JPCERT/CC
別名: JVN、Japan Vulnerability Notes
試験: LinuC202
要約: 日本のセキュリティ事故の調整センターで、JVN で脆弱性の情報を発信します。
一般社団法人 JPCERT コーディネーションセンターです。注意喚起を出し、脆弱性の情報のポータル JVN を、IPA と運営します。
例: JVN の脆弱性の情報、注意喚起の一覧
注意: 米国の CERT/CC とは別の組織です。
関連: 脆弱性、パッチ

### auditd
試験: LinuC3SS
要約: Linux の監査(誰が何をしたかの記録)をログに書く、デーモンです。
カーネルが捕まえた事象を、`/var/log/audit/audit.log` に書きます。設定は `/etc/audit/auditd.conf` で、記録する規則は `/etc/audit/rules.d/` に書きます。
例: `service auditd restart`、`auditctl -l`
注意: Red Hat 系では、`systemctl restart auditd` を受け付けないことがあります。
関連: 監査ログ、auditctl

### auditctl
試験: LinuC3SS
要約: 監査の規則を、実行中のカーネルに足したり、見たりするコマンドです。
`-w` でファイルを監視し、`-a always,exit` でシステムコールを記録します。`-l` で一覧、`-s` で状態を見ます。
例: `auditctl -w /etc/passwd -p wa -k identity`、`auditctl -l`
注意: 足した規則は、再起動で消えます。残すには `/etc/audit/rules.d/` に書いて、`augenrules --load` を実行します。
関連: auditd、ausearch

### ausearch
試験: LinuC3SS
要約: 監査ログから、条件に合う記録を探すコマンドです。
キー(`-k`)、記録の種類(`-m`)、ユーザー、ファイル、時刻(`-ts`)などで絞ります。`-i` で数字を名前に直して読みやすくします。
例: `ausearch -k identity -i -ts today`
注意: 規則に `-k` でキーを付けておかないと、後で絞りにくくなります。
関連: auditd、aureport

### aureport
試験: LinuC3SS
要約: 監査ログを集計して、報告にするコマンドです。
ログイン(`-l`)、認証(`--auth`)、ファイル(`-f`)、実行したプログラム(`-x`)などの報告を作ります。`--failed` で失敗だけに絞れます。
例: `aureport -l --failed -ts this-week`、`aureport --auth --summary`
注意: 集計のコマンドで、1 件ずつの詳しい中身を探すには `ausearch` を使います。
関連: auditd、ausearch

### Suricata
別名: NIDS、NIPS
試験: LinuC3SS
要約: 通信を規則と照らし合わせて、不審なものを見つける(必要なら止める)ネットワーク型の道具です。
設定は `/etc/suricata/suricata.yaml`、規則は `suricata-update` で取ってきます。ミラーポートで見るだけなら NIDS、経路の途中(インライン)に置いて `drop` の規則を使えば NIPS になります。ログは `fast.log` と `eve.json` です。
例: `suricata -T -c /etc/suricata/suricata.yaml`、`alert http any any -> $HOME_NET any (msg:"..."; sid:1000001; rev:1;)`
注意: 最初は警告だけで動かし、誤検知を確かめてから `drop` にします。
関連: IDS、WAF

### ModSecurity
別名: mod_security
試験: LinuC3SS
要約: Web サーバーに組み込む WAF です。HTTP の要求を調べて、攻撃を止めます。
Apache のモジュールか、Nginx の ModSecurity v3 で使います。`SecRuleEngine` で動きを決めます(`On`、`DetectionOnly`、`Off`)。ルールは `SecRule` で書き、OWASP CRS を使うのが基本です。
例: `SecRuleEngine DetectionOnly`、`SecRule ARGS "@rx (?i)<script" "id:100001,phase:2,deny,status:403"`
注意: 最初は `DetectionOnly` で誤検知を確かめます。誤検知は、ルール ID を指定して例外にします。WAF 全体を止めません。
関連: WAF、OWASP CRS、SQL インジェクション

### OWASP CRS
別名: Core Rule Set、CRS
試験: LinuC3SS
要約: ModSecurity で使う、公開されたルールの集まりです。
SQL インジェクション、XSS、パス・トラバーサルなどの攻撃を、広く見ます。要求ごとに点数(異常スコア)を足して、しきい値を超えたら拒否する方式が基本です。しきい値の既定は、版で違うことがあります。
例: Debian 系の `modsecurity-crs` パッケージ
注意: そのまま入れると、正常な要求を止めることがあります。最初は記録だけにして、調整します。
関連: ModSecurity、WAF

### CVSS
別名: Common Vulnerability Scoring System
試験: LinuC3SS
要約: 脆弱性の深刻さを、0.0 から 10.0 の点数にする仕組みです。
0.1〜3.9 が低、4.0〜6.9 が中、7.0〜8.9 が高、9.0〜10.0 が緊急です。基本評価のほかに、現状評価、環境評価があります。版(v3.1、v4.0 など)で点数が違うことがあります。
例: 基本評価 9.8(緊急)の CVE
注意: 点数だけで優先順位を決めません。自分の環境で、その弱点に届くかを見ます。
関連: 脆弱性、CPE

### CPE
別名: Common Platform Enumeration
試験: LinuC3SS
要約: 製品や版を表す名前の形式です。
`cpe:2.3:a:ベンダー:製品:版:…` の形で書きます。CVE(脆弱性の番号)と組み合わせて、どの製品のどの版が影響を受けるかを表します。
例: `cpe:2.3:a:openssl:openssl:3.0.2:*:*:*:*:*:*:*`
注意: 脆弱性の番号ではありません。番号は CVE です。
関連: 脆弱性、CVSS

### Trivy
別名: trivy
試験: LinuC3SS
要約: コンテナのイメージ、ファイル、リポジトリ、設定ファイルを調べる、オープンソースのスキャナーです。
`trivy image`、`trivy fs`、`trivy repo`、`trivy config` で対象を選びます。既知の脆弱性、設定の不備、埋め込まれた秘密を見つけます。`--severity` で表示を絞り、`--exit-code 1` で見つかったときに失敗させます。
例: `trivy image --severity HIGH,CRITICAL --exit-code 1 myapp:1.0`
注意: 脆弱性のデータベースは毎日更新されます。古いデータベースでは、新しい脆弱性を見逃します。
関連: 脆弱性スキャン、SBOM

### ZAP
別名: ZAP by Checkmarx、OWASP ZAP
試験: LinuC3SS
要約: Web アプリの脆弱性を調べる、オープンソースの診断ツールです。旧 OWASP ZAP です。
プロキシとして通信を見る「パッシブスキャン」と、調べる要求を送る「アクティブスキャン」があります。2023 年 8 月に OWASP のプロジェクトでなくなり、Checkmarx の支援を受けるコミュニティのプロジェクトです。
例: `zap-baseline.py -t https://staging.example.test -r report.html`
注意: アクティブスキャンは、データを変えたり負荷をかけたりすることがあります。自分が管理するか、許可を得た検証環境にだけ行います。
関連: 脆弱性スキャン、SQL インジェクション

## OS の守り

### SELinux
別名: AppArmor
試験: LinuC102、Docker
要約: プロセスがアクセスできるものを、ラベルで強制的に制限する仕組みです。
Linux で、プロセスが触れるファイルや操作を、細かいルールで制限する仕組みです(強制アクセス制御)。root で動くプロセスでも制限できます。
例: `getenforce`、`ls -Z`、`restorecon -Rv /var/www`、`setsebool -P httpd_can_network_connect on`
注意: 困ったからといって無効にせず、ラベルや boolean を直します。
関連: root

### ケーパビリティ
別名: capabilities
試験: Docker、K8s
要約: root の権限を細かく分けたものです。
root の強い権限を、細かい単位(ネットワークの設定、低い番号のポートの使用など)に分けたものです。コンテナでは、すべて外して(`drop: ALL`)、必要なものだけを足すのが安全です。
例: `CAP_NET_BIND_SERVICE`(1024 未満のポート)、`docker run --cap-drop ALL --cap-add NET_BIND_SERVICE`
注意: `--privileged` はほぼすべてのケーパビリティを与えるので、原則として使いません。
関連: root、最小権限の原則

### chroot
試験: LinuC202
要約: プロセスから見えるルートディレクトリを、別の場所に替える仕組みです。
プロセスにとっての `/` を、指定したディレクトリに替えます。BIND などのサービスを、その中に閉じ込めると、乗っ取られても外のファイルに届きません。
例: `named -t /var/named/chroot -u named`、Red Hat 系の `named-chroot.service`
注意: chroot だけでは完全な隔離にならないので、root 以外のユーザーで動かす設定と合わせます。
関連: BIND

### root_squash
別名: all_squash、no_root_squash
試験: LinuC202
要約: NFS で、クライアントの root を匿名のユーザーに変えるオプションです。
NFS のサーバーで、クライアントの root(UID 0)を、匿名のユーザー(`nobody` など)に変えるオプションです。既定で有効です。すべてのユーザーを匿名にするのは `all_squash`、root をそのまま扱うのは `no_root_squash` です。
例: `/srv/share 192.168.1.0/24(rw,root_squash)`
注意: `no_root_squash` は、クライアントの root が、サーバーのファイルを自由に書き換えられるので、必要なときだけ使います。
関連: NFS

### 強制アクセス制御
別名: MAC、Mandatory Access Control
試験: LinuC3SS
要約: 管理者が決めたルールで、持ち主や root でも変えられないアクセスの制限です。
通常のファイルの権限は、持ち主が変えられます(任意アクセス制御)。強制アクセス制御は、ルールを管理者が決め、root のプロセスでも、ルールで許されないことはできません。Linux では SELinux と AppArmor があります。
例: SELinux(Red Hat 系で既定)、AppArmor(Ubuntu で既定)
注意: 通常の権限(DAC)とは別に判定されます。両方が許したときだけ、アクセスが通ります。
関連: SELinux、最小権限の原則

### セキュリティコンテキスト
別名: SELinux コンテキスト、SELinux ラベル
試験: LinuC3SS
要約: SELinux が、プロセスやファイルに付けるラベルです。
`ユーザー:ロール:タイプ:レベル` の形で、通常は、**タイプ**を見ます。ポリシーが「このタイプのプロセスは、このタイプのファイルを読める」と決めています。表示には `-Z` オプションを使います。
例: `ls -Z /var/www/html`、`ps -eZ`、`restorecon -Rv /var/www/html`
注意: `mv` は元のラベルのまま、`cp` は置き先のラベルになります。移したあとにアクセスできないときは、ラベルを疑います。
関連: SELinux、拡張属性

### SELinux ブール値
別名: ブール値、setsebool
試験: LinuC3SS
要約: SELinux のポリシーを、オンとオフで切り替えるスイッチです。
よくある許可の切り替え(Web サーバーが外へ接続するのを許す、など)を、ルールを書かずに行えます。`getsebool -a` で一覧を見て、`setsebool -P` で恒久的に設定します。
例: `getsebool -a | grep httpd`、`setsebool -P httpd_can_network_connect on`
注意: `-P` を付けない設定は、再起動で元に戻ります。
関連: SELinux、セキュリティコンテキスト

### AVC 拒否
別名: AVC、type=AVC
試験: LinuC3SS
要約: SELinux が、アクセスを拒否したときの記録です。
`/var/log/audit/audit.log` に `type=AVC` の行として残ります。`scontext` が操作したプロセス、`tcontext` が対象、`permissive=0` なら本当に拒否されたことを表します。
例: `ausearch -m AVC -ts recent`、`audit2allow -w`
注意: `dontaudit` のルールが記録を隠すことがあります。記録がないのに拒否されるときは、`semodule -DB` で見えるようにします。
関連: SELinux、監査ログ

### AppArmor プロファイル
別名: aa-genprof、aa-logprof
試験: LinuC3SS
要約: AppArmor で、プログラムごとにできることを、パスで書いたものです。
`/etc/apparmor.d/` に置きます。モードは enforce(拒否して記録)と complain(記録だけ)です。`aa-genprof` で作り、`aa-logprof` で育てます。
例: `aa-status`、`aa-complain /usr/sbin/myapp`、`apparmor_parser -r /etc/apparmor.d/usr.sbin.myapp`
注意: ファイルを書き換えただけでは、カーネルの内容は変わりません。`apparmor_parser -r` で読み込み直します。
関連: 強制アクセス制御、SELinux

### seccomp
別名: SECCOMP_MODE_FILTER、SystemCallFilter
試験: LinuC3SS
要約: プロセスが呼べるシステムコールを、制限する仕組みです。
モードは、`SECCOMP_MODE_DISABLED`、`SECCOMP_MODE_STRICT`、`SECCOMP_MODE_FILTER` の 3 つです。フィルタは BPF プログラムで書きます。systemd では `SystemCallFilter=` で設定します。
例: `grep Seccomp /proc/self/status`、`SystemCallFilter=~@privileged`
注意: 一度付けたフィルタは外せず、子プロセスに引き継がれます。
関連: システムコール、ケーパビリティ

### NoNewPrivileges
別名: no_new_privs
試験: LinuC3SS
要約: プロセスが、新しい権限を得るのを禁止する設定です。
systemd では `NoNewPrivileges=yes` と書きます。`setuid` のビットや、ファイルの Capability によって、権限が上がらなくなります。
例: `NoNewPrivileges=yes`、`AmbientCapabilities=CAP_NET_BIND_SERVICE`
注意: すでに持っている Capability を外す設定ではありません。外すのは `CapabilityBoundingSet=` です。
関連: ケーパビリティ、最小権限の原則

### AIDE
別名: Advanced Intrusion Detection Environment
試験: LinuC3SS
要約: ファイルの状態を記録しておき、あとで比べて、改ざんを見つける道具です。
`aide --init` で正常な状態を記録し、`aide --check` で今の状態と比べます。比べる項目(権限、所有者、サイズ、ハッシュ値)は `aide.conf` に書きます。
例: `aide --init`、`aide --check`、`aide --update`
注意: 記録も改ざんの対象です。読み取り専用の媒体や別のサーバーに置きます。感染したあとで記録を作ると、その状態が正常になります。
関連: IDS、ClamAV

### ClamAV
別名: clamscan、freshclam
試験: LinuC3SS
要約: オープンソースのウイルス対策ソフトです。ファイルをシグネチャと照らし合わせて調べます。
`freshclam` でシグネチャを更新し、`clamscan`(または常駐の `clamd` に調べさせる `clamdscan`)で調べます。終了コードは、0 が見つからない、1 が見つかった、2 がエラーです。
例: `clamscan -r --infected --move=/var/quarantine /srv/uploads`
注意: シグネチャにない新しいものは見つけられません。`--remove` は戻せないので、最初は `--move`(隔離)にします。
関連: YARA、AIDE

### YARA
別名: yara
試験: LinuC3SS
要約: 文字列やバイトの並びの規則を自分で書いて、ファイルを探す道具です。
規則は `strings` と `condition` で書き、`yara -r 規則ファイル ディレクトリ` で調べます。マルウェアの調査でよく使います。
例: `yara -r rules.yar /srv/uploads`、`yara -s rules.yar sample.bin`
注意: 条件が広すぎると、正常なファイルまで合います。正常なファイルの集まりで試してから使います。
関連: ClamAV、AIDE

### XCCDF
別名: OVAL、Extensible Configuration Checklist Description Format
試験: LinuC3SS
要約: 設定の基準(ルールとプロファイル)を、機械で読める形で書く形式です。
SCAP の仕様の 1 つです。システムの状態を調べる手順は、OVAL という言語で書きます。OpenSCAP は、この 2 つが入ったデータストリームを読み込んで検査します。
例: `oscap xccdf eval --profile ... ds.xml`
注意: XCCDF は基準、OVAL は検査の手順です。役割を取り違えないようにします。
関連: OpenSCAP、脆弱性スキャン

## Web とメールのセキュリティ

### HSTS
別名: HTTP Strict Transport Security、Strict-Transport-Security
試験: LinuC3SS
要約: 「このサイトは HTTPS だけでつなぐ」と、ブラウザーに一定期間覚えさせる HTTP ヘッダーです。
HTTP でつなぐと書き換えられる攻撃を防ぎます。`max-age` で覚える期間を、`includeSubDomains` で、サブドメインも対象にするかを決めます。
例: `add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;`
注意: 一度覚えさせると取り消しにくいので、最初は短い `max-age` で試します。
関連: TLS、セキュリティヘッダー

### セキュリティヘッダー
別名: CSP、Content-Security-Policy、X-Frame-Options、X-Content-Type-Options、Referrer-Policy
試験: LinuC3SS
要約: ブラウザーに、安全な動きを指示するために、Web サーバーが返す HTTP ヘッダーの総称です。
CSP は読み込める取得元を制限し、`X-Frame-Options` は iframe への埋め込みを制限します。`X-Content-Type-Options: nosniff` は MIME スニッフィングを止め、`Referrer-Policy` は参照元の送り方を決めます。
例: `curl -sI https://example.com`
注意: nginx の `add_header` は、下の階層に 1 つでもあると、上の階層のものが引き継がれません。
関連: HSTS、HTTP

### SPF
別名: Sender Policy Framework
試験: LinuC3SS
要約: そのドメインのメールを送ってよいサーバーを、DNS の TXT レコードに書いておく仕組みです。
受信側は、メールを送ってきたサーバーの IP アドレスが、許可されているかを確かめます。見るのは、封筒の送信元(`MAIL FROM`)です。
例: `"v=spf1 mx ip4:192.0.2.25 -all"`、`dig +short TXT example.com`
注意: メールを転送すると、IP アドレスが変わって、失敗しやすくなります。1 つのドメインに SPF の TXT は 1 つだけです。
関連: DKIM、DMARC

### DKIM
別名: DomainKeys Identified Mail、OpenDKIM
試験: LinuC3SS
要約: メールに電子署名を付け、受信側が、DNS の公開鍵で、改ざんされていないかを確かめる仕組みです。
公開鍵は、`<セレクター>._domainkey.<ドメイン>` の TXT レコードに置きます。OpenDKIM は、Postfix にミルターとしてつないで、署名と検証をするソフトです。
例: `opendkim-genkey -b 2048 -d example.com -s 202611`、`opendkim-testkey -d example.com -s 202611 -vvv`
注意: 秘密鍵が他のユーザーに読めると、なりすましの署名ができます。権限は 600 にします。
関連: SPF、DMARC

### DMARC
別名: Domain-based Message Authentication, Reporting and Conformance
試験: LinuC3SS
要約: SPF と DKIM の結果が、`From:` のドメインと合っているかを見て、失敗したときの扱いを決める仕組みです。
`_dmarc.<ドメイン>` の TXT レコードに、`p=none`、`quarantine`、`reject` と、報告の送り先(`rua`)を書きます。
例: `"v=DMARC1; p=none; rua=mailto:dmarc@example.com"`
注意: いきなり `p=reject` にせず、`p=none` で報告を見てから強めます。SPF や DKIM が成功しても、ドメインが `From:` と合っていないと、DMARC は失敗します。
関連: SPF、DKIM

## DNS のセキュリティ

### KSK
別名: ZSK、鍵署名鍵、ゾーン署名鍵
試験: LinuC3SS
要約: DNSSEC の 2 種類の鍵です。KSK は DNSKEY の組に署名し、ZSK はほかのレコードに署名します。
KSK のハッシュを、DS として親のゾーンに登録します。KSK は長く使い、ZSK は短い周期で替えます。`dnssec-policy default` は、1 つの鍵で両方をする CSK を使います。
例: `dnssec-keygen -a ECDSAP256SHA256 -f KSK -n ZONE example.com`
注意: KSK を替えると、親の DS も替える必要があります。これを忘れると、検証が失敗します。
関連: DNSSEC、トラストアンカー

### NSEC3
別名: NSEC、NSEC3PARAM
試験: LinuC3SS
要約: 「その名前は存在しない」ことを署名で示すレコードです。NSEC3 は、名前をハッシュにして示します。
NSEC は、存在する名前を順につなぐので、ゾーンの名前の一覧を集められます。NSEC3 は、これをしにくくします。ハッシュの設定は NSEC3PARAM が持ちます。
例: `dig example.com NSEC3PARAM +short`
注意: ハッシュの繰り返しの回数は 0 にするのが、今の推奨です(RFC 9276)。
関連: DNSSEC、KSK

### トラストアンカー
別名: trust-anchors
試験: LinuC3SS
要約: DNSSEC の検証の出発点にする、信頼できる鍵(またはそのハッシュ)です。
通常は、ルートゾーンの鍵です。BIND の `dnssec-validation auto;` は、組み込みのルートの鍵を使います。内部のゾーンなどは、`trust-anchors` に、`static-key` や `static-ds` で自分で登録します。
例: `trust-anchors { "corp.example.internal" static-ds 12345 13 2 "…"; };`
注意: `static-*` は自動で追従しません。鍵を交換したら、手で更新します。
関連: DNSSEC、KSK

### dnssec-policy
試験: LinuC3SS
要約: BIND で、DNSSEC の鍵の作成、署名、鍵の交換を、自動にする設定です。
BIND 9.16 以降で使えます。`dnssec-policy default;` を `zone` に書きます。9.18 では、静的なゾーンファイルには `inline-signing yes;` も書きます。
例: `rndc dnssec -status example.com`、`rndc reconfig`
注意: DS を親のゾーンに登録するのは、人の作業です。登録したら `rndc dnssec -checkds` で named に伝えます。
関連: DNSSEC、KSK、BIND
